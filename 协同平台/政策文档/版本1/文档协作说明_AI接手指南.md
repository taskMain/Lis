# 检验中心协同平台 — 文档协作说明与 AI 接手指南

> 版本：v0.1 | 日期：2026-05-13 | 状态：讨论中
>
> **用途**：本文用于帮助后续接手的 AI 快速理解当前需求讨论工作的文档体系、文档关系、写入顺序、写入时机和内容边界。

## 1. 当前工作目标

当前不是直接开发系统，也不是直接输出最终 PRD。

当前工作是基于 `P0功能清单_检验中心协同平台.md`，逐一讨论每个 P0 功能，重新澄清平台功能边界、遗漏功能、异常处理、字段、流程和外部系统边界，并把确认后的内容沉淀到纠正版功能清单中。

讨论时必须遵循一个核心边界：

- 只讨论 **平台功能** 或 **平台应提供的能力**。
- HIS 的医嘱开立、收费、医保结算、退费、医生工作站原生交互，不作为平台功能。

## 3. 推荐接手阅读顺序

后续 AI 接手时，建议按以下顺序阅读：

1. `文档协作说明_AI接手指南.md`
2. `纠正版功能清单_修订原则说明.md`
3. `讨论todo`
4. `纠正版功能清单_检验中心协同平台`
5. `风险_待内部讨论确定.md`
6. `系统实现相关.md`
7. `讨论稿1.md`
8. `P0功能清单_检验中心协同平台.md`
9. `PRD_检验中心协同平台.md`

理由：

- 先读本说明，知道当前协作规则。
- 再读修订原则，明确平台边界。
- 再读 todo，知道讨论进度。
- 再读纠正版，知道哪些已经定稿。
- 再读风险文档，知道哪些当前选择不能直接当作最终无风险结论。
- 再读系统实现相关文档，知道哪些技术和性能问题已暂存等待后续讨论。
- 再读讨论稿，了解正在讨论的中间过程。
- 最后按需回看原始 P0 和 PRD，避免把旧设想误当新结论。

## 4. 写入顺序与时机

### 4.1 初始化讨论功能

当需要从原始 P0 中提取待讨论功能时：

1. 阅读 `P0功能清单_检验中心协同平台.md`。
2. 提取功能编号、功能名称、模块、来源。
3. 写入 `讨论todo`。
4. 初始状态设为 `待讨论`。

如果讨论中发现新增平台功能：

1. 先写入 `讨论todo`。
2. 来源标为 `讨论新增`。
3. 状态标为 `新增待讨论`。
4. 不要直接写入纠正版功能清单正文，除非该新增功能已经完成讨论。

### 4.2 开始讨论某个功能

当用户指定继续讨论某个功能时：

1. 在 `讨论todo` 中将该功能状态改为 `讨论中`。
2. 阅读原始 P0 中该功能的描述。
3. 结合 `纠正版功能清单_修订原则说明.md` 重新校正平台边界。
4. 讨论过程中形成的临时结论、疑问、备选方案，写入 `讨论稿1.md`。

### 4.3 功能讨论过程中

讨论过程中应优先写入 `讨论稿1.md`，不要急于写入纠正版功能清单。

`讨论稿1.md` 适合记录：

- 用户临时判断。
- 尚未完全确认的结论。
- 对原始 P0 的疑问。
- 待确认问题。
- 可能新增的功能点。
- 中间方案对比。

如果发现新增功能，必须同步更新 `讨论todo`。

如果某项当前选择存在明显业务或技术风险，且用户要求后续内部讨论确认，必须同步写入 `风险_待内部讨论确定.md`。

如果讨论进入性能指标、接口实现机制、同步/异步处理、缓存、重试、限流、部署架构等系统实现细节，且用户未要求立即定稿，应写入 `系统实现相关.md`，暂缓深入讨论。

### 4.4 完成一个功能讨论

只有当用户明确认可该功能已经讨论完成，或上下文已形成明确闭环时，才执行：

1. 将 `讨论todo` 中该功能状态改为 `已完成`。
2. 将该功能的正式结论写入 `纠正版功能清单_检验中心协同平台`。
3. 写入内容应参考 `P0功能清单_检验中心协同平台.md` 的文档风格，但必须以修订后的平台边界为准。
4. 如果讨论完成时产生了新增功能，也要确认新增功能是否一起完成；未完成则保留 `新增待讨论`。
5. 如果该功能仍存在内部待确认风险，不应直接写成无条件最终结论；需要在纠正版功能清单中标注遗留问题，并确保 `风险_待内部讨论确定.md` 已登记。

## 5. 各文档写入边界

### 5.1 不建议直接修改的文档

#### `PRD_检验中心协同平台.md`

这是原始完整 PRD，主要作为背景参考。除非用户明确要求修订 PRD，否则不要改。

#### `P0功能清单_检验中心协同平台.md`

这是原始 P0 来源文档。当前工作已经转为“讨论后生成纠正版”，因此不要继续把纠正结论写回原 P0。原 P0 中的内容可以作为讨论素材，但不代表最终结论。

### 5.2 需要持续维护的文档

#### `讨论todo`

这是讨论过程的任务状态源。任何功能状态变化、新增功能、讨论完成，都要更新它。

状态定义：

| 状态 | 含义 |
|------|------|
| `待讨论` | 原 P0 功能，尚未开始详细讨论 |
| `讨论中` | 正在讨论，已有中间结论但未定稿 |
| `已完成` | 已完成讨论，并已写入纠正版功能清单 |
| `新增待讨论` | 讨论中新发现的新功能，尚未开始或尚未定稿 |

#### `讨论稿1.md`

这是讨论草稿，不是最终定稿。用于承接过程性内容。

可以写入：

- 本轮讨论摘要。
- 追问问题。
- 用户回答。
- 临时判断。
- 注意事项。
- 备选方案。
- 未定稿结论。

#### `风险_待内部讨论确定.md`

这是风险和内部待确认事项文档。用于记录“当前已按用户选择暂定，但存在业务/技术风险，需要后续内部确认”的事项。

必须写入：

- 当前讨论选择。
- 当前规则。
- 风险说明。
- 待内部确认问题。

不要把风险事项只留在聊天记录或讨论稿里。只要用户明确要求“风险/待内部讨论确定”，就必须同步写入该文档。

#### `系统实现相关.md`

这是系统实现待讨论事项文档。用于记录当前阶段暂不展开的技术实现类问题。

适合写入：

- 性能指标。
- 接口响应时限。
- 同步/异步处理机制。
- 重试、幂等、限流、缓存等技术机制。
- 部署、架构、扩展性、安全实现细节。

当前阶段优先讨论需求和平台业务边界。除非用户明确要求，否则不要在功能讨论中深入系统实现细节。

#### `纠正版功能清单_检验中心协同平台`

这是最终沉淀文档。只写已经完成讨论的功能。

不要把“讨论中”“可能”“待确认”的内容写成正式功能定义。此类内容应先留在 `讨论稿1.md`。

#### `纠正版功能清单_修订原则说明.md`

这是全局原则文档。只有以下情况才改：

- 平台与 HIS 的职责边界发生变化。
- 条码、项目目录、收费、集成方式等全局规则发生变化。
- 讨论流程或沉淀规则发生变化。

## 6. 纠正版功能清单写作格式

每个完成讨论的功能建议按以下结构写入 `纠正版功能清单_检验中心协同平台`：

```md
### 功能编号 功能名称

| 属性 | 内容 |
|------|------|
| 功能编号 |  |
| 功能名称 |  |
| 所属模块 |  |
| 业务价值 |  |
| 核心用户 |  |
| 平台入口/接口 |  |
| 当前状态 | 已完成讨论 |

#### 功能定位

#### 平台负责

#### 平台不负责

#### 触发条件

#### 前置条件

#### 后置结果

#### 核心字段/数据对象

#### 主流程

#### 异常处理

#### 性能与时效要求

#### 通知与审计要求

#### 平台 vs 外部系统边界

#### 本轮确认结论
```

写作原则：

- 用确定语气写已确认结论。
- 不写“可能”“待确认”“建议后续评估”等未闭环内容。
- 若必须保留风险或未决点，应单独放在该功能末尾的“遗留问题”中，并在 `讨论todo` 备注中体现。
- 功能内容应聚焦平台，不展开 HIS 内部实现。

## 7. 当前已知关键结论

截至 2026-05-13，已形成以下全局结论：

- 平台不负责 HIS 收费、医保结算、退费。
- 平台不负责 HIS 医生工作站原生界面。
- 平台不通过 iframe、弹窗、嵌入式页面接入 HIS。
- HIS 负责开立检验项目，并将已确认可送检的申请传入平台。
- 平台维护以检验中心为主的区域标准项目库。
- HIS 厂商/机构自行维护本地项目到平台标准项目的映射。
- 平台统一生成样本条码。
- 条码粒度是一支物理样本容器一个条码。
- 一个申请单可以生成多个样本条码。
- 一个样本条码可以关联多个检验项目。
- 已发现新增功能：`F-022 样本采集规则与合管规则配置`。
- 已登记风险事项：F-001 平台不做创建申请接口幂等。
- 已登记风险事项：F-001 平台 P0 不做重复申请提醒。
- 已暂存系统实现事项：F-001 创建申请接口性能要求。
