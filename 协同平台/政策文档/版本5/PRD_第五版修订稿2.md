## 1. 功能需求

### 术语说明

以下术语在文档各章节中频繁出现，在此统一定义。后续章节不再重复解释。

| 术语 | 定义 |
|------|------|
| 平台申请单号 | 平台在申请创建成功后生成的唯一标识，用于在平台内定位一笔申请 |
| 机构申请号 | 发起机构本地 HIS/LIS 系统生成的申请编号，用于机构侧识别同一笔申请。在同一发起机构内与平台申请单号一一对应，共同用于重复提交判断 |
| 患者摘要 | 平台为申请查询、详情展示、送出快照、报告追溯和危急值推送保存的患者概要信息；具体信息项由接口设计文档定义 |
| 就诊摘要 | 平台为申请查询、详情展示和业务追溯保存的本次就诊概要信息；具体信息项由接口设计文档定义 |
| 样本条码 | 发起机构采样后生成并打印的条码，贴于样本实物上。不要求全平台唯一，唯一性范围限定为同一发起机构内 |
| 样本主状态 | 表达具体样本轮次在平台主流程中的当前位置，包括待送出、已送出、已接收、检测中、检测完成、已终止流转。由业务动作驱动，不人工修改 |
| 样本轮次 | 同一申请下多次样本流转的顺序编号。申请创建时生成第 1 轮，每次样本重新送检生成下一轮。同一时间只有一个当前流转轮次 |
| 当前流转轮次 | 同一申请下当前正在操作的样本轮次，是送出、接收、检测、报告上传等业务动作的操作对象。历史轮次仅用于追溯 |
| 发起机构 | 提交检验申请的医疗机构，负责开单、采样、送样 |
| 接收方 | 接收样本并完成检验的机构（检验中心/实验室），负责接收、检测、出具报告，并由上传方通过平台对外接口将报告提交至平台 |
| 上传方 | 代表接收方通过平台对外接口向平台提交报告文件、结构化结果（如有）和危急值信息（如有）的接收方机构或其授权系统，是报告和危急值的数据来源方 |
| 平台标准项目编码 | 平台标准检验项目目录中的项目唯一标识，由平台运营人员在项目目录中维护（见 1.12）。申请创建时通过机构项目对照关系从机构项目编码转换而来 |
| 费用状态 | 发起机构提交并可后续通过接口变更的费用相关业务标识，只记录、展示和查询，不阻断平台主流程 |
| 绿色通道 | 发起机构提交的特殊业务识别信息，只作为人工识别和业务核对参考，不改变平台主流程 |
| 项目加急 | 申请项目上的加急标识，只影响项目清单排序、展示和人工识别，不改变样本送出、接收、检测、报告上传和报告发布主流程 |
| 组合项目 | 由多个明细项目组成的一组检验项目，对应业务概念中的"大项目"（见 1.12） |
| 明细项目 | 组合项目下的具体检测项，对应业务概念中的"小项目"（见 1.12） |
| 包 | 平台内用于将同一发起机构的多个样本条码归集为一个业务单元，用于按包送出、按包接收和追溯。不要求线下一定存在实体箱 |
| 流转时间线 | 申请详情中以时间顺序展示的该申请全生命周期事件视图，按样本轮次分组。展示内容见 1.1.14 中“申请详情应内嵌流转时间线”规则 |
| 外部接入系统 | 调用平台对外接口的第三方系统，包括发起机构的 HIS/LIS 系统、接收方的 LIS/中间件系统等。本文档中"通过系统提交""机构系统"等均指外部接入系统通过平台对外接口与平台交互，非平台自身的功能模块 |

### 功能分类说明

本平台的功能分为两大类：

1. **平台页面功能**：平台用户在浏览器页面上可直接操作的能力（如查询申请、创建包、页面送出、报告审核、危急值处理等）。各章节中标注为"页面功能"的规则，均指平台提供的 UI 操作入口。
2. **平台对外接口功能**：平台提供给外部接入系统调用的 API 能力（如创建申请、提交报告、回传检测状态等）。各章节中标注为"对外接口"的规则，均指平台暴露的接口，由外部接入系统调用，平台页面不提供对应的人工操作入口。

同一业务章节可能同时包含页面功能和对外接口功能。各章在功能定位、功能入口等小节中分别说明：哪些能力通过平台页面操作（标注为"平台页面提供"），哪些能力由外部接入系统通过平台对外接口调用（标注为"通过平台对外接口"），仅提供其中一种的明确标注另一种"不提供"。

### 1.1 申请管理

#### 1.1.1 功能定位

申请管理用于接收发起机构通过平台对外接口提交的检验申请，生成平台申请单号，并建立平台申请、机构申请、患者摘要、就诊摘要、平台标准项目编码、样本条码、接收方、费用状态和绿色通道信息之间的关系。

平台不承担开单职责，不作为医生或机构人员的检验申请录入系统。发起机构应在本地 HIS、LIS 或检验系统中完成开单、采样、条码生成和条码打印后，再提交至平台。

#### 1.1.2 角色约定

本文档涉及以下角色，后续各章节引用时不再重复定义：

| 角色 | 定义 | 典型职责 |
| ---- | ---- | ---- |
| 发起机构 | 提交检验申请的医疗机构，负责开单、采样、送样、终止申请和样本重新送检 | 创建申请、送出样本、终止申请、样本重新送检 |
| 发起机构用户 | 发起机构内经权限系统授权的平台业务用户，可在本机构权限范围内查看本机构相关申请、样本、报告、通知和项目对照，并通过平台页面执行发起机构侧业务动作 | 查询申请、查看报告、查看流转追踪、查看项目对照、页面创建包、页面送出、页面终止申请、页面发起样本重新送检 |
| 接收方 | 接收样本并完成检验的机构（检验中心/实验室） | 接收样本、检测、出具报告并由上传方通过平台对外接口提交、审核发布报告、危急值处理 |
| 接收方用户 | 接收方的普通业务用户 | 查询提交给本接收方的申请和包 |
| 接收方检验人员 | 接收方具备检验和危急值处理权限的用户 | 接收样本、处理危急值 |
| 接收方管理人员 | 接收方具备管理权限的用户 | 报告审核、报告版本追溯、异常处理登记 |
| 平台运营人员 | 平台运营方的管理员用户，按权限范围跨机构执行运维和兜底操作 | 项目目录维护、项目对照维护、报告作废兜底处置、跨机构查询排查 |
| 接收方人员 | 接收方用户、接收方检验人员和接收方管理人员的统称，用于通知对象等不需要细分权限点的场景 | 接收方范围内的业务查看、处理和通知接收 |
| 业务用户 | 发起机构用户、接收方用户和接收方检验人员的统称，区别于具备管理权限的接收方管理人员和平台运营人员 | 查询申请、查看当前有效报告、日常业务操作 |

各角色的具体权限点、角色分配和数据范围由统一权限系统定义，本 PRD 仅在业务规则中说明操作需要哪些角色参与。

#### 1.1.3 功能入口

1. 平台仅支持外部接入系统通过平台对外接口创建申请。
2. 平台页面不提供正常业务下的人工补录申请入口。
3. 平台页面提供申请查询、明细查看、终止申请、流转追踪、异常排查和操作留痕查看能力。

#### 1.1.4 申请创建规则

1. 创建申请时必须提供样本条码。
2. 申请创建时，一个平台申请只能提交一个原始样本条码，并生成第 1 轮样本流转。
3. 同一发起机构内，一个样本条码一旦绑定到某平台申请，即不可用于创建其他平台申请，该条码与申请的绑定关系持续有效，不允许再绑定到其他平台申请；即使申请终止，也不释放用于创建新申请（见 1.1.10.9）。同一平台申请内，允许不同样本轮次沿用同一样本条码。
4. 不同发起机构之间允许存在相同样本条码。
5. 一个平台申请可以包含多个平台标准项目编码。
6. 平台维护标准检验项目目录和机构项目对照，用于将机构项目编码转换为平台标准项目编码。
7. 创建申请成功后，平台生成平台申请单号。
8. 创建申请成功后，申请状态为有效，第 1 轮样本成为当前流转轮次，样本主状态进入待送出。

#### 1.1.5 字段类别

创建申请时，PRD 层面要求覆盖以下信息类别；具体对接信息项由接口设计文档另行定义。

1. 发起机构信息。
2. 机构申请号。
3. 原始样本条码。
4. 患者摘要。
5. 就诊摘要。
6. 机构项目编码清单、项目加急标识及转换后的平台标准项目编码清单。
7. 接收方。
8. 费用状态。
9. 绿色通道信息。
10. 备注或扩展信息。

#### 1.1.6 关键校验规则

1. 必填信息不能为空。
2. 同一发起机构内，样本条码不可重复绑定多个不同平台申请。
3. 不同发起机构允许使用相同样本条码。
4. 机构项目编码必须存在启用的机构项目对照，并映射到启用的平台标准项目。
5. 接收方必须在发起机构允许提交的接收方范围内。
6. 终止申请后，原样本条码在同一发起机构内不可用于创建新的平台申请。
7. 平台不校验项目与患者年龄、性别、病区、床号等医学或院内业务规则冲突。

#### 1.1.7 重复提交处理

平台以发起机构、机构申请号、样本条码作为重复提交判断的主要依据。

1. 如果重复提交的发起机构、机构申请号、样本条码和核心业务字段一致，平台不创建新申请，返回已有平台申请单号，不视为错误请求。
2. 如果机构申请号相同但样本条码不同，平台拒绝创建，并提示重复申请号但条码不一致。
3. 如果同一发起机构内样本条码相同但机构申请号不同，平台拒绝创建，并提示条码已被占用。
4. 如果机构申请号和样本条码相同，但核心业务字段不一致，平台拒绝创建，并提示重复提交内容与原申请不一致。

核心业务字段定义见 1.1.8。

#### 1.1.8 申请字段修改

申请创建成功后，平台不支持修改核心业务字段。

核心业务字段包括：

1. 发起机构。
2. 机构申请号。
3. 样本条码。
4. 患者唯一标识，或患者摘要关键信息（具体信息项由接口设计文档定义）。
5. 就诊摘要关键信息（具体信息项由接口设计文档定义）。
6. 平台标准项目编码清单。
7. 接收方。
8. 样本类型及其他影响送检、接收和检测判断的信息（具体信息项由接口设计文档定义）。

核心业务字段不一致的判断以平台保存的申请创建快照为准；患者摘要、就诊摘要和样本类型等字段的具体比对项由接口设计文档定义，但不得影响本章节中"创建后不可修改、重复提交不一致则拒绝"的业务规则。

核心业务字段同时作为重复提交判断依据（见 1.1.7）。

如机构发现核心业务字段错误，应终止原申请，再由外部接入系统通过平台对外接口重新提交新的申请并使用新的样本条码。申请已经送出、接收、检测或上传报告后，不允许通过修改申请字段修正业务错误，也不通过回退样本主状态修正业务错误，应根据当前阶段进入终止申请、样本异常处理、报告作废或报告上传等后续处理。

#### 1.1.9 样本条码、轮次、接收定位与重新送检

本条约定申请维度下的条码概念，避免后续章节混淆：

- **原始样本条码**：申请创建时提交的条码，属于申请的固定属性，创建后不变。
- **当前样本条码**：当前流转轮次所使用的条码。可能与原始样本条码相同（沿用），也可能不同（重新送检时使用了新条码）。
- **新样本条码**：重新送检时如果机构不沿用原条码，则为新轮次指定的条码，受同申请内条码唯一性约束。

样本条码不要求全平台唯一，跨申请唯一性范围限定为同一发起机构内。平台通过样本轮次区分同一申请下多次样本流转。

1. 申请创建时，平台按"发起机构 + 样本条码"校验该条码是否已绑定到其他平台申请。
2. 同一发起机构内，一个样本条码一旦绑定到某平台申请，即不可用于创建其他平台申请，该条码与申请的绑定关系持续有效，不允许再绑定到其他平台申请（见 1.1.4.3 和 1.1.10.9）。
3. 同一平台申请内，允许不同样本轮次沿用同一样本条码，也允许重新送检时使用新的样本条码。
4. 首次申请创建生成第 1 轮样本流转；每次样本重新送检生成下一轮样本流转。
5. 样本轮次应能在同一申请内唯一识别、排序和追溯；具体轮次展示格式由产品和设计方案确定。
6. 同一申请同一时间只能存在一个当前流转轮次。
7. 送出、接收、异常处理、报告上传和报告版本均应关联具体样本轮次。
8. 接收样本时必须能明确接收方、发起机构和样本条码。
9. 平台接收样本时，按发起机构和样本条码定位平台申请；如同一申请下同一条码存在多个历史轮次，平台应定位到当前流转轮次，历史轮次只用于追溯，不参与接收。
10. 如果只能获得样本条码、无法明确发起机构，平台不应自动模糊匹配，应提示无法定位样本。
11. 平台页面按条码逐条接收时，可以通过先选择发起机构、送出记录或包来确定发起机构，再连续录入样本条码。
12. 按包接收时，如包内样本已明确发起机构，平台可根据包内样本关系定位每个条码。包是否允许跨发起机构样本，在样本打包管理章节中定义。

样本重新送检用于同一申请下当前样本因退回样本、样本损毁、无法检测、运输丢失等异常结论不再继续流转时，由发起机构为该申请发起新一轮样本流转。

1. 样本重新送检必须关联一条已存在的异常记录。
2. 异常记录必须属于同一申请、同一发起机构和当前流转轮次。
3. 允许触发重新送检的异常处理结果包括：退回样本、样本损毁、无法检测、运输丢失。
4. 未到货本身不触发样本重新送检；未到货经线下确认为运输丢失并关闭为"运输丢失"处理结果后，允许触发样本重新送检。继续检测、关闭异常不触发样本重新送检。
5. 重新送检可使用新的样本条码，也可沿用原样本条码。
6. 是否允许沿用原样本条码，由发起机构依据本机构采样、条码和质控规则决定；平台仅校验该条码仍归属于同一平台申请，不校验发起机构内部条码复用规则。
7. 重新送检成功后，原轮次进入已终止流转，新轮次样本主状态为待送出，并成为当前流转轮次。
8. 样本重新送检不改变申请状态；申请仍保持有效。
9. 发起机构如不再继续检测，应主动发起终止申请。
10. 样本重新送检支持发起机构通过平台对外接口提交，也支持发起机构用户在平台页面发起。
11. 接收方用户不能代替发起机构发起样本重新送检。
12. 当前版本不提供平台运营人员代发起机构发起样本重新送检的默认业务入口；如后续需要，应作为特殊权限能力另行设计。
13. 样本重新送检优先通过平台申请号定位申请。为兼容外部接入系统未保存平台申请号的场景，平台支持通过发起机构与样本条码的组合定位原申请，但定位结果必须唯一，否则拒绝重新送检。具体对接方式由接口设计文档定义。

#### 1.1.10 终止申请

终止申请用于停止申请后续业务流转。平台统一使用终止申请，不再单独设计独立的取消流程；样本未送出前的终止，作为终止申请的一种业务类型记录为未送出取消。

1. 发起机构可在申请创建后的任意阶段发起终止申请。
2. 终止申请支持发起机构通过平台对外接口触发，也支持发起机构用户在平台页面触发。
3. 终止申请提交后在平台内立即生效，申请状态变为已终止。
4. 终止申请按申请整体生效，一个申请下存在多个检验项目时，终止申请即表示该申请下全部项目停止后续流转。
5. 平台不支持申请内项目级部分终止。
6. 终止申请不回退样本主状态，不删除或回退已经发生的送出、接收、检测、报告、危急值和推送事实。
7. 终止申请后，不允许继续打包、送出、接收、检测推进、上传报告、审核发布报告、发起新的报告或危急值推送，以及处理异常记录。
8. 终止申请后，原申请不可恢复为有效。
9. 终止申请后，原样本条码在同一发起机构内不可再次创建新的平台申请。
10. 终止申请后，不支持将已终止申请下的样本自动关联到新的申请。
11. 发起机构如需在已终止申请后继续检测，应重新提交新的申请，并使用新的样本条码；样本重新送检仅适用于申请仍有效的异常后续处理，不适用于已终止申请。
12. 终止申请时必须记录终止原因、终止时间、终止发起方、操作来源（人工/系统）、终止时样本主状态、终止时报告状态摘要。
13. 终止原因从平台预置枚举中选择（后续版本可扩展枚举值）。
14. 当前版本终止原因包括：申请信息错误、患者信息变更、不再需要检测、重复申请、费用或结算原因、其他。
15. 选择"其他"时，终止说明必填；其他终止原因的终止说明可选填写。
16. 平台页面触发终止时，应提示终止影响，包括整单终止、原样本条码不可复用、后续业务动作被阻断、已发布报告将自动作废、未发布报告将自动标记为失效。
17. 接收方用户不能代替发起机构终止申请，只能根据申请已终止状态停止后续处理。在接收环节检测到申请已终止时，直接拦截并记录拦截原因，样本不进入已接收。
18. 当前版本不提供平台运营人员代发起机构终止申请的默认业务入口；如后续需要，应作为特殊权限能力另行设计。
19. 样本重新送检属于申请有效时的异常后续处理，不纳入终止申请流程；已终止申请不允许发起样本重新送检。
20. 终止申请生效后，平台自动联动处理关联报告：
    - 当前有效报告 → 系统自动标记为"已作废"（作废原因=终止申请，触发来源=终止申请联动）
    - 未发布报告（待审核、审核不通过）→ 系统自动标记为"已失效"
    - 联动处置立即执行，不依赖人工操作
    - 已替代、已废弃、已作废等历史版本不再处理

终止申请涉及两个独立概念，需区分：

- **终止类型**：由系统根据终止发生时样本所处的阶段自动判定，不由发起机构选择。用于记录终止时申请所处的业务阶段，决定后续阻断范围。
- **终止原因**：由发起机构从平台预置枚举中选择，表达业务上为何终止。当前版本包括申请信息错误、患者信息变更、不再需要检测、重复申请、费用或结算原因、其他。选择"其他"时终止说明必填；其他终止原因的终止说明可选填写，用于补充具体原因。

终止类型根据终止发生时所处阶段记录，包括：

| 终止类型 | 适用阶段 | 主要影响 |
| ---- | ---- | ---- |
| 未送出取消 | 样本仍为待送出 | 不允许继续打包、送出 |
| 送出后终止 | 样本已送出但未接收 | 不回到待送出，不允许接收，送出记录保留 |
| 接收后终止 | 样本已接收但未进入检测 | 不回退接收事实，不允许进入检测 |
| 检测中终止 | 样本处于检测中 | 不回退检测事实，不允许继续推进检测完成或上传报告 |
| 检测完成后终止 | 样本已检测完成且从未发布过报告 | 不回退检测完成，不允许继续上传、审核或发布报告 |
| 报告后终止 | 已存在已发布或已替代的报告版本 | 不删除历史报告，系统自动将当前有效报告作废（如有），无当前有效报告时仅记录，不作废 |

> **终止类型判定规则**：当样本主状态为检测完成时，系统需额外判断是否存在已发布或已替代的报告版本——若存在，则判定为"报告后终止"；若从未发布过报告，则判定为"检测完成后终止"。
>
> **注意**："接收后终止"覆盖样本已接收但尚未进入检测阶段的终止场景。检测侧的样本问题应在终止前通过异常处理流程解决；终止申请生效后不允许继续处理异常记录。

#### 1.1.11 申请状态

申请状态只表达平台申请本身是否仍然有效。

| 状态 | 说明 |
| ---- | ---- |
| 有效 | 申请创建成功后进入该状态 |
| 已终止 | 终止申请成功后进入该状态 |

样本流转状态不写入申请状态，由当前流转轮次的样本主状态单独表达。样本主状态包括：待送出、已送出、已接收、检测中、检测完成、已终止流转。

报告状态、异常状态、推送状态分别由报告、异常和推送相关对象承载。平台不设置申请已完成状态；检测完成、报告发布等结果由样本和报告状态体现。申请已终止是申请维度的总控状态，不替代样本、报告、异常、危急值和推送对象自身状态。

#### 1.1.12 多项目申请与报告关系

1. 一个平台申请可以包含多个平台标准项目编码。
2. 平台申请下可以存在多个历史样本轮次，但同一时间只能存在一个当前流转轮次。
3. 样本送出、样本接收、样本异常和样本主状态按具体样本轮次处理。
4. 同一申请下只维护一个报告业务对象。
5. 同一申请下多次上传报告时，应作为同一报告业务对象的不同版本处理，每个报告版本必须关联具体样本轮次和样本条码。
6. 任一时间同一申请最多只有一份当前有效报告。
7. 报告上传不强制声明报告覆盖项目范围。
8. 平台不基于项目范围判断报告完整性、项目完成状态、项目重复覆盖或项目漏报。
9. 报告查询时应展示报告对应的申请、样本轮次、样本条码、上传时间、版本状态和当前有效状态。
10. 终止申请按整单处理，不支持仅终止申请中的部分项目。
11. 发起机构如需取消或调整部分项目，应重新提交新的申请，不通过项目级部分终止。
12. 项目加急是项目级属性，一个申请可以同时包含加急项目和普通项目。
13. 项目加急只影响项目清单排序、展示和人工识别，不改变样本送出、接收、检测、报告上传和报告发布主流程。
14. 申请级可汇总展示是否含加急项目，但含加急项目不表示整单所有项目均加急。

#### 1.1.13 费用状态与绿色通道

费用状态和绿色通道只记录、展示和查询，不阻断平台主流程。绿色通道与项目加急相互独立。

1. 平台不负责收费、退费、医保结算和费用规则判断。
2. 机构创建申请时可以提供费用状态和绿色通道信息。
3. 费用状态枚举包括：已收费、未收费、无需收费、未知。
4. 绿色通道信息包括：是否绿色通道、绿色通道原因或说明。
5. 后续如需扩展费用状态或绿色通道原因，由平台字典配置或后续版本规则定义。
6. 未收费或未知费用状态不阻断申请创建。
7. 未收费或未知费用状态不阻断样本打包、送出、接收、检测、报告上传和报告发布。
8. 绿色通道信息只作为人工识别和业务核对参考，不改变平台主流程。
9. 绿色通道不自动表示项目加急，项目加急也不自动表示绿色通道。
10. 费用状态和绿色通道在申请创建后允许由发起机构通过平台对外接口发起变更，平台页面不提供变更入口；具体对接方式由接口设计文档定义。
11. 每次变更应记录变更留痕（变更前值、变更后值、变更时间、调用系统），并可在申请详情中查看变更历史。

#### 1.1.14 申请查询与明细展示

平台应支持申请列表查询和申请详情查看。

申请列表至少支持以下查询条件：

1. 平台申请单号。
2. 机构申请号。
3. 发起机构。
4. 样本条码。
5. 患者摘要关键字。
6. 申请时间。
7. 申请状态。
8. 样本主状态。
9. 接收方。

申请列表支持按样本主状态展示当前查询结果中各状态的申请数量（如待送出 N、已送出 N、已接收 N、检测中 N、检测完成 N、已终止流转 N）。不提供排行、趋势和汇总分析。

权限规则：

1. 发起机构用户只能查询本机构发起的申请，或按授权范围查询与本机构相关的申请。
2. 接收方用户可查询提交给本接收方的申请。
3. 平台运营人员可按权限查询全平台申请。

详情展示：

1. 申请详情应展示申请基础信息、患者摘要、就诊摘要、原始样本条码、当前流转轮次、当前样本条码、项目清单、是否含加急项目、接收方、费用状态、绿色通道、申请状态、当前样本主状态和关键时间。
2. 申请详情应展示包、送出、接收、异常、报告和推送的摘要信息；如某类业务尚未发生，应展示为空或无记录。
3. 申请已终止时，申请详情应展示终止类型、终止原因、终止时间、终止发起方、操作来源（人工/系统）、终止时样本主状态、终止时报告状态摘要、终止影响摘要，以及关联报告处置结果（已发布报告已作废或未发布报告已失效）。
4. 申请详情应展示样本轮次历史，包括轮次号、样本条码、样本主状态、是否当前流转轮次、异常结论、关联异常记录、送出/接收摘要和关联报告版本。
5. 申请详情应内嵌流转时间线，按样本轮次分组展示。每个轮次块展示轮次号、样本条码、是否当前流转轮次，以及该轮次的生命周期事件（包括：申请创建/样本重新送检、加入包/移出包、送出、补送、送出撤回、接收、异常、报告上传/审核/发布/作废等）。报告事件挂在产生该报告版本的轮次下；因终止申请联动产生的报告作废事件，仍挂在被作废报告版本对应的样本轮次下。终止申请作为申请级事件独立展示于轮次分组之外，申请级通知事件（终止申请、异常关闭、报告发布、危急值发布、报告作废、包内样本因终止被阻断）作为通知类事件独立展示，不替代轮次下对应业务事件。每个事件展示时间、类型、摘要信息，可跳转到对应业务模块查看完整明细。已终止流转的轮次块标注导致该轮次终止流转的业务原因或关联异常处理结果。
6. 申请详情应可展开查看包历史——各样本轮次曾属于哪些包（含当前和历史），以及每次按包送出时的送出快照。包和送出快照默认收起，点击展开后展示。
7. 终止申请拦截记录应在申请详情时间线中展示（拦截时间、拦截原因）。
8. 包、送出、接收、异常、报告和推送的完整明细，应跳转到对应功能模块页面查看。
9. 申请查询不是统计报表，不提供排行、趋势、汇总分析等能力。

项目清单展示规则：

1. 项目清单应展示机构原始项目编码、机构项目名称（如有）、平台标准项目编码、平台标准项目名称、项目类型和是否加急。
2. 项目展示排序应先展示加急项目，再展示普通项目。
3. 同为加急或同为普通时，保持机构提交的项目顺序。
4. 组合项目作为整体参与排序；组合项目下的明细项目跟随组合项目展示，不单独拆出重排。
5. 申请列表和申请详情可汇总展示是否含加急项目。

**流转追溯查询路径：**

常见运维追溯场景的查询路径：

| 场景 | 查询路径 |
|------|---------|
| 样本当前状态 | 申请查询 → 申请详情 → 查看样本主状态和流转时间线 |
| 报告未收到 | 申请查询 → 跳转报告查询 → 查看报告状态和推送结果 |

| 报告版本争议 | 报告查询 → 版本追溯入口 → 查看版本链、替代关系、作废记录 |
| 危急值追溯 | 危急值处理列表 → 查看处理状态和处理记录 |
| 样本异常追溯 | 申请详情时间线 → 跳转异常详情 → 查看处理结果和追加记录 |

当前版本不建设独立的业务运维与追溯查询页面，运维追溯通过上述各业务模块页面完成。

#### 1.1.15 不支持范围

1. 不支持平台生成样本条码。
2. 不支持平台打印样本条码。
3. 不支持页面人工补录申请。
4. 不支持申请内项目级部分终止。
5. 不支持创建后修改申请核心业务字段。
6. 不负责收费、退费、医保结算。
7. 不在申请管理中展开项目目录和机构项目对照维护规则，具体见 1.12。
8. 不在申请管理中定义系统对接细节。

#### 1.1.16 验收标准

1. 能通过平台对外接口创建平台申请，并获得平台申请单号。
2. 平台页面不提供正常业务下的人工补录申请入口。
3. 申请创建时，一个平台申请只能提交一个原始样本条码，并生成第 1 轮样本流转。
4. 同一发起机构内，一个样本条码不能重复绑定多个不同平台申请；同一申请内允许不同样本轮次沿用同一样本条码。
5. 不同发起机构允许存在相同样本条码。
6. 重复提交时，发起机构、机构申请号、样本条码和核心业务字段一致的，平台不创建新申请，并能识别为已有申请。
7. 机构申请号相同但样本条码不同时，拒绝创建并提示重复申请号但条码不一致。
8. 同一发起机构内样本条码相同但机构申请号不同时，拒绝创建并提示条码已被占用。
9. 机构申请号和样本条码相同但核心业务字段不一致时，拒绝创建并提示重复提交内容与原申请不一致。
10. 创建成功后，申请状态为有效，第 1 轮样本成为当前流转轮次，样本主状态为待送出。
11. 申请创建成功后，不允许修改患者、原始条码、项目、接收方等核心业务字段；异常后的继续流转应通过样本重新送检生成新轮次处理。
12. 发起机构可通过平台对外接口或平台页面触发终止申请。
13. 终止申请提交后在平台内立即生效，申请状态变为已终止。
14. 终止申请按整单处理，不支持项目级部分终止。
15. 终止申请不回退样本主状态，不删除或改写已发生的业务事实。
16. 终止申请后阻断后续打包、送出、接收、检测推进、报告上传、报告发布、新推送和异常处理。
17. 终止申请后不可恢复，且同一发起机构内原样本条码不可用于创建新的平台申请。
18. 终止申请后不支持将原样本自动关联到新的申请；如需继续检测，应重新提交新申请并使用新样本条码。
19. 样本重新送检必须关联允许触发重新送检的异常记录，并生成新的样本轮次。
20. 同一申请同一时间只能存在一个当前流转轮次。
21. 样本重新送检可使用新样本条码，也可沿用原样本条码，但必须通过样本轮次区分不同流转历史。
22. 申请详情应展示终止类型、终止原因、终止时间、终止发起方、操作来源（人工/系统）、终止时样本主状态、终止时报告状态摘要、终止影响摘要，以及关联报告处置结果。
23. 终止原因从平台预置枚举中选择；当前版本包括申请信息错误、患者信息变更、不再需要检测、重复申请、费用或结算原因、其他。选择"其他"时终止说明必填，其他终止原因的终止说明可选填写。
24. 平台页面触发终止时，应提示终止影响（整单终止、条码不可复用、后续阻断、已发布报告自动作废、未发布报告自动标记为失效）。
25. 接收方用户不能代替发起机构终止申请或发起样本重新送检，系统应拦截越权操作。
26. 费用状态和绿色通道信息可以记录、展示和查询，但不阻断申请创建、样本送出、样本接收、检测和报告流程。
27. 支持申请列表查询和申请详情查看，并按发起机构、接收方和平台管理权限隔离数据。
28. 申请详情应展示申请基础信息、患者摘要、项目清单、项目加急标识、是否含加急项目、原始样本条码、当前流转轮次、当前样本条码、接收方、费用状态、绿色通道、申请状态、当前样本主状态、样本轮次历史和关键流转摘要。
29. 终止申请生效后，已发布报告自动作废，未发布报告自动标记为已失效。

### 1.2 样本打包管理

#### 1.2.1 功能定位

样本打包管理用于将一个或多个样本条码归集为平台业务包。包是平台内用于样本归集、送出、接收和追溯的业务对象，不要求线下一定存在实体箱。

#### 1.2.2 包内样本机构范围

1. 一个包只能包含同一发起机构的样本。
2. 不允许在同一个包内混装多个发起机构的样本。
3. 包创建后，应记录包所属发起机构。
4. 向包内加入样本时，平台校验样本发起机构必须与包所属发起机构一致。
5. 按包接收时，平台可通过包确定发起机构，再结合包内样本条码定位样本。

#### 1.2.3 入包样本范围

1. 只有申请状态为有效的样本可以加入包。
2. 只有样本主状态为待送出的样本可以加入包。
3. 已终止申请对应的样本不能加入包。
4. 已送出、已接收、检测中、检测完成、已终止流转或已有报告的样本不能加入包。本文档中"已有报告的样本"指报告已上传成功的样本，不论报告当前处于待审核、已发布、已作废等何种状态。
5. 平台向包内加入样本时，应校验样本所属发起机构、申请状态、样本轮次和样本主状态；只有当前流转轮次且样本主状态为待送出的样本可以加入包。

#### 1.2.4 包内样本调整

1. 包处于未送出状态时，允许向包内加入符合入包条件的样本。
2. 包处于未送出状态时，允许从包内移出样本。
3. 包送出后，包内样本关系锁定，不允许继续加入或移出样本。
4. 包内样本调整必须记录调整时间、操作来源（人工/系统）、调整动作和调整前后样本清单摘要。
5. 从包内移出的样本，如申请有效且样本仍为待送出，可继续按条码送出或加入其他符合规则的包。
6. 包内样本调整不改变样本主状态；样本主状态仍由送出、接收、检测等动作驱动。
7. 包内样本的申请被终止后，系统自动将该样本从所有未送出包中移出，并记录自动移出留痕（移出原因=申请已终止联动，触发来源=终止申请联动）。包创建者收到"包内样本因终止被阻断"通知，告知样本已自动移出。自动移出后，包内其他符合条件的样本不受影响，可正常送出。
8. 已终止的样本不允许新加入包（1.2.3.1 已有规则覆盖）。
9. 包内样本全部移出后，若包处于未送出状态，包仍继续存在且状态为有效，可继续加入符合入包条件的样本。包不因样本全部移出而自动作废。

#### 1.2.5 包作废

1. 包未送出前允许作废。
2. 包送出后不允许作废。
3. 包作废后不可恢复有效。
4. 包作废后不允许继续加入、移出或调整样本。
5. 包作废不改变包内样本的申请状态和样本主状态。
6. 包作废后，包内样本如申请有效且样本仍为待送出，可按条码送出或加入其他符合规则的包。
7. 包作废必须记录作废原因、作废时间、操作来源（人工/系统）。
8. 已送出包如果需要撤回，应走送出撤回；如果接收时发现问题，应走接收异常或样本异常处理，不通过包作废处理。
9. 按包送出后发生送出撤回时，原包不恢复编辑，不允许再次基于原包送出。

#### 1.2.6 打包流程属性

1. 打包是可选流程，不是申请创建、样本送出、样本接收、检测和报告的必经流程。
2. 样本可以不打包，直接按条码或申请送出。
3. 样本也可以先加入包，再按包送出。
4. 未打包样本可以正常送出、接收、检测、上传报告和查询追溯。
5. 打包只影响样本归集、按包送出、按包接收和包维度追溯，不改变样本主状态。
6. 包不承载样本流转状态，样本流转状态仍由样本主状态表达。

#### 1.2.7 样本归包唯一性

1. 一个样本同一时间最多属于一个有效未送出包。
2. 同一样本不能同时存在于多个有效未送出包中。
3. 向包内加入样本时，平台应校验该样本当前是否已属于其他有效未送出包。
4. 如果样本已属于其他有效未送出包，平台拒绝加入新包，并提示样本已在其他包中。
5. 样本从原包移出后，如仍满足入包条件，可以加入其他包。
6. 原包作废后，包内样本如仍满足入包条件，可以加入其他包。
7. 包送出后，未撤回样本已进入已送出状态，不允许再加入其他包。
8. 按包送出后被撤回的样本，如样本主状态回到待送出且仍满足入包条件，可以加入新的未送出包。
9. 被撤回样本加入新包时，不改变原包和原送出快照。

#### 1.2.8 包创建入口

1. 支持发起机构通过平台对外接口提交创建包。
2. 支持发起机构用户在平台页面创建包。
3. 包创建时必须明确包所属发起机构。

#### 1.2.9 包查询与明细展示

**包列表查询条件：**

1. 包号。
2. 包所属发起机构。
3. 包状态（有效、已作废）。注：包状态仅表达包本身是否被作废；包是否已送出通过"是否已送出"字段独立表达。有效包在送出前后行为不同——未送出前可编辑、可作废，送出后锁定且不可作废，但两种情况下包状态均为有效。
4. 创建时间范围。
5. 是否已送出。
6. 送出记录号。

**包列表展示字段：**

1. 包号。
2. 包所属发起机构。
3. 包内样本数量。
4. 包状态（有效 / 已作废）。
5. 是否已送出。
6. 创建时间。
7. 最近一次调整时间。

**包详情展示：**

1. 包基础信息：包号、发起机构、状态、创建时间、创建人或调用系统。
2. 当前包内样本清单：样本条码、平台申请号、机构申请号、患者摘要关键字段、加入时间。
3. 包内样本变更记录：调整时间、操作来源（人工/系统）、调整动作（加入/移出）、调整前后样本清单摘要。

**权限规则：**

1. 发起机构用户只能查询本机构发起的包。
2. 接收方用户可查询提交给本接收方的包。
3. 平台运营人员可按权限查询全平台包。

#### 1.2.10 验收标准

1. 能通过平台对外接口或平台页面创建包，并记录包所属发起机构。
2. 一个包只能包含同一发起机构的样本。
3. 不允许在同一个包内混装多个发起机构的样本。
4. 只能将申请有效且样本主状态为待送出的样本加入包。
5. 已终止流转、已送出、已接收、检测中、检测完成或已有报告的样本不能加入包。
6. 同一样本同一时间不能属于多个有效未送出包。
7. 包未送出前允许加入和移出样本，并记录调整留痕。
8. 包送出后包内样本关系锁定，不能继续加入或移出样本。
9. 未送出的包允许作废，作废后不可恢复。
10. 包送出后不允许作废。
11. 包作废不改变包内样本的申请状态和样本主状态。
12. 包作废后，包内样本如仍满足入包条件，可以加入其他包或按条码送出。
13. 打包是可选流程，未打包样本仍可正常按条码或申请送出。
14. 包不承载样本主状态，样本状态仍由送出、接收、检测等动作驱动。
15. 按包送出后发生送出撤回时，原包不恢复编辑，不允许再次基于原包送出。
16. 按包送出后被撤回并回到待送出的样本，如仍满足入包条件，可以加入新的未送出包。
17. 包维度能查询当前样本清单和包内样本变更记录。
18. 能按包号、发起机构、状态、创建时间、是否送出、送出记录号查询包列表。
19. 包列表展示包号、发起机构、样本数量、状态、是否送出、创建时间、最近调整时间。
20. 包详情应展示包基础信息、当前样本清单和包内样本变更记录。
21. 包查询按发起机构、接收方和平台管理权限隔离数据。

### 1.3 样本送出管理

#### 1.3.1 功能定位

样本送出管理用于发起机构确认样本从本机构送出至接收方，形成送出记录和送出快照，并推动样本主状态进入已送出。

#### 1.3.2 送出入口

1. 样本送出只支持按条码/申请送出和按包送出。其中"按条码/申请送出"指不通过包的送出方式，具体包括按样本条码逐个送出和按申请（平台申请号或机构申请号）定位样本后送出。
2. 支持按单个或多个样本条码送出。
3. 支持按平台申请或机构申请定位样本后送出。
4. 支持按包送出。
5. 未打包样本可以按条码或申请送出。
6. 已打包且未送出的样本可以按包送出。

#### 1.3.3 送出样本范围

1. 仅申请有效、当前流转轮次样本主状态为待送出、目标接收方明确的样本允许送出。
2. 申请状态必须为有效。
3. 样本主状态必须为待送出。
4. 样本必须有明确接收方。
5. 已终止申请对应的样本不允许按条码/申请送出，也不允许随包送出。按包送出时如包内存在已终止申请对应的样本，整包送出失败。
6. 已送出、已接收、检测中、检测完成、已终止流转或已有报告的样本不允许再次送出。
7. 送出撤回成功后，当前流转轮次样本主状态回到待送出，满足其他条件时可以再次送出。
8. 未到货后的样本，如经异常处理确认无需终止且样本仍满足送出条件，允许再次送出。

#### 1.3.4 按包送出校验

1. 按包送出时整包校验；任一样本不满足送出条件，则整包不能送出。
2. 按包送出前，平台应校验包状态、包所属发起机构、包内样本清单和每个样本的送出条件。
3. 包内所有样本均满足送出条件时，允许整包送出。
4. 包内任一样本不满足送出条件时，整包送出失败。
5. 包内存在已终止申请对应的样本时，视为存在不满足送出条件的样本，整包送出失败。
6. 平台不自动移除不满足条件的样本。
7. 平台不支持同一包内部分样本送出、部分样本保留未送出。
8. 如包内存在不满足条件的样本，应在包未送出前由用户手动调整包内样本后再送出。

#### 1.3.5 送出记录与送出快照

1. 送出记录是一次送出动作形成的业务凭证，用于表达谁在什么时间、将哪些样本、以什么方式送往哪个接收方。
2. 一次送出动作生成一条送出记录。
3. 按条码/申请送出时，一次送出中包含的一个或多个样本生成同一条送出记录。
4. 分多次送出的样本生成多条送出记录，平台不因接收方相同、时间接近或样本同批而自动合并送出记录。
5. 按包送出时，一次按包送出生成一条送出记录，并关联送出时的包。
6. 送出记录应包含送出记录号。
7. 送出记录应记录送出方式，包括按条码/申请送出、按包送出。
8. 送出记录如属于补送，应单独记录补送业务类型，并关联原按包送出记录。
9. 送出记录应记录发起机构、接收方、送出时间、操作来源（人工/系统）。
10. 送出记录应记录本次送出的样本清单。
11. 每个样本的送出快照应至少包含平台申请号、机构申请号、样本条码、患者摘要关键字段、平台标准项目编码清单。
12. 按包送出时，送出记录应记录包号和送出时包内样本清单。
13. 补送记录应关联原按包送出记录，用于追溯本次补送对应的原送出。
14. 送出记录可记录送出备注。
15. 送出记录后续应展示送出记录状态、业务标签、样本级处理结果和接收侧处理结果摘要。
16. 送出快照形成后，不因后续包调整、患者摘要变化或其他对象变化而改变。当前版本不定义送出记录和送出快照的自动归档或自动清理规则；送出记录存在期间，送出快照应随送出记录一并保留。

#### 1.3.6 送出后的状态变化

1. 样本送出成功后，样本主状态由待送出变为已送出。
2. 按条码/申请送出时，送出记录直接关联样本清单。
3. 按包送出时，送出记录关联包号和送出时包内样本清单。
4. 按包送出成功后，包应记录已用于送出。
5. 包已用于送出后，包内样本关系锁定，不允许继续加入或移出样本。
6. 包已用于送出后，不允许作废包。
7. 包不承载样本主状态，样本主状态仍由样本对象表达。
8. 送出记录承载本次送出动作和送出快照，包只作为送出时的归集对象和追溯维度。

#### 1.3.7 送出撤回

1. 送出撤回用于处理送出登记后、接收前发现本次送出登记不应继续成立的场景，包括实物未实际送出、送错样本、多登记样本、误操作送出等。
2. 送出撤回只适用于样本主状态为已送出且尚未被接收的样本。
3. 已接收、检测中、检测完成或已有报告的样本不能撤回送出。
4. 撤回动作针对送出记录中的样本明细，不直接修改原送出快照。
5. 按条码/申请送出和按包送出均允许撤回一条送出记录中的一个或多个未接收样本。
6. 如果撤回样本不是本次送出记录中的全部样本：剩余未撤回样本中仍有未产生接收结果且未被终止申请拦截的，送出记录状态保持为已送出；剩余样本均已产生接收结果或已被终止申请拦截的，状态变为接收完成。通过有撤回标签和样本明细表达撤回事实。
7. 如果撤回本次送出记录中的全部样本，该送出记录状态为全部撤回。
8. 撤回成功的样本主状态回到待送出。
9. 未撤回样本继续处于已送出，并继续等待接收侧处理。
10. 已撤回样本不能再基于原送出记录接收。
11. 撤回不删除原送出记录，不修改原送出快照，不表示历史送出登记不存在。
12. 撤回成功的样本满足送出条件时，可以再次按条码/申请送出，或加入新的未送出包后按新包送出。
13. 重新送出必须生成新的送出记录，不修改或复用原送出记录。
14. 按包送出发生样本撤回时，撤回的是样本在本次送出记录中的送出关系，不是从原包中移除样本。
15. 按包送出发生部分样本撤回时，原包、原包快照和原送出快照均不改变。
16. 按包送出发生整包撤回时，本质是撤回该送出记录下全部未接收样本；原包仍保留已用于送出的历史标记，不恢复编辑，不允许再次基于原包送出。
17. 送出撤回必须记录撤回原因、撤回时间、操作来源（人工/系统）、撤回样本清单。

#### 1.3.8 送出补送

1. 补送不是独立主流程，是按包送出后的限定后续动作。
2. 补送用于原按包送出记录整体有效，但发现有应随该包送出的样本未包含在原包或原送出记录中的场景。补送关联的是"同一批次应一起送出的样本"这一业务关系，不依赖于线下是否存在实体箱；包本身仍是平台业务归集单元。
3. 按条码/申请送出时如漏送样本，漏送样本仍为待送出，直接再次普通送出即可，不要求使用补送。
4. 补送不向原包追加样本，不修改原包清单，不修改原送出快照。
5. 补送应生成新的送出记录，业务类型标记为补送，并关联原按包送出记录。
6. 补送样本必须满足送出样本范围要求。
7. 补送记录可以按条码/申请形成，也可以通过新的未送出包形成。
8. 接收方按补送记录独立接收补送样本。
9. 原按包送出记录和补送记录应能在追溯中互相关联展示。
10. 补送样本的接收方必须与原按包送出记录的接收方一致，平台校验不一致时拒绝补送。
11. 补送样本的发起机构必须与原按包送出记录或原包所属发起机构一致，平台校验不一致时拒绝补送。
12. 不论补送按条码/申请形成，还是通过新的未送出包形成，均应校验补送样本的接收方和发起机构一致性。
13. 除接收方和发起机构一致性校验外，补送样本还需满足送出样本范围要求（申请有效、样本待送出、接收方明确）。
14. 平台不校验补送样本是否"应该随原包"——这是发起机构业务判断，平台不替代。平台也不校验补送样本与原包内样本的项目、时间等关联性。

#### 1.3.9 送出记录状态、标签与样本明细

1. 送出记录状态用于表达一条送出记录是否仍需要接收侧继续处理，不替代样本主状态。
2. 送出记录状态包括：已送出、接收完成、全部撤回。
3. 送出记录创建成功后，状态为已送出。
4. 送出记录中仍存在未撤回、未形成接收侧处理结果且未被终止申请拦截的样本时，状态保持为已送出。
5. 送出记录中所有未撤回样本均已有接收侧处理结果，或已被终止申请拦截后，状态为接收完成。
6. 送出记录中全部样本均被撤回时，状态为全部撤回。
7. 接收结果包括正常接收、异常接收、未到货。
8. 部分撤回不作为送出记录主状态；部分撤回通过有撤回标签和样本明细表达。
9. 送出记录业务标签用于提示记录内存在特殊情况，不承担流程判断。
10. 送出记录业务标签至少包括：有撤回、有异常、补送。
11. 有撤回标签用于表示送出记录中存在部分样本已撤回，但该记录未达到全部撤回。
12. 有异常标签用于表示送出记录中存在异常接收、未到货或其他接收侧异常结果。
13. 补送标签用于表示该送出记录是原按包送出记录的补送记录。
14. 送出记录内每个样本应保留样本级处理结果，包括待接收、已撤回、已接收、异常接收、未到货。因终止申请被拦截的样本，在送出记录中标记为"拦截（原因：申请已终止）"，不作为样本级接收结果，不生成接收记录，但在送出记录状态结算时视为该样本已不再需要接收侧处理。样本级处理结果仅"未到货"允许后续变更为正常接收或异常接收，变更需记录变更时间、操作人和变更原因；其他处理结果一旦确认不可修改。
15. 单个样本不使用部分撤回或全部撤回描述；单个样本只记录是否已撤回。

#### 1.3.10 验收标准

1. 支持按条码/申请送出样本。
2. 支持按包送出样本。
3. 仅申请有效、样本待送出、接收方明确的样本可送出。
4. 按包送出时整包校验，任一样本不满足条件则整包失败。
5. 送出成功后生成送出记录和不可变送出快照。
6. 送出成功后样本状态进入已送出。
7. 按包送出后包记录已用于送出，包内样本关系锁定。
8. 已送出未接收样本支持按送出记录明细撤回一个或多个样本。
9. 已接收及后续状态样本不能撤回送出。
10. 撤回成功样本回到待送出。
11. 重新送出必须生成新的送出记录，不修改或复用原送出记录。
12. 按包送出发生撤回时，原包不恢复编辑，不允许再次基于原包送出。
13. 按包送出漏样本时支持补送，补送生成新的送出记录并关联原按包送出记录，业务类型标记为补送。补送校验接收方与原按包送出记录一致，发起机构与原按包送出记录或原包所属发起机构一致。
14. 补送记录与原按包送出记录应能双向关联展示。
15. 未到货确认实物仍在机构时，可通过送出撤回（样本回到待送出后重新送出）或补送流程处理。按条码/申请漏送时需先撤回再送出；按包漏送时可选择补送或撤回后重新送出。未到货确认运输丢失时，不通过送出撤回重新送出原轮次，应按样本异常处理规则触发样本重新送检。
16. 送出记录状态包括已送出、接收完成、全部撤回。
17. 部分撤回通过有撤回标签和样本明细表达，不作为送出记录主状态。
18. 送出记录应展示样本级处理结果和接收侧处理结果。
19. 送出快照不因后续包或申请相关信息变化而改变。

### 1.4 样本接收管理

#### 1.4.1 功能定位

样本接收管理用于接收方确认已送出的样本到达接收方，形成接收记录，并推动样本主状态进入已接收或形成异常接收处理结果。

#### 1.4.2 接收入口

1. 样本接收只支持按条码接收和按包接收。
2. 支持按样本条码接收。
3. 支持按包接收。
4. 按条码接收时，必须能明确发起机构和样本条码。
5. 按包接收时，平台根据包和送出记录定位包内样本。
6. 未打包样本可按条码接收。
7. 已按包送出的样本可按包接收，也可在满足规则时按条码逐个接收。
8. 平台应提供"待接收清单"页面：
   - 默认展示状态为"已送出"的送出记录（含部分撤回但仍有待接收样本的记录）。
   - 补送记录作为独立送出记录出现在待接收清单中，业务标签展示为"补送"，并关联原按包送出记录号。
   - 可按送出记录状态筛选：已送出（默认）、接收完成、全部撤回。
   - 可按发起机构、送出时间范围筛选。
   - 列表展示送出记录号、发起机构、送出方式、包号（如有）、待接收样本数量、送出时间。
   - 点击送出记录进入接收详情，进行逐项核对和接收操作。不支持从清单页跨送出记录批量接收。
   - 待接收清单的查询数据同样支持接收方通过平台对外接口获取，具体对接信息项由接口设计文档另行定义。

#### 1.4.3 接收样本范围

1. 仅当前流转轮次中已送出、未撤回、接收方匹配的样本允许接收。
2. 样本主状态必须为已送出。
3. 样本不能处于已撤回送出状态。
4. 当前接收方必须与送出记录中的接收方一致。
5. 未送出的样本不能接收。
6. 已撤回送出的样本不能接收。
7. 已接收、检测中、检测完成、已终止流转或已有报告的样本不能重复接收（"已有报告"定义同 1.2.3.4）。
8. 平台不会因接收未送出样本而自动补记送出记录。
9. 接收时必须能关联到未全部撤回的送出记录，以及该记录中未撤回、未处理的样本明细。
10. 申请已终止的样本不允许接收。
11. 样本送出后、接收前发生终止申请时，接收方接收时直接拦截，提示申请已终止、不可接收，并记录拦截原因。样本主状态不变，不生成接收结果，不进入异常处理范围。拦截记录可在申请详情流转时间线和送出记录详情中查看。

#### 1.4.4 按条码接收定位规则

1. 按条码接收时，必须能明确接收方、发起机构和样本条码。
2. 平台按发起机构和样本条码定位平台申请和样本。
3. 如果只能获得样本条码、无法明确发起机构，平台不应自动模糊匹配，应提示无法定位样本。
4. 页面逐条录入接收时，可以通过先选择发起机构、送出记录或包来确定发起机构，再连续录入样本条码。
5. 不同发起机构存在相同条码时，平台按发起机构隔离识别，不视为重复样本。

#### 1.4.5 按包接收结果处理

1. 按包接收允许逐样本给出接收结果。
2. 包只是批量接收入口，不强制包内所有样本使用同一接收结果。
3. 按包接收时，平台应展示该送出记录下未撤回、未处理的待接收样本清单。
4. 接收方检验人员或接收方通过平台对外接口可以逐样本确认接收结果。
5. 样本级接收结果包括正常接收、异常接收、未到货。
6. 包内部分样本正常接收时，正常样本进入已接收。
7. 包内部分样本异常接收时，异常样本进入已接收并生成异常记录，不影响其他正常样本接收。
8. 包内部分样本未到货时，样本不进入已接收，不影响其他正常样本接收。
9. 已撤回样本不进入待接收清单，但可在送出记录明细或历史链路中展示为已撤回。
10. 包接收记录应能汇总展示本次接收处理样本的接收结果。
11. 按包接收页面提供"全部标记为正常接收"快捷操作，可将当前待接收清单中所有样本默认标记为正常接收。用户仍可逐条修改为异常接收或未到货，确认后一次性提交，生成同一条接收记录。
12. 补送记录如通过新的未送出包形成，按包接收规则同样适用；按包接收时平台应展示补送标签和原按包送出记录关联信息。

#### 1.4.6 接收结果分类

接收方核对送出记录中的样本清单，对每个样本逐项给出处置结果。接收结果分为三类：

1. **正常接收**：实物符合，确认接收。样本主状态由已送出变为已接收。

2. **异常接收**：实物存在但有问题（样本破损、条码无法识别、样本不符、容器不符等）。样本主状态由已送出变为已接收，同时登记异常记录。异常记录未关闭时，默认阻断检测流程。

3. **未到货**：送出记录中有但实物没有。样本不进入已接收，停留在已送出状态。生成异常记录，标记为未到货。未到货不表示样本必然丢失，可能是延迟到货、未实际送出、送出登记错误或运输丢失；具体处理路径见 1.6.7。

接收结果总览：

| 接收结果 | 样本主状态 | 异常记录 | 适用场景 |
|----------|-----------|----------|----------|
| 正常接收 | 已送出 → 已接收 | 无 | 实物符合，确认接收 |
| 异常接收 | 已送出 → 已接收 | 有（处理路径见 1.6.6，检测/报告阻断规则见 1.5.3、1.5.4 和 1.5.5） | 破损、条码不清、样本不符、容器问题等实物存在但有问题 |
| 未到货 | 停留在已送出 | 有（来源=未到货） | 漏送：送出记录有但实物没有 |

关键规则：

1. 异常接收和未到货均不自动导致终止申请。申请保持有效，未到货需经发起机构和接收方线下确认后，再按延迟到货、送出登记错误、补送或运输丢失等路径处理。
2. 异常类型、异常描述、发现时间、发现人或调用系统、处理意见均应记录。
3. 接收结果的后续处理路径在样本异常处理章节（1.6）定义。

#### 1.4.7 接收记录

1. 接收成功、异常接收或未到货时，均应形成接收记录或接收处理记录。
2. 接收记录应包含接收记录号。
3. 接收记录应记录接收方式，包括按条码接收、按包接收。
4. 接收记录应记录发起机构、接收方、接收时间、操作来源（人工/系统）。
5. 接收记录应关联送出记录号。
6. 按包接收时，接收记录应关联包号。
7. 接收记录应记录本次处理的样本清单。
8. 每个样本应记录接收结果，包括正常接收、异常接收、未到货。
9. 如存在异常，应记录异常类型、异常描述和处理意见。
10. 接收记录可记录接收备注。
11. 接收记录应关联申请、样本条码、送出记录和接收方。
12. 因终止申请被拦截不可接收时，应记录终止申请拦截记录（非接收结果），用于后续追溯。拦截记录不进入异常处理范围。

#### 1.4.8 接收后样本状态变化

1. 正常接收和异常接收进入已接收；未到货不进入已接收。
2. 样本正常接收后，样本主状态由已送出变为已接收。
3. 样本选择异常接收时，样本主状态由已送出变为已接收，同时生成异常记录。
4. 样本选择未到货时，样本不进入已接收，停留在已送出状态。
5. 未到货的后续处理方式，在样本异常处理章节定义。
6. 接收动作不直接将样本推进到检测中。
7. 检测中状态应由后续检测状态回传或检测流程触发。
8. 当送出记录中所有未撤回样本均已有接收侧处理结果，或已被终止申请拦截后，送出记录状态为接收完成。终止申请拦截不作为接收结果，但在送出记录状态结算时视为该样本已不再需要接收侧处理。
9. 因终止申请被拦截不可接收的样本，不进入已接收，不生成接收结果，样本主状态不回退。

#### 1.4.9 验收标准

1. 支持按条码接收。
2. 支持按包接收。
3. 按条码接收必须能明确接收方、发起机构和样本条码。
4. 仅已送出、未撤回、接收方匹配的样本允许接收。
5. 未送出样本不能接收，平台不自动补记送出记录。
6. 按包接收允许逐样本给出接收结果（正常接收、异常接收、未到货）。
7. 正常接收后样本进入已接收。
8. 未到货时样本不进入已接收。
9. 异常接收时样本进入已接收并生成异常记录。
10. 接收记录能关联申请、样本条码、送出记录和接收方。
11. 按包接收记录能关联包并展示本次处理样本的接收结果。
12. 接收完成后能回写或更新送出记录的接收侧处理结果摘要，并在满足条件时将送出记录状态更新为接收完成。
13. 申请已终止的样本不允许接收，并应展示终止申请拦截记录（在申请详情时间线中可查看）。
14. 平台提供待接收清单页面，默认展示已送出状态的送出记录，支持按状态、发起机构、送出时间筛选。
15. 接收方应可通过平台对外接口获取待接收清单；待接收清单至少包含送出记录号、发起机构、送出方式、包号（如有）、待接收样本数量和送出时间，具体接口设计由接口设计文档定义。

### 1.5 样本状态管理

#### 1.5.1 功能定位

样本状态管理用于表达样本在平台主流程中的当前位置，并为申请查询、送出、接收、检测、报告和运维追溯提供统一状态依据。

样本状态管理只管理样本主状态，不替代申请状态、送出记录状态、接收处理结果、异常状态、报告状态和推送状态。

#### 1.5.2 样本主状态范围

1. 样本主状态以样本轮次为维度管理。
2. 样本主状态包括：待送出、已送出、已接收、检测中、检测完成、已终止流转。
3. 已终止流转表示该样本轮次不再继续送出、接收、检测或上传报告，不表示申请已终止。
4. 样本主状态不包含异常、撤回、退回、终止申请、报告上传、报告发布、报告作废等状态。
5. 终止申请由申请状态表达。
6. 送出撤回由送出记录和撤回记录表达。
7. 异常接收和未到货由接收处理记录和异常记录表达。
8. 样本异常由异常记录表达。
9. 报告上传、审核、发布、撤回由报告相关状态表达。
10. 样本主状态用于表达具体样本轮次在平台主流程中的当前位置，不替代其他业务对象状态。

#### 1.5.3 检测中状态定位

1. 检测中表示接收方已经开始对样本进行检测处理。
2. 检测中为可选状态，接收方可通过平台对外接口回传检测开始触发进入，也可跳过直接从已接收进入检测完成。
3. 样本正常接收后，默认停留在已接收，不自动进入检测中。
4. 如果接收方通过平台对外接口回传检测开始，样本可由已接收进入检测中。检测中不提供独立页面人工触发按钮（见 1.5.8）。
5. 如果接收方不回传检测开始，平台允许样本由已接收直接进入检测完成。
6. 检测中不是报告上传或检测完成的强制前置状态。
7. 样本进入检测中前，应满足申请有效、当前流转轮次样本已接收、未被异常阻断等前置条件。
8. 如果样本存在待处理的接收后异常，默认不允许进入检测中，除非异常处理结果允许继续检测。
9. 接收方通过平台对外接口回传检测开始时，如样本不满足前置条件（如存在阻断性未关闭异常），平台应拒绝回传，并返回错误提示说明原因（如"样本存在待处理异常，无法进入检测中"）。

#### 1.5.4 检测完成触发规则

1. 报告上传成功后，平台将对应样本主状态更新为检测完成。
2. 如果样本当前状态为已接收，可由已接收直接转换至检测完成。
3. 如果样本当前状态为检测中，可由检测中转换至检测完成。
4. 检测中不是进入检测完成的强制前置状态。
5. 平台以报告上传成功作为样本主状态进入检测完成的业务依据。
6. 样本进入检测完成前，应满足申请有效、当前流转轮次样本已接收、未被异常阻断等前置条件。
7. 如果样本存在待处理的接收后异常，默认不允许进入检测完成，除非异常处理结果允许继续检测或异常已关闭。
8. 申请已终止时，样本不允许继续推进到检测完成。

#### 1.5.5 未接收样本与报告上传

报告上传必须满足样本已接收等前置条件，具体规则和校验逻辑见 1.7.3（报告上传前置条件）。样本主状态未进入已接收时不允许上传报告，平台不因报告上传自动补记接收记录。

#### 1.5.6 样本状态逆流程原则

1. 样本主状态原则上按正常主链向前流转，不通过回退主状态抹除已经发生的业务事实。
2. 已送出且未接收的样本，允许通过送出撤回回到待送出。
3. 异常接收后的样本，异常处理结果为退回样本或样本损毁时，当前样本轮次进入已终止流转，不回到待送出；如需继续原申请，应通过样本重新送检生成新轮次。
4. 检测中发现样本问题且无法继续检测时，异常处理结果为无法检测，当前样本轮次进入已终止流转。
5. 未到货经线下确认为运输丢失时，异常处理结果为运输丢失，当前样本轮次进入已终止流转；如需继续原申请，应通过样本重新送检生成新轮次。
6. 送出撤回是样本主状态回退到待送出的明确例外。
7. 已接收、检测中、检测完成后的问题，不通过人工直接回退样本主状态处理。
8. 已接收后的样本问题，应通过样本异常处理、样本重新送检或后续业务动作处理。
9. 报告内容错误，应通过再次上传报告或报告作废处理，不通过直接回退样本主状态处理。
10. 报告作废后不影响样本检测完成状态；作废只影响报告版本有效性。
11. 平台不提供通用的样本主状态手工回退能力。
12. 终止申请不属于样本主状态逆流程；终止申请后样本主状态保持终止发生时的状态。

#### 1.5.7 样本状态变更历史

1. 每次样本主状态变化均应形成状态变更历史。
2. 状态变更历史应记录变更前状态、变更后状态、触发动作、关联业务记录、变更时间、操作来源（人工/系统）。
3. 触发动作包括申请创建、样本重新送检、送出、送出撤回、接收、异常处理退回样本、异常处理样本损毁、异常处理无法检测、异常处理运输丢失、检测开始、报告上传成功等。
4. 关联业务记录应记录触发该变更的业务对象类型（如申请、样本轮次、送出记录、接收记录、异常记录、报告记录）及其标识。无对应业务对象时，应记录触发来源和说明。
5. 状态变更历史作为业务留痕，不允许人工编辑或删除。
6. 平台不单独提供“样本状态记录管理”菜单或维护功能。
7. 状态变更历史应在申请详情（含流转时间线）中展示。
8. 当前版本不建设独立的样本状态历史查询页面，状态历史通过申请详情流转时间线和相关业务记录详情查看。

#### 1.5.8 页面兜底、状态展示与人工维护边界

1. 样本状态不提供独立人工维护入口。
2. 平台不提供直接将样本改为待送出、已送出、已接收、检测中、检测完成的页面操作。
3. 样本主状态只能由业务动作驱动。
4. 驱动样本主状态变化的业务动作包括申请创建、送出、送出撤回、接收、检测状态回传、报告上传成功等。
5. 对于未完成系统对接的机构，平台可按业务模块分别提供页面兜底入口；是否提供以各业务章节明确的页面入口为准。
6. 已提供页面兜底入口的业务动作，应操作业务动作本身，例如页面送出、页面接收、页面异常处理，而不是直接修改样本状态。
7. 页面业务动作必须生成对应业务记录和状态变更历史。
8. 检测中不提供单独页面人工触发按钮。
9. 检测中仅由接收方通过平台对外接口回传或后续检测流程触发；如果没有检测中回传，允许样本由已接收直接进入检测完成。
10. 检测完成由报告上传成功驱动，不提供单独人工改为检测完成的状态维护入口。
11. 样本状态管理不作为独立功能菜单，平台不提供独立的”样本状态管理”页面。
12. 当前流转轮次的样本主状态应在申请详情中展示，并应在相关送出记录、接收记录、异常记录和报告记录中展示。
13. 历史轮次的样本主状态和状态变更历史应在申请详情样本轮次历史和流转时间线中展示。

#### 1.5.9 验收标准

1. 样本主状态范围包括待送出、已送出、已接收、检测中、检测完成、已终止流转。
2. 样本主状态不包含异常、撤回、退回、终止申请、报告上传、报告发布、报告作废等状态。
3. 申请创建成功后，样本主状态进入待送出。
4. 送出成功后，样本主状态进入已送出。
5. 已送出且未接收的样本撤回成功后，样本主状态回到待送出。
6. 正常接收或异常接收时，样本主状态进入已接收。
7. 未到货的样本不进入已接收。
8. 检测中作为可选状态保留；无检测中回传时，样本允许由已接收直接进入检测完成。
9. 检测中不提供单独页面人工触发按钮。
10. 报告上传成功后，样本主状态进入检测完成。
11. 未接收样本不允许上传报告，上传请求将被拒绝并提示未满足上传条件。
12. 样本主状态原则上不回退，明确例外为已送出未接收样本通过送出撤回回到待送出；退回样本、样本损毁、无法检测和运输丢失不回退到待送出，而是使当前样本轮次进入已终止流转。
13. 终止申请不回退样本主状态，样本主状态保持终止发生时的状态。
14. 平台不提供直接人工维护样本主状态的入口。
15. 未完成系统对接的机构可通过已提供的页面业务动作完成送出、接收、异常处理等操作；报告上传仍由上传方通过平台对外接口提交。页面操作必须生成对应业务记录，不允许直接修改样本主状态。
16. 每次样本主状态变化均应形成状态变更历史。
17. 状态变更历史应记录变更前状态、变更后状态、触发动作、关联业务记录、变更时间、操作来源（人工/系统）。
18. 状态变更历史不允许人工编辑或删除。
19. 样本状态管理不提供独立功能菜单或独立管理页面。
20. 当前流转轮次、历史轮次、样本当前主状态和状态变更历史应在申请详情（含流转时间线）中展示。
21. 报告作废后不影响样本检测完成状态，具体规则在报告审核与发布章节定义。

### 1.6 样本异常处理

#### 1.6.1 功能定位

样本异常处理用于记录和处理样本相关异常，包括接收环节产生的异常（异常接收、未到货），以及接收后人工发现的样本异常。

样本异常处理不作为全平台异常中心，不处理申请错误、送出错误、报告错误和推送失败等非样本类异常。

#### 1.6.2 异常处理范围

1. 样本异常处理只处理样本相关异常。
2. 接收时选择异常接收的样本，进入样本异常处理记录范围。
3. 接收时选择未到货的样本，进入样本异常处理记录范围。
4. 已接收后人工发现的样本破损、信息不一致、容器问题、样本量不足等样本问题，进入样本异常处理记录范围。
5. 申请信息错误应优先按终止申请、重新提交或业务协商处理，不纳入样本异常处理主范围。
6. 送出错误在接收前优先按送出撤回处理，不纳入样本异常处理主范围。
7. 报告内容错误按再次上传报告或报告作废处理，不纳入样本异常处理主范围。
8. 推送失败按推送记录和推送管理处理，不纳入样本异常处理主范围。

#### 1.6.3 异常状态与样本主状态关系

1. 异常作为独立异常记录管理，不覆盖样本主状态。
2. 样本主状态仍按正常主链表达，包括待送出、已送出、已接收、检测中、检测完成。
3. 样本异常不作为样本主状态。
4. 异常处理状态由异常记录单独表达。
5. 异常记录状态包括：待处理、已关闭。
6. 一个样本可以存在异常记录，同时保留其当前样本主状态。
7. 异常接收时，样本主状态为已接收，异常记录状态为待处理。
8. 未到货时，样本不进入已接收，停留在已送出，并生成异常记录。

#### 1.6.4 异常处理结果

1. 异常处理结果包括继续检测、退回样本、样本损毁、无法检测、运输丢失、关闭异常。
2. 继续检测表示样本虽存在异常记录，但业务判断可以继续后续检测流程。
3. 退回样本表示样本需要退回发起机构或相关责任方。仅异常接收（实物已接收）场景下可选此处理结果；未到货场景不适用（无实物可退）。
4. 样本损毁表示样本实物已销毁无法退回，当前样本轮次不能继续流转。
5. 无法检测表示样本已接收或进入检测处理后，因样本质量、样本量、污染、容器、信息核对等问题，当前轮次不能继续检测或不能出具有效报告。
6. 运输丢失表示样本已确认从发起机构送出，但在运输或交接过程中无法找回，当前样本轮次不能继续流转。
7. 关闭异常表示异常已完成说明、确认或处理，不再需要继续跟进。
8. 补充说明作为处理意见记录，不作为独立处理结果。
9. 样本重新送检、重新创建申请、新条码等作为异常处理后的后续业务动作，不作为异常处理结果枚举。
10. 处理结果为"继续检测"：解除检测阻断，异常记录自动关闭（关闭原因=继续检测），样本可进入检测流程。
11. 处理结果为"退回样本"：当前样本轮次进入已终止流转，异常记录自动关闭。机构如需继续完成原申请，应由发起机构发起样本重新送检。
12. 处理结果为"样本损毁"：当前样本轮次进入已终止流转，异常记录自动关闭。机构如需继续完成原申请，应由发起机构发起样本重新送检。
13. 处理结果为"无法检测"：当前样本轮次进入已终止流转，异常记录自动关闭。机构如需继续完成原申请，应由发起机构发起样本重新送检。
14. 处理结果为"运输丢失"：当前样本轮次进入已终止流转，异常记录自动关闭。机构如需继续完成原申请，应由发起机构发起样本重新送检。
15. 处理结果为"关闭异常"：异常完成，解除检测阻断（如有）；未到货延迟到货并完成接收后，可选择关闭异常用于结束跟进。
16. 退回样本、样本损毁、无法检测和运输丢失的后续处理逻辑见 1.6.5 和 1.1.9。
17. 每次处理结果变更应记录处理时间、处理人或调用系统、处理意见。

异常来源与处理结果适用范围：

| 异常来源 | 继续检测 | 关闭异常 | 退回样本 | 样本损毁 | 无法检测 | 运输丢失 |
| ---- | ---- | ---- | ---- | ---- | ---- | ---- |
| 异常接收 | 可选 | 可选 | 可选 | 可选 | 可选 | 不适用 |
| 未到货 | 不适用 | 可选 | 不适用 | 不适用 | 不适用 | 可选 |
| 已接收后人工登记（已接收） | 可选 | 可选 | 可选 | 可选 | 可选 | 不适用 |
| 已接收后人工登记（检测中） | 可选 | 可选 | 不适用 | 不适用 | 可选 | 不适用 |
| 已接收后人工登记（检测完成） | 不适用 | 可选 | 不适用 | 不适用 | 不适用 | 不适用 |

> 注意："无法检测"的触发不依赖"检测中"状态。由于检测中为可选状态（见 1.5.3），实践中"无法检测"主要由已接收阶段触发；检测中入口仅在接收方回传检测开始后可用。

#### 1.6.5 异常处理结果、样本重新送检与终止申请的联动

1. 异常处理结果为"退回样本"、"样本损毁"、"无法检测"或"运输丢失"时，当前样本轮次进入已终止流转，不自动触发终止申请。
2. 发起机构如需继续完成原申请，应基于该异常记录发起样本重新送检，生成新的样本轮次。新轮次可使用新的样本条码，也可沿用原样本条码；是否允许沿用原样本条码，由发起机构依据本机构采样、条码和质控规则决定。
3. 同一异常记录原则上只能触发一次样本重新送检，避免重复生成多个并行样本轮次。
4. 未到货只有在被确认为运输丢失后，才允许触发样本重新送检。
5. 发起机构如决定不再继续此申请，应主动发起终止申请。
6. 终止申请是独立流程，由发起机构主动发起（任意阶段）。样本异常处理结果不自动触发终止申请。
7. 未到货场景如需终止申请，应由接收方管理人员或平台运营人员登记处理意见或线下通知发起机构，由发起机构正式发起终止申请；接收方用户和平台运营人员在当前版本不代替发起机构终止申请。
8. 异常处理记录中应能关联后续触发的样本重新送检记录或终止申请记录，用于追溯。

#### 1.6.6 异常接收后的样本处理

异常接收（实物存在但有问题，如样本破损、条码无法识别、样本不符、容器不符等）：样本主状态进入已接收，同时生成异常记录。异常记录处于待处理状态时，默认不允许进入检测中或检测完成。

处理路径（选择处理结果后，异常记录自动关闭。"继续检测"和"关闭异常"解除阻断，"退回样本"、"样本损毁"和"无法检测"使当前样本轮次进入已终止流转）：

1. 异常记录未处理 → 阻断检测。样本停留在已接收。
2. 异常处理结果为"继续检测" → 解除阻断，异常记录自动关闭，样本进入检测流程。
3. 异常处理结果为"关闭异常" → 解除阻断，异常记录关闭，样本进入检测流程。
4. 异常处理结果为"退回样本"、"样本损毁"或"无法检测" → 当前样本轮次进入已终止流转，异常记录自动关闭。机构如需继续完成原申请，应由发起机构发起样本重新送检，生成新的样本轮次。

#### 1.6.7 未到货后的样本处理

未到货（漏送）：样本不进入已接收，停留在已送出状态，生成异常记录（异常来源=未到货，状态=待处理）。

处理路径：未到货异常记录先保持待处理，用于承载延迟到货、未实际送出、送出登记错误、补送或运输丢失等后续确认过程。未到货本身不等同于运输丢失，不自动触发送出撤回、样本重新送检或终止申请。

1. 发起机构和接收方线下确认实物情况。
2. 如确认只是延迟到货，样本到达后接收方可在待接收清单中对该样本重新标记接收结果（正常接收或异常接收）。原"未到货"标记作为历史记录保留在异常记录中，不删除；送出记录中该样本的处理结果从"未到货"变更为最终接收结果，并记录变更时间、操作人和变更原因。接收完成后，未到货异常记录需人工关闭（选择关闭异常），处理说明记录延迟到货和实际接收情况。
3. 如确认实物未实际送出或送出登记错误：走送出撤回（1.3.7），样本回到待送出后重新送出，不需要重新采样。异常记录需人工关闭（选择关闭异常），关闭原因可引用撤回记录。异常记录详情中应展示关联的送出撤回记录。
4. 如原送出是按包送出且确认存在漏装、漏送：可走补送流程（1.3.8）生成补送记录关联原包。异常记录需人工关闭（选择关闭异常），关闭原因可引用补送记录。
5. 如确认样本已实际送出但在运输或交接过程中无法找回：异常处理结果选择运输丢失，当前样本轮次进入已终止流转，异常记录自动关闭。运输丢失的处理结果由接收方检验人员登记，登记前应与发起机构线下确认运输丢失结论。发起机构如需继续完成原申请，应基于该异常记录发起样本重新送检，生成新的样本轮次。
6. 未到货的异常处理不自动终止申请。继续检测、退回样本、样本损毁和无法检测的处理结果不适用于未到货异常。
7. 关闭未到货异常前，应由发起机构和接收方线下确认实物情况后达成一致。关闭异常或运输丢失时，应在处理说明中记录确认结论和处理方式（如延迟到货已接收、已走送出撤回、已补送、已确认运输丢失等）。异常关闭后如发现判定错误，不影响原异常记录状态，应通过追加处理记录补充说明（见 1.6.8）。

#### 1.6.8 异常处理记录追加规则

1. 异常处理记录一旦生成，不允许修改或删除。
2. 如需补充说明或修正，只能追加新的处理记录。
3. 追加记录字段规则：

| | 首次处理记录 | 追加记录 |
|------|------|------|
| 处理结果 | 必填 | 不可选（沿用原处理结果） |
| 处理说明 | 可选 | 必填 |
| 处理人 | 必填 | 必填 |
| 处理时间 | 必填 | 必填 |

4. 追加记录不改变原始处理结果。
5. 危急值处理记录（1.8）的追加记录字段规则与此一致（首次必填处理结果，追加记录沿用原处理结果、必填处理说明）。

#### 1.6.9 异常记录内容

1. 异常记录应能支撑样本异常来源、处理过程、处理结果和退回追溯。
2. 异常记录应包含异常记录号。
3. 异常记录应关联平台申请号、发起机构、接收方和样本条码。
4. 异常记录应关联送出记录号。
5. 如样本已接收，异常记录应关联接收记录号。
6. 异常记录应记录异常来源，包括异常接收、未到货、已接收后人工登记。
7. 异常记录应记录异常类型和异常描述。
8. 异常记录应记录发现时间、发现人或调用系统。
9. 异常记录应记录异常状态，包括待处理、已关闭。
10. 异常记录应记录处理结果，包括继续检测、退回样本、样本损毁、无法检测、运输丢失、关闭异常。
11. 异常记录应记录处理意见、处理时间、处理人或调用系统。
12. 如处理结果涉及退回样本，应在处理意见中记录退回相关信息（退回时间、物流方式等，如有）。平台不做物流追踪。
13. 如处理结果触发后续样本重新送检，应能关联样本重新送检记录和新样本轮次。

#### 1.6.10 验收标准

1. 能记录异常接收、未到货、已接收后人工登记的样本异常。
2. 样本异常以独立异常记录管理，不覆盖样本主状态。
3. 异常记录状态包括待处理、已关闭。
4. 异常处理结果包括继续检测、退回样本、样本损毁、无法检测、运输丢失、关闭异常。退回样本、样本损毁、无法检测和运输丢失均使当前样本轮次进入已终止流转，异常记录自动关闭。
5. 未到货不进入已接收。
6. 未到货生成异常记录。
7. 异常接收样本进入已接收并生成异常记录。
8. 异常接收待处理时，默认不允许进入检测中或检测完成。
9. 处理结果为继续检测或关闭异常时，允许继续检测。
10. 处理结果为退回样本、样本损毁、无法检测或运输丢失时，当前样本轮次进入已终止流转；机构如需继续完成原申请，应由发起机构发起样本重新送检。
11. 未到货异常先保持待处理；延迟到货可基于原送出记录继续接收，实物未实际送出或送出登记错误可走送出撤回，包漏装漏送可走补送，运输丢失应通过样本重新送检生成新轮次。
12. 样本重新送检必须关联允许触发重新送检的异常记录，并生成新的样本轮次。
13. 异常处理结果不自动触发终止申请；如需终止申请，应由发起机构正式发起，接收方管理人员或平台运营人员可登记处理意见或线下通知发起机构。
14. 异常记录能关联申请、样本轮次、样本条码、送出记录和接收记录。
15. 异常处理过程能记录处理意见、处理时间、处理人或调用系统。
16. 异常处理记录不可修改、不可删除，只允许追加；追加记录沿用原处理结果、必填处理说明。

### 1.7 报告审核与发布

#### 1.7.1 功能定位

报告审核与发布用于管理上传方通过平台对外接口提交报告后的发布控制、报告有效性、审核留痕、上传、作废和查询边界。

本功能只做报告发布控制，不作为医学自动审核规则引擎。平台不判断报告内容是否医学正确，不自动判断结果高低、异常或危急值。

> **术语说明**：本章中"发布"指平台将上传方提交的报告版本标记为对发起机构可见的状态变更，并非平台出具或签发报告。报告内容的医学正确性由出具报告的检验机构负责。平台只管理报告版本的可见性和有效性，不参与报告内容的生成、修改或医学审核。

平台不出具报告，不提供平台页面人工上传报告能力。报告文件、结构化结果（如有）和危急值信息（如有）均由上传方通过平台对外接口提交。

报告状态独立于样本主状态。报告审核不通过、再次上传报告、报告作废均不回退样本主状态。

报告版本链追溯规则（版本号、当前有效报告、替代关系、版本追溯）在本章 1.7.15 和 1.7.16 中定义。

#### 1.7.2 审核开关

1. 报告审核开关由外部配置系统提供，本 PRD 不定义该配置能力的实现。
2. 本 PRD 仅定义审核开关启用或未启用时，对报告上传和发布流程的业务影响。
3. 报告审核开关默认启用。
4. 审核开关启用时，报告上传成功后进入待审核，审核通过后发布。
5. 审核开关未启用时，报告上传成功后自动发布。
6. 审核开关的配置入口、配置权限、配置留痕和配置生效机制，由外部配置系统定义，不纳入本 PRD。
7. 当前版本不支持按机构、项目、发起方/接收方关系配置差异化审核规则。
8. 审核开关从"启用"切换为"未启用"时，仅影响切换后新上传的报告；切换前已处于"待审核"状态的报告仍保留待审核，需人工审核通过后发布。
9. 审核开关变更不改变已生成报告版本的状态，除非该报告版本后续发生审核、上传、作废等业务动作。

#### 1.7.3 报告上传前置条件

1. 申请必须存在且处于有效状态。
2. 报告上传仅支持上传方通过平台对外接口提交，平台页面不提供人工上传报告或出具报告能力。
3. 报告上传必须针对当前流转轮次。
4. 当前流转轮次样本必须已经完成正常接收，或属于异常接收且允许继续检测。
5. 样本处于待送出、已送出的，不允许上传报告。
6. 已终止流转的历史轮次不允许上传报告。
7. 样本存在阻断性未关闭异常时，不允许上传报告。
8. 上传方必须是该申请/当前流转轮次样本对应的接收方机构或其授权系统。
9. 申请已终止、样本未到货且未进入已接收的，不允许上传报告。
10. 平台不因报告上传自动补记接收记录。
11. 不提供管理员绕过上传前置校验的兜底能力。

#### 1.7.4 报告上传内容

1. 报告上传必须包含报告 PDF。
2. 上传方提交报告时必须包含 PDF 文件，未包含则提交失败。
3. 结构化检验结果可以上传，但不是报告生成和发布的必填条件。
4. 未提供结构化结果，不影响平台生成报告版本号及版本记录、审核、发布、查询、下载和推送。
5. 报告上传不强制提供报告覆盖的项目编码清单。
6. 上传方提交什么内容，平台即保存什么、展示什么。
7. 平台不基于 PDF 内容进行项目级别的完整性判断，不判断报告覆盖了哪些检验项目。
8. 平台不做项目级完成判断、漏报判断、重复覆盖判断。
9. 同一申请下只维护一个报告业务对象，多次上传形成该报告的不同版本。
10. 每个报告版本必须关联对应的样本轮次和样本条码。
11. 报告名称或报告类型可以作为可选展示字段，但不作为报告拆分、版本合并或业务校验依据。
12. 报告文件的格式约束（文件大小上限、是否接受加密 PDF、页数限制等）由接口设计文档定义。

#### 1.7.5 报告上传成功与样本检测完成

1. 样本主状态只表达样本轮次是否已完成检测，不表达申请内各检验项目的检测进度或完成情况。
2. 报告上传成功后，平台将对应当前流转轮次样本主状态更新为检测完成。
3. 报告是否已发布、是否审核通过，不影响样本主状态已经进入检测完成。
4. 如果审核不通过、再次上传报告、报告作废，样本主状态原则上不回退。
5. 报告有效性由报告状态表达，样本检测完成只表示平台已收到该样本对应的检测报告。
6. 平台不判断申请内所有项目是否均已出报告。
7. 终止申请后，不允许通过报告上传推动样本进入检测完成。

#### 1.7.6 报告版本与上传

1. 报告上传成功后立即生成报告版本号。
2. 每次上传生成新的报告版本号。同一申请下已有报告时再次上传，平台在原报告业务对象下生成新版本号，不创建新的报告对象。
3. 同一申请下只维护一个报告业务对象（详见 1.7.15）。
4. 版本号用于区分同一申请下的不同报告版本；每个报告版本应记录对应样本轮次和样本条码。
5. 版本号一经生成，不允许复用或覆盖。
6. 同一报告不允许同时存在多个可被审核的待审核版本。
7. 本 PRD 不限定版本号展示格式，只要求版本可唯一识别、可排序、可追溯。
8. 只有报告上传前置校验通过，并且报告文件成功接收并存储后，才生成报告版本。
9. 上传失败不生成报告版本号，不进入报告业务状态，不推动样本进入检测完成。
10. 上传失败时应能向上传方说明未生成报告版本的业务原因。
11. 上传失败不作为报告业务版本展示。
12. 上传方可选填上传说明。申请下已存在已发布报告或非终止原因已作废版本时再次上传，上传说明必填。

#### 1.7.7 报告发布审核

1. 审核开关启用时，报告上传成功后进入待审核。
2. 接收方管理人员必须逐份打开报告详情后处理。
3. 平台不提供批量审核通过、批量审核不通过功能。
4. 接收方管理人员应能查看报告 PDF、报告关联申请、样本、患者摘要、项目、上传方、上传时间和历史版本信息。
5. 接收方管理人员可对单份报告执行审核通过或审核不通过。
6. 接收方管理人员审核通过后，该报告版本状态变为已发布，对发起机构可见。
7. 平台不设置独立待发布状态，不提供单独发布按钮。
8. 审核通过即代表报告对发起机构可查询、可下载，并按配置触发推送。
9. 接收方管理人员不能修改报告 PDF、结构化结果、危急值标记、项目结果或患者申请信息。
10. 如发现报告内容、文件、项目覆盖或患者信息存在问题，应审核不通过并填写原因。

#### 1.7.8 审核不通过

1. 审核不通过后，当前报告版本状态为审核不通过。
2. 审核不通过版本不允许发布、查询给发起机构、下载给发起机构用户和其他无报告版本追溯权限的用户或对外推送。
3. 审核不通过原因必填。
4. 审核不通过原因记录在平台内，可在报告详情、审核记录或报告版本追溯入口中查看。
5. 本章节不要求向上传方提供审核不通过原因的独立查询能力。
6. 上传方如需重新提交，应通过平台对外接口再次上传报告，生成新报告版本。
7. 新版本按审核开关重新进入待审核或自动已发布。
8. 原审核不通过版本保留历史，不物理删除，不作为最新有效报告。
9. 报告审核不通过只影响报告版本状态，不回退样本主状态。

#### 1.7.9 报告作废

1. 报告作废用于处理当前有效报告不应继续对外查询、下载或推送的场景。
2. 作废只允许作用于当前有效报告。
3. 待审核、审核不通过、已废弃、已失效、已替代、已作废版本不允许再次作废。
4. 报告作废仅支持接收方管理人员通过平台页面发起，不支持上传方通过平台对外接口自动发起。
5. 平台运营人员可发起报告作废，用于平台发现明显风险或收到线下确认问题后的兜底处置。
6. 平台运营人员发起报告作废时，应记录触发来源、作废原因、线下确认依据或风险说明。
7. 发起机构不能直接作废接收方上传的报告。
8. 报告作废提交后立即生效，不受报告审核开关控制。
9. 作废生效后，该报告版本不再作为当前有效报告。
10. 作废后面向业务用户的报告查询不再提供该报告。
11. 作废后平台面向业务用户的报告查询页面显示该申请暂无当前有效报告。
12. 作废后不自动回退到上一已替代历史版本。
13. 作废后不可恢复为已发布，不提供重新启用能力。
14. 非终止原因作废后，如需重新对外提供报告，上传方应通过平台对外接口再次上传报告生成新版本；终止申请联动作废后不允许继续基于该申请上传报告。
15. 非终止原因产生的已作废版本允许再次上传生成新版本，上传时必须形成版本记录并关联原已作废版本和新报告版本；已作废版本本身不恢复有效。
16. 报告作废必须填写作废原因。
17. 作废原因是平台预置枚举：报告错误、重复报告、业务取消、终止申请、其他。后续版本可扩展。
18. 作废原因选择"其他"时，作废说明必填；其他作废原因的作废说明可选填写。
19. 终止申请联动作废时，作废原因固定为终止申请，不需要人工填写作废说明。
20. 报告作废必须记录作废时间、作废人或调用系统、作废原因和关联报告版本。
21. 报告作废不删除历史报告版本。
22. 报告作废不影响样本检测完成状态。
23. 报告作废后应触发报告作废通知，具体推送规则见 1.9。
24. 终止申请时如存在当前有效报告，当前有效报告应进入报告作废处理（已发布报告只能作废，不使用已失效）。作废后不自动恢复历史版本。

#### 1.7.10 报告状态

1. 报告状态包括待审核、审核不通过、已废弃、已失效、已发布、已替代、已作废。
2. 待审核：审核开关启用时，报告上传成功后的状态。
3. 审核不通过：发布审核未通过，不可发布，不作为当前有效报告对发起机构查询、下载或推送；可在报告版本追溯入口按权限查看版本状态、上传信息、审核记录和审核不通过原因。
4. 已废弃：待审核或审核不通过版本被新上传版本替代，不再允许审核、发布，不作为当前有效报告对发起机构查询、下载或推送。
5. 已失效：待审核、审核不通过的未发布报告版本因终止申请退出待处理范围，不再允许审核、发布，不作为当前有效报告对发起机构查询、下载或推送。
6. 已发布：审核通过并发布，且尚未被新版本替代或作废时，作为当前有效报告对外提供。当新版本发布后，原已发布版本变为已替代，不再作为当前有效报告。
7. 已替代：原已发布版本被新发布版本替代。
8. 已作废：当前有效报告被作废后进入该状态，不再作为当前有效报告。
9. 已发布报告不允许反审核，不允许回退到待审核。
10. 已发布报告发现问题时，只能通过再次上传报告或报告作废处理。
11. 平台不提供管理员强制反审核能力。
12. 所有报告版本均不可物理删除，平台不提供报告删除入口。

> 补充说明：已失效仅用于未发布版本（待审核、审核不通过），与"已作废"的区别在于——已失效用于从未发布过的版本，已作废用于曾经发布过的版本。当前有效报告的判定规则见 1.7.16，各状态之间的流转由具体业务动作驱动。

#### 1.7.11 审核记录与状态变化记录

1. 每次审核动作必须形成审核记录。
2. 审核记录至少包含报告版本号、审核动作类型、审核结果、审核人、审核时间、审核意见或不通过原因。
3. 审核动作类型为报告发布审核。
4. 审核通过或不通过导致报告状态变化时，应形成报告状态变化记录。
5. 报告状态变化记录用于追溯状态从什么变成什么，以及由哪个业务动作触发。
6. 不要求在审核记录本身重复记录审核前状态和审核后状态。
7. 发布审核通过时，审核意见可选填写。
8. 发布审核不通过时，不通过原因必填。
9. 报告作废不是审核动作，不进入审核记录；作废应形成作废记录和报告状态变化记录。
10. 因终止申请导致未发布报告版本失效时，应形成报告状态变化记录。

#### 1.7.12 报告查询、下载和页面入口

1. 面向业务用户的报告查询只提供当前有效报告。
2. 面向业务用户的报告查询不提供待审核、审核不通过、已废弃、已失效、已替代、已作废报告。
3. 外部系统不能通过面向业务用户的报告查询获取历史版本或无效版本。
4. 如后续确需对外开放历史版本，应作为独立的版本追溯能力处理，不与面向业务用户的报告查询混用。
5. 平台面向业务用户的报告查询页面默认只展示当前有效报告。
6. 报告查询页面支持在线查看和下载当前有效报告 PDF；当前版本不支持报告内容的结构化渲染、标注或对比。
7. 面向业务用户的报告查询页面根据场景展示不同文案：

| 场景 | 查询结果说明 |
|------|-------------|
| 从未上传过报告 | 提示暂无报告 |
| 报告被人工作废 | 提示暂无当前有效报告 |
| 报告因终止申请被作废 | 提示申请已终止且报告已作废，可展开查看作废原因和终止原因摘要 |
| 申请已终止且从未上传报告 | 提示申请已终止且暂无报告 |
| 有当前有效报告 | 正常展示报告 |

8. 历史报告的查看跳转到版本追溯入口（按权限控制），不在面向业务用户的报告查询页面展示。已作废报告在所有入口（含面向业务用户的报告查询和版本追溯）均不可下载。
9. 非当前有效报告不在面向业务用户的报告查询页面展示，也不可从该入口下载。
10. 报告下载应记录操作留痕。
11. 报告审核入口用于处理发布审核。
12. 发布审核页签展示状态为待审核的报告版本；已失效的报告版本不进入发布审核页签。
13. 报告作废页面入口仅对接收方管理人员和平台运营人员开放。
14. 报告版本追溯用于接收方管理人员和平台运营人员查看全部历史版本、替代关系、作废记录和审核记录；版本追溯入口中的"查看"用于追溯版本状态、版本链、替代关系、作废记录和审核记录，不等同于所有报告文件均可下载。
15. 申请详情中应展示报告摘要，并支持跳转到对应报告页面；如尚未上传报告，应展示无报告记录。
16. 发起机构用户和其他无报告版本追溯权限的用户不直接面对全部报告版本，避免误用历史或无效报告。
17. 报告下载权限接入统一权限系统；本章节只定义报告状态对下载的业务限制，不展开具体角色授权配置。

#### 1.7.13 报告上传结果和上传方通知

1. 报告上传成功后，上传方应能获得报告版本号。
2. 上传方应能获得当前报告状态：审核开关启用时为待审核，审核开关未启用时为已发布。
3. 上传方应能知道报告是否已自动发布。
4. 上传失败时，应向上传方说明未生成报告版本的业务原因。
5. 报告上传成功或失败的结果反馈不提供完整报告详情。
6. 报告审核结果（审核通过、审核不通过）通过"报告审核结果通知"推送给上传方，具体推送规则见 1.9。
7. 上传方如需查看报告审核、发布状态或不通过原因的明细，可在权限范围内通过平台页面查看。

#### 1.7.14 危急值与报告审核开关

1. 报告上传时可以同时上传危急值信息。
2. 危急值必须关联本次报告版本、申请、样本条码、上传方和接收方。
3. 审核开关启用时，报告和关联危急值在审核通过后才对外发布或推送。
4. 审核开关未启用时，报告上传成功自动发布，关联危急值进入可推送状态。
5. 危急值本身的记录、平台内部处理、业务推送边界和医院侧处理回执，在危急值记录与处理留痕、报告和危急值推送管理章节定义。
6. 平台不自动判断危急值，危急值信息由上传方提供。

#### 1.7.15 报告对象与版本关系

1. 同一申请下只维护一个报告业务对象。
2. 首次报告上传成功后，生成该报告业务对象的第一个报告版本。
3. 同一申请再次上传报告时，必须作为该报告业务对象的新版本处理，并记录本次报告对应的样本轮次和样本条码。
4. 平台不根据报告名称、报告类型、项目范围或 PDF 内容自动拆分多个报告对象。
5. 报告名称或报告类型仅作为展示字段，不作为版本链判断依据。
6. 分批出结果、补充结果、修正报告内容，均通过再次上传报告生成新版本。
7. 项目多或一页显示不完，不作为拆分多个报告对象的理由。

#### 1.7.16 当前有效报告判定

1. 任一时间同一申请最多只有一份当前有效报告。
2. 面向业务用户的报告查询只能提供当前有效报告。
3. 报告首次发布后，该版本成为当前有效报告。
4. 已发布报告再次上传后，新版本发布前，原已发布版本仍为当前有效报告。
5. 新版本发布后，新版本成为当前有效报告，原已发布版本进入已替代。
6. 如果新版本审核不通过，原当前有效报告继续有效。
7. 当前有效报告作废后，该申请暂无当前有效报告。
8. 当前有效报告作废后，已替代历史版本不自动恢复为当前有效报告。
9. 终止申请导致当前有效报告作废或失效后，该申请暂无当前有效报告。
10. 非终止原因作废后，如需重新对外提供报告，上传方必须通过平台对外接口再次上传生成新版本；新版本发布后才重新成为当前有效报告。
11. 终止申请导致报告作废或失效后，不允许继续基于该申请再次上传报告；如需继续检测或出具报告，应重新提交新申请。

#### 1.7.17 验收标准

1. 平台支持统一报告审核开关对报告上传和发布审核的业务流程产生影响。
2. 审核开关启用时，报告上传成功后进入待审核。
3. 审核开关未启用时，报告上传成功后自动发布。
4. 报告上传仅支持上传方通过平台对外接口提交，平台页面不提供人工上传报告或出具报告能力。
5. 报告上传前必须校验申请有效、上传对象为当前流转轮次、样本已接收或允许继续检测、上传方为对应接收方、无阻断性未关闭异常。
6. 待送出、已送出、申请已终止、未到货且未接收的样本不允许上传报告。
7. 报告上传必须包含 PDF，结构化结果可选。
8. 报告上传不强制提供覆盖项目范围，平台不做项目级完成、漏报或重复覆盖判断。
9. 报告上传成功后生成报告版本号，报告版本记录对应样本轮次和样本条码，并推动当前流转轮次样本主状态进入检测完成。
10. 报告审核不通过、再次上传、作废均不回退样本检测完成状态。
11. 上传失败不生成报告版本，不推动样本进入检测完成。
12. 审核通过即发布，不设置独立待发布状态或单独发布按钮。
13. 报告审核不支持批量审核。
14. 接收方管理人员不能修改报告内容，只能审核通过或审核不通过。
15. 审核不通过原因必填，审核不通过版本不可发布，不作为当前有效报告对发起机构查询、下载或推送；可在报告版本追溯入口按权限查看版本状态、上传信息、审核记录和审核不通过原因。
16. 待审核报告允许上传方通过平台对外接口主动再次上传，原待审核版本标记为已废弃。
17. 已发布报告再次上传后，新版本发布前原已发布版本继续有效。
18. 新版本发布后成为当前有效报告，原已发布版本标记为已替代。
19. 上传方可以通过平台对外接口再次上传报告；接收方管理人员可以通过平台页面发起报告作废；平台运营人员可在平台发现明显风险或收到线下确认问题后发起报告作废兜底处置。
20. 平台运营人员发起报告作废时，应记录触发来源、作废原因、线下确认依据或风险说明。
21. 报告作废只允许作用于当前有效报告，作废立即生效且不受审核开关控制。
22. 报告作废后进入已作废，不再作为当前有效报告。
23. 非终止原因导致报告作废后不自动回退历史版本；如需重新对外提供报告，应通过再次上传生成新版本。终止申请联动作废后不允许继续基于该申请再次上传报告。
24. 终止申请时，未发布报告版本应进入已失效，不再允许审核、发布，不作为当前有效报告对发起机构查询、下载或推送。
25. 终止申请时如存在当前有效报告，当前有效报告应进入报告作废处理。
26. 报告状态包括待审核、审核不通过、已废弃、已失效、已发布、已替代、已作废。
27. 已发布报告不允许反审核，只能通过再次上传或作废处理问题。
28. 每次审核动作必须形成审核记录，并在状态变化时形成报告状态变化记录。
29. 面向业务用户的报告查询只能提供当前有效报告。
30. 面向业务用户的报告查询页面只展示当前有效报告，并支持在线查看和下载 PDF；当前版本不支持报告内容的结构化渲染、标注或对比。
31. 报告审核入口用于处理发布审核。
32. 报告版本追溯入口可按权限查看全部历史版本、替代关系、作废记录和审核记录；版本追溯入口中的"查看"用于追溯版本状态、版本链、替代关系、作废记录和审核记录，不等同于所有报告文件均可下载。
33. 报告上传成功后，上传方应能获得报告版本号、当前报告状态和是否已自动发布。
34. 报告审核结果通过"报告审核结果通知"推送给上传方，推送规则见 1.9 章节。
35. 报告上传可包含危急值信息，危急值发布/推送跟随报告审核开关。

### 1.8 危急值记录与处理留痕

#### 1.8.1 功能定位

危急值记录与处理留痕用于记录上传方随报告提交的危急值信息，并支持平台内部对危急值进行轻量闭环处理。

平台不自动判断危急值，不根据结构化结果、参考范围或 PDF 内容生成危急值，也不提供页面人工新建危急值入口。危急值是否存在、具体项目、结果值、危急说明和危急等级等信息，由上传方随报告提供。

本功能只定义平台内部危急值记录和处理留痕；医院侧处理回执、危急值推送给发起机构等内容，在报告和危急值推送管理章节定义。

#### 1.8.2 危急值来源与报告版本关系

1. 危急值仅随报告上传进入平台。
2. 平台不支持报告上传后单独补录危急值。
3. 平台不提供页面人工新建危急值能力。
4. 每条危急值必须关联申请、样本条码、报告版本、上传方和接收方。
5. 危急值作为报告版本内容的一部分记录。
6. 报告版本未发布前，关联危急值不对外发布或推送。
7. 报告版本发布后，关联危急值才进入当前有效危急值范围。
8. 报告版本被新版本替代后，旧版本关联危急值不再作为当前有效危急值。
9. 报告版本被作废后，关联危急值不再作为当前有效危急值。
10. 终止申请导致报告作废或失效后，关联危急值不再作为当前有效危急值。
11. 平台不把危急值脱离报告版本单独变成有效对象。

#### 1.8.3 当前有效危急值规则

1. 当前有效危急值只来自当前有效报告版本。
2. 新报告版本发布后，只以新版本携带的危急值作为当前有效危急值。
3. 如果新版本未携带危急值，则平台认为当前有效报告版本下没有危急值。
4. 平台不自动继承旧版本危急值。
5. 平台不要求上传方额外声明是否继承或取消旧版本危急值。
6. 历史危急值仍可在报告版本追溯或危急值详情中查看。
7. 历史危急值不作为当前待处理危急值。
8. 待审核、审核不通过或已失效且从未发布过的报告版本下的危急值，只作为报告版本内容保存，不进入平台内部处理闭环，不计入待处理数量，也不需要手动关闭。
9. 危急值不提供单独作废动作。
10. 危急值有效性跟随报告版本，报告被替代或作废后，关联危急值自动不再当前有效。
11. 终止申请不删除历史危急值；终止申请导致报告作废或失效后，关联危急值退出当前有效范围。
12. 曾经进入当前有效范围的危急值退出当前有效范围时，不自动改变其平台内部处理状态；该危急值不再进入当前待处理列表，但可在"已失效待处理"筛选项中查看和手动关闭（见 1.8.9）。历史详情中保留原处理状态和处理记录。

#### 1.8.4 危急值字段类别

PRD 层面要求危急值记录覆盖以下信息类别；具体对接信息项由接口设计文档另行定义。

1. 申请信息。
2. 样本条码。
3. 报告版本。
4. 患者摘要。
5. 项目名称或项目编码。
6. 结果值。
7. 单位。
8. 参考范围或危急阈值。
9. 危急类型或危急说明。
10. 危急等级。
11. 上传方。
12. 上传时间。
13. 平台内部处理状态。
14. 处理记录摘要。

平台不维护危急值判断规则，不根据结果值自动判断是否危急，不维护危急值阈值体系。

#### 1.8.5 平台内部处理状态

1. 危急值平台内部处理状态只包括待处理、已处理。
2. 危急值记录随报告上传生成时，先作为报告版本内容保存；报告版本发布、危急值进入当前有效范围后，平台内部处理状态默认为待处理。
3. 具备权限的用户完成平台内部处理后，状态变为已处理。
4. 待审核、审核不通过或已失效且从未发布过的报告版本下的危急值，不进入平台内部处理状态，不作为待处理危急值。
5. 不设置处理中、已查看、已通知、已关闭等状态。
6. 查看、确认、电话通知、补充说明等过程信息通过处理记录体现，不进入主状态。
7. 是否已通知医院、推送是否成功、医院是否已处理，不写入平台内部处理状态。
8. 危急值已处理后，不允许重新打开为待处理。
9. 后续如有补充情况，只允许追加处理记录。

#### 1.8.6 平台内部处理规则

1. 危急值从待处理变为已处理时，必须选择处理结果。
2. 处理结果从平台预置枚举中选择（后续版本可扩展枚举值）。
3. 当前版本危急值平台内部处理结果包括：已电话通知、已人工确认、无需进一步处理、已失效关闭、其他。
4. 平台记录当次选择的处理结果编码和处理结果名称。
5. 处理说明或备注可选填写；处理结果选择"其他"时，处理说明必填。
6. 未选择处理结果时，不允许完成处理。
7. 处理记录应包含处理人、处理时间、处理结果和处理说明。
8. 推送成功不自动置为已处理。
9. 医院侧处理回执不自动置为平台内部已处理。
10. 平台内部处理完成不代表医院侧已处理。

#### 1.8.7 处理权限边界

1. 危急值平台内部处理仅允许具备对应权限的用户操作。
2. 具备危急值处理权限的用户才可以将危急值从待处理置为已处理。
3. 具备危急值处理权限的用户才可以追加危急值处理记录。
4. 用户是否拥有该权限，由统一权限系统判断。
5. 本 PRD 不定义危急值处理权限的权限点配置、授权流程、组织范围和数据范围配置。
6. 无危急值处理权限的用户不能进入危急值处理列表、查看待处理数量或执行处理操作；如需查看危急值历史或关联报告信息，应通过报告版本追溯、危急值详情等页面按统一权限系统单独授权。

#### 1.8.8 处理记录留痕

1. 每条危急值独立处理。
2. 同一报告版本包含多条危急值时，每条危急值分别维护处理状态和处理记录。
3. 危急值处理记录一旦生成，不允许修改。
4. 危急值处理记录不允许删除。
5. 如果原处理记录有错误、遗漏或后续补充情况，只能追加新的处理记录说明。
6. 追加记录需要记录处理人、处理时间和处理说明，不重新选择处理结果。
7. 原始处理记录必须完整保留，用于业务追溯。
8. 平台内部处理记录和医院侧处理回执需要分开记录。
9. 平台内部处理记录不等同于医院侧已处理。
10. 医院侧处理回执不自动替代平台内部处理记录。
11. 追加处理记录的字段规则与异常处理记录统一（见 1.6.8）：首次处理必填处理结果，追加记录不重新选择处理结果，沿用原处理结果，并必填处理说明。

#### 1.8.9 列表与查询范围

1. 危急值处理列表默认只展示当前有效报告版本关联的危急值。
2. 已替代、已作废、已失效、审核不通过、待审核报告版本下的危急值，不进入危急值处理列表的默认范围。
3. 待审核、审核不通过或已失效且从未发布过的报告版本下的危急值，不计入待处理数量，也不进入"已失效待处理"筛选。
4. 历史危急值可在报告版本追溯或危急值详情中查看。
5. 历史危急值不作为当前待处理危急值提示。
6. 当前版本不建设独立待办中心。
7. 当前版本不生成独立待办事项。
8. 当前版本不提供首页危急值待办入口、全局角标、消息提醒或升级提醒。
9. 危急值处理页面提供待处理筛选。
10. 危急值处理页面应展示待处理数量。
11. 待处理数量按当前有效报告版本下、平台内部处理状态为待处理的危急值计算。
12. 危急值处理页面提供"已失效待处理"筛选，用于查看因报告作废、被替代或终止申请联动而退出当前有效范围、但平台内部处理状态仍为待处理的危急值。用户可逐条查看详情并手动完成处理（选择处理结果），处理记录由真实操作人留痕。
13. 用户需要具备危急值处理权限，才可查看危急值列表和待处理数量；具体授权由统一权限系统判断。
14. 危急值处理完成后，该条记录不再出现在待处理筛选结果中。

#### 1.8.10 当前版本不支持范围

1. 不支持平台自动判断危急值。
2. 不支持页面人工新建危急值。
3. 不支持报告上传后单独补录危急值。
4. 不支持危急值单独作废或恢复。
5. 不支持危急值处理记录修改或删除。
6. 不支持危急值处理附件。
7. 不支持危急值批量处理。
8. 不支持危急值处理二次确认强制规则。
9. 不单独提供危急值处理记录导出。
10. 不设置危急值超时提醒、超时统计和升级提醒。
11. 不建设独立危急值待办中心。

#### 1.8.11 验收标准

1. 报告上传时可随报告版本提交危急值信息。
2. 平台不支持脱离报告版本单独创建当前有效危急值。
3. 危急值必须绑定申请、样本条码和报告版本。
4. 当前有效危急值只来自当前有效报告版本。
5. 新版本报告未携带危急值时，旧版本危急值不再作为当前有效危急值。
6. 报告作废、被替代或已失效后，关联危急值不再进入当前处理列表。
7. 曾经进入当前有效范围的危急值退出当前有效范围时，不自动改变其平台内部处理状态，历史详情保留原处理状态和处理记录；退出后仍为待处理的危急值可通过"已失效待处理"筛选查看并手动关闭。
8. 待审核、审核不通过或已失效且从未发布过的报告版本下的危急值，不进入平台内部处理闭环，不计入待处理数量，也不需要手动关闭。
9. 危急值处理状态只包括待处理和已处理。
10. 危急值完成处理时必须选择平台预置的处理结果；当前版本处理结果包括已电话通知、已人工确认、无需进一步处理、已失效关闭、其他。
11. 危急值处理结果选择"其他"时，处理说明必填。
12. 每条危急值独立处理，不支持批量处理。
13. 危急值处理记录不可修改、不可删除，只允许追加。
14. 危急值处理列表支持查看当前有效报告版本下的待处理危急值和待处理数量，以及通过"已失效待处理"筛选查看已失效但仍待处理的危急值。
15. 当前版本不建设独立待办中心、超时提醒、升级提醒和处理附件能力。

### 1.9 报告和危急值推送管理

#### 1.9.1 功能定位

报告和危急值推送管理用于定义报告发布后、危急值产生后，平台向发起机构进行业务通知的边界，以及医院侧危急值处理回执的业务含义。

本 PRD 只定义推送业务目标、推送对象、推送时机和推送内容类别；不定义推送系统实现。

推送失败后的补充推送、推送运维和外部机构接口对接规则不在本 PRD 展开，作为配套设计事项处理。

#### 1.9.2 推送业务目标

1. 报告发布后，发起机构应能及时获取报告。
2. 再次上传报告并发布新版本后，发起机构应能获取最新报告。
3. 当前有效报告版本包含危急值时，发起机构应能收到危急值通知。
4. 医院侧如已处理危急值，平台应能记录医院侧处理回执。
5. 平台内部危急值处理闭环与医院侧处理回执分开，不互相替代。
6. 报告审核完成后，上传方应能获知审核结果，以便在审核不通过时及时再次上传报告。

#### 1.9.3 推送类型与对象

1. 报告和危急值相关通知共用业务上的推送能力，但需要区分推送类型。
2. 推送类型包括报告发布推送、报告作废通知、危急值发布推送、危急值失效通知、报告审核结果通知。
3. 报告发布推送不替代危急值发布推送。
4. 危急值发布推送不替代报告发布推送。
5. 报告作废通知用于告知发起机构当前有效报告已被作废。
6. 危急值失效通知用于告知发起机构原当前有效危急值已退出当前有效范围。
7. 报告审核结果通知用于告知上传方其上传的报告已完成发布审核，通知内容包含审核结果（审核通过/审核不通过）。
8. 推送对象按发起机构确定；报告审核结果通知的推送对象为上传方。
9. 平台根据申请归属关系确定应通知的机构；报告审核结果通知根据上传方确定通知对象。
10. 本 PRD 只要求平台能够按申请归属确定应通知机构；外部机构接口对接方式不在本 PRD 定义。

#### 1.9.4 报告推送业务规则

1. 报告发布后，应触发报告发布推送。
2. 报告未发布前，不触发报告发布推送。
3. 待审核、审核不通过、已作废的报告版本不触发报告发布推送。
4. 报告发布推送内容以当前发布的报告版本为准。
5. 再次上传报告并发布新版本后，新版本报告发布推送即视为报告更新通知。
6. 平台不额外生成独立的报告更新通知类型。
7. 旧报告版本被新版本替代后，当前版本不单独推送旧版本失效通知。
8. 当前有效报告被人工作废或终止申请联动作废后，应触发报告作废通知。
9. 报告作废通知内容应能让发起机构识别被作废的报告版本、申请、样本条码、作废原因和作废时间。
10. 医院侧如果主动查询报告状态，应能看到报告已作废。
11. 终止申请后，不再触发新的报告发布推送；终止申请联动报告作废时仍应触发报告作废通知。
12. 当前版本不自动向医院或发起机构推送终止申请外部通知。

#### 1.9.5 危急值推送业务规则

1. 报告发布后，平台判断当前发布报告版本是否包含危急值。
2. 如果当前报告版本包含危急值，应触发危急值发布推送。
3. 危急值未随报告上传的，不单独生成危急值发布推送。
4. 报告未发布前，不触发危急值发布推送。
5. 待审核、审核不通过、已作废、已替代的报告版本，不触发当前危急值发布推送。
6. 危急值发布推送内容来自当前发布报告版本内的危急值记录。
7. 同一报告版本包含多条危急值时，按每条危急值分别表达危急值发布推送结果。
8. 某条危急值发布推送失败，不影响其他危急值的业务推送结果。
9. 某条危急值收到医院侧处理回执，不代表同报告内其他危急值已回执。
10. 报告作废后，关联危急值随报告版本失效，应触发危急值失效通知。
11. 报告被新版本替代后，旧版本关联危急值退出当前有效范围，应触发危急值失效通知。无论新版本是否携带同项目危急值，旧版本危急值退出时均应触发失效通知。
12. 终止申请导致报告作废或失效后，关联危急值随报告版本失效，应触发危急值失效通知。
13. 终止申请后，不再触发新的危急值发布推送；终止申请联动危急值失效时仍应触发危急值失效通知。
14. 危急值失效通知内容应能让发起机构识别失效危急值、关联报告版本、申请、样本条码、失效原因和失效时间。
15. 危急值失效通知只表示该危急值退出当前有效范围，不改变该危急值的平台内部处理状态。

#### 1.9.6 报告审核结果推送业务规则

1. 报告审核通过后，应触发报告审核结果通知，推送对象为上传方。
2. 报告审核不通过后，应触发报告审核结果通知，推送对象为上传方。
3. 审核不通过的通知应包含不通过原因，以便上传方判断是否需要再次上传报告。
4. 审核开关未启用、报告上传后自动发布时，不触发报告审核结果通知。
5. 终止申请导致报告作废或失效后，不再触发报告审核结果通知。
6. 报告上传失败时，不触发报告审核结果通知。
7. 报告审核结果通知不替代报告发布推送；两者推送对象不同（报告发布推送对象为发起机构，审核结果通知对象为上传方）。
8. 报告审核结果通知内容应能让上传方识别报告版本、申请、样本条码和审核结果。

#### 1.9.7 推送内容类别

报告发布推送内容应让发起机构能够获取当前发布的报告内容，至少包含以下类别：

1. 报告基础信息。
2. 报告文件或报告访问地址。
3. 报告版本信息。

报告作废通知内容应让发起机构能够识别被作废的报告，至少包含以下类别：

1. 报告基础信息。
2. 报告版本信息。
3. 申请信息。
4. 样本条码。
5. 作废原因和作废时间。

危急值发布推送内容应让发起机构能够识别并处理具体危急值，至少包含以下类别：

1. 危急值核心信息。
2. 关联报告版本信息。
3. 申请信息。
4. 样本条码。
5. 患者摘要。

危急值失效通知内容应让发起机构能够识别失效危急值，至少包含以下类别：

1. 危急值核心信息。
2. 关联报告版本信息。
3. 申请信息。
4. 样本条码。
5. 失效原因和失效时间。

报告审核结果通知内容应让上传方能够识别审核结果，至少包含以下类别：

1. 报告基础信息。
2. 报告版本信息。
3. 申请信息。
4. 样本条码。
5. 审核结果（审核通过/审核不通过）。
6. 审核不通过原因（审核不通过时必含）。

本 PRD 只定义推送内容类别；报告文件获取方式、具体对接信息项和安全控制规则不在本 PRD 展开。

#### 1.9.8 业务可见推送记录

1. 平台在各推送类型触发后，记录推送是否已触发。
2. 推送是否已触发的记录用于在申请详情流转时间线中展示对应的推送事件，供业务用户判断通知是否已发出。
3. 具体推送执行结果（成功/失败）、推送重试、推送补偿和推送运维由推送系统管理，不在本 PRD 定义。

#### 1.9.9 医院侧危急值处理回执

1. 当前版本只对危急值支持医院侧处理回执。
2. 报告推送不要求医院侧业务回执。
3. 当前版本不单独定义医院侧接收回执。
4. 医院侧处理回执表示医院侧已经对危急值完成确认或处理。
5. 医院侧处理回执只允许由发起机构系统通过医院侧接口回传，平台不提供人工登记入口。
6. 医院侧处理回执不自动完成平台内部危急值处理。
7. 平台内部危急值处理完成后，不自动生成医院侧处理回执。
8. 没有医院侧处理回执，不影响平台内部危急值处理闭环。
9. 医院侧处理回执需要在业务层展示。
10. 危急值相关页面应展示是否已有医院侧处理回执，以及最新回执摘要。
11. 最新回执摘要至少包括回执状态、回执时间、处理说明和回执来源。
12. 如存在多次医院侧处理回执，可在详情中查看回执历史。
13. 医院侧处理回执展示不等同于平台内部危急值处理状态。
14. 本 PRD 不定义医院侧处理回执的接口实现规则。

#### 1.9.10 当前版本不支持范围

1. 推送系统的实现、失败处理、接口对接和运维规则由推送系统设计文档定义，不在本 PRD 展开。
2. 不单独推送旧报告版本失效通知。
3. 不做面向外部机构的终止申请推送通知。
4. 不要求报告推送医院侧业务回执。
5. 不定义医院侧接收回执。

#### 1.9.11 验收标准

1. 报告发布后，业务上应触发报告发布推送。
2. 报告新版本发布后，业务上应触发新版本报告发布推送。
3. 当前有效报告作废后，业务上应触发报告作废通知。
4. 当前有效报告版本包含危急值时，业务上应按单条危急值触发危急值发布推送。
5. 危急值退出当前有效范围时，业务上应触发危急值失效通知。
6. 危急值失效通知不改变危急值的平台内部处理状态。
7. 报告审核通过或审核不通过后，业务上应向上传方触发报告审核结果通知。
8. 报告发布推送、报告作废通知、危急值发布推送、危急值失效通知和报告审核结果通知需要区分推送类型。
9. 各推送类型触发后，平台应记录推送是否已触发，并在申请详情流转时间线中展示对应推送事件。
10. 报告发布推送内容类别包含报告基础信息、报告文件或访问地址、报告版本信息。
11. 报告作废通知内容类别包含报告基础信息、报告版本信息、申请、样本条码、作废原因和作废时间。
12. 危急值发布推送内容类别包含危急值核心信息、关联报告版本信息、申请、样本条码和患者摘要。
13. 危急值失效通知内容类别包含危急值核心信息、关联报告版本信息、申请、样本条码、失效原因和失效时间。
14. 报告审核结果通知内容类别包含报告基础信息、报告版本信息、申请、样本条码、审核结果和审核不通过原因（审核不通过时必含）。
15. 当前版本不单独推送旧报告版本失效通知。
16. 当前版本不做面向外部机构的终止申请推送通知。
17. 终止申请后不再触发新的报告发布推送、危急值发布推送和报告审核结果通知；终止申请联动报告作废或危急值失效时，仍应触发对应通知。
18. 当前版本只对危急值支持医院侧处理回执。
19. 医院侧处理回执不自动完成平台内部危急值处理。
20. 平台内部危急值处理不自动生成医院侧处理回执。
21. 医院侧处理回执应在业务层查看，历史可追溯。

### 1.10 平台内部通知

#### 1.10.1 功能定位

平台内部通知用于在关键业务事件发生时，向相关平台用户发出业务提示。通知不同于面向外部机构的推送（见 1.9），以平台用户为通知对象，在申请详情时间线和列表页中体现。

当前版本只覆盖明确的业务通知场景，不建设独立消息中心、站内信或个性化通知配置。

本章节定义的平台内部通知不属于 1.9 中面向外部机构的推送通知。

#### 1.10.2 通知触发规则

以下通知对象中，"接收方人员"指该申请对应接收方下全体用户（含接收方用户、接收方检验人员、接收方管理人员），不做子角色区分。

| 通知场景 | 触发时机 | 通知对象 |
|----------|----------|----------|
| 申请已终止 | 终止申请生效后 | 该申请的接收方人员 |
| 包内样本因终止被阻断 | 终止申请生效后，该申请的当前流转轮次样本从所有未送出包中自动移出 | 该包的创建者 |
| 异常已处理 | 异常记录关闭后 | 该申请的发起机构用户 |
| 报告已发布 | 报告发布生效后 | 该申请的发起机构用户 |
| 危急值已发布 | 包含危急值的报告发布生效后 | 该申请的发起机构用户 |
| 报告已作废 | 报告作废生效后 | 该申请的发起机构用户 |

#### 1.10.3 通知表现形式

1. 通知以事件形式记录在申请详情流转时间线中，展示通知类型、触发时间和摘要信息。
2. 申请列表页支持筛选"有关键通知事件的申请"。
3. 关键通知事件指本章节定义的通知触发事件已在申请详情时间线中形成记录。
4. "有关键通知事件"仅表示申请存在相关通知事件，不表示未读、待办、待处理或需要用户执行确认动作。
5. 筛选结果按通知对象和用户权限展示，用户只能看到自己权限范围内可见的申请和通知事件。
6. 当前版本不提供独立通知列表页面、全局通知角标或消息弹窗。

#### 1.10.4 不支持范围

1. 不建设独立消息中心或站内信。
2. 不支持已读/未读状态。
3. 不支持短信、邮件、移动推送等外部通知渠道。
4. 不支持用户自定义通知规则或订阅配置。
5. 不做通知超时提醒或升级。

#### 1.10.5 验收标准

1. 终止申请、异常关闭、报告发布、危急值发布、报告作废、包内样本因终止被阻断六类事件触发后，通知对象范围内的用户可在申请详情时间线中看到通知事件。
2. 申请列表页支持按"有关键通知事件"筛选。
3. "有关键通知事件"不表示未读、待办或待处理。
4. 通知事件记录不可编辑、不可删除。

### 1.11 权限、隐私与追溯边界

#### 1.11.1 权限边界

1. 本 PRD 仅定义业务规则描述中使用的角色名称和职责边界，不定义权限系统中的角色模型。
2. 本 PRD 不定义具体权限点。
3. 本 PRD 不定义授权流程。
4. 本 PRD 不定义角色分配、组织范围和数据范围配置。
5. 各业务页面、查询、处理、登记、查看、跳转等能力，应接入平台统一权限系统。
6. 用户是否可见、可查、可操作，由统一权限系统判断。
7. 本 PRD 只在具体业务规则中声明哪些能力需要权限控制。
8. 具体权限配置由权限系统设计确认。

#### 1.11.2 隐私与脱敏边界

1. 本 PRD 不定义具体患者脱敏规则。
2. 本 PRD 不定义敏感信息搜索规则。
3. 本 PRD 不定义敏感信息导出规则。
4. 涉及患者姓名、手机号、证件号、病历号、报告内容、危急值等敏感信息时，必须遵循平台统一隐私、脱敏和数据权限规范。
5. 患者敏感信息的展示、查询、搜索、导出，由平台统一隐私规范和权限系统确定。
6. 各业务模块不得单独定义一套与平台统一规范冲突的脱敏规则。

#### 1.11.3 审计边界

1. 当前版本不建设统一审计日志系统。
2. 本 PRD 中要求的业务留痕（状态变更历史、操作留痕、处理记录等）即为本版本的业务追溯手段。
3. 业务留痕在各业务章节中分别定义，不单独设置统一的审计日志模块。
4. 业务留痕记录不可编辑、不可删除，作为操作证据保留。
5. 后续如建设统一审计日志，业务留痕可作为审计数据来源之一，届时由统一审计规范确定接入方式。

#### 1.11.4 外部依赖系统说明

本 PRD 引用了以下外部系统或规范：

| 外部依赖 | 说明 |
|---------|------|
| 统一权限系统 | 本 PRD 中的角色定义仅用于业务规则描述，具体权限点、授权流程、组织范围和数据范围由统一权限系统管理 |
| 统一隐私规范/脱敏规范 | 患者敏感信息的展示、查询、搜索、导出和脱敏规则由统一隐私规范确定 |
| 外部配置系统 | 报告审核开关等平台级业务配置由外部配置系统提供配置入口、权限、留痕和生效机制 |

#### 1.11.5 验收标准

1. PRD 中涉及权限控制的业务能力，应说明接入统一权限系统。
2. PRD 不单独定义具体权限模型。
3. 涉及患者敏感信息时，应遵循平台统一隐私、脱敏和数据权限规范。
4. 关键业务操作应在本 PRD 各业务章节定义的范围内形成业务留痕，业务留痕不可编辑、不可删除。

### 1.12 检验项目目录与对照管理

#### 1.12.1 功能定位

检验项目目录与对照管理用于维护平台标准检验项目目录，以及发起机构项目编码与平台标准项目编码之间的对照关系。申请创建时，平台根据发起机构提交的机构项目编码识别对应的平台标准项目编码。

平台标准项目目录和机构项目对照用于申请创建校验、项目展示、查询和追溯，不承担收费、医保、医学判断、参考范围、危急值阈值、检测方法学或实验室内部规则管理职责。

#### 1.12.2 平台标准项目目录

1. 平台标准项目目录由平台运营人员维护。
2. 平台标准项目类型包括组合项目和明细项目。
3. 组合项目指由多个明细项目组成的一组检验项目，可理解为业务口径中的大项目。
4. 明细项目指具体检测项，可理解为业务口径中的小项目。
5. 平台标准项目应至少包含平台标准项目编码、平台标准项目名称、项目类型、项目状态。
6. 明细项目如归属于组合项目，应维护父级组合项目关系。
7. 组合项目可维护其包含的明细项目清单。
8. 项目状态包括启用、停用。
9. 只有启用的标准项目可以用于新申请创建。
10. 已创建申请保存创建时的项目快照，不因后续标准项目目录调整或停用而自动改变。
11. 标准项目目录的新增、修改、启用、停用由平台运营人员直接操作，保存后立即生效，不需审批。
12. 每次变更应记录操作人、操作时间、变更类型（新增/修改/停用/启用）和变更前后关键信息，可在项目详情中查看变更历史。

#### 1.12.3 标准项目目录不包含范围

当前版本标准项目目录不维护以下内容：

1. 样本类型要求或适用样本类型。
2. 价格、收费、退费、医保规则。
3. 医学参考范围。
4. 危急值阈值。
5. 检测方法学。
6. 检测设备、试剂、实验室内部规则。
7. 项目与患者年龄、性别、病区、床号等医学或院内业务规则。
8. 项目默认加急规则。

#### 1.12.4 机构项目对照

1. 机构项目对照用于将发起机构项目编码映射为平台标准项目编码。
2. 机构项目对照维度为发起机构、机构项目编码和平台标准项目编码。
3. 同一发起机构下，一个启用的机构项目编码应唯一映射到一个启用的平台标准项目。
4. 机构项目可以对照到平台标准组合项目，也可以对照到平台标准明细项目。
5. 对照关系状态包括启用、停用。
6. 只有启用的对照关系可以用于新申请创建。
7. 对照关系停用后，不影响已创建申请中保存的项目快照。
8. 平台运营人员维护机构项目对照。
9. 发起机构用户可查看本机构项目对照。
10. 当前版本不提供发起机构自助维护并直接生效的项目对照能力；如需新增或调整对照，由发起机构通过线下或工单流程提交，平台运营人员维护后生效。
11. 对照关系的新增、修改、启用、停用由平台运营人员直接操作，保存后立即生效，仅影响后续新申请，不回溯已有申请。
12. 每次对照变更应记录操作人、操作时间、变更类型、发起机构、机构项目编码、变更前后映射关系。发起机构用户可在本机构项目对照页面查看变更历史。

#### 1.12.5 申请创建时的项目识别

1. 发起机构创建申请时，可以提交机构组合项目编码，也可以提交机构明细项目编码。
2. 平台按"发起机构 + 机构项目编码"查找启用的机构项目对照。
3. 查找到启用对照后，平台转换为对应的平台标准项目编码。
4. 如果机构项目对照到平台标准组合项目，申请保存平台标准组合项目编码，并应展示该组合项目包含的明细项目。
5. 如果机构项目对照到平台标准明细项目，申请保存平台标准明细项目编码。
6. 平台不要求机构同时提交组合项目和明细项目。
7. 如果机构项目编码不存在启用对照，或对照到的标准项目已停用，平台拒绝创建申请，不生成平台申请号，并提示机构项目未配置有效的平台标准项目对照。
8. 申请创建成功后，应保存机构原始项目编码、机构项目名称（如有）、机构提交顺序、项目加急标识、转换后的平台标准项目编码、平台标准项目名称和项目快照。
9. 后续标准项目目录或机构项目对照变更，不自动改写已创建申请的项目快照。

#### 1.12.6 项目与报告关系

1. 申请可包含多个平台标准项目编码。
2. 平台应展示组合项目及其包含的明细项目。
3. 平台不基于明细项目判断报告完整性、项目完成状态、项目重复覆盖或项目漏报。
4. 报告上传不强制声明报告覆盖项目范围。
5. 报告仍按申请维度维护一个报告业务对象，具体规则见 1.7（报告审核与发布）。
6. 项目加急由本次申请提交决定，平台标准项目目录不维护项目默认加急规则。

#### 1.12.7 验收标准

1. 平台运营人员可以维护平台标准项目目录。
2. 平台标准项目支持组合项目和明细项目。
3. 组合项目可维护其包含的明细项目清单。
4. 平台标准项目支持启用、停用状态。
5. 平台运营人员可以维护发起机构项目编码与平台标准项目编码的对照关系。
6. 机构项目对照支持启用、停用状态。
7. 发起机构用户可以查看本机构项目对照。
8. 当前版本不支持发起机构自助维护并直接生效的项目对照。
9. 创建申请时，平台能根据发起机构和机构项目编码转换为平台标准项目编码。
10. 无启用对照或对照到停用标准项目时，拒绝创建申请并提示机构项目未配置有效的平台标准项目对照。
11. 已创建申请保存项目快照、机构提交顺序和项目加急标识，不因后续目录或对照关系变更而自动改变。
12. 标准项目目录和机构项目对照的变更均无需审批，保存后立即生效，仅影响后续新申请。
13. 标准项目目录和机构项目对照的每次变更均应记录操作留痕，并可在对应页面查看变更历史。
14. 平台不基于明细项目判断报告完整性、项目完成状态、项目重复覆盖或项目漏报。

### 1.13 平台对外接口汇总

本章汇总平台提供给外部接入系统的全部对外接口能力。各接口的详细业务规则、前置条件和校验逻辑见对应章节，本章仅做概览索引。接口的具体对接信息项由接口设计文档定义。

#### 1.13.1 发起机构侧接口

以下接口由发起机构的外部接入系统（HIS/LIS）调用：

| 接口能力 | 说明 | 详细规则 |
|---------|------|---------|
| 创建申请 | 提交检验申请，生成平台申请单号 | 1.1.4 |
| 终止申请 | 停止申请后续业务流转 | 1.1.10 |
| 样本重新送检 | 发起新一轮样本流转 | 1.1.9 |
| 变更费用状态/绿色通道 | 更新申请的费用状态或绿色通道信息 | 1.1.13 |
| 创建包 | 将多个样本条码归集为业务包 | 1.2.8 |
| 样本送出 | 按条码/申请或按包送出样本，形成送出记录 | 1.3.2 |

#### 1.13.2 接收方/上传方侧接口

以下接口由接收方或上传方的外部接入系统（LIS/中间件）调用：

| 接口能力 | 说明 | 详细规则 |
|---------|------|---------|
| 获取待接收清单 | 查询待接收的送出记录及样本明细 | 1.4.2 |
| 样本接收确认 | 逐样本提交接收结果（正常接收/异常接收/未到货） | 1.4.5 |
| 回传检测开始 | 通知平台样本已进入检测中（可选） | 1.5.3 |
| 上传报告 | 提交报告 PDF、结构化结果（可选）和危急值信息（可选），同一申请再次上传时生成新版本 | 1.7.3、1.7.4、1.7.6、1.8.2 |

#### 1.13.3 医院侧接口

以下接口由发起机构的系统调用，用于回传处理结果：

| 接口能力 | 说明 | 详细规则 |
|---------|------|---------|
| 危急值处理回执 | 回传医院侧对危急值的确认或处理结果 | 1.9.9 |

#### 1.13.4 补充说明

1. 本章所列均为平台对外接口（API），由外部接入系统调用。对应的平台页面操作入口见各业务章节的"功能入口"或对应小节。
2. 当前版本不支持上述接口列表以外的对外接口能力。报告作废、报告审核等操作仅通过平台页面执行，不提供对外接口。
3. 各接口的具体字段、传输方式、安全控制规则由接口设计文档定义，不在本 PRD 展开。
4. 报告和危急值的推送通知（1.9）由平台主动向外部机构发起，不属于外部接入系统调用的接口范畴，因此未列入上述接口清单。

#### 1.13.5 验收标准

1. 平台对外接口汇总覆盖发起机构侧、接收方/上传方侧和医院侧全部对外接口能力。
2. 各接口的详细业务规则能在对应章节中找到。
3. 本章所列均为平台对外接口（API），不包含平台页面操作入口。
4. 报告作废、报告审核等仅通过平台页面执行的操作不在对外接口清单中。

## 2. 当前版本范围边界

### 2.1 当前版本不包含清单

当前版本明确不包含以下范围：

1. 不建设独立待办中心。
2. 不做危急值超时提醒和升级提醒。
3. 不做危急值处理附件。
4. 不做危急值批量处理。
5. 不单独提供危急值处理记录导出。
6. 不单独推送旧报告版本失效通知。
7. 推送系统的实现、失败处理、接口对接和运维规则由推送系统设计文档定义，不在本 PRD 展开。
8. 不在各业务模块详情页中展示系统接口排障信息。
9. 不支持独立业务运维与追溯查询导出。
10. 不定义权限系统中的角色模型、权限点配置、授权流程、组织范围和数据范围配置。
11. 不定义患者隐私脱敏规则。
12. 不定义外部系统不可用处理。
13. 不定义外部系统故障处理规则。
14. 不支持申请列表、报告列表、异常记录等业务数据的导出功能。
15. 不支持申请内项目级部分终止。
16. 不支持已终止申请的原样本条码用于创建新的平台申请。
17. 不支持将已终止申请下的样本自动关联到新的申请。
18. 不在终止申请章节定义系统对接细节。
19. 不做面向外部机构的终止申请推送通知。
20. 不做异常记录超时自动处理。异常记录创建后如长时间无人处理，状态将保持为待处理，需人工手动关闭。
21. 不支持同一申请下多个样本轮次并行流转、并行送出、并行接收或并行检测。
22. 不支持无异常记录触发的样本重新送检。
23. 不支持标准项目目录维护样本类型、价格、医保、参考范围、危急值阈值、检测方法学、设备、试剂和实验室内部规则。
24. 不支持发起机构自助维护并直接生效的项目对照。
25. 不支持项目加急等级、加急 SLA、加急超时提醒或加急升级提醒。
26. 不建设独立的业务运维与追溯查询页面。运维追溯通过各业务模块页面（申请详情、接收记录、异常处理、报告查询等）完成。
27. 不支持平台页面人工上传报告，不支持平台出具报告；报告只能由上传方通过平台对外接口提交。
28. 不支持物流追踪（运单号、物流状态、运输时效等）。样本送出后至接收前的运输环节不纳入平台管理范围。
29. 不支持申请创建后变更接收方。接收方属于核心业务字段，创建后不可修改。如选错接收方，应终止原申请后使用新样本条码重新创建。
30. 不支持平台人工登记医院侧危急值处理回执；医院侧危急值处理回执只允许由发起机构系统通过医院侧接口回传。

### 2.2 边界说明

1. 当前版本不包含清单用于明确范围边界，避免评审和开发误解。
2. 清单不表示未来版本承诺，只表达当前版本范围。
3. 各业务章节中如有局部边界说明，应与本清单保持一致。
4. 外部系统不可用、接口异常、系统故障等内容，不纳入当前 PRD 范围；如后续需要，由对应系统设计、技术方案或非功能需求文档单独定义。
5. 本 PRD 以业务规则、流程边界、状态变化、页面能力和业务留痕为主，不定义接口结构、传输方式、系统内部处理机制和非功能技术方案。
