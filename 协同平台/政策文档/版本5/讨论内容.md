# 版本5讨论内容

> 记录第五版需求细化过程中的讨论结论、暂定规则和后续整理方向。

## 1. 申请管理

### 1.1 当前目标

本轮先围绕“申请管理”明确功能边界、业务规则、异常场景、状态关系、接口与页面职责，以及需要团队确认的问题。

### 1.2 已确认工作方式

1. 第四版文档作为参考，不直接修改。
2. 第五版讨论内容和待确认问题统一放在 `版本5` 目录。
3. 每个功能按独立章节逐项讨论，先形成讨论记录，再整理为第五版修订稿。

### 1.3 申请管理初始拆解

申请管理需要重点明确以下内容：

1. 功能定位：平台接收机构侧已开立、已确认可送检的检验申请。
2. 使用入口：仅支持机构系统通过接口创建申请；平台页面不提供人工补录申请入口。
3. 创建规则：一平台申请对应一个样本条码；同一发起机构内，一个样本条码只能对应一个平台申请。
4. 项目规则：一个申请可包含多个平台标准项目编码，但平台不维护机构项目对照。
5. 状态关系：申请创建成功后，样本主状态进入待送出；申请状态与样本状态分开管理。
6. 取消规则：待送出可取消；送出撤回后回到待送出可取消；取消后不可恢复。
7. 不支持项：平台不生成条码、不打印条码、不支持申请内项目级部分取消、不处理收费结算。

### 1.4 已确认边界

#### 1.4.1 申请创建入口

结论：选择 A，仅支持机构系统接口创建申请。

规则说明：

1. 平台不承担开单职责，不作为医生或机构人员的检验申请录入系统。
2. 平台页面不提供正常业务下的人工补录申请入口。
3. 发起机构应在本地 HIS、LIS 或检验系统中完成开单、采样、条码生成和条码打印。
4. 平台只接收机构系统提交的已开立、已确认可送检的申请信息。
5. 平台页面可支持申请查询、明细查看、取消、流转追踪、异常排查和运维留痕，但不新增申请。

设计理由：

1. 可以避免平台扩大为开单系统，保持协同平台边界清晰。
2. 患者、医嘱、收费、条码打印等前置业务仍由机构本地系统负责。
3. 减少人工录入造成的患者信息、项目编码、条码和接收方错误。
4. 便于后续接口、权限、留痕和责任边界设计。

#### 1.4.2 重复提交与重复条码

结论：选择 B，同一机构申请号 + 同一条码 + 核心信息一致时，返回已有平台申请；核心信息不一致时拒绝创建。

规则说明：

1. 平台以发起机构、机构申请号、样本条码作为重复提交判断的主要依据。
2. 如果重复提交的机构申请号、样本条码和核心申请信息一致，平台不创建新申请，返回已有平台申请单号和当前申请状态。
3. 如果机构申请号相同但样本条码不同，平台拒绝创建，并返回重复申请号但条码不一致的错误。
4. 如果样本条码相同但机构申请号不同，平台拒绝创建，并返回条码已被占用的错误。
5. 如果机构申请号和样本条码相同，但患者摘要、项目、接收方等核心信息不一致，平台拒绝创建，并提示重复提交内容与原申请不一致。
6. 该规则用于业务层面的重复提交处理；接口幂等字段、请求流水号和重复请求窗口等技术规则在接口设计阶段细化。

核心信息建议包括：

1. 发起机构。
2. 机构申请号。
3. 样本条码。
4. 患者唯一标识或患者摘要关键字段。
5. 平台标准项目编码清单。
6. 接收方。

设计理由：

1. 支持机构系统因网络超时或调用重试导致的重复提交。
2. 避免同一条码或同一机构申请号生成多个平台申请。
3. 将“可容错重试”和“业务数据冲突”区分处理。
4. 不把接口幂等技术细节提前写死在 PRD 中。

#### 1.4.3 申请创建后的字段修改

结论：选择 A，申请创建成功后不支持修改核心业务字段；如核心业务字段错误，应取消原申请后重新提交。

核心业务字段包括：

1. 发起机构。
2. 机构申请号。
3. 样本条码。
4. 患者唯一标识或患者摘要关键字段。
5. 就诊摘要关键字段。
6. 平台标准项目编码清单。
7. 接收方。
8. 样本类型等影响送检、接收和检测判断的字段。

规则说明：

1. 申请创建成功后，平台不提供核心业务字段修改功能。
2. 如果机构发现核心业务字段错误，应在允许取消的状态下取消原申请，再由机构系统重新提交新的申请。
3. 如果申请已经送出、接收、检测或上传报告，不允许通过修改申请字段修正业务错误，应走异常处理、报告重传或报告撤回等后续流程。
4. 费用状态、绿色通道、备注、联系电话等非核心字段是否允许更新，暂不纳入申请核心修改规则，后续在“费用状态和绿色通道是否参与流程控制”问题中统一讨论。
5. 平台应保留申请创建时的原始请求摘要和创建结果，便于追溯。

设计理由：

1. 避免申请字段变化导致样本、送出记录、接收记录、报告和推送记录含义前后不一致。
2. 保持“一个平台申请 + 一个样本条码”的业务对象稳定。
3. 将源头错误通过取消重提或异常处理解决，而不是在平台中覆盖历史数据。

#### 1.4.4 多机构条码唯一性与接收定位

结论：样本条码不要求全平台唯一，唯一性范围限定为同一发起机构内；接收接口必须传入发起机构ID和样本条码，平台按“发起机构ID + 样本条码”定位样本。

背景说明：

1. 平台需要对接多家医院或机构系统，各机构条码生成规则可能不同。
2. 不同机构之间可能生成相同的条码字符串。
3. 如果平台仅按条码字符串做全平台唯一，会误判不同机构的样本为重复样本。

规则说明：

1. 申请创建时，平台校验“发起机构ID + 样本条码”在平台内不可重复绑定多个平台申请。
2. 不同发起机构可以存在相同样本条码。
3. 接收接口必须传入接收方机构ID、发起机构ID和样本条码。
4. 平台接收样本时，按“发起机构ID + 样本条码”查找平台申请和样本。
5. 如果接收接口只传样本条码、不传发起机构ID，平台不应自动模糊匹配，应返回参数缺失或无法定位样本。
6. 平台页面扫码接收时，可以通过先选择发起机构、送出记录或包来确定发起机构，再连续扫码。
7. 按包接收时，如果包内样本已明确发起机构，平台可根据包内样本关系定位每个条码；具体包是否允许跨发起机构样本，放到“样本打包管理”章节讨论。

设计理由：

1. 兼容多医院、多厂商条码规则不一致的实际情况。
2. 避免不同机构相同条码导致误接收、误查询或误报告。
3. 接口责任边界清晰，接收方系统必须提供足够定位样本的信息。
4. 页面可通过选择上下文降低扫码操作复杂度，但底层定位规则保持明确。

#### 1.4.5 申请取消后的条码复用

结论：同一发起机构内，申请取消后原样本条码不可再次用于创建新的平台申请。

规则说明：

1. 条码唯一性按“发起机构ID + 样本条码”判断。
2. 同一发起机构内，一个样本条码一旦创建过平台申请，即使申请后续被取消，也不可再次绑定新的平台申请。
3. 不同发起机构之间允许存在相同样本条码，不受该规则影响。
4. 申请取消后，平台保留原申请、原条码、取消时间、取消原因、操作人或调用系统。
5. 如机构需要重新送检，应由机构本地系统生成新的样本条码，并重新提交新的平台申请。

设计理由：

1. 避免同一发起机构内同一条码在历史上对应多个平台申请。
2. 便于送出、接收、异常、报告和推送记录追溯。
3. 避免接收方或查询方仅凭条码时出现历史含义混淆。

#### 1.4.6 多项目申请与报告拆分

结论：选择 B，同一申请/同一样本条码下允许存在多份报告，每份报告可以覆盖一个或多个检验项目。

规则说明：

1. 一个平台申请可以包含多个平台标准项目编码。
2. 平台申请、样本送出、样本接收、样本异常和样本主状态仍按整个申请和样本条码处理。
3. 当上传方提供报告名称、报告类型或覆盖项目范围时，平台可用于展示；当前版本不强制要求报告上传接口显式传入覆盖项目范围。
4. 同一申请/同一样本条码下允许上传多份报告，不要求所有项目必须合并到一份报告中。
5. 一份报告可以覆盖一个项目，也可以覆盖多个项目。
6. 平台不基于项目覆盖范围判断同一项目是否被多份当前有效报告重复覆盖。
7. 报告查询时，应能展示报告对应的申请、样本条码、报告名称或报告类型、上传时间和版本状态。

设计理由：

1. 兼容同一条码下不同项目分时完成、分报告上传的实际情况。
2. 保持样本流转按条码管理，报告管理按报告版本和发布状态管理。
3. 避免强制一条码一报告导致接收方 LIS 出报告方式受限。

后续已确认：

1. 报告上传接口不强制传入报告覆盖的项目编码清单。
2. 如果报告 PDF 中已有项目内容，平台只保存并展示报告 PDF，不强制结构化拆分报告覆盖项目。
3. 如果不传覆盖项目范围，平台不判断同一项目是否被多份有效报告重复覆盖。
4. 报告查询以申请、样本条码、报告名称或报告类型、上传时间和版本状态为主，不要求按项目过滤。

#### 1.4.7 费用状态与绿色通道

结论：选择 A，费用状态和绿色通道只记录、展示和查询，不阻断申请创建、样本送出、样本接收、检测和报告流程。

规则说明：

1. 平台不负责收费、退费、医保结算和费用规则判断。
2. 机构创建申请时可以传入费用状态和绿色通道信息。
3. 费用状态建议包括：已收费、未收费、无需收费、未知。
4. 绿色通道信息建议包括：是否绿色通道、绿色通道原因或说明。
5. 未收费或未知费用状态不阻断申请创建。
6. 未收费或未知费用状态不阻断样本打包、送出、接收、检测、报告上传和报告发布。
7. 绿色通道信息只作为接收方优先级判断、人工识别和业务核对参考，不改变平台主流程。

设计理由：

1. 收费和医保结算属于机构本地系统或医院收费系统职责。
2. 避免平台因费用信息不完整影响绿色通道、先检后付等业务场景。
3. 保持协同平台聚焦申请、样本流转、报告和追溯。

#### 1.4.8 申请取消规则

结论：选择 A，仅样本处于待送出时允许取消申请。

规则说明：

1. 申请创建成功后，样本主状态进入待送出，此时允许取消申请。
2. 如果样本已送出但接收方尚未接收，不允许直接取消申请。
3. 已送出未接收时，如业务确需取消，应先执行送出撤回；撤回成功后样本回到待送出，再取消申请。
4. 样本处于已接收、检测中、检测完成或已有报告时，不允许取消申请。
5. 申请取消后不可恢复。
6. 申请取消后，不允许继续打包、送出、接收、检测、上传报告和推送报告。
7. 取消申请时必须记录取消原因、取消时间、操作人或调用系统。
8. 申请取消后，原样本条码在同一发起机构内不可再次创建新的平台申请。

设计理由：

1. 取消申请属于源头终止动作，应限制在样本尚未进入中心流转前。
2. 已送出样本已有交接行为，应通过送出撤回处理物流和交接关系。
3. 已接收、检测或报告后的问题应进入异常处理、报告重传或报告撤回流程，不应通过取消申请解决。

#### 1.4.9 申请查询与明细展示

结论：选择 A，申请查询作为申请管理基础能力提供。

规则说明：

1. 平台应支持申请列表查询和申请详情查看。
2. 查询条件建议包括：平台申请单号、机构申请号、发起机构、样本条码、患者摘要关键字、申请时间、申请状态、样本主状态、接收方。
3. 普通机构用户只能查询本机构发起的申请，或按授权范围查询与本机构相关的申请。
4. 接收方用户可查询提交给本接收方的申请。
5. 平台管理端授权用户可按权限查询全平台申请。
6. 申请详情应展示申请基础信息、患者摘要、就诊摘要、样本条码、项目清单、接收方、费用状态、绿色通道、申请状态、样本主状态和关键时间。
7. 申请详情可展示包、申请批次、送出、接收、异常、报告和推送的摘要信息。
8. 包、批次、送出、接收、异常、报告和推送的完整明细，应跳转到对应功能模块或业务运维明细页面查看。
9. 申请查询不是统计报表，不提供排行、趋势、汇总分析等能力。

设计理由：

1. 申请是后续样本流转和报告追溯的入口，需要基础查询能力。
2. 查询详情只展示跨模块摘要，避免申请管理章节承载所有业务明细。
3. 权限按机构和接收关系隔离，避免跨机构查看患者和报告信息。

#### 1.4.10 申请状态定义

结论：选择 A，申请状态只包括有效、已取消。

规则说明：

1. 申请状态用于表达平台申请本身是否仍然有效。
2. 申请创建成功后，申请状态为有效。
3. 申请取消成功后，申请状态为已取消。
4. 样本流转状态不写入申请状态，由样本主状态单独表达。
5. 样本主状态包括：待送出、已送出、已接收、检测中、检测完成。
6. 报告状态、异常状态、推送状态分别由报告、异常、推送相关对象承载。
7. 不设置申请已完成状态；检测完成、报告发布等结果由样本和报告状态体现。

设计理由：

1. 避免申请状态与样本状态重复。
2. 申请管理只负责申请是否成立、是否取消。
3. 样本、报告、异常、推送各自管理状态，便于后续模块独立设计。

### 1.5 申请管理验收标准

1. 能通过机构系统接口创建平台申请，并返回平台申请单号。
2. 平台页面不提供正常业务下的人工补录申请入口。
3. 一个平台申请只能对应一个样本条码。
4. 同一发起机构内，一个样本条码不能重复绑定多个平台申请。
5. 不同发起机构允许存在相同样本条码。
6. 重复提交时，发起机构、机构申请号、样本条码和核心信息一致的，返回已有平台申请单号和当前状态。
7. 重复提交时，机构申请号、样本条码或核心信息与原申请不一致的，拒绝创建并返回明确错误。
8. 创建成功后，申请状态为有效，样本主状态为待送出。
9. 申请创建成功后，不允许修改患者、条码、项目、接收方等核心业务字段。
10. 待送出状态允许取消申请。
11. 已送出未接收的申请不能直接取消，应先撤回送出，样本回到待送出后再取消。
12. 已接收、检测中、检测完成或已有报告的申请不能取消。
13. 申请取消后不可恢复，且同一发起机构内原样本条码不可复用。
14. 费用状态和绿色通道信息可以记录、展示和查询，但不阻断申请创建、样本送出、样本接收、检测和报告流程。
15. 支持申请列表查询和申请详情查看，并按发起机构、接收方和平台管理权限隔离数据。
16. 申请详情能展示申请基础信息、患者摘要、项目清单、样本条码、接收方、费用状态、绿色通道、申请状态、样本主状态和关键流转摘要。

### 1.6 接口字段与错误码边界

结论：选择 A + C。第五版 PRD 的申请管理章节只写必填字段类别和关键业务校验，不展开完整接口字段清单、错误码、幂等字段、签名规则和响应结构；完整接口细节后续单独形成接口设计文档。

PRD 中需要覆盖的字段类别：

1. 发起机构信息。
2. 机构申请号。
3. 样本条码。
4. 患者摘要。
5. 就诊摘要。
6. 平台标准项目编码清单。
7. 接收方。
8. 费用状态。
9. 绿色通道信息。
10. 备注或扩展信息。

PRD 中需要覆盖的关键业务校验：

1. 必填信息不能为空。
2. 同一发起机构内样本条码不可重复绑定多个平台申请。
3. 不同发起机构允许相同样本条码。
4. 平台标准项目编码必须可识别、可用。
5. 接收方必须在允许提交范围内。
6. 重复提交时，核心信息一致返回已有申请，核心信息不一致拒绝。
7. 已取消条码在同一发起机构内不可复用。

后续接口设计文档需要覆盖：

1. 完整请求字段、字段类型、长度、枚举值和是否必填。
2. 响应结构。
3. 错误码。
4. 接口幂等字段和重复请求处理窗口。
5. 签名、鉴权和调用方身份识别。
6. 字段映射、扩展字段和兼容策略。

### 1.7 本轮待讨论边界

1. 报告上传接口是否必须传入报告覆盖项目范围：已在“报告审核与发布”章节确认不强制传入。
2. 是否可以开始整理“申请管理”第五版章节草稿。

## 2. 样本打包管理

### 2.1 当前目标

本轮围绕“样本打包管理”明确包的业务定位、包内样本范围、创建与调整规则、作废规则、与送出和接收的关系，以及需要团队确认的问题。

### 2.2 已确认边界

#### 2.2.1 包内样本机构范围

结论：选择 A，一个包只能包含同一发起机构的样本。

规则说明：

1. 包是平台内用于样本归集、送出、接收和追溯的业务对象。
2. 一个包只能绑定同一发起机构下的样本。
3. 不允许在同一个包内混装多个发起机构的样本。
4. 包创建后，应记录包所属发起机构。
5. 向包内加入样本时，平台校验样本发起机构必须与包所属发起机构一致。
6. 按包接收时，平台可通过包确定发起机构，再结合包内样本条码定位样本。

设计理由：

1. 与“发起机构ID + 样本条码”定位样本的规则一致。
2. 避免不同机构相同条码在同一个包内造成识别和接收歧义。
3. 降低按包送出、按包接收、送出撤回和异常处理复杂度。
4. 便于现场人员按机构进行交接和核对。

#### 2.2.2 入包样本范围

结论：选择 A，仅允许申请有效且样本主状态为待送出的样本加入包。

规则说明：

1. 只有申请状态为有效的样本可以加入包。
2. 只有样本主状态为待送出的样本可以加入包。
3. 已取消申请对应的样本不能加入包。
4. 已送出、已接收、检测中、检测完成或已有报告的样本不能加入包。
5. 平台向包内加入样本时，应校验样本所属发起机构、申请状态和样本主状态。

设计理由：

1. 包主要服务于送出前样本归集。
2. 避免已经进入送出、接收、检测或报告流程的样本被重新归集，导致流转追溯混乱。
3. 保持送出记录快照稳定，不因后续入包动作改变既有交接含义。

#### 2.2.3 包内样本调整

结论：选择 B，包未送出前允许加入或移出样本；包送出后不允许调整包内样本。

规则说明：

1. 包处于未送出状态时，允许向包内加入符合入包条件的样本。
2. 包处于未送出状态时，允许从包内移出样本。
3. 包送出后，包内样本关系锁定，不允许继续加入或移出样本。
4. 包内样本调整必须记录调整时间、操作人或调用系统、调整动作和调整前后样本清单摘要。
5. 从包内移出的样本，如申请有效且样本仍为待送出，可继续按条码送出或加入其他符合规则的包。
6. 包内样本调整不改变样本主状态；样本主状态仍由送出、接收、检测等动作驱动。

设计理由：

1. 支持送出前现场误扫、漏扫、错扫的纠正。
2. 包送出后锁定样本关系，确保包送出和接收追溯口径一致。
3. 避免包当前样本清单与送出时样本清单产生冲突。

#### 2.2.4 包作废规则

结论：选择 A，仅未送出的包允许作废，作废后不可恢复。

规则说明：

1. 包未送出前允许作废。
2. 包送出后不允许作废。
3. 包作废后不可恢复有效。
4. 包作废后不允许继续加入、移出或调整样本。
5. 包作废不改变包内样本的申请状态和样本主状态。
6. 包作废后，包内样本如申请有效且样本仍为待送出，可按条码送出或加入其他符合规则的包。
7. 包作废必须记录作废原因、作废时间、操作人或调用系统。
8. 已送出包如果需要撤回，应走送出撤回；如果接收时发现问题，应走接收异常或样本异常处理，不通过包作废处理。

设计理由：

1. 包作废用于处理送出前的包创建错误。
2. 已送出包已经形成交接语义，应由送出记录、接收记录和异常记录处理后续问题。
3. 避免“包作废”和“送出撤回”概念混淆。

#### 2.2.5 打包流程属性

结论：选择 A，打包是可选流程，不是申请创建、样本送出、样本接收、检测和报告的必经流程。

规则说明：

1. 样本可以不打包，直接按条码或申请送出。
2. 样本也可以先加入包，再按包送出。
3. 未打包样本可以正常送出、接收、检测、上传报告和查询追溯。
4. 打包只影响样本归集、按包送出、按包接收和包维度追溯，不改变样本主状态。
5. 包不承载样本流转状态，样本流转状态仍由样本主状态表达。

设计理由：

1. 兼容不同机构、小批量送检、单样本送检和批量送检场景。
2. 避免把简单送检流程强制复杂化。
3. 保持包作为可选归集对象，而不是必经流程单据。

#### 2.2.6 样本归包唯一性

结论：选择 A，一个样本同一时间最多属于一个有效未送出包。

规则说明：

1. 同一样本不能同时存在于多个有效未送出包中。
2. 向包内加入样本时，平台应校验该样本当前是否已属于其他有效未送出包。
3. 如果样本已属于其他有效未送出包，平台拒绝加入新包，并提示样本已在其他包中。
4. 样本从原包移出后，如仍满足入包条件，可以加入其他包。
5. 原包作废后，包内样本如仍满足入包条件，可以加入其他包。
6. 包送出后，样本已进入已送出状态，不允许再加入其他包。

设计理由：

1. 避免同一样本被多个包重复送出。
2. 保持包与样本送出关系清晰。
3. 降低现场核对和平台追溯复杂度。

### 2.3 样本打包管理验收标准

1. 能创建包，并记录包所属发起机构。
2. 一个包只能包含同一发起机构的样本。
3. 不允许在同一个包内混装多个发起机构的样本。
4. 只能将申请有效且样本主状态为待送出的样本加入包。
5. 已取消、已送出、已接收、检测中、检测完成或已有报告的样本不能加入包。
6. 同一样本同一时间不能属于多个有效未送出包。
7. 包未送出前允许加入和移出样本，并记录调整留痕。
8. 包送出后包内样本关系锁定，不能继续加入或移出样本。
9. 未送出的包允许作废，作废后不可恢复。
10. 包送出后不允许作废。
11. 包作废不改变包内样本的申请状态和样本主状态。
12. 包作废后，包内样本如仍满足入包条件，可以加入其他包或按条码送出。
13. 打包是可选流程，未打包样本仍可正常按条码或申请送出。
14. 包不承载样本主状态，样本状态仍由送出、接收、检测等动作驱动。
15. 包维度能查询当前样本清单和包内样本变更记录。

### 2.4 本轮待讨论边界

1. 样本打包管理是否需要补充接口字段边界。
2. 是否可以开始讨论下一个功能“申请批次管理”。

## 3. 申请批次管理

### 3.1 当前目标

本轮围绕“申请批次管理”明确申请批次的业务定位、归集范围、调整规则、作废规则、与样本送出/接收的边界，以及需要团队确认的问题。

### 3.2 已确认边界

#### 3.2.1 申请批次功能定位

结论：选择 A，申请批次只做申请归集、查询和核对，不参与样本送出、样本接收和样本状态流转。

规则说明：

1. 申请批次是平台内用于归集多个平台申请的管理对象。
2. 申请批次用于分类、查询、管理、核对和业务追溯。
3. 申请批次不是包。
4. 申请批次不是送出入口。
5. 申请批次不是接收入口。
6. 申请批次不承载样本流转状态。
7. 批次内申请和样本的送出、接收、检测、报告等状态由对应业务对象单独表达。

设计理由：

1. 避免申请批次与包、送出记录、接收记录混用。
2. 保持样本送出入口为条码/申请或包，接收入口为条码或包。
3. 申请批次只作为管理和核对维度，降低流程复杂度。

#### 3.2.2 申请归属批次唯一性

结论：选择 A，一个申请同一时间最多属于一个有效申请批次。

规则说明：

1. 一个平台申请同一时间最多归属于一个有效申请批次。
2. 将申请加入批次时，平台应校验该申请当前是否已属于其他有效批次。
3. 如果申请已属于其他有效批次，平台拒绝加入，并提示申请已在其他批次中。
4. 申请从原批次移出后，可以加入其他有效批次。
5. 平台应保留申请加入批次、移出批次和调整批次归属的变更记录。
6. 历史批次归属记录用于追溯，不影响申请当前批次归属判断。

设计理由：

1. 避免同一申请在多个有效批次中重复核对。
2. 支持批次归集错误后的纠正。
3. 通过历史记录保留批次调整过程，兼顾追溯和当前管理口径。

#### 3.2.3 批次内申请机构范围

结论：选择 A，一个申请批次只能包含同一发起机构的申请。

规则说明：

1. 创建申请批次时，应明确批次所属发起机构。
2. 批次只能加入同一发起机构下的申请。
3. 不允许在同一申请批次内混入多个发起机构的申请。
4. 将申请加入批次时，平台应校验申请发起机构与批次所属发起机构一致。
5. 不同发起机构如需分别核对，应分别创建各自的申请批次。
6. 平台管理端如需跨机构查看，可通过查询条件或后续统计分析能力实现，不通过申请批次实现跨机构汇总。

设计理由：

1. 保持批次权限、查询和核对口径清晰。
2. 避免批次内出现跨机构患者信息展示和权限隔离问题。
3. 与样本包“同一包只能包含同一发起机构样本”的边界保持一致。

#### 3.2.4 批次调整与作废

结论：采用轻量方案，申请批次状态只包括有效、已作废；有效批次允许加入或移出申请，已作废批次不允许调整。不设置关闭、锁定、解锁和可锁定提示。

规则说明：

1. 申请批次状态包括：有效、已作废。
2. 批次创建成功后，状态为有效。
3. 有效批次允许加入符合规则的申请。
4. 有效批次允许从批次中移出申请。
5. 已作废批次不允许继续加入或移出申请。
6. 批次作废后不可恢复有效。
7. 批次作废不改变批次内申请状态、样本主状态、送出状态、接收状态或报告状态。
8. 批次作废只表示该批次分组不再继续使用，不表示批次内申请或样本流程终止。
9. 平台不提供批次关闭、批次锁定、批次解锁和可锁定提示。
10. 批次加入、移出、作废操作必须记录操作时间、操作人或调用系统、操作对象和原因。

设计理由：

1. 申请批次只是申请分组和核对维度，不应扩展成流程管理模块。
2. 取消关闭、锁定和解锁，减少功能复杂度。
3. 保留作废能力，用于处理批次建错、重复创建或不再使用的场景。
4. 批次调整不影响样本流转，保持批次与送出、接收、检测、报告解耦。

### 3.3 申请批次管理验收标准

1. 能创建申请批次，并记录批次所属发起机构。
2. 申请批次只用于申请归集、查询、核对和追溯。
3. 申请批次不作为送出入口。
4. 申请批次不作为接收入口。
5. 申请批次不承载样本流转状态。
6. 一个批次只能包含同一发起机构的申请。
7. 一个申请同一时间最多属于一个有效批次。
8. 有效批次允许加入和移出申请。
9. 已作废批次不允许加入或移出申请。
10. 批次作废后不可恢复有效。
11. 批次作废不影响批次内申请、样本、送出、接收、检测、报告状态。
12. 平台不提供批次关闭、锁定、解锁和可锁定提示。
13. 批次加入、移出、作废操作应记录操作留痕。
14. 能按批次查询当前申请清单。

### 3.4 本轮待讨论边界

1. 申请批次管理是否需要补充接口字段边界。
2. 是否可以开始讨论下一个功能“样本送出管理”。

## 4. 样本送出管理

### 4.1 当前目标

本轮围绕“样本送出管理”明确送出入口、送出条件、送出记录、送出快照、送出撤回、与包和申请批次的边界，以及需要团队确认的问题。

### 4.2 已确认边界

#### 4.2.1 送出入口

结论：选择 A，样本送出只支持按条码/申请送出和按包送出。

规则说明：

1. 支持按单个或多个样本条码送出。
2. 支持按平台申请或机构申请定位样本后送出。
3. 支持按包送出。
4. 不支持按申请批次送出。
5. 未打包样本可以按条码或申请送出。
6. 已打包且未送出的样本可以按包送出。
7. 申请批次只用于归集、查询和核对，不作为送出入口。

设计理由：

1. 与“打包是可选流程”的规则一致。
2. 与“申请批次不参与样本流转”的规则一致。
3. 保持送出入口简单，避免包、申请批次和送出记录混用。

#### 4.2.2 送出样本范围

结论：选择 A，仅申请有效、样本主状态为待送出、目标接收方明确的样本允许送出。

规则说明：

1. 申请状态必须为有效。
2. 样本主状态必须为待送出。
3. 样本必须有明确接收方。
4. 已取消申请对应的样本不允许送出。
5. 已送出、已接收、检测中、检测完成或已有报告的样本不允许再次送出。
6. 送出撤回成功后，样本主状态回到待送出，满足其他条件时可以再次送出。
7. 异常退回后的样本是否允许再次送出，应由样本异常处理结果决定，不在送出管理中默认放开。

设计理由：

1. 送出是样本进入跨机构流转的起点，应限制在有效申请和待送出样本上。
2. 避免同一样本重复形成多个有效送出行为。
3. 将异常退回后的后续处理交由异常处理模块决定，避免送出管理越界。

#### 4.2.3 按包送出校验

结论：选择 A，按包送出时整包校验；任一样本不满足送出条件，则整包不能送出。

规则说明：

1. 按包送出前，平台应校验包状态、包所属发起机构、包内样本清单和每个样本的送出条件。
2. 包内所有样本均满足送出条件时，允许整包送出。
3. 包内任一样本不满足送出条件时，整包送出失败。
4. 平台不自动移除不满足条件的样本。
5. 平台不支持同一包内部分样本送出、部分样本保留未送出。
6. 如包内存在不满足条件的样本，应在包未送出前由用户手动调整包内样本后再送出。

设计理由：

1. 保持包送出的业务语义完整。
2. 避免一个包出现部分送出、部分未送出的复杂状态。
3. 避免系统自动调整包内样本导致现场核对和追溯不一致。

#### 4.2.4 送出记录与送出快照

结论：送出成功后必须形成送出记录和不可变送出快照。

规则说明：

1. 每次送出成功后，平台生成一条送出记录。
2. 送出记录应包含送出记录号。
3. 送出记录应记录送出方式，包括按条码/申请送出、按包送出。
4. 送出记录应记录发起机构、接收方、送出时间、操作人或调用系统。
5. 送出记录应记录本次送出的样本清单。
6. 每个样本的送出快照应至少包含平台申请号、机构申请号、样本条码、患者摘要关键字段、平台标准项目编码清单。
7. 按包送出时，送出记录应记录包号和送出时包内样本清单。
8. 送出记录可记录送出备注。
9. 送出记录后续应能展示撤回状态和接收侧处理结果摘要。
10. 送出快照形成后，不因后续包调整、申请批次调整、患者摘要变化或其他对象变化而改变。

设计理由：

1. 送出记录用于证明一次样本交接动作已经发生。
2. 送出快照用于固定送出当时的样本清单和关键业务信息。
3. 不可变快照可以避免后续对象变化影响历史追溯。

#### 4.2.5 送出后的状态变化

结论：选择 A，送出成功后样本主状态进入已送出；按包送出后，包记录已用于送出，但包不承载样本主状态。

规则说明：

1. 样本送出成功后，样本主状态由待送出变为已送出。
2. 按条码/申请送出时，送出记录直接关联样本清单。
3. 按包送出时，送出记录关联包号和送出时包内样本清单。
4. 按包送出成功后，包应记录已用于送出。
5. 包已用于送出后，包内样本关系锁定，不允许继续加入或移出样本。
6. 包已用于送出后，不允许作废包。
7. 包不承载样本主状态，样本主状态仍由样本对象表达。
8. 送出记录承载本次送出动作和送出快照，包只作为送出时的归集对象和追溯维度。

设计理由：

1. 样本主状态表达样本真实流转阶段。
2. 包记录已用于送出，是为了控制包后续调整和作废。
3. 避免包状态与样本状态重复或冲突。

#### 4.2.6 送出撤回

结论：选择 B，已送出未接收的样本允许全部或部分撤回；已接收样本不能撤回。

规则说明：

1. 送出撤回只适用于样本主状态为已送出且尚未被接收的样本。
2. 已接收、检测中、检测完成或已有报告的样本不能撤回送出。
3. 支持撤回一条送出记录中的全部未接收样本。
4. 支持撤回一条送出记录中的部分未接收样本。
5. 部分撤回后，送出记录继续保留，未撤回样本继续处于已送出并等待接收。
6. 撤回成功的样本主状态回到待送出。
7. 撤回成功的样本满足送出条件时，可以再次按条码/申请送出。
8. 按包送出的样本发生部分撤回时，不改变原送出快照。
9. 按包送出后，无论是否撤回，包仍保留已用于送出的历史标记，包内样本关系不因撤回而重新开放调整。
10. 送出撤回必须记录撤回原因、撤回时间、操作人或调用系统、撤回样本清单。

设计理由：

1. 支持送出后、接收前发现送错或不应送出的纠错场景。
2. 已接收样本已经进入接收方流程，应通过接收异常或样本异常处理，不再通过送出撤回处理。
3. 保持送出快照不可变，避免撤回动作改变历史送出事实。

#### 4.2.7 送出记录状态

结论：选择 A，送出记录状态包括已送出、部分撤回、全部撤回、接收完成。

规则说明：

1. 送出记录创建成功后，状态为已送出。
2. 送出记录中部分样本被撤回，且仍存在未撤回样本时，状态为部分撤回。
3. 送出记录中全部样本均被撤回时，状态为全部撤回。
4. 送出记录中所有未撤回样本均已有接收侧处理结果后，状态可标记为接收完成。
5. 接收侧处理结果包括正常接收、异常退回或后续在接收管理中定义的其他接收结果。
6. 送出记录状态用于列表展示和业务追踪，不替代样本主状态。
7. 送出记录内每个样本仍应保留样本级撤回状态、接收状态和接收侧处理结果。

设计理由：

1. 送出记录总状态便于业务人员快速判断一条送出记录的处理进展。
2. 样本级结果用于准确追溯单个样本的撤回和接收情况。
3. 总状态和样本级结果结合，避免列表过重，也避免追溯信息丢失。

### 4.3 样本送出管理验收标准

1. 支持按条码/申请送出样本。
2. 支持按包送出样本。
3. 不支持按申请批次送出。
4. 仅申请有效、样本待送出、接收方明确的样本可送出。
5. 按包送出时整包校验，任一样本不满足条件则整包失败。
6. 送出成功后生成送出记录和不可变送出快照。
7. 送出成功后样本状态进入已送出。
8. 按包送出后包记录已用于送出，包内样本关系锁定。
9. 已送出未接收样本支持全部或部分撤回。
10. 已接收及后续状态样本不能撤回送出。
11. 撤回成功样本回到待送出。
12. 送出记录能展示已送出、部分撤回、全部撤回、接收完成。
13. 送出记录能展示样本级撤回状态和接收侧处理结果。
14. 送出快照不因后续包、批次或申请相关信息变化而改变。

## 5. 样本接收管理

### 5.1 当前目标

本轮围绕“样本接收管理”明确接收入口、接收条件、按条码接收定位规则、按包接收规则、异常接收边界、接收记录和状态变化，以及需要团队确认的问题。

### 5.2 已确认边界

#### 5.2.1 接收入口

结论：选择 A，样本接收只支持按条码接收和按包接收。

规则说明：

1. 支持按样本条码接收。
2. 支持按包接收。
3. 不支持按申请批次接收。
4. 按条码接收时，必须能明确发起机构ID和样本条码。
5. 按包接收时，平台根据包和送出记录定位包内样本。
6. 未打包样本可按条码接收。
7. 已按包送出的样本可按包接收，也可在满足规则时按条码逐个接收。

设计理由：

1. 与“申请批次不参与样本流转”的规则一致。
2. 与“打包是可选流程”的规则一致。
3. 接收入口保持为条码和包，便于处理未打包和已打包两类场景。

#### 5.2.2 接收样本范围

结论：选择 A，仅已送出、未撤回、接收方匹配的样本允许接收。

规则说明：

1. 样本主状态必须为已送出。
2. 样本不能处于已撤回送出状态。
3. 当前接收方必须与送出记录中的接收方一致。
4. 未送出的样本不能接收。
5. 已撤回送出的样本不能接收。
6. 已接收、检测中、检测完成或已有报告的样本不能重复接收。
7. 平台不会因接收未送出样本而自动补记送出记录。
8. 接收时必须能关联到有效的送出记录或送出快照。

设计理由：

1. 接收是对已送出样本的到达确认，不能脱离送出记录存在。
2. 避免未送出样本被接收后破坏送出和交接追溯。
3. 避免撤回后样本仍被接收，造成发起方和接收方状态冲突。

#### 5.2.3 按条码接收定位规则

结论：选择 A，接口按条码接收时必须传入发起机构ID。

规则说明：

1. 接收接口按条码接收时，必须传入接收方机构ID、发起机构ID和样本条码。
2. 平台按“发起机构ID + 样本条码”定位平台申请和样本。
3. 如果接口只传样本条码、不传发起机构ID，平台不应自动模糊匹配，应返回参数缺失或无法定位样本。
4. 页面扫码接收时，可以通过先选择发起机构、送出记录或包来确定发起机构，再连续扫码。
5. 不同发起机构存在相同条码时，平台按发起机构ID隔离识别，不视为重复样本。

设计理由：

1. 多机构接入场景下，样本条码不要求全平台唯一。
2. 接收接口必须提供足够定位样本的信息，避免误接收。
3. 页面可通过操作上下文降低录入成本，但底层定位规则保持一致。

#### 5.2.4 按包接收结果处理

结论：选择 B，按包接收允许逐样本给出接收结果。

规则说明：

1. 包只是批量接收入口，不强制包内所有样本使用同一接收结果。
2. 按包接收时，平台应展示或返回包内待接收样本清单。
3. 接收人员或接收方系统可以逐样本确认接收结果。
4. 样本级接收结果可以包括正常接收、异常退回、接收后异常处理等。
5. 包内部分样本正常接收时，正常样本进入已接收。
6. 包内部分样本异常时，异常样本按异常接收规则处理，不影响其他正常样本接收。
7. 包接收记录应能汇总展示包内各样本的接收结果。

设计理由：

1. 现实接收场景中，同一包内可能只有部分样本破损、漏送、信息不符或需退回。
2. 包是归集和批量操作对象，样本才是状态流转对象。
3. 逐样本结果能兼顾批量接收效率和异常处理准确性。

#### 5.2.5 接收异常处理路径

结论：选择 B，接收异常支持异常退回和接收后异常处理两类路径。

规则说明：

1. 接收时发现异常，可选择异常退回。
2. 异常退回时，平台登记异常和退回记录，样本不进入已接收。
3. 异常退回适用于样本破损、条码无法识别、样本漏送、样本不符、容器不符等不适合接收的情况。
4. 接收时发现异常，也可选择接收后异常处理。
5. 接收后异常处理时，样本先进入已接收，同时登记异常记录。
6. 接收后异常处理适用于样本可先接收，但需要后续补充说明、人工确认或继续跟进的情况。
7. 接收后异常处理的后续结果，包括继续检测、补充说明、退回、终止或关闭异常，在样本异常处理章节继续定义。
8. 异常退回和接收后异常处理均应记录异常类型、异常描述、发现时间、发现人或调用系统、处理意见。

设计理由：

1. 区分“不能接收”的异常和“可接收但需后续处理”的异常。
2. 避免所有异常都进入已接收，导致无法真实表达接收失败。
3. 支持实际业务中先接收再人工确认的场景。

#### 5.2.6 接收记录

结论：接收成功、异常退回或接收后异常处理时，均应形成接收记录或接收处理记录。

规则说明：

1. 接收记录应包含接收记录号。
2. 接收记录应记录接收方式，包括按条码接收、按包接收。
3. 接收记录应记录发起机构、接收方、接收时间、操作人或调用系统。
4. 接收记录应关联送出记录号。
5. 按包接收时，接收记录应关联包号。
6. 接收记录应记录本次处理的样本清单。
7. 每个样本应记录接收结果，包括正常接收、异常退回、接收后异常处理。
8. 如存在异常，应记录异常类型、异常描述和处理意见。
9. 接收记录可记录接收备注。
10. 接收记录应关联申请、样本条码、送出记录和接收方。

设计理由：

1. 接收记录用于证明接收方对样本进行过接收确认或异常处理。
2. 样本级接收结果用于支持按包接收时部分正常、部分异常的场景。
3. 与送出记录关联后，可以形成送出到接收的追溯链路。

#### 5.2.7 接收后样本状态变化

结论：选择 A，正常接收和接收后异常处理进入已接收；异常退回不进入已接收。

规则说明：

1. 样本正常接收后，样本主状态由已送出变为已接收。
2. 样本选择接收后异常处理时，样本主状态由已送出变为已接收，同时生成异常记录。
3. 样本选择异常退回时，样本不进入已接收。
4. 异常退回后的样本状态和后续处理方式，在样本异常处理章节定义。
5. 接收动作不直接将样本推进到检测中。
6. 检测中状态应由后续检测状态回传或检测流程触发。
7. 当送出记录中所有未撤回样本均已有接收侧处理结果后，送出记录可标记为接收完成。

设计理由：

1. 区分实际接收成功和接收失败。
2. 保持已接收状态只表示接收方已经确认接收样本。
3. 接收和检测分属不同业务环节，不在接收时直接进入检测中。

### 5.3 样本接收管理验收标准

1. 支持按条码接收。
2. 支持按包接收。
3. 不支持按申请批次接收。
4. 按条码接收接口必须传入接收方机构ID、发起机构ID和样本条码。
5. 仅已送出、未撤回、接收方匹配的样本允许接收。
6. 未送出样本不能接收，平台不自动补记送出记录。
7. 按包接收允许逐样本给出接收结果。
8. 正常接收后样本进入已接收。
9. 异常退回时样本不进入已接收。
10. 接收后异常处理时样本进入已接收并生成异常记录。
11. 接收记录能关联申请、样本条码、送出记录和接收方。
12. 按包接收记录能关联包并展示包内样本接收结果。
13. 接收完成后能回写或更新送出记录的接收侧处理结果摘要。

### 5.4 本轮待讨论边界

1. 样本接收管理是否需要补充接口字段边界。
2. 是否可以开始讨论下一个功能“样本异常处理”。

## 6. 样本异常处理

### 6.1 当前目标

本轮围绕“样本异常处理”明确异常来源、异常类型、异常处理路径、异常状态、退回与后续处理、与申请取消、送出撤回、报告重传/撤回的边界，以及需要团队确认的问题。

### 6.2 已确认边界

#### 6.2.1 异常处理范围

结论：选择 A，样本异常处理覆盖接收环节产生的异常，以及接收后人工发现的样本异常。

规则说明：

1. 样本异常处理只处理样本相关异常。
2. 接收时选择异常退回的样本，进入样本异常处理记录范围。
3. 接收时选择接收后异常处理的样本，进入样本异常处理记录范围。
4. 已接收后人工发现的样本破损、信息不一致、容器问题、样本量不足等样本问题，进入样本异常处理记录范围。
5. 申请信息错误应优先按申请取消、重新提交或业务协商处理，不纳入样本异常处理主范围。
6. 送出错误在接收前优先按送出撤回处理，不纳入样本异常处理主范围。
7. 报告内容错误按报告重传或报告撤回处理，不纳入样本异常处理主范围。
8. 推送失败按推送记录和推送管理处理，不纳入样本异常处理主范围。

设计理由：

1. 保持样本异常处理聚焦样本本身和接收后的样本问题。
2. 避免异常处理扩展成全平台异常中心。
3. 让申请、送出、报告、推送各模块按各自规则处理对应异常。

#### 6.2.2 异常状态与样本主状态关系

结论：选择 A，异常作为独立异常记录管理，不覆盖样本主状态。

规则说明：

1. 样本主状态仍按正常主链表达，包括待送出、已送出、已接收、检测中、检测完成。
2. 样本异常不作为样本主状态。
3. 异常处理状态由异常记录单独表达。
4. 异常记录状态建议包括：待处理、处理中、已关闭。
5. 一个样本可以存在异常记录，同时保留其当前样本主状态。
6. 接收后异常处理时，样本主状态可以为已接收，异常记录状态可以为待处理或处理中。
7. 异常退回时，样本不进入已接收，并生成异常记录和退回记录。

设计理由：

1. 避免异常状态打断样本正常主状态链。
2. 支持同一样本在已接收状态下仍存在待处理异常。
3. 异常记录与样本主状态分离，便于后续异常处理闭环和状态追溯。

#### 6.2.3 异常处理结果

结论：选择 A，异常处理结果包括继续检测、退回样本、终止处理、关闭异常。

规则说明：

1. 继续检测：样本虽存在异常记录，但业务判断可以继续后续检测流程。
2. 退回样本：样本需要退回发起机构或相关责任方。
3. 终止处理：样本不再继续后续检测或报告流程。
4. 关闭异常：异常已完成说明、确认或处理，不再需要继续跟进。
5. 补充说明作为处理意见记录，不作为独立处理结果。
6. 重新送出、重新创建申请、新条码等作为异常处理后的后续业务动作，不作为异常处理结果枚举。
7. 每次处理结果变更应记录处理时间、处理人或调用系统、处理意见。

设计理由：

1. 保持异常处理结果精简，避免异常模块变成复杂流程引擎。
2. 将说明类信息放入处理意见，避免结果枚举过多。
3. 将重新送出、重新创建申请等业务动作留给对应功能模块处理。

#### 6.2.4 异常退回后的样本处理

结论：选择 A，异常退回不进入已接收，不回到待送出；退回事实由异常记录和退回记录承载。

规则说明：

1. 接收时选择异常退回的样本，不进入已接收。
2. 异常退回后的样本不自动回到待送出。
3. 平台应生成异常记录和退回记录。
4. 退回记录应关联申请、样本条码、送出记录、接收方和退回原因。
5. 异常退回后的后续处理方式由异常处理结果和业务规则决定。
6. 如果后续需要重新送检，不由平台自动重送，应按异常处理后的业务动作处理。
7. 是否复用原申请、是否重新创建申请、是否使用新条码，在样本异常处理或后续业务规则中明确，不由异常退回动作自动决定。

设计理由：

1. 异常退回表示接收方没有完成样本接收，不能进入已接收。
2. 异常退回不等同于发起方送出前的待送出状态，不能直接回到待送出。
3. 退回事实应被独立追溯，避免覆盖原送出和接收处理过程。

#### 6.2.5 接收后异常处理与检测

结论：选择 A，接收后异常处理的样本允许继续检测，但必须有异常处理结果为继续检测或异常已关闭。

规则说明：

1. 接收后异常处理的样本主状态进入已接收，同时生成异常记录。
2. 异常记录处于待处理或处理中时，默认不允许进入检测中或检测完成。
3. 异常处理结果为继续检测时，允许样本继续进入检测流程。
4. 异常记录已关闭且未标记终止处理时，允许样本继续进入检测流程。
5. 异常处理结果为退回样本或终止处理时，不允许继续检测。
6. 是否继续检测应记录处理意见、处理时间、处理人或调用系统。

设计理由：

1. 保留异常对检测流程的控制作用。
2. 支持轻微异常或可补充说明的样本继续检测。
3. 避免存在未处理异常的样本直接进入检测或报告流程。

#### 6.2.6 异常记录内容

结论：异常记录应能支撑样本异常来源、处理过程、处理结果和退回追溯。

规则说明：

1. 异常记录应包含异常记录号。
2. 异常记录应关联平台申请号、发起机构、接收方和样本条码。
3. 异常记录应关联送出记录号。
4. 如样本已接收，异常记录应关联接收记录号。
5. 异常记录应记录异常来源，包括接收异常退回、接收后异常、已接收后人工登记。
6. 异常记录应记录异常类型和异常描述。
7. 异常记录应记录发现时间、发现人或调用系统。
8. 异常记录应记录异常状态，包括待处理、处理中、已关闭。
9. 异常记录应记录处理结果，包括继续检测、退回样本、终止处理、关闭异常。
10. 异常记录应记录处理意见、处理时间、处理人或调用系统。
11. 如处理结果涉及退回样本，应关联退回记录。

设计理由：

1. 异常记录需要支持从发现、处理到关闭的完整追溯。
2. 与申请、样本、送出、接收记录关联后，可以定位异常发生的业务上下文。
3. 处理结果和处理意见分开记录，既便于查询统计，也保留人工说明。

### 6.3 样本异常处理验收标准

1. 能记录接收异常退回、接收后异常、已接收后人工登记的样本异常。
2. 样本异常以独立异常记录管理，不覆盖样本主状态。
3. 异常记录状态包括待处理、处理中、已关闭。
4. 异常处理结果包括继续检测、退回样本、终止处理、关闭异常。
5. 异常退回不进入已接收，也不回到待送出。
6. 异常退回生成异常记录和退回记录。
7. 接收后异常处理样本进入已接收并生成异常记录。
8. 接收后异常未处理完成前，默认不允许进入检测中或检测完成。
9. 处理结果为继续检测，或异常已关闭且未终止处理时，允许继续检测。
10. 处理结果为退回样本或终止处理时，不允许继续检测。
11. 异常记录能关联申请、样本条码、送出记录、接收记录和退回记录。
12. 异常处理过程能记录处理意见、处理时间、处理人或调用系统。

### 6.4 本轮待讨论边界

1. 样本异常处理是否需要补充接口字段边界。
2. 是否可以开始讨论下一个功能“样本状态管理”。

## 7. 样本状态管理

### 7.1 本轮讨论目标

本轮围绕“样本状态管理”明确样本主状态范围、状态流转触发来源、检测中与检测完成的业务含义、异常和撤回与主状态的关系、状态变更记录，以及需要团队确认的问题。

### 7.2 已确认设计点

#### 7.2.1 样本主状态模型

结论：选择 A，样本主状态只保留正常流转主链。

规则说明：

1. 样本主状态包括：待送出、已送出、已接收、检测中、检测完成。
2. 样本主状态按正常业务流转表达，不混入异常、撤回、退回、取消、报告状态。
3. 申请取消由申请状态表达。
4. 送出撤回由送出记录和撤回记录表达。
5. 接收异常退回由接收处理记录、异常记录和退回记录表达。
6. 样本异常由异常记录表达。
7. 报告上传、审核、发布、撤回由报告相关状态表达。
8. 样本主状态用于表达样本在平台主流程中的当前位置，不替代其他业务对象状态。

设计理由：

1. 保持样本主状态链稳定，降低状态组合复杂度。
2. 避免一个样本同时因为异常、撤回、报告等业务动作出现多个互斥主状态。
3. 与前面申请管理、送出管理、接收管理和异常处理章节保持一致。

#### 7.2.2 检测中状态定位

结论：选择 C，保留检测中，但检测中作为可选状态。

规则说明：

1. 检测中表示接收方已经开始对样本进行检测处理。
2. 样本正常接收后，默认停留在已接收，不自动进入检测中。
3. 如果接收方系统回传检测开始，或平台存在人工触发开始检测的业务入口，样本可由已接收进入检测中。
4. 如果接收方不回传检测开始，平台允许样本由已接收直接进入检测完成。
5. 检测中不是报告上传或检测完成的强制前置状态。
6. 样本进入检测中前，应满足申请有效、样本已接收、未被异常阻断等前置条件。
7. 如果样本存在待处理或处理中的接收后异常，默认不允许进入检测中，除非异常处理结果允许继续检测。

设计理由：

1. 兼容不同接收方系统能力，有的系统能回传检测开始，有的只能在报告或结果完成时回传。
2. 保留检测中可以支持更细的流程追踪和时效统计。
3. 不强制检测中可以避免接口接入难度过高，减少因缺少中间状态导致流程无法推进的问题。

#### 7.2.3 检测完成触发规则

结论：选择 A，报告上传成功时自动推动样本进入检测完成。

规则说明：

1. 报告上传成功后，平台将对应样本主状态更新为检测完成。
2. 如果样本当前状态为已接收，允许直接进入检测完成。
3. 如果样本当前状态为检测中，允许进入检测完成。
4. 检测中不是进入检测完成的强制前置状态。
5. 报告上传成功是平台判断检测完成的主要业务依据。
6. 样本进入检测完成前，应满足申请有效、样本已接收、未被异常阻断等前置条件。
7. 如果样本存在待处理或处理中的接收后异常，默认不允许进入检测完成，除非异常处理结果允许继续检测或异常已关闭且未终止处理。

设计理由：

1. 报告上传通常代表接收方已经完成检测并形成结果。
2. 不要求接收方额外回传检测完成，可以降低接口接入成本。
3. 与检测中可选的设计保持一致，避免没有检测中回传时样本状态无法闭环。

#### 7.2.4 未接收样本与报告上传

结论：选择 A，未接收样本不允许上传报告。

规则说明：

1. 报告上传前，样本必须已经完成正常接收，或接收后异常处理并允许继续检测。
2. 样本主状态为待送出、已送出的，不允许上传报告。
3. 样本发生异常退回且未进入已接收的，不允许上传报告。
4. 平台不因报告上传自动补记样本接收。
5. 平台不允许未接收样本通过报告上传直接进入检测完成。
6. 如果接收方误传未接收样本报告，平台应拒绝并返回明确原因。
7. 该规则后续在报告管理章节继续细化接口错误码、返回结构和报告重传边界。

设计理由：

1. 样本接收是检测流程的交接前置事实，未接收不应出现正式检测结果。
2. 避免报告上传绕过送出、接收和异常处理规则。
3. 保持样本流转链条可追溯，避免平台自动补接收造成事实失真。

#### 7.2.5 样本状态逆流程总原则

结论：选择 A，采用事实追加模型，样本主状态原则上不回退。

规则说明：

1. 样本主状态原则上按正常主链向前流转，不通过回退主状态抹除已经发生的业务事实。
2. 已送出且未接收的样本，允许通过送出撤回回到待送出。
3. 送出撤回是样本主状态回退的明确例外，适用于尚未完成接收交接的样本。
4. 已接收、检测中、检测完成后的问题，不通过直接回退样本主状态处理。
5. 已接收后的样本问题，应通过样本异常处理、退回记录或后续业务动作处理。
6. 报告内容错误，应通过报告重传或报告撤回处理，不通过直接回退样本主状态处理。
7. 报告撤回后不影响样本检测完成状态；撤回只影响报告版本有效性。
8. 管理员或接口不提供通用的样本主状态手工回退能力。

设计理由：

1. 状态回退容易抹掉已经发生的送出、接收、检测和报告事实。
2. 事实追加模型更适合审计追溯，能保留原动作、修正动作和处理结果。
3. 限定唯一例外为送出未接收撤回，可以满足实际物流纠错，又避免接收后流程失真。

#### 7.2.6 样本状态变更历史

结论：选择 A，记录样本状态变更历史，但不做独立状态记录管理功能。

规则说明：

1. 每次样本主状态变化均应形成状态变更历史。
2. 状态变更历史应记录变更前状态、变更后状态、触发动作、关联业务记录、变更时间、操作人或调用系统。
3. 触发动作包括申请创建、送出、送出撤回、接收、检测开始、报告上传成功等。
4. 关联业务记录可包括申请号、送出记录号、接收记录号、异常记录号、报告记录号等。
5. 状态变更历史作为审计留痕，不允许人工编辑或删除。
6. 平台不单独提供“样本状态记录管理”菜单或维护功能。
7. 状态变更历史可在申请详情、样本详情、流转时间线或业务运维明细中展示。
8. 后续业务运维明细查询章节可继续定义状态历史的查询条件和展示范围。

设计理由：

1. 状态历史能支撑流转追溯和问题排查。
2. 不做独立管理功能，可以避免新增维护入口和权限复杂度。
3. 状态历史是系统事实留痕，不应被人工修改。

#### 7.2.7 页面兜底与状态人工维护边界

结论：确认采用业务动作页面兜底，禁止直接人工维护样本主状态。

规则说明：

1. 样本状态不提供独立人工维护入口。
2. 平台不提供直接将样本改为待送出、已送出、已接收、检测中、检测完成的页面操作。
3. 样本主状态只能由业务动作驱动。
4. 驱动样本主状态变化的业务动作包括申请创建、送出、送出撤回、接收、检测状态回传、报告上传成功等。
5. 对于未对接接口的机构，平台可提供对应业务动作的页面兜底入口。
6. 页面兜底入口应操作业务动作本身，例如页面送出、页面接收、页面异常处理、页面上传报告，而不是直接修改样本状态。
7. 页面业务动作必须生成对应业务记录和状态变更历史。
8. 检测中不提供单独页面人工触发按钮。
9. 检测中仅由接收方系统回传或后续检测流程触发；如果没有检测中回传，允许样本由已接收直接进入检测完成。
10. 检测完成由报告上传成功驱动，不提供单独人工改为检测完成的状态维护入口。

设计理由：

1. 未对接接口的机构确实需要页面业务操作作为兜底。
2. 页面兜底应补业务动作，不应变成状态后台维护。
3. 禁止直接改状态可以避免出现没有送出记录却已送出、没有接收记录却已接收、没有报告却检测完成的事实缺口。

#### 7.2.8 样本状态管理页面范围

结论：选择 A，样本状态管理不提供独立页面。

规则说明：

1. 样本状态管理不作为独立功能菜单。
2. 平台不提供独立的“样本状态管理”页面。
3. 样本当前主状态可在申请详情、样本详情、送出记录、接收记录、异常记录、报告记录和业务运维明细中展示。
4. 样本状态变更历史可在流转时间线或业务运维明细中展示。
5. 样本状态不提供独立编辑、调整、回退、删除操作。
6. 如后续需要按状态筛选样本，应归入申请查询、样本查询或业务运维明细查询，不单独新增状态管理模块。

设计理由：

1. 样本状态是各业务动作的结果，不应成为独立可维护对象。
2. 不提供独立页面可以降低功能复杂度。
3. 将状态展示嵌入详情和运维明细，更符合实际排查路径。

### 7.3 样本状态管理验收标准

1. 样本主状态范围包括待送出、已送出、已接收、检测中、检测完成。
2. 样本主状态不包含异常、撤回、退回、取消、报告上传、报告发布、报告撤回等状态。
3. 申请创建成功后，样本主状态进入待送出。
4. 送出成功后，样本主状态进入已送出。
5. 已送出且未接收的样本撤回成功后，样本主状态回到待送出。
6. 正常接收或接收后异常处理时，样本主状态进入已接收。
7. 异常退回样本不进入已接收。
8. 检测中作为可选状态保留；无检测中回传时，样本允许由已接收直接进入检测完成。
9. 检测中不提供单独页面人工触发按钮。
10. 报告上传成功后，样本主状态进入检测完成。
11. 未接收样本不允许上传报告，平台不因报告上传自动补记接收。
12. 样本主状态原则上不回退，唯一明确例外为已送出未接收样本通过送出撤回回到待送出。
13. 平台不提供直接人工维护样本主状态的入口。
14. 未对接接口的机构可通过页面业务动作完成送出、接收、异常处理、报告上传等操作，但页面操作必须生成对应业务记录，不允许直接修改样本主状态。
15. 每次样本主状态变化均应形成状态变更历史。
16. 状态变更历史应记录变更前状态、变更后状态、触发动作、关联业务记录、变更时间、操作人或调用系统。
17. 状态变更历史不允许人工编辑或删除。
18. 样本状态管理不提供独立功能菜单或独立管理页面。
19. 样本当前主状态和状态变更历史可在申请详情、样本详情、流转时间线或业务运维明细中展示。
20. 报告撤回后不影响样本检测完成状态，具体规则已在报告审核与发布章节确认。

### 7.4 本轮待讨论边界

1. 是否可以开始讨论下一个功能“报告审核与发布”。

## 8. 报告审核与发布

### 8.1 本轮讨论范围

本轮围绕“报告审核与发布”明确审核开关、报告上传前置条件、报告发布审核、审核不通过、报告重传、报告撤回、报告状态、样本检测完成关系、查询下载范围、页面入口和接口边界。

### 8.2 讨论结论

#### 8.2.1 审核开关基础规则

结论：沿用审核开关规则，审核开关采用全平台统一开关。

规则说明：

1. 平台存在统一的报告审核开关。
2. 审核开关启用时，报告上传或重传成功后进入待审核，审核通过后发布。
3. 审核开关未启用时，报告上传或重传成功后自动发布。
4. 审核开关配置功能不在本章节展开，本 PRD 只描述开关对报告业务流程的影响。
5. 暂不支持按机构、项目、发起方/接收方关系配置差异化审核规则。
6. 平台审核是报告发布控制，不是医学自动审核规则引擎。
7. 平台不判断报告内容是否医学正确，不自动判断结果高低、异常或危急值。

设计理由：

1. 统一开关规则最简单，便于当前版本落地。
2. 审核开关可以兼容“上传后需人工审核”和“上传成功自动发布”两类业务模式。
3. 将审核定位为发布控制，可以避免平台承担医学结果判定责任。

#### 8.2.2 报告上传前置条件

结论：报告上传前置条件严格校验。

规则说明：

1. 申请必须存在且处于有效状态。
2. 样本必须已经完成正常接收，或属于接收后异常处理且允许继续检测。
3. 样本处于待送出、已送出的，不允许上传报告。
4. 样本存在阻断性未关闭异常时，不允许上传报告。
5. 上传方必须是该申请/样本对应的接收方机构或其授权系统。
6. 申请已取消、样本异常退回且未进入已接收的，不允许上传报告。
7. 平台不因报告上传自动补记接收记录。
8. 不提供管理员绕过上传前置校验的兜底能力。

设计理由：

1. 报告上传会推动样本进入检测完成，并可能触发发布和推送，必须保证前置业务链路成立。
2. 严格校验可以避免未接收、错误接收方或异常未处理样本直接形成报告。
3. 不自动补记接收，可以保持样本流转记录完整可信。

#### 8.2.3 报告上传内容

结论：报告上传必须包含 PDF，结构化结果可选，报告覆盖项目范围不强制传入。

规则说明：

1. 报告上传必须包含报告 PDF。
2. 未包含 PDF 的报告上传请求应被拒绝。
3. 结构化检验结果可以上传，但不是报告生成和发布的必填条件。
4. 未提供结构化结果，不影响报告版本生成、审核、发布、查询、下载和推送。
5. 报告上传不强制传入报告覆盖的项目编码清单。
6. 平台上传什么就保存什么、展示什么。
7. 平台不解析 PDF，不判断报告覆盖了哪些检验项目。
8. 平台不做项目级完成判断、漏报判断、重复覆盖判断。
9. 同一申请/样本条码下多份报告以报告列表展示，用户通过报告名称、报告类型、上传时间、版本状态和 PDF 内容识别。
10. 报告名称或报告类型可以作为可选展示字段，但不作为业务校验依据。

设计理由：

1. 不强制传入覆盖项目范围，可以降低多医院系统对接难度。
2. 平台聚焦报告文件、版本和发布状态管理，不承担报告内容解析和项目级完整性判断。
3. PDF 必传可以保障报告查询、下载和推送有稳定载体。

#### 8.2.4 报告上传成功与样本检测完成

结论：上传任意报告成功即推动样本主状态进入检测完成。

规则说明：

1. 样本主状态按样本维度管理，不表达项目级完成度。
2. 报告上传成功后，平台将对应样本主状态更新为检测完成。
3. 报告是否已发布、是否审核通过，不影响样本主状态已经进入检测完成。
4. 如果审核不通过、报告重传、报告撤回，样本主状态原则上不回退。
5. 报告有效性由报告状态表达，样本检测完成只表示平台已收到该样本对应的检测报告。
6. 平台不判断申请内所有项目是否均已出报告。

设计理由：

1. 样本状态保持轻量，不承载项目级报告完成度。
2. 报告审核、发布、撤回属于报告对象状态，不反向污染样本主状态。
3. 保持“事实不回退”的状态管理原则。

#### 8.2.5 报告版本与上传失败

结论：每次报告上传或重传成功都生成独立版本号，上传失败不生成报告版本。

规则说明：

1. 报告上传成功后立即生成报告版本号。
2. 每次重传生成新的报告版本号。
3. 版本号用于区分同一申请、同一样本条码、同一报告业务对象下的不同报告版本。
4. 版本号一经生成，不允许复用或覆盖。
5. 版本号生成规则属于实现细节，PRD 只要求版本可唯一识别、可排序、可追溯。
6. 只有报告上传前置校验通过，并且报告 PDF 保存成功后，才生成报告版本。
7. 上传失败不生成报告版本号，不进入报告业务状态，不推动样本进入检测完成。
8. 上传失败原因应返回给调用方。
9. 上传失败请求可进入接口日志或审计日志，但不作为报告业务版本展示。

设计理由：

1. 上传成功即生成版本号，便于待审核、不通过、发布、替代、撤回全过程追溯。
2. 上传失败不生成业务版本，可以避免污染报告版本历史。

#### 8.2.6 报告发布审核

结论：审核通过即发布，不设置独立待发布状态；不支持批量审核；审核人员不能修改报告内容。

规则说明：

1. 审核开关启用时，报告上传成功后进入待审核。
2. 审核人员必须逐份打开报告详情后处理。
3. 平台不提供批量审核通过、批量审核不通过功能。
4. 审核人员应能查看报告 PDF、报告关联申请、样本、患者摘要、项目、上传方、上传时间和历史版本信息。
5. 审核人员可对单份报告执行审核通过或审核不通过。
6. 审核通过后，报告直接进入已发布。
7. 平台不设置独立待发布状态，不提供单独发布按钮。
8. 审核通过即代表报告对发起机构可查询、可下载，并按配置触发推送。
9. 审核人员不能修改报告 PDF、结构化结果、危急值标记、项目结果或患者申请信息。
10. 如发现报告内容、文件、项目覆盖或患者信息存在问题，应审核不通过并填写原因。

设计理由：

1. 审核通过即发布可以减少流程环节。
2. 报告审核涉及医疗结果发布控制，不支持批量审核可以降低误发布风险。
3. 平台不是报告编辑系统，内容修正应由上传方通过重传处理。

#### 8.2.7 审核不通过

结论：审核不通过后，当前版本状态为审核不通过，上传方需通过重传生成新版本。

规则说明：

1. 审核不通过后，当前报告版本状态为审核不通过。
2. 审核不通过版本不允许发布、查询给发起机构、下载给普通业务用户或对外推送。
3. 审核不通过原因必填。
4. 审核不通过原因记录在平台内，可在报告详情、审核记录或业务运维明细中查看。
5. 本章节不要求通过接口向上传方返回或查询审核不通过原因。
6. 上传方如需重新提交，应通过报告重传生成新报告版本。
7. 新版本按审核开关重新进入待审核或自动已发布。
8. 原审核不通过版本保留历史，不物理删除，不作为最新有效报告。
9. 报告审核不通过只影响报告版本状态，不回退样本主状态。

设计理由：

1. 不修改原版本，符合版本强制保留和不物理覆盖原则。
2. 不通过原因留痕能支撑上传方修正和后续追溯。
3. 样本是否检测完成与报告是否可用分开表达，状态边界更清楚。

#### 8.2.8 报告重传

结论：仅上传方可以发起报告重传；待审核、审核不通过、已发布、已撤回版本均可按规则重传。

规则说明：

1. 报告重传应由报告上传方发起。
2. 平台审核人员不能代上传方重传报告。
3. 平台管理员不能代上传方重传报告。
4. 待审核报告允许上传方主动重传。
5. 待审核版本被重传后，原待审核版本标记为已重传作废，不再允许审核、发布、查询或推送。
6. 同一报告不允许同时存在多个可被审核的待审核版本。
7. 已发布报告允许重传生成新版本。
8. 已发布报告重传后，新版本发布前，原已发布版本仍为当前最新有效报告。
9. 新版本审核通过并发布后，新版本成为最新有效报告，原已发布版本标记为已替代。
10. 如果新版本审核不通过，原已发布版本继续有效，不受影响。
11. 已发布报告发起重传时，重传原因必填。
12. 已替代、已撤回历史版本如允许基于其重传，重传原因也应必填。
13. 待审核报告主动重传时，重传原因可选。
14. 审核不通过报告重传时，可引用审核不通过原因，重传原因可选。
15. 每次重传都必须形成重传记录，并关联原报告版本和新报告版本。
16. 报告撤回后，如上传方需要重新提供报告，可基于已撤回版本重传生成新版本。
17. 已撤回版本仍保留历史状态，不恢复为已发布。

设计理由：

1. 上传方对报告内容负责，平台不代替上传方生成新报告版本。
2. 已发布报告重传期间旧版本继续有效，可以避免审核期间无有效报告。
3. 重传记录能保持版本替代关系可追溯。

#### 8.2.9 报告撤回

结论：仅上传方可以发起报告撤回，撤回受审核开关控制，撤回不影响样本检测完成。

规则说明：

1. 已发布报告可由上传方发起撤回。
2. 平台审核人员只负责撤回审核，不主动发起撤回。
3. 平台管理员不直接发起业务撤回。
4. 上传方发起撤回时必须说明撤回原因。
5. 审核开关启用时，已发布报告提交撤回后进入撤回待审核。
6. 撤回待审核期间，原已发布报告仍作为当前有效报告。
7. 发起机构仍可查询、下载原报告。
8. 推送补偿或重新推送仍以原已发布报告为准。
9. 撤回审核通过后，原报告撤回生效，报告不再作为当前有效报告。
10. 撤回审核不通过时，原已发布报告继续有效。
11. 审核开关未启用时，撤回提交后立即生效。
12. 撤回审核通过时，必须填写撤回审核意见或确认说明。
13. 撤回审核不通过时，必须填写不通过原因。
14. 撤回申请作为报告业务记录保留。
15. 撤回审核不通过记录应保留，不影响原报告有效性。
16. 报告撤回不受推送状态限制，是否已经推送、推送成功、推送失败或尚未推送，不影响撤回申请。
17. 报告撤回生效后，样本主状态仍保持检测完成。
18. 如果撤回后没有任何当前有效报告，平台在报告查询中显示无当前有效报告。
19. 如需重新对外提供报告，上传方应通过报告重传生成新版本。
20. 报告撤回是否触发撤回推送或作废通知，放到报告和危急值推送管理章节展开。

设计理由：

1. 报告内容责任在上传方，撤回应由上传方发起。
2. 撤回待审核期间原报告继续有效，可以避免审核期间报告突然不可用。
3. 撤回是报告对象状态，不应改变样本已检测完成这一业务事实。

#### 8.2.10 报告状态

结论：报告状态先采用待审核、审核不通过、已重传作废、已发布、已替代、撤回待审核、已撤回。

规则说明：

1. 待审核：审核开关启用时，报告上传或重传成功后的状态。
2. 审核不通过：发布审核未通过，不可发布、查询、下载、推送。
3. 已重传作废：待审核版本被新重传版本替代，不再允许审核。
4. 已发布：当前可对发起机构查询、下载、推送的有效报告。
5. 已替代：原已发布版本被新发布版本替代。
6. 撤回待审核：已发布报告提交撤回，等待撤回审核。
7. 已撤回：撤回生效后，不再作为当前有效报告。
8. 已发布报告不允许反审核，不允许回退到待审核。
9. 已发布报告发现问题时，只能通过报告重传或报告撤回处理。
10. 平台不提供管理员强制反审核能力。

设计理由：

1. 该状态集合能覆盖报告上传、审核、重传、替代和撤回主流程。
2. 不增加发布中、上传失败等状态，可以保持报告业务状态轻量。
3. 失败请求由接口日志或审计处理，不进入报告版本状态。

#### 8.2.11 审核记录与状态变化记录

结论：采用审核记录和报告状态变化记录分开留痕。

规则说明：

1. 每次审核动作必须形成审核记录。
2. 审核记录至少包含报告版本号、审核动作类型、审核结果、审核人、审核时间、审核意见或不通过原因。
3. 审核动作类型包括报告发布审核、报告撤回审核。
4. 审核通过或不通过导致报告状态变化时，应形成报告状态变化记录。
5. 报告状态变化记录用于追溯状态从什么变成什么，以及由哪个业务动作触发。
6. 不要求在审核记录本身重复记录审核前状态和审核后状态。
7. 发布审核通过时，审核意见可选填写。
8. 发布审核不通过时，不通过原因必填。
9. 撤回审核通过时，撤回审核意见或确认说明必填。
10. 撤回审核不通过时，不通过原因必填。

设计理由：

1. 审核记录表达审核动作，状态变化记录表达状态流转，两者职责更清楚。
2. 不在审核记录中重复记录前后状态，可以避免字段定义过细。
3. 撤回会使已发布报告失效，审核意见要求更严格。

#### 8.2.12 报告查询、下载和页面入口

结论：接口只能查询当前有效报告；页面按查询、审核、追溯拆分入口。

规则说明：

1. 报告查询接口只能返回当前有效的已发布报告。
2. 普通报告查询接口不返回待审核、审核不通过、已重传作废、已替代、撤回待审核、已撤回报告。
3. 外部系统不能通过普通报告查询接口获取历史版本或无效版本。
4. 如后续确需开放历史版本，应另设有权限控制的版本追溯接口，不与普通报告查询接口混用。
5. 平台普通报告查询页面默认只展示当前有效报告。
6. 报告查询页面支持在线查看和下载当前有效已发布报告 PDF。
7. 非当前有效报告不在普通报告查询页面展示，也不可从该入口下载。
8. 报告下载应记录操作留痕。
9. 报告审核入口用于处理发布审核和撤回审核，包含发布审核、撤回审核两个页签。
10. 发布审核页签展示状态为待审核的报告版本。
11. 撤回审核页签展示状态为撤回待审核的报告或撤回申请。
12. 报告版本追溯用于有权限人员查看全部历史版本、替代关系、撤回记录和审核记录。
13. 申请详情、样本详情、业务运维明细中可以展示报告摘要，并跳转到对应报告页面。
14. 普通业务用户不直接面对全部报告版本，避免误用历史或无效报告。
15. 更细的下载权限是否配置，放到权限/审计章节处理，不在报告审核与发布章节展开。

设计理由：

1. 接口强制只返回有效报告，可以避免外部系统误取旧版本或无效版本。
2. 页面拆分查询、审核、追溯入口，可以避免一个页面承载过多职责。
3. 普通查询看有效报告，管理和运维按权限看历史，更符合实际使用场景。

#### 8.2.13 报告上传接口返回和上传方通知

结论：报告上传成功返回版本号、当前状态和是否自动发布；本版本不提供上传方后续审核结果查询或通知。

规则说明：

1. 报告上传成功后返回报告版本号。
2. 返回当前报告状态：审核开关启用时通常为待审核，审核开关未启用时为已发布。
3. 返回是否已自动发布。
4. 上传失败时返回明确失败原因。
5. 不返回完整报告详情。
6. 本章节不新增上传方查询审核/发布结果接口要求。
7. 本版本不要求在报告审核通过后通知上传方。
8. 审核不通过也不通过接口或消息通知上传方。
9. 上传方如需查看报告审核、发布状态或不通过原因，可通过平台页面查看。
10. 上传方系统侧自动闭环能力作为后续增强，不纳入当前报告审核与发布章节。

设计理由：

1. 上传成功响应需要让上传方知道本次报告初始状态。
2. 不扩展后续查询和通知接口，可以控制本版本接口范围。
3. 审核处理闭环先通过平台页面完成，后续如需系统自动闭环再单独增强。

#### 8.2.14 危急值与报告审核开关

结论：报告上传可以包含危急值信息，危急值发布/推送跟随报告审核开关。

规则说明：

1. 报告上传时可以同时上传危急值信息。
2. 危急值必须关联本次报告版本、申请、样本条码、上传方和接收方。
3. 审核开关启用时，报告和关联危急值在审核通过后才对外发布或推送。
4. 审核开关未启用时，报告上传成功自动发布，关联危急值进入可推送状态。
5. 危急值本身的处理记录、推送失败、补推和作废通知，放到报告和危急值推送管理章节继续展开。
6. 平台不自动判断危急值，危急值信息由上传方提供。

设计理由：

1. 危急值随报告上传，可以减少独立接口复杂度。
2. 危急值发布/推送跟随审核开关，可以保持报告和关联危急值发布边界一致。
3. 危急值后续处理和推送细节独立到推送管理章节，避免本章节过度展开。

### 8.3 报告审核与发布验收标准

1. 平台支持统一报告审核开关对报告上传、重传、撤回的业务流程产生影响。
2. 审核开关启用时，报告上传或重传成功后进入待审核。
3. 审核开关未启用时，报告上传或重传成功后自动发布。
4. 报告上传前必须校验申请有效、样本已接收或允许继续检测、上传方为对应接收方、无阻断性未关闭异常。
5. 待送出、已送出、申请已取消、异常退回且未接收的样本不允许上传报告。
6. 报告上传必须包含 PDF，结构化结果可选。
7. 报告上传不强制传入覆盖项目范围，平台不做项目级完成、漏报或重复覆盖判断。
8. 报告上传成功后生成报告版本号，并推动样本主状态进入检测完成。
9. 报告审核不通过、重传、撤回均不回退样本检测完成状态。
10. 上传失败不生成报告版本，不推动样本进入检测完成。
11. 审核通过即发布，不设置独立待发布状态或单独发布按钮。
12. 报告审核不支持批量审核。
13. 审核人员不能修改报告内容，只能审核通过或审核不通过。
14. 审核不通过原因必填，审核不通过版本不可发布、查询、下载或推送。
15. 待审核报告允许上传方主动重传，原待审核版本标记为已重传作废。
16. 已发布报告重传后，新版本发布前原已发布版本继续有效。
17. 新版本发布后成为当前有效报告，原已发布版本标记为已替代。
18. 仅上传方可以发起报告重传和报告撤回。
19. 已发布报告撤回受审核开关控制；撤回待审核期间原报告继续有效。
20. 撤回审核通过后报告进入已撤回，不再作为当前有效报告。
21. 撤回审核不通过后原报告继续有效，并保留撤回申请和审核记录。
22. 报告状态包括待审核、审核不通过、已重传作废、已发布、已替代、撤回待审核、已撤回。
23. 已发布报告不允许反审核，只能通过重传或撤回处理问题。
24. 每次审核动作必须形成审核记录，并在状态变化时形成报告状态变化记录。
25. 报告查询接口只能返回当前有效的已发布报告。
26. 普通报告查询页面只展示当前有效报告，并支持在线查看和下载 PDF。
27. 报告审核入口包含发布审核和撤回审核两个页签。
28. 报告版本追溯入口可按权限查看全部历史版本、替代关系、撤回记录和审核记录。
29. 报告上传成功返回报告版本号、当前报告状态和是否已自动发布。
30. 本章节不要求提供上传方后续查询审核结果接口，也不要求审核通过或不通过后通知上传方。
31. 报告上传可包含危急值信息，危急值发布/推送跟随报告审核开关。

### 8.4 本轮待讨论边界

1. 报告和危急值推送失败、重试、补推和作废通知，放到“报告和危急值推送管理”章节继续讨论。
2. 报告历史版本对发起机构是否开放专门追溯接口，当前不纳入普通报告查询接口。
3. 更细的报告下载权限和审计规则，放到权限/审计或业务动作留痕章节继续讨论。

## 9. 报告版本管理

### 9.1 本轮讨论范围

本轮围绕“报告版本管理”继续细化报告对象、版本链、当前有效报告、报告作废、版本追溯入口和推送边界。

本节结论对第 8 节中“报告撤回”相关结论进行更新：当前版本不再保留“撤回待审核/已撤回”流程，统一改为“报告作废”。

### 9.2 讨论结论

#### 9.2.1 报告版本管理定位

结论：采用轻量追溯能力，不做复杂独立管理模块。

规则说明：

1. 报告版本管理用于追溯同一样本条码下报告上传、审核、发布、重传、替代和作废过程。
2. 普通业务用户只查询当前有效报告。
3. 有权限人员可通过报告详情、版本追溯入口或业务运维明细查看历史版本链。
4. 不提供人工编辑报告版本、人工调整版本状态、删除历史版本或恢复历史版本能力。

#### 9.2.2 一个条码一个报告对象

结论：当前版本采用一个样本条码一个报告对象、一个当前有效报告。

规则说明：

1. 同一申请、同一样本条码下只维护一个报告业务对象。
2. 首次上传报告成功后，生成该报告业务对象的第一个版本。
3. 同一样本条码再次上传报告时，必须作为该报告业务对象的重传版本。
4. 平台不根据报告名称、报告类型、项目范围或 PDF 内容自动拆分多个报告对象。
5. 分批出结果、补充结果、修正报告内容，均通过报告重传生成新版本。
6. 项目多或一页显示不完，不作为拆分多个报告对象的理由。
7. 平台不按项目范围判断报告是否覆盖全部申请项目。

#### 9.2.3 当前有效报告规则

结论：任一时间同一样本条码最多只有一份当前有效已发布报告。

规则说明：

1. 报告首次发布后，该版本成为当前有效报告。
2. 已发布报告重传后，新版本发布前，原已发布版本仍为当前有效报告。
3. 新版本发布后，新版本成为当前有效报告，原已发布版本进入已替代。
4. 如果新版本审核不通过，原当前有效报告继续有效。
5. 当前有效报告作废后，该样本条码暂无当前有效报告。
6. 当前有效报告作废后，已替代历史版本不自动恢复为当前有效报告。
7. 如需重新对外提供报告，上传方必须重传生成新版本。

#### 9.2.4 报告作废

结论：统一为报告作废，不再区分撤回和停用。

规则说明：

1. 报告作废用于处理当前有效报告不应继续对外查询、下载或推送的场景。
2. 作废只允许作用于当前有效的已发布报告。
3. 作废立即生效，不受报告审核开关控制。
4. 作废后普通查询接口不再返回该报告。
5. 作废后不自动回退历史版本。
6. 作废后不可恢复，不提供重新启用能力。
7. 作废必须填写原因。
8. 作废原因建议分类包括：报告错误、重复报告、业务取消、其他。
9. 上传方可以作废自己上传的当前有效报告。
10. 平台授权人员可在必要时作废当前有效报告。
11. 发起机构不能直接作废报告。
12. 作废不删除历史版本，不影响样本检测完成状态。
13. 作废后如需重新提供报告，只能通过重传生成新版本。

#### 9.2.5 报告状态收敛

结论：报告状态调整为待审核、审核不通过、已重传作废、已发布、已替代、已作废。

规则说明：

1. 删除原“撤回待审核”和“已撤回”状态。
2. 报告作废不是审核动作，不进入撤回审核。
3. 作废应形成作废记录和报告状态变化记录。
4. 已发布报告不允许反审核，只能通过重传或作废处理问题。

#### 9.2.6 版本追溯与推送边界

结论：版本追溯面向有权限人员；作废通知规则后续放到推送章节。

规则说明：

1. 版本追溯应展示版本号、版本状态、上传方、上传时间、发布审核记录、重传关系、替代关系、作废记录和当前有效标识。
2. 普通报告查询页面不展示无效历史版本。
3. 如后续需要对外开放历史版本追溯接口，应独立于普通报告查询接口，并进行权限控制。
4. 报告作废是否向发起机构发送作废通知，不在本章节展开。
5. 作废通知失败、补发、重推、医院端已下载旧报告后的处理，放到报告和危急值推送管理章节讨论。

### 9.3 验收标准

1. 同一申请、同一样本条码下只存在一个报告业务对象。
2. 首次上传生成第一个报告版本，再次上传按重传生成新版本。
3. 任一时间同一样本条码最多只有一份当前有效已发布报告。
4. 新版本发布前，原已发布版本继续作为当前有效报告。
5. 新版本发布后，原已发布版本进入已替代。
6. 当前有效报告作废后，该样本条码暂无当前有效报告。
7. 作废后不自动回退历史版本。
8. 作废后不可恢复，只能通过重传生成新版本重新对外提供报告。
9. 报告状态范围为待审核、审核不通过、已重传作废、已发布、已替代、已作废。
10. 有权限人员可以查看版本链、替代关系、作废记录和审核记录。

### 9.4 本轮待讨论边界

1. 报告作废是否触发对外作废通知，放到“报告和危急值推送管理”章节继续讨论。
2. 作废通知失败、补发、重推、医院端已下载旧报告后的处理，放到“报告和危急值推送管理”章节继续讨论。
3. 是否开放有权限控制的历史版本追溯接口，后续按接口范围继续确认；当前普通报告查询接口只返回当前有效已发布报告。
