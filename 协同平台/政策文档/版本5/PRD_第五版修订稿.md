## 1. 功能需求

### 1.1 申请管理

#### 1.1.1 功能定位

申请管理用于接收发起机构系统提交的检验申请，生成平台申请单号，并建立平台申请、机构申请、患者摘要、就诊摘要、平台标准项目编码、样本条码、接收方、费用状态和绿色通道信息之间的关系。

平台不承担开单职责，不作为医生或机构人员的检验申请录入系统。发起机构应在本地 HIS、LIS 或检验系统中完成开单、采样、条码生成和条码打印后，再提交至平台。

#### 1.1.2 功能入口

1. 平台仅支持机构系统提交创建申请。
2. 平台页面不提供正常业务下的人工补录申请入口。
3. 平台页面可提供申请查询、明细查看、申请终止、流转追踪、异常排查和操作留痕查看能力。

#### 1.1.3 申请创建规则

1. 创建申请时必须提供样本条码。
2. 一个平台申请只能对应一个样本条码。
3. 同一发起机构内，一个样本条码只能对应一个平台申请。
4. 不同发起机构之间允许存在相同样本条码。
5. 一个平台申请可以包含多个平台标准项目编码。
6. 平台不维护机构项目对照，不提供平台标准项目维护能力。
7. 创建申请成功后，平台生成平台申请单号。
8. 创建申请成功后，申请状态为有效，样本主状态进入待送出。

#### 1.1.4 字段类别

创建申请时，PRD 层面要求覆盖以下信息类别；具体接口字段由接口设计文档另行定义。

1. 发起机构信息。
2. 机构申请号。
3. 样本条码。
4. 患者摘要。
5. 就诊摘要。
6. 平台标准项目编码清单。
7. 接收方。
8. 费用状态。
9. 绿色通道信息。
10. 备注或扩展信息。

#### 1.1.5 关键校验规则

1. 必填信息不能为空。
2. 同一发起机构内，样本条码不可重复绑定多个平台申请。
3. 不同发起机构允许使用相同样本条码。
4. 平台标准项目编码必须可识别、可用。
5. 接收方必须在发起机构允许提交的接收方范围内。
6. 申请终止后，原样本条码在同一发起机构内不可复用。
7. 平台不校验项目与患者年龄、性别、病区、床号等医学或院内业务规则冲突。

#### 1.1.6 重复提交处理

平台以发起机构、机构申请号、样本条码作为重复提交判断的主要依据。

1. 如果重复提交的发起机构、机构申请号、样本条码和核心申请信息一致，平台不创建新申请，应能识别为已有申请。
2. 如果机构申请号相同但样本条码不同，平台拒绝创建，并提示重复申请号但条码不一致。
3. 如果同一发起机构内样本条码相同但机构申请号不同，平台拒绝创建，并提示条码已被占用。
4. 如果机构申请号和样本条码相同，但患者摘要、项目、接收方等核心信息不一致，平台拒绝创建，并提示重复提交内容与原申请不一致。

核心申请信息至少包括：发起机构、机构申请号、样本条码、患者唯一标识或患者摘要关键字段、平台标准项目编码清单、接收方。

#### 1.1.7 申请字段修改

申请创建成功后，平台不支持修改核心业务字段。

核心业务字段包括：

1. 发起机构。
2. 机构申请号。
3. 样本条码。
4. 患者唯一标识或患者摘要关键字段。
5. 就诊摘要关键字段。
6. 平台标准项目编码清单。
7. 接收方。
8. 样本类型等影响送检、接收和检测判断的字段。

如机构发现核心业务字段错误，应终止原申请，再由机构系统重新提交新的申请并使用新的样本条码。申请已经送出、接收、检测或上传报告后，不允许通过修改申请字段修正业务错误，也不通过回退样本主状态修正业务错误，应根据当前阶段进入申请终止、样本异常处理、报告作废或报告重传等后续处理。

#### 1.1.8 多机构条码唯一性与接收定位

样本条码不要求全平台唯一，唯一性范围限定为同一发起机构内。

1. 申请创建时，平台按“发起机构ID + 样本条码”校验唯一性。
2. 接收样本时必须能明确接收方、发起机构和样本条码。
3. 平台接收样本时，按发起机构和样本条码定位平台申请和样本。
4. 如果只能获得样本条码、无法明确发起机构，平台不应自动模糊匹配，应提示无法定位样本。
5. 平台页面扫码接收时，可以通过先选择发起机构、送出记录或包来确定发起机构，再连续扫码。
6. 按包接收时，如包内样本已明确发起机构，平台可根据包内样本关系定位每个条码。包是否允许跨发起机构样本，在样本打包管理章节中定义。

#### 1.1.9 申请终止

申请终止用于停止申请后续业务流转。平台统一使用申请终止，不再单独设计独立的取消流程；样本未送出前的终止，作为申请终止的一种业务类型记录为未送出取消。

1. 发起机构可在申请创建后的任意阶段发起申请终止。
2. 申请终止支持发起机构系统触发，也支持发起机构授权用户在平台页面触发。
3. 申请终止提交后在平台内立即生效，申请状态变为已终止。
4. 申请终止按申请整体生效，一个申请下存在多个检验项目时，终止申请即表示该申请下全部项目停止后续流转。
5. 平台不支持申请内项目级部分终止。
6. 申请终止不回退样本主状态，不删除或改写已经发生的送出、接收、检测、报告、危急值和推送事实。
7. 申请终止后，不允许继续打包、送出、接收、检测推进、上传报告、审核发布报告和发起新的报告或危急值推送。
8. 申请终止后，原申请不可恢复为有效。
9. 申请终止后，原样本条码在同一发起机构内不可再次创建新的平台申请。
10. 申请终止后，不支持将已终止申请下的样本自动关联到新的申请。
11. 发起机构如需继续检测，应重新提交新的申请，并使用新的样本条码。
12. 申请终止时必须记录终止原因、终止时间、终止发起方、操作人或调用系统、终止时样本主状态、终止时报告状态摘要。
13. 终止原因建议来自字典系统，终止说明可选填写。
14. 平台页面触发终止时，应提示终止影响，包括整单终止、原样本条码不可复用、后续业务动作被阻断、已发布报告可能进入作废或失效处理。
15. 接收方和检验中心用户不能代替发起机构终止申请，只能根据申请已终止状态停止后续处理。
16. 平台管理员代发起机构终止申请属于特殊权限能力，当前版本不默认提供。
17. 样本复用或转关联属于独立业务能力，不纳入申请终止流程。

终止类型根据终止发生时所处阶段记录，建议包括：

| 终止类型 | 适用阶段 | 主要影响 |
| ---- | ---- | ---- |
| 未送出取消 | 样本仍为待送出 | 不允许继续打包、送出 |
| 送出后终止 | 样本已送出但未接收 | 不回到待送出，不允许接收，送出记录保留 |
| 接收后终止 | 样本已接收但未进入检测 | 不回退接收事实，不允许进入检测 |
| 检测中终止 | 样本处于检测中 | 不回退检测事实，不允许继续推进检测完成或上传报告 |
| 检测完成后终止 | 样本已检测完成但无当前有效报告 | 不回退检测完成，不允许继续上传、审核或发布报告 |
| 报告后终止 | 已存在当前有效报告 | 不删除历史报告，当前有效报告应进入作废或失效处理 |

#### 1.1.10 申请状态

申请状态只表达平台申请本身是否仍然有效。

| 状态 | 说明 |
| ---- | ---- |
| 有效 | 申请创建成功后进入该状态 |
| 已终止 | 申请终止成功后进入该状态 |

样本流转状态不写入申请状态，由样本主状态单独表达。样本主状态包括：待送出、已送出、已接收、检测中、检测完成。

报告状态、异常状态、推送状态分别由报告、异常和推送相关对象承载。平台不设置申请已完成状态；检测完成、报告发布等结果由样本和报告状态体现。申请已终止是申请维度的总控状态，不替代样本、报告、异常、危急值和推送对象自身状态。

#### 1.1.11 多项目申请与报告关系

1. 一个平台申请可以包含多个平台标准项目编码。
2. 平台申请、样本送出、样本接收、样本异常和样本主状态按整个申请和样本条码处理。
3. 同一申请、同一样本条码下只维护一个报告业务对象。
4. 同一样本条码多次上传报告时，应作为同一报告业务对象的不同版本处理。
5. 任一时间同一样本条码最多只有一份当前有效已发布报告。
6. 报告上传不强制声明报告覆盖项目范围。
7. 平台不基于项目范围判断报告完整性、项目完成状态、项目重复覆盖或项目漏报。
8. 报告查询时应能展示报告对应的申请、样本条码、上传时间、版本状态和当前有效状态。
9. 申请终止按整单处理，不支持仅终止申请中的部分项目。
10. 发起机构如需取消或调整部分项目，应重新提交新的申请，不通过项目级部分终止处理。

#### 1.1.12 费用状态与绿色通道

费用状态和绿色通道只记录、展示和查询，不阻断平台主流程。

1. 平台不负责收费、退费、医保结算和费用规则判断。
2. 机构创建申请时可以提供费用状态和绿色通道信息。
3. 费用状态建议包括：已收费、未收费、无需收费、未知。
4. 绿色通道信息建议包括：是否绿色通道、绿色通道原因或说明。
5. 未收费或未知费用状态不阻断申请创建。
6. 未收费或未知费用状态不阻断样本打包、送出、接收、检测、报告上传和报告发布。
7. 绿色通道信息只作为接收方优先级判断、人工识别和业务核对参考，不改变平台主流程。

#### 1.1.13 申请查询与明细展示

平台应支持申请列表查询和申请详情查看。

查询条件建议包括：

1. 平台申请单号。
2. 机构申请号。
3. 发起机构。
4. 样本条码。
5. 患者摘要关键字。
6. 申请时间。
7. 申请状态。
8. 样本主状态。
9. 接收方。

权限规则：

1. 普通机构用户只能查询本机构发起的申请，或按授权范围查询与本机构相关的申请。
2. 接收方用户可查询提交给本接收方的申请。
3. 平台管理端授权用户可按权限查询全平台申请。

详情展示：

1. 申请详情应展示申请基础信息、患者摘要、就诊摘要、样本条码、项目清单、接收方、费用状态、绿色通道、申请状态、样本主状态和关键时间。
2. 申请详情可展示包、申请批次、送出、接收、异常、报告和推送的摘要信息。
3. 申请已终止时，申请详情应展示终止类型、终止原因、终止时间、终止发起方、操作人或调用系统、终止时样本主状态、终止影响摘要。
4. 包、批次、送出、接收、异常、报告和推送的完整明细，应跳转到对应功能模块或业务运维明细页面查看。
5. 申请查询不是统计报表，不提供排行、趋势、汇总分析等能力。

#### 1.1.14 不支持范围

1. 不支持平台生成样本条码。
2. 不支持平台打印样本条码。
3. 不支持页面人工补录申请。
4. 不支持申请内项目级部分终止。
5. 不支持创建后修改申请核心业务字段。
6. 不负责收费、退费、医保结算。
7. 不提供项目标准化和机构项目对照维护。
8. 不在申请管理中定义系统对接细节。

#### 1.1.15 验收标准

1. 能通过机构系统创建平台申请，并获得平台申请单号。
2. 平台页面不提供正常业务下的人工补录申请入口。
3. 一个平台申请只能对应一个样本条码。
4. 同一发起机构内，一个样本条码不能重复绑定多个平台申请。
5. 不同发起机构允许存在相同样本条码。
6. 重复提交时，发起机构、机构申请号、样本条码和核心信息一致的，平台不创建新申请，并能识别为已有申请。
7. 重复提交时，机构申请号、样本条码或核心信息与原申请不一致的，拒绝创建并提示原因。
8. 创建成功后，申请状态为有效，样本主状态为待送出。
9. 申请创建成功后，不允许修改患者、条码、项目、接收方等核心业务字段。
10. 发起机构可通过机构系统或平台页面触发申请终止。
11. 申请终止提交后在平台内立即生效，申请状态变为已终止。
12. 申请终止按整单处理，不支持项目级部分终止。
13. 申请终止不回退样本主状态，不删除或改写已发生的业务事实。
14. 申请终止后阻断后续打包、送出、接收、检测推进、报告上传、报告发布和新推送。
15. 申请终止后不可恢复，且同一发起机构内原样本条码不可复用。
16. 申请终止后不支持将原样本自动关联到新的申请；如需继续检测，应重新提交新申请并使用新样本条码。
17. 申请详情能展示终止类型、终止原因、终止时间、终止发起方和终止影响摘要。
18. 费用状态和绿色通道信息可以记录、展示和查询，但不阻断申请创建、样本送出、样本接收、检测和报告流程。
19. 支持申请列表查询和申请详情查看，并按发起机构、接收方和平台管理权限隔离数据。
20. 申请详情能展示申请基础信息、患者摘要、项目清单、样本条码、接收方、费用状态、绿色通道、申请状态、样本主状态和关键流转摘要。

### 1.2 样本打包管理

#### 1.2.1 功能定位

样本打包管理用于将一个或多个样本条码归集为平台业务包。包是平台内用于样本归集、送出、接收和追溯的业务对象，不要求线下一定存在实体箱。

#### 1.2.2 包内样本机构范围

1. 一个包只能包含同一发起机构的样本。
2. 不允许在同一个包内混装多个发起机构的样本。
3. 包创建后，应记录包所属发起机构。
4. 向包内加入样本时，平台校验样本发起机构必须与包所属发起机构一致。
5. 按包接收时，平台可通过包确定发起机构，再结合包内样本条码定位样本。

#### 1.2.3 入包样本范围

1. 只有申请状态为有效的样本可以加入包。
2. 只有样本主状态为待送出的样本可以加入包。
3. 已终止申请对应的样本不能加入包。
4. 已送出、已接收、检测中、检测完成或已有报告的样本不能加入包。
5. 平台向包内加入样本时，应校验样本所属发起机构、申请状态和样本主状态。

#### 1.2.4 包内样本调整

1. 包处于未送出状态时，允许向包内加入符合入包条件的样本。
2. 包处于未送出状态时，允许从包内移出样本。
3. 包送出后，包内样本关系锁定，不允许继续加入或移出样本。
4. 包内样本调整必须记录调整时间、操作人或调用系统、调整动作和调整前后样本清单摘要。
5. 从包内移出的样本，如申请有效且样本仍为待送出，可继续按条码送出或加入其他符合规则的包。
6. 包内样本调整不改变样本主状态；样本主状态仍由送出、接收、检测等动作驱动。

#### 1.2.5 包作废

1. 包未送出前允许作废。
2. 包送出后不允许作废。
3. 包作废后不可恢复有效。
4. 包作废后不允许继续加入、移出或调整样本。
5. 包作废不改变包内样本的申请状态和样本主状态。
6. 包作废后，包内样本如申请有效且样本仍为待送出，可按条码送出或加入其他符合规则的包。
7. 包作废必须记录作废原因、作废时间、操作人或调用系统。
8. 已送出包如果需要撤回，应走送出撤回；如果接收时发现问题，应走接收异常或样本异常处理，不通过包作废处理。
9. 按包送出后发生送出撤回时，原包不恢复编辑，不允许再次基于原包送出。

#### 1.2.6 打包流程属性

1. 打包是可选流程，不是申请创建、样本送出、样本接收、检测和报告的必经流程。
2. 样本可以不打包，直接按条码或申请送出。
3. 样本也可以先加入包，再按包送出。
4. 未打包样本可以正常送出、接收、检测、上传报告和查询追溯。
5. 打包只影响样本归集、按包送出、按包接收和包维度追溯，不改变样本主状态。
6. 包不承载样本流转状态，样本流转状态仍由样本主状态表达。

#### 1.2.7 样本归包唯一性

1. 一个样本同一时间最多属于一个有效未送出包。
2. 同一样本不能同时存在于多个有效未送出包中。
3. 向包内加入样本时，平台应校验该样本当前是否已属于其他有效未送出包。
4. 如果样本已属于其他有效未送出包，平台拒绝加入新包，并提示样本已在其他包中。
5. 样本从原包移出后，如仍满足入包条件，可以加入其他包。
6. 原包作废后，包内样本如仍满足入包条件，可以加入其他包。
7. 包送出后，未撤回样本已进入已送出状态，不允许再加入其他包。
8. 按包送出后被撤回的样本，如样本主状态回到待送出且仍满足入包条件，可以加入新的未送出包。
9. 被撤回样本加入新包时，不改变原包和原送出快照。

#### 1.2.8 验收标准

1. 能创建包，并记录包所属发起机构。
2. 一个包只能包含同一发起机构的样本。
3. 不允许在同一个包内混装多个发起机构的样本。
4. 只能将申请有效且样本主状态为待送出的样本加入包。
5. 已终止、已送出、已接收、检测中、检测完成或已有报告的样本不能加入包。
6. 同一样本同一时间不能属于多个有效未送出包。
7. 包未送出前允许加入和移出样本，并记录调整留痕。
8. 包送出后包内样本关系锁定，不能继续加入或移出样本。
9. 未送出的包允许作废，作废后不可恢复。
10. 包送出后不允许作废。
11. 包作废不改变包内样本的申请状态和样本主状态。
12. 包作废后，包内样本如仍满足入包条件，可以加入其他包或按条码送出。
13. 打包是可选流程，未打包样本仍可正常按条码或申请送出。
14. 包不承载样本主状态，样本状态仍由送出、接收、检测等动作驱动。
15. 按包送出后发生送出撤回时，原包不恢复编辑，不允许再次基于原包送出。
16. 按包送出后被撤回并回到待送出的样本，如仍满足入包条件，可以加入新的未送出包。
17. 包维度能查询当前样本清单和包内样本变更记录。

### 1.3 申请批次管理

#### 1.3.1 功能定位

申请批次管理用于将多个平台申请归集为批次，支持分类、查询、管理、核对和业务追溯。

申请批次只做申请归集、查询和核对，不参与样本送出、样本接收和样本状态流转。

#### 1.3.2 边界规则

1. 申请批次是平台内用于归集多个平台申请的管理对象。
2. 申请批次不是包。
3. 申请批次不是送出入口。
4. 申请批次不是接收入口。
5. 申请批次不承载样本流转状态。
6. 批次内申请和样本的送出、接收、检测、报告等状态由对应业务对象单独表达。

#### 1.3.3 申请归属批次唯一性

1. 一个平台申请同一时间最多归属于一个有效申请批次。
2. 将申请加入批次时，平台应校验该申请当前是否已属于其他有效批次。
3. 如果申请已属于其他有效批次，平台拒绝加入，并提示申请已在其他批次中。
4. 申请从原批次移出后，可以加入其他有效批次。
5. 平台应保留申请加入批次、移出批次和调整批次归属的变更记录。
6. 历史批次归属记录用于追溯，不影响申请当前批次归属判断。

#### 1.3.4 批次内申请机构范围

1. 创建申请批次时，应明确批次所属发起机构。
2. 批次只能加入同一发起机构下的申请。
3. 不允许在同一申请批次内混入多个发起机构的申请。
4. 将申请加入批次时，平台应校验申请发起机构与批次所属发起机构一致。
5. 不同发起机构如需分别核对，应分别创建各自的申请批次。
6. 平台管理端如需跨机构查看，可通过查询条件或后续统计分析能力实现，不通过申请批次实现跨机构汇总。

#### 1.3.5 批次调整与作废

1. 申请批次状态包括：有效、已作废。
2. 批次创建成功后，状态为有效。
3. 有效批次允许加入符合规则的申请。
4. 有效批次允许从批次中移出申请。
5. 已作废批次不允许继续加入或移出申请。
6. 批次作废后不可恢复有效。
7. 批次作废不改变批次内申请状态、样本主状态、送出状态、接收状态或报告状态。
8. 批次作废只表示该批次分组不再继续使用，不表示批次内申请或样本流程终止。
9. 平台不提供批次关闭、批次锁定、批次解锁和可锁定提示。
10. 批次加入、移出、作废操作必须记录操作时间、操作人或调用系统、操作对象和原因。

#### 1.3.6 验收标准

1. 能创建申请批次，并记录批次所属发起机构。
2. 申请批次只用于申请归集、查询、核对和追溯。
3. 申请批次不作为送出入口。
4. 申请批次不作为接收入口。
5. 申请批次不承载样本流转状态。
6. 一个批次只能包含同一发起机构的申请。
7. 一个申请同一时间最多属于一个有效批次。
8. 有效批次允许加入和移出申请。
9. 已作废批次不允许加入或移出申请。
10. 批次作废后不可恢复有效。
11. 批次作废不影响批次内申请、样本、送出、接收、检测、报告状态。
12. 平台不提供批次关闭、锁定、解锁和可锁定提示。
13. 批次加入、移出、作废操作应记录操作留痕。
14. 能按批次查询当前申请清单。

### 1.4 样本送出管理

#### 1.4.1 功能定位

样本送出管理用于发起机构确认样本从本机构送出至接收方，形成送出记录和送出快照，并推动样本主状态进入已送出。

#### 1.4.2 送出入口

1. 样本送出只支持按条码/申请送出和按包送出。
2. 支持按单个或多个样本条码送出。
3. 支持按平台申请或机构申请定位样本后送出。
4. 支持按包送出。
5. 不支持按申请批次送出。
6. 未打包样本可以按条码或申请送出。
7. 已打包且未送出的样本可以按包送出。
8. 申请批次只用于归集、查询和核对，不作为送出入口。

#### 1.4.3 送出样本范围

1. 仅申请有效、样本主状态为待送出、目标接收方明确的样本允许送出。
2. 申请状态必须为有效。
3. 样本主状态必须为待送出。
4. 样本必须有明确接收方。
5. 已终止申请对应的样本不允许送出。
6. 已送出、已接收、检测中、检测完成或已有报告的样本不允许再次送出。
7. 送出撤回成功后，样本主状态回到待送出，满足其他条件时可以再次送出。
8. 异常退回后的样本是否允许再次送出，应由样本异常处理结果决定，不在送出管理中默认放开。

#### 1.4.4 按包送出校验

1. 按包送出时整包校验；任一样本不满足送出条件，则整包不能送出。
2. 按包送出前，平台应校验包状态、包所属发起机构、包内样本清单和每个样本的送出条件。
3. 包内所有样本均满足送出条件时，允许整包送出。
4. 包内任一样本不满足送出条件时，整包送出失败。
5. 平台不自动移除不满足条件的样本。
6. 平台不支持同一包内部分样本送出、部分样本保留未送出。
7. 如包内存在不满足条件的样本，应在包未送出前由用户手动调整包内样本后再送出。

#### 1.4.5 送出记录与送出快照

1. 送出记录是一次送出确认动作形成的业务凭证，用于表达谁在什么时间、将哪些样本、以什么方式送往哪个接收方。
2. 一次确认送出动作生成一条送出记录。
3. 按条码/申请送出时，一次确认送出中包含的一个或多个样本生成同一条送出记录。
4. 分多次确认送出的样本生成多条送出记录，平台不因接收方相同、时间接近或样本同批而自动合并送出记录。
5. 按包送出时，一次按包确认送出生成一条送出记录，并关联送出时的包。
6. 送出记录应包含送出记录号。
7. 送出记录应记录送出方式，包括按条码/申请送出、按包送出。
8. 送出记录如属于补送，应单独记录补送业务类型，并关联原按包送出记录。
9. 送出记录应记录发起机构、接收方、送出时间、操作人或调用系统。
10. 送出记录应记录本次送出的样本清单。
11. 每个样本的送出快照应至少包含平台申请号、机构申请号、样本条码、患者摘要关键字段、平台标准项目编码清单。
12. 按包送出时，送出记录应记录包号和送出时包内样本清单。
13. 补送记录应关联原按包送出记录，用于追溯本次补送对应的原送出。
14. 送出记录可记录送出备注。
15. 送出记录后续应能展示送出记录状态、业务标签、样本级处理结果和接收侧处理结果摘要。
16. 送出快照形成后，不因后续包调整、申请批次调整、患者摘要变化或其他对象变化而改变。

#### 1.4.6 送出后的状态变化

1. 样本送出成功后，样本主状态由待送出变为已送出。
2. 按条码/申请送出时，送出记录直接关联样本清单。
3. 按包送出时，送出记录关联包号和送出时包内样本清单。
4. 按包送出成功后，包应记录已用于送出。
5. 包已用于送出后，包内样本关系锁定，不允许继续加入或移出样本。
6. 包已用于送出后，不允许作废包。
7. 包不承载样本主状态，样本主状态仍由样本对象表达。
8. 送出记录承载本次送出动作和送出快照，包只作为送出时的归集对象和追溯维度。

#### 1.4.7 送出撤回

1. 送出撤回用于处理送出登记后、接收前发现本次送出登记不应继续成立的场景，包括实物未实际送出、送错样本、多登记样本、误操作送出等。
2. 送出撤回只适用于样本主状态为已送出且尚未被接收的样本。
3. 已接收、检测中、检测完成或已有报告的样本不能撤回送出。
4. 撤回动作针对送出记录中的样本明细，不直接修改原送出快照。
5. 按条码/申请送出和按包送出均允许撤回一条送出记录中的一个或多个未接收样本。
6. 如果撤回样本不是本次送出记录中的全部样本，该送出记录保留为已送出或接收完成状态，并通过有撤回标签和样本明细表达撤回事实。
7. 如果撤回本次送出记录中的全部样本，该送出记录状态为全部撤回。
8. 撤回成功的样本主状态回到待送出。
9. 未撤回样本继续处于已送出，并继续等待接收侧处理。
10. 已撤回样本不能再基于原送出记录接收。
11. 撤回不删除原送出记录，不修改原送出快照，不表示历史送出登记不存在。
12. 撤回成功的样本满足送出条件时，可以再次按条码/申请送出，或加入新的未送出包后按新包送出。
13. 重新送出必须生成新的送出记录，不修改或复用原送出记录。
14. 按包送出发生样本撤回时，撤回的是样本在本次送出记录中的送出关系，不是从原包中移除样本。
15. 按包送出发生部分样本撤回时，原包、原包快照和原送出快照均不改变。
16. 按包送出发生整包撤回时，本质是撤回该送出记录下全部未接收样本；原包仍保留已用于送出的历史标记，不恢复编辑，不允许再次基于原包送出。
17. 送出撤回必须记录撤回原因、撤回时间、操作人或调用系统、撤回样本清单。

#### 1.4.8 送出补送

1. 补送不是独立主流程，是按包送出后的限定后续动作。
2. 补送用于原按包送出记录整体有效，但发现有应随该包送出的样本未包含在原包或原送出记录中的场景。
3. 按条码/申请送出时如漏送样本，漏送样本仍为待送出，直接再次普通送出即可，不要求使用补送。
4. 补送不向原包追加样本，不修改原包清单，不修改原送出快照。
5. 补送应生成新的送出记录，业务类型标记为补送，并关联原按包送出记录。
6. 补送样本必须满足送出样本范围要求。
7. 补送记录可以按条码/申请形成，也可以通过新的未送出包形成。
8. 接收方按补送记录独立接收补送样本。
9. 原按包送出记录和补送记录应能在追溯中互相关联展示。

#### 1.4.9 送出记录状态、标签与样本明细

1. 送出记录状态用于表达一条送出记录是否仍需要接收侧继续处理，不替代样本主状态。
2. 送出记录状态包括：已送出、接收完成、全部撤回。
3. 送出记录创建成功后，状态为已送出。
4. 送出记录中仍存在未撤回且未形成接收侧处理结果的样本时，状态保持为已送出。
5. 送出记录中所有未撤回样本均已有接收侧处理结果后，状态为接收完成。
6. 送出记录中全部样本均被撤回时，状态为全部撤回。
7. 接收侧处理结果包括正常接收、异常退回、接收后异常处理、因申请终止不可接收或后续在接收管理中定义的其他接收结果。
8. 部分撤回不作为送出记录主状态；部分撤回通过有撤回标签和样本明细表达。
9. 送出记录业务标签用于提示记录内存在特殊情况，不承担流程判断。
10. 送出记录业务标签至少包括：有撤回、有异常、补送。
11. 有撤回标签用于表示送出记录中存在部分样本已撤回，但该记录未达到全部撤回。
12. 有异常标签用于表示送出记录中存在异常退回、接收后异常处理或其他接收侧异常结果。
13. 补送标签用于表示该送出记录是原按包送出记录的补送记录。
14. 送出记录内每个样本应保留样本级处理结果，包括待接收、已撤回、已接收、异常退回、接收后异常处理、因申请终止不可接收等。
15. 单个样本不使用部分撤回或全部撤回描述；单个样本只记录是否已撤回。

#### 1.4.10 验收标准

1. 支持按条码/申请送出样本。
2. 支持按包送出样本。
3. 不支持按申请批次送出。
4. 仅申请有效、样本待送出、接收方明确的样本可送出。
5. 按包送出时整包校验，任一样本不满足条件则整包失败。
6. 送出成功后生成送出记录和不可变送出快照。
7. 送出成功后样本状态进入已送出。
8. 按包送出后包记录已用于送出，包内样本关系锁定。
9. 已送出未接收样本支持按送出记录明细撤回一个或多个样本。
10. 已接收及后续状态样本不能撤回送出。
11. 撤回成功样本回到待送出。
12. 重新送出必须生成新的送出记录，不修改或复用原送出记录。
13. 按包送出发生撤回时，原包不恢复编辑，不允许再次基于原包送出。
14. 按包送出漏样本时支持补送，补送生成新的送出记录并关联原按包送出记录。
15. 按条码/申请漏送样本时，直接再次普通送出即可。
16. 送出记录状态包括已送出、接收完成、全部撤回。
17. 部分撤回通过有撤回标签和样本明细表达，不作为送出记录主状态。
18. 送出记录能展示样本级处理结果和接收侧处理结果。
19. 送出快照不因后续包、批次或申请相关信息变化而改变。

### 1.5 样本接收管理

#### 1.5.1 功能定位

样本接收管理用于接收方确认已送出的样本到达接收方，形成接收记录，并推动样本主状态进入已接收或形成异常接收处理结果。

#### 1.5.2 接收入口

1. 样本接收只支持按条码接收和按包接收。
2. 支持按样本条码接收。
3. 支持按包接收。
4. 不支持按申请批次接收。
5. 按条码接收时，必须能明确发起机构ID和样本条码。
6. 按包接收时，平台根据包和送出记录定位包内样本。
7. 未打包样本可按条码接收。
8. 已按包送出的样本可按包接收，也可在满足规则时按条码逐个接收。

#### 1.5.3 接收样本范围

1. 仅已送出、未撤回、接收方匹配的样本允许接收。
2. 样本主状态必须为已送出。
3. 样本不能处于已撤回送出状态。
4. 当前接收方必须与送出记录中的接收方一致。
5. 未送出的样本不能接收。
6. 已撤回送出的样本不能接收。
7. 已接收、检测中、检测完成或已有报告的样本不能重复接收。
8. 平台不会因接收未送出样本而自动补记送出记录。
9. 接收时必须能关联到未全部撤回的送出记录，以及该记录中未撤回、未处理的样本明细。
10. 申请已终止的样本不允许接收。
11. 样本送出后、接收前发生申请终止时，样本不回到待送出，接收方接收时应提示申请已终止。

#### 1.5.4 按条码接收定位规则

1. 按条码接收时，必须能明确接收方、发起机构和样本条码。
2. 平台按发起机构和样本条码定位平台申请和样本。
3. 如果只能获得样本条码、无法明确发起机构，平台不应自动模糊匹配，应提示无法定位样本。
4. 页面扫码接收时，可以通过先选择发起机构、送出记录或包来确定发起机构，再连续扫码。
5. 不同发起机构存在相同条码时，平台按发起机构ID隔离识别，不视为重复样本。

#### 1.5.5 按包接收结果处理

1. 按包接收允许逐样本给出接收结果。
2. 包只是批量接收入口，不强制包内所有样本使用同一接收结果。
3. 按包接收时，平台应展示该送出记录下未撤回、未处理的待接收样本清单。
4. 接收人员或接收方系统可以逐样本确认接收结果。
5. 样本级接收结果可以包括正常接收、异常退回、接收后异常处理、因申请终止不可接收等。
6. 包内部分样本正常接收时，正常样本进入已接收。
7. 包内部分样本异常时，异常样本按异常接收规则处理，不影响其他正常样本接收。
8. 已撤回样本不进入待接收清单，但可在送出记录明细或历史链路中展示为已撤回。
9. 包接收记录应能汇总展示本次接收处理样本的接收结果。

#### 1.5.6 接收异常处理路径

1. 接收异常支持异常退回和接收后异常处理两类路径。
2. 接收时发现异常，可选择异常退回。
3. 异常退回时，平台登记异常和退回记录，样本不进入已接收。
4. 异常退回适用于样本破损、条码无法识别、样本漏送、样本不符、容器不符等不适合接收的情况。
5. 接收时发现异常，也可选择接收后异常处理。
6. 接收后异常处理时，样本先进入已接收，同时登记异常记录。
7. 接收后异常处理适用于样本可先接收，但需要后续补充说明、人工确认或继续跟进的情况。
8. 接收后异常处理的后续结果，包括继续检测、补充说明、退回、终止或关闭异常，在样本异常处理章节继续定义。
9. 异常退回和接收后异常处理均应记录异常类型、异常描述、发现时间、发现人或调用系统、处理意见。

#### 1.5.7 接收记录

1. 接收成功、异常退回或接收后异常处理时，均应形成接收记录或接收处理记录。
2. 接收记录应包含接收记录号。
3. 接收记录应记录接收方式，包括按条码接收、按包接收。
4. 接收记录应记录发起机构、接收方、接收时间、操作人或调用系统。
5. 接收记录应关联送出记录号。
6. 按包接收时，接收记录应关联包号。
7. 接收记录应记录本次处理的样本清单。
8. 每个样本应记录接收结果，包括正常接收、异常退回、接收后异常处理。
9. 如存在异常，应记录异常类型、异常描述和处理意见。
10. 接收记录可记录接收备注。
11. 接收记录应关联申请、样本条码、送出记录和接收方。
12. 因申请终止不可接收时，应记录申请已终止的接收侧处理结果或拦截记录，用于后续追溯。

#### 1.5.8 接收后样本状态变化

1. 正常接收和接收后异常处理进入已接收；异常退回不进入已接收。
2. 样本正常接收后，样本主状态由已送出变为已接收。
3. 样本选择接收后异常处理时，样本主状态由已送出变为已接收，同时生成异常记录。
4. 样本选择异常退回时，样本不进入已接收。
5. 异常退回后的样本状态和后续处理方式，在样本异常处理章节定义。
6. 接收动作不直接将样本推进到检测中。
7. 检测中状态应由后续检测状态回传或检测流程触发。
8. 当送出记录中所有未撤回样本均已有接收侧处理结果后，送出记录状态为接收完成。
9. 因申请终止不可接收的样本不进入已接收，样本主状态不回退。

#### 1.5.9 验收标准

1. 支持按条码接收。
2. 支持按包接收。
3. 不支持按申请批次接收。
4. 按条码接收必须能明确接收方、发起机构和样本条码。
5. 仅已送出、未撤回、接收方匹配的样本允许接收。
6. 未送出样本不能接收，平台不自动补记送出记录。
7. 按包接收允许逐样本给出接收结果。
8. 正常接收后样本进入已接收。
9. 异常退回时样本不进入已接收。
10. 接收后异常处理时样本进入已接收并生成异常记录。
11. 接收记录能关联申请、样本条码、送出记录和接收方。
12. 按包接收记录能关联包并展示本次处理样本的接收结果。
13. 接收完成后能回写或更新送出记录的接收侧处理结果摘要，并在满足条件时将送出记录状态更新为接收完成。
14. 申请已终止的样本不允许接收，并应能展示因申请终止不可接收的处理结果或拦截记录。

### 1.6 样本异常处理

#### 1.6.1 功能定位

样本异常处理用于记录和处理样本相关异常，包括接收环节产生的异常，以及接收后人工发现的样本异常。

样本异常处理不作为全平台异常中心，不处理申请错误、送出错误、报告错误和推送失败等非样本类异常。

#### 1.6.2 异常处理范围

1. 样本异常处理只处理样本相关异常。
2. 接收时选择异常退回的样本，进入样本异常处理记录范围。
3. 接收时选择接收后异常处理的样本，进入样本异常处理记录范围。
4. 已接收后人工发现的样本破损、信息不一致、容器问题、样本量不足等样本问题，进入样本异常处理记录范围。
5. 申请信息错误应优先按申请终止、重新提交或业务协商处理，不纳入样本异常处理主范围。
6. 送出错误在接收前优先按送出撤回处理，不纳入样本异常处理主范围。
7. 报告内容错误按报告重传或报告作废处理，不纳入样本异常处理主范围。
8. 推送失败按推送记录和推送管理处理，不纳入样本异常处理主范围。

#### 1.6.3 异常状态与样本主状态关系

1. 异常作为独立异常记录管理，不覆盖样本主状态。
2. 样本主状态仍按正常主链表达，包括待送出、已送出、已接收、检测中、检测完成。
3. 样本异常不作为样本主状态。
4. 异常处理状态由异常记录单独表达。
5. 异常记录状态包括：待处理、处理中、已关闭。
6. 一个样本可以存在异常记录，同时保留其当前样本主状态。
7. 接收后异常处理时，样本主状态可以为已接收，异常记录状态可以为待处理或处理中。
8. 异常退回时，样本不进入已接收，并生成异常记录和退回记录。

#### 1.6.4 异常处理结果

1. 异常处理结果包括继续检测、退回样本、终止处理、关闭异常。
2. 继续检测表示样本虽存在异常记录，但业务判断可以继续后续检测流程。
3. 退回样本表示样本需要退回发起机构或相关责任方。
4. 终止处理表示样本不再继续后续检测或报告流程。
5. 关闭异常表示异常已完成说明、确认或处理，不再需要继续跟进。
6. 补充说明作为处理意见记录，不作为独立处理结果。
7. 重新送出、重新创建申请、新条码等作为异常处理后的后续业务动作，不作为异常处理结果枚举。
8. 每次处理结果变更应记录处理时间、处理人或调用系统、处理意见。

#### 1.6.5 异常退回后的样本处理

1. 异常退回不进入已接收，不回到待送出；退回事实由异常记录和退回记录承载。
2. 接收时选择异常退回的样本，不进入已接收。
3. 异常退回后的样本不自动回到待送出。
4. 平台应生成异常记录和退回记录。
5. 退回记录应关联申请、样本条码、送出记录、接收方和退回原因。
6. 异常退回后的后续处理方式由异常处理结果和业务规则决定。
7. 如果后续需要重新送检，不由平台自动重送，应按异常处理后的业务动作处理。
8. 是否复用原申请、是否重新创建申请、是否使用新条码，在样本异常处理或后续业务规则中明确，不由异常退回动作自动决定。

#### 1.6.6 接收后异常处理与检测

1. 接收后异常处理的样本允许继续检测，但必须有异常处理结果为继续检测或异常已关闭。
2. 接收后异常处理的样本主状态进入已接收，同时生成异常记录。
3. 异常记录处于待处理或处理中时，默认不允许进入检测中或检测完成。
4. 异常处理结果为继续检测时，允许样本继续进入检测流程。
5. 异常记录已关闭且未标记终止处理时，允许样本继续进入检测流程。
6. 异常处理结果为退回样本或终止处理时，不允许继续检测。
7. 是否继续检测应记录处理意见、处理时间、处理人或调用系统。

#### 1.6.7 异常记录内容

1. 异常记录应能支撑样本异常来源、处理过程、处理结果和退回追溯。
2. 异常记录应包含异常记录号。
3. 异常记录应关联平台申请号、发起机构、接收方和样本条码。
4. 异常记录应关联送出记录号。
5. 如样本已接收，异常记录应关联接收记录号。
6. 异常记录应记录异常来源，包括接收异常退回、接收后异常、已接收后人工登记。
7. 异常记录应记录异常类型和异常描述。
8. 异常记录应记录发现时间、发现人或调用系统。
9. 异常记录应记录异常状态，包括待处理、处理中、已关闭。
10. 异常记录应记录处理结果，包括继续检测、退回样本、终止处理、关闭异常。
11. 异常记录应记录处理意见、处理时间、处理人或调用系统。
12. 如处理结果涉及退回样本，应关联退回记录。

#### 1.6.8 验收标准

1. 能记录接收异常退回、接收后异常、已接收后人工登记的样本异常。
2. 样本异常以独立异常记录管理，不覆盖样本主状态。
3. 异常记录状态包括待处理、处理中、已关闭。
4. 异常处理结果包括继续检测、退回样本、终止处理、关闭异常。
5. 异常退回不进入已接收，也不回到待送出。
6. 异常退回生成异常记录和退回记录。
7. 接收后异常处理样本进入已接收并生成异常记录。
8. 接收后异常未处理完成前，默认不允许进入检测中或检测完成。
9. 处理结果为继续检测，或异常已关闭且未终止处理时，允许继续检测。
10. 处理结果为退回样本或终止处理时，不允许继续检测。
11. 异常记录能关联申请、样本条码、送出记录、接收记录和退回记录。
12. 异常处理过程能记录处理意见、处理时间、处理人或调用系统。

### 1.7 样本状态管理

#### 1.7.1 功能定位

样本状态管理用于表达样本在平台主流程中的当前位置，并为申请查询、送出、接收、检测、报告和运维追溯提供统一状态依据。

样本状态管理只管理样本主状态，不替代申请状态、送出记录状态、接收处理结果、异常状态、报告状态和推送状态。

#### 1.7.2 样本主状态范围

1. 样本主状态只保留正常流转主链。
2. 样本主状态包括：待送出、已送出、已接收、检测中、检测完成。
3. 样本主状态不包含异常、撤回、退回、申请终止、报告上传、报告发布、报告作废等状态。
4. 申请终止由申请状态表达。
5. 送出撤回由送出记录和撤回记录表达。
6. 接收异常退回由接收处理记录、异常记录和退回记录表达。
7. 样本异常由异常记录表达。
8. 报告上传、审核、发布、撤回由报告相关状态表达。
9. 样本主状态用于表达样本在平台主流程中的当前位置，不替代其他业务对象状态。

#### 1.7.3 检测中状态定位

1. 检测中表示接收方已经开始对样本进行检测处理。
2. 检测中作为可选状态保留。
3. 样本正常接收后，默认停留在已接收，不自动进入检测中。
4. 如果接收方系统回传检测开始，或平台存在人工触发开始检测的业务入口，样本可由已接收进入检测中。
5. 如果接收方不回传检测开始，平台允许样本由已接收直接进入检测完成。
6. 检测中不是报告上传或检测完成的强制前置状态。
7. 样本进入检测中前，应满足申请有效、样本已接收、未被异常阻断等前置条件。
8. 如果样本存在待处理或处理中的接收后异常，默认不允许进入检测中，除非异常处理结果允许继续检测。

#### 1.7.4 检测完成触发规则

1. 报告上传成功后，平台将对应样本主状态更新为检测完成。
2. 如果样本当前状态为已接收，允许直接进入检测完成。
3. 如果样本当前状态为检测中，允许进入检测完成。
4. 检测中不是进入检测完成的强制前置状态。
5. 报告上传成功是平台判断检测完成的主要业务依据。
6. 样本进入检测完成前，应满足申请有效、样本已接收、未被异常阻断等前置条件。
7. 如果样本存在待处理或处理中的接收后异常，默认不允许进入检测完成，除非异常处理结果允许继续检测或异常已关闭且未终止处理。
8. 申请已终止时，样本不允许继续推进到检测完成。

#### 1.7.5 未接收样本与报告上传

1. 报告上传前，样本必须已经完成正常接收，或接收后异常处理并允许继续检测。
2. 样本主状态为待送出、已送出的，不允许上传报告。
3. 样本发生异常退回且未进入已接收的，不允许上传报告。
4. 平台不因报告上传自动补记样本接收。
5. 平台不允许未接收样本通过报告上传直接进入检测完成。
6. 如果接收方上传未接收样本报告，平台应拒绝并提示未满足上传条件。
7. 申请已终止的样本不允许通过报告上传进入检测完成。
8. 该规则后续在报告管理章节继续细化报告上传业务边界。

#### 1.7.6 样本状态逆流程原则

1. 样本主状态原则上按正常主链向前流转，不通过回退主状态抹除已经发生的业务事实。
2. 已送出且未接收的样本，允许通过送出撤回回到待送出。
3. 送出撤回是样本主状态回退的明确例外，适用于尚未完成接收交接的样本。
4. 已接收、检测中、检测完成后的问题，不通过直接回退样本主状态处理。
5. 已接收后的样本问题，应通过样本异常处理、退回记录或后续业务动作处理。
6. 报告内容错误，应通过报告重传或报告作废处理，不通过直接回退样本主状态处理。
7. 报告作废后不影响样本检测完成状态；作废只影响报告版本有效性。
8. 平台不提供通用的样本主状态手工回退能力。
9. 申请终止不属于样本主状态逆流程；申请终止后样本主状态保持终止发生时的状态。

#### 1.7.7 样本状态变更历史

1. 每次样本主状态变化均应形成状态变更历史。
2. 状态变更历史应记录变更前状态、变更后状态、触发动作、关联业务记录、变更时间、操作人或调用系统。
3. 触发动作包括申请创建、送出、送出撤回、接收、检测开始、报告上传成功等。
4. 关联业务记录可包括申请号、送出记录号、接收记录号、异常记录号、报告记录号等。
5. 状态变更历史作为审计留痕，不允许人工编辑或删除。
6. 平台不单独提供“样本状态记录管理”菜单或维护功能。
7. 状态变更历史可在申请详情、样本详情、流转时间线或业务运维明细中展示。
8. 后续业务运维明细查询章节可继续定义状态历史的查询条件和展示范围。

#### 1.7.8 页面兜底与状态人工维护边界

1. 样本状态不提供独立人工维护入口。
2. 平台不提供直接将样本改为待送出、已送出、已接收、检测中、检测完成的页面操作。
3. 样本主状态只能由业务动作驱动。
4. 驱动样本主状态变化的业务动作包括申请创建、送出、送出撤回、接收、检测状态回传、报告上传成功等。
5. 对于未完成系统对接的机构，平台可提供对应业务动作的页面兜底入口。
6. 页面兜底入口应操作业务动作本身，例如页面送出、页面接收、页面异常处理、页面上传报告，而不是直接修改样本状态。
7. 页面业务动作必须生成对应业务记录和状态变更历史。
8. 检测中不提供单独页面人工触发按钮。
9. 检测中仅由接收方系统回传或后续检测流程触发；如果没有检测中回传，允许样本由已接收直接进入检测完成。
10. 检测完成由报告上传成功驱动，不提供单独人工改为检测完成的状态维护入口。

#### 1.7.9 样本状态管理页面范围

1. 样本状态管理不作为独立功能菜单。
2. 平台不提供独立的“样本状态管理”页面。
3. 样本当前主状态可在申请详情、样本详情、送出记录、接收记录、异常记录、报告记录和业务运维明细中展示。
4. 样本状态变更历史可在流转时间线或业务运维明细中展示。
5. 样本状态不提供独立编辑、调整、回退、删除操作。
6. 如后续需要按状态筛选样本，应归入申请查询、样本查询或业务运维明细查询，不单独新增状态管理模块。

#### 1.7.10 验收标准

1. 样本主状态范围包括待送出、已送出、已接收、检测中、检测完成。
2. 样本主状态不包含异常、撤回、退回、申请终止、报告上传、报告发布、报告作废等状态。
3. 申请创建成功后，样本主状态进入待送出。
4. 送出成功后，样本主状态进入已送出。
5. 已送出且未接收的样本撤回成功后，样本主状态回到待送出。
6. 正常接收或接收后异常处理时，样本主状态进入已接收。
7. 异常退回样本不进入已接收。
8. 检测中作为可选状态保留；无检测中回传时，样本允许由已接收直接进入检测完成。
9. 检测中不提供单独页面人工触发按钮。
10. 报告上传成功后，样本主状态进入检测完成。
11. 未接收样本不允许上传报告，平台不因报告上传自动补记接收。
12. 样本主状态原则上不回退，唯一明确例外为已送出未接收样本通过送出撤回回到待送出。
13. 申请终止不回退样本主状态，样本主状态保持终止发生时的状态。
14. 平台不提供直接人工维护样本主状态的入口。
15. 未完成系统对接的机构可通过页面业务动作完成送出、接收、异常处理、报告上传等操作，但页面操作必须生成对应业务记录，不允许直接修改样本主状态。
16. 每次样本主状态变化均应形成状态变更历史。
17. 状态变更历史应记录变更前状态、变更后状态、触发动作、关联业务记录、变更时间、操作人或调用系统。
18. 状态变更历史不允许人工编辑或删除。
19. 样本状态管理不提供独立功能菜单或独立管理页面。
20. 样本当前主状态和状态变更历史可在申请详情、样本详情、流转时间线或业务运维明细中展示。
21. 报告作废后不影响样本检测完成状态，具体规则在报告审核与发布章节定义。

### 1.8 报告审核与发布

#### 1.8.1 功能定位

报告审核与发布用于管理接收方上传报告后的发布控制、报告有效性、审核留痕、重传、作废和查询边界。

本功能只做报告发布控制，不作为医学自动审核规则引擎。平台不判断报告内容是否医学正确，不自动判断结果高低、异常或危急值。

报告状态独立于样本主状态。报告审核不通过、报告重传、报告作废均不回退样本主状态。

#### 1.8.2 审核开关

1. 平台存在统一的报告审核开关。
2. 审核开关启用时，报告上传或重传成功后进入待审核，审核通过后发布。
3. 审核开关未启用时，报告上传或重传成功后自动发布。
4. 审核开关配置功能不在本章节展开，本 PRD 只描述开关对报告业务流程的影响。
5. 暂不支持按机构、项目、发起方/接收方关系配置差异化审核规则。

#### 1.8.3 报告上传前置条件

1. 申请必须存在且处于有效状态。
2. 样本必须已经完成正常接收，或属于接收后异常处理且允许继续检测。
3. 样本处于待送出、已送出的，不允许上传报告。
4. 样本存在阻断性未关闭异常时，不允许上传报告。
5. 上传方必须是该申请/样本对应的接收方机构或其授权系统。
6. 申请已终止、样本异常退回且未进入已接收的，不允许上传报告。
7. 平台不因报告上传自动补记接收记录。
8. 不提供管理员绕过上传前置校验的兜底能力。

#### 1.8.4 报告上传内容

1. 报告上传必须包含报告 PDF。
2. 未包含 PDF 的报告上传请求应被拒绝。
3. 结构化检验结果可以上传，但不是报告生成和发布的必填条件。
4. 未提供结构化结果，不影响报告版本生成、审核、发布、查询、下载和推送。
5. 报告上传不强制提供报告覆盖的项目编码清单。
6. 平台上传什么就保存什么、展示什么。
7. 平台不解析 PDF，不判断报告覆盖了哪些检验项目。
8. 平台不做项目级完成判断、漏报判断、重复覆盖判断。
9. 同一申请/样本条码下只维护一个报告业务对象，多次上传形成该报告的不同版本。
10. 报告名称或报告类型可以作为可选展示字段，但不作为报告拆分、版本合并或业务校验依据。

#### 1.8.5 报告上传成功与样本检测完成

1. 样本主状态按样本维度管理，不表达项目级完成度。
2. 报告上传成功后，平台将对应样本主状态更新为检测完成。
3. 报告是否已发布、是否审核通过，不影响样本主状态已经进入检测完成。
4. 如果审核不通过、报告重传、报告作废，样本主状态原则上不回退。
5. 报告有效性由报告状态表达，样本检测完成只表示平台已收到该样本对应的检测报告。
6. 平台不判断申请内所有项目是否均已出报告。
7. 申请终止后，不允许通过报告上传推动样本进入检测完成。

#### 1.8.6 报告版本与上传失败

1. 报告上传成功后立即生成报告版本号。
2. 每次重传生成新的报告版本号。
3. 版本号用于区分同一申请、同一样本条码、同一报告业务对象下的不同报告版本。
4. 版本号一经生成，不允许复用或覆盖。
5. 版本号生成规则属于实现细节，PRD 只要求版本可唯一识别、可排序、可追溯。
6. 只有报告上传前置校验通过，并且报告 PDF 保存成功后，才生成报告版本。
7. 上传失败不生成报告版本号，不进入报告业务状态，不推动样本进入检测完成。
8. 上传失败时应能向上传方说明未生成报告版本的业务原因。
9. 上传失败不作为报告业务版本展示。

#### 1.8.7 报告发布审核

1. 审核开关启用时，报告上传成功后进入待审核。
2. 审核人员必须逐份打开报告详情后处理。
3. 平台不提供批量审核通过、批量审核不通过功能。
4. 审核人员应能查看报告 PDF、报告关联申请、样本、患者摘要、项目、上传方、上传时间和历史版本信息。
5. 审核人员可对单份报告执行审核通过或审核不通过。
6. 审核通过后，报告直接进入已发布。
7. 平台不设置独立待发布状态，不提供单独发布按钮。
8. 审核通过即代表报告对发起机构可查询、可下载，并按配置触发推送。
9. 审核人员不能修改报告 PDF、结构化结果、危急值标记、项目结果或患者申请信息。
10. 如发现报告内容、文件、项目覆盖或患者信息存在问题，应审核不通过并填写原因。

#### 1.8.8 审核不通过

1. 审核不通过后，当前报告版本状态为审核不通过。
2. 审核不通过版本不允许发布、查询给发起机构、下载给普通业务用户或对外推送。
3. 审核不通过原因必填。
4. 审核不通过原因记录在平台内，可在报告详情、审核记录或业务运维明细中查看。
5. 本章节不要求向上传方系统提供审核不通过原因查询能力。
6. 上传方如需重新提交，应通过报告重传生成新报告版本。
7. 新版本按审核开关重新进入待审核或自动已发布。
8. 原审核不通过版本保留历史，不物理删除，不作为最新有效报告。
9. 报告审核不通过只影响报告版本状态，不回退样本主状态。

#### 1.8.9 报告重传

1. 报告重传应由报告上传方发起。
2. 平台审核人员不能代上传方重传报告。
3. 平台管理员不能代上传方重传报告。
4. 待审核报告允许上传方主动重传。
5. 待审核版本被重传后，原待审核版本标记为已重传作废，不再允许审核、发布、查询或推送。
6. 同一报告不允许同时存在多个可被审核的待审核版本。
7. 已发布报告允许重传生成新版本。
8. 已发布报告重传后，新版本发布前，原已发布版本仍为当前最新有效报告。
9. 新版本审核通过并发布后，新版本成为最新有效报告，原已发布版本标记为已替代。
10. 如果新版本审核不通过，原已发布版本继续有效，不受影响。
11. 已发布报告发起重传时，重传原因必填。
12. 已替代、已作废历史版本如允许基于其重传，重传原因也应必填。
13. 待审核报告主动重传时，重传原因可选。
14. 审核不通过报告重传时，可引用审核不通过原因，重传原因可选。
15. 每次重传都必须形成重传记录，并关联原报告版本和新报告版本。
16. 报告作废后，如上传方需要重新提供报告，可基于已作废版本重传生成新版本。
17. 已作废版本仍保留历史状态，不恢复为已发布。
18. 申请已终止后，不允许继续基于该申请重传报告。

#### 1.8.10 报告作废

1. 报告作废用于处理当前有效报告不应继续对外查询、下载或推送的场景。
2. 作废只允许作用于当前有效的已发布报告。
3. 待审核、审核不通过、已重传作废、已替代、已作废版本不允许再次作废。
4. 报告作废可由报告上传方发起。
5. 平台授权人员可在必要时发起报告作废，用于平台发现明显风险或收到线下确认问题后的处置。
6. 发起机构不能直接作废接收方上传的报告。
7. 报告作废提交后立即生效，不受报告审核开关控制。
8. 作废生效后，该报告版本不再作为当前有效报告。
9. 作废后普通报告查询不再提供该报告。
10. 作废后平台普通报告查询页面显示该样本条码暂无当前有效报告。
11. 作废后不自动回退到上一已替代历史版本。
12. 作废后不可恢复为已发布，不提供重新启用能力。
13. 如需重新对外提供报告，上传方应通过报告重传生成新版本。
14. 已作废版本允许作为重传来源继续生成新版本，但已作废版本本身不恢复有效。
15. 报告作废必须填写作废原因。
16. 作废原因建议分类包括：报告错误、重复报告、业务取消、其他。
17. 报告作废必须记录作废时间、作废人或调用系统、作废原因和关联报告版本。
18. 报告作废不删除历史报告版本。
19. 报告作废不影响样本检测完成状态。
20. 报告作废是否触发对外作废通知，放到报告和危急值推送管理章节展开。
21. 申请终止时如存在当前有效已发布报告，当前有效报告应进入报告作废或失效处理；作废或失效后不自动恢复历史版本。

#### 1.8.11 报告状态

1. 报告状态包括待审核、审核不通过、已重传作废、因申请终止失效、已发布、已替代、已作废。
2. 待审核：审核开关启用时，报告上传或重传成功后的状态。
3. 审核不通过：发布审核未通过，不可发布、查询、下载、推送。
4. 已重传作废：待审核版本被新重传版本替代，不再允许审核。
5. 因申请终止失效：待审核等未发布报告版本因申请终止退出待处理范围，不再允许审核、发布、查询、下载或推送。
6. 已发布：当前可对发起机构查询、下载、推送的有效报告。
7. 已替代：原已发布版本被新发布版本替代。
8. 已作废：当前有效已发布报告被作废后进入该状态，不再作为当前有效报告。
9. 已发布报告不允许反审核，不允许回退到待审核。
10. 已发布报告发现问题时，只能通过报告重传或报告作废处理。
11. 平台不提供管理员强制反审核能力。

#### 1.8.12 审核记录与状态变化记录

1. 每次审核动作必须形成审核记录。
2. 审核记录至少包含报告版本号、审核动作类型、审核结果、审核人、审核时间、审核意见或不通过原因。
3. 审核动作类型为报告发布审核。
4. 审核通过或不通过导致报告状态变化时，应形成报告状态变化记录。
5. 报告状态变化记录用于追溯状态从什么变成什么，以及由哪个业务动作触发。
6. 不要求在审核记录本身重复记录审核前状态和审核后状态。
7. 发布审核通过时，审核意见可选填写。
8. 发布审核不通过时，不通过原因必填。
9. 报告作废不是审核动作，不进入审核记录；作废应形成作废记录和报告状态变化记录。
10. 因申请终止导致未发布报告版本失效时，应形成报告状态变化记录。

#### 1.8.13 报告查询、下载和页面入口

1. 普通报告查询只提供当前有效的已发布报告。
2. 普通报告查询不提供待审核、审核不通过、已重传作废、因申请终止失效、已替代、已作废报告。
3. 外部系统不能通过普通报告查询获取历史版本或无效版本。
4. 如后续确需对外开放历史版本，应作为独立的版本追溯能力处理，不与普通报告查询混用。
5. 平台普通报告查询页面默认只展示当前有效报告。
6. 报告查询页面支持在线查看和下载当前有效已发布报告 PDF。
7. 非当前有效报告不在普通报告查询页面展示，也不可从该入口下载。
8. 报告下载应记录操作留痕。
9. 报告审核入口用于处理发布审核。
10. 发布审核页签展示状态为待审核的报告版本；因申请终止失效的报告版本不进入发布审核页签。
11. 报告作废入口仅对上传方和平台授权人员开放。
12. 报告版本追溯用于有权限人员查看全部历史版本、替代关系、作废记录和审核记录。
13. 申请详情、样本详情、业务运维明细中可以展示报告摘要，并跳转到对应报告页面。
14. 普通业务用户不直接面对全部报告版本，避免误用历史或无效报告。
15. 更细的下载权限是否配置，放到权限/审计章节处理，不在报告审核与发布章节展开。

#### 1.8.14 报告上传结果和上传方通知

1. 报告上传成功后，上传方应能获得报告版本号。
2. 上传方应能获得当前报告状态：审核开关启用时通常为待审核，审核开关未启用时为已发布。
3. 上传方应能知道报告是否已自动发布。
4. 上传失败时，应向上传方说明未生成报告版本的业务原因。
5. 不提供完整报告详情。
6. 本章节不新增上传方系统侧查询审核或发布结果的要求。
7. 本版本不要求在报告审核通过后通知上传方。
8. 审核不通过也不要求通知上传方系统。
9. 上传方如需查看报告审核、发布状态或不通过原因，可通过平台页面查看。
10. 上传方系统侧自动闭环能力作为后续增强，不纳入当前报告审核与发布章节。

#### 1.8.15 危急值与报告审核开关

1. 报告上传时可以同时上传危急值信息。
2. 危急值必须关联本次报告版本、申请、样本条码、上传方和接收方。
3. 审核开关启用时，报告和关联危急值在审核通过后才对外发布或推送。
4. 审核开关未启用时，报告上传成功自动发布，关联危急值进入可推送状态。
5. 危急值本身的记录、平台内部处理、业务推送边界和医院侧处理回执，在危急值记录与处理留痕、报告和危急值推送管理章节定义。
6. 平台不自动判断危急值，危急值信息由上传方提供。

#### 1.8.16 验收标准

1. 平台支持统一报告审核开关对报告上传、重传和发布审核的业务流程产生影响。
2. 审核开关启用时，报告上传或重传成功后进入待审核。
3. 审核开关未启用时，报告上传或重传成功后自动发布。
4. 报告上传前必须校验申请有效、样本已接收或允许继续检测、上传方为对应接收方、无阻断性未关闭异常。
5. 待送出、已送出、申请已终止、异常退回且未接收的样本不允许上传报告。
6. 报告上传必须包含 PDF，结构化结果可选。
7. 报告上传不强制提供覆盖项目范围，平台不做项目级完成、漏报或重复覆盖判断。
8. 报告上传成功后生成报告版本号，并推动样本主状态进入检测完成。
9. 报告审核不通过、重传、作废均不回退样本检测完成状态。
10. 上传失败不生成报告版本，不推动样本进入检测完成。
11. 审核通过即发布，不设置独立待发布状态或单独发布按钮。
12. 报告审核不支持批量审核。
13. 审核人员不能修改报告内容，只能审核通过或审核不通过。
14. 审核不通过原因必填，审核不通过版本不可发布、查询、下载或推送。
15. 待审核报告允许上传方主动重传，原待审核版本标记为已重传作废。
16. 已发布报告重传后，新版本发布前原已发布版本继续有效。
17. 新版本发布后成为当前有效报告，原已发布版本标记为已替代。
18. 上传方可以发起报告重传和报告作废，平台授权人员可在必要时发起报告作废。
19. 报告作废只允许作用于当前有效已发布报告，作废立即生效且不受审核开关控制。
20. 报告作废后进入已作废，不再作为当前有效报告。
21. 报告作废后不自动回退历史版本；如需重新对外提供报告，应通过重传生成新版本。
22. 申请终止时，未发布报告版本应进入因申请终止失效，不再允许审核、发布、查询、下载或推送。
23. 申请终止时如存在当前有效已发布报告，当前有效报告应进入报告作废或失效处理。
24. 报告状态包括待审核、审核不通过、已重传作废、因申请终止失效、已发布、已替代、已作废。
25. 已发布报告不允许反审核，只能通过重传或作废处理问题。
26. 每次审核动作必须形成审核记录，并在状态变化时形成报告状态变化记录。
27. 普通报告查询只能提供当前有效的已发布报告。
28. 普通报告查询页面只展示当前有效报告，并支持在线查看和下载 PDF。
29. 报告审核入口用于处理发布审核。
30. 报告版本追溯入口可按权限查看全部历史版本、替代关系、作废记录和审核记录。
31. 报告上传成功后，上传方应能获得报告版本号、当前报告状态和是否已自动发布。
32. 本章节不要求提供上传方系统侧后续查询审核结果能力，也不要求审核通过或不通过后通知上传方系统。
33. 报告上传可包含危急值信息，危急值发布/推送跟随报告审核开关。

### 1.9 报告版本管理

#### 1.9.1 功能定位

报告版本管理用于对同一样本条码下的报告上传、审核、发布、重传、替代和作废过程进行轻量追溯。

报告版本管理不作为复杂独立管理模块，不提供人工编辑报告版本、人工调整版本状态、删除历史版本或恢复历史版本的能力。普通业务用户通过报告查询查看当前有效报告；有权限人员可通过报告详情、版本追溯入口或业务运维明细查看历史版本链。

#### 1.9.2 报告对象与版本关系

1. 同一申请、同一样本条码下只维护一个报告业务对象。
2. 首次报告上传成功后，生成该报告业务对象的第一个报告版本。
3. 同一样本条码再次上传报告时，必须作为该报告业务对象的重传版本处理。
4. 平台不根据报告名称、报告类型、项目范围或 PDF 内容自动拆分多个报告对象。
5. 报告名称或报告类型仅作为展示字段，不作为版本链判断依据。
6. 分批出结果、补充结果、修正报告内容，均通过报告重传生成新版本。
7. 项目多或一页显示不完，不作为拆分多个报告对象的理由。

#### 1.9.3 当前有效报告

1. 任一时间同一样本条码最多只有一份当前有效已发布报告。
2. 普通报告查询只能提供当前有效已发布报告。
3. 报告首次发布后，该版本成为当前有效报告。
4. 已发布报告重传后，新版本发布前，原已发布版本仍为当前有效报告。
5. 新版本发布后，新版本成为当前有效报告，原已发布版本进入已替代。
6. 如果新版本审核不通过，原当前有效报告继续有效。
7. 当前有效报告作废后，该样本条码暂无当前有效报告。
8. 当前有效报告作废后，已替代历史版本不自动恢复为当前有效报告。
9. 申请终止导致当前有效报告作废或失效后，该样本条码暂无当前有效报告。
10. 如需重新对外提供报告，上传方必须重传生成新版本；新版本发布后才重新成为当前有效报告。

#### 1.9.4 版本状态与状态流转

报告版本状态包括：待审核、审核不通过、已重传作废、因申请终止失效、已发布、已替代、已作废。

1. 待审核：审核开关启用时，报告上传或重传成功后的状态。
2. 审核不通过：发布审核未通过，不可发布、查询、下载或推送。
3. 已重传作废：待审核版本被新重传版本替代，不再允许审核。
4. 因申请终止失效：未发布报告版本因申请终止退出待处理范围，不再允许审核、发布、查询、下载或推送。
5. 已发布：当前可对发起机构查询、下载、推送的有效报告。
6. 已替代：原已发布版本被新发布版本替代。
7. 已作废：当前有效已发布报告被作废后进入该状态，不再作为当前有效报告。

#### 1.9.5 报告作废规则

1. 报告作废统一承担报告失效类场景，不再区分常规失效和紧急下线。
2. 作废只允许作用于当前有效的已发布报告。
3. 作废立即生效，不受报告审核开关控制。
4. 作废后普通查询不再提供该报告。
5. 作废后不自动回退历史版本。
6. 作废后不可恢复，不提供重新启用能力。
7. 作废必须填写原因。
8. 作废原因建议分类包括：报告错误、重复报告、业务取消、申请终止、其他。
9. 作废必须记录作废时间、作废人或调用系统、作废原因和关联报告版本。
10. 上传方可以作废自己上传的当前有效报告。
11. 平台授权人员可在必要时作废当前有效报告。
12. 发起机构不能直接作废报告，但发起机构触发申请终止时，可由申请终止规则联动当前有效报告作废或失效。
13. 作废不删除历史版本。
14. 作废不影响样本检测完成状态。
15. 作废后如需重新提供报告，只能通过重传生成新版本。

#### 1.9.6 版本追溯入口

1. 报告版本追溯只面向有权限人员开放。
2. 版本追溯应展示同一样本条码下的全部报告版本。
3. 版本追溯应展示版本号、版本状态、上传方、上传时间、发布审核记录、重传关系、替代关系、作废记录、因申请终止失效记录和当前有效标识。
4. 普通报告查询页面不展示无效历史版本。
5. 普通业务用户不直接面对全部报告版本，避免误用历史报告或无效报告。
6. 如后续需要对外开放历史版本追溯能力，应独立于普通报告查询，并进行权限控制。

#### 1.9.7 推送边界

1. 本章节只定义报告版本状态和当前有效报告规则。
2. 报告推送、危急值推送和医院侧处理回执，在报告和危急值推送管理章节定义业务边界。
3. 推送的系统实现和技术处理不在本章节定义。

#### 1.9.8 验收标准

1. 同一申请、同一样本条码下只存在一个报告业务对象。
2. 首次上传生成第一个报告版本，再次上传按重传生成新版本。
3. 任一时间同一样本条码最多只有一份当前有效已发布报告。
4. 新版本发布前，原已发布版本继续作为当前有效报告。
5. 新版本发布后，原已发布版本进入已替代。
6. 因申请终止失效的未发布报告版本不允许审核、发布、查询、下载或推送。
7. 当前有效报告作废后，该样本条码暂无当前有效报告。
8. 申请终止导致当前有效报告作废或失效后，该样本条码暂无当前有效报告。
9. 作废后不自动回退历史版本。
10. 作废后不可恢复，只能通过重传生成新版本重新对外提供报告。
11. 报告状态范围为待审核、审核不通过、已重传作废、因申请终止失效、已发布、已替代、已作废。
12. 有权限人员可以查看版本链、替代关系、作废记录、因申请终止失效记录和审核记录。

### 1.10 危急值记录与处理留痕

#### 1.10.1 功能定位

危急值记录与处理留痕用于记录报告上传方随报告提交的危急值信息，并支持平台内部对危急值进行轻量闭环处理。

平台不自动判断危急值，不根据结构化结果、参考范围或 PDF 内容生成危急值，也不提供页面人工新建危急值入口。危急值是否存在、具体项目、结果值、危急说明和危急等级等信息，由报告上传方随报告提供。

本功能只定义平台内部危急值记录和处理留痕；医院侧处理回执、危急值推送给发起机构等内容，在报告和危急值推送管理章节定义。

#### 1.10.2 危急值来源与报告版本关系

1. 危急值仅随报告上传进入平台。
2. 平台不支持报告上传后单独补录危急值。
3. 平台不提供页面人工新建危急值能力。
4. 每条危急值必须关联申请、样本条码、报告版本、上传方和接收方。
5. 危急值作为报告版本内容的一部分记录。
6. 报告版本未发布前，关联危急值不对外发布或推送。
7. 报告版本发布后，关联危急值才进入当前有效危急值范围。
8. 报告版本被新版本替代后，旧版本关联危急值不再作为当前有效危急值。
9. 报告版本被作废后，关联危急值不再作为当前有效危急值。
10. 申请终止导致报告作废或失效后，关联危急值不再作为当前有效危急值。
11. 平台不把危急值脱离报告版本单独变成有效对象。

#### 1.10.3 当前有效危急值规则

1. 当前有效危急值只来自当前有效报告版本。
2. 新报告版本发布后，只以新版本携带的危急值作为当前有效危急值。
3. 如果新版本未携带危急值，则平台认为当前有效报告版本下没有危急值。
4. 平台不自动继承旧版本危急值。
5. 平台不要求上传方额外声明是否继承或取消旧版本危急值。
6. 历史危急值仍可在报告版本追溯、危急值详情或业务运维明细中查看。
7. 历史危急值不作为当前待处理危急值。
8. 危急值不提供单独作废动作。
9. 危急值有效性跟随报告版本，报告被替代或作废后，关联危急值自动不再当前有效。
10. 申请终止不删除历史危急值；申请终止导致报告作废或失效后，关联危急值退出当前有效范围。

#### 1.10.4 危急值字段类别

PRD 层面要求危急值记录覆盖以下信息类别；具体接口字段由接口设计文档另行定义。

1. 申请信息。
2. 样本条码。
3. 报告版本。
4. 患者摘要。
5. 项目名称或项目编码。
6. 结果值。
7. 单位。
8. 参考范围或危急阈值。
9. 危急类型或危急说明。
10. 危急等级。
11. 上传方。
12. 上传时间。
13. 平台内部处理状态。
14. 处理记录摘要。

平台不维护危急值判断规则，不根据结果值自动判断是否危急，不维护危急值阈值体系。

#### 1.10.5 平台内部处理状态

1. 危急值平台内部处理状态只包括待处理、已处理。
2. 危急值记录生成后，平台内部处理状态默认为待处理。
3. 具备权限的用户完成平台内部处理后，状态变为已处理。
4. 不设置处理中、已查看、已通知、已关闭等状态。
5. 查看、确认、电话通知、补充说明等过程信息通过处理记录体现，不进入主状态。
6. 是否已通知医院、推送是否成功、医院是否已处理，不写入平台内部处理状态。
7. 危急值已处理后，不允许重新打开为待处理。
8. 后续如有补充情况，只允许追加处理记录。

#### 1.10.6 平台内部处理规则

1. 危急值从待处理变为已处理时，必须选择处理结果。
2. 处理结果来源于字典系统。
3. 本平台不在本章节定义处理结果枚举。
4. 本平台不提供危急值处理结果字典维护能力。
5. 字典系统的配置、权限、维护流程不在本 PRD 章节讨论。
6. 平台记录当次选择的处理结果编码和处理结果名称。
7. 处理说明或备注可选填写。
8. 未选择处理结果时，不允许完成处理。
9. 处理记录应包含处理人、处理时间、处理结果和处理说明。
10. 推送成功不自动置为已处理。
11. 医院侧处理回执不自动置为平台内部已处理。
12. 平台内部处理完成不代表医院侧已处理。

#### 1.10.7 处理权限边界

1. 危急值平台内部处理仅允许具备对应权限的用户操作。
2. 具备危急值处理权限的用户，才可以将危急值从待处理置为已处理。
3. 具备危急值处理权限的用户，才可以追加危急值处理记录。
4. 用户是否拥有该权限，由统一权限系统判断。
5. 本 PRD 不定义权限分配规则、角色体系、按钮权限和组织范围。
6. 无权限用户是否可查看、不可见或只读，由权限系统和页面权限配置决定。

#### 1.10.8 处理记录留痕

1. 每条危急值独立处理。
2. 同一报告版本包含多条危急值时，每条危急值分别维护处理状态和处理记录。
3. 危急值处理记录一旦生成，不允许修改。
4. 危急值处理记录不允许删除。
5. 如果原处理记录有错误、遗漏或后续补充情况，只能追加新的处理记录说明。
6. 追加记录需要记录处理人、处理时间、处理结果和处理说明。
7. 原始处理记录必须完整保留，用于业务追溯。
8. 平台内部处理记录和医院侧处理回执需要分开记录。
9. 平台内部处理记录不等同于医院侧已处理。
10. 医院侧处理回执不自动替代平台内部处理记录。

#### 1.10.9 列表与查询范围

1. 普通危急值处理列表默认只展示当前有效报告版本关联的危急值。
2. 已替代、已作废、因申请终止失效、审核不通过、待审核报告版本下的危急值，不进入普通处理列表。
3. 历史危急值可在报告版本追溯、危急值详情或业务运维明细中查看。
4. 历史危急值不作为当前待处理危急值提示。
5. 当前版本不建设独立待办中心。
6. 当前版本不生成独立待办事项。
7. 当前版本不提供首页危急值待办入口、全局角标、消息提醒或升级提醒。
8. 危急值处理页面提供待处理筛选。
9. 危急值处理页面可展示待处理数量。
10. 待处理数量按当前有效报告版本下、平台内部处理状态为待处理的危急值计算。
11. 用户需要具备危急值查看或处理权限，才可查看危急值列表和待处理数量。
12. 危急值处理完成后，该条记录不再出现在待处理筛选结果中。

#### 1.10.10 当前版本不支持范围

1. 不支持平台自动判断危急值。
2. 不支持页面人工新建危急值。
3. 不支持报告上传后单独补录危急值。
4. 不支持危急值单独作废或恢复。
5. 不支持危急值处理记录修改或删除。
6. 不支持危急值处理附件。
7. 不支持危急值批量处理。
8. 不支持危急值处理二次确认强制规则。
9. 不单独提供危急值处理记录导出。
10. 不设置危急值超时提醒、超时统计和升级提醒。
11. 不建设独立危急值待办中心。

#### 1.10.11 验收标准

1. 报告上传时可随报告版本提交危急值信息。
2. 平台不支持脱离报告版本单独创建当前有效危急值。
3. 危急值必须绑定申请、样本条码和报告版本。
4. 当前有效危急值只来自当前有效报告版本。
5. 新版本报告未携带危急值时，旧版本危急值不再作为当前有效危急值。
6. 报告作废、被替代或因申请终止失效后，关联危急值不再进入当前处理列表。
7. 危急值处理状态只包括待处理和已处理。
8. 危急值完成处理时必须选择来自字典系统的处理结果。
9. 每条危急值独立处理，不支持批量处理。
10. 危急值处理记录不可修改、不可删除，只允许追加。
11. 危急值处理列表支持查看当前有效报告版本下的待处理危急值和待处理数量。
12. 当前版本不建设独立待办中心、超时提醒、升级提醒和处理附件能力。

### 1.11 报告和危急值推送管理

#### 1.11.1 功能定位

报告和危急值推送管理用于定义报告发布后、危急值产生后，平台向申请来源机构或发起机构进行业务通知的边界，以及医院侧危急值处理回执的业务含义。

本 PRD 只定义推送业务目标、推送对象、推送时机、推送内容类别、业务可见推送结果和医院侧危急值处理回执；不定义推送系统实现。

推送系统如何实现、失败后如何处理、与机构系统如何对接等内容，后续由推送系统设计或接口设计确认。

#### 1.11.2 推送业务目标

1. 报告发布后，发起机构应能及时获取报告。
2. 报告重传并发布新版本后，发起机构应能获取最新报告。
3. 当前有效报告版本包含危急值时，发起机构应能收到危急值通知。
4. 医院侧如已处理危急值，平台应能记录医院侧处理回执。
5. 平台内部危急值处理闭环与医院侧处理回执分开，不互相替代。

#### 1.11.3 推送类型与对象

1. 报告推送和危急值推送共用业务上的推送能力，但需要区分推送类型。
2. 推送类型包括报告推送和危急值推送。
3. 报告推送不替代危急值推送。
4. 危急值推送不替代报告推送。
5. 推送对象按申请来源机构或发起机构确定。
6. 平台根据申请归属关系确定应通知的机构。
7. 具体机构对接方式由接口配置或推送系统设计确定。

#### 1.11.4 报告推送业务规则

1. 报告发布后，应触发报告推送。
2. 报告未发布前，不触发报告推送。
3. 待审核、审核不通过、已作废的报告版本不触发当前报告推送。
4. 报告推送内容以当前发布的报告版本为准。
5. 报告重传并发布新版本后，新版本报告推送即视为报告更新通知。
6. 平台不额外生成独立的报告更新通知类型。
7. 旧报告版本被新版本替代后，当前版本不单独推送旧版本失效通知。
8. 报告作废后，当前版本不自动向医院或发起机构推送报告作废通知。
9. 医院侧如果主动查询报告状态，应能看到报告已作废。
10. 申请终止后，不再触发新的报告推送。
11. 当前版本不自动向医院或发起机构推送申请终止通知。

#### 1.11.5 危急值推送业务规则

1. 报告发布后，平台判断当前发布报告版本是否包含危急值。
2. 如果当前报告版本包含危急值，应触发危急值推送。
3. 危急值未随报告上传的，不单独生成危急值推送。
4. 报告未发布前，不触发危急值推送。
5. 待审核、审核不通过、已作废、已替代的报告版本，不触发当前危急值推送。
6. 危急值推送内容来自当前发布报告版本内的危急值记录。
7. 同一报告版本包含多条危急值时，按每条危急值分别表达危急值推送结果。
8. 某条危急值推送失败，不影响其他危急值的业务推送结果。
9. 某条危急值收到医院侧处理回执，不代表同报告内其他危急值已回执。
10. 报告作废后，关联危急值随报告版本失效。
11. 申请终止导致报告作废或失效后，关联危急值随报告版本失效。
12. 申请终止后，不再触发新的危急值推送。
13. 当前版本不自动向医院或发起机构推送危急值失效通知。

#### 1.11.6 推送内容类别

报告推送内容应让发起机构能够获取当前发布的报告内容，至少包含以下类别：

1. 报告基础信息。
2. 报告文件或报告访问地址。
3. 报告版本信息。

危急值推送内容应让发起机构能够识别并处理具体危急值，至少包含以下类别：

1. 危急值核心信息。
2. 关联报告版本信息。
3. 申请信息。
4. 样本条码。
5. 患者摘要。

报告文件获取方式、字段细节和安全要求，由接口设计或安全规范定义。

#### 1.11.7 业务可见推送结果

1. 报告推送和危急值推送都需要在业务层展示轻量推送结果。
2. 业务可见推送结果用于表达是否已尝试或完成向发起机构通知。
3. 业务可见推送结果包括未推送、推送成功、推送失败。
4. 推送成功只表示平台侧已完成对外推送，不代表医院已查看报告，也不代表医院已处理危急值。
5. 推送失败只表示平台侧对外推送未成功，不定义具体失败原因和技术细节。
6. 系统内部处理状态由推送系统设计决定。
7. 业务可见推送结果是否支持人工修正，由推送系统设计或运维流程决定，本 PRD 不定义。

#### 1.11.8 医院侧危急值处理回执

1. 当前版本只对危急值支持医院侧处理回执。
2. 报告推送不要求医院侧业务回执。
3. 当前版本不单独定义医院侧接收回执。
4. 医院侧处理回执表示医院侧已经对危急值完成确认或处理。
5. 医院侧处理回执来源可包括医院系统回传和平台人工登记。
6. 医院侧处理回执不自动完成平台内部危急值处理。
7. 平台内部危急值处理完成后，不自动生成医院侧处理回执。
8. 没有医院侧处理回执，不影响平台内部危急值处理闭环。
9. 医院侧处理回执需要在业务层展示。
10. 危急值相关页面可展示是否已有医院侧处理回执，以及最新回执摘要。
11. 最新回执摘要可包括回执状态、回执时间、处理说明和回执来源等业务信息。
12. 如存在多次医院侧处理回执，可在详情中查看回执历史。
13. 医院侧处理回执展示不等同于平台内部危急值处理状态。
14. 本 PRD 不定义医院侧处理回执的接口实现规则。

#### 1.11.9 当前版本不支持范围

1. 不定义推送系统实现。
2. 不定义推送失败后的技术处理规则。
3. 不定义机构系统对接的技术细节。
4. 不建设独立推送运维中心。
5. 不定义推送记录的技术管理规则。
6. 不做报告作废通知。
7. 不做旧报告版本失效通知。
8. 不做危急值失效通知。
9. 不做申请终止通知。
10. 不要求报告推送医院侧业务回执。
11. 不定义医院侧接收回执。

#### 1.11.10 验收标准

1. 报告发布后，业务上应触发报告推送。
2. 报告新版本发布后，业务上应触发新版本报告推送。
3. 当前有效报告版本包含危急值时，业务上应按单条危急值触发危急值推送。
4. 报告推送和危急值推送需要区分推送类型。
5. 报告推送和危急值推送都展示未推送、推送成功、推送失败三类业务可见结果。
6. 报告推送内容类别包含报告基础信息、报告文件或访问地址、报告版本信息。
7. 危急值推送内容类别包含危急值核心信息、关联报告版本信息、申请、样本条码和患者摘要。
8. 当前版本不做报告作废通知、旧版本失效通知和危急值失效通知。
9. 当前版本不做申请终止通知。
10. 申请终止后不再触发新的报告推送和危急值推送。
11. 当前版本只对危急值支持医院侧处理回执。
12. 医院侧处理回执不自动完成平台内部危急值处理。
13. 平台内部危急值处理不自动生成医院侧处理回执。
14. 医院侧处理回执可在业务层查看，历史可追溯。

### 1.12 业务运维与追溯查询

#### 1.12.1 功能定位

业务运维与追溯查询是平台侧业务排查和追溯工具，用于帮助平台运营、客服、平台管理人员快速定位单个申请或样本的全链路状态，并向机构解释当前业务状态和历史处理过程。

本功能不定位为运营统计报表，不定位为系统对接排障平台，不替代申请、样本、报告、危急值等业务模块的正常操作页面。

#### 1.12.2 目标用户

1. 平台运营人员。
2. 平台客服人员。
3. 具备相应权限的平台管理人员。
4. 发起机构用户不作为业务运维明细的主要使用对象。
5. 检测机构用户不作为业务运维明细的主要使用对象。
6. 机构侧用户如需查看业务进度，应通过各自业务页面或接口查询。
7. 业务运维明细是否开放给其他角色，由权限系统和运营管理策略决定。

#### 1.12.3 典型场景与痛点

本功能优先覆盖客服高频问题场景：

1. 状态查询：平台人员需要回答申请或样本当前处于哪个环节。
2. 报告未收到：机构反馈报告没有收到，需要查看报告是否发布、是否推送、当前推送结果。
3. 样本未接收：机构或检测方反馈样本未到，需要查看样本是否送出、是否接收、是否退回。
4. 报告版本争议：机构看到的报告和平台记录不一致，需要查看报告版本、重传、替代、作废情况。
5. 危急值通知追溯：需要查看危急值是否存在、是否平台内部处理、是否推送、是否有医院侧处理回执。
6. 异常退回查询：需要查看样本异常、退回原因、处理结果、是否重新送出或终止。
7. 申请终止追溯：需要查看申请为何终止、终止发生在哪个阶段、终止后阻断或失效了哪些业务对象。

本功能应解决信息分散、链路难追、问题定位慢、无法快速解释业务状态等问题。

#### 1.12.4 查询视角与入口

1. 业务运维明细支持申请视角。
2. 业务运维明细支持样本条码视角。
3. 申请视角用于查看同一申请下的样本、报告、危急值、异常、推送等整体情况。
4. 样本条码视角用于精确追踪单个样本的流转、检测、报告和异常情况。
5. 如果一个申请下有多个样本，申请详情中应能展开查看各样本明细。
6. 如果通过样本条码进入，应能反查所属申请。
7. 两种视角可共用同一套详情数据，只是入口和默认聚焦对象不同。
8. 业务运维明细提供独立菜单入口，作为平台侧运维和客服查询工具。
9. 入口权限、菜单权限和数据范围由权限系统统一控制。

#### 1.12.5 查询能力

1. 业务运维明细首页提供统一搜索框。
2. 统一搜索框用于根据单一业务线索快速定位申请或样本。
3. 业务运维明细首页提供结构化筛选表单。
4. 结构化筛选表单用于批量排查、按条件检索和运营问题定位。
5. 查询能力至少围绕申请号、样本条码、机构、时间、状态等业务线索设计。
6. 是否允许按患者姓名、手机号、证件号等敏感信息搜索，不在本章节单独定义。
7. 患者敏感信息搜索涉及隐私保护、脱敏展示、访问权限、操作审计和合规要求，应由平台统一隐私规则、权限系统和审计规则决定。

#### 1.12.6 详情页结构

业务运维详情页采用当前概览、模块分组和全链路时间线结合的组织方式。

当前概览用于快速判断当前业务状态，可包含：

1. 当前申请状态。
2. 当前样本状态。
3. 当前报告状态。
4. 是否存在异常或退回。
5. 是否存在当前有效危急值。
6. 报告或危急值业务推送结果摘要。
7. 申请终止类型、终止原因和终止影响摘要。

模块分组用于查看业务细节，可包含：

1. 申请信息。
2. 样本信息。
3. 包与送出信息。
4. 接收与异常信息。
5. 检测与报告信息。
6. 危急值信息。
7. 推送与医院侧回执信息。

全链路时间线用于还原历史过程，可包含：

1. 申请创建。
2. 样本送出。
3. 送出补送。
4. 送出撤回。
5. 样本接收。
6. 接收异常。
7. 退回。
8. 检测状态回传。
9. 报告上传、审核、发布、重传、作废。
10. 危急值生成、平台处理、医院侧回执。
11. 报告或危急值推送业务结果。
12. 申请终止、因申请终止不可接收、因申请终止失效的报告版本、申请终止联动的报告作废或失效。

当前版本不根据状态自动生成问题定位提示，不提供疑似卡点、疑似推送失败、疑似未接收等自动诊断文案。

#### 1.12.7 查询与操作边界

1. 业务运维明细当前版本定位为只读查询、排查和追溯工具。
2. 当前版本不在业务运维明细内直接处理业务。
3. 当前版本不在业务运维明细内提供重新触发推送、处理危急值、登记医院回执、关闭异常、撤回送出、终止申请等操作。
4. 如用户具备权限，可从详情跳转到对应业务页面进行处理。
5. 跳转后的操作权限、按钮权限和数据范围，由对应业务模块和权限系统控制。
6. 业务运维明细本身以只读展示为主，避免成为跨模块操作台。

#### 1.12.8 当前信息与历史信息

1. 业务运维明细默认优先展示当前有效信息。
2. 历史信息不默认全部铺开，避免页面过载。
3. 业务运维明细支持展开查看历史记录。
4. 历史范围包括旧报告版本、作废报告、因申请终止失效的报告版本、报告重传和替代关系、历史危急值、危急值处理记录、医院侧回执历史、申请终止记录、终止影响对象、送出补送、送出撤回、样本退回、接收异常、因申请终止不可接收记录、历史推送业务结果、包关系和送出快照。
5. 包和送出快照默认不展示，仅在展开历史链路时展示。
6. 展开历史链路时，应能查看样本曾属于哪个包、包内当时包含哪些样本、哪次送出使用了该包、送出时的样本快照、送出记录状态、业务标签、样本级处理结果、是否发生补送、是否发生送出撤回、是否发生样本退回或异常。
7. 历史记录用于追溯和解释问题，不改变当前状态展示。

#### 1.12.9 当前版本不支持范围

1. 不作为运营统计报表。
2. 不作为系统对接排障平台。
3. 不展示系统接口排障信息。
4. 不支持导出查询结果。
5. 不支持导出申请、样本、报告、危急值、推送、异常等详情。
6. 不提供文件导出能力。
7. 查看日志由平台统一审计日志规范决定，本章节不单独定义。

#### 1.12.10 验收标准

1. 业务运维明细提供独立入口。
2. 业务运维明细主要面向平台运营、客服和具备权限的平台管理人员。
3. 支持按申请视角和样本条码视角追溯业务链路。
4. 首页支持统一搜索框和结构化筛选表单。
5. 查询能力围绕申请号、样本条码、机构、时间、状态等业务线索设计。
6. 详情页包含当前概览、模块分组和全链路时间线。
7. 当前版本不做自动问题定位提示。
8. 当前版本只读，不直接处理业务。
9. 默认展示当前有效信息，支持展开查看历史。
10. 包和送出快照仅在展开历史链路时展示。
11. 能查看申请终止记录、终止类型、终止原因、终止时阶段和终止影响对象。
12. 不展示系统接口排障信息。
13. 当前版本不支持导出。

### 1.13 权限、隐私与审计边界

#### 1.13.1 权限边界

1. 本 PRD 不定义权限系统设计。
2. 本 PRD 不定义角色体系。
3. 本 PRD 不定义具体权限模型。
4. 本 PRD 不定义授权流程。
5. 各业务页面、查询、处理、登记、查看、跳转等能力，应接入平台统一权限系统。
6. 用户是否可见、可查、可操作，由统一权限系统判断。
7. 本 PRD 只在具体业务规则中声明哪些能力需要权限控制。
8. 具体权限配置由权限系统设计确认。

#### 1.13.2 隐私与脱敏边界

1. 本 PRD 不定义具体患者脱敏规则。
2. 本 PRD 不定义敏感信息搜索规则。
3. 本 PRD 不定义敏感信息导出规则。
4. 涉及患者姓名、手机号、证件号、病历号、报告内容、危急值等敏感信息时，必须遵循平台统一隐私、脱敏和数据权限规范。
5. 患者敏感信息的展示、查询、搜索、导出、审计，由平台统一隐私规范、权限系统和审计规范确定。
6. 各业务模块不得单独定义一套与平台统一规范冲突的脱敏规则。

#### 1.13.3 审计边界

1. 本 PRD 不定义审计日志字段。
2. 本 PRD 不定义审计日志保留期限。
3. 本 PRD 不定义审计日志查询权限。
4. 本 PRD 不定义审计日志导出规则。
5. 关键业务操作应遵循平台统一审计规范。
6. 敏感数据访问应遵循平台统一审计规范。
7. 报告发布、报告作废、危急值处理、医院侧回执人工登记、异常退回、送出撤回、业务运维明细查看等，是否入审计日志由统一审计规范确定。
8. 申请终止、因申请终止导致的报告失效或作废、因申请终止不可接收等关键业务动作，是否入审计日志由统一审计规范确定。
9. 本 PRD 中的业务留痕记录不替代统一审计日志。

#### 1.13.4 验收标准

1. PRD 中涉及权限控制的业务能力，应说明接入统一权限系统。
2. PRD 不单独定义具体权限模型。
3. 涉及患者敏感信息时，应遵循平台统一隐私、脱敏和数据权限规范。
4. 关键业务操作和敏感数据访问是否进入审计日志，由平台统一审计规范决定。
5. 业务留痕记录不替代统一审计日志。
