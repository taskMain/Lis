# 第四版需求讨论内容

## 一、文档修正方向

第四版需求文档需要围绕以下结构重新整理：

1. 背景与目标：说明为什么建设检验中心协同平台。
2. 范围与边界：明确本系统做什么、不做什么，哪些能力归外部系统或其他平台。
3. 用户与场景：说明谁使用平台，以及至少两个实际业务场景。
4. 功能需求：区分平台自身功能和平台需要提供的接口能力。
5. 验收标准：只描述功能做到什么程度算完成，不写性能指标。

## 二、已确认结论

### 1. 项目标准化与机构项目对照边界

项目标准化与机构项目对照由独立项目标准化系统维护，本平台不提供项目对照维护功能。

机构提交检验申请时，应提交平台标准项目编码；平台仅校验编码是否可识别、是否可用，以及是否满足本次申请所需的基础业务约束。

第四版 PRD 中应删除平台维护标准项目、小项目、大项目组合关系、机构项目对照关系等功能描述，只保留边界说明和申请侧使用规则。

### 2. 验收标准口径

第四版 PRD 的验收标准只描述功能完成标准，例如功能是否可操作、数据是否可记录、接口是否可调用、流程是否可闭环、状态是否可查询。

验收标准中不写性能相关描述，例如并发量、响应时间、吞吐量、容量、稳定性等指标。

### 3. 样本流转从装箱调整为打包与配送单

第四版 PRD 中不再使用“装箱/箱子”作为核心业务概念，统一调整为“打包 + 配送单”。

包是平台中的虚拟业务单位，用来绑定多个样本条码，不要求线下一定存在实体箱。配送单表示一次送检或配送任务，可包含一个或多个包。

样本可以先打包再加入配送单，也可以在创建配送单时直接选择样本并自动形成默认包。平台流转主线从“按箱送出”调整为“按配送单送出”。

接收方支持按配送单、包或样本条码进行接收。后续主流程图、样本流转流程图、功能需求和验收标准均按“打包 + 配送单”模型重新描述。

### 4. 费用信息与绿色通道标识

平台不负责收费、退费、医保结算，也不替代机构 HIS 或收费系统完成费用闭环。

机构创建检验申请时，可以向平台传入费用状态和绿色通道相关信息。费用状态可用于表达已收费、未收费、无需收费或未知等情况；绿色通道信息可用于表达是否绿通及绿通原因。

平台只负责接收、记录、展示和查询这些信息，用于接收方判断优先级、业务核对或人工处理参考。

平台默认不因未付费状态阻断申请创建，是否允许未付费申请继续流转由机构本地系统或线下管理规则负责。

### 5. 平台申请与样本条码关系

第四版 PRD 中明确采用“同一个条码就是一个申请”的业务粒度。

一个平台申请只能对应一个样本条码，一个样本条码也只能对应一个平台申请。一个平台申请内可以包含多个检验项目，但这些项目作为同一申请的项目集合整体参与流转。

申请撤回、样本撤回、异常处理、配送流转、报告发布、报告更正等后续流程均以平台申请和样本条码为最小业务单元进行处理。

平台不支持一个申请内只撤回或取消其中某一个项目。如果机构需要取消部分项目，应由机构本地系统处理后，按新的条码和申请规则重新提交平台申请。

同一个条码下可以产生多个报告，用于支持多个项目分批出报告、补充报告或报告更正。平台需通过报告类型、项目范围、报告版本和最新有效标识进行区分。

### 6. 主要逆流程范围

第四版 PRD 需要定义主要业务逆流程，但不做申请内项目级撤回。

申请撤回：申请创建后、样本未送出前允许撤回。撤回后申请不可继续进入打包、配送、接收、检测和报告流程。

配送撤回：配送单未被接收前，允许撤回送出或取消配送单。撤回后样本回到可重新打包或重新生成配送单的状态。

接收退回：接收方发现样本问题时，可登记异常并执行退回。退回不删除申请和样本记录，需保留异常原因、处理意见、退回时间和操作记录。

报告撤回与更正：报告发布后不物理删除。需要撤回或更正时，平台标记旧版本状态，并生成新的报告版本或保留撤回说明。

危急值记录更正：已产生的危急值记录不删除，只能追加处理记录、更正说明或后续处置结果。

所有逆流程均必须保留原始业务记录和操作留痕，不允许通过物理删除方式处理。

### 7. 报告审核与发布控制

中心机构或接收方上传检验结果和报告后，报告先进入待审核状态。

平台支持中心人员或有权限人员在平台对报告进行审核。审核通过后，报告状态变为已发布，机构才可以查询、下载，平台才可以按配置推送给机构或厂商接口。

审核不通过时，报告退回上传方重新上传或更正，并记录不通过原因、审核人和审核时间。

平台审核是报告发布控制，不是医学自动审核规则引擎。平台不自动判断结果是否正确，不自动计算高低、异常或危急值。

报告更正、重传、撤回后，如产生新的报告版本，新版本也需要重新审核。审核通过的新版本成为最新有效版本，旧版本强制保留用于追溯。

### 8. 报告历史版本强制保留

所有报告版本必须强制保留，不允许物理删除。

每次报告上传、重传、更正、撤回后重新上传，均生成独立报告版本。平台需要记录版本号、版本状态、上传时间、上传方、审核状态、审核人、审核时间和更正或撤回原因。

平台默认查询返回审核通过后的最新有效版本。历史版本仅供有权限人员追溯查看。

如果报告被撤回且没有新的有效版本，平台可以显示当前无有效报告，但历史报告版本仍需保留，状态标记为已撤回。

报告推送只推送审核通过后的最新有效版本。历史版本不主动推送；发生报告更正时，平台可推送更正后的最新有效版本，并在推送内容中体现更正关系。

### 9. 患者信息与申请数据查看范围

普通机构用户只能查看本机构发起的申请，以及提交给本机构处理的申请相关信息。

接收机构或中心用户只能查看提交给自己的申请，以及相关样本流转、报告、异常和危急值信息。

同一患者在其他机构产生的申请和报告，不因患者身份相同而向普通机构用户开放查看。

平台管理端授权用户可以查看平台下所有机构的申请、样本流转、报告状态、异常和危急值记录，用于平台运维、问题排查、业务监管和管理统计。

报告 PDF 下载、患者敏感信息明细查看等高敏操作是否需要更高权限控制，需要结合框架权限设计细化。

### 10. 样本流转状态与报告推送状态边界

样本流转状态只表达申请和样本在业务流程中的位置，不承载报告推送接口的执行结果。

报告已推送不作为样本流转状态，也不作为报告业务生效状态。报告是否业务生效以报告已发布为准。

报告已推送属于报告推送记录中的接口状态，用于表达平台是否已经通过 HTTP 将报告推送给医院或厂商接口。

报告推送记录可包含待推送、推送成功、推送失败、重试中、已取消推送等状态。推送失败不影响平台内报告已发布状态，也不导致样本状态倒退。

### 11. 异常处理状态不进入样本主状态

异常处理中不作为样本主状态。样本主状态只表达申请和样本当前所处的业务流程位置。

异常可能发生在申请后、打包时、配送中、接收时、检测前、报告后等多个环节，因此异常处理应作为独立异常记录管理。

异常记录可包含异常已登记、待处理、处理中、已处理、已关闭等处理状态。

一个样本可以在保持当前主状态的同时存在异常记录。例如样本已接收后发现溶血，可登记异常；如果业务允许继续检测，样本主状态仍可继续推进。

第四版 PRD 中应删除异常处理中作为样本流转状态的描述，改为在样本异常登记与处理功能中描述异常记录状态。

### 12. 样本主状态重新设计

样本主状态采用精简主链，只表达样本当前所处的物理或业务流转阶段，不承载报告审核、报告发布、报告推送和异常处理状态。

样本主状态包括：

1. 申请已创建
2. 待配送
3. 已配送
4. 已接收
5. 检测中
6. 检测完成

检测中为可选回传状态。若接收方 LIS 或检验系统不回传检测中状态，样本可从已接收直接进入检测完成。

报告相关状态单独进入报告模块，例如待审核、审核不通过、已发布、已撤回、已更正等。

报告推送相关状态单独进入报告推送记录，例如待推送、推送成功、推送失败、重试中等。

异常处理相关状态单独进入异常记录，例如异常已登记、待处理、处理中、已处理、已关闭等。

样本退回、申请撤回等逆流程状态作为终止类或逆流程类状态处理，不混入正常主链。

### 13. 查询统计、业务配置和运维明细查询边界

查询统计功能不纳入本 PRD，由独立查询统计系统负责。检验中心协同平台只保留业务流程中必要的明细查询，不做统计分析、报表、排行、趋势等功能。

机构基础信息维护、机构启停用状态、机构接入标识、API 凭证、用户、角色、菜单、权限、数据范围、机构人员账号管理等归入框架、主数据或权限系统，本 PRD 不展开。

本 PRD 保留业务配置管理，范围包括：

1. 机构默认接收方配置
2. 机构可提交目标范围配置
3. 报告推送接收地址配置
4. 危急值推送接收地址配置

本 PRD 保留业务运维明细查询，范围包括：

1. 按申请单号、条码、配送单号查询业务明细
2. 查询样本当前状态和流转记录
3. 查询报告审核、发布和版本状态
4. 查询报告或危急值推送记录及失败原因
5. 查询异常处理记录和危急值处理记录

业务配置管理和业务运维明细查询作为两个独立功能描述，不合并为一个功能。

### 16. 实际业务场景

第四版 PRD 至少描述以下 5 个实际业务场景：

1. 基层机构送检到中心：机构开单、生成条码、提交申请、打包、生成配送单、中心接收、检测、上传报告、平台审核发布，并推送回机构。
2. 样本接收异常退回：中心接收时发现条码无法识别、样本破损、漏送等问题，登记异常并退回，机构查看异常后重新处理。
3. 报告更正与版本追溯：报告发布后发现需要更正，上传方撤回或更正报告，新版本重新审核发布，旧版本强制保留。
4. 申请撤回：申请创建后、样本未配送前，机构撤回申请，平台终止后续打包、配送、接收、检测和报告流程。
5. 危急值协同：上传结果时包含危急值，平台记录危急值信息，按配置推送，并形成处理留痕或接收医院侧处理结果回传。

配送单撤回不单独作为实际场景展开，放入配送单管理功能规则中描述。

### 17. 第四版主流程

第四版 PRD 主流程按以下顺序描述和绘制：

1. 机构在本地系统完成开单并生成样本条码。
2. 机构向平台创建申请。
3. 平台创建平台申请，进入待配送。
4. 机构对样本进行打包。
5. 机构创建配送单，并将一个或多个包加入配送单。
6. 机构确认配送单送出。
7. 接收方接收配送单、包或样本条码。
8. 接收方完成检测，样本进入检测完成。
9. 上传方上传检验结果、报告 PDF 和危急值信息。
10. 报告进入待审核。
11. 审核通过后报告发布。
12. 平台提供报告查询下载，并按配置推送报告。

主流程中需要体现以下分支：

1. 申请创建后、未配送前可撤回。
2. 配送单未被接收前可撤回或取消。
3. 接收异常时可登记异常并退回。
4. 报告审核不通过时退回上传方重新上传或更正。
5. 报告发布后可更正或撤回，但所有历史版本强制保留。

### 18. 功能验收标准写法

第四版 PRD 的验收标准按功能完成程度描述，不写性能指标。

每个功能的验收标准优先从以下三类描述：

1. 页面或接口操作可完成：说明用户或外部系统能否完成该功能的核心操作。
2. 数据记录完整：说明状态、时间、操作人或调用方、原因、版本、关联对象等关键数据是否被保存。
3. 后续流程可衔接：说明该功能完成后，是否能进入后续业务流程，或是否能被查询、审核、推送、追溯。

验收标准中不写响应时间、并发量、数据容量、可用性百分比、性能压测指标等内容。
