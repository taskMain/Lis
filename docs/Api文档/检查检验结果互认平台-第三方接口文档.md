## 3. 接口总目录

本文后续章节使用下表编号定位接口。接口 1 至 4 由医院侧采集服务接入，接口 5 至 10 由医院 HIS 接入；同一家医院可以同时承担两个角色。接口 5 至 8 的自动端点前缀规则为 `/Api/{接口简单名}/{动作名去掉 Async}`，具体路径以联调环境实际路由为准。

| 编号 | 接入级别 | 名称 | 方法 | 路径 | 调用方 | 简述 |
| ---- | -------- | ---- | ---- | ---- | ------ | ---- |
| 1 | 必接 | 提交完整检验报告 | POST | `/api/v1/report-pdf/laboratory-report` | 医院侧采集服务 | multipart 提交检验报告 JSON 文档与 PDF 文件 |
| 2 | 必接 | 提交完整检查报告 | POST | `/api/v1/report-pdf/examination-report` | 医院侧采集服务 | multipart 提交检查报告 JSON 文档与 PDF 文件 |
| 3 | 必接 | 作废检验报告 | POST | `/Api/MedicalRecognitionReport/VoidLaboratoryReport` | 医院侧采集服务 | 按报告单号作废检验报告 |
| 4 | 必接 | 作废检查报告 | POST | `/Api/MedicalRecognitionReport/VoidExaminationReport` | 医院侧采集服务 | 按报告单号作废检查报告 |
| 5 | 必接 | 请求互认匹配 | POST | `/Api/MedicalRecognitionReport/RequestRecognitionMatches` | 医院 HIS | 按患者证件与本次就诊查询可互认报告 |
| 6 | 必接 | 提交互认处理结果 | POST | `/Api/MedicalRecognitionReport/SubmitRecognitionProcessingResults` | 医院 HIS | 按匹配记录整组提交采纳或不采纳决定 |
| 7 | 必接 | 提交互认引用结果 | POST | `/Api/MedicalRecognitionReport/SubmitRecognitionReferences` | 医院 HIS | 提交已写入病历的引用事实 |
| 8 | 必接 | 获取互认引用详情 | POST | `/Api/MedicalRecognitionReportQuery/QueryRecognitionCitationDetail` | 医院 HIS | 按患者证件与本次就诊取回可写入病历的引用内容 |
| 9 | 必接 | 下载报告版本 PDF | GET | `/api/v1/report-pdf/{reportId}/versions/{reportVersionId}/pdf` | 医院 HIS | 下载匹配或引用详情中报告版本的 PDF 文件 |
| 10 | 按需接入 | 查询互认项目配置 | POST | 待实现 | 医院 HIS | 查询当前院区有效的互认项目、可互认天数与配置金额 |

本文不提供的接口：平台标准目录管理、互认配置管理、统计查询等页面功能接口；登录认证接口见配套登录文档。本文无平台向第三方的业务推送与回调。

## 4. 文档使用方式

登录认证、Token 刷新和登录服务接口以配套登录接口文档为准。本文从取得有效 Bearer Token 后的业务调用开始说明。

报告上报方（医院侧采集服务）的最小流程：

1. 调用接口 1 或接口 2 提交完整检验或检查报告（JSON 文档与 PDF 共同提交）。
2. 报告需要作废时，调用接口 3 或接口 4。

医院 HIS 的最小流程：

1. 医生开单时调用接口 5，按患者证件与本次就诊请求互认匹配，取得可互认的报告与项目。
2. 医生在 HIS 侧作出采纳或不采纳决定后，调用接口 6 按匹配记录整组提交处理结果。
3. 医生在病历中实际引用互认结果时，调用接口 8 获取可写入病历的引用详情与报告公共上下文。
4. 需要报告 PDF 时，用接口 8 或接口 5 返回的报告标识与报告版本标识调用接口 9 下载。
5. 引用实际写入病历后，调用接口 7 提交引用结果。

接口 10 用于接入前和运行期查询当前院区有效的互认项目、可互认时间天数与配置金额；建议首次接入时调用一次核对编码，避免使用已停用或超出互认范围的编码提交请求。

## 5. 认证与数据范围

第三方必须先按配套登录文档取得有效 Token，并在业务请求中携带 `Authorization: Bearer <access-token>`。

Token 用于确定当前调用方的组织、医院、院区、科室、用户和可访问的数据范围。本文所说的"组织、医院、院区路径"是这三个编码的组合；其中任一编码不同，都属于不同路径。

本文接口的组织、医院、院区全部由服务端可信上下文从 Token 解析确定，调用方一律不在请求中提交、伪造或覆盖这些字段。业务角色字段（如申请科室、申请医生、检验人、检查医生）由调用方按接口参数表成对提交业务标识与名称，平台按提交内容保存，不校验这些业务主体是否存在于权限系统。

请求与响应中的 `source` 前缀字段（如 `sourceHospitalCode`）表示报告来源机构，由平台在响应中回填；使用方路径（`receiver` 前缀字段）在匹配记录中由平台写入。二者都是业务参与方，不是当前登录人。

## 6. 通用约定

### 6.1 成功与失败

| 场景 | 当前口径 |
| ---- | -------- |
| 成功写入（接口 1、2、3、4、6、7） | 返回布尔真 `true` |
| 成功匹配查询（接口 5） | 返回匹配响应对象；无命中时返回 `hasMatches=false` 的成功结果 |
| 成功引用详情查询（接口 8） | 返回引用详情对象；无可返回项目时接口调用失败 |
| 成功 PDF 下载（接口 9） | 返回 `application/pdf` 文件流 |
| 未认证或 Token 无效 | 接口调用失败 |
| 请求格式错误、字段校验失败、业务规则失败 | 接口调用失败；调用方不得依赖固定错误 JSON 结构 |

失败响应由平台宿主框架统一处理，本文不保证固定的 `code/message` 错误 JSON 结构；调用方应根据接口调用是否成功判断处理结果，排查问题时向部署方提供请求追踪信息。

除非接口章节另有说明，统一按以下规则处理：

- Token 缺失、无效或过期，请求体无法绑定，字段类型错误，必填字段缺失、空白或格式非法时，接口调用失败。
- Token 缺少组织、医院或院区信息，或可信上下文不可解析时，接口调用失败。
- 业务时间（申请时间、报告时间、作废时间、互认时间、引用时间等）必须传真实发生时间，不得使用默认或占位时间；时间格式为 ISO 8601。
- JSON 字段名使用 camelCase；大小写不敏感读取，但公开约定为 camelCase。报告提交文档（接口 1、2 的 `reportJson`）拒绝未知字段，拼错字段名会导致整份文档被拒绝。
- 枚举按本文列出的整数值传输，传枚举名称或字符串形式的数值会解析失败。
- 只读查询（接口 8、9）可以安全重试；写接口的重试行为按第 6.3 节各接口声明执行。

### 6.2 必填、应填与成对字段

本文参数表使用以下必填口径：

- **必填**：缺失、空串、纯空白或零值时间即整次请求失败。
- **应填**：来源系统存在该信息时必须提供，来源确实不存在时允许为空。
- **条件应填**：仅在对应条件成立时必须提供（如住院时提供住院号、病区名称）。
- **成对**：标识与名称必须同时有值或同时为空，不得只提交其一。

其他规则：

- 参数表按 JSON 字段逐项列示，一个表格行只描述一个字段；数组子字段使用 `数组字段名[].子字段名` 形式逐项列示。
- 人员标识与名称按医院请求提供并保存，平台不补查权限系统。
- 请求 JSON 只能提交各接口参数表列出的字段；可信上下文已确定的调用方字段即使与响应字段同名，也不得放入请求体。
- 部分字符串字段在保存前去除首尾空白，证件号码统一大写保存；调用方应自行提交去除空白后的值。

### 6.3 幂等与重复调用规则

- **接口 1、2（提交完整报告）不按内容判重**：每次成功提交都追加一个完整版本并设为当前版本，重复提交会产生新版本。调用方应避免网络重试造成重复版本；平台不依据源端报告修改时间判断顺序。
- **接口 3、4（作废报告）**：已作废且作废时间、作废原因与本次完全一致时幂等成功，不重复登记作废事件；任一事实不同返回作废信息冲突，不覆盖既有事实。
- **接口 5（请求互认匹配）**：每次调用按平台收到时间重新判定，重复调用可能形成新的匹配记录，不属于幂等重试。
- **接口 6（提交处理结果）**：相同业务键下互认时间、科室标识、医生标识、项目决定、不采纳原因及补充说明完全一致时幂等成功，不重复保存、不重复统计；参与比较的事实不一致时返回冲突，不覆盖既有决定。
- **接口 7（提交引用结果）**：相同匹配项、实际引用时间、引用科室标识、引用医生标识完全一致时幂等成功；事实不一致返回冲突。
- **接口 8、9（只读查询）**：可安全重试，结果反映调用时的当前状态。

### 6.4 常用枚举

| 枚举 | 值 |
| ---- | -- |
| 报告类型 `reportType` | `1` 检验报告；`2` 检查报告 |
| 就诊类型 `visitType` | `1` 门诊；`2` 急诊；`3` 住院；`4` 体检；`5` 其他（仅用于无法归入前四类的特殊就诊，不接受未知取值，不得作缺省值） |
| 项目类型 `itemType` | `0` 检验；`1` 检查 |
| 报告生命周期状态 | `1` 有效；`2` 已作废（不可逆） |
| 检验结果类型 `resultType` | `1` 数值型；`2` 定性型；`3` 文本型 |
| 检验异常标志 `abnormalFlag` | `1` 正常；`2` 偏高；`3` 偏低；`4` 其他异常 |
| 来源影像状态 `sourceImageStatus` | `1` 有影像；`2` 无影像；`3` 未知 |
| 互认结果 `result` | `1` 采纳；`2` 不采纳 |
| 不采纳原因 `nonAdoptionReason` | `1` 病情变化致结果难以满足诊疗需求；`2` 结果在疾病发展演变中变化较快；`3` 手术、输血等重大医疗措施前；`4` 患者处于急诊、急救等紧急状态；`5` 涉及司法、伤残及病退等鉴定；`6` 其他情形确需复查（补充说明必填） |

接口字段中的枚举均直接提交本节给出的整数值；未列出的整数值均无效。取值为"其他"时，按对应接口要求提交说明字段。

## 7. 业务接口

### 接口 1 提交完整检验报告

**调用方/方法/路径：** 医院侧采集服务，POST `/api/v1/report-pdf/laboratory-report`。

**Content-Type：** 请求 `multipart/form-data`；成功响应 `application/json; charset=utf-8`。

**业务说明与数据范围：** 提交一份完整检验报告，结构化内容与 PDF 必须共同成功或共同失败；任一步骤失败时整次提交不保存任何报告内容。组织、医院、院区由 Token 确定；操作人与操作时间由服务端写入，调用方不提交。平台按报告业务标识（组织、医院、院区、报告类型、报告单号）定位报告：不存在时创建生命周期状态为当前有效的报告，存在时追加版本并设为当前版本；已作废报告不得追加版本。

## 9. 数据安全与使用要求

1. 生产环境使用部署方提供的 HTTPS 地址；Token、患者证件号码、联系电话、诊断和报告 PDF 不得写入普通日志、截图或异常追踪文本。
2. 仅提交各接口参数表列出的字段，不提交平台内部主键、存储路径、下载 URL 或未约定的扩展字段；报告提交文档含未知字段会被整体拒绝。
3. 患者和临床敏感字段按最小必要原则传输和保存；报告 PDF 使用私有存储，不写入公共缓存。
4. 第三方应保护访问 Token 和刷新令牌，不在前端公开环境、共享日志或工单中传播。
5. 人员业务标识与姓名按接口要求成对提交；不得用 Token 当前调用人替代申请、检验、检查、审核、互认或引用等业务角色。

## 10. PDF 上传与下载约定

1. 上传端点仅接受 PDF。平台同时检查 `Content-Type=application/pdf`、`.pdf` 扩展名和 `%PDF-` 文件签名，文件不能为空。
2. 单文件默认上限为 83 886 080 字节（80 MB），取自服务端配置节 `ReportPdfFiles:MaxFileBytes`，实际部署可能调整，集成前应向部署方确认。
3. multipart 仅使用 `reportJson` 与 `pdfFile` 两个顶层部件。`reportJson` 承载完整报告 JSON 文档，拒绝未知字段；元数据不得提交任何文件内部标识、路径或 URL。
4. 上传文件名不安全（含路径分隔符、控制字符或百分号编码字符）时，下载名回退为「报告单号 + .pdf」；报告单号不可用字符全部过滤时回退为 `report.pdf`。
5. 下载成功返回 `application/pdf`，使用上传时保存的下载名，响应包含 `Cache-Control: no-store, no-cache, must-revalidate`。第三方系统不得将报告写入公共缓存或日志。
6. 上传失败时不会保存部分报告数据；写库失败时平台删除本次新落盘的文件，调用方仍应通过报告查询确认最终状态。
