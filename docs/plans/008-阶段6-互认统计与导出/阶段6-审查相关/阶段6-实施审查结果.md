### F-04 本批全部改动与新增文件为 LF 行尾，与仓库现行 CRLF 工作区约定不一致

- 类型：建议；严重度：低
- 位置：本批 23 个修改文件与 4 个新增代码文件（抽查 `docs/uml/5-RecognitionStatisticsUiQuery.wsd`、`server/Dy.MedicalRecognition.Application.Contracts/Queries/RecognitionStatistics/` 全部 11 个请求文件、`Stage6StatisticsContractTests.cs` 均为 LF）
- 证据：仓库 `core.autocrlf=true`；对这批文件执行构建、测试与 git 操作时反复输出「LF will be replaced by CRLF the next time Git touches it」告警（构建输出 5 条、测试输出 5 条、`git diff --check` 输出 6 条）。
- 影响：`git diff --check` 通过（退出码 0），git 因 autocrlf 在暂存时统一换行，内容差异与提交结果不受影响；残余影响是工作区文件下次被 git 触碰时行尾会被改写，以及每次操作输出告警噪音。
- 建议方向：后续批次按仓库现行约定保存文件行尾，消除告警。

## 一、发现清单

### F-01 互认科室展示名称子查询只按科室 ID 等值定位，跨分组同名科室 ID 的名称可能进入取值集合

- 类型：缺陷；严重度：中
- 位置：`server/Dy.MedicalRecognition.Repository/Queries/MedicalRecognitionReportQuery.xml:997-999`（`QueryRecognitionUsageSummaryPage` 内展示名称标量子查询）；守卫锚点 `server/Dy.MedicalRecognition.Tests/Stage6SqlMapTests.cs:448-449`
- 证据：子查询谓词为 `l.recognition_dept_id = g.recognition_dept_id and l.recognition_time = g.last_recognition_time` 加日期范围，未限定接收组织、医院或院区。该维度的分组键按设计取「接收院区 + 处理结果互认科室 ID」（Server/design.md「SQL 聚合口径」分组键条，第 87 行），把院区纳入键的原因是科室 ID 为医院侧业务标识：`CONTEXT.md`「医院业务科室和人员统一规则（2026-09-01）」第 2 条规定科室 ID 统一按 String 接收、不要求与其他平台主数据使用相同标识；`SubmitRecognitionProcessingResultsCommand.cs:41-44` 写明该 ID「在来源系统中的标识；按请求直接保存，不向权限系统补查」。两个不同院区或医院存在相同科室 ID 字符串、且外组处理结果的互认时间与本组内最晚互认时间相等时，外组处理结果的名称进入 min 候选集合，展示名称可能取到本分组事实之外的名称。设计 V20（Server/design.md 验证矩阵第 144 行）声明「展示名称取范围内互认时间最晚一条处理结果保存的名称」，取值主体应为本分组归类的处理结果。
- 影响：仅互认科室维度行的展示名称可能取错；筛选、计数与分页不受影响。触发需要跨组同 ID 且时间并列，概率低但结构上可达。V20 行为面（真实数据库）由票 03-05 取证，语句文本属本票交付物。
- 建议方向：子查询补充接收三值定位（经匹配记录关联），或改为分组内派生取最晚时间名称的写法；修复时同步更新 `Stage6SqlMapTests.cs:448-449` 对该子查询文本的两条锚定断言，避免守卫把缺陷文本一并冻结。

### F-02 两处「判别力」断言为构造性恒真，不产生拦截能力证明

- 类型：缺陷；严重度：低
- 位置：`server/Dy.MedicalRecognition.Tests/Stage6SqlMapTests.cs:412-417`（排序兜底键判别力）、`server/Dy.MedicalRecognition.Tests/Stage6SqlMapTests.cs:466-471`（互认科室分组键判别力）
- 证据：两处均先用 `string.Replace` 把被断言文本从语句副本中替换掉，再断言原文本在副本中不出现。Replace 的语义保证替换后原文本必不存在，该断言对任意输入都为真，与语句真实内容无关，与第 2 轮 F-01（`Stage5ConstraintTests.cs:800-808`，恒真断言）同款模式。同文件其余判别力块真实执行了判定：`$PeriodStart` 剔除比较（第 329–331 行）验证抽取片段确实含日期参数，`limit 1` 注入（第 369–371 行）真实运行方言扫描器，索引列序重排（第 167–173 行）对真实脚本执行抽取比对。
- 影响：两处所在用例的主断言（排序字符串 Contains、分组键 Contains）本身有效且已通过，语句守卫的拦截能力不受影响；无效的只是附带证据面。
- 建议方向：对变异文本调用与主断言相同的判定并断言其不成立，或删除这两处恒真断言；与第 2 轮 F-01 同批修复。

### F-03 同筛选守卫的比较窗口不含 from 子句，联接集合漂移不在此拦截面上

- 类型：建议；严重度：低
- 位置：`server/Dy.MedicalRecognition.Tests/Stage6SqlMapTests.cs:555-571`（`ExtractFilterRegion`，窗口为最后一个 where 到 group by 或 order by 之间）
- 证据：守卫比较的片段从 where 起算，联接行位于窗口之外。计数与取页语句的联接集合或联接类型不一致（例如一方把左联写成内联）时行集基数不同、总数与当页错位，该守卫仍通过。审查代理对七对语句的联接集合做了独立抽取比对：当前全部逐字一致（各对分别 7、6、7、7、7、7、6 条联接），无实际漂移。
- 影响：现状无差异；守卫对「计数与取页同一行集」目标的覆盖面窄于 where 片段面，后续修改任一语句的联接时此守卫不报。
- 建议方向：把比较窗口向前扩到 from 起点，或对七对语句做去注释后的分区段等值判定，把联接集合一并纳入冻结。

### F-04 「项目类型」筛选在汇总与明细语句解析于不同事实列

- 类型：疑问；严重度：低
- 位置：汇总语句 `MedicalRecognitionReportQuery.xml:939`、`MedicalRecognitionReportQuery.xml:1049`（`sc.item_type = $ItemType`，标准目录所属分类）；明细语句 `MedicalRecognitionReportQuery.xml:1276`、`MedicalRecognitionReportQuery.xml:1333` 等八处（`mi.item_type = $ItemType`，匹配项保存值）
- 证据：同一请求字段 ItemType 在接收侧汇总语句按标准目录分类的项目类型过滤，在四类接收侧明细与来源侧明细语句按匹配项保存值过滤。汇总行投影的项目类型取 sc.item_type（与自身筛选一致），明细行投影取 mi.item_type（与自身筛选一致），各语句内部自洽；两条事实列在标准目录重分类或匹配项保存值与目录不一致时取值不同。页面交互按汇总行项目类型预填明细筛选，此时可能出现汇总行有值而下钻明细为空，触及 V25「汇总与明细计数一致性」（Server/design.md 验证矩阵第 146 行）的边界。设计正文（Server/design.md 第 60、86–87 行）未明示筛选列口径。
- 影响：本票语句面内部自洽，无静态缺陷；口径分歧在行为面（票 03-05）才可能表现为汇总与下钻计数不一致。
- 建议方向：票 03-05 编写行为用例时明确该筛选列口径（统一取标准目录或统一取匹配项保存值），并在 V25 用例覆盖「汇总行预填下钻」场景。

### F-05 原因汇总语句返回全部分组的原因行，与语句清单「当页分组」表述存在范围差

- 类型：疑问；严重度：低
- 位置：语句 `MedicalRecognitionReportQuery.xml:1080-1135`（无分页限定）；设计出处 Server/design.md「统计语句清单」第 74 行「当页分组的不采纳原因汇总」；端口备注 `IMedicalRecognitionReportQueryRepository.Statistics.cs:38-48`（「不带分页，调用方按分组键装配进所属分组行」）

- 影响：页面场景会多取当页之外的分组原因行，行数随分组数与原因种类增长（性能面由负责人权衡）；功能正确性由应用层装配保证（票 03 取证）。范围取舍需负责人确认，避免行为票按另一侧解释编写用例。
- 建议方向：由负责人确认按「全量行集加应用层装配」口径登记（含导出复用理由与行数上限评估），或要求语句限定当页分组键集合；确认结论补进 Server/design.md 或 testReport.md。

### F-01 提醒明细不承载处理结果决策列，已反馈行的决策字段恒为空值

- 类型：缺陷；严重度：中

## 一、发现清单

### F-01 路由用例的一处「变异证据」为恒真断言，不产生判别力证明

- 类型：缺陷；严重度：低
- 位置：`server/Dy.MedicalRecognition.Tests/Stage6EndpointTests.cs:90-92`（用例 `Export_controller_declares_versioned_route_with_two_post_actions`）
- 证据：第 84 行已用 `Assert.Equal("api/v1/statistics-export", controllerRoute)` 把路由文本冻结为固定值，第 91-92 行再断言该固定值与常量拼出的 `Api/IMedicalRecognitionReportQueryAppService` 不相等，两侧均为既定值，断言对任意路由输入都为真。注释写明「把控制器路由前缀换成自动端点前缀形态后，同一条判据必须判出冲突」，但代码从未对变异文本执行任何判定。同文件第 3 例（第 153-160 行）对缓存头判定做了真实变异并断言其失败，第 1 例（第 48-50 行）以查询入口反例证明 NonAction 判定不恒真，对照之下此处的「变异证据」为装饰性。与第 2 轮 F-01、第 3 轮 F-02 同款模式。
- 影响：用例的主断言（路由等值、两段前缀、两动作路由与绑定）全部有效；无效的只是附带证据面。
- 建议方向：删除该三行，或把路由文本抽取为判定函数后对「换成自动端点前缀形态」的变异文本调用同一判定并断言其报出冲突；与后续测试批次顺带处理。

## 三、关键决策独立判断

**1. NonAction 口径：成立，判据与设计意图闭合。** 审查代理独立反编译本机缓存 `dy.apron.http/1.1.0.48`（经宿主 `Dy.Apron.QuickStart` 传递引用，`Directory.Packages.props:11-14` 同族版本 1.1.0.48）：`Dy.Apron.Http.DynamicController.ControllerModelConvention.Apply` 对每个动作以 `!actionModel.ActionMethod.IsDefined(typeof(NonActionAttribute)) && !IsDefined(RouteAttribute) && !IsDefined(HttpMethodAttribute, inherit: true)` 为注册前提，带三特性之一的方法不获得路由、选择器与 ApiExplorer 可见性；`HttpServiceHelper.GetHttpVisibility(ActionModel)` 同样把 NonAction 映射为 `HttpVisibility.Hidden`。判定对象 `ActionMethod` 是实现类型（应用服务继承 `ApplicationService` 实现 `IHttpService`，故进入该约定）上的方法信息，特性声明在实现方法上即为框架所读取的位置——接口无需也不持有该特性（接口分片第 142 行无特性，与实现一致）。特性位置经双重证实：源码核读（`StatisticsExport.cs:49、117`）与 `Stage6EndpointTests.cs:43-46` 的运行时反射断言；第 1 例另以查询入口 `QueryRecognitionMatchRecordAsync` 无该特性的反例证明判定不恒真。设计一致性：V1（Server/design.md 第 128 行）声明「宿主共 11 个端点，导出控制器含平台/本院两个 POST 动作」，即九个自动端点加两个手工 POST，结构上要求导出入口排除自动注册，`[NonAction]` 为框架原生排除机制；`GetBranchStatisticsExportAsync` 仅存在于实现类，若无排除将被注册为第三个端点，两实现方法都带该特性是必要且充分的。阶段 4 对照属实：`ReportPdfFileController` 同为 `[Route("api/v1/…")]` 手工控制器、第 130-131 行同一 `CacheControl` 取值与 `File(content, contentType, fileName)` 形态，`Stage4EndpointTests` 第 270-288 行有同款静态守卫。分层判断：**与 `backend-architecture.md` 不冲突**——该规范对 Application 的禁用面为 Repository 具体类型、SQL、ORM/DataMapper（HTTP 禁令针对 Domain），`Server/design.md` 层映射表对 Application 允许「平台 NuGet 契约」；且 Application 工程经 `Microsoft.AspNetCore.OpenApi` 可见 ASP.NET Core 类型是生成骨架既有事实（`git show HEAD` 证实该引用在票 05 之前已存在），本票未新增任何包引用，`[NonAction]` 仅为宿主侧约定消费的声明特性，未向应用层引入 HTTP 行为。残余边界：真实宿主上的 11 端点全景与导出下载链路归票 09（V40/V44），与本判定不冲突。

**2. ClassifyReasonRows 等价重构：成立。** 提取后的私有静态方法（`StatisticsExport.cs:427-446`）与页面路径调用点（`Statistics.cs:685-686`）逐行比对：(1) 归并键——`ReasonGroupKey` 六字段（接收组织/医院/院区、互认科室 ID、项目类型、标准项目编码）与 `MapUsageSummaryRow` 的查询键构造（`Statistics.cs:716-718`）同源同序，两侧由同一 record 类型构造，键一致性不变；(2) 排序——方法内仅按仓储返回顺序逐行追加列表，提取前后均无排序动作，组内原因顺序保持仓储序，既有用例对 `NonAdoptionReasons[0]/[1]` 的顺序断言未改且通过；(3) 占比分母——仍在 `MapReasonSummary`（`Statistics.cs:768-775`）以行内不采纳次数为分母计算，提取未触碰该计算；(4) 其他原因归并——发生在 SQL 层统一归入其他代码（票 02 已审语句），应用层装配面无归并逻辑，提取不改变该口径。既有汇总用例 `Usage_summary_assembles_reason_rows_into_their_group_rows_with_inline_ratio`（`:358-388`）断言集合与第 4 轮登记逐项一致（装配、行内占比 0.5、其他代码 6、跨页原因行丢弃、零不采纳组为空），全量运行通过。导出侧新增调用以同一方法处理全量原因行，属新增调用点而非页面路径行为变化。

## 三、关键判断

**1. DI 注册「冲突」查证：第 6 轮结论与票 09 实测不存在矛盾，开发根因判定经独立反编译证实成立。** 第 6 轮反编译的对象是 `Dy.Apron.Http` 的**端点暴露约定**（`ControllerModelConvention` 对 NonAction/Route/HttpMethod 的注册跳过），回答的是「导出入口为何不自动暴露为端点」，从未对 **DI 服务注册**形态下过结论；二者是不同机制，所谓冲突的前提不成立。审查代理本轮独立反编译 `dy.apron.core/1.1.0.48`：`PluginManager.ExposeServices` 对模块程序集全部公共非抽象非泛型类调用 `ServiceLifetimeManager.RegisterType`；`getRegisterTypes` 在无 `ExposeServicesAttribute`（源码 grep 证实该服务无此特性）、无 `IRegisterType<>` 接口时按「接口名去 `I` 前缀后与具体类名互为后缀」取第一个匹配——`IMedicalRecognitionReportQueryAppService` 恰命中，单元素列表走 `ServiceDescriptor.DescribeKeyed(接口, null, 具体类, Transient)` + `TryAdd`，即**只注册接口形态，具体类不在容器中**。因此手工控制器 `RecognitionStatisticsExportController` 构造函数按具体类注入时激活失败，报出的正是报告引用的异常；阶段 4 先例 `ReportPdfFileController` 只注入接口形态，故该缺陷在阶段 4/5 不可见、到首个注入具体类的手工控制器才暴露。修复（`OnPostConfigureServices` 补一行 `AddScoped<MedicalRecognitionReportQueryAppService>()`，git diff 逐行核对恰此一处加注释）最小、不触碰契约分片、不改变任何接口约定；与框架注册无冲突（服务类型不同、框架侧为 TryAdd）。一项注记：新增注册为 Scoped 而框架的接口形态为 Transient，现工作区唯一消费者是按请求激活的控制器，无同一消费者同时注入两种形态，动态端点经 `ActivatorUtilities` 创建不经该注册，行为无影响——登记备查，不构成缺陷。
