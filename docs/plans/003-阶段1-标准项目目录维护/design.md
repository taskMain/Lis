# 阶段 1 标准项目目录维护（F01）设计

本阶段交付平台统一的标准医疗项目类型、分类、分组与标准项目维护能力，以及当前有效标准目录查询。阶段划分与计划原则见 [总体计划设计](../001-总体计划/design.md)。

本文是阶段 1 的阶段设计。后端设计与测试前矩阵见 [Server/design.md](Server/design.md)，前端设计与测试前矩阵见 [Client/design.md](Client/design.md) 与 [Client/testPlan.md](Client/testPlan.md)。实施批次见 [impl.md](impl.md)，实际执行结果见 [testReport.md](testReport.md)。

**当前处于实施与验证收口阶段。** 用户已确认本平台尚未建表，不使用归属未确认的非本平台对象，物理表统一使用 `mrec_` 前缀，实体不加前缀（S1-D3/S1-D31）。S1-D29 已于 2026-09-14 确认进入实现与验证。页面与交互设计见 [Client/design.md](Client/design.md)。

## 目标与范围

- **目标及可验收结果**：平台管理员可维护标准医疗项目分类、分组与标准项目，可查询当前有效标准目录；本阶段涉及的写接口与查询接口端到端可用，管理端页面可从宿主登录页与宿主菜单进入并完成上述维护。

- **排除范围**：互认配置（F02）、金额维护（F10）、报告采集（F03）及后续阶段能力；其他 16 张表的创建；报告生命周期、匹配、处理结果、引用相关命令与查询；其余 16 个实体的仓储 `scope` 修正（随各自阶段处理）；标准目录对象的物理删除能力（SRS 明确规定不提供）；领域事件的发布与订阅机制。
- **需求与领域模型依据**：SRS `F01 标准医疗项目目录管理`（业务规则 7 条、备选流 4 条、关键属性 5 条、主事件流 5 步、后置条件 3 条）；SRS 界面章节的「互认项目分类分组管理」与「标准医疗项目管理」两节；SRS 通用界面要求 4 条；`CONTEXT.md` 的「互认项目类型、分类和分组」条目；`docs/uml/1-MedicalRecognitionReport.wsd` 中三个实体与对应命令、事件；`docs/uml/2-MedicalRecognitionConfigurationUiQuery.wsd` 中标准目录相关查询与 ReadModel。
- **前置依赖及当前确认状态**：阶段 0 基线见 [阶段 0 实施记录](../002-阶段0-现状对齐/impl.md)；历史证据不等于本阶段验收。分类、分组修改规则及整份保存语义已按 S1-D26 确认；本阶段仍处于设计阶段，不代表整体设计通过或开始实施。

## 设计

### SqlMap 作用域与语句解析

失败证据见 [阶段 0 实施记录](../002-阶段0-现状对齐/impl.md) 与 [Project Context](../../../.agents/instructions/project-context.md) §3.4：调用 `POST /Api/MedicalRecognitionReport/CreateMedicalStandardCategory` 返回 `HTTP 500`，异常为

```
Dy.Earthrace.Exceptions.EarthraceException:
Can not find Statement. FullSqlId:MedicalRecognitionReport.CreateMedicalStandardCategory
```

框架按 `{作用域}.{语句 ID}` 解析语句。生成物在两端都把作用域写成了**聚合名**：

| | 已验证可工作的对照项目 | 本项目生成物 |
|---|---|---|
| SqlMap `Scope` | **实体名** | 聚合名 `MedicalRecognitionReport` |
| Repository 作用域 | **实体名** | 聚合名 `MedicalRecognitionReport` |

该对照仅保留阶段 0 所取样例的生成物差异与外部项目证据，不概括所有 LisCenter 仓储。下文用于物理映射的 LisCenter 样例使用聚合作用域，两者不可混为普遍规则。异常只证明当次查找未命中，不能据此确定是语句未注册还是注册在其他键下；聚合作用域是待核实的原因之一，不因多个实体共用作用域就断定必然失败。

框架侧签名证据与默认行为推导分开记录：

- 写方法签名为 `DataMapper.InsertAsync(entity, scope, sqlId, realSql, triggerEntityEvent)`，`UpdateAsync` / `DeleteAsync` 同形；已缓存版本 `1.0.0.44 / .51 / .59 / .60` 签名一致。
- 历史记录曾由 `[CallerMemberName]` 推导默认语句名为 `InsertAsync → Insert`；仅有签名与属性不能证明参数省略位置、内部转调及去掉 `Async` 的处理链。当前未附完整调用链证据，该默认行为解释保持待核实，不作为修法依据。本阶段每个调用点显式传 `scope/sqlId`，不依赖该默认推导；若实施需要分析默认路径，再按具体属性位置、调用链和实际查找键取证。

**本阶段采用的作用域修法：作用域一律取实体名，写成显式 `scope:` 实参，并在每个 `DataMapper` 调用点传入。**

```csharp
// 仓储内每个调用点显式传实体作用域；常量按实体声明在仓储局部文件内
private const string CategoryScope = "MedicalStandardCategory";

public async Task<int> CreateMedicalStandardCategoryAsync(MedicalStandardCategory category) =>
  await DataMapper.InsertAsync(category, scope: CategoryScope, sqlId: "CreateMedicalStandardCategory");
```

作用域常量按实体在仓储局部文件内声明，取值必须与对应 SqlMap 的 `Scope` 属性逐字一致。

同时做两项配套处置：

1. **SqlMap `Scope` 改为各自实体名**，使注册侧与查找侧一致；物理 SQL 表名另按 S1-D31 改为本平台 `mrec_` 表名，二者是独立映射维度。
2. **仓储去掉 `SetContext`**：`SetContext` 写入的是共享映射器实例上的可变作用域状态，并发调用方会互相翻转作用域；对照项目的仓库测试明确禁止生产仓储依赖该状态。改由逐调用显式传参，作用域不再依赖可变状态。

**不拆仓储**：沿用单个聚合级仓储（按实体拆局部文件）。作用域正确性与仓储是否按实体拆类是两个独立问题，对照项目即聚合仓储 + 实体作用域。

**本阶段 SqlMap 的改动边界**：对齐 `Scope` 属性值及 SQL 中的物理表名，保留既有业务语句 ID，不因物理前缀修改实体名或逻辑作用域。业务规则所需的读取与条件更新（查重、当前状态条件更新）按各自设计新增或调整，不以“SQL 内容不变”阻止必要整改。

生成物中本模块的 `QueryAll<X>`（如 `QueryAllMedicalStandardCategory`）保留语句 ID，其物理表引用也须同步为本平台表名；本阶段 4 个公开查询仍走独立查询仓储与独立作用域，不因表名整改改走这些语句。

#### 尚未闭合项与探测办法

作用域的**确切解析顺序**及实际注册键未经本项目运行时探测。已知旧调用未找到指定语句；以下只是待探测的候选解释，并未排除语句加载或注册失败：

| 解释 | 旧调用解析出的键 | 修法 |
|---|---|---|
| A：框架默认作用域取实体名，仓储的 `SetContext` 聚合名被忽略或仅作回退 | 需以探测输出为准 | SqlMap `Scope` 与调用点 `scope:` 均改实体名 |
| B：框架默认作用域取仓储 `SetContext` 的值（聚合名），而 XML 的 `Scope` 不参与注册键 | 注册键来源需以探测输出为准 | 同上；两者仍都改实体名 |

两种解释下都采用已确认的实体作用域对齐方案；在解释 B 下，XML 的调整可能只是约定对齐，不能据此声称它修复了查找失败。方案可继续设计，实际修复须经首批探测确认。

**首批次探测要求**：须输出实际查找键（`FullSqlId`）**与**当前已注册的语句键清单，以区分「未注册」与「注册在别的键下」两类原因；只观察一条写接口是否返回 500 无法区分。

若探测发现语句未加载、注册机制不同或实体作用域对齐不能解决问题，暂停相关作用域修复，依据证据修订该部分设计；其他独立工作不受阻塞。不得为维持原推论忽略新证据或扩改其他实体。

**跨项目证据的适用边界**：阶段 0 所选对照的可用性属另一项目的证据，不能证明本项目生成物的语句注册形态相同，也不能推导 LisCenter 全部采用实体作用域。本项目已选实体作用域与业务 `sqlId` 保持不变，实际注册键仍以探测为准；物理表映射样例只证明显式 SQL 可以引用带前缀的表。

同一结论供后续 16 个实体沿用。

### 启停状态与新建字段类型

`CONTEXT.md` 与 SRS 均把启停表达为"是否启用"的布尔语义。SRS 要求启停只能通过独立操作改变、创建后默认启用、普通修改不改变启停状态、重复启用或重复停用按幂等成功处理且不重复发布启停事件。

本平台三表从新建起使用 `is_valid boolean`，与实体 `bool IsValid` 一致；`oper_time` 直接使用 `timestamptz`，由实际后端 `DateTimeOffset` 写入、读取及序列化验证。不存在本平台历史整数值转换或历史时间解释任务，不引入类型处理器或 SqlMap 类型转换来兼容其他系统表。

### 幂等与派生"实际有效"

"实际有效"是派生值而非存储字段：SRS 规定当前有效标准项目必须同时满足自身、所属分组和所属分类均启用，且上级停用不修改下级自身状态、上级恢复后下级自身仍启用的对象自动恢复当前有效。

- **幂等在领域层判断**：先读当前状态，已是目标状态则直接按成功返回、不调用仓储、也不收集事件。
- **派生"实际有效"不落库**，由查询语句的三表条件表达。

选择领域层判断的理由：SRS 要求的是"按幂等成功处理"而非"静默不更新"，调用方必须得到明确的成功语义；而按受影响行数判断无法区分"已是目标状态"与"记录不存在"。

### 数据一致性与新建 DDL

用户已确认本平台尚未建表，三张无前缀标准目录表属于归属未确认的非本平台对象。旧共享复用、整数转布尔、旧注释回退、14 索引保留例外及外部消费方兼容门槛全部撤销。历史报告保留其取证时点，但不得指导当前建表或推导本平台已有数据。

1. **最终 DDL 与实际结构一致**：三份 `Repository/Scripts` 建表脚本包含列定义、类型、可空性、表/列元数据注释及三个业务唯一索引，实际执行结果逐项核对；不再保留“生成脚本不含索引”的交付例外。
2. **数据库表与后端实体一致**：按 UML 和公共字段约定建表，`is_valid boolean`、`oper_time timestamptz` 直接创建，物理表名由显式 SQL 映射，实体名不加前缀。
3. **不操作旧对象**：不共享、重命名、复制或迁入其他系统表，不建设双写或兼容视图，不读取旧数据作为本平台初始化来源。发现目标同名对象时暂停交负责人核对，不以 `create table if not exists` 静默跳过。
4. **执行闸门**：负责人确认目标数据库及 schema、最终 DDL 与对象范围后执行并确认完成，之后才进行依赖这些表的目标库数据库测试；不猜测 schema。不依赖数据库的实现、契约与静态验证可独立推进。
5. **受控库验证**：V30 核对新建结构及实际后端写入、回读和序列化，V58 核对新建 DDL 元数据；均须负责人确认对应受控库及 DDL 执行，不以受控库结果代替目标库完成确认。V55 的历史异常整数迁移用例退休，不改写其历史记录。

### 建表脚本与物理命名

全平台按 [Project Context](../../../.agents/instructions/project-context.md) 的本项目 DDL 规则整改，随业务阶段落地。本阶段只整改三张标准目录表脚本，其他 16 张表在所属阶段处理，不提前建表。

- 字段顺序固定为 `id` → 普通业务字段 → 启用/作废/逻辑删除等状态标志 → `oper_time` → `oper_id`。普通字段保持对应 UML Entity 中的相对顺序，多个状态标志也保持 UML 相对顺序；不把所有 Boolean 或业务枚举机械视为尾部状态标志，不为了排列新增 UML 不存在的字段。末尾操作字段顺序按负责人本次要求明确为操作时间、操作人。
- 表注释取 UML 实体中文名称，字段注释取对应属性中文名称及已声明的业务说明；公共 `id/oper_time/oper_id` 使用主键 ID、操作时间、操作人约定，不因 UML 省略公共字段而缺注释。缺失或冲突的业务说明先登记核对，不猜测。注释须落为数据库元数据，只有 SQL 文件头部或行内说明不算完成。
- 建表脚本同时交付元数据注释与业务唯一索引，不设置独立旧表注释迁移。受保护人工修正须登记清单与再生成检查，不直接重跑生成器覆盖配置。
- 平台自有业务表统一使用已确认的 `mrec_` 前缀，本阶段保留原完整 `snake_case` 基础表名。表名不要求由实体名自动推导，以明确的物理映射为准；前缀不改变领域实体名、UML 名称、API 名称或已选 SqlMap 逻辑作用域。实施前核对表名、索引及约束名称是否冲突，不把前缀视为无冲突保证。

| 实体 | 新建物理表 | 业务唯一索引键 |
|---|---|---|
| `MedicalStandardCategory` | `mrec_medical_standard_category` | `name` |
| `MedicalStandardGroup` | `mrec_medical_standard_group` | `category_id, name` |
| `MedicalStandardItem` | `mrec_medical_standard_item` | `code` |

三个业务唯一索引均覆盖启用与停用记录，不加仅启用条件；分类名称全平台唯一、分组名称分类内唯一、项目编码全平台唯一。索引名称在最终 DDL 中明确并与异常翻译核对，不能继承其他系统的索引清单或以旧索引存在代替新建。

**显式 SQL 物理映射依据**：只读检查负责人指定的 LisCenter 项目源码，Domain 的 `StandardItemEntity.cs` 无表映射特性且实体名不含 `lis_`；`ReceiverBranchLabItemCapabilityRepository.StandardItem.cs` 在 `DataMapper` 调用中传入 `scope: SqlScope`，同目录 `ReceiverBranchLabItemCapability.xml:118–131` 通过显式 `insert/from lis_standard_item` 指定物理表。该样例的 Scope 是聚合，不证明所有 LisCenter Scope 均为实体，也不证明框架不支持表映射特性。

本项目沿用显式 SQL 指定上述物理表，保留已选实体 scope 与业务 sqlId，不要求新增表映射特性。DDL、写入/查重/状态更新 SQL、查询 SQL 及本模块保留语句中的表引用必须一致；实体仍使用原名称。V57 静态核对映射与完整 DDL，V30 以实际后端读写验证映射，V58 核对新建列序、注释及索引元数据。

### 唯一性校验与错误语义

SRS 要求分类名称在全平台标准目录内唯一、分组名称在同一分类下唯一、标准项目编码全平台唯一，违反时拒绝保存。

本阶段采用两层保障：**先查重抛业务异常 + 数据库唯一索引兜底**。查重语句内 `count(1)` 并按可选排除条件排除自身，由领域层判断后决定是否抛异常；数据库唯一索引用于兜底并发写入，不作为常规错误路径。

业务异常沿用对照项目的既有约定（S1-D18）：抛 `InvalidOperationException` 并携带中文业务消息，不引入自定义异常类型。

### 上级有效性判断与"使用关系"判断

SRS 用两个不同措辞表达两种不同判断，本阶段严格区分：

| 场景 | 判定依据 |
|---|---|
| 新增分组、项目 | 上级必须存在且**启用**，归属必须一致 |
| 分类修改项目类型 | 只看**是否存在下级分组**，含已停用分组；存在则项目类型不可改 |
| 分类、分组修改名称和备注 | 不受自身、上级启停状态或下级使用情况限制；名称唯一性规则不变 |
| 分组所属分类 | 创建时确定，之后始终不可改；更新契约不含 `CategoryId`，页面不提供改挂或拖拽移动 |

### 业务规则归属

SRS F01 的规则当前在领域层完全空缺（管理器中无任何 `if` 与 `throw`）。本阶段在领域层实现：唯一性校验、新增时上下级存在性与启用状态校验、分类项目类型限制、分组归属不可修改、创建后默认启用及启停幂等语义；"实际有效"在查询侧派生。资料整份保存遵循 S1-D26，不增加无变更短路。领域不变量、事务边界与 Command-Event 归属见 [Server/design.md](Server/design.md)。

### ReadModel 契约修正

生成的 ReadModel 存在两类问题：选项型字段与层级集合退化为 `object`；`Remark` 为非空 `string`，与实体和数据库列的可空性不符。本阶段按下表修正。

**修正依据分两类，实施与验收时必须区分**：

- **修复生成退化**：`ItemType` 与层级集合。UML 对这四个属性只写了单个类型名、未标集合记号，生成本应表达为嵌套 ReadModel，退化为 `object` 属生成缺陷。
- **有意改变公共契约**：`Remark` 可空、嵌套明细的 `Remark` 可空、以及 S1-D22 新增的「使用情况」字段。相对原生成基线属于契约变更，现已同步 UML2；不再以长期偏离 UML 的方式维护。

| 字段 | 由 | 改为 | 性质 |
|---|---|---|---|
| `ItemType` | `object` | `MedicalItemType` | 修复生成退化 |
| 层级集合 `ItemTypes`/`Categories`/`Groups`/`Items` | `object` | 对应的嵌套 ReadModel 类型 | 修复生成退化 |
| 三个 List ReadModel 的 `Remark` | `string`（非空） | `string?` | 有意改变契约 |
| `EffectiveMedicalStandardCatalog` 层级内各明细 ReadModel 的 `Remark` | `string`（非空） | `string?` | 有意改变契约 |
| 分类、分组 List ReadModel 的「使用情况」 | 无此字段 | 新增派生字段（S1-D22） | 有意改变契约 |

**契约修正须纳入生成后核对清单**，以当前 UML 和本设计为准；生成器无法准确表达的部分才作受保护手工修正。嵌套明细的 `Remark` 与三个列表同级处理，不得只改列表而漏掉嵌套结构。

UML 的 `Remark String?` 是正式可空契约。现有 dy-puml 校验器以 P005 报告 ReadModel 可空信息不能被生成器正确保留；不为消除该诊断退回非空声明。实施时核对并手工补齐生成类型及序列化，V26/C27 验证最终契约；此限制不等于完整生成器校验通过。

### 查询能力

当前 20 个查询全部未实现，51 个 ReadModel 是孤立声明、无任何消费者。本阶段实现 4 个查询：分类列表、分组列表、标准项目列表、当前有效标准目录。

- **契约**：沿用 UML 定义的 ReadModel，不退回实体 DTO；「当前有效标准目录」是三级层级结构，无法用单个实体的形状表达。
- **作用域**：查询使用独立作用域，不挤进实体仓储。
- **派生有效**：「当前有效标准目录」由一条三表 join 的 SQL 表达三级状态过滤，应用层只做扁平结果到层级结构的组装。
- **分页**：4 个查询均不分页。UML 的三个 List ReadModel 没有分页字段，引入分页需要变更契约。
- **单条查询**：不新增按 ID 取单条的查询；编辑回显使用列表查询结果，列表 ReadModel 已含全部可编辑字段。
- **入参边界**：筛选条件严格等于 UML 查询入参，不额外增加入参，也不引入可配置排序；四个查询的入参以 UML 声明为准（分类列表按项目类型，分组列表按分类 ID，标准项目列表按分类 ID/分组 ID/编码/名称/是否启用，有效目录按项目类型与分类名称）。
- **展示边界**：页面展示字段以 SRS 展示清单为准，**加上**本阶段经确认的派生呈现（「当前有效」列与分类/分组「使用情况」）；除此之外不增加展示字段。
- **匹配语义**：公共 API 的 `Code`、`Name`、`CategoryName` 采用字面包含匹配，`%`、`_` 为普通字符，不支持模式输入（S1-D28）；大小写仍按数据库默认规则，不承诺与前端本地比较完全等价。空值与纯空白的处置不变，见 [Server/design.md](Server/design.md) 的查询语义表。

### 页面形态的原型比对

页面形态通过一次性 UI 原型比对确定。当前采用负责人确认的 A2，原 A/B/C 保留作对照而非并行实施方案；各变体共用内存数据，原型不代表真实业务能力已实现。

| 变体 | 结构 | 编辑形态 |
|---|---|---|
| A | 左侧固定宽度目录树（类型→分类→分组）+ 右侧项目列表 | 分类、分组、项目备注均用弹窗 |
| A2（采用） | 保留 A 的左树右表；树仅标停用、编辑与更多图标常显；左侧显示停用复选框、右侧三态状态筛选；窄屏上下排列 | 分类、分组使用情况移入编辑弹窗，只读呈现；业务规则不变 |
| B | 目录横向铺开为分类卡片与分组标签，项目表格占满全宽 | 分类与分组用弹窗，项目备注改为表格行内编辑 |
| C | 左侧窄树 + 右侧就地编辑面板 + 项目表格 | 分类与分组在右侧面板直接改，项目仍用弹窗 |

**结论：采用 A2 方案**（S1-D19、S1-D27）。以确认的布局、操作位置、弹窗和联动作为正式 UI 依据；保留当前有效、分类类型冻结、编辑表单不含业务启用开关、独立启停不级联及不分页的既有规则。原型备注归一化及筛选组合行为存在已登记偏差，正式实施须按 [Client/design.md](Client/design.md) 的备注原值、显示过滤及选择回退口径对齐，不直接沿用原型内存逻辑；本轮只修订设计，未修复或重新验证原型代码。

原型保留在子应用 `src/pages/prototype/`，路由为 `prototype/standard-catalog`，A2 使用 `?variant=A2`。正式页面落实已确认设计，但不直接把原型内存 store、模拟数据或方案切换器上线；正式实现须接入真实 API 并完成校验、异常恢复与适用测试。前端批次主责在正式交付前完成原型开发环境隔离，生产环境不注册原型路由、不包含原型模块及模拟数据；具体处置与验证见 [Client/impl.md](Client/impl.md)。源码保留作设计对照，不要求本轮删除。原型的局部交互验证只记入测试报告，不代替业务矩阵或宿主验收。整体阶段仍处于设计阶段。

### 已否决的备选方案

| 备选 | 否决理由 |
|---|---|
| 复用、改名或复制其他系统三表并转换历史数据 | 不符合已确认的独立新建与资源归属；不恢复旧表迁移或外部消费方兼容门槛 |
| 新表仍用 integer 并以类型处理器或 SQL 转换适配 bool | 不符合直接新建 boolean 与实体类型一致的规则 |
| 保留 `SetContext` 传聚合名（生成物原形态） | 不符合已选实体作用域及逐调用显式传参约定；实际注册键仍待探测，不把作用域差异写成已证实根因 |
| 保留 `SetContext` 但改传实体名 | 作用域取值正确，但仍把作用域放在共享可变状态上；对照项目的仓库测试明确禁止生产仓储依赖该状态 |
| 按实体拆仓储 | 作用域正确性与仓储粒度是两个独立问题；对照项目即聚合仓储 + 实体作用域，拆分反而割裂聚合 |
| 只改调用点 `scope:`、不改 SqlMap `Scope` | 不满足调用与配置两端实体作用域对齐约定；不能在注册机制未经探测时声称只改一端必然成功或必然失败 |
| 把查询挤进实体仓储 | 查询作用域与实体作用域语义不同，混用会使作用域与实体不再一一对应 |
| 为 4 个查询引入分页 | 需要变更 UML 的 List ReadModel 契约，不属于本阶段范围 |
| 新增按 ID 取单条查询 | 需要变更 UML 契约，而列表 ReadModel 已含全部可编辑字段 |
| 本阶段接通领域事件发布与订阅 | 订阅方选择与订阅后处理不属本平台职责，F01 也无事件消费需求 |
| 幂等改为按受影响行数判断 | 无法区分"已是目标状态"与"记录不存在"，破坏了 SRS 要求的幂等成功语义 |
| 引入自定义业务异常类型 | 会新增无消费方的抽象；前端按平台错误边界处理，不解析异常类型 |
| 页面采用「横向目录铺开 + 行内编辑备注」（原型变体 B） | 目录横向铺开会把分类与分组压成标签，层级关系与"分组归属分类"的一对多表达变弱；行内改备注在表格列宽紧张时可用空间不足 |
| 页面采用「选中即编辑」（原型变体 C） | 缺少独立编辑确认步骤，树选中同时承担筛选与切换编辑上下文两种语义，改动会即时生效、不利于核对 |

## 已知影响与风险

S1-D23 的 `AcceptedRisk` 仅表示负责人接受本平台 MVP 的并发边界，不表示已通过测试或发生的数据不一致会自动恢复。本平台独立建表，其他系统旧表及其消费方不在本阶段操作范围，不新增外部兼容、迁移或并发治理任务。

| 项 | 说明 |
|---|---|
| 目标库与 schema 未确认 | 由负责人确认本平台目标库/schema 和最终 DDL；不得沿用其他系统表所在位置或凭前缀猜测归属，遇同名对象暂停核对 |
| 建表执行前置 | 目标库 DDL 由负责人执行并确认；依赖该库的读写测试随后进行。V30/V58 受控库验证需单独执行确认，不替代目标库确认，不阻塞独立静态工作 |
| 最终 DDL 尚未验证 | 新建脚本必须含正确类型、列序、表/列注释及三个覆盖停用记录的业务唯一索引；V57/V58 核对，不能用旧系统索引或源码检查替代实际元数据 |
| `oper_time` 实际映射 | 新建 timestamptz 与 DateTimeOffset 的 Provider 写入、回读及响应序列化须由 V30 取得实际证据，不以脚本类型正确代替运行验证 |
| ReadModel 生成结果仍需核对 | UML 已同步 `Remark` 可空与 `UsageStatus`；重生成后核对是否准确表达，未准确生成的部分按受保护手工修正维护，不预设生成器一定覆盖 |
| 作用域传参依赖调用点 | 每个 `DataMapper` 调用点须显式传 `scope:`；漏传后的默认解析和失败方式待探测，不能预断为静默走错或一定报错 |
| 作用域解析顺序未探测 | 探测须输出实际查找键与已注册键清单；若不支持当前候选解释，暂停相关修复并修订设计，不扩大至其他实体 |
| 跨项目证据的适用边界 | 历史作用域样例与本轮物理映射源码分别限定用途；LisCenter 物理映射样例使用聚合 Scope，不能概括为全部实体 Scope，也不能替代本项目注册及实际读写探测 |
| 异常类型的框架翻译链路未验证 | S1-D18 选定 `InvalidOperationException` 的依据是对照项目的使用统计，**本项目**框架是否把它包装为业务错误响应（而非未处理异常 500）尚无证据；前端错误边界与 C2/C28 等用例建立在该链路上。列为实施期验证门 |
| 不分页偏离前端大列表规范（`AcceptedRisk`） | `frontend-application.md` 要求面向用户的大列表使用后端分页，本阶段 4 个查询均不分页（S1-D7）。理由：UML 的三个 List ReadModel 无分页字段，引入分页需变更契约；不以其他系统历史行数作为本平台规模。**触发重审条件**：单表标准项目超过 2000 条，或页面首屏渲染出现可感知卡顿。届时重新评估是否变更契约引入分页 |
| 其余实体按阶段处理 | 本阶段仅处理三张平台表及对应 SQL，其他 16 个实体的显式作用域、物理前缀与新建 DDL 随所属阶段落实，不从历史其他系统结构推导本平台转换任务 |

## 验收与停止条件

- **适用验证面及通过条件**：后端写接口与查询接口在真实数据库上端到端可用；SRS F01 的业务规则有对应失败测试并转绿；前端单一工作台页面可从宿主登录页与宿主菜单进入并完成分类、分组与标准项目的维护操作；API Client 重生成后构建与类型检查通过。后端测试前矩阵写在 [Server/design.md](Server/design.md) 的验证矩阵章节，前端矩阵写在 [Client/testPlan.md](Client/testPlan.md)，实际执行结果统一写入 [testReport.md](testReport.md)。
- **环境或数据依赖**：后端与前端端口、数据库连接、宿主与拦截配置全部引用 [Test Environment](../../../.agents/instructions/test-environment.md)，不在本阶段复制。
- **矩阵变更边界**：V55 退休，V1–V58 排除 V42/V55 后共 56 条有效后端用例；V30 改为新建结构及实际后端回读，V57 为完整 DDL/显式映射静态核对，V58 为受控库新建元数据验证。其他业务覆盖保留，正式状态仍为 `NotRun`，历史计数不改写。
- **负责人执行 DDL 或其他外部动作**：负责人确认目标库/schema 与最终 DDL 并执行，完成确认后才进行依赖该库的数据库测试；不涉及旧数据迁入或旧对象操作。**在外部权限系统新增宿主菜单项（标准项目目录维护）同样由项目负责人执行**，其完成仅是 Host 验收的前置，不阻塞客户端生成或组件开发。
