### 交互控制方式与边界（重要限制）

本轮宿主页面在受管 Chrome 中可用 `mousemove`，但 `Input.dispatchMouseEvent` 的 `mousePressed`/`mouseReleased` 未产生 `mousedown`/`mouseup`/`click`，`Input.insertText` 与 `Input.dispatchKeyEvent` 亦未生效（页面未收到事件，`document.activeElement` 保持 `body`）。因此本轮页面交互统一改为**在目标元素上调用其 React 事件属性**（`__reactProps` 的 `onClick`/`onChange`，并补 `nativeEvent`）驱动真实组件处理器，其余行为（渲染、派生、写请求、读回）均为应用真实逻辑。

该限制必须如实记录：`mousedown` 级硬件语义未取得证据，但本轮结论不建立在此之上——所有判定都由组件真实状态、DOM 派生结果与后端读回共同支持。首个失败尝试（缺少 `nativeEvent` 导致 Ant Design 复选框处理器抛错）本身就是这一控制方式的风险实例，其现象一度被误读为产品缺陷，见下节。

### 9.5 移交：框架层系统性请求绑定缺陷

实测写接口与查询接口对**类型不匹配**的入参一律返回 `500` 而非 `400`：

| 入参形态 | 写接口 | 查询接口 |
|---|---|---|
| 字符串字段传数字/对象/数组 | `NullReferenceException` | — |
| 枚举字段传字符串 | `NullReferenceException` | — |
| Guid 字段传 `"abc"`/`""`/`null` | `NullReferenceException` | `ArgumentNullException`（参数名 `request`） |
| 布尔字段传字符串 | — | `ArgumentNullException`（参数名 `request`） |

查询侧异常参数名直接是 `request`，说明**整个请求对象为 null**——框架吞掉了反序列化异常并把 null 交给 action。影响：违反 V48「参数错误与业务拒绝可区分」，且 500 响应携带完整堆栈（含服务器文件路径），属信息外泄。

**处置**：不写防御代码（请求到不了 Application 层），登记为框架层缺陷，建议反馈框架方；如需止血，走横向治理阶段在 Host 统一异常处理中屏蔽生产环境堆栈。

### 40.3 自查发现的缺陷与修复（重要）

本轮最初用 `[RegularExpression(@"\\S")]` 表达「非空白」，**实测证明该写法错误**，有两个反直觉行为：

1. **整串锚定匹配**：`\\S` 实际等价于「整串恰好一个非空白字符」，导致**所有正常名称被拒**（合法名称 `probe-nocat` 被判 `参数校验失败：名称不能为空。`）；
2. **对空串短路放行**：查询侧 `code: ""` 未被拒绝，返回 `200` 全量数据，违背 V39「空字符串与纯空白视为非法输入」。

**定位过程**：先写失败单测（合法请求被拒 + 空串未被拒），再用反射逐特性打印判定结果，得到决定性证据：

```
value=[probe-nocat]  Required=True ; RegularExpression("\\S")=False ; StringLength=True
```

**修正**：写侧改用 BCL `[Required]`（其 `Trim().Length != 0` 判定天然拒绝空串与纯空白，无需正则）；查询侧改用语义明确的 `[NonEmpty]`；原 `NonEmptyGuidAttribute` 相应扩展并改名 `NonEmptyAttribute`（文档与代码无残留引用）。

## 第四十一轮 查询布尔筛选的参数绑定修复（2026-09-15）

**背景**：收口后核实登记项「Provider 中立性与 `<IsNotEmpty>` 空值语义」时，以真实宿主认证链路对查询入参做矩阵实测，发现一个**未被 V/C 矩阵覆盖的真实缺陷**。

### 41.1 缺陷与根因

`QueryMedicalStandardItemList` 的 `IsValid` 筛选在传入时返回 HTTP 500：`Npgsql.PostgresException (0x80004005): 42883: 操作符不存在: boolean = integer`。

根因：共享 XML 用 `i.is_valid = $IsValid` 比较布尔列与参数，但**未声明参数绑定类型**——本项目共享 XML 此前完全没有 `ParameterMap` / `TypeHandler`；框架默认把布尔参数按整数绑定，PostgreSQL 的 boolean 列与 integer 比较没有对应操作符。页面按设计走本地筛选（`Server/design.md` 查询语义的入参拒绝边界）从不提交该字段，因此既有 V/C 用例未覆盖该分支。

### 41.2 `<IsNotEmpty>` 空值语义核实（LisCenter 对照）

- LisCenter 已有结论并留有踩坑记录（该仓库 `docs/plans/012-阶段10-全量联调验收与发布收口/testReport.md` 的 `R1-P005`）：`<IsNotEmpty>` 在参数为空时**跳过该 SQL 片段**，用于**更新可空字段**会导致「清空值写不进去」，其修法是把该字段改为无条件更新。
- 本项目核对：5 处 `<IsNotEmpty>` **全部在查询侧**（4 个可选筛选 + `ExcludedId` 排除自身），**写语句零使用**；`ChangeMedicalStandardItemRemark` 为无条件 `remark = $Remark`，清空可正常落库 → **不存在该陷阱**。
- 实测补证：枚举 `0` 被 `<IsNotEmpty>` 视为非空（`itemType=0` 命中 7 条、`itemType=1` 命中 2 条）。
- 由此第 26 轮 D1 与 V39 的分歧闭合：空串/纯空白由 Request 层拒绝（第 40 轮），到达 SQL 的只剩 `null`，「三义同义」不再影响契约。
