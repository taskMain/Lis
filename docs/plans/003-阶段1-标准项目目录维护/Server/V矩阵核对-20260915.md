## 8. 本轮发现的两处契约差异（需负责人决策）

**D1：V39「空字符串应被拒绝」与实现不一致。**
`MedicalRecognitionReportQuery.xml` 的筛选项使用 `<IsNotEmpty Prepend="and" Property="X">`。该条件对 `null`、空字符串与纯空白**都不拼接条件**，即三者行为相同、都按“不过滤”处理；而 V39 的预期是“`null` 表示不过滤，空字符串或纯空白被拒绝为参数校验失败”。
- 影响：V39 在当前实现下不能按原预期判定通过；这是契约与实现的语义分歧，不是缺陷或正确之分——需负责人确认以哪一侧为准。
- 若确认为“跟随现状”，需同步修改 `Server/design.md` 的 V39 预期；若确认为“按原预期”，则需新增入参校验并补失败测试。本轮未自行改动任一侧。

**D2：V29 的结案口径。**
V29 要求“恰好一条成功、另一条由**实际唯一索引**拒绝并返回可识别业务冲突，记录翻译前的数据库异常及约束名”。第 22 轮观察到的 `500 业务拒绝：分类名称已存在` 来自普通查重路径，按用例定义**不能**据此结案；唯一索引分支仍需单独取证。

**D3：V28/V38 的“排序稳定且唯一”缺少重复读取证据。**
`order by` 已确认存在且列组合唯一，但 V38 还要求“重复读取顺序一致”。静态 SQL 可强支持该结论，但严格按用例定义仍需两次真实读取比对。

#### 为什么 V38 不需要「重复读取比对」（对批注 2 的技术回答）

**结论：负责人判断正确。** 四个查询的 `order by` 实际形态（`MedicalRecognitionReportQuery.xml`）：

| 查询 | `order by` | 唯一键收尾 |
|---|---|---|
| 分类列表 | `c.item_type, c.name, c.id` | ✅ 主键 `c.id` |
| 分组列表 | `g.category_id, g.name, g.id` | ✅ 主键 `g.id` |
| 标准项目列表 | `i.category_id, i.group_id, i.code, i.id` | ✅ 主键 `i.id` |
| 当前有效目录 | `c.item_type, c.name, c.id, g.name, g.id, i.name, i.id` | ✅ 主键 `i.id` |

四条**全部以唯一主键收尾**，排序构成**全序**，不存在并列行，同一份数据两次读取顺序必然相同，重复读取比对不可能产生新信息。这就是「按 `order by` 设计就不会冲突」的确切含义。

**什么场景才会出现顺序不一致**（即原要求要防的情形）：当 `order by` 列组合**不构成全序**、存在并列行时，数据库对并列行的返回顺序**不作任何保证**，两次执行可能不同；诱因包括执行计划或索引选择变化、并行扫描、物理元组位置被 `UPDATE`/HOT 更新或 `autovacuum` 改变、缓存状态差异、分区裁剪。若再叠加 `limit/offset` 分页，并列行跨页会**重复或丢失**——这才是真实危害场景。

**对本项目的意义**：本设计该风险结构性不存在，**静态证据（列组合唯一）即足以结案**。**保留一条前置**：该结论依赖「`order by` 始终以唯一键收尾」这一形态；**将来若有人改动排序、去掉唯一键收尾，或为这些查询加分页，V38 的结论即失效，必须重新评估。**
