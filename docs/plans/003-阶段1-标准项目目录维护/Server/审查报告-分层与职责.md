### A-1（中·AppService 职责）公共 Request 校验缺失，校验被下沉到 Manager

**规范依据**

- `backend-architecture.md:78-87` 标准流程首两步为 `Request 校验` → `可信身份/组织/权限解析`；`:91`：`公共 Request 校验和权限范围。`
- `backend-architecture.md:113`：Manager `校验所有入口都必须遵守的领域不变量。`（即领域不变量，不是入参格式）

**实际代码**

`Application/.../MedicalRecognitionReportAppService.cs:21-27`（其余 11 个写用例同形，`:31-138`）

```csharp
public async Task<bool> CreateMedicalStandardCategoryAsync(CreateMedicalStandardCategoryRequest request)
{
  var createMedicalStandardCategoryCommand = request.MapToCreateMedicalStandardCategoryCommand();
  if (!Guid.TryParse(HttpRequestInfo?.UserId, out var userId) || userId == Guid.Empty) throw new InvalidOperationException("无法确定有效的操作人。");
  createMedicalStandardCategoryCommand.OperId = userId;
  createMedicalStandardCategoryCommand.OperTime = DateTimeOffset.UtcNow;
  return await manager.CreateMedicalStandardCategoryAsync(createMedicalStandardCategoryCommand);
}
```

整个写 AppService 中除操作人解析外没有任何 `request` 字段校验（无 null/必填/枚举范围检查）；对同一批规则，校验集中在 Manager：

`Domain/.../MedicalRecognitionReportManager.cs:14`、`:24`、`:55`、`:66`、`:95`、`:108` 调用校验，`:135-138` 定义

```csharp
private static void ValidateName(string? value) { if (string.IsNullOrWhiteSpace(value)) throw Input("名称不能为空。"); }
private static void ValidateCode(string? value) { if (string.IsNullOrWhiteSpace(value)) throw Input("标准项目编码不能为空。"); }
private static void ValidateItemType(MedicalItemType value) { if (!Enum.IsDefined(value)) throw Input("项目类型无效。"); }
private static void ValidateId(Guid value, string name) { if (value == Guid.Empty) throw Input($"{name}ID不能为空。"); }
```

阶段证据也证实这是运行时的实际报错位置：`决策与结论-20260915.md:28,142` 记录的 `参数校验失败：编码不能是空白。`/`参数校验失败：名称不能为空。` 均来自上述 `Input(...)`。设计本身要求相反：`Server/design.md:298`：`校验所在层 | AppService 在构造 Command 后、调用 Manager 前校验；Manager 不再重复判断身份来源`。

**为什么违反**：必填、空白、Guid 空值与枚举定义域属于「调用方能够提交的字段和格式约束」，是 Request 校验职责（`backend-architecture.md:36` 的公共 Request 职责），应由 AppService 在映射 Command 前后完成；Manager 应只保留必须所有入口共守的领域不变量（唯一性、父级启用/归属一致、状态是否允许变化）。当前实现使「入参格式错误」与「业务拒绝」两类失败都由 Domain 抛出，AppService 无法在进入领域前拒绝非法请求，也让领域层承担了传输层契约知识。

**建议修法**：在 AppService 内（或框架允许的 Request 上）补齐必填/空值/枚举校验；Manager 只保留查重、父级状态与归属、`ItemType` 变更限制等领域不变量；`Input(...)` 型消息回到应用层，`Business(...)` 型消息留在领域层。若框架已有统一 Request 校验机制，优先复用它而不是逐方法手写。

### M-1（中·Manager/实体职责）启停状态机不在领域对象里

**规范依据**

- `backend-command-query-event.md:87`：`Repository 可以实现锁定读取和并发控制；是否允许状态变化仍由 Domain 判断。`

**实际代码（三段证据）**

1) 幂等/状态判断写在 Manager：`Domain/.../MedicalRecognitionReportManager.cs:35-41`（分类启用；`:48`、`:79`、`:88`、`:119`、`:128` 同类）

```csharp
if (existing.IsValid) return true;
```

2) 实体没有任何状态方法：`Domain/.../MedicalStandardCategory.cs:7-37`（`MedicalStandardGroup.cs:7-37`、`MedicalStandardItem.cs:7-45` 同形）只有 `partial` 属性，`IsValid` 是公开可写数据位。

```csharp

```

`Repository/.../MedicalStandardCategory.xml:19`

```xml
update mrec_medical_standard_category set is_valid = true, oper_id = $OperId, oper_time = current_timestamp where id = $Id and is_valid = false
```

**为什么违反**：启停是「聚合状态流转」，规范把它归给 Manager/实体；当前 Manager 只做前置判断，真正的状态迁移由持久化层的 `UpdateAsync(Command)` 与 SQL 字面量 `is_valid = true/false` 完成，「是否已启用」这条只依赖单实体状态的规则也停留在 Manager。实体退化为纯数据载体，领域内不存在可复用的状态机：任何新增入口（批量启停、级联、导入）都必须重新拼一遍同样的判断与 SQL 意图。

**建议修法**：在实体上落 `Enable(auditInfo)` / `Disable(auditInfo)`（内部做幂等短路与 `IsValid` 赋值）与只读判定，Manager 调用实体方法后持久化**实体**；仓储签名从 `EnableMedicalStandardCategoryAsync(EnableMedicalStandardCategoryCommand)` 改为接收实体（或实体 + 操作字段），SQL 维持单条 UPDATE。若因生成器不能表达实体方法而必须保留现状，需在设计/生成物维护清单中把「状态机位于 Manager + SQL」登记为已确认例外并说明理由。

**规范依据**

- `backend-architecture.md:127`：`Repository 负责查询、锁、映射和持久化，不负责判断业务状态是否允许变化。特殊 SQL、并发策略和兼容语义必须有测试。`
- `backend-command-query-event.md:77`：`先读后写不自动要求事务。设计必须说明并发由数据库唯一约束、条件更新、版本检查、影响行数检查还是锁定快照兜底；……`
- `backend-architecture.md:173`：复杂查询块注释必须写清「做什么、为什么、最终结果」

**实际代码**

`Repository/.../MedicalStandardCategory.xml:19,22`（Group `:19,22`、Item `:19,22` 同形）

```xml
enable:  ... set is_valid = true,  ... where id = $Id and is_valid = false
disable: ... set is_valid = false, ... where id = $Id and is_valid = true
```

对应的写用例没有显式事务：`Application/.../MedicalRecognitionReportAppService.cs:40,50,80,90,120,130` 只有 `[WorkUnit]`（`UseTransaction` 默认假），即「先 `GetById` 判断 → 再条件 UPDATE」。因此这条 `and is_valid = …` 是唯一的并发兜底（另一处兜底是唯一索引）。阶段材料明确不做该验证：`Server/impl.md:20`：`并发范围：本 MVP 不实施专门锁定读、交错注入或并发启停测试。……低概率跨行竞态不作为本阶段业务承诺。`

**为什么违反**：规范把「并发策略必须有测试」写成 Repository 的硬性要求，本阶段以「低概率」为由取消测试，属于明文条款的主动偏离（且未登记为批准例外）。同时该 WHERE 在 XML 中没有任何注释：它有双重身份——领域前置条件（Manager 已判）与并发兜底（Manager 判不到的那部分），读者容易误认为 Repository 在替 Domain 做业务状态判断，而 0 行影响被 `Manager:40,49` 统一翻译成 `分类状态更新失败。`，与「并发下状态已被他人改变」的真实原因不一致。

**建议修法**（择一，并留证据）：① 按规范补一条并发用例（两个会话对同一行并发启停，断言恰好一次成功、另一次得到可区分的结果）；② 若负责人确认降为 `AcceptedRisk`，在设计中给出目标 Provider 上可实现的替代依据（如 `UPDATE … WHERE is_valid = false` 影响行数 + 唯一索引 + 单语句原子性），并在 XML 相邻位置用 `<!-- -->` 说明该条件的存在理由与失败语义；③ 0 行影响时区分「并发已变更」与「记录不存在」的返回语义。

**规范依据**

- `backend-architecture.md:132`：`共享 SQL/XML Statement 必须保持数据库 Provider 和版本中立，使用项目确认的公共 SQL 子集；不得包含绑定某一数据库、驱动或版本的类型、函数、分页语法（LIMIT/OFFSET、TOP）、空值排序（NULLS FIRST/LAST）、行值 COUNT(DISTINCT (...))、标识符写法、系统表、查询提示、类型转换、JSON 运算符或其他方言特征。`

- 设计闸门 `Server/design.md:185`：`……必须共同采用 Provider 中立的转义/谓词方式……实施首批次核实共享 SQL/XML 的可行写法；若公共 SQL 子集无法表达该语义，暂停相关实现并回到设计确认`

**实际代码**

`Repository/Queries/MedicalRecognitionReportQuery.xml:26`（`:27`、`:39` 同形）

```xml

```

`replace(...)` 与 `like … escape '!'` 可辩护为公共写法（`escape` 是 SQL 标准）；但 **3 参数 `concat(...)`** 不是所有目标 Provider 都能接受（Oracle 的 `CONCAT` 只接受 2 个参数，需 `||`）。仓库内找不到「项目确认的公共 SQL 子集」清单，阶段证据也只覆盖行为：`testReport.md:784`（`均使用 like ... escape '!' 转义`）、`决策与结论-20260915.md:143-144`（V49/V23 实测 `%`/`_` 未被当作通配符）。没有看到「该表达式属于公共子集 / 已核实 Provider 中立」的记录。

**为什么违反**：设计明确把「核实 Provider 中立」设为实施闸门，规范禁止共享 XML 出现方言特征；`concat` 的三参形态在未确认的子集内属于待证事项，当前处于「行为已验证、中立性未证」的状态。

**建议修法**：优先改为不依赖 `concat` 的公共写法（例如 `$Code` 与 `'%'` 用标准连接符或把 `%` 前缀/后缀放进参数），或在设计中补齐公共 SQL 子集清单并记录 `concat` 属该子集、覆盖哪些 Provider；二者都不成立时回到设计确认，必要时按 `backend-architecture.md:133` 在 Repository 内建 Provider 适配器。无论哪种，都要同时补上该查询块的 `<!-- -->` 原因注释（见 S-1）。

**规范依据**：`backend-command-query-event.md:65`：`查询必须定义范围、空值语义、稳定唯一排序和分页策略。`；`backend-architecture.md:172`（动态条件分支必须注释说明）

**实际代码**：`Repository/Queries/MedicalRecognitionReportQuery.xml:28`


`Application/Queries/MedicalRecognitionReportQueryAppService.cs:31` 把 `request.IsValid` 原样传给仓储，`Application.Contracts/Queries/MedicalRecognitionReportQueryContracts.cs:29` 声明 `public bool? IsValid { get; init; }`，设计对它的语义有明确要求（`Server/design.md:176`：`null 或未传时不过滤；IsValid = false 只匹配停用，不匹配 null`）。

**为什么记录**：`IsNotEmpty` 对**布尔 false** 的判定结果决定了「筛选停用」是否真的生效——若框架把 `false` 视为空值而不拼接条件，`IsValid=false` 会退化成「不过滤」。这一层语义无法只读 XML 判定（阶段自身已有同类教训：`决策与结论-20260915.md:31`「只读 XML 不足以判定层间语义，必须实测」），而现有证据恰好缺这一分支：`testReport.md:608` 记 `C14 标准项目新增完整矩阵 … 尚未执行其停用筛选分支`。同时该动态条件没有任何注释说明 null/true/false 三种语义。

**建议修法**：补一次真实查询证据（`IsValid=false` 只返回停用行、`true` 只返回启用行、`null` 不过滤），把结论写入矩阵；在 XML 该条件旁用 `<!-- -->` 写明三值语义。若实测发现 `false` 被跳过，则改为显式 `IsNotNull`/等价判断并回到设计确认写法。

### TS-1（低·测试证据）静态文本断言替代行为验证，并固化 SQL 字面量

**规范依据**：`backend-architecture.md:127`：`特殊 SQL、并发策略和兼容语义必须有测试。`；`backend-command-query-event.md` §4.2 要求区分「源码确认」与真实数据库/工作单元失败路径证据。

**实际代码**：`Tests/Stage1SqlMapProbeTests.cs:13-24`


`:153-164` 的 `FindRepositorySqlMap` 从 `AppContext.BaseDirectory` 逐级向上查找仓库**源码目录**中的 XML 文件（而非读取嵌入资源），`Stage1ArchitectureTests.cs:12-30` 则用反射断言 `WorkUnit` 标注。

**为什么记录**：这两类断言有真实价值（它们确实守住了事务声明与「请求不得提交 is_valid」），但它们是文本/反射级证据：既不验证 Manager 的领域规则（无单测、无仓储替身），也不验证 SQL 的行为语义；同时 `Assert.Contains("is_valid,")`、`Assert.DoesNotContain("$IsValid")`、`Assert.Contains("true", …)` 把 R-2 讨论的 SQL 字面量写法锁成契约，未来改回实体驱动会先撞测试。`FindRepositorySqlMap` 依赖源码树存在，在只发布产物或干净 CI 检出中会抛 `FileNotFoundException`。

**建议修法**：保留现有静态门槛，另给 Manager 增加带仓储替身的领域单测（幂等不登记事件、父级停用拒绝、分组归属不一致拒绝等），把「SqlMap 文本契约」改为读取嵌入资源并只断言与设计相关的结构（如不含方言关键字），避免锁定字段赋值形式。
