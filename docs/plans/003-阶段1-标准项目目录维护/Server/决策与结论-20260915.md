## 2. D1 落地细节与第 27 轮更正

第 26 轮按 D1 裁定把 [Server/design.md](design.md) 的入参边界改为「`null`/未传/空串/纯空白均不过滤」，依据是查询 XML 使用 `<IsNotEmpty>`。

**该依据不完整，结论错误，已在第 27 轮撤回并把文档恢复为原预期。** 实测（同一宿主 token 调用真实后端）：

| 入参 | 实际返回 |
|---|---|
| `code: null` | 完整集合（200） |
| 省略 `code` | 完整集合（200） |
| `code: ""` | `参数校验失败：编码不能是空白。`（500） |
| `code: "   "` | 同上 |

实现依据：`MedicalRecognitionReportQueryAppService.ValidateOptionalText` 显式拒绝空串与纯空白；`<IsNotEmpty>` 只影响是否拼接 where 条件，不能代表入参校验行为。**教训：只读 XML 不足以判定层间语义，必须实测。**

结论：V39 的**原始预期成立**，`null`/未传不过滤、空串/纯空白被拒绝；**代码无需改动**。客户端 `allowClear` 清空后不发送该字段、`filterItems` 本地过滤把空串视为不过滤，因此页面不会触发该拒绝。

### 3.5 与设计文字的一处澄清（非缺陷）

[Server/design.md](design.md) 的 V30 描述文字提到「三个实体全部字段」并列举 `MedicalItemType` 按 `Laboratory=0`、`Examination=1` 存取，容易被读成「`item_type` 是三表共有列」。实际设计正文第 381–383 行的列表定义中，**`item_type` 只属于分类表**；项目列表查询的 `item_type` 由 `join mrec_medical_standard_category c` 取得（见 `MedicalRecognitionReportQuery.xml`），分组表也没有该列。

本次只读核对确认库中不存在 `item_type` 的冗余存储，且「项目分类等于所属分组分类」的完整性检查为 0 例外，说明类型一致性由归属约束保证。该点按设计本意记录，不需要改库或改代码。

## 4. D5 事件登记方式一致性核对

负责人的要求是「保证添加事件的方式与 LisCenter 项目一致」。核对结果：

| 维度 | `Dy.LisCenter\server` | 本项目 | 一致 |
|---|---|---|---|
| 事件基类 | `public partial record XxxEvent : DomainEvent`（`[IPropertyChangedAware]`） | `public record XxxEvent : DomainEvent` | 是 |
| `AggregateId` | `override` 返回聚合常量 | `override` 返回 `MedicalRecognitionReportConst.AggregateId` | 是 |
| `EventType` | `nameof(XxxEvent).RemovePostFix("Event")` | `nameof(XxxEvent)` | **语义等价** |
| 事件工厂 | `Command` 上的 `CreateXxxEvent(...)` | `Command` 上的 `CreateXxxEvent(...)` | 是 |
| 登记位置 | 领域实体内 `this.AddEvent(command.CreateXxxEvent(...))` | 领域实体内 `AddEvent(command.CreateXxxEvent(...))` | 是 |
| 登记时机 | 规则通过并写入成功后登记 | 同 | 是 |

`EventType` 的差异说明：本项目事件类型名本身不含 `Event` 后缀参与取值也无影响——两侧都通过 `nameof` 取类型名再去掉/不带 `Event` 后缀，对外语义都是「事件短名」。`RemovePostFix` 在本项目下与直接 `nameof` 结果相同，属等价写法，**不需要修改**。

结论：事件登记方式与 LisCenter 一致，V56 按 `N/A` 结案，事件队列语义（登记后是否持久化/消费）作为残余风险登记，待后续需要读事件表的阶段一并验证。

### 6.2 已裁定的契约差异

**D7：V48「类型缺失应被拒绝」与实现不一致 → 负责人裁定采用方案一。**
V48 原预期包含「类型缺失」须被拒绝。实测 `itemType` 为可空枚举参数，**不传时默认 `0`（Laboratory）并创建成功**（探测记录 `S1-V48-PROBE-20260915`）；仅当传入未定义枚举值（如 `7`）才被拒绝。

- 争点：`0` 是合法枚举值，无法与「未传」区分，属设计取舍。
- **裁定（2026-09-15）**：采用方案一——未传按默认 `Laboratory=0` 处理，不要求类型必填；仅未定义枚举值拒绝。已同步 [Server/design.md](design.md) 的 V48 预期；**无需改契约、客户端或重新生成**。
- 探测记录 `S1-V48-PROBE-20260915` 已按「不删除、全部停用」的裁定停用。
