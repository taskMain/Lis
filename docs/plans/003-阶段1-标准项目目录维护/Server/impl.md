## 新建表交付与暂停点

平台尚未建库表，`DysoftHIS` 无前缀三表不是平台既有或共享对象。本阶段只交付三张独立 `mrec_medical_standard_category/group/item` 表的新建定义，不迁移、重命名、复制旧表或旧数据，不交付旧列转换、旧注释迁移及其回退脚本。

1. 实施侧交付三份新建 DDL，按 S1-D30 固定列序并补齐表/列数据库注释，直接使用 `boolean` 与 `timestamptz`；字段、类型和可空性按后端设计核对，其他模块表随所属阶段处理。
2. 除主键外，DDL 包含分类 `name`、分组 `category_id/name`、项目 `code` 三条全行唯一索引，覆盖停用对象。不沿用旧表 14 索引例外，不复制无关索引或新增未确认约束。
3. 物理表名通过本模块 SqlMap 显式引用，沿用已核对的 LisCenter 声明模式；不改实体名、逻辑 Scope/sqlId，不新增映射特性或全局映射器。V57 检查新建 DDL 与全部 SQL 引用的一致性。
4. 请求负责人执行前明确目标库/schema、脚本范围与名称占用；发现同名其他系统对象时暂停并报告，不静默跳过、删除或改名。目标库表未建成前，仅依赖其结构的数据库读、写验证受阻；独立实现、脚本准备及契约/静态检查可继续。
5. V30/V58 在负责人另行授权并确认建表的受控库分别验证真实持久化与 DDL 元数据，不等待目标库先建成。V30 使用正常业务路径准备数据并回读归属完整性，异常交负责人裁决，不自动修正数据。受控库结果不能冒充目标库已建成；目标库验证须有该环境执行确认。
6. V55 随旧类型迁移方案退役，不复用编号、不转记通过；有效矩阵为 56 条。V28 的 325 条只是独立测试样本，不代表已有平台数据。正式未执行验证保持 `NotRun`，前置实际受阻时按规范记 `Blocked`。

## 生成物维护方式

本阶段的改动跨越「生成物骨架」与「有意手工修改」两类，实施时须分别处理并在再生成后核对：

| 改动 | 维护方式 |
|---|---|
| 仓储调用点改为显式传 `scope:` | 手工修改；再生成后必须核对恢复 |
| SqlMap `Scope` 改为实体名 | 手工修改；再生成后必须核对恢复 |
| 实体公共属性顺序（`OperTime` 在 `OperId` 前） | 优先在生成源表达；若生成器不能表达，则列入受保护手工修正清单，并在再生成后核对实体、SqlMap 参数/结果列与 DDL 的 `oper_time → oper_id` 顺序 |
| ReadModel 契约修正（`Remark` 可空、`UsageStatus` 新增、层级集合嵌套） | 有意改变契约，属受保护手工修改清单 |
| 分类/分组/项目备注的整份修改契约（S1-D26） | 更新分组 Request/Command 移除 `CategoryId`；查重和事件从已有分组取所属分类，XML 不更新 `category_id`。分类更新只对类型变化检查下级；备注直接赋值（含 `null`），不增加省略保留或无变更短路；重生成后核对 Request→Command→SQL→读回及操作字段/事件 |
| 领域规则、查询仓储、查询端口与内部投影 | 本阶段新增 |
| 公开查询服务契约与实现关系 | 新增 Contracts/Queries 的 `IMedicalRecognitionReportQueryAppService`，由 Application 查询类实现；四方法签名及本模块 ReadModel 目录归属按后端设计对齐，V26/V53 核对，不追加到写服务或扩展内部 Manager 接口 |
| AppService 的 `WorkUnit` 标注 | 手工修改 |
| 三表新建 DDL、唯一索引与 SqlMap 物理表引用 | 按 S1-D30 列序/注释及已确认 mrec_ 新表命名；能由生成源表达则固化生成源，否则列为受保护人工修正并在再生成后复核。保留新建唯一索引和显式 SQL 表名，不修改实体名、逻辑 Scope/sqlId，不生成旧表迁移或复制方案 |
| 其余生成骨架 | 按生成物管理；再生成前先确认生成器对已手工修改文件的行为（拒绝、覆盖或要求恢复），不得概括为「重跑一律覆盖」 |
