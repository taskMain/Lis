### 1.2 阶段推进规则

1. 同一时间只推进一个阶段，不并行开两个阶段。
2. 推进下一阶段前核对前一阶段的适用收口证据及负责人确认：具体实现阶段使用根 `testReport.md`；纯规范阶段只有经确认的替代证据可用，阶段 0 按 S0-D1/S0-D3 使用其 `impl.md`，不补造测试报告。已有记录或后续设计文档不代表前阶段已获验收批准，也不自动授权正式实施。
3. 每个阶段开始时，先按阶段模板创建本阶段文档并在 [阶段计划](../README.md) 入口表登记。
4. 阶段范围发生变化时，先更新该阶段 `design.md` 再实施，不在实施中悄悄扩大范围。

## 2. 通用执行规则

### 2.1 阶段开始前的固定动作

1. 执行 Git 工作区状态检查，保护既有修改，不回退非本阶段内容。
2. 确认本阶段涉及的实体、表、接口与既有生成物的对应关系。
3. 确认本阶段的前置阶段已收口。

### 2.2 后端先行

1. 先稳定后端契约与领域规则，再生成 API Client，最后实现前端页面。
2. 修改既有代码符号前完成上游影响分析；新增符号按项目规范处理。
3. 行为变化先取得准确失败测试再实现；等价重构先建立通过基线。
4. 写操作的事务边界、操作人注入与时间来源按项目后端规范执行，不在前端补偿。

### 2.3 独立建表与初始化

1. 本平台尚未建立数据库表。初始化前由负责人确认目标数据库与 schema，开发过程负责产出与核对最终 DDL 和物理表映射；建表由**项目负责人执行**，收到完成确认后继续依赖新表的集成测试。
2. 全平台 19 表按 [Project Context](../../../.agents/instructions/project-context.md)「本项目 DDL 脚本规则」统一最终格式，仍按业务阶段实施：阶段 1 只处理 3 表，后续 16 表随所属阶段处理，不预建、不另开横向治理阶段。
3. S1-D30 已确认的 CREATE 列顺序为 `id`、按 UML 顺序的业务列、保持 UML 相对顺序的生命周期状态标志、`oper_time`、`oper_id`；按语义识别是否作废/逻辑删除/启用等标志，不机械移动所有 bool。表/字段中文注释依 UML，公共字段补“主键ID、操作时间、操作人”，随新建最终 DDL 交付；不重排、重建既存对象或向其提交注释迁移。
4. 数据库写操作与连接凭据按环境规范处理，不在文档中记录凭据。
5. 用户已确认全平台独立新建 `mrec_` 加已选业务基础表名的物理表，当前三表保留现有脚本基础名，不改实体名/SqlMap scope/API 名；实体与表通过 SqlMap 显式对应，不强制命名推导或机械保留 `Entity` 后缀。[阶段 1 设计](../003-阶段1-标准项目目录维护/design.md) S1-D31 原候选前缀及共享表切换待定口径被覆盖。历史无前缀三表归属未确认，旧复用/迁移、整型布尔转换和保留其 14 个索引的方案不再执行；不改名、复制或修改其他系统对象及数据。
6. 建表前核对所属阶段 UML 顺序、中文注释、所需索引与约束及物理表映射，建表后核对实际结构和注释；不继承历史三表索引，不因格式整改扩改字段结构或数据类型。连接配置保持不变，同库不等于同表，也不代表初始化目标已获批准。

### 2.4 SqlMap 与仓储

1. 每个业务阶段只修正本模块涉及的 SqlMap 与 Repository，不批量重构其他模块。
2. 阶段 1 已按 S1-D1/S1-D2 选定显式 `scope` 与业务化 `sqlId`、不调用 `SetContext` 的方案，尚待运行验证；后续模块只沿用已验证结论，不把聚合作用域的候选根因当成事实。
3. 修正后必须用真实调用验证到达业务层，不能只凭构建通过。

### 2.5 Kiota 与 API Client

1. 每个阶段在后端契约稳定后，按 [Frontend API Client](../../../.agents/instructions/frontend-api-client.md) 的公共规则，以同一包“已交付范围 + 本阶段稳定契约”累计选择 tag/path/operationId 并按需重生成，保留已交付接口，不提前生成后续功能。下文各阶段的“本模块生成”均指纳入本阶段稳定契约，不替换累计范围；已暴露或已有生成骨架不等于已交付。
2. 生成前核对已交付接口清单和本阶段稳定契约；重生成后按累计范围核对已交付接口保留、未提前纳入后续功能、登录接口排除规则保留、`kiota-lock.json` 指向包内稳定 OpenAPI、入口导出完整、无退化类型。
3. 重生成会覆盖 `src/` 下的手写入口文件，生成后必须核对并恢复手写内容。
4. 前端不在页面中直接扩散生成的 Kiota 类型，统一经子应用的 API Client 上下文访问。

### 2.6 前端后置

1. 页面实现前先建立稳定 API 适配层。
2. 不新增业务错误类型、错误拦截器、响应处理器或绕过框架的错误提示。
3. 路由与页面必须与宿主菜单入口一致。

### 2.7 阶段测试与报告

1. 具体实现阶段的后端测试前矩阵写在 `Server/design.md` 的验证矩阵章节；前端矩阵写在 `Client/testPlan.md`；不为阶段 0 创建空端文档。
2. 具体实现阶段的实际执行命令、结果、证据与残余风险只写阶段根 `testReport.md`；阶段 0 按 S0-D1/S0-D3 写入其 `impl.md`，不建测试报告。
3. 测试状态使用统一枚举，未执行项填 `NotRun`，前置受阻填 `Blocked`。
4. 页面能力必须从宿主登录页与宿主菜单进入验收；本地直达、接口直测与构建成功不能替代。

### 2.8 阶段收尾

每个阶段收尾执行适用测试、构建、静态检查、差异检查；具体实现阶段更新阶段根测试报告，阶段 0 更新其 `impl.md` 替代证据，并在 [阶段计划](../README.md) 入口表按实际证据更新状态。记录存在不等于负责人已批准收口或验收。

报告列表、历史版本列表、版本详情与 PDF 下载页面与路由，按权限与数据归属控制，宿主链路验收。

### 7.5 阶段内规则

1. 完整报告提交的事务语义（结构化内容与 PDF 共同成功或共同失败）在本阶段内按设计实现，不依赖生成器扩展。
2. 建表由项目负责人按批次执行，不在批次一一次性建完全部 10 张表，以免后续批次设计变更导致返工。
3. PDF 文件处理依赖文件服务配置；该配置不可用时只暂停受影响验证。

## 8. 阶段 5 在线互认主流程（F04+F05+F06+F07）

**本阶段为纯后端阶段，不创建前端页面文档与实现。**

1. **F04 互认匹配查询**：按患者身份与拟开项目编码匹配、编码整批校验与去重、候选报告筛选、最近有效报告选择、联合报告分组、匹配记录与匹配项生成、无匹配返回空结果。
2. **F05 互认处理结果**：整组原子保存、不可更改语义、不采纳原因与补充说明校验、按接收方当前金额计算预计节省金额、幂等与冲突判定。
3. **F06 获取引用详情**：引用详情有效期控制、采纳前提与版本有效性校验、项目内容与报告公共上下文返回。
4. **F07 提交引用结果**：按匹配项定位、跨匹配记录整批原子保存、实际引用时间与科室医生记录、幂等与冲突判定。
5. **数据**：创建 `mrec_recognition_match_record`、`mrec_recognition_match_item`、`mrec_recognition_processing_result`、`mrec_recognition_reference`，由项目负责人按第 2.3 节执行。
6. **API Client**：本阶段接口为医院接入契约，阶段末按实际需要重生成，供医院侧联调使用。
7. 本阶段依赖阶段 4 已采集的报告数据，按串行口径推进，不提前造数据。

## 9. 阶段 6 互认统计与导出（F08+F09）

1. **后端**：实现接收侧与来源侧汇总、明细下钻、同期互认率、预计节省金额、不采纳原因汇总，以及按当前查询条件、数据权限与脱敏规则的 Excel 导出。
2. **数据**：无新表。
3. **API Client**：按本模块范围重生成并验证。
4. **前端**：实现「接收医院互认使用统计」「来源医院被互认统计」「统计导出入口」，以及只读的查看互认匹配记录入口；宿主链路验收。
5. 导出格式仅 Excel，查询条件与脱敏规则继承 F08，不重复设计。

## 10. 阶段 7 横向治理与发布收口

1. **跨模块一致性核对**：患者信息脱敏、页面数据权限、可信组织范围校验在全部页面与接口上的一致性；发现不一致时按最小修复处理，不做重构。
2. **排除项回归确认**：逐条确认 SRS 的排除项与设计约束中的不建设内容未被实现。
3. **发布前全量联调与证据收口**：宿主链路全量回归、各阶段证据汇总、残余风险登记、阶段入口表收口。
4. **本阶段不新增业务功能、不做重构式治理。**
5. **不单设代码审查阶段**：代码审查按需在各业务阶段内进行，结论写入该阶段根 `testReport.md`；本阶段只做跨模块一致性、排除项回归与发布收口三类事。
6. **发布收口判定**（开始时冻结，执行中不得放宽）：冻结本轮矩阵版本与分母（各阶段现行矩阵用例之和 + 本阶段新增用例）；只把 `Passed` 与经范围确认的 `N/A` 计入完成，存在 `Blocked`/`NotRun`/`PendingRetest` 即不构成干净轮次；发布结论只输出 `Ready`/`ReadyWithAcceptedResiduals`/`NotReady`；收口前核对宿主全链路回归、上游依赖与外部服务健康、测试数据余量、端口与进程边界、起始提交与工作区快照。判定条件全文见 [总体计划设计](design.md) 4.9。
