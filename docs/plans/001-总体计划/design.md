# 总体计划设计

本文确定本项目的阶段划分、计划原则、阶段边界与前后端协作口径。业务事实以 SRS、UML 和 `CONTEXT.md` 为准，本文不复制业务规则；环境值引用 [Test Environment](../../../.agents/instructions/test-environment.md)，不在本文重复维护。

阶段入口见 [阶段计划](../README.md)。本文配套的实施任务与执行顺序见 [总体计划实施方案](impl.md)。

## 1. 背景与当前基线

### 1.1 业务范围

平台业务由 SRS 的 F01–F10 十个功能构成（SRS `产品功能` 表）。其中 F04 查询互认匹配、F05 提交互认处理结果、F06 获取引用详情、F07 提交引用结果四者被 SRS 共同定义为面向医院 HIS 的**在线互认主流程**；报告采集、身份认证、互认项目配置、报告更正或作废不计入该四类核心能力（SRS `产品功能` 章末段）。

使用端划分为两类，依据 SRS `接口` 章：

| 端 | 内容 | SRS 依据 |
|---|---|---|
| 管理端页面 | 「用户界面」章的 9 个界面节；其内部支撑能力由 F01、F02、F08、F09、F10 及「用户界面」章规定，**不作为医院接入契约** | SRS `接口` 章首段 |
| 医院接入接口 | 检验与检查完整报告提交、两类报告作废、互认匹配查询、互认处理结果提交、引用详情获取、PDF 文件下载、引用结果提交，共 9 项 | SRS `医院接入接口` |

SRS 另有 23 条明确排除项与设计约束中的多项不建设内容，阶段设计与验证不得纳入这些能力。

### 1.2 仓库当前状态

| 项 | 状态 |
|---|---|
| 后端 | 已由 `dy-codegen` 从 `docs/uml/` 确定性生成六个项目（PostgreSQL 方言），可 restore、build、test；可启动并暴露 OpenAPI |

### 1.3 已观测阻断与待验证解释

以下保留历史观测，不作为全部失败原因的穷尽结论；阶段 0 另记录的三表类型差异属于归属未确认对象，不是本平台迁移依据。

1. **SqlMap 语句解析失败**：带合法 token 调用写接口返回 500，异常为 `Can not find Statement. FullSqlId:MedicalRecognitionReport.CreateMedicalStandardCategory`。

   生成物的实际形态：19 个 Earthrace SqlMap 文件**共用同一个 `Scope="MedicalRecognitionReport"`**（聚合级作用域），实体之间靠 `Statement Id` 前缀区分，共 54 个语句（19 个 `<X>Columns`、19 个 `QueryAll<X>`、16 个写语句）；其中只有 4 个文件含写语句（`MedicalStandardCategory`、`MedicalStandardGroup`、`MedicalStandardItem`、`MutualRecognitionItem`），其余 15 个文件只有 `XColumns` 与 `QueryAllX`。Repository 侧只有一个 `MedicalRecognitionReportRepository`，对 4 个实体提供写方法并统一 `SetContext("MedicalRecognitionReport")` 且显式传入 `sqlId`，其余 15 个实体没有任何仓储方法，也没有任何查询方法。

   已确认的是**给定查找键找不到语句的现象**，聚合作用域只是候选解释，不能因多个实体共用作用域就断定必然失败。当前按阶段 1 S1-D1/S1-D2：本模块写入 SqlMap 使用实体名作用域，每个 `DataMapper` 调用点显式传 `scope`，保留业务化 `sqlId`，不调用 `SetContext`、不按实体拆仓储类。实施首批次核对实际查找键与已注册语句键；探测不支持候选解释时暂停相关修复并修订设计。后续模块仅沿用经本项目运行验证的结论，不沿用已被替代的历史推论。

2. **数据库表尚未建立**：历史盘点记录 `Scripts/*.sql` 未执行，19 个脚本与 19 个实体一一对应（当时表名与文件名一致，为实体名的 snake_case 派生）；按这些无前缀名称查询时，仅发现 `medical_standard_category`、`medical_standard_group`、`medical_standard_item` 三张。2026-09-11 用户澄清这些是归属未确认的既存对象，本平台尚未建表，原“3/19 已建”推断被覆盖；历史查询结果不改写为新查询。

**处理口径**：不单独设立横向整改阶段。SqlMap 随各业务阶段在本模块范围内修正；平台表按模块独立新建。原三表复用/迁移、整型布尔转换和保留其 14 个索引的计划均被用户澄清覆盖，不再执行；不修改其他系统对象或数据。

## 2. 目标

1. 按 SRS 的 F01–F10 分阶段交付可验收的业务能力，每个业务阶段自成一个最小业务闭环。
2. 每个业务阶段自带本阶段的代码范围与建表批次，不跨模块改动，不形成横向整改阶段。
3. 每阶段的交付顺序固定为：后端契约稳定 → 重生成 API Client → 前端页面（若该阶段含管理端页面）。
4. 页面能力必须通过宿主登录页与宿主菜单进入验收，不以本地直达、接口成功或构建成功替代。

## 3. 计划原则

### 3.1 阶段按业务模块切分，不按代码结构切分

阶段边界等于业务模块边界。一个阶段是"某个业务能力端到端可用"，不是"某一层或某一类技术债处理完"。以代码层、基础设施或技术债为主题切分阶段，会把阶段性工作膨胀成跨越多个模块的整改，使具体业务迟迟无法推进。

### 3.2 建表按模块分批，与所属阶段同步落地

平台数据库表随所属业务阶段独立新建，不由某个统一阶段集中建表。每个业务阶段只处理本阶段模块的脚本，不预建后续阶段的表；实际初始化须先确认目标数据库与 schema，再由负责人执行最终 DDL。

全平台 19 表的最终脚本统一遵循 [Project Context](../../../.agents/instructions/project-context.md)「本项目 DDL 脚本规则」：S1-D30 已确认 `id` 第一、业务列按 UML 顺序、生命周期状态标志按 UML 相对顺序放到操作字段前，最后 `oper_time`、`oper_id`；不把所有 bool 移尾。表/字段中文注释依 UML，未画公共字段按“主键ID、操作时间、操作人”补齐。顺序与注释落实到独立新建的 CREATE 及最终 DDL，不对归属未确认对象重排列、补注释或做类型转换；新表所需索引与约束按阶段契约明确，不继承旧三表索引，不因格式整改扩改字段结构或数据类型。

用户已确认平台独立新建，物理表名为 `mrec_` 加已选业务基础表名，不强制与实体名完全一致，不改实体名、SqlMap scope 或 API 名；[阶段 1 设计](../003-阶段1-标准项目目录维护/design.md) S1-D31 原候选前缀及共享表切换待定口径据此被覆盖。当前三表保留现有脚本基础名，下文后续表名作为各阶段设计基线。实体与表通过 SqlMap 显式对应，不从实体名或 `Entity` 后缀机械推导。阶段 1 只建 3 表，后续 16 表按原所属阶段落实；连接配置不变，同库不等于同表，不改名、复制或迁移历史三表，不另开横向治理阶段。

### 3.3 已知阻断随各模块阶段各自解决

SqlMap 与仓储的显式作用域对齐、以及本模块独立建表，都在对应业务阶段内完成，不抽成独立阶段。只有该阶段涉及的实体需要在本阶段内改对；不要求一次性修正全部 19 个实体。

### 3.4 跨模块依赖串行

存在真实依赖的模块按依赖顺序串行推进，不并行、不合并成大阶段，也不为下游阶段提前造数据。已确认的串行关系：F03 报告采集与生命周期先于 F04–F07 在线互认主流程；F01 标准目录先于 F02 互认配置，F02 先于 F10 金额维护。

### 3.5 阶段内后端先行

每阶段先稳定后端契约，再重生成 API Client，最后实现前端页面。前端不得在契约稳定前扩散 Kiota 生成类型。

### 3.6 API Client 每阶段按需重生成

每个业务阶段在后端契约稳定后按需重生成 API Client；同一客户端包按“已交付范围 + 本阶段稳定契约”累计选择 tag/path/operationId，保留已交付接口，不提前生成后续功能。各阶段所称“本模块生成”均受 [Frontend API Client](../../../.agents/instructions/frontend-api-client.md) 的公共累计规则约束，不表示以本阶段范围替换整个包。当前后端已暴露接口与前端已生成内容不代表业务契约稳定或已交付。

### 3.7 质量内建

新功能与行为变化先取得失败测试再实现；具体实现阶段的后端测试前矩阵写在 `Server/design.md` 的验证矩阵章节，前端矩阵写在 `Client/testPlan.md`，实际执行结果统一写入阶段根 `testReport.md`。阶段 0 为纯规范阶段，按 S0-D1/S0-D3 使用其 `impl.md` 记录验证证据，不建测试报告。测试状态只使用统一枚举定义，无实际证据不得写为通过。

### 4.2 阶段 0：现状对齐

**定位**：进入实际开发前的基线确认阶段，不实现业务功能，不修改业务代码。

**对齐范围**：后端项目结构与包依赖、应用契约与请求模型、应用服务事务边界与操作人注入、领域聚合与状态规则、仓储与 Earthrace XML/SQL 脚本、外部依赖边界；API Client 的 OpenAPI 固化位置、`kiota-lock.json`、登录接口排除规则、入口导出、退化类型与空壳模型风险；前端微前端接入、运行时配置、路由与页面缺口；工作区未提交变更说明。

**方法**：把差距按后续阶段归属，不在本阶段内修复业务代码。

**输出物**：各端现状结论、构建与静态验证结果、工作区变更说明、后续阶段处理建议，按 S0-D1/S0-D3 记录于阶段 0 `impl.md`。当前已有实施与验证记录，不再记为未开始；记录存在不等于负责人已批准收口或验收。

**不处理范围**：不修改后端业务代码、不重新生成 API Client、不新增前端业务页面、不调整数据库脚本内容、不提交代码。

### 4.3 阶段 1：标准项目目录维护（F01）

**范围**：平台统一的标准医疗项目类型、分类、分组与标准项目维护，以及当前有效标准目录。

**为什么最先做**：标准目录是后续互认配置的基础，且命令已进入生成范围，适合作为首个业务闭环；仍需独立新建本模块 3 表，补齐领域规则、查询、页面与真实验证，并完成本模块 Repository/SqlMap 修正。阶段 1 同时验证已选定的修法，后续模块只沿用经验证的结论。

**数据库范围**：独立新建 `mrec_medical_standard_category`、`mrec_medical_standard_group`、`mrec_medical_standard_item`，按 S1-D30 整理最终 CREATE、中文注释及本阶段所需索引与约束，不处理后续 16 表。不复用无前缀三表，不执行其类型转换、数据迁移、索引继承或注释迁移，不改变其他系统对象及历史数据。

**初始化放行**：连接配置保持不变，但不能由同库配置推断表归属或初始化目标已批准。先由负责人确认目标数据库与 schema，核对本阶段最终 DDL 和物理表映射仅指向平台独立表，再由负责人执行。收到初始化完成确认前暂停依赖新表的集成测试；不依赖初始化的设计与静态核对可继续，不操作其他系统数据。

**当前进度**：A2 页面形态已获设计确认，整体设计仍待审查通过，正式实施未开始；原型证据不等于真实 API 或宿主验收。

**端**：跨端。管理端页面为「互认项目分类分组管理」与「标准医疗项目管理」。

### 4.4 阶段 2：标准项目互认配置（F02）

**范围**：按组织选择当前有效标准项目，维护可互认时间与互认配置启停状态。

**前置**：阶段 1 完成，标准目录可用。

**建表**：`mrec_mutual_recognition_item`。

**端**：跨端。管理端页面为「互认项目管理」。

### 4.5 阶段 3：互认项目金额维护（F10）

**范围**：平台管理员与医院管理员在权限范围内维护组织、医院、院区、标准项目对应的当前金额。

**前置**：阶段 2 完成，组织级互认配置可用（金额查询只返回组织级互认配置已存在的标准项目）。

**建表**：`mrec_organization_hospital_branch_recognition_amount`。

**端**：跨端。管理端页面为「互认项目金额维护」（平台管理员，按请求提交的组织、医院、院区维护）与「本院区互认项目金额」（医院管理员，组织与医院取自可信上下文、只选择院区）两个页面。第二个页面由阶段 3 按 F10 参与者划分确定，见阶段 3 决策 S3-D1。

### 4.6 阶段 4：报告采集与生命周期（F03）

**范围**：检验报告与检查报告的完整提交、独立作废、完整版本保存，以及管理端受权限控制的只读历史版本查看与 PDF 下载。含 F03.1 作废、F03.2 检验报告采集、F03.3 检查报告采集三个子节。

**这是本项目工作量最大的阶段**：涉及 10 个实体、完整报告提交的 Facade 事务语义、患者身份解析与核对、来源端身份与报告时间规则、PDF 文件处理，以及报告管理页面。命令侧当前被生成器局部阻断（Facade、复杂入参、非标准 CRUD），本阶段内需要按设计补齐。

**前置**：阶段 3 完成。

**建表**：`mrec_platform_patient`、`mrec_medical_recognition_report`、`mrec_medical_report_version`、`mrec_laboratory_report_content`、`mrec_laboratory_result_item`、`mrec_laboratory_bacteria_result`、`mrec_laboratory_antimicrobial_susceptibility`、`mrec_examination_report_content`、`mrec_examination_item`、`mrec_examination_site`，共 10 张。

**端**：跨端。管理端页面为「报告管理与历史版本」。

### 4.7 阶段 5：在线互认主流程（F04+F05+F06+F07）

**范围**：SRS 定义的医院 HIS 在线互认主流程四类核心能力——互认匹配查询、互认处理结果提交、引用详情获取、引用结果提交。含匹配查询的项目去重、最近有效报告选择与联合报告分组，处理结果的整组原子不可更改保存与预计节省金额，引用详情有效期控制与身份核对，以及实际引用事实记录。

**前置**：阶段 4 完成。本阶段依赖阶段 4 已采集的报告数据，按阶段 3.4 串行口径推进，不提前造数据。

**建表**：`mrec_recognition_match_record`、`mrec_recognition_match_item`、`mrec_recognition_processing_result`、`mrec_recognition_reference`。

**端**：纯后端，不建 `Client/`。SRS 明确医院 HIS 界面不在平台建设范围（SRS `医院 HIS 界面边界`）。

**本阶段不包含**：`GetRecognitionCitationDetailApi` 之外的 HIS 侧页面、影像与 PDF 的院内呈现实现、危急值处理、PushCenter 推送。

### 4.8 阶段 6：互认统计与导出（F08+F09）

**范围**：提醒、采纳、不采纳、引用、同期互认率、预计节省金额、接收医院使用与来源医院被互认分析，以及按当前查询条件、数据权限和脱敏规则导出汇总与明细。导出格式**仅 Excel `.xlsx`**。

**为什么合并 F08 与 F09**：F09 的查询条件、数据权限与脱敏规则完全继承 F08，独立成阶段会产生同一批查询对象的反复修改。

**前置**：阶段 5 完成，处理结果与引用事实已落地。

**建表**：无新表，统计事实来自既有实体。

### 4.9 阶段 7：横向治理与发布收口

**范围**：只做三类事，不做新业务功能，不做重构式治理。

1. **跨模块一致性核对**：患者信息脱敏、页面数据权限、可信组织范围校验在全部页面与接口上的一致性。
2. **排除项回归确认**：SRS 的 23 条排除项与设计约束中的不建设内容，逐条确认未被实现。
3. **发布前全量联调与证据收口**：宿主链路全量回归、阶段证据汇总、残余风险登记。

**为什么需要它**：脱敏、数据权限、组织范围是天然横向、无单一模块归属的规则；23 条排除项也需要一次集中回归。若散进各业务阶段，会让每个阶段都背上"顺带核对全平台一致性"的负担，正是原则 3.1 要避免的臃肿；若不排，则这些规则无人负责、无证据可查。

## 5. 前后端协作边界

1. **后端**负责领域规则、事务边界、契约稳定性、数据权限与组织范围校验。
2. **API Client** 由 Kiota 从后端 OpenAPI 生成，每阶段在后端契约稳定后按 3.6 的累计范围按需重生成，保留同一包已交付接口；`/auth/login` 始终排除；`kiota-lock.json` 指向包内稳定 OpenAPI。
3. **前端**通过子应用本地 API Client 上下文访问后端，不在页面中直接扩散生成类型；不新增业务错误类型、错误拦截器或绕过框架的错误提示。
4. **联调顺序**：后端契约稳定 → API Client 生成与构建 → 前端页面实现 → 宿主链路验收。
5. **权限**：菜单与接口授权由权限系统负责，本项目不重复建设角色授权模型，但仍保护数据归属范围。
6. **业务人员标识**：医院业务请求中的科室与人员 ID 为字符串，名称随请求保存，不要求存在于平台权限系统，不按 ID 补查或覆盖业务名称。

## 6. 质量与验收口径

1. 行为变化先取得准确失败测试再实现；等价重构先建立通过的特征或契约基线。
2. 具体实现阶段的后端测试前矩阵在 `Server/design.md` 的验证矩阵章节；前端矩阵在 `Client/testPlan.md`；实际执行命令、结果、证据与残余风险只写阶段根 `testReport.md`。阶段 0 按 S0-D1/S0-D3 以 `impl.md` 为替代证据，不要求补建报告。
3. 页面能力必须从宿主登录页与宿主菜单进入，核对页面、DOM、Console、Network 与最终业务状态；本地直达、Scalar、接口直测与构建成功都不能替代宿主验收。
4. 测试状态使用统一枚举定义，无实际证据不得写为通过。
5. 每阶段收尾执行适用测试、构建、静态检查与差异检查；具体实现阶段更新阶段根测试报告，阶段 0 更新其 `impl.md` 证据。证据齐备与负责人批准收口须分别确认。
