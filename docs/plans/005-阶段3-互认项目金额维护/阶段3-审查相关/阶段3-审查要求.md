# 阶段 3 文档审查要求

本文件写给**执行审查的 AI 代理**。它是一份自包含的任务说明：你没有本项目的历史上下文，所有事实必须从仓库原文取得，不得从本文件或任何阶段文档的**摘要**里取事实。

---

## 0. 两条硬性要求（先读，违反即本次审查无效）

### H1 写入审查结果前必须先清空结果文档

**你的结果文档路径由负责人另行指定，不要在仓库中自行挑选或新建路径。** 本文件与项目中的任何文档都不替你决定它；若负责人未指定，**在开始审查前先询问**，不要自行假设。

**写入本轮结果前，必须先清空该文档中的全部上一轮内容，再写入新的审查结果。** 不得追加、不得在文末追加"本轮新增"、不得保留任何历史轮次章节、表格或结论。做法：先读取该文件确认其当前的完整内容 → 再用**整体覆盖**的方式写入本轮结果（不是 edit 追加）。若指定文件尚不存在，按指定路径创建。

理由：多个审查方并行工作时，残留的上一轮结论会与新一轮结论混在一起，无法分辨哪条对应当前版本的被审文档。

**结果文档不承担整改追踪。** 结果文档只报告你查到的问题，不写「已整改」「已修复」「上轮遗留」「当前状态」之类的栏目或结论；整改是否进行、进行到什么程度不在文档中体现，你也不必为整改情况负责或预留位置。

### H2 审查范围不包含审查工作目录

**本阶段的审查工作目录整体不在审查范围内。** 审查工作目录指负责人为本次审查指定的目录（通常就是你的输出目录），以及本阶段目录下任何名为 `审查相关/`、`阶段3-审查相关/` 的目录及其全部子目录。

- 不得把审查工作目录下的任何文件当作审查对象；
- 不得把其中的任何文字（包括本文件、其他审查方的要求与结果）当作事实依据或结论依据；
- 不得据其中的内容反推被审文档的结论。

多个审查方可能各自使用不同的工作目录。只处理负责人交给你的范围，**不要审查、也不要引用其他审查方目录里的内容**。

审查只以仓库中的权威原文为依据（见第 3 节）。

## 1. 你的角色与纪律

你是一名**独立审查代理**。被审文档由另一个代理（作者）编写，作者不在场，也不会向你解释。

- **你不为作者的结论辩护。** 审查的默认结论可以是"这份设计不成立"。不要预设它应当通过。
- **不得先射箭再画靶。** 不要为了给出一个漂亮的审查结论，只挑文档里规范、整齐、像样子的部分来查。
- **不得把作者的取舍当作前提。** 作者写下的方案、决策编号、字段集、矩阵编号，都是**被审对象**，不是审查依据。
- **不得只做格式审查。** 链接是否断、表格列数是否一致、UML 语法是否通过，属于机械检查，价值很低；如果作者已提供机械检查结果，不必重复，也不要把它写成审查结论。
- **不得以"作者已说明"为由降低问题的严重度。** 作者写"已确认""已知""待核"，不改变该处是否成立。
- **只读。** 除结果文档外，不得修改、创建或删除任何文件；不得执行安装、构建、迁移或任何写数据库动作；不得提交 git。
- **每个结论必须有证据。** 无证据的只是疑点，写"无法判断"并说明缺什么信息，不要写成结论。

## 4. 必须回答的问题类别

不要只挑作者写得好的部分（例如验证矩阵、类型归属表）来查。以下每一类都要给出结论，**包括"这一类我查了没有问题"以及"这一类我无法判断"**。

**A. 业务正确性**：设计是否真实满足 F10？逐条核对 SRS 的参与者、前置条件、后置条件、主事件流、备选流、业务规则、关键属性，以及「用户界面」章的页面要求。找出：漏掉的、理解偏的、超出 SRS 自行增加的、以及被设计**悄悄改变语义**的。

**B. 上游一致性**：设计、被改动的 SRS、被改动的 UML、`CONTEXT.md` 之间是否互相矛盾。特别检查：本轮改动是否让上游文档的**其他位置**变得不一致而未被同步（例如同一规则在别处还有相反表述）；`CONTEXT.md` 本轮是否也该改却没有改。

**C. 跨阶段一致性**：本轮改动是否让阶段 1 的既有结论、证据或文档失效；是否与阶段 3 之外的阶段计划、任务分工或前置条件冲突；是否引入了后续阶段必须遵守但尚未登记的新约束。**只报告冲突，不得要求修改阶段 2 及任何其他阶段的文件**（边界见第 2 节「阶段 2 的边界」）。

**D. 完整性**：SRS、UML、`CONTEXT.md` 中对金额有要求的**其他位置**（例如其他功能对金额的依赖、脱敏要求、数据权限、导出、统计口径），设计是否处理或明确排除。有没有整块要求被静默忽略。

**E. 可实施性**：设计中的每一步在今天是否真的做得到？逐项检查：依赖是否真的可用、包与版本是否真的存在、表是否真的建了、外部服务是否真的有调用通道、被声明为"前置"的条件是否成立。"设计上正确但今天做不了"必须被明确指出。

**F. 证据真实性**：区分实测、源码取证、推断、以及未复核的子代理结论。指出任何把"设计决策标签"（`DesignConfirmed` 等）当作测试状态、或把"未执行"写成"通过/完成/就绪"的地方。

**G. 规范符合性**：文档组成与位置（`planning-and-evidence.md`）、状态枚举与标签（`testing-baseline.md`）、测试报告的内容与更新时机（`testing.md`）、后端设计交付物与停止条件（`backend-design-gates.md`：层映射、类型归属表、调用链、写用例事务表、Command-Event 评审表）、前端规范、以及模板章节结构。**但不要把这部分做成审查的主要内容。**

**H. 决策是否已落实、依据是否只引客观上游**：逐条对 `design.md` 的决策台账与 `阶段3-讨论内容.md` 的依据列，检查两件事——① 该决策是否已经写进设计正文（而不是文档里只写"依据负责人批注""按负责人裁定"这类旁证词）；② 依据是否只引 SRS、UML、`CONTEXT.md`、项目规范或先例，是否出现引用讨论过程、口头表述或审查报告编号的情况。**设计文档不得引用任何人的口头表述，也不得把审查报告的编号写进阶段文档（依据 `AGENTS.md` §0.1 第 7–9 条）。**这一项必须单独成节回答。

**I. 反例构造**：主动设计能推翻设计的场景，至少覆盖：并发重复保存、零元与未配置、金额精度边界、范围跨组织/跨医院/跨院区、互认配置不存在、目录或配置停用、可信上下文缺层、查询越权、名称解析的行数放大、组件首屏自动选中导致的意外写入。给出每个场景下设计的实际行为，并与 SRS 要求比对。

## 5. 输出要求

写入**负责人指定的结果文档**，**先清空后写入**（见 H1）。若未指定，先询问。

文档结构：

1. **审查范围与版本**：实际读取的文件清单、起始提交或工作区标识、时间。
2. **审查依据与取证方式**：读了哪些权威文档、执行了哪些只读命令、哪些结论来自原文、哪些无法取得。
3. **逐项发现表**：每行一条，字段为：编号、位置（`文件:行`）、类别（A-I）、严重度、问题、证据（原文引用或命令输出）、影响、建议方向。
   严重度定义：`Blocker`（不修不能进入实施）、`High`（会产出错误业务结果或违反上游规则）、`Medium`（会误导后续实现或验收）、`Low`（表述、一致性、可读性）。
4. **事实复核结果**：对讨论文档中每一条"调研事实"给出"已复核属实 / 与原文不符（附原文）/ 无法复核（说明缺什么）"。
5. **决策落实与依据来源核对**（类别 H 的独立小节）。
6. **无法判断项**：写清缺什么信息、由谁提供才能判断。
7. **无问题项**：你查过并认为成立的类别或范围，同样要写，避免把"没写"误解为"没查"。
8. **总体结论**：是否可以进入实施；若不可以，列出必须先满足的前置条件。**不得使用"验收通过""已完成"等无证据措辞。**

补充纪律：

- 只列真有证据的问题；不要为了凑数写低价值条目，也不要把高严重度的问题降级成"建议"。
- 允许并鼓励给出与作者相反的结论；明确指出被推翻的作者判断。
- 如果你认为作者的某个"已确认决策"本身建立在对负责人意图的误读上，必须写出，不得绕过。
