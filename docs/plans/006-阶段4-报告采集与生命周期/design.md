# 阶段 4：报告采集与生命周期（F03）

阶段设计见 [Server/design.md](Server/design.md) 与 [Client/design.md](Client/design.md)；批次与矩阵编号见 [impl.md](impl.md)、[Server/impl.md](Server/impl.md) 和 [Client/impl.md](Client/impl.md)；测试结果见 [testReport.md](testReport.md)。

## 目标与范围

- 目标：接收医院侧提交的检验报告与检查报告完整版本，按报告业务标识维护报告生命周期与不可变版本，支持独立作废，并在管理端提供受数据权限控制的只读历史版本查看与 PDF 下载。
- 纳入：检验完整报告提交、检验报告作废、检查完整报告提交、检查报告作废四个医院接入能力；报告主体、版本、平台患者、检验专项内容与明细、检查专项内容与明细共 10 张表的新建；管理端「报告管理与历史版本」两个入口、两个页面与路由；API Client 累计重生成。
- 排除：报告变化的下游主动推送与推送记录、PushCenter 对接、影像文件接收或代理、报告更正原因与版本变更原因、历史版本差异比较、版本修改删除恢复或重新启用、独立版本管理菜单、报告查看角色或权限项、报告使用关系表、HIS 侧匹配与引用能力（阶段 5）、互认统计与导出（阶段 6）。
- 依据：SRS F03.1/F03.2/F03.3、SRS「医院接入接口」表与「用户界面」章「报告管理与历史版本」、UML `1-MedicalRecognitionReport.wsd`、总体计划 4.6 与 §7。
- 前置：阶段 3 完成。
- 端：跨端。

## 已确认设计

**实现边界。** 全部按受保护的手工维护推进，不重跑代码生成器；在既有生成物上继续修改请求、命令、事件、实体、映射声明、仓储接口与实现、SqlMap 与建表脚本，并新增应用服务、查询实现与手工控制器。既有 10 个报告实体、19 个对外 DTO 与 14 个 SqlMap 文件是起点。

**聚合与代码组织。** 沿用唯一聚合 `MedicalRecognitionReportAggregate`，报告主体是聚合根；版本、专项内容、结果明细、检查项目与检查部位通过实体外键字段关联，不引入聚合内对象图集合。全部新增类型平铺在既有聚合目录，管理器与仓储沿用既有单套实现。

**四个医院接入能力。** 两个完整报告提交接口使用 `multipart/form-data`：文本部件承载完整报告 JSON 文档、文件部件承载 PDF 文件流；两个作废接口使用标准 JSON，只提交来源报告单号、作废时间与原因。四个接口成功统一返回 `Boolean=true`，失败以既有框架业务异常表达。两个提交接口由手工控制器动作承载：控制器动作只做 multipart 绑定、文件校验与落盘、失败补偿与文件流响应，编排"文件落盘 + 调用应用服务"；事务边界声明在公开应用服务（提交入口）的方法上，控制器不承载事务；应用服务只组装一个提交命令，管理器先完成全部校验再按下述顺序写入，最后登记事件：定位或创建报告（创建时登记报告已创建事件）、追加版本并更新当前版本指向与报告主体上的报告时间、患者姓名、证件号码、解析平台患者、写入检验或检查专项内容、写入全部明细。任一子步骤失败时整次提交不保存任何报告内容，也不登记后续步骤的事件。

**报告业务标识与版本。** 报告由组织、医院、院区、报告类型与来源报告单号共同定位，组织、医院、院区来自可信调用身份。报告不存在时创建当前有效报告；报告存在且未作废时每次成功完整提交追加一个完整版本并立即成为当前版本；报告已作废时拒绝追加。不比较报告内容、不使用源端报告修改时间判断版本顺序或重传，该时间仅随版本保存用于来源追溯。版本按平台成功形成顺序生成内部版本序号，旧版本不保存可变状态，历史版本只用于管理端只读查看。

**报告时间与患者检索字段在报告主体上冗余保存。** 报告主体新增报告时间、患者姓名与证件号码列，取值均来自当前版本；追加版本时与当前版本指向在同一事务内更新，因此报告主体上的这三列恒等于当前版本的对应取值且非空。报告时间用于管理端列表的筛选、排序与索引，患者姓名与证件号码用于列表的患者筛选，使列表查询不需要按当前版本反复关联；报告主体的患者姓名与证件号码建前缀索引，两列的筛选按输入值前缀匹配、`%` 与 `_` 按普通字符处理；它们不改变各自字段的来源与语义，报告时间也不参与版本顺序判断。

**作废。** 作废只改变报告生命周期状态、作废时间与作废原因，不生成内容版本、不物理删除；作废时间不得早于当前版本平台接收时间、不得晚于本次请求接收时间，两端含边界；已作废且作废时间与原因完全一致时幂等成功，任一不同即返回作废信息冲突，不覆盖首次保存的作废事实。已作废报告不得通过再次提交或历史版本恢复。

**患者归属。** 平台患者按证件类型与证件号码识别，用姓名、性别代码与出生日期核对。首次提交创建平台患者并关联报告；后续版本必须解析到该报告原有关联患者，解析到其他患者或核心身份不一致时拒绝追加，不允许报告跨患者迁移。患者解析是管理器内部步骤，不构成独立命令；并发首次解析撞证件键时由证件键唯一索引拒绝，数据库异常按原样向外传播，不复读、不重试。

**PDF 文件。** 采用本地文件目录存储：契约只暴露保存流返回文件键、按键读取、按键删除；存储根目录由配置键提供完整绝对路径，配置缺失或目录不可用即抛异常、不隐式兜底；文件键为日期目录加平台生成的文件名，创建模式为不覆盖，含写失败清理与路径穿越防护。版本表保存文件键与该版本的下载文件名，文件字节不进业务 JSON、不进数据库。提交链路先落文件、再写库；写库失败删除本次新文件并原样抛出原始异常；删除文件失败只记日志、不改变对外结果。历史版本文件全部保留，本阶段不做清理或归档。单文件上限由配置节提供（默认 83886080 字节），控制器动作在读取文件流前拒绝超限请求；单文件上限必须低于宿主请求体上限，使控制器的超限拒绝分支可达。

**下载。** 按报告标识与报告版本标识定位版本与报告，并按报告的来源组织、医院、院区与可信范围比对后返回 `application/pdf` 文件流与该版本保存的下载文件名，响应头禁止缓存，不返回文件键、物理路径或对外下载地址；版本不存在、文件缺失与归属不匹配分别抛出明确业务事实；已作废报告的历史版本仍可下载。

**管理端报告查询与页面。** 拆成平台管理员与医院管理员两个入口、两条独立路由、两个页面、两个菜单。平台管理员入口的组织、医院、院区取自请求；医院管理员入口的组织与医院取自令牌可信上下文并覆盖同名请求字段，院区取自请求且必须属于可信医院。列表支持按组织、医院、院区、报告时间日期范围、报告类型、报告单号、患者证件号码与患者姓名查询，患者姓名只作为明确输入的查询条件；采用服务端分页，时间范围作用于报告业务时间并采用左闭右开区间，排序为报告时间倒序加主键倒序。患者证件号码与患者姓名按规范形式比较：证件号码去首尾空白并统一大写，姓名去首尾空白；列表筛选先按同一规则规范化输入值，再做前缀匹配，`%` 与 `_` 按普通字符处理；证件号码与姓名都只是明确输入的查询条件，不用于患者身份匹配。组织、医院、院区名称由服务端按名称回填口径对当页整体赋值，调用次数不随返回行数增长。列表与版本详情完整展示患者姓名与证件号码，患者联系电话按业务原值展示。版本信息只读，按平台成功形成顺序展示并区分当前有效版本、已被替代的历史版本与报告已作废状态；报告责任人员以结构化字段返回。

**权限与异常。** 本阶段不新增任何权限判定：后端不重复判断操作权限，前端不做角色可见性或操作门控，能进入页面即视为已获授权。范围与归属校验保留：平台管理员入口按请求使用组织、医院、院区并校验三者存在、启用与父子归属；医院管理员入口的组织与医院取可信上下文，院区须属于可信医院，列表、版本列表、版本详情与下载按可信范围与报告来源归属比对后返回，跨医院或跨院区定位不可得。后端不新增异常中间件、过滤器、响应转换器或错误包装模型，业务失败直接抛出；仓储把违反唯一约束翻译为 `Duplicate*Exception` 只在仓储到管理器内部使用，不改变对外响应形态。前端由宿主统一展示错误，页面只做本地恢复。

**数据与索引。** 10 张表统一 `mrec_` 前缀，列序按项目 DDL 规则（主键、UML 业务列序、生命周期状态标志、操作时间、操作人），补表与列中文注释；实体名与 SqlMap 作用域不变，实体与物理表通过 SqlMap 显式对应。报告主体建业务键唯一索引；报告版本建报告与版本序号唯一索引；平台患者建证件键唯一索引；报告主体建组织、医院、院区、报告时间与主键组合索引，并建患者姓名与证件号码前缀索引。
