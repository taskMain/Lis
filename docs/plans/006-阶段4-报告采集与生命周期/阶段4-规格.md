# 阶段 4 规格：报告采集与生命周期（F03）

## Problem Statement

医院已经完成审核的检验报告和检查报告，目前没有任何渠道进入互认平台。医生在开单时无法引用其他医院已有的结果，患者只能重复检查；医院也拿不到"本院报告被其他医院采纳了多少次"的事实基础。

从医院侧看，问题有四个具体面：

- 医院源系统（LIS / PACS）报告一旦首次审核通过或修订后重新审核，必须有一份"当前完整版本"能稳定送达平台，且**结构化内容和原始 PDF 必须一起到达**——只到一半（有结构化没 PDF，或反之）对医生毫无价值。
- 报告修订后要能重新提交，平台必须能区分"这是同一份报告的新版本"，同时医院**不需要理解或填写平台的版本号、版本状态、更正原因**。
- 报告在源系统被作废后，平台必须立刻停止把它当作可用结果，但**不能丢失或改写已经收到的内容和文件**——追溯要留得住。
- 医院不希望平台要求它先建患者主档、先维护院内项目对照或预先上传挂号记录；报告随附的患者身份和就诊信息就应当足够。

从平台侧看，问题在于：接收的数据要能支撑后续的互认匹配（阶段 5）、统计与导出（阶段 6），因此报告、版本、患者、明细之间的归属关系必须一开始就正确，且历史版本必须可追溯、不可被新版本覆盖。

从管理员侧看，问题在于：报告集中到平台后，管理员需要一个受权限控制的只读查看入口，能按异常报告快速定位、能看到全部历史版本、能下载任一版本的原始 PDF；并且**医院管理员只能看本医院及有权院区的报告**，平台管理员按现有数据权限查看授权范围，其他医院不得查看来源医院的报告。

## Solution

为医院侧提供一个"完整报告提交 + 独立作废"的采集能力，为平台提供一个"只读历史版本查看与 PDF 下载"的管理能力。

- 检验报告与检查报告各有独立的完整提交能力与独立的作废能力。完整提交一次只处理一份报告，同时携带完整结构化报告与 PDF 文件流；作废只声明报告不再有效，不重复提交内容。
- 平台按"组织 + 医院 + 院区 + 报告类型 + 来源报告单号"识别报告：报告不存在时创建，存在且未作废时每次成功提交追加一个完整且不可变的新版本并立即成为当前版本，报告已作废时拒绝追加。平台不比较内容、不判断是否重传、不要求医院提供版本号。
- 平台按证件类型与证件号码识别患者，并用姓名、性别代码、出生日期核对；同一报告的所有版本必须始终关联同一个患者，不允许报告在不同版本之间迁移患者。
- 作废只改变报告的生命周期状态并保存作废时间与原因，不生成内容版本、不删除历史内容与文件；已作废报告不可恢复。
- 管理端提供两个入口（平台管理员、医院管理员）的只读报告查看：按多个条件查询报告、查看全部历史版本、查看任一版本的完整结构化内容、下载任一版本的 PDF；页面的可见性由权限系统的菜单授权控制，平台不重复判断权限。

## User Stories

1. 作为医院侧采集服务，我希望把一份已经审核完成的检验报告（完整结构化内容 + PDF）一次性提交给平台，这样平台就拥有了这份报告的当前完整版本。
2. 作为医院侧采集服务，我希望同一份报告在修订并重新审核后再次提交时，平台自动形成新版本并把新版本作为当前版本，这样我不需要理解平台版本概念也不需要提交版本号。
3. 作为医院侧采集服务，我希望提交请求里不需要携带平台的报告 ID、组合业务标识、更正原因或版本变更原因，这样接入成本最低。
4. 作为医院侧采集服务，我希望只上传一份报告就能让平台自己判断"创建首个版本"还是"追加新版本"，这样我的调用逻辑不需要分支。
5. 作为医院侧采集服务，我希望每次成功提交都返回明确成功，校验失败或报告已作废时返回明确的业务失败说明，这样我能区分"重试有用"和"重试无用"。
6. 作为医院侧采集服务，我希望超时或未取得明确结果时可以原样重发，并且重发成功会形成一次新的完整版本，而不是被平台悄悄合并或判重。
7. 作为医院侧采集服务，我希望报告作废能力只提交报告单号、作废时间和原因，不需要重复提交报告内容和 PDF。
8. 作为医院侧采集服务，我希望重复作废同一份报告且内容完全相同时按幂等成功处理，内容不同时明确告诉我"作废信息冲突"，且不覆盖首次作废事实。
9. 作为医院侧采集服务，我希望作废时间有明确的可接受范围（不早于平台收到当前版本的时间、不晚于本次请求到达平台的时间），这样我能判断自己的系统时钟是否需要校准。
10. 作为医院侧采集服务，我希望报告里的互认项目编码可以缺失、可以填了但当前不可用（不存在、超出组织范围、停用或目录停用），这些都不影响整份报告被接收，只是那些明细不参与互认。
11. 作为医院侧采集服务，我希望上传请求可以携带 PDF 文件名；文件名缺失或不安全时平台自动使用"报告单号加扩展名"作为下载名，而不是拒绝整份报告。
12. 作为医院侧采集服务，我希望一次请求只处理一份报告，且报告之间互不影响，这样我可以并发提交多份独立报告。
13. 作为医院侧采集服务，我希望平台不要求我预先上传患者主档或挂号记录，报告随附的患者与就诊信息就足够。
14. 作为医院侧采集服务，我希望平台不要求我维护院内项目与互认项目的对照，也不要求我先把科室和人员维护到平台权限体系。
15. 作为医院侧采集服务，我希望提交的科室和人员直接使用业务 ID 与名称（ID 为字符串），平台原样保存、不补查、不覆盖。
16. 作为医院 LIS/PACS 对接方，我希望检验报告可以包含普通检验结果，以及按需提供的细菌鉴定结果与药敏结果；检查报告可以包含一个或多个检查项目及其结构化检查部位，这样联合报告不需要被我强行拆分。
17. 作为医院 LIS 对接方，我希望培养未发现细菌时仍能提交一条"未检出"的细菌鉴定结果（结论 + 来源文字），不需要伪造菌种编码或名称。
18. 作为医院 LIS 对接方，我希望检查报告的检查所见与检查结论属于整份报告、不重复挂到每个项目上，这样不需要改动我的报告结构。
19. 作为医院 PACS 对接方，我希望检查报告可以按来源情况提供影像状态与单个影像调阅地址；来源没有可用地址时仍可接收报告，只是表达为"存在影像但暂不可调阅"。
20. 作为患者，我希望同一份报告的修订版本不会把我的身份信息搞错、也不会把报告挂到别人名下，这样我的病历引用是安全的。
21. 作为患者，我希望报告修订后旧版本内容仍然可追溯（而不是被覆盖），这样医院对我的历史结果负责时有据可查。
22. 作为平台管理员，我希望按组织、医院、院区、报告时间范围、报告类型、报告单号、患者证件号码和患者姓名查询报告，这样我可以快速定位需要关注的数据。
23. 作为平台管理员，我希望报告列表用服务端分页，并且能看到满足条件的记录总数，这样报告量增长后仍能稳定浏览。
24. 作为平台管理员，我希望列表按报告时间从新到旧排列，这样最新报告排在最前。
25. 作为平台管理员，我希望列表显示来源组织、医院、院区名称，而不是让我自己去对照编码。
26. 作为平台管理员，我希望从列表进入详情后，看到该报告的全部历史版本，并清楚区分"当前有效版本""已被后续版本替代的历史版本"和"报告已作废"。
27. 作为平台管理员，我希望每个版本显示平台内部版本序号、源端报告修改时间、平台接收时间、报告责任人员、来源报告备注与 PDF 文件名，这样我能核对这是哪一版、谁负责、对应哪个文件。
28. 作为平台管理员，我希望查看任一版本的完整结构化内容（检验：标本与全部结果；检查：所见结论、项目与部位），这样异常报告不需要下载 PDF 就能先看内容。
29. 作为平台管理员，我希望下载任一版本的 PDF，并且下载文件名就是该版本保存时的文件名，这样我能把文件与原报告对上。
30. 作为平台管理员，我希望已作废报告的旧版本 PDF 仍可下载，这样追溯作废前的原始报告不被阻断。
31. 作为平台管理员，我希望在同一个页面看到患者姓名与证件号码，联系电话默认脱敏，这样既能核对身份又不便于无关人员滥用。
32. 作为医院管理员，我希望平台的组织与医院自动取自我登录的身份，我只需要选择院区，这样我不必担心选错组织。
33. 作为医院管理员，我希望只能看到本医院及其有权院区上传的报告，其他医院的报告不出现在我的列表里。
34. 作为医院管理员，我希望看到本医院报告的全部历史版本和完整内容，用于回应临床与质控追溯。
35. 作为医院管理员，我希望页面上的操作失败提示由平台统一处理，页面本身不要另弹一份错误，这样提示口径一致、不出现双重提示。
36. 作为医院管理员，我希望列表加载失败时保留我已经看到的数据、能重试，而不是整页清空。
37. 作为平台管理员或医院管理员，我希望筛选条件改变时自动回到第一页并保留我选的每页条数，这样不会出现"改完筛选发现是空列表"。
38. 作为平台管理员或医院管理员，我希望列表页不展示平台内部存储标识、文件路径或技术排障信息，这样页面只表达业务事实。
39. 作为平台管理员或医院管理员，我希望历史版本区域是只读的——不提供修改、删除、恢复、重新设为当前版本或重新启用，也不显示来源报告里本来没有的"更正原因"。
40. 作为平台运维/实施人员，我希望 PDF 文件存放在由配置指定的本地目录，文件随结构化数据共同生效，这样不需要引入平台目前没有的文件服务依赖。
41. 作为平台运维/实施人员，我希望 PDF 存储目录可以在部署时通过配置更换，并在配置缺失或目录不可用时明确失败，而不是静默落到某个默认目录。
42. 作为平台运维/实施人员，我希望报告提交失败时不会留下"有文件没记录"的垃圾文件，这样磁盘不会被失败请求污染。
43. 作为平台运维/实施人员，我希望历史版本的文件全部保留，且这一取舍被显式登记为已接受风险与重审条件，这样成本是可预期的。
44. 作为平台侧开发人员，我希望报告的接收、作废、查询三个链路的职责边界清晰（控制器只做绑定与文件编排，应用服务做上下文解析与命令组装，管理器做不变量），这样后续阶段（匹配、统计）能直接复用报告与版本模型，不需要返工。
45. 作为平台侧开发人员，我希望报告提交的编排不使用本项目框架里不存在的机制（不发明"子命令编排"），而是沿用已验证的事务声明与失败补偿形态。
46. 作为项目负责人，我希望本阶段不新增任何权限判定与角色门控——能进页面即视为有权限，平台只负责数据正确性与归属一致性。
47. 作为项目负责人，我希望本阶段的异常处理与本项目既有阶段完全一致：不新增中间件、过滤器或响应包装，失败直接抛出；前端错误由宿主统一展示。
48. 作为项目负责人，我希望验收数据只由平台自身的接口与页面形成，不通过直接写库或脚本注入数据。
49. 作为项目负责人，我希望本阶段的验证不依赖无法构造的环境（跨组织真实宿主面、正常业务不可达的数据状态），不可构造项如实登记而不是伪造证据。
50. 作为后续阶段（在线互认主流程）的实现者，我希望本阶段交付的报告、版本、患者与明细模型在字段与归属上完整可信，并且"当前有效版本"的判断口径是明确的（报告当前版本指向 + 报告生命周期状态推导），这样匹配与引用查询不需要重新解释报告语义。

## Implementation Decisions

**领域模型与聚合**

- 沿用唯一聚合边界，报告主体是聚合根；版本、平台患者、检验专项内容、普通检验结果、细菌鉴定结果、药敏结果、检查专项内容、检查项目、检查部位共 10 类实体，通过实体外键字段关联，**不引入聚合内对象图集合**，保持既有实体的扁平字段形态。
- 报告业务标识为组织、医院、院区、报告类型与来源报告单号；组织、医院、院区来自可信调用身份，报告类型由所调用的接口确定，报告单号取请求。
- 版本不保存"当前版本/已被替代"等可变状态；版本当前性由报告当前版本指向与报告生命周期状态推导。版本序号在同一报告内按平台成功形成顺序递增。
- 患者归属：按证件类型与证件号码识别，用姓名、性别代码与出生日期核对；首次提交创建患者并关联报告，后续版本必须解析到该报告原有关联患者。

**接口与契约**

- 两个完整报告提交接口使用 `multipart/form-data`，只有两个顶层部件：结构化报告 JSON（camelCase 字段名，反序列化拒绝未知字段）与 PDF 文件流；检验与检查各一个端点，**不设置报告类型判别字段**。
- 两个作废接口使用标准 JSON，只提交报告单号、作废时间与原因。四个接口成功统一返回布尔真，失败以既有框架业务异常表达（不使用 false 承载失败）。
- 请求字段的必填、成对（ID 与名称同时有值或同时为空）、条件应填（源系统存在时必须提供）与明细唯一性规则按 SRS F03.1/F03.2/F03.3 逐条落实；必填时间省略或传零值视为缺失并拒绝，业务时间顺序为申请时间不得晚于报告时间、报告时间不得晚于审核时间（审核时间为空时不参与比较），逆序即整份报告失败，拒绝文案只描述业务事实。
- 明细唯一性三条同时实现：来源明细标识（提供时同一版本内不重复，缺失合法）、普通检验结果展示序号（同一版本内不重复）、药敏展示序号（同一版本、同一细菌鉴定结果下不重复）；任一重复整份报告失败。
- 互认项目编码字段统一命名 `StandardProjectCode`（与领域实体和 UML 一致），编码缺失或不可用不阻止接收。
- 来源影像状态的填报要求为应填：源系统能够判断时必须提供，不能判断时填未知；字段未提供时按未知处理并保存，不作为缺失拒绝整份报告。
- 单文件上限由配置节 `ReportPdfFiles` 的 `MaxFileBytes` 提供（单位字节，默认 83886080，不硬编码），控制器动作在读取文件流前拒绝超限请求；**单文件上限必须低于宿主请求体上限**，使控制器分支可达：宿主请求体上限由框架程序集设置、应用源码内无配置键，实测约为 104857600 字节；部署侧反向代理请求体上限同步到不小于宿主请求体上限的取值。

**编排、事务与事件**

- 报告提交由**手写控制器的上传动作**承载：动作负责 multipart 绑定、PDF 校验与落盘、调用应用服务，**事务边界声明在应用服务的公开提交入口方法上**（控制器不承载事务）；应用服务只组装一个提交命令，管理器先完成全部校验，再按序写入（定位或创建报告 → 解析患者 → 追加版本并更新当前版本指向与报告主体上的报告时间、患者姓名、证件号码 → 写入专项内容 → 写入全部明细），最后登记事件。服务端设计必须给出框架机制映射：事务声明方式、公开事务入口、文件落盘与事务的相对位置、事件登记与提交的边界，以及可静态识别的机械检查点。
- 报告提交在本项目框架下**不使用"编排命令 + 子命令"机制**（该机制在框架中不存在）；UML 中的内部子命令降级为管理器内部分步，其业务规则文字保留。报告创建并入版本追加步骤：仅新建报告时登记报告已创建事件。
- 作废只有一条写语句，依靠语句级原子性，不声明事务；作废入口走既有应用服务接口自动暴露的端点。
- 事件只在写入完成后登记；不测试框架工作单元的事务与事件行为。

**并发**

- 仅以数据库唯一索引兜底，冲突一律翻译为业务拒绝，不自动重试：报告业务键唯一索引（同一业务标识的并发首插）、报告版本序号唯一索引（同一报告的并发追加）、患者证件键唯一索引（同一证件的并发首插，撞键后复读一次并核对核心身份，一致则继续、不一致按患者身份信息冲突拒绝）。
- 不增加版本字段、悲观锁、自动重试或专门的并发压测。

**数据与索引**

- 10 张表统一 `mrec_` 前缀，列序按项目 DDL 规则（主键、UML 业务列序、生命周期状态标志、操作时间、操作人），补表与列中文注释；字符串使用文本类型；实体名与 SqlMap 作用域保持实体名，实体与物理表通过 SqlMap 显式对应。
- 报告主体：业务键唯一索引（组织、医院、院区、报告类型、报告单号，**不加状态过滤**，作废报告仍占住业务键）；组合索引覆盖组织、医院、院区、报告时间倒序、主键倒序；患者姓名与证件号码各建文本前缀索引（按目标数据库前缀匹配所需的运算符类显式声明，PostgreSQL 为 `text_pattern_ops`）支撑列表的患者筛选。
- 报告版本：报告标识与版本序号唯一索引。
- 平台患者：证件类型与证件号码唯一索引。
- 各明细表：报告版本标识（药敏为细菌鉴定结果标识）外键索引。
- 建表按三个批次执行（批次一 3 张报告与版本基础、批次二 4 张检验、批次三 3 张检查），与代码批次一致；未建表的批次不做依赖新表的运行验证。

**PDF 存储与下载**

- 自建本地文件存储端口：只暴露"保存流返回文件键、按键读取、按键删除"；存储根目录由配置键 `ReportPdfFiles:RootDirectory` 提供**完整绝对路径**，单文件上限由同一配置节的 `MaxFileBytes` 提供（默认 83886080 字节，必须低于宿主请求体上限）；文件键为日期目录加平台生成文件名；不覆盖写入、写失败删除半成品、路径穿越防护；配置缺失或目录不可用时抛出明确业务事实，**不隐式兜底**。受版本控制的默认配置只放空根目录与默认上限，开发期绝对路径写在开发环境配置。
- 提交链路为"先落文件、再写库"：写库失败时删除本次新文件并原样抛出原始异常；删除文件失败只记录日志，不改变对外结果。
- 版本表保存文件键与下载文件名，文件字节不进业务 JSON、不进数据库。
- 患者身份字段先按规范形式处理再比较：证件类型代码、证件号码与患者姓名的首尾空白去除，证件号码统一为大写；平台患者定位与核对、报告主体检索列使用规范形式，报告版本表按来源原值保存。
- 下载按报告标识与报告版本标识定位，返回文件流与该版本保存的下载文件名，禁止缓存，不返回文件键或物理路径；版本不存在、文件缺失与归属不匹配分别抛出明确业务事实；**已作废报告的历史版本仍可下载**。
- 历史版本文件全部保留，本阶段不做清理或归档（登记为已接受风险，重审条件为出现可复现的磁盘压力或部署目录配额问题）。

**管理端查询与页面**

- 两个独立入口、两条独立路由、两个页面、两个菜单：平台管理员入口的组织、医院、院区取自请求；医院管理员入口的组织与医院取令牌可信上下文并覆盖同名请求字段，院区取自请求且必须属于可信医院。两个入口共用同一分页契约与读模型。
- 服务端分页契约新增公共类型：请求含一基页码与 1–200 的页容量；响应含当页数据与分页信息（页码、页容量、长整型总数）；仓储先取总数再取当页；前端使用受控分页配置（表格下方、页容量可选、显示总数、改变页容量回到第 1 页）。
- 列表筛选支持组织、医院、院区、报告时间日期范围、报告类型、报告单号、患者证件号码与患者姓名；证件号码与患者姓名按规范形式做前缀匹配（输入值去首尾空白、证件号码统一大写；`%` 与 `_` 按普通字符处理），报告主体的这两列有文本前缀索引支撑，两者都只是明确输入的查询条件；时间范围作用于报告业务时间，采用左闭右开区间；排序为报告时间倒序加主键倒序（报告主体上的报告时间恒有值）。
- 组织、医院、院区名称由服务端按名称回填口径对当页整体赋值：组织全量只读一次，每个不同组织读取一次医院，每家不同医院读取一次院区，调用次数只随当页涉及的组织与医院数量增长、不随返回行数增长，禁止按行 N+1；外部服务不可用时整次查询失败，不降级为编码或空名称。
- 读模型由生成态重建为可用形态：枚举与嵌套占位类型改为强类型，并同时返回枚举值与文本字段（文本由服务端按枚举描述派生）；版本内容的公共、检验、检查三段分别强类型化，检验与检查各一套内容读模型；版本文件信息去掉对外下载地址字段；版本信息的报告责任人员以结构化字段返回，不做字符串拼接。
- 患者姓名与证件号码完整展示；患者联系电话按来源字段保存，返回时脱敏。
- 本阶段不新增报告查看权限模型与角色门控：能进入页面即视为已获授权，前端不做角色可见性或操作门控；**保留请求可信业务归属的范围校验**，列表、版本列表、版本详情与下载按可信组织、医院范围与报告来源归属比对后返回，跨医院或跨院区定位不可得。

**异常与错误边界**

- 后端不新增异常中间件、过滤器、响应转换器或错误包装模型，业务失败直接抛出；仓储把违反唯一约束翻译为内部异常类型，仅在仓储到管理器内部使用，不改变对外响应形态。
- 前端由宿主统一展示接口错误；页面只做本地恢复（结束加载、保留输入与已有数据、保持必要弹窗、不误刷新、不误报成功），不新增本地错误提示、不解析错误响应体、不新增请求拦截器。
- 前端本阶段不新增第三方依赖；PDF 下载使用浏览器原生能力配合已鉴权客户端取二进制后触发保存。

**API 客户端**

- 按累计范围重新生成：保留阶段 1–3 已交付接口，加入本阶段稳定契约（作废两个端点、提交两个端点、两个列表查询、版本列表、版本详情、按版本取文件的下载端点），排除后续阶段接口与登录接口；生成后核对公开入口、字段、可空性、枚举、分页形状，并恢复被覆盖的手写入口文件。

## Testing Decisions

**什么算好测试**

- 只测外部行为与契约，不测实现细节：断言请求与响应的契约形状、业务结果（写入结果、状态变化、返回文本）、失败语义与数据一致性；不断言私有方法、内部调用顺序（名称回填的调用次数除外——它是明确的性能不变量）或字符串实现细节。
- 每条用例的判定必须是可判定的（有明确预期值或明确的拒绝事实），并且其前置数据能通过平台接口或页面构造。
- 不测试框架行为（工作单元事务回滚、事件可见性）；与失败相关的用例只覆盖本项目自己的代码路径。

**接缝（优先级从高到低，尽量复用既有接缝，不新增）**

1. **接口层**：两个提交端点（multipart，两个部件）、两个作废端点、两个列表查询端点、版本列表端点、版本详情端点、按版本下载端点。覆盖四个医院接入能力的成功/失败语义、契约字段与分页/下载响应形状。
2. **管理器（领域校验与不变量）**：报告定位与创建、版本追加与当前版本指向、患者核对与冲突、作废边界与幂等、明细唯一性、成对字段规则。
3. **查询应用服务**：分页窗口校验与结果映射、两个入口的取值来源、筛选与排序、名称回填调用次数不随行数增长、枚举文本派生、脱敏。
4. **本地文件存储实现（真实文件系统）**：落盘与读取、路径穿越防护、写失败清理、删除幂等、配置缺失或目录不可用拒绝。
5. **控制器动作（编排与失败补偿）**：先落文件再写库、写库失败删除新文件且保留原始异常、超限拒绝、文件名回退。

**既有先例（同类测试在仓库中的形态）**

- 后端：阶段 2 与阶段 3 的写入路径测试、查询测试、SqlMap 探测测试、请求校验探针测试、架构与源码守卫测试（含"仓储调用必须显式传作用域""SqlMap 语句标识必须显式绑定"两类机械检查）；阶段 1 的读模型枚举文本测试可作为枚举文本断言的先例。
- 前端：既有页面的适配层测试、页面组件测试、路由测试与枚举元数据钩子测试；分页与下载属于本项目首次落地，先例取自参考实现的同构测试（受控分页配置、非法分页响应拒绝、二进制下载处理）。

**覆盖要求**

- 正反用例成对：成功路径与校验失败/冲突路径都要有；边界含时间范围两端、作废时间两端、文件上限、分页越界页。
- 每条用例标注是否需要真实数据库与真实文件系统；条件不具备记 `Blocked`，不伪造证据。
- 不设需要构造"正常业务不可达"前置的普通业务用例（例如可信身份缺失某层编码、重复主键）；为验证防御分支可以构造不可达或损坏前置，但必须逐条标注目的、只用于该防御分支本身。

## Out of Scope

- 在线互认主流程：互认匹配查询、处理结果提交、引用详情获取、引用结果提交，以及医院 HIS 侧界面（阶段 5）。
- 互认统计与导出：提醒、采纳、不采纳、引用、同期互认率、预计节省金额、来源医院被互认与导出（阶段 6）。
- 报告变化的下游主动推送、推送记录、PushCenter 对接与恢复处理。
- 影像文件接收、代理、缓存或长期保存；平台不接收 DICOM，只保存来源影像状态与单个受控 HTTPS 调阅地址。
- 报告更正原因、版本变更原因、版本差异比较、版本修改/删除/恢复/重新设为当前版本/重新启用、独立版本管理菜单。
- 报告使用关系表、调阅状态或调阅统计。
- 报告查看权限模型、角色权限判断（可见性由权限系统的菜单与接口授权控制；请求可信业务归属的范围校验保留，见 Implementation Decisions）。
- 历史报告导入（平台只接收上线后新产生并审核完成的报告）。
- 文件清理与归档策略（作为已接受风险登记，不在本阶段实现）。
- 管理端的报告提交上传界面（提交接口面向医院侧采集服务，管理端不提供上传界面）。
