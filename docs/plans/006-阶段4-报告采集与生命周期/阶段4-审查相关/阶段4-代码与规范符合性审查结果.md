### 2.2 结束日筛选窗口只覆盖当天前 8 小时（阻塞 V63）

| 项目 | 内容 |
|---|---|
| 位置 | `client/apps/dy-medical-recognition/src/pages/reportManagement/reportsApi.ts:194`（`toRequestDate` 按本地零点构造）、`:283`、`:286`（`applyFilters` 下发）；`server/Dy.MedicalRecognition.Application/Queries/MedicalRecognitionReportQueryAppService.Reports.cs:54`（`ReportTimeTo = request.ReportDateTo?.Date.AddDays(1)`） |
| 原文摘录 | `const date = new Date(Number(matched[1]), Number(matched[2]) - 1, Number(matched[3]))`；`ReportTimeTo = request.ReportDateTo?.Date.AddDays(1)` |
| 对照依据 | `Client/design.md` 的时间筛选口径「以起止日期提交，页面不拼接时分秒」；`Server/design.md` 的列表筛选「起始日零点含边界、结束日次日零点不含上界」；V63（`Server/design.md:356`）「起始日零点含边界、结束日次日零点不含上界；跨日数据分别命中」 |
| 实测事实 | 运行宿主（`ASPNETCORE_ENVIRONMENT=Development`，`localhost:15014`）以真实宿主令牌实测，机器时区为 China Standard Time（UTC+08:00）。库中 `mrec_medical_recognition_report.report_time` 为 `timestamp without time zone`，21 行有效数据位于 `2026-09-18 01:00` 至 `01:05`（数据库服务端时区 `Asia/Shanghai`）。单日筛选 `2026-09-18` 下发 `reportDateFrom=2026-09-17T16:00:00.000Z`、`reportDateTo=2026-09-17T16:00:00.000Z`，返回 `totalCount=21`。逐点探测下界：下发 `2026-09-17T17:04:00.000Z` 得 1 行、`17:06:00.000Z` 得 0 行，证明下界按东八区墙钟比较 |
| 机制 | 上界为 `reportDateTo.Date` 再 `AddDays(1)`。本地零点经序列化变为前一日 16:00Z，其 `.Date` 丢失时区后按���八区解释，使有效上界落在**结束日的 08:00**，而非结束日次日零点。因此结束日 `[00:00, 08:00)` 内的数据被包含、`[08:00, 24:00)` 内的数据被排除 |
| 影响 | 结束日当天上午 8 点之后形成的报告在按该日筛选时不返回。当前验收数据恰好全部位于凌晨 `01:00` 至 `01:05`，因此现有取证无法暴露该缺陷，V63 的 `Passed` 结论对该分支不成立 |
| 建议处理 | 由适配层按 UTC 零点构造整天边界，或把两个筛选字段改为日期类型并与后端约定边界；补一条结束日 08:00 之后数据的用例 |
| 严重度 | `high` |
| 是否阻塞收口 | 是。V63 在 `testReport.md:56` 被声称已覆盖，实际结束日后半段被排除 |

**与子代理结论的差异说明**：前端审查子代理判定该缺陷为「结束日整天被排除」并给出「返回 0 行」的预期。主控实测得到同一天筛选返回 21 行，与该预期不符。经逐点探测确认实际机制为上界落在结束日 08:00，缺陷成立但范围窄于子代理的描述；本文件按实测口径登记。
