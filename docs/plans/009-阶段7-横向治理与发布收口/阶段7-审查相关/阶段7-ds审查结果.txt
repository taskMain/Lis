## 发现

### 发现 1 — V20 在本轮票 05 的清单中失去动作项，README 仍把 V20 列为票 05 的矩阵编号

| 要素 | 内容 |
|---|---|
| 编号 | 1 |
| 类型 | 缺陷 |
| 严重度 | 中 |
| 位置 | `阶段7-Tickets/README.md:29`（票 05 的矩阵编号列「V20-V29、C1-C10、C14-C18」）、`阶段7-Tickets/05-宿主链路全量走查.md:5`（执行节奏「接口组（V20-V29）…」）、同文 `:11`（验收项「V21-V29 医院接入接口 9 项成功主路径」）、同文 `:15`（C16-C18 项末句「回写登记动作作为 C20 输入由票 06 定案」） |
| 证据 | 上一轮票 05 的 C16-C18 项写「确需统一的按等价修复执行并经负责人确认，V20 回写登记」，本轮改为「…回写登记动作作为 C20 输入由票 06 定案」，票 05 的验收项清单因此只列 V21 至 V29（`:11`），V20 仅出现在执行节奏的范围记法与 README 的归属列。设计 V20 为「同步动作：同类能力统一（如需后端配合）的回写 | 静态 | 逐条登记有证据」（`Server/design.md:43`），C20 为「同步动作登记 | 前端文档同步（患者原值、控件统一等）逐条登记」（`Client/testPlan.md:26`），二者是两条并行用例：V20 记录统一动作的回写，C20 登记同步动作。设计的状态与分母构成要求本阶段矩阵用例全部取得本轮证据（`design.md:118`、S7-D2 的 `design.md:104`）。 |
| 影响 | 冻结分母中的 V20 在票集合里没有对应的验收动作：执行者按票 05 的清单作业时不会产生 V20 的证据，V30 核对分母与冻结记录一致时会暴露缺项；若把统一动作的登记只记入 C20，则 V20 与 C20 的完成判据混为一条，票 05 与票 06 的完成标准不唯一。 |
| 建议方向 | 在票 05 恢复 V20 的动作项（统一动作的回写登记，含「如需后端配合」分支），或明确写「V20 与 C20 由同一登记动作同时满足」并在票 06 的 C20 定案中注明 V20 的完成判据；同步 README 的归属列表述。 |

### 发现 2 — 票 04 把 V11、C12 的过堂范围扩到本阶段矩阵条目，设计这两条用例不含该范围

| 要素 | 内容 |
|---|---|
| 编号 | 2 |
| 类型 | 缺陷 |
| 严重度 | 低 |
| 位置 | `阶段7-Tickets/04-各阶段非干净条目过堂定级.md:3`（What to build「对冻结分母中的非干净条目（阶段 2 至阶段 6 现行矩阵，以及本阶段矩阵在宿主不可用等情形下产生的 `Blocked` 条目）逐条定级过堂」）、同文 `:9`（「本阶段矩阵宿主类条目（如 V6）逐条定级」） |
| 证据 | 设计 V11 为「各阶段非干净条目后端面过堂（阶段 2/3/4/5/6；前端面条目归 C12）：逐条定级并登记」（`Server/design.md:34`），C12 为「各阶段非干净条目前端面过堂 | 阶段 2 C17、阶段 3 C3/C11/C15/C22/C23、阶段 4 前端未收口条目及阶段 6 潜在前端非干净条目逐条定级」（`Client/testPlan.md:18`），两条都限定在阶段 2 至阶段 6 的条目。本阶段自身条目在宿主不可用时记 `Blocked` 并走定级残余出口（`design.md:121`），S7-D2 的三出口适用于分母内条目（`design.md:104`），但设计中承接该定级动作的用例只有上述两条。 |
| 影响 | 票 04 的动作超出 V11、C12 的登记范围：该定级在设计中无承载用例，验收时 V11 与 C12 的通过与「本阶段 V6 的定级」强绑，可能使 V11 的完成判据包含设计未列的对象；反之若执行者严格按设计范围作业，本阶段 `Blocked` 条目的定级没有归属。 |
| 建议方向 | 二选一：在设计侧把 V11 或 C12 的范围补上「本阶段矩阵中宿主不可用产生的 `Blocked` 条目」，或在票 04 中改为由 V30 的重新冻结记录一并定案并在 README 注明归属。 |

### 发现 3 — 票 02 的①桶写入「小改动」限定，与 README 和设计 S7-D4① 的表述不一致

| 要素 | 内容 |
|---|---|
| 编号 | 3 |
| 类型 | 缺陷 |
| 严重度 | 低 |
| 位置 | `阶段7-Tickets/02-一致性核对静态面与库前预校验抽查.md:16`（「①等价修复在本票内直接修复（小改动、无行为扩散）并登记 V19/C20」）；对照 `阶段7-Tickets/README.md:17`（「①等价修复在发现票内直接修复并登记 V19/C20」） |
| 证据 | 设计 S7-D4①（`design.md:106`）为「等价修复（实现与决策不一致、无行为扩散）在本阶段修复并回写对应阶段 testReport」，条件只有「无行为扩散」，没有改动量限定；README 的执行纪律复述时也未加该限定；票 02 的表述加入「小改动」，票 05 的末项写「同票 02 末项口径」，因此该限定在发现票之间传递。阶段的验收条件要求矩阵与过堂清单全部定级，未引入改动量门槛（`design.md:118`）。 |
| 影响 | 发现票遇到改动量较大的等价修复时，按「小改动」限定可以不修复也不登记，形成设计与票之间的口径差异：该问题既不进入①桶也不必然进入②桶，收口时无法判定其归属，可能带着未处置的等价偏差进入发布结论。 |
| 建议方向 | 删去「小改动」限定，与 S7-D4① 的「无行为扩散」条件保持一致；若拆分者认为较大改动需另走决策，应把它写成②桶（范围级）的判定条件并与设计确认。 |

### 发现 4 — C22 承接清单中「处理结果值域」出现两次且承接用例不同

| 要素 | 内容 |
|---|---|
| 编号 | 4 |
| 类型 | 缺陷 |
| 严重度 | 低 |
| 位置 | `阶段7-Tickets/02-一致性核对静态面与库前预校验抽查.md:15`（C22 项承接清单第 2 组「原因代码与处理结果值域 → 阶段 5 V33/V35b」与第 4 组「处理结果值域 → 阶段 5 V22b/V93、阶段 6 V27/C13」） |
| 证据 | 设计 §3 首段例举的第四类约束是处理结果值域（SRS :1517「处理结果值域只包括采纳和不采纳，不要求提交未处理、未查看、暂未决定或关闭提醒状态；长期未反馈的互认匹配记录不设有效期、过期状态或自动清理」，`design.md:30`）。承接用例经核对均真实存在且相关：V33 为「不采纳原因非法」、V35b 为「处理结果值域非法」（`docs/plans/007-阶段5-在线互认主流程/Server/design.md:206`、:209），V22b 为「匹配查询不形成处理结果、引用结果或调阅状态」、V93 为「提醒事实口径」（同文 :195、:274），V27 为「未反馈语义」、C13 为「明细表四类型与未反馈」（`docs/plans/008-阶段6-互认统计与导出/Server/design.md:146`、`Client/testPlan.md:28`）。两组对象覆盖该约束的不同侧面（值域合法性与未反馈状态），但标签相同。 |
| 影响 | 执行者按标签检索时会把两组视为同一对象的重复表述，只核对其中一组即记为完成，另一组覆盖的侧面（未反馈与未处理状态不形成事实、不设过期状态）可能漏核对；C22 的判定对象与完成判据因此不唯一。 |
| 建议方向 | 按侧面改写标签，例如「处理结果值域合法性 → 阶段 5 V33/V35b」与「未反馈与未处理状态面 → 阶段 5 V22b/V93、阶段 6 V27/C13」，并写明两组须同时核对。 |
