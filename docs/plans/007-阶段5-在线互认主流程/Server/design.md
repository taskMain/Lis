# 阶段 5 后端设计

总体范围与关键决策见 [阶段设计](../design.md)；本文件细化实现边界与验证矩阵，不复制决策台账。

## 领域与契约

聚合沿用 `MedicalRecognitionReportAggregate`。本阶段只新增在线互认主流程能力：四个医院接入接口、四张表、互认匹配查询、互认处理结果、引用详情查询与引用结果提交；不提供前端页面、PDF 下载接口实现、统计与导出、跨组织互认或角色权限模型。

当前代码事实：四个互认实体已在聚合目录下生成（分部类、扁平字段、无导航属性）；四张表的建表脚本与四个映射文件已生成——映射作用域已是各自实体名（阶段 4 交付时一并改正），映射语句仍为占位形态（仅列清单与无条件全量查询），建表脚本的表名尚无统一前缀、且无任何索引；本阶段涉及的契约读模型已生成但把集合与枚举字段退化为无类型对象；三个领域事件、四个接口的请求类型、管理器方法、仓储方法与查询实现**均不存在**。以上是待实现或待修正的现状，不是已验证结论。

### 公共契约与分层

**四个接口。** 互认匹配查询、互认处理结果提交、获取引用详情、提交引用结果全部走既有应用服务接口的自动端点；无手写控制器。**返回形态分两类**：互认处理结果提交与提交引用结果成功时返回布尔真；互认匹配查询返回匹配响应、获取引用详情返回引用详情响应，二者承载业务数据。四者的失败一律以既有框架业务异常表达。

**匹配查询链。** 自动端点 → 应用服务校验请求、解析可信身份与操作人、读取并校验三个系统参数、组装查询命令 → 管理器按序执行：校验并去重项目编码、解析平台患者、筛选候选报告、逐项目选优、确定非空后写匹配记录与匹配项、登记事件 → 返回匹配响应；空匹配在写入前返回成功空结果。

**处理结果链。** 自动端点 → 应用服务校验请求、解析可信身份与操作人、组装提交命令 → 管理器按序执行：读取既有处理结果、幂等识别、未命中时校验项目数组完整性、互认时间边界、决定内容与原因、科室与医生成对、报告版本有效性，随后读取采纳项目当前金额、原子保存并写入处理结果保存时间、登记事件。

**引用详情链。** 自动端点 → 查询应用服务校验请求、解析可信身份、读取并校验引用详情有效时长参数 → 查询仓储按可信身份三值加患者证件与就诊取候选采纳记录 → 应用服务按各匹配记录计算经过时间、逐项校验版本有效性、按同版本同项目取最近一条 → 映射读模型并派生枚举文本；全部项目不可返回时抛业务异常。

**引用结果链。** 自动端点 → 应用服务校验请求、解析可信身份与操作人、组装提交命令 → 管理器逐项反查匹配记录、处理结果与报告版本，校验归属一致、决定为采纳、科室与医生成对、时间序与幂等，随后原子保存并登记事件。

**分层职责。** Host 只做装配；Application 做请求校验、可信身份解析、参数读取校验、命令组装与读模型映射；Domain 管理器做业务不变量校验、持久化协调与事件登记；Repository 做读写、业务键定位与影响行数检查，不做数据库异常识别与翻译；Contracts 不引用领域实体。

## 数据与集成

### 四张表的结构约束

| 表 | 业务列 | 索引 |
|---|---|---|
| 互认匹配记录 | 接收组织、医院、院区编码；患者证件类型与号码；就诊类型与流水号；匹配生成时间；处理结果保存时间（可空，空表示尚待处理） | 按接收三值与患者证件、匹配生成时间支撑查询 |
| 互认匹配项 | 所属匹配记录；项目类型；标准项目编码；报告标识；报告版本标识 | 按所属匹配记录；按标准项目编码 |
| 互认处理结果 | 所属匹配记录；互认匹配项标识；互认时间；互认结果；互认科室标识与名称；互认医生标识与名称；不采纳原因与补充说明（可空）；预计节省金额（可空） | 按互认匹配项标识唯一 |
| 互认引用事实 | 互认匹配项标识；实际引用时间；引用科室标识与名称；引用医生标识与名称 | 按互认匹配项标识唯一 |

**处理结果表与引用事实表都不保存项目编码**：两者的项目编码均由互认匹配项标识反查匹配项取得。

四张表统一前缀、全量中文表列注释、显式索引、列序按项目既定规则；建表脚本按批次交付，由项目负责人确认目标数据库与 schema 后执行。设计不写具体语句与物理类型宽度。两个业务时间列（互认时间、实际引用时间）**精度不低于秒**；报表可按更粗粒度汇总，但不得降低原始业务时间精度。

**四张表的索引**：匹配记录表按接收组织、医院、院区编码与患者证件、匹配生成时间建索引；匹配项表按所属匹配记录建索引，并按标准项目编码建索引（供后续按项目汇总关联）；处理结果表与引用事实表各按互认匹配项标识建唯一索引，一一对应关系与引用事实的并发撞键兜底都由该唯一索引承担。建表脚本当前无统一前缀、且无任何索引，四项索引随建表脚本在批次 1 一并交付。

**三类计数为派生统计口径**：采纳次数、引用次数与来源医院被互认次数按已保存事实派生，本阶段四张表不含计数列，也不维护计数器；V23 与 V72 中三处表述只表观察口径，三项计数的读取与汇总不在本阶段取证范围。

### 映射与作用域

四个实体映射的作用域已是各自实体名（阶段 4 交付时一并改正；既有静态探测断言已断言四条实体作用域键存在、旧聚合作用域键不存在）。四个映射文件当前仍为占位形态（仅列清单与无条件全量查询），本阶段按实际写入与读取需要补齐语句，语句标识与仓储方法名对应（去掉异步后缀），作用域逐调用显式传入，不调用上下文设置方法。语句补齐后，既有语句清单断言中相应键需按补齐结果同步。**映射文件的存放位置由阶段 4 确定**：阶段 4 曾把 19 个映射移入按能力分组的子目录，导致宿主按资源逻辑名注册失败、全部写接口报缺作用域；处置后新增守卫用例 `Stage1SqlMapProbeTests.Sql_map_resources_stay_directly_under_one_folder` 断言每个映射的内嵌资源名只含一层目录，与仓储类同处程序集根下一级目录。本阶段四个映射补齐语句时须留在该位置，不新建分组子目录。

**集合参数写法**：匹配候选查询按一组标准项目编码过滤，参数名直接跟在 `in` 之后、不带括号，由框架展开为值列表；仓储侧把只读集合直接赋给同名属性。本平台现有映射文件尚未使用该写法，本阶段为该写法在本项目的首例，需在实施时以映射语句文本静态取证其展开形态。

**候选报告查询**：以报告主体关联当前版本、再关联专项内容；按报告类型分别以左连接取检验检测完成时间或检查实际检查时间，合并为统一排序键；**报告时间取自报告主体上冗余保存的报告时间列**（由报告采集能力交付并随版本追加在同一事务内更新，恒等于当前版本取值）。排序为匹配基准时间倒序、报告时间倒序、报告版本标识升序。

### 系统参数集成

三个参数经平台系统参数服务读取，参数编码为小写下划线形态，**按平台级编码读取、不传组织与医院与院区维度**。参数服务的代理映射位于宿主开发环境配置 `server/Dy.MedicalRecognition/appsettings.Development.json`：该文件被 `server/.gitignore` 覆盖、未纳入版本控制，当前工作区已含 `ISystemParameterAppService` 的代理映射与 PDF 存储根目录；**部署到其他宿主时须确认该配置包含本服务**。

读取形态为直接注入服务后在调用处就地读取，参数编码以常量声明在使用处；不引入参数解析 helper。返回值为字符串，由应用服务按各自规则解析并校验：

| 参数 | 取值要求 | 失败语义 |
|---|---|---|
| 本院报告匹配开关（`own_hospital_match_switch`） | 字符串 1 或 0，1 表示开启、0 表示关闭 | 不存在、非法或服务失败即整次失败 |
| 本院报告排除时长（`own_hospital_exclude_hours`） | 非负整数小时，允许零 | 不存在、非法或服务失败即整次失败 |
| 引用详情有效时长（`citation_detail_valid_hours`） | 正整数小时 | 不存在、非法或服务失败即整次失败 |

**本阶段是该服务在本项目的首个调用点**：本项目的 `server/` 下当前没有任何系统参数调用代码，因此严格失败语义的实现与取证均无本项目内既有先例，需在实施时以取值缺失、取值非法与参数服务异常三类前置分别取得证据。

### 并发与失败语义

MVP 不重并发：仅在引用表按匹配项标识建唯一索引兜底，撞键时数据库异常按原样向外传播，不加锁、不重试、不做并发压测。处理结果与引用结果的整批原子性由显式事务保证，逐个写入后比对影响行数，不为 1 即失败并整批不保存。

业务失败一律抛出现有框架的异常，不新增异常中间件、过滤器、响应转换器或错误包装模型；业务方不做任何异常捕获与加工，数据库异常按原样向外传播。

### 与阶段 4 的衔接

阶段 4 报告采集与生命周期能力已交付：其批次 0–5 完成、10 张报告表已按三批建成、目标库与 schema 已确认，其代码、建表脚本与设计文档均已纳入版本控制。

匹配查询依赖报告主体上的两类索引：按组织、医院、院区与报告时间的组合索引 `ix_mrec_medical_recognition_report_scope`，以及业务键唯一索引 `ux_mrec_medical_recognition_report_business_key`。两者已由阶段 4 交付，本阶段只在前置依赖中声明、不重复交付。阶段 4 在报告主体上共交付四条索引，另两条为患者姓名前缀索引与证件号码前缀索引，供其管理端报告列表筛选使用，本阶段不依赖。专项内容表的物理类型与宽度问题同属阶段 4 范围。PDF 下载接口本身归阶段 4，阶段 4 已交付该动作（控制器 `ReportPdfFileController`，路由前缀 `api/v1/report-pdf`，下载动作 `GET api/v1/report-pdf/{reportId}/versions/{reportVersionId}/pdf`）；本阶段响应只提供文件标识、下载入口与原始文件名，不新增下载接口、不改动该动作。

**来源医疗机构名称的回填。** 报告侧只保存来源组织、医院、院区三个编码，不保存名称——报告主体表只有这三个编码列，报告版本表只有来源报告名称与各类科室、医生名称。匹配响应与引用详情的来源医疗机构名称按报告主体的来源三值经既有 `OrganizationPathResolver` 批量解析取得：该解析点为 `ResolveOrThrow`，接收一批目标组织路径并按输入顺序返回三层业务编码与名称，阶段 4 的报告列表查询已在该解析点批量回填名称。读取次数只随本批涉及的不同组织与医院数量增长，不随条目数增长，与阶段 4 列表查询的名称回填同一解析点、同一口径。该解析点按存在、启用与父子归属校验三层，来源侧任一层不成立时按既有文案整次失败。本阶段不为此新增冗余名称列。
