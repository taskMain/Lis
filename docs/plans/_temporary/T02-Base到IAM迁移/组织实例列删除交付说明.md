# 组织实例标识列删除交付说明

配套脚本（两个文件，分别执行）：
- 回收：`server/Dy.MedicalRecognition.Repository/Scripts/Migrations/20261025_t02_drop_organization_instance_ids.up.sql`
- 回滚：`server/Dy.MedicalRecognition.Repository/Scripts/Migrations/20261025_t02_drop_organization_instance_ids.down.sql`
脚本只包含 up 与 down 两段纯 DDL，执行前后的核对语句收在本说明内，不写进脚本文件（脚本需通过仓储 SQL 的数据库方言中立校验）。

## 1. 回收对象

`20261023_t02_organization_instance_ids.sql` 在四张业务表上新增的 10 个 uuid 列：

| 表 | 列 |
| --- | --- |
| `mrec_medical_recognition_report` | `organization_id`、`hospital_id`、`branch_id` |
| `mrec_recognition_match_record` | `receiver_organization_id`、`receiver_hospital_id`、`receiver_branch_id` |
| `mrec_organization_hospital_branch_recognition_amount` | `organization_id`、`hospital_id`、`branch_id` |
| `mrec_mutual_recognition_item` | `organization_id` |

组织范围在业务表上以 IAM 组织业务编码表达（`organization_code`、`hospital_code`、`branch_code` 及匹配记录的 `receiver_*` 编码列）。写入、查询过滤、分组投影与统计排序都只使用编码列；唯一键与范围索引本就落在编码列，因此删除上述列不改变任何业务键、索引或约束，不需要重建索引。

## 2. 执行前置条件

1. 已部署的后端版本不再读写这 10 个列：建表脚本与全部 SqlMap 中无对应列，实体、命令、查询类型与读模型上无同名属性。
2. 目标库已完成本脚本之前的全部迁移，且四张表的编码列已按组织业务编码就绪（见第 3 节的空值核对）。
3. 已确认没有其他系统或离线作业直接读取这 10 个列。
4. 已备份目标库或至少备份上述四张表。

## 3. 执行前核对

结构核对：应返回 10 行。

```sql
select table_name, column_name, data_type, is_nullable
from information_schema.columns
where table_schema = 'public'
  and table_name in ('mrec_medical_recognition_report',
                     'mrec_recognition_match_record',
                     'mrec_organization_hospital_branch_recognition_amount',
                     'mrec_mutual_recognition_item')
  and column_name in ('organization_id', 'hospital_id', 'branch_id',
                      'receiver_organization_id', 'receiver_hospital_id', 'receiver_branch_id')
order by table_name, column_name;
```

编码列核对：四张表的编码列应存在，且没有空值行（空值行在删列后将无法按组织检索）。

```sql
select 'report' as tab, count(*) filter (where organization_code is null or btrim(organization_code) = '') as blank_rows
from mrec_medical_recognition_report
union all
select 'match_record', count(*) filter (where receiver_organization_code is null or btrim(receiver_organization_code) = '')
from mrec_recognition_match_record
union all
select 'amount', count(*) filter (where organization_code is null or btrim(organization_code) = '')
from mrec_organization_hospital_branch_recognition_amount
union all
select 'mutual_item', count(*) filter (where organization_code is null or btrim(organization_code) = '')
from mrec_mutual_recognition_item;
```

索引核对：唯一键与范围索引应全部落在编码列，确认没有索引引用待删除列。

```sql
select tablename, indexname, indexdef
from pg_indexes
where schemaname = 'public'
  and tablename like 'mrec_%'
  and (indexdef like '%organization_id%' or indexdef like '%hospital_id%' or indexdef like '%branch_id%');
```

期望：空结果。若有命中，先处理该索引再执行删列。

## 4. 执行

只执行 `.up.sql`。

不要执行整个合并文件：早期交付版本把 up 与 down 放在同一文件，整份执行会先删列、随后 down 段立即把列重建为空列，表面上执行成功，实际列仍在且原值丢失。该版本已删除并拆分为 `.up.sql` 与 `.down.sql`。

判断是否发生过这种误执行：目标列仍然存在，且这些列全为 NULL 并保留「组织实例ID」注释，即说明列被重建过一次，需要重新只执行 `.up.sql`。

## 5. 执行后核对

结构核对：与第 3 节同一查询应返回 0 行。

编码列核对：第 3 节的编码列查询应仍能执行，且业务表上的 `organization_code`、`hospital_code`、`branch_code`（及匹配记录的 `receiver_*` 编码列）仍然存在。

索引核对：唯一键与范围索引仍存在。

## 6. 回滚

执行脚本的 down 段，即可按 `20261023_t02_organization_instance_ids.sql` 原文重建这 10 个列与列注释。重建后列内容为空，不还原历史取值。

## 7. 已知后果

- 既有业务行的编码列中，早于本次口径切换写入的取值是组织实例标识的文本形式。删除列后这些行仍保留，但不再匹配按组织业务编码的过滤，等于从列表、统计与导出中不可见。已确认不回流历史数据；测试数据使用 IAM 现有组织重新建立。
- 编码列中取值为空的行在删列后同样无法按组织检索，执行前应完成第 3 节的空值核对。
