# T01 项目导出功能 · 实施交接文档

本文档是负责人交给实施方的开发指令，与票据（`T01-Tickets/`）配合使用。阶段文档是设计的唯一权威；本文档只补充过程要求，与阶段文档冲突时以阶段文档为准。

## 一、任务定位与当前状态

- **当前阶段**：T01 项目导出功能（临时阶段），目录 `docs/plans/_temporary/T01-项目导出功能/`。
- **交付目标**：「互认项目」「互认项目金额维护」「本院区互认项目金额」三个管理端页面各新增 Excel 导出，后端 ClosedXML 生成、三页列表上沿按钮、宿主链路验收，最终同步回正式阶段文档。
- **阶段文档**：根 `design.md`、`impl.md`、`testReport.md`，`Server/design.md`、`Server/impl.md`，`Client/design.md`、`Client/impl.md`、`Client/testPlan.md`。设计已通过三轮独立审查（58 项 finding 全部闭环），**负责人已批准进入实施**。
- **票据**：`T01-Tickets/` 下 01~08 共八票，依赖链为 01→02→03→04→05→06→07→08。你的**第一项动作**是完成工单 01 的机械部分：把决策台账转正（T01-D1~D7、D9 → `DesignConfirmed`，T01-D8 → `AcceptedRisk`），`impl.md` 批次 0 关闭，勾选工单 01；然后按依赖序推进 02 → 08。
- **证据归属**：验证矩阵为 T01-V1~V11（`Server/design.md`）与 T01-C1~C10（`Client/testPlan.md`），分母 21；证据按 `impl.md` 批次归属登记到阶段根 `testReport.md`。工单决定执行顺序，阶段文档是证据与设计的权威载体。

## 二、工作方式与团队要求

1. 开发全程使用 **Agent Team** 功能组织工作；开始之前先阅读 `AGENTS.md`，评估分析当前任务，准备匹配的 team 成员。
2. 团队成员在开发之前**按需加载对应规范**（规范入口全部在 `AGENTS.md` 第 5 节导航，不预读无关主题）。
3. 使用技能 **/implement** 推进票据；全程使用 **/ponytail full**；开发模式使用 **/tdd**；操作浏览器使用技能 **dy-dev-browser-debugging**。
4. 团队中**必须设审查角色**：对应开发完成后派出审查是否严格按照规范开发，发现问题提出、由具体开发整改并复验。
5. **进度及时同步**：每完成一项就更新阶段文档的对应位置（`impl.md` 批次状态、`Server/impl.md`、`Client/impl.md` 执行状态、根 `testReport.md` 证据行），并勾选票据验收项。不要只标票据完成，不要等全部完成才回头补阶段文档。
6. 完成检查按规范执行：适用测试、构建、静态检查、`git diff --check`、GitNexus `detect-changes`。

## 三、开发与测试边界（负责人强调项）

1. **MVP 心态**：当前是 MVP 开发，不注重并发，不要在并发上花重资源。
2. **账号**：只有测试规范（Test Environment）中的两个测试账号可用（平台管理员与医院管理员），无法提供第二个组织编码。
3. **不测正常业务不可达的数据**：无法提供医院编码为空、院区编码为空的账号（权限系统限制），这类用例不要设计、不要浪费资源；设计矩阵中已有的 `N/A`/降级登记口径照执行即可。
4. **造数方式**：开发阶段数据不够，就用对应接口造数或用页面造数；数据库仍然只读，不直接写库（AGENTS 闸门）。
5. **数据脏正常**：开发阶段的测试数据、冗余数据、孤岛数据、错误数据很正常，不要在上面浪费时间。
6. **不做框架事务的构造测试**：类似「一个命令改多表、部分失败整体回滚」这类测试，当前框架下无法强行构造错误，且属于框架层事务控制，业务方无法修改框架，不要为此设计测试。
7. **权限零扩散**：前后端不做任何权限相关的扩散开发。能访问接口即认定有权限；前端能打开页面即认定有权限，不再做二次确认。
8. **异常零加工**：后端与既有阶段完全一致——遇到问题直接抛出异常，不做任何包装、加工或特殊处理（这是框架行为，提前包装会在框架升级时冲突）；数据库报错原样抛出。前端异常由宿主统一处理，与既有阶段一致，不做多余处理。
9. **唯一性等可提前判定的问题先查再写**：面向可能出现的唯一索引冲突，正确做法是先检查数据是否已存在、存在即按业务拒绝抛出，而不是等数据库唯一索引报错。举一反三：凡能提前发现的问题都不应等数据库爆出来。（注意：本阶段导出为纯只读链、无写用例，此条主要作为团队通用纪律。）

## 四、文档与沟通纪律

1. **批注必须落成设计**：沟通中负责人输出的设计与批注，要写成具体的设计表述，**不得**在文档中引用「负责人批注」「方案 A」等会话内容。例：批注说「按钮应该是蓝色」→ 文档写「按钮是蓝色」，不写「按钮颜色依据负责人批注」。本阶段设计已定稿，此条约束实施过程中的任何文档新增。
2. **不引用讨论内容.md**：该文档只用于讨论，正式阶段文档不得引用它（该文档随后会被删除）。
3. **只管当前阶段**：负责人可能手动运行 GitNexus 更新索引、生成一些技能或其他文件——不用处理、不用汇报；除当前阶段文档外，其他文档的增删剪裁都不要处理、不要汇报。提交（commit）只在负责人明确要求时执行，要求提交时全部包含即可。
4. 阶段文档只写最终设计状态，不写「本轮修改」补丁章节（`planning-and-evidence` 文档一致性条款）。

## 五、流程纪律

1. **不使用 goal/plan 功能**。
2. 设计已确认，**直接开始**：按票据依赖开发，该并行的并行（02 完成后 03 → 04 → 05 为串行主线，因其共用文件与基础设施；06 收口于 03~05 之后），推进到所有票据完成，或遇到真实阻塞。
3. **除非真实业务阻塞（你无法做主），不要向负责人提问**，负责人不会守在电脑前；提问可能导致整夜停滞。其他开发问题一律自己做主。遇到真实阻塞就直接停在该处并记录清楚阻塞原因与已尝试的路径，不要用提问功能、不要用 plan 功能空转。
