## 2. 任务 A：可信组织上下文（S2-D12 / V11、V19、V22、V27）

### A1 组织编码来源与类型 —— 已取证

组织编码为 **`String`**，服务端取自框架请求上下文的 `HttpRequestInfo.OrgId`，其值为 Bearer token 的 `org` claim。

### B2 谁 Flush、何时可见 —— 已取证（源码确认）

`Dy.Apron.Http` 1.1.0.48 → `ActionUnit.EventBusActionUnitFilter`：

- `OnExecuting`：`EventBusFactory.CurrentEventQueue = excutingContext.HttpContext.RequestServices.GetRequiredService<IEventQueue>()`
- `OnCompletedAsync`：`await EventBusFactory.CurrentEventQueue.FlushAsync();`
- `OnFailedAsync`：`EventBusFactory.CurrentEventQueue.Clear();`

`Dy.Apron.Bridge` 1.1.0.48 → `EventBus.EventQueue.FlushAsync`：先在锁内**快照并清空** `eventFactories`，再逐条 `localEventBus.PublishAsync(...)`；`IDistributedEvent` 额外走 `distributedEventBus`；处理器异常被收集到 `exceptions` 后经 `ThrowExceptions` **重抛**（队列已清空，不会重放）。`EventBusBase.PublishAsync` 在 `IServiceProvider` 内同步查找并 `await handler.TriggerAsync(...)`。

**时点结论**：事件处理器在**同一 HTTP 请求内、业务方法返回成功结果之后、响应产出之前**被同步触发；Flush 由框架完成，业务代码不参与，也不存在"提交后才发布"的保证。

### B3 失败语义 —— 已取证（源码确认）

| 场景 | 数据库提交 | 事件 | 异常传播 | 可重试 |
|---|---|---|---|---|
| 正常（无 `[WorkUnit]`） | 单条语句由 Provider 语句级原子性落地；`TransactionActionUnitFilter.IsHandleTransaction()` 依赖 `HttpContextInfo.Current.TransactionInfo.IsActionUnitTransaction()`，无 `[WorkUnit]` 时 `TransactionInfo == null` ⇒ **不 Begin/Commit/Rollback** | 请求完成时 `FlushAsync`，本项目无 `ILocalEventHandler<>`/`IDistributedEventHandler<>` 实现 ⇒ 无处理器被触发 | 无异常 | 无 |
| 写入失败（Repository/Domain 抛异常） | 无显式事务 ⇒ **已执行的语句不会回滚**（无 `Rollback` 调用） | `OnFailedAsync` → `Clear()`，队列丢弃 | `WorkUnitEndpointFilter` 捕获后 `FailedAsync` 再 `throw` | 无自动重试 |
| 事件处理失败（FlushAsync 内处理器抛异常） | 事件 Flush 在 `CompletedAsync` 内、提交之前，但无事务 ⇒ **写入已落地且不回滚** | `FlushAsync` 重抛；`throw` 进入 `WorkUnitEndpointFilter` 的 catch ⇒ `FailedAsync` → `Clear()` | 客户端得到失败响应 | **不可重试**（队列已清空，无持久化队列/Outbox） |
| 事务路径（对比，不属于本阶段） | `[WorkUnit(UseTransaction=true)]` ⇒ `TransactionActionUnitFilter` 先于提交执行 `EventBusActionUnitFilter.OnCompletedAsync`，即事件处理器先于 Commit 观察到事件 | 同上 | 提交失败时事件可能已处理 | — |

失败响应的形态：`ResultActionUnitFilter.OnFailedAsync` 仅当 `WrapMode != UnWrap` 时把异常转成响应；本项目 `HttpConfig.WrapResult = "Disable"`（`ResultWrapMode.Disable = 0` ⇒ `ActualWrapMode.UnWrap`），故异常继续向外抛，由宿主 ASP.NET 管线产生失败响应——与阶段 1 观测到的 HTTP 500 现象一致。

### B4 本项目当前实现与设计的差异（静态事实，供实现批次使用）

`MedicalRecognitionReportManager` 的四个互认方法当前**无条件**在写入后登记事件，登记语句位于 `result > 0` 判断之前：

```text
:234-235  修改：var result = await repository.Update...; AddEvent(...); return result > 0;
:239      启用：var result = await repository.Enable...;   AddEvent(...); return result > 0;
:243      停用：var result = await repository.Disable...;  AddEvent(...); return result > 0;
:229-230  创建：写入后无条件 AddEvent（未校验影响行数）
```

即当前生成物与设计"恰好 1 行才登记、0 行或异常不登记"（V16）不一致，属待实施整改项，不是运行结论。
