# 简介

## 目的

本文档用于定义检验检查结果互认平台的软件需求规约，明确当前版本的业务范围、参与者、前置条件、后置条件、主事件流、备选流、业务规则、关键属性、设计约束和用户界面要求，作为后续设计、开发、测试、评审和验收的业务依据。

本文档适用于检验检查结果互认平台及其与标准项目管理系统、平台权限体系、医院侧采集服务和医院 HIS 之间的业务协作。医院 LIS、PACS 及医院侧采集服务的内部实现不属于互认平台的建设范围，本文仅在相关功能中描述其与互认平台之间必要的业务责任和交互边界。

本文档不替代接口设计文档、数据库设计、技术架构、安全设计、部署方案或医院院内系统改造方案。本文未定义具体路由、报文结构、数据传输协议、数据库表、代码模型、后台任务或其他技术实现。

## 定义、首字母缩写词和缩略语

| 术语或缩写 | 定义 |
| --- | --- |
| HIS | Hospital Information System，医院信息系统。医院根据自身接诊或开单流程调用互认平台能力、向医生展示候选并反馈处理及引用结果。 |
| LIS | Laboratory Information System，实验室信息系统。医院侧采集服务可以从 LIS 获取审核完成的检验报告，但互认平台不规定其内部采集方式。 |
| PACS | Picture Archiving and Communication System，医学影像存档与通信系统。互认平台不接收或保存 DICOM 影像文件，只处理检查报告随附的影像调阅地址及来源影像状态。 |
| 标准医疗项目 | 由标准项目管理系统统一维护的医疗项目，是各业务平台进行项目语义对齐的共同基准。 |
| 互认项目 | 互认平台从标准医疗项目中选定并保存、允许进入结果互认业务范围的最细层项目。互认项目保存标准项目编码和名称、可互认时间、当前参考价格、启停状态和来源状态。 |
| 可互认时间 | 从报告时间开始计算、报告可以作为互认候选返回的时间长度。查询使用互认项目的当前配置，该配置不用于报告接收校验，也不是报告保存期限。 |
| 院内项目 | 医院某一院区在本地业务系统中实际使用的检查或检验项目及其编码。相同编码在不同医院或院区不必具有相同语义。 |
| 项目编码对照 | 医院在当前医院和院区范围内维护的院内项目与互认项目之间的语义对应关系。普通检验结果和检查项目明细通过当前有效对照关联互认项目。 |
| 来源不可用 | 互认项目所引用的标准医疗项目已不在标准项目管理系统当前有效目录中的状态。该状态保留既有业务数据，但阻止相关新增对照、新报告上传和已有报告查询。 |
| 报告业务标识 | 由医院、院区、报告类型和报告单号共同组成，用于在互认平台唯一识别一份检验或检查报告。 |
| 报告操作类型 | 医院提交报告时明确提供的新增、更正或作废业务指令。新增和更正提交完整报告，作废提交报告业务标识及作废信息。 |
| 报告版本 | 一份报告在新增或更正过程中形成的内容版本。更正形成新版本并保留版本关系，原版本停止参与后续候选查询和新的引用。 |
| 当前有效报告 | 当前未被作废、且在存在更正时属于最新有效版本的报告。是否能够成为互认候选，还需满足互认项目状态、可互认时间及候选查询的其他规则。 |
| 混合项目报告 | 同时包含已对码和未对码项目明细的完整报告。至少有一个明细完成有效对码时可以接收整份报告，未对码明细只用于保持报告完整、展示和来源追溯。 |
| 互认候选 | 平台针对一个去重后的互认项目，按照候选选择规则确定并返回的一份当前有效报告。联合报告可以同时为多个互认项目形成候选，但报告内容不按项目拆分为多份报告。 |
| 互认候选引用 | 平台为每个“候选报告版本 + 互认项目”提供的稳定引用，用于医院 HIS 后续提交互认处理结果、获取引用详情和提交引用结果。 |
| 互认时间 | 医生实际作出某次采纳或不采纳决定的业务时间，由医院 HIS 提供并精确到秒，用于区分同一就诊中针对同一候选发生的多次真实互认处理。 |
| 互认处理结果 | 医生明确作出的采纳或不采纳决定。候选返回、结构化内容展示、PDF 或影像入口访问均不自动形成互认处理结果。 |
| 引用详情 | 医生采纳候选后，医院 HIS 获取的、可用于写入本次病历的项目内容及必要报告公共上下文。获取引用详情本身不表示已经成功写入病历。 |
| 引用结果 | 医院 HIS 将已采纳内容成功写入本次病历后向平台提交的实际引用事实。平台只接收已经引用的正向事实，不要求提交未引用状态。 |
| 提醒次数 | 平台成功处理候选查询并针对一个去重后的互认项目返回候选时形成的统计次数。提醒次数不表示医院 HIS 已实际弹窗，也不表示医生已经查看、采纳或引用。 |
| 预计节省金额 | 医生采纳互认项目时，按照该互认项目当时的当前参考价格形成的业务统计金额。该金额不表示实际收费、医保结算、患者退费或医院财务收入。 |
| 平台科室 ID、平台医生 ID | 平台权限体系中用于标识科室和医生的业务接口标识。平台根据 ID 校验医院及院区归属、查询名称，并将 ID 和当次名称随业务记录保存。 |

## 概述

本文后续内容按照以下结构组织：

1. “整体说明”描述产品总体效果、产品功能、用户特征、约束、假设与依赖关系，以及当前版本范围和排除项。
2. “具体需求”的“功能”部分按照稳定功能编号描述互认项目管理、项目编码对照、报告采集与生命周期、互认候选查询、互认处理结果、引用详情、引用结果、统计分析和统计导出。每项功能统一说明参与者、需求背景、前置条件、后置条件、主事件流、备选流、业务规则和关键属性。
3. “具体需求”的“设计约束”部分描述已经确认且必须遵守的业务设计边界，不定义技术选型或内部实现。
4. “具体需求”的“接口”部分只描述平台用户界面的业务级要求。医院 HIS 在线互认能力仍在对应功能需求中表达，不在本文中另行定义软件接口技术规格。

# 整体说明

## 产品总体效果

检验检查结果互认平台用于统一跨医疗机构的检查、检验项目语义，接收和管理医院审核完成的检查、检验报告，并在患者接诊或开单过程中向医院 HIS 提供可互认候选。医生在医院 HIS 中查看候选内容后作出采纳或不采纳决定；采纳后，医院 HIS 可以获取引用详情，将相应内容写入本次病历并反馈实际引用结果。

平台通过互认项目和医院项目编码对照解决不同医院、院区使用不同院内项目编码的问题，通过患者精确关联、报告版本管理和候选选择规则保证候选业务身份明确。平台记录医院明确反馈的互认处理和引用事实，并面向医院及平台管理员提供权限范围内的统计、下钻和 Excel 导出能力。

平台不代替医生作出临床决定，不直接操作医院 HIS 中的医嘱或病历。候选返回、结构化内容展示、PDF 查看或影像入口访问均不自动表示医生已经采纳或引用。报告中的来源异常、危急值、检查所见和诊断结论均按来源内容保存和展示，平台不重新计算、推断或改写临床结论。

## 产品功能

| 编号 | 功能 | 说明 |
| --- | --- | --- |
| F01 | 互认项目管理 | 从当前有效的标准医疗项目中选取互认项目，维护可互认时间、当前参考价格、启停状态和来源状态。 |
| F02 | 项目编码对照管理 | 医院在当前医院和院区范围内维护院内项目与互认项目之间的对应关系。 |
| F03 | 报告采集与生命周期 | 接收检验报告和检查报告的新增、更正及作废，保存完整结构化内容、PDF、版本关系和必要来源信息。 |
| F04 | 互认候选查询 | 根据患者身份和一个或多个拟开院内项目返回符合条件的互认候选，并对联合报告进行完整分组；没有候选时返回空候选集合。 |
| F05 | 互认处理结果 | 接收医生明确作出的采纳或不采纳决定，支持引用前的决定更正，并形成对应统计事实和预计节省金额。 |
| F06 | 获取引用详情 | 在互认决定为采纳且候选报告版本仍有效时，返回本次病历引用所需的项目内容和报告公共上下文。 |
| F07 | 提交引用结果 | 接收医院 HIS 已成功写入本次病历的实际引用事实，记录实际引用时间、科室和医生。 |
| F08 | 互认统计与分析 | 提供提醒、采纳、不采纳、引用、同期互认率、预计节省金额、接收医院使用和来源医院被互认分析。 |
| F09 | 互认统计导出 | 按当前查询条件、数据权限和脱敏规则导出互认汇总及明细，文件格式为 Excel。 |

平台面向医院 HIS 的在线互认主流程由查询互认候选、提交互认处理结果、获取引用详情和提交引用结果四类核心业务能力组成。报告采集、身份认证、项目编码对照、报告更正或作废等其他能力不计入这四类核心业务能力。

端到端业务过程如下：

1. 平台管理员从标准医疗项目中选取并维护互认项目。
2. 医院在当前医院、院区范围内维护院内项目与互认项目的编码对照。
3. 医院侧采集服务在检查或检验报告审核完成后自动增量提交报告；平台校验并保存符合接收条件的完整报告。
4. 医院 HIS 在患者接诊或开单过程中，以患者身份和拟开院内项目发起互认候选查询。
5. 平台解析项目编码对照，按当前有效报告、可互认时间和候选选择规则返回符合条件的候选结果。
6. 医院 HIS 向医生展示候选结果及可用的 PDF、影像入口；医生根据患者当前情况作出采纳或不采纳决定。
7. 医院 HIS 提交互认处理结果；平台记录实际决定、互认时间、科室、医生、不采纳原因或预计节省金额。
8. 对于已采纳候选，医院 HIS 获取引用详情并将相应内容写入本次病历，写入成功后提交引用结果。
9. 平台依据候选返回、当前有效互认决定和实际引用事实形成权限范围内的统计、下钻和导出结果。

## 用户特征

| 用户或外部参与方 | 特征与职责 |
| --- | --- |
| 平台管理员 | 维护互认项目及其业务配置；查看全县范围内的项目编码对照并在异常情况下按权限停用；查看、下钻和导出全县范围的接收侧互认使用统计及来源侧被互认统计；不代替医院执行日常对码。 |
| 医院管理员 | 在当前登录医院和院区范围内维护院内项目编码对照，核对并处理本院对码问题；在本院及有权院区范围内查看接收侧互认使用统计、来源侧被互认统计及相应脱敏明细，并按权限导出。 |
| 医院侧采集服务 | 由医院或实施厂商负责，在来源报告审核完成后自动增量提交报告，并处理明确失败、超时重传、更正和作废。该服务不属于互认平台的建设模块。 |
| 医院 HIS | 决定在线互认能力在接诊或开单流程中的调用时机，展示候选，提交互认处理结果，获取引用详情，将内容写入病历并反馈引用结果。 |
| 医生 | 在医院 HIS 中查看候选结构化内容、报告 PDF 或影像，根据患者当前情况作出采纳或不采纳决定；平台不代替医生判断。 |

医院侧采集服务、医院 HIS、LIS、PACS 和影像服务由医院或相应厂商建设和维护。互认平台只定义与其发生业务协作时的输入、输出、责任和状态边界，不规定医院内部页面、数据读取方式、采集表、轮询周期、本地队列、硬件或网络实现。

## 约束

1. 平台只接收上线后新产生并审核完成的检查、检验报告，不导入上线前历史报告。
2. 一份报告至少包含一个能够通过当前有效项目编码对照关联互认项目的明细时，平台才接收整份报告；已对码和未对码明细共同保留，未对码明细不形成候选。
3. 报告接收不按可互认时间进行筛选，但只将当前启用且来源有效的互认项目关系视为有效对码。互认项目停用或来源不可用时阻止相关新报告上传；可互认时间在候选查询时按当前配置判断。
4. 跨院患者以证件类型和证件号码精确关联，并使用姓名、性别代码和出生日期进行一致性校验。平台不使用姓名相似度、电话或院内就诊卡进行替代匹配。
5. 报告上传、互认处理和引用结果涉及的科室、医生只接收平台科室 ID、平台医生 ID。任一 ID 不存在或不属于当前调用医院、院区时，按对应功能的整体校验规则拒绝保存。
6. 平台科室或医生 ID 存在且归属正确但已经停用时，允许医院补交真实的报告、互认处理或引用事实。平台不校验医生当前所属科室与同一业务记录中的科室一致。
7. 平台根据科室、医生 ID 查询并保存当次名称。科室或医生以后改名时，不动态修改已有业务记录保存的名称。
8. 每次报告变更请求只处理一份报告。新增和更正提交完整结构化报告及 PDF，二者作为一个提交单元共同成功或共同失败；作废只提交报告业务标识和作废信息。
9. 报告按医院、院区、报告类型和报告单号唯一识别。相同标识和内容的重复提交按幂等成功处理，内容不一致时不得静默覆盖。
10. 报告更正保留版本关系并使原版本停止参与候选查询和新的引用；报告作废不物理删除，但作废后不再返回为候选或新的引用内容。
11. 每个互认项目只返回查询时点前、当前可互认时间内检查或检验时间最晚的一份有效报告；检查或检验时间相同时，优先选择报告时间较晚的一份；两者均相同时，在候选数据及相关配置未变化的情况下稳定返回同一份报告。
12. 一份联合报告命中多个互认项目时，按一份完整报告分组返回；互认候选、处理决定和引用事实仍按具体互认项目分别形成。
13. 平台不通过查询流水号或拟开项目业务标识区分互认处理。医院提供的互认时间精确到秒，相同业务归属和候选引用下不同互认时间表示不同的真实处理。
14. 候选查询、候选返回、结构化内容展示、PDF 查看、影像入口访问和引用详情获取均不自动形成采纳或引用事实。
15. 互认处理结果必须来自医生明确反馈的采纳或不采纳；引用结果必须来自医院 HIS 已经成功写入本次病历的正向事实。平台不根据未反馈状态推断拒绝、忽略、采纳或引用。
16. 不采纳必须使用平台统一原因代码；选择其他原因时必须提供补充说明。各医院不得自行扩展或修改原因代码。
17. 预计节省金额在采纳时按互认项目当时的当前参考价格形成，不采集数量，不模拟按次、按部位、组合收费、医保结算或患者实际退费。
18. 提醒、采纳、不采纳、引用和预计节省金额分别使用已确认的业务时间归入统计期间，接口接收时间不得替代业务时间。
19. 医院管理员只能查看本院及有权院区的数据，平台管理员按授权查看全县数据。统计页面和导出中的患者姓名、证件号码必须保持脱敏。
20. 本院报告候选由全局开关控制，默认关闭；开启后使用全局本院报告排除时长，默认四十八小时。参数调整只影响后续查询，不倒改已有报告、互认处理、引用和统计事实。

## 假设与依赖关系

1. 标准项目管理系统能够提供当前有效的标准医疗项目目录，并保证标准项目编码能够稳定标识相应项目。目录获取不完整或失败时，互认平台保留既有状态，不以不完整结果覆盖当前来源状态。
2. 医院在接入平台前已经将本医院、院区下需要参与业务的科室和医生维护到平台权限体系，并能够在院内系统中关联对应的平台 ID。
3. 平台权限体系能够根据平台科室 ID、平台医生 ID 返回其存在性、医院院区归属、停用状态和当前名称，并为平台页面提供必要的身份及数据权限控制。
4. 医院或实施厂商负责建设并运行医院侧采集服务。该服务能够从医院源系统识别审核完成、修订后重新审核或作废的报告，并明确提交新增、更正或作废操作。
5. 医院 LIS、PACS 或其他来源系统能够提供已确认字段中在源系统实际存在的内容；对于规定为“源系统存在时必须提供”的信息，医院不得在源系统存在时无故省略。
6. 医院 HIS 负责在合适的接诊或开单环节调用在线互认能力、向医生展示候选、执行院内医嘱或病历操作，并在真实业务动作完成后提交处理或引用结果。
7. 接入医院只上传依其制度允许常规跨院共享的报告。需要专项授权才能共享的报告在相关授权机制另行明确前不上传。
8. 检查报告的影像调阅地址由医院或区域影像中心提供并负责其可用性、访问控制、内容和保存期限。平台只在权限校验后提供入口，不保证外部影像服务持续可用。
9. 医院侧在调用超时或未取得明确处理结果时，使用相同操作类型和相同业务内容重新提交。平台依据业务标识、当前状态和内容一致性执行相应的幂等或冲突处理。
10. 医院 HIS 对已经接收并保存在院内的数据承担后续更新和失效处理责任。平台不通过主动推送补偿医院未反馈引用结果或未重新查询的情况。

## 当前版本范围与排除项

当前版本包含以下业务范围：

1. 互认项目及其可互认时间、当前参考价格、启停状态和来源状态维护。
2. 医院、院区范围内的项目编码对照维护。
3. 检验报告和检查报告的自动增量采集、新增、更正、作废、完整内容保存及版本管理。
4. 批量互认候选查询、项目去重、最近有效报告选择和候选结果返回。
5. 采纳、不采纳、决定更正、不采纳原因和预计节省金额记录。
6. 引用详情获取和实际引用结果记录。
7. 接收医院使用统计、来源医院被互认分析、不采纳原因统计、明细下钻及 Excel 导出。
8. 与上述业务相关的医院院区归属校验、科室医生关联、页面数据权限和患者信息脱敏。

当前版本明确不包含以下能力：

1. 同一互认项目返回多个独立历史报告、历史趋势或多版本候选。
2. 独立的调阅状态、调阅反馈接口、调阅统计，或者以结构化内容、PDF、影像入口访问推断医生已查看、采纳或引用。
3. DICOM 影像文件上传、存储、代理或缓存，以及 PACS 影像号、检查实例 UID、序列 UID 等影像技术标识采集。
4. 平台上线前历史报告导入。
5. 查询业务流水号、调用方事件标识、拟开项目业务标识或通用传输批次设计。
6. 报告更正或作废后的下游主动推送、PushCenter 接入、推送记录、状态核对、自动恢复或人工恢复。
7. 医院 HIS 页面人工逐份上传报告、平台逐份审批正常报告或平台修改报告临床内容。
8. 医院内部 LIS、PACS、采集服务的数据读取、采集表、轮询、本地队列、硬件和网络实现。
9. 患者姓名模糊匹配、概率匹配，或者根据电话、院内就诊卡等信息替代跨院患者标识。
10. 标准编码、LOINC、菌种代码、药敏代码、检查部位代码、临床诊断、检查所见、检查结论或结果异常状态的自动推断、换算和重判。
11. 来源保密标识驱动的敏感报告分级、患者专项授权、上传医院逐份审批或特殊调阅流程。
12. 危急值通知、确认、回执、超时提醒、升级提醒或闭环处置；平台只保存和展示来源危急值标志。
13. 每次收费、按部位收费、组合收费、数量计费、医保结算、患者退费或医院财务收入模拟。
14. 互认项目参考价格的独立版本、变更历史或历史价格恢复，以及根据新价格重算既有预计节省金额。
15. 通用重量级审计、报告完整操作过程日志、医院实验室仪器原始日志或质控过程重建。
16. 报告采集前置机作为平台建设模块，以及医院侧采集任务、失败任务或传输状态管理页面。
17. 趋势图、医生互认率、预计节省金额排名、医生绩效排名或其他医生考核能力。
18. CSV、PDF 或其他统计导出格式，以及通过导出解除脱敏或扩大数据权限。
19. 本院报告按医院分别配置不同的候选规则，或者为本院报告开关和排除时长单独建设配置模块。
20. 已形成引用事实后的引用撤销，或者将对应互认决定从采纳更正为不采纳。

# 具体需求

## 功能

### F01 互认项目管理

#### 参与者

| 参与者 | 职责 |
| --- | --- |
| 平台管理员 | 获取标准医疗项目目录，选择互认项目，维护可互认时间、参考价格和启停状态。 |
| 标准项目管理系统 | 提供当前有效的最细层标准医疗项目及其类型、类别和分组信息。 |

#### 需求背景

不同医院需要使用统一的项目语义开展结果互认。平台从标准医疗项目中选择当前允许参与互认的最细层项目，并维护候选查询和预计节省金额所需的业务配置。

#### 前置条件

1. 操作人员具有互认项目管理权限。
2. 标准项目管理系统已配置为平台可调用的目录来源。
3. 新增互认项目所引用的标准医疗项目属于当前有效目录中的最细层项目。

#### 后置条件

1. 新增成功后形成一条默认启用的互认项目，保存标准项目编码和名称、可互认时间、当前参考价格、启停状态及来源状态。
2. 配置修改后，新的可互认时间、参考价格或启停状态按各自业务规则影响后续业务。
3. 项目停用或来源不可用时保留已有项目、编码对照、报告和历史业务事实。

#### 主事件流

1. 操作人员进入互认项目管理页面，平台自动获取一次当前有效标准项目目录；操作人员也可以手动刷新。
2. 平台在完整获取成功后，以标准项目编码核对已选互认项目的来源状态。
3. 操作人员从当前有效的最细层项目中选择一个、多个或全部项目。
4. 操作人员为每个拟新增项目填写可互认时间和参考价格。
5. 平台校验项目来源、必填配置和重复选择情况。
6. 校验通过后保存互认项目并默认启用。
7. 操作人员可以后续调整可互认时间、当前参考价格和启停状态。

#### 备选流

1. 标准目录获取失败或返回不完整时，平台提示刷新失败并保留原有目录核对结果和来源状态。
2. 已选标准项目不再属于当前有效目录时，平台将对应互认项目标记为来源不可用，不自动按名称或相似度替换。
3. 可互认时间或参考价格为空、格式不合法时，平台拒绝保存本次新增或修改。
4. 已存在相同标准项目编码的互认项目时，平台拒绝重复新增。
5. 停用项目重新启用时，只有其标准项目来源当前有效才允许启用。

#### 业务规则

1. 互认项目必须引用当前有效标准目录中的最细层项目。
2. 互认项目保存标准项目编码和名称，不保存项目类型、类别和分组；类型、类别和分组按需从当前标准目录获取。
3. 可互认时间从报告时间开始计算，只用于候选查询窗口，不用于报告接收校验或报告保存期限判断。
4. 可互认时间调整对已有报告的后续候选查询即时生效，不倒改已有互认处理或引用事实。
5. 每个互认项目必须维护一个参考价格。上线初始化时由县医院提供当时有效的价格清单，平台管理员据此录入；后续价格调整仍由平台管理员执行，不要求平台从价格系统自动同步。
6. 互认项目只保留当前参考价格，不建立独立价格版本或价格变更历史；框架已有修改时间和修改人用于记录维护操作。
7. 参考价格调整保存成功后只影响新形成的采纳决定，不重新计算历史预计节省金额。
8. 互认项目新增后默认启用，不提供物理删除。
9. 互认项目停用后，阻止相关新报告上传，相关已有报告立即停止参与候选查询；重新启用后按当前可互认时间及其他候选规则重新判断。
10. 来源不可用时，阻止新增或重新启用相关编码对照、上传新报告和查询已有报告。
11. 替代标准项目必须作为新的互认项目重新选择，医院应重新调整项目编码对照。

#### 关键属性

| 属性 | 说明 |
| --- | --- |
| 标准项目编码 | 被选标准医疗项目的稳定编码，创建后不可替换为其他项目编码。 |
| 标准项目名称 | 选择互认项目时保存的标准医疗项目名称。 |
| 可互认时间 | 从报告时间开始计算的候选有效时长，必填。 |
| 当前参考价格 | 形成新采纳决定预计节省金额的统一价格，必填。 |
| 启停状态 | 启用或停用；新增后默认启用。 |
| 来源状态 | 来源有效或来源不可用，由完整目录刷新结果确定。 |
| 修改时间、修改人 | 使用平台框架已有信息记录维护操作，不形成独立价格或配置版本。 |

### F02 项目编码对照管理

#### 参与者

| 参与者 | 职责 |
| --- | --- |
| 医院管理员 | 在当前医院和院区范围内新增、修改、启用或停用项目编码对照。 |
| 平台管理员 | 跨机构查看编码对照，并在异常情况下按权限停用对照。 |

#### 需求背景

各医院和院区使用的院内项目编码及名称不同。平台需要由医院自行维护院内项目与互认项目的语义对应关系，使报告上传和医院 HIS 候选查询能够解析到统一互认项目。

#### 前置条件

1. 操作人员已登录平台并具有项目编码对照管理权限。
2. 医院管理员的当前医院和院区能够从可信登录上下文确定。
3. 新建或重新启用对照所选择的互认项目当前启用且来源有效。

#### 后置条件

1. 新建成功后形成当前医院、院区下默认启用的项目编码对照。
2. 对照修改或启停只影响后续上传报告及后续院内项目解析，不重写已接收报告保存的互认项目关系。
3. 停用对照后保留既有对照和历史业务数据。

#### 主事件流

1. 医院管理员进入项目编码对照管理页面，平台按当前医院和院区限定数据范围。
2. 平台提供当前启用且来源有效的互认项目平铺列表，并支持按项目编码或名称搜索。
3. 医院管理员填写院内项目编码、院内项目名称，选择一个互认项目，并可填写备注。
4. 平台校验医院、院区、院内项目编码的唯一性及所选互认项目状态。
5. 校验通过后保存对照并默认启用。
6. 医院管理员可以修改院内项目名称、所选互认项目和备注，或者启用、停用对照。

#### 备选流

1. 当前医院、院区和院内项目编码已存在另一条启用对照时，平台拒绝新增或启用。
2. 所选互认项目停用或来源不可用时，平台拒绝新增、修改为该项目或重新启用相关对照。
3. 平台管理员发现异常对照时，可以按权限停用，但不代替医院修改日常对码内容。
4. 历史对码错误已经影响报告时，不通过修改对照重写报告，医院应对来源报告执行更正或作废。

#### 业务规则

1. 项目编码对照归属于确定的医院和院区，医院管理员不得跨越当前登录范围维护。
2. 唯一性按医院、院区和院内项目编码判断；一个院内项目同时最多存在一条启用对照。
3. 多个院内项目可以对照同一个互认项目。
4. 对照直接保存院内项目编码和名称，不依赖平台内独立的院内项目目录。
5. 医院、院区和院内项目编码创建后不可修改；需要改变上述身份时应新建对照并停用原对照。
6. 院内项目名称、互认项目和备注允许修改，修改只影响后续上传和解析。
7. 对照不维护或选择价格，预计节省金额使用互认项目的当前参考价格。
8. 新建对照校验成功后默认启用，不经过平台逐条审批。
9. 对照不物理删除；停用只阻止后续报告上传，不改变已接收报告保存的互认项目关系。
10. 平台管理员可以跨机构查看和异常停用，但医院负责本院日常对码及正确性。

#### 关键属性

| 属性 | 说明 |
| --- | --- |
| 医院、院区 | 对照的数据归属，来自创建时的可信组织范围，创建后不可修改。 |
| 院内项目编码 | 医院院区本地业务系统使用的项目编码，创建后不可修改。 |
| 院内项目名称 | 医院项目名称，允许修改且只影响后续上传。 |
| 互认项目 | 当前院内项目对应的互认项目，允许修改且只影响后续上传和解析。 |
| 启停状态 | 启用或停用；新增后默认启用。 |
| 备注 | 对照维护的补充说明，可选。 |

### F03 报告采集与生命周期

#### F03.1 公共报告要求与生命周期

##### 参与者

| 参与者 | 职责 |
| --- | --- |
| 医院源系统 | 在报告首次审核完成、修订后再次审核或作废时形成明确业务事件。 |
| 医院侧采集服务 | 将一份报告的新增、更正或作废操作提交到互认平台，处理失败重传和结果未知重试。 |
| 互认平台 | 校验患者、就诊、组织人员、项目对照、报告内容和操作条件，保存报告及版本关系并同步返回最终处理结果。 |
| 平台权限体系 | 校验科室、医生的存在性和医院院区归属，并提供当次名称。 |

##### 需求背景

平台需要持续接收上线后新产生并审核完成的检查、检验报告，保持来源报告的结构化内容和原始 PDF，并通过明确的新增、更正和作废操作管理报告有效性。医院侧采集服务是外部参与方，平台不规定其内部采集实现。

##### 前置条件

1. 来源报告已经完成医院内部审核，操作类型已明确为新增、更正或作废。
2. 新增或更正报告至少包含一个能够通过当前有效项目编码对照关联到当前启用且来源有效互认项目的项目明细。
3. 报告携带有效的跨院患者标识、必填人口学信息、来源就诊标识及规定的报告公共信息。
4. 报告涉及的平台科室 ID、平台医生 ID 已在当前调用医院和院区范围内存在。
5. 新增和更正同时提供完整结构化报告、报告 PDF 和用于内容一致性判断的 PDF 文件摘要。
6. 更正存在当前有效原报告；作废存在尚未物理删除的原报告。

##### 后置条件

1. 新增成功后保存一份当前有效报告及其完整内容，平台记录实际接收时间。
2. 更正成功后保存新版本及版本关系，原版本停止参与候选查询、引用详情和新的引用。
3. 作废成功后保存作废时间和原因，报告停止参与候选查询、引用详情和新的引用，但报告及历史版本不被物理删除。
4. 任一校验或保存步骤失败时，本次报告变更不产生部分业务数据。
5. 平台同步返回成功、幂等成功、校验失败、内容冲突、过期更正、顺序冲突或原报告不存在等明确结果。

##### 主事件流

1. 医院源系统形成新增、更正或作废事件，医院侧采集服务按原操作类型提交一份报告变更。
2. 平台根据医院、院区、报告类型和报告单号识别报告业务标识。
3. 平台校验调用医院院区、患者身份、来源就诊、平台科室医生归属、报告公共字段和项目编码对照。
4. 新增或更正时，平台将结构化报告和 PDF 作为一个完整单元校验，并核对至少一个项目明细已有效对码。
5. 平台按照操作类型执行新增、更正或作废处理。
6. 平台保存报告变更后同步返回最终成功结果；只有业务数据已经完整保存时才能返回成功。

##### 备选流

1. 相同报告业务标识的新增已存在且内容一致时，返回幂等成功；内容不一致时返回报告冲突，不静默覆盖。
2. 更正内容与当前版本一致时返回幂等成功；内容不一致且源端报告修改时间晚于当前版本时形成新版本，否则返回过期更正或顺序冲突。
3. 更正找不到当前有效原报告时返回原报告不存在，不自动按新增处理。
4. 作废对象已经作废时返回幂等成功；找不到原报告时返回原报告不存在。
5. 患者证件已存在但姓名、性别或出生日期不一致时返回患者身份信息冲突，不覆盖患者资料，也不创建第二个患者。
6. 没有任何项目明细能够完成有效对码时拒绝接收整份报告。
7. 任一平台科室或医生 ID 不存在或跨越当前调用医院、院区时，整次请求失败且不保存业务数据。
8. 结构化内容、PDF、文件摘要或任一必填内容校验失败时，整份报告失败，不先保存其中一部分。
9. 调用超时或医院侧未取得明确结果时，医院侧以相同操作类型和内容重新提交，平台按当前状态执行幂等或冲突判断。

##### 业务规则

1. 检验报告和检查报告分别使用各自的报告提交能力，但均通过报告操作类型表达新增、更正和作废。
2. 每次请求只处理一份报告，不将多份报告组成共同成功或共同失败的业务批次；医院侧可以并发提交多份独立报告。
3. 报告业务标识由医院、院区、报告类型和报告单号共同组成。
4. 报告操作类型是本次业务指令，不作为报告当前状态或最近操作字段。
5. 平台不根据内容变化、记录缺失或传输状态猜测报告操作类型。
6. 新增和更正提交完整报告，不支持局部字段修改；作废不重复提交报告内容和 PDF。
7. 更正保留原版本和新版本关系，旧版本责任人员及其他历史内容不得被新版本覆盖。
8. 新增和更正必须提供源端报告修改时间；报告时间不能替代源端报告修改时间。
9. 报告公共时间包括必填的申请时间、报告时间，以及源系统存在时应提供的审核时间；平台接收时间不作为来源报告业务时间。
10. 报告时间是计算可互认时间的起点。
11. 报告随附来源患者和就诊信息，平台不要求医院预先上传独立挂号或就诊记录。
12. 来源就诊由医院、院区、就诊类型和院内就诊流水号共同识别；就诊类型和稳定且不循环复用的院内就诊流水号必填。
13. 就诊类型至少覆盖门诊、急诊、住院和体检。住院号、病区、病房和床位在住院来源系统存在时应提供，但不参与患者或就诊自动匹配。
14. 患者姓名、性别代码、出生日期、证件类型和证件号码必填。相同证件下姓名、性别或出生日期冲突时不得覆盖既有患者信息。
15. 患者联系电话和报告时年龄在源系统存在时应提供，只用于授权展示和人工核对，不参与患者匹配；联系电话默认脱敏展示。
16. 报告上传只接收平台科室和医生 ID，不接收院内科室编码、医生工号或调用方自行填写的名称。
17. 申请科室、申请医生、执行科室、报告科室、报告医生、审核医生及报告类型要求的检验人或检查医生，按各自规则保存平台 ID 和当次查询名称。
18. ID 存在且归属正确但主体停用时允许提交真实报告；平台不校验医生当前所属科室与报告科室一致。
19. 科室或医生以后改名时，已有报告版本继续展示保存时名称。
20. 一份报告至少一个项目明细关联到当前启用且来源有效的互认项目时，保存全部报告内容；只有保存了有效互认项目关系的明细能够形成候选。互认项目停用或来源不可用时阻止相关新报告上传。
21. 项目对照关系在报告接收时解析并随报告明细保存；后续对照修改或停用不重写已有报告关系。
22. 来源保密标识只按来源值保存，不驱动敏感等级、患者授权、上传审批或候选过滤。需要专项授权才能共享的报告暂不上传。
23. 平台不采集来源医嘱优先级、院内报告过程状态、传输批次号、上传状态、校验标志或调用方事件标识。
24. 报告更正或作废立即限制旧版本继续参与候选查询、引用详情和新的引用，但不否定医院稍后提交的既有互认处理或已发生引用事实。
25. 平台不因报告更正或作废建设下游主动推送、推送记录或恢复处理。

##### 关键属性

| 属性组 | 关键属性与说明 |
| --- | --- |
| 业务身份 | 医院、院区、报告类型、报告单号，共同组成报告业务标识。 |

| 患者信息 | 姓名、性别代码、出生日期、证件类型、证件号码；联系电话、报告时年龄按来源情况提供。 |

#### F03.2 检验报告专项要求

##### 参与者

医院 LIS 或其他检验报告来源系统、医院侧采集服务、互认平台及报告涉及的平台科室和医生。

##### 需求背景

检验报告以一份报告单和一个标本为单位，可以包含普通检验结果、细菌鉴定结果和药敏结果。平台需要完整保留最终报告内容，同时只将完成有效项目对码的普通检验结果用于互认候选。

##### 前置条件

1. 满足 F03.1 的公共前置条件。
2. 报告提供院内标本号、标本类型编码、标本类型名称和检测完成时间。
3. 报告至少包含一条普通检验结果，且至少一条普通结果能够通过有效项目编码对照关联互认项目。
4. 每条普通结果提供院内项目编码、名称、完整来源结果文本、受控结果类型和唯一展示序号。

##### 后置条件

平台保存一份与单一标本关联的完整检验报告、全部普通结果、可选细菌鉴定结果和药敏结果；已对码普通结果可以形成候选，未对码普通结果及补充结果只用于保持报告完整、展示和追溯。

##### 主事件流

1. 平台校验检验报告公共信息、标本信息和检验时间线。
2. 平台逐条校验普通检验结果，按来源医院、院区和院内项目编码解析当前有效对照。
3. 平台保存普通结果来源原文、结果类型、展示顺序和源系统实际提供的辅助信息。
4. 报告包含细菌鉴定结果时，平台保存最终鉴定结论及相关来源信息。
5. 报告包含药敏结果时，平台校验其与细菌鉴定结果的明确关联并保存最终药敏结论及量值。
6. 全部结构化内容与 PDF 校验通过后，平台按 F03.1 保存报告变更。

##### 备选流

1. 报告同时包含已对码和未对码普通结果时，平台完整接收报告，仅已对码结果参与候选。
2. 普通结果、细菌结果或药敏结果的来源明细标识缺失时，如源系统确实不存在则允许为空；提供时在相应报告版本范围内不得重复。
3. 培养未发现细菌时，仍应提交一条细菌鉴定结果表达未检出及来源结论，不要求伪造菌种编码或名称。
4. 单位、参考范围、LOINC、检测方法、仪器、收费代码等应填信息在源系统确实不存在或不适用时允许为空，不得由平台推断或填充占位值。
5. 结果展示序号缺失或在规定范围内重复时，平台拒绝报告。

##### 业务规则

1. 一份检验报告只对应一个标本；多个标本分别形成不同报告。
2. 标本采集时间、送检时间和检验科接收时间在源系统存在时应提供，检测完成时间必填；不采集上机、离心和培养过程节点。
3. 来源报告名称必填；报告类别编码、名称和报告备注在源系统存在时应提供，只用于展示、筛选和追溯。
4. 报告整体异常标识在源系统存在时应提供，不替代结果明细异常标志，也不参与互认资格判断。
5. 来源医嘱流水号在源系统存在时应提供，只用于追溯，不参与报告身份、患者关联和互认判断；不保存报告级单一医嘱项目代码。
6. 普通结果完整保存来源最终结果文本，并使用受控结果类型区分数值型、定性型和文本型；平台不重复采集独立定量、定性字段。
7. 平台不采集或推断统一检验结果代码，不解析、换算或重新判定来源结果。
8. LOINC 在源 LIS 已维护时应提供，但不替代项目编码对照，也不由平台根据名称推断。
9. 单位、参考范围和检测方法按来源文本保存；平台不统一单位、不拆分参考上下限、不换算或重算参考范围。
10. 普通结果可以分别提供来源仪器编号和名称；平台不维护仪器目录，仪器不参与候选资格判断。
11. 每条普通结果的展示序号必填，在同一报告版本的普通结果内不得重复；平台不依赖接口数组或数据库顺序。
12. 来源检验收费项目编码和医保收费项目编码在源系统已维护时应提供，但不用于报告采集阶段的金额计算。
13. 异常标志按来源受控值保存，危急值标志按来源判断保存；平台不重新计算，也不因异常或危急值标志排除候选。
14. 细菌鉴定和药敏结果是检验报告补充结果，不独立进行互认项目对码。
15. 检出具体菌种时来源菌种名称必填，来源菌种编码按源系统情况提供；未检出时保存明确检测结论和来源文字。
16. 菌落计数、培养基、培养时间、培养条件和发现方式按源系统实际内容提供并保存，平台不标准化或重建培养过程。
17. 细菌检测结论必填；详细描述、仪器、试验板信息按源系统情况提供，不据此重新判定临床结果。
18. 药敏结果必须明确关联细菌鉴定结果，提供受试药物名称和来源结论文字；来源代码按源系统情况提供。
19. 纸片含药量、MIC、抑菌环直径和参考值按包含单位及比较符号的来源文本保存，平台不拆分、换算或重新判读。
20. 药敏展示序号必填，在同一报告版本、同一细菌鉴定结果下不得重复；检测方法和试验板序号按来源情况提供。药敏结果不重复保存试验板名称，也不使用试验板序号代替与细菌鉴定结果的明确关联。
21. 报告级检验人必填；普通结果、细菌结果和药敏结果的检测人及明细审核人在源系统存在且能够关联平台医生时应提供，缺失不阻止报告接收。

##### 关键属性

| 属性组 | 关键属性 |
| --- | --- |
| 报告信息 | 来源报告名称、报告类别编码和名称、报告备注、整体异常标识、来源医嘱流水号。 |
| 标本信息 | 院内标本号、标本类型编码、标本类型名称。 |
| 检验时间线 | 标本采集时间、送检时间、检验科接收时间、检测完成时间。 |
| 普通结果 | 来源明细标识、院内项目编码和名称、来源结果文本、结果类型、LOINC、单位、参考范围、检测方法、仪器、展示序号、收费代码、异常标志、危急值标志、明细责任人员。 |
| 细菌鉴定 | 来源明细标识、检出状态、菌种编码和名称、菌落计数、培养信息、检测结论、详细描述、仪器、试验板、明细责任人员。 |
| 药敏结果 | 来源明细标识、关联细菌、受试药物、药敏代码、结论、抗药结果代码、纸片含药量、MIC、抑菌环直径、参考值、展示序号、检测方法、试验板序号、明细责任人员。 |

#### F03.3 检查报告专项要求

##### 参与者

医院 PACS 或其他检查报告来源系统、医院侧采集服务、互认平台、影像服务及报告涉及的平台科室和医生。

##### 需求背景

检查报告以一份来源报告为完整业务对象，可以包含一个或多个检查项目明细。项目、部位属于明细，检查所见、检查结论、PDF 和影像调阅入口属于整份报告，联合报告不因项目对码被拆成多份报告。

##### 前置条件

1. 满足 F03.1 的公共前置条件。
2. 报告提供一个或多个检查项目明细，至少一个明细能够通过有效项目编码对照关联互认项目。
3. 每个项目明细提供院内检查项目编码和名称；存在明确检查部位时提供结构化部位集合。
4. 报告提供检查所见、检查结论、来源临床诊断名称、实际检查时间和检查医生平台 ID。

##### 后置条件

平台保存完整检查报告、全部项目明细及其部位集合、报告级临床内容、PDF、来源影像状态和按规则提供的影像调阅地址；已对码项目形成候选，未对码项目只用于报告完整展示和追溯。

##### 主事件流

1. 平台校验检查报告公共信息、实际检查时间、检查医生和报告级临床内容。
2. 平台逐个检查项目明细解析当前有效编码对照，并保持项目与其部位集合的明确归属。
3. 平台保存整份报告的检查所见、检查结论、来源诊断、病情描述、检查目的、检查方法及设备信息。
4. 平台按来源影像状态校验影像调阅地址的一致性。
5. 全部结构化内容、PDF 和按规则提供的影像信息校验通过后，平台按 F03.1 保存报告变更。

##### 备选流

1. 联合检查报告同时包含已对码和未对码项目时完整接收，仅已对码项目形成候选。
2. 项目没有明确检查部位时部位集合允许为空；存在部位时部位名称必填，来源部位编码按源系统情况提供。
3. 特殊检查确实没有检查所见时，来源系统应明确提供“无”等来源表达，平台不自动补写。
4. 来源影像状态为有影像但没有跨院可用地址时仍可接收报告，并表达为存在影像但暂不可调阅。
5. 来源影像状态为无影像时调阅地址必须为空；状态为未知时地址可以有或无。

##### 业务规则

1. 一份检查报告可以包含一个或多个项目明细，各明细分别解析互认项目。
2. 检查项目明细不采集具有业务含义的展示序号，平台采用稳定、可重复的方式展示，来源版式和临床阅读顺序以 PDF 为准。
3. 检查部位归属于具体检查项目明细，不以分隔文本笼统归属于整份报告。
4. 每个部位名称必填，来源部位编码在源系统存在时应提供；平台不统一或推断部位编码。
5. 检查所见和检查结论属于报告级必填完整原文，不拆分或重复保存到项目明细，不由平台整理、推断或改写。
6. 平台不定义通用检查结果代码、定性结果或定量结果字段，不从所见或结论中抽取、换算结构化指标。
7. 来源检查类型编码和名称在源系统存在时应提供，只用于展示、筛选和追溯，不关联标准项目分类或决定互认资格。
8. 来源检查设备编号和名称、检查方法在源系统存在时应提供，均为报告级信息，不参与项目对码或候选资格判断。
9. 来源临床诊断名称必填，诊断编码按源系统情况提供；平台不统一诊断编码，不从检查结论反推诊断。
10. 病情描述和检查目的在源系统存在时应提供，分别保存，不合并或自动生成，也不参与互认资格判断。
11. 实际检查时间必填，不采集预约时间，也不拆分检查开始和完成时间。
12. 检查医生平台 ID 必填，可以与报告医生或审核医生为同一人员。
13. 一份检查报告最多保存一个 HTTPS 影像调阅地址。平台不接收、代理、缓存或长期保存 DICOM 文件。
14. 来源影像状态使用有影像、无影像或未知；平台不根据调阅地址是否为空反推来源影像状态。
15. 影像地址缺失不影响结构化报告和 PDF 的互认资格，报告作废后不再返回原地址。
16. 平台不采集 PACS 影像号、检查实例 UID、序列 UID 等影像技术标识，也不自行拼接影像调阅地址。
17. 来源检查报告整体异常标识在源系统存在时应提供，只用于报告列表提示、候选快速提示和人工核对；平台不根据检查所见、检查结论或项目内容自行推断，也不因异常标识排除互认。

##### 关键属性

| 属性组 | 关键属性 |
| --- | --- |
| 检查项目明细 | 院内项目编码、院内项目名称、关联互认项目及结构化检查部位集合。 |
| 检查部位 | 所属项目、来源部位编码、部位名称。 |
| 报告内容 | 检查所见、检查结论、来源整体异常标识。 |
| 临床背景 | 来源临床诊断编码和名称、病情描述、检查目的。 |
| 检查信息 | 来源检查类型编码和名称、实际检查时间、检查方法、设备编号和名称、检查医生。 |
| 影像信息 | 来源影像状态、单个 HTTPS 影像调阅地址。 |

### F04 互认候选查询

#### 参与者

| 参与者 | 职责 |
| --- | --- |
| 医院 HIS | 在患者接诊或开单过程中提交患者身份、本次来源就诊和一个或多个拟开院内项目，接收符合条件的候选结果。 |
| 互认平台 | 校验患者和项目，选择每个互认项目的最近有效报告，组织候选内容并形成提醒统计。 |
| 医生 | 在医院 HIS 中查看候选结构化内容、PDF 或影像入口并作出临床决定。 |

#### 需求背景

医院 HIS 在拟开检查或检验项目时，需要查询同一患者是否存在仍可使用的跨机构结果。一次查询可能包含多个院内项目，平台需要消除项目语义重复，只返回符合条件的候选，并保持联合报告的完整性；没有符合条件的候选属于正常查询结果。

#### 前置条件

1. 调用方能够从可信身份上下文确定当前接收医院和接收院区。
2. 查询提供有效的患者证件类型和证件号码，以及本次来源就诊类型和院内就诊流水号。
3. 查询至少包含一个拟开院内项目，每个项目明确检查或检验类型，并提供当前医院、院区使用的院内项目编码。
4. 当前医院、院区的项目编码对照和候选报告数据可供查询。

#### 后置条件

1. 查询成功时只返回符合条件的候选；没有任何符合条件的候选时返回空候选集合。
2. 每个去重后的互认项目最多返回一份报告的当前有效内容，并返回稳定的互认候选引用。
3. 同一联合报告命中多个项目时只返回一份报告公共信息，各项目分别形成候选引用。
4. 每个成功返回候选的去重互认项目形成一次提醒统计；无候选或整次查询失败不形成提醒。
5. 查询本身不形成互认处理结果、引用结果或调阅状态。

#### 主事件流

1. 医院 HIS 提交患者身份、本次来源就诊和一个或多个拟开院内项目。
2. 平台校验调用医院院区、患者身份、来源就诊和项目输入。
3. 平台按当前医院、院区、项目类型和院内项目编码解析当前有效项目编码对照。
4. 多个拟开院内项目解析到同一互认项目时合并处理。
5. 平台针对每个去重互认项目筛选报告：报告版本当前有效、报告对应互认项目当前启用且来源有效、检查或检验时间不晚于查询时点，并处于当前可互认时间内。
6. 平台按本院报告候选开关和本院报告排除时长处理来源医院与接收医院相同的报告。
7. 平台选择检查或检验时间最晚的一份报告；时间相同时选择报告时间较晚的一份；两者均相同时稳定选择同一份报告。
8. 平台按报告分组组织公共信息，并按互认项目组织候选引用及项目内容。
9. 平台返回符合条件的候选；没有任何符合条件的候选时返回空候选集合，并记录成功返回候选所形成的提醒次数。

#### 备选流

1. 拟开项目不存在当前有效对照、对应互认项目停用或来源不可用时，该项目不形成候选，也不影响同一请求中其他项目的处理。
2. 患者不存在、没有满足时间和有效性规则的报告，或者报告均被本院候选规则排除时，不返回相应候选；没有任何候选时返回成功的空候选集合。
3. 查询输入、患者身份或调用归属校验失败时，整次查询失败，不形成提醒统计。
4. 一份报告已经更正时只使用新版本；报告已经作废时不参与候选选择。
5. 一份联合报告同时命中多个互认项目时，报告公共内容只组织一次，项目候选和处理边界仍相互独立。
6. 查询超时或医院 HIS 未取得明确成功响应时不形成提醒；医院 HIS 可以重新发起查询，后续成功返回候选时按新的查询形成提醒。

#### 业务规则

1. 查询截止点使用平台收到本次查询的时间，医院 HIS 不需要额外提供挂号时间、入院时间或统一就诊时间。
2. 候选时间判断使用检查报告的实际检查时间或检验报告的检测完成时间；该时间不得晚于查询时点。
3. 可互认时间从报告时间开始计算，并使用互认项目查询时的当前配置。
4. 每个互认项目只返回最近一份有效报告，不返回其他较早独立报告或历史趋势。
5. 检查或检验时间相同时，报告时间是唯一业务选择条件。两者均相同时，不增加临床质量、机构级别或其他业务排序条件；在候选数据及相关配置未变化时必须稳定返回同一份报告，具体稳定排序方式在设计阶段确定。
6. 联合报告按完整报告返回，但只有本次查询命中的互认项目形成候选，未命中项目不得形成候选引用。
7. 多个拟开院内项目解析到同一互认项目时，只形成一个候选和一次提醒，不重复返回或统计。
8. 本院报告候选开关为平台全局参数，默认关闭。关闭时来源医院与接收医院相同的报告不参与候选，不区分院区。
9. 开关开启后，本院报告排除时长使用另一个全局非负小时参数，默认四十八小时；配置为零表示不增加额外等待时间，负数无效。
10. 本院报告经过时间大于或等于排除时长，且小于或等于互认项目可互认时间时满足时间条件；两个边界均包含。
11. 排除时长可以等于或大于某些项目的可互认时间，不作为配置错误；大于时该项目不会返回本院报告。
12. 本院报告参数只影响后续候选查询，不删除报告或撤销既有处理、引用和统计事实。
13. 检验候选返回来源机构、报告名称、检查或检验时间、报告时间、报告业务标识、标本类型名称、本次命中互认项目对应的全部普通检验结果明细和 PDF 入口；每条结果按报告版本保存的展示序号返回，并包含项目名称、来源结果原文、单位、参考范围、异常标志和危急值标志。
14. 检验候选不返回用于来源追溯的标本类型编码和院内标本号。
15. 检查候选返回来源机构、报告名称、实际检查时间、报告时间、报告业务标识、命中项目的检查部位、整体异常标识、PDF 入口、来源影像状态及按规则可用的影像入口。
16. 检查候选不直接返回篇幅较大的检查所见和检查结论；医生通过 PDF 或影像查看后决定是否采纳。
17. 候选中的异常和危急值仅表达来源医院判断，平台不重新计算，也不自动排除异常报告。
18. 提醒次数只表示平台成功提供候选，不表示医院 HIS 已显示弹窗或医生已经查看、采纳、拒绝或引用。

#### 关键属性

| 属性组 | 关键属性 |
| --- | --- |
| 调用归属 | 当前接收医院、接收院区，来自可信身份上下文。 |
| 患者与就诊 | 证件类型、证件号码、本次来源就诊类型、本次院内就诊流水号。 |
| 拟开项目 | 检查或检验类型、院内项目编码；解析并去重为互认项目。 |
| 候选公共信息 | 来源医院及院区、来源报告名称、检查或检验时间、报告时间、报告业务标识、PDF 入口。 |
| 候选引用 | 绑定候选报告版本和具体互认项目的稳定引用。 |
| 检验候选内容 | 标本类型名称及命中互认项目对应的全部普通检验结果明细，按报告保存的展示序号返回。 |
| 检查候选内容 | 命中项目检查部位、整体异常标识、来源影像状态及影像入口。 |
| 候选集合 | 只包含符合条件的候选；没有符合条件的候选时为空集合。 |

### F05 互认处理结果

#### 参与者

| 参与者 | 职责 |
| --- | --- |
| 医生 | 查看候选后作出采纳或不采纳决定，并在引用前按真实情况更正决定。 |
| 医院 HIS | 提交一个或多个项目的处理结果、实际互认时间、决定科室和决定医生。 |
| 互认平台 | 整批校验并保存当前有效决定、不采纳原因和预计节省金额，维护对应统计事实。 |

#### 需求背景

平台只能记录医生明确作出的互认决定，不能从查询、调阅或医院后续行为推断采纳情况。处理结果需要归属于本次就诊、候选项目、实际决定时间、科室和医生，并允许在尚未形成引用事实时纠正决定。

#### 前置条件

1. 医院 HIS 已取得候选查询返回的稳定候选引用。
2. 医生已经明确作出采纳或不采纳决定。
3. 每条结果提供本次来源就诊、候选引用、精确到秒的互认时间、处理结果、平台科室 ID 和平台医生 ID。
4. 不采纳时提供平台统一原因代码；原因为其他时提供补充说明。

#### 后置条件

1. 一次请求中的全部处理结果校验成功后共同保存；任一记录失败时整批不保存。
2. 每个“接收医院、接收院区、本次来源就诊、候选引用、互认时间”只保留一个当前有效决定。
3. 当前决定为采纳时形成采纳次数、来源医院被互认次数、报告使用关系和预计节省金额；不采纳时形成不采纳次数和原因。
4. 相同决定幂等重试不重复计数；引用前决定更正后，相关统计按最新有效决定重新计算。

#### 主事件流

1. 医院 HIS 提交一个或多个候选项目的处理结果。
2. 平台校验调用医院院区、来源就诊、候选引用、互认时间、决定内容，以及全部科室医生 ID 的存在性和归属。
3. 平台确认每条候选引用能够定位相应报告版本和互认项目，但不因提交时报告后来更正或作废而拒绝既有处理事实。
4. 处理结果为不采纳时，平台校验统一原因代码及补充说明。
5. 处理结果为采纳时，平台读取互认项目当前参考价格形成预计节省金额。
6. 全部记录校验通过后，平台在一个整体操作中保存全部当前有效决定及对应统计事实。
7. 平台返回整次请求成功。

#### 备选流

1. 任一记录校验失败时整批不保存，返回整个请求失败，不返回逐条成功结果。
2. 相同业务键重复提交完全相同的处理内容时返回幂等成功，不新增记录或重复统计。
3. 相同业务键提交不同决定且尚未形成引用结果时，医院 HIS 必须提供实际作出最新决定的科室和医生；平台更新为最新有效决定，将当前记录及统计改为归属于最新决定主体，并调整采纳、不采纳、来源医院被互认次数和预计节省金额。
4. 已形成引用结果后尝试将决定改为不采纳时，平台拒绝更正。
5. 不采纳未提供原因、原因无效，或者原因为其他但缺少说明时，整批失败。
6. 任一科室或医生 ID 不存在或不属于当前调用医院、院区时，整批失败；ID 停用但存在且归属正确时允许提交。
7. 接口超时、失败或未取得明确结果时，医院 HIS 使用相同互认时间和原记录重新提交。

#### 业务规则

1. 处理结果值域只包括采纳和不采纳，不要求提交未处理、未查看、暂未决定或关闭提醒状态。
2. 候选返回、结构化展示、PDF 或影像访问不自动形成处理结果。
3. 处理决定归属于候选报告中的具体互认项目，不笼统归属于整份联合报告。
4. 同一请求可以提交一个或多个项目，但请求整体校验、整体保存。
5. 互认时间是医生实际作出决定的时间，保存到秒；接口接收时间不得替代互认时间。
6. 相同候选可以在同一就诊中因不同时间发生的真实诊疗需要形成多次处理，不同互认时间分别形成记录和统计。
7. 平台科室和医生表示实际作出决定的主体，接口调用账号不得替代；采纳和不采纳均必须提供。
8. 平台分别校验科室和医生属于当前调用医院、院区，不校验医生当前所属科室与决定科室一致。
9. 科室和医生名称按提交时查询结果保存，名称不参与业务唯一键或幂等一致性判断。
10. 平台接收稍后提交的既有处理事实时，不比较互认时间与报告更正或作废时间。
11. 统一不采纳原因字典由平台内置并使用本功能规定的固定代码，不提供医院新增、修改或停用；代码 `6` 表示其他情形确需复查，使用时补充说明必填。
12. 处理结果为采纳时不得填写不采纳原因；平台不审查不采纳的临床理由，也不据此干涉医院继续开单或采取其他诊疗措施。
13. 采纳时按互认项目当时的当前参考价格形成预计节省金额，不等待引用结果。
14. 平台只保存预计节省金额，不在处理记录中重复保存一份参考价格。
15. 相同采纳的幂等重试不因参考价格已经变化而重新计算金额。
16. 采纳改为不采纳时取消该次金额；不采纳改为采纳时使用重新采纳时的当前参考价格形成金额。
17. 报告后续更正或作废不撤销或重算已经形成且当前决定仍为采纳的预计节省金额。
18. 预计节省金额归属于接收医院、院区和决定科室，不在来源医院侧重复形成贡献金额。
19. 决定更正继续使用原互认时间归入统计期间，重新查询原期间时按最新有效决定计算。

| `2` | 检查检验结果在疾病发展演变过程中变化较快。 |
| `3` | 检查检验项目对于疾病诊疗意义重大，如手术、输血等重大医疗措施前。 |

| `5` | 涉及司法、伤残及病退等鉴定。 |
| `6` | 其他情形确需复查；选择该代码时补充说明必填。 |

| 决定科室、决定医生 | 平台 ID 及当次查询后保存的名称。 |
| 不采纳原因 | 平台统一原因代码；其他原因对应补充说明。 |
| 预计节省金额 | 当前有效决定为采纳时形成的统计金额。 |
| 当前有效决定 | 相同业务键下最新有效的决定；形成引用后固定为采纳。 |

### F06 获取引用详情

#### 参与者

| 参与者 | 职责 |
| --- | --- |
| 医院 HIS | 在医生采纳候选后请求写入本次病历所需的项目内容。 |
| 互认平台 | 校验调用归属、来源就诊、互认决定和候选版本有效性，返回项目级引用内容。 |

#### 需求背景

候选查询只用于医生判断，病历引用需要在采纳后通过独立能力取得受控内容。平台必须保证返回内容属于当前医院、本次就诊、已采纳项目和仍有效的报告版本。

#### 前置条件

1. 当前调用医院、院区能够从可信身份上下文确定。
2. 请求提供本次来源就诊、候选引用和对应互认时间。
3. 相应互认处理记录存在，当前有效决定为采纳。
4. 候选引用绑定的报告版本仍为当前有效版本。

#### 后置条件

1. 校验成功时只返回当前候选引用对应互认项目的内容及必要报告公共上下文。
2. 获取引用详情不自动形成引用结果、引用次数或新的互认处理。
3. 校验失败时不返回受保护的报告引用内容。

#### 主事件流

1. 医院 HIS 提交本次来源就诊、候选引用和互认时间。
2. 平台校验当前医院院区与候选、来源就诊和互认处理记录的归属一致。
3. 平台校验当前有效决定为采纳，候选引用绑定的报告版本仍为当前有效版本。
4. 平台按候选引用定位具体互认项目及报告公共上下文。
5. 平台返回项目级引用内容，供医院 HIS 写入本次病历。

#### 备选流

1. 互认处理不存在、当前决定为不采纳、来源就诊或医院院区不匹配时拒绝返回。
2. 报告已经更正、作废，或者候选引用绑定的版本不再是当前有效版本时拒绝返回。
3. 联合报告只采纳其中部分项目时，仅返回当前候选引用对应项目，不返回其他未采纳、未命中项目。

#### 业务规则

1. 获取引用详情与候选查询、处理结果提交、引用结果提交相互独立。
2. 引用详情必须校验“当前医院院区 + 本次来源就诊 + 候选引用 + 互认时间”与当前有效采纳决定一致。
3. 检验引用详情按当前互认项目返回相应检验结果，不细分为每条结果独立引用事实。
4. 检查所见和检查结论属于整份报告公共内容，可以随当前检查项目返回。
5. 必要报告公共上下文至少包括来源医疗机构、来源报告名称、检查或检验时间、报告时间、来源申请医生和来源审核医生。
6. 获取详情只表示平台提供了引用所需数据，不表示医院 HIS 已写入病历。
7. PDF 或影像访问不能替代获取引用详情，也不能形成引用结果。

#### 关键属性

| 属性组 | 关键属性 |
| --- | --- |
| 请求定位 | 当前医院院区、本次来源就诊、候选引用、互认时间。 |
| 公共上下文 | 来源医疗机构、来源报告名称、检查或检验时间、报告时间、来源申请医生、来源审核医生。 |
| 检验引用内容 | 当前互认项目对应的检验结果及必要解释信息。 |
| 检查引用内容 | 当前互认项目、检查部位，以及整份报告的检查所见和检查结论。 |

### F07 提交引用结果

#### 参与者

| 参与者 | 职责 |
| --- | --- |
| 医院 HIS | 在已采纳内容成功写入本次病历后，提交一条或多条实际引用事实。 |
| 互认平台 | 执行整批主体校验，再逐条校验和保存引用结果并返回逐条结果。 |

#### 需求背景

互认采纳和病历引用是连续但独立的业务事实。平台只有在医院 HIS 明确确认已成功写入病历后才能记录引用，不得从引用详情获取、文件访问或未反馈状态推断引用。

#### 前置条件

1. 医院 HIS 已将相应互认内容成功写入本次病历。
2. 每条记录提供本次来源就诊、候选引用、对应互认时间、实际引用时间、引用科室 ID 和引用医生 ID。
3. 对应互认处理记录存在且当前有效决定为采纳。
4. 全部引用科室和医生 ID 存在并属于当前调用医院、院区。

#### 后置条件

1. 全部主体 ID 前置校验通过后，各引用记录独立保存并分别返回新增成功、幂等成功或明确失败。
2. 每个业务唯一键只形成一个引用事实，幂等重试不增加引用次数或重复形成报告使用关系。
3. 成功引用按实际引用时间计入引用统计，不再次增加采纳次数、来源医院被互认次数或预计节省金额。

#### 主事件流

1. 医院 HIS 提交一条或多条已经发生的引用结果。
2. 平台先校验请求内全部引用科室、引用医生的存在性和当前医院院区归属。
3. 全部主体校验通过后，平台逐条校验来源就诊、候选引用、互认时间和当前有效采纳决定。
4. 平台按业务唯一键检查是否已有引用结果，并核对实际引用时间、引用科室和引用医生。
5. 新引用结果保存实际引用事实；相同事实返回幂等成功；其他业务校验失败返回该条明确失败。
6. 平台返回逐条处理结果。

#### 备选流

1. 任一记录的科室或医生 ID 不存在或跨医院院区时，整次请求失败，整批不保存。
2. 主体前置校验通过后，某条记录的决定不存在、当前为不采纳或业务归属不匹配时，只拒绝该条，不回滚其他成功记录。
3. 相同业务键且实际引用时间、科室和医生一致时返回幂等成功。
4. 相同业务键但任一事实字段不同，返回内容冲突，不覆盖已有引用结果。
5. 医院修正失败记录后可以重新提交整个原批次，先前成功记录按幂等规则处理。
6. 报告在实际引用之后发生更正或作废、且医院稍后提交引用结果时，平台不因提交时报告已失效而拒绝该项已经发生的引用事实。

#### 业务规则

1. 平台只接收已经引用的正向事实，不要求医院提交未引用或引用失败状态。
2. 获取引用详情、查看结构化结果、访问 PDF 或影像均不自动形成引用结果。
3. 引用粒度为候选报告版本中的具体互认项目，不继续细分到每条普通检验展示明细。
4. 业务唯一键由接收医院、接收院区、本次来源就诊、候选引用和互认时间共同组成，不要求医院生成额外幂等流水号。
5. 实际引用时间是医院成功写入病历的业务时间；接口接收时间不得替代。
6. 引用科室和引用医生是实际执行引用的主体，调用账号不得替代。
7. 平台分别校验引用科室和医生属于当前调用医院、院区，不校验医生当前所属科室与引用科室一致。
8. 科室或医生停用但仍存在且归属正确时，允许补交真实引用事实。
9. 报告更正或作废阻止继续获取原版本引用详情和发生新的引用，但不拒绝原版本有效期间已经发生、稍后提交的引用结果。
10. 引用结果形成后，对应互认决定固定为采纳，不允许更正为不采纳，也不提供引用撤销。
11. 引用只增加引用次数，不再次增加互认采纳、来源医院被互认次数或预计节省金额。

#### 关键属性

| 属性 | 说明 |
| --- | --- |
| 本次来源就诊 | 就诊类型和院内就诊流水号。 |
| 候选引用 | 定位已采纳报告版本和具体互认项目。 |
| 互认时间 | 定位对应的当前有效采纳决定。 |
| 实际引用时间 | 医院 HIS 成功写入本次病历的时间。 |
| 引用科室、引用医生 | 平台 ID 及提交时保存的名称。 |
| 逐条处理结果 | 新增成功、幂等成功或明确失败。 |

### F08 互认统计与分析

#### 参与者

| 参与者 | 职责 |
| --- | --- |
| 医院管理员 | 在本院及有权院区范围内查看接收侧互认使用汇总、来源侧被互认汇总及相应脱敏明细。 |
| 平台管理员 | 查看权限范围内的全县汇总、医院明细和业务下钻。 |
| 互认平台 | 按原始业务事实、业务时间、当前有效决定和权限范围计算统计。 |

#### 需求背景

平台需要同时反映候选提供、医生决定、病历引用、预计节省金额和来源医院报告贡献，并保证每项指标能够回到相应业务明细核对。统计用于业务管理和监管，不用于自动评价医生绩效或替代真实财务结算。

#### 前置条件

1. 当前用户已登录并具有对应统计页面及数据范围权限。
2. 查询提供日期范围，并可按允许的医院、院区、决定科室、决定医生或互认项目等条件筛选。
3. 平台已保存候选返回、当前有效互认决定、引用结果和互认项目参考价格形成的业务事实。

#### 后置条件

1. 平台返回当前权限和查询条件范围内的汇总、分类统计及可下钻明细。
2. 统计按各指标已确认的业务时间归入期间，包含稍后提交或决定更正后重新计算的事实。
3. 患者姓名和证件号码在统计页面及明细中保持脱敏。
4. 总体统计和跨机构统计分别展示，跨机构作为总体子集，不重复累计。

#### 主事件流

1. 用户进入接收医院互认使用分析或来源医院被互认分析页面。
2. 平台依据登录身份确定可访问的医院、院区或县域数据范围。
3. 用户选择日期范围及其他允许的查询条件。
4. 平台按指标对应业务时间汇总提醒、采纳、不采纳、引用、预计节省金额或来源医院被互认次数。
5. 平台计算同期互认率、不采纳原因次数及占比，并按标准项目分类组织统计。
6. 平台同时提供总体口径和适用的跨机构子集口径。
7. 用户从汇总数字下钻查看对应脱敏业务明细。

#### 备选流

1. 提醒次数为零时，同期互认率不计算，不以零或百分之百代替。
2. 不采纳总次数为零时，各原因占比不计算。
3. 医院 HIS 稍后提交处理或引用结果时，重新查询原业务时间所属期间应包含新增事实。
4. 引用前决定发生更正时，重新查询原互认时间所属期间应按最新有效决定调整采纳、不采纳、来源医院被互认次数和预计节省金额。
5. 查询时间与互认时间跨越统计边界导致短周期同期互认率超过百分之百时，按原始结果展示，不截断或强制封顶。
6. 医院管理员请求超出本院或有权院区的数据时，平台拒绝访问或将查询限制在授权范围内。

#### 业务规则

1. 提醒次数在平台成功返回候选时形成，按候选查询成功返回时间归入统计期间。
2. 同一次查询中多个院内项目合并为同一互认项目时只计一次提醒；联合报告命中多个不同互认项目时分别计数。
3. 无候选、整次查询失败、超时或没有取得明确成功响应时不计提醒。
4. 采纳次数、不采纳次数、来源医院被互认次数和预计节省金额按互认时间归入统计期间。
5. 引用次数按实际引用时间归入统计期间。
6. 接口接收时间只用于传输、安全和审计，不改变统计归属日期。
7. 每个不同互认时间的真实采纳分别计算采纳次数、来源医院被互认次数和预计节省金额；相同互认时间的幂等重试不重复计数。
8. 引用结果只增加引用次数，不再次增加采纳、来源医院被互认次数或预计节省金额；没有引用结果不撤销已经成立的采纳。
9. 同期互认率为统计范围内采纳次数除以提醒次数并乘以百分之百。未收到处理结果的提醒保留在分母中，但不记为不采纳。
10. 平台不建立提醒与采纳的一一对应流水，不另设“采纳次数除以采纳与不采纳之和”的比例指标。
11. 不采纳原因统计按平台统一原因代码汇总次数及占比，占比分母为当前权限和查询条件下的不采纳总次数。
12. 其他原因统一归入其他分类，补充说明只在脱敏明细及导出中展示，不按任意文字生成新分类。
13. 接收医院使用分析包含提醒、采纳、不采纳、引用、同期互认率和预计节省金额。
14. 医院管理员在接收侧互认使用分析中只能查看本院及有权院区的数据；平台管理员按权限查看全县汇总及医院明细。
15. 来源医院被互认分析在接收侧明确采纳时形成，不等待引用结果；来源医院只统计次数和明细，不统计贡献金额。
16. 医院管理员在来源侧被互认分析中只能查看本院提供报告形成的数据；其他医院管理员不得查看与本院无关的来源医院数据。
17. 本院报告候选开关开启后，本院报告形成的提醒、处理、引用和预计节省金额进入总体统计，本院报告被采纳也进入来源医院被互认总体次数。
18. 跨机构口径只包含来源医院与接收医院不同的记录，是总体统计的子集，不得与总体相加。
19. 同一医院不同院区之间的使用属于非跨机构，可以按来源院区和接收院区筛选或分组，但不形成独立跨院区核心指标。
20. 互认使用和来源医院被互认统计统一按标准项目目录中的检查或检验类型、类别、分组及具体互认项目筛选和汇总，不使用各医院来源报告分类进行横向比较。
21. 接收医院汇总支持医院、院区、决定科室和互认项目维度；决定医生只作为明细查询条件和展示内容，不形成互认率、金额或绩效排名。
22. 提醒、采纳、不采纳、引用和来源医院被互认汇总均应支持下钻到对应业务明细。
23. 预计节省金额随采纳明细展示，不另建重复的金额事实或金额明细。
24. 统计管理页面中的患者姓名和证件号码必须脱敏，不提供解除脱敏或查看完整患者身份的能力。
25. 统计通过用户选择的日期范围展示汇总、分类和下钻明细，不生成按日、小时或分钟的趋势图。

#### 关键属性

| 指标或维度 | 说明 |
| --- | --- |
| 提醒次数 | 成功返回去重互认项目候选的次数。 |
| 采纳次数 | 当前有效决定为采纳的互认处理次数。 |
| 不采纳次数 | 当前有效决定为不采纳的互认处理次数。 |
| 引用次数 | 医院 HIS 明确反馈成功写入病历的次数。 |
| 同期互认率 | 采纳次数除以提醒次数；提醒为零时不计算。 |
| 预计节省金额 | 当前有效采纳决定形成的金额合计，归属于接收医院、院区和决定科室。 |
| 来源医院被互认次数 | 来源报告被接收侧明确采纳的次数，不包含贡献金额。 |
| 不采纳原因 | 统一原因代码的次数、占比及脱敏明细。 |
| 业务时间 | 提醒按返回时间；处理及金额按互认时间；引用按实际引用时间。 |
| 统计范围 | 总体口径和来源医院不同于接收医院的跨机构子集口径。 |
| 分类维度 | 标准项目类型、类别、分组、互认项目，以及权限允许的医院、院区和决定科室。 |

### F09 互认统计导出

#### 参与者

| 参与者 | 职责 |
| --- | --- |
| 医院管理员 | 按权限导出本院及有权院区的接收侧互认使用汇总、来源侧被互认汇总及相应明细。 |
| 平台管理员 | 按权限导出全县或指定机构范围的数据。 |
| 互认平台 | 按当前查询条件、权限和脱敏规则生成 Excel 文件。 |

#### 需求背景

页面分页用于浏览，不能满足业务核对和线下汇总需求。平台需要在不扩大数据权限、不解除患者脱敏的前提下，导出当前查询条件下的全部匹配记录。

#### 前置条件

1. 用户具有对应统计页面和导出能力权限。
2. 用户已经在统计页面形成有效查询条件。
3. 查询条件处于当前用户可访问的数据范围内。

#### 后置条件

1. 平台生成一个 `.xlsx` 文件，包含当前查询条件和权限范围内的全部匹配记录。
2. 导出中的患者姓名和证件号码与页面保持相同脱敏规则。
3. 导出不改变任何互认、引用或统计业务事实。

#### 主事件流

1. 用户在相应统计汇总或明细页面设置查询条件并发起导出。
2. 平台重新校验用户权限和医院、院区数据范围。
3. 平台使用当前查询条件获取全部匹配记录，不使用页面当前页码和每页条数限制导出范围。
4. 平台按页面相同规则处理患者脱敏和指标口径。
5. 平台生成 Excel 文件供用户获取。

#### 备选流

1. 用户没有对应导出权限或请求超出数据范围时，平台拒绝导出。
2. 当前查询没有匹配记录时，平台提示“当前条件下无可导出数据”，不生成 Excel 文件，也不扩大查询范围补充其他记录。
3. 导出过程中权限或查询条件校验失败时，不生成可获取文件。

#### 业务规则

1. 当前版本只提供 Excel `.xlsx` 格式，不同时提供 CSV、PDF 或其他格式。
2. 可导出互认使用汇总、提醒明细、采纳明细、不采纳明细、引用明细、来源医院被互认汇总和来源医院被互认明细。
3. 明细导出覆盖当前查询条件和权限范围内的全部匹配记录，不只导出页面当前页。
4. 导出必须继承当前用户的数据权限和当前查询条件，不得扩大医院、院区或县域范围。
5. 患者姓名和证件号码始终脱敏，导出不提供完整身份或解除脱敏能力。
6. 预计节省金额随采纳明细导出，不另生成独立金额明细。
7. 其他不采纳原因的补充说明可以随有权脱敏明细导出，不据此生成新的原因分类。

#### 关键属性

| 属性 | 说明 |
| --- | --- |
| 导出类型 | 互认使用汇总及四类明细、来源医院被互认汇总及明细。 |
| 文件格式 | Excel `.xlsx`。 |
| 查询条件 | 发起导出时页面当前有效查询条件。 |
| 数据范围 | 当前用户权限允许的医院、院区或县域范围。 |
| 记录范围 | 查询条件下全部匹配记录，不受页面分页限制。 |
| 脱敏规则 | 与对应统计页面一致，不允许解除。 |

## 设计约束

1. 本规约只定义业务需求和边界，不预设数据库表、接口路由、报文对象、代码模型、后台任务、部署方式或技术框架。
2. 平台不使用查询流水号、拟开项目业务标识或调用方事件标识区分互认处理和引用事实。
3. 互认时间和实际引用时间必须保存到秒；报表可以按更粗粒度汇总，但不得降低原始业务时间精度。
4. 平台不得使用接口调用账号代替实际作出决定或执行引用的平台科室、医生。
5. 平台科室和医生名称随业务记录保存；基础资料改名不得动态修改已有报告、互认处理或引用记录中的名称。
6. 平台不得根据名称或相似度自动推断标准项目、互认项目、LOINC、菌种、药敏、检查部位或诊断编码。
7. 平台不得根据患者姓名、电话或其他非跨院稳定标识进行模糊或概率患者匹配。
8. 平台不得解析、换算或重新判定来源检验结果、参考范围、异常、危急值、药敏结论、检查所见和检查结论。
9. 平台不得将查询、候选返回、结构化展示、PDF、影像或引用详情访问自动解释为医生采纳或实际引用。
10. 报告新增和更正必须保持结构化数据与 PDF 共同成功或共同失败，不能先保存一部分后补齐另一部分。
11. 报告更正和作废不接入 PushCenter，不建设下游主动推送、推送记录、任务核对或恢复能力。
12. 平台不存储、代理或缓存 DICOM 文件，只保存来源影像状态和单个受控 HTTPS 影像调阅地址。
13. 影像调阅地址的定位参数由医院或区域影像中心封装，平台不得依据 PACS 或 DICOM 技术标识自行拼接。
14. 预计节省金额使用互认项目当前参考价格形成，不模拟实际收费、医保结算、患者退费或医院收入。
15. 统计导出只使用 Excel `.xlsx` 格式，必须继承页面查询条件、权限和脱敏规则。
16. 当前版本不建设通用重量级审计、价格独立版本、趋势图、医生排名或绩效评价能力。

## 接口

### 医院接入接口

本节集中说明医院侧系统接入互认平台所需的业务接口能力。平台管理端页面所需的内部支撑能力由 F01、F02、F08、F09 及“用户界面”章节规定，其前后端接口属于后续设计内容，不作为医院接入契约。平台调用标准项目管理系统、权限体系等依赖关系已在“假设与依赖关系”中说明，本节不展开其技术规格。

| 接入能力 | 调用方 | 业务目的 | 主要业务输入与输出 | 对应功能 |
| --- | --- | --- | --- | --- |
| 检验报告提交 | 医院侧采集服务 | 将审核完成的检验报告新增、更正或作废事实提交至平台。 | 新增和更正提交一份完整结构化检验报告及 PDF，作废提交报告业务标识和作废信息；平台返回成功、幂等成功或明确失败。 | F03.1、F03.2 |
| 检查报告提交 | 医院侧采集服务 | 将审核完成的检查报告新增、更正或作废事实提交至平台。 | 新增和更正提交一份完整结构化检查报告及 PDF、来源影像状态和按规则提供的影像入口，作废提交报告业务标识和作废信息；平台返回成功、幂等成功或明确失败。 | F03.1、F03.3 |
| 互认候选查询 | 医院 HIS | 在患者接诊或开单过程中查询可以提供给医生判断的互认候选。 | 提交患者身份、本次来源就诊和一个或多个拟开院内项目；平台返回符合条件的候选，没有候选时返回成功的空候选集合。 | F04 |
| 互认处理结果提交 | 医院 HIS | 提交医生针对具体候选作出的采纳或不采纳决定及允许的决定更正。 | 提交候选引用、本次来源就诊、互认时间、实际决定科室和医生，以及决定结果和适用的不采纳原因；平台按整批原子规则保存并返回处理结果。 | F05 |
| 引用详情获取 | 医院 HIS | 在候选已被采纳后获取写入本次病历所需的项目内容和报告公共上下文。 | 提交候选引用、本次来源就诊和互认时间；平台校验采纳决定及候选版本有效性后返回对应引用内容。 | F06 |
| 引用结果提交 | 医院 HIS | 将互认内容已经成功写入本次病历的事实提交至平台。 | 提交一条或多条候选引用、来源就诊、互认时间、实际引用时间及引用科室和医生；平台完成整批主体前置校验后逐条处理并返回结果。 | F07 |

医院接入接口共同遵循以下边界：

1. 调用方必须符合表中责任划分。医院侧采集服务负责报告提交，医院 HIS 负责在线候选查询、医生决定反馈和病历引用相关交互。
2. 当前调用医院和院区必须来自可信身份上下文；各接口不得使用调用账号替代实际报告、决定或引用所涉及的业务科室和医生。
3. 各接口的前置条件、后置条件、主事件流、备选流、业务规则、必填口径、幂等及冲突处理以对应功能章节为准，本节不重复改变其业务语义。
4. 本规约不定义接口路由、请求方法、报文对象、字段结构、认证协议、传输协议或技术错误码；上述内容在后续接口设计及接口契约中确定。
5. 平台内部接口不得作为医院接入契约直接承诺；医院接入接口的后续技术设计不得要求医院调用平台管理端专用接口完成上述业务流程。

### 用户界面

#### 通用界面要求

1. 平台页面的可见、查询、操作、下钻和导出能力必须受平台统一权限和可信医院院区上下文控制。
2. 页面应以业务名称、当前状态、关键时间和必要说明表达业务事实，不展示平台内部存储标识或技术排障信息。
3. 页面中的患者姓名、证件号码、联系电话等敏感信息按照对应业务用途和权限展示；统计及导出场景必须保持脱敏。
4. 页面具体布局、控件类型、菜单位置和视觉样式由界面设计确定，但不得减少本规约定义的业务能力、查询条件、状态提示或权限边界。

#### 互认项目管理

1. 页面进入时自动刷新当前有效标准项目目录，并提供手动刷新能力。
2. 页面展示互认项目的标准项目编码和名称、可互认时间、当前参考价格、启停状态、来源状态及框架修改信息。
3. 页面支持从当前有效最细层标准项目中选择项目，填写可互认时间和参考价格后新增并默认启用。
4. 页面支持修改可互认时间、参考价格和启停状态，不提供物理删除、价格历史或版本恢复。
5. 目录刷新失败时明确提示并保留既有来源状态；来源不可用项目应有明确状态提示和受限操作。

#### 项目编码对照管理

1. 医院用户页面只展示和维护当前登录医院、院区的数据；平台管理员按权限跨机构查看。
2. 页面以平铺列表提供当前启用且来源有效的互认项目，并支持按编码或名称搜索选择。
3. 页面支持新增、修改、启用和停用对照；医院、院区、院内项目编码创建后不得提供修改入口。
4. 页面展示院内项目编码、名称、互认项目、启停状态和备注，不提供价格维护或平台逐条审批操作。
5. 唯一性冲突、互认项目停用或来源不可用时，页面应明确提示不能保存或启用的业务原因。

#### 接收医院互认使用统计

1. 页面支持按日期范围、医院、院区、决定科室和互认项目查询权限范围内的数据；决定医生可以作为明细查询条件。
2. 页面展示提醒、采纳、不采纳、引用、同期互认率和预计节省金额，并区分总体口径与跨机构子集口径。
3. 提醒、采纳、不采纳和引用汇总数字支持下钻到对应脱敏明细，预计节省金额随采纳明细展示。
4. 页面提供不采纳原因次数及占比，并允许在明细中查看其他原因的脱敏补充说明。
5. 页面不提供趋势图、医生排名、绩效评价或患者身份解除脱敏能力。

#### 来源医院被互认统计

1. 医院管理员在来源医院被互认统计中只能查看本院报告形成的被互认汇总和脱敏明细；平台管理员按权限查看全县数据。
2. 页面展示被互认总体次数和跨机构被互认子集，不将两者相加。
3. 明细可以展示互认项目、接收医院及院区、决定科室、决定医生和互认时间，患者姓名必须脱敏。
4. 页面不展示或汇总来源医院贡献金额。

#### 统计导出入口

1. 互认使用和来源医院被互认的汇总及明细页面按权限提供 Excel 导出入口。
2. 导出入口沿用页面当前查询条件和数据权限，导出全部匹配记录而非当前分页。
3. 页面应明确导出仍使用脱敏数据，不提供 CSV、PDF 或解除脱敏选项。
4. 当前查询没有匹配记录时，页面提示“当前条件下无可导出数据”，不生成空 Excel 文件。

#### 医院 HIS 界面边界

1. 候选提醒、医生查看、采纳或不采纳操作、继续或撤销院内医嘱以及病历写入界面由医院 HIS 负责。
2. 互认平台不规定医院 HIS 的页面布局、弹窗形式、控件、菜单或调用时机。
3. 医院 HIS 的界面行为不得替代明确的处理结果和引用结果提交；关闭提示、查看文件或离开页面均不能由平台推断为采纳、不采纳或引用。
