# 简介



## 目的



本文档用于定义检验检查结果互认平台的软件需求规约，明确当前版本的业务范围、参与者、前置条件、后置条件、主事件流、备选流、业务规则、关键属性、设计约束和用户界面要求，作为后续设计、开发、测试、评审和验收的业务依据。



本文档适用于检验检查结果互认平台及其与平台权限体系、可信组织服务、医院侧采集服务和医院 HIS 之间的业务协作。医院 LIS、PACS 及医院侧采集服务的内部实现不属于互认平台的建设范围，本文仅在相关功能中描述其与互认平台之间必要的业务责任和交互边界。



本文档不替代接口设计文档、数据库设计、技术架构、安全设计、部署方案或医院院内系统改造方案。本文未定义具体路由、报文结构、数据传输协议、数据库表、代码模型、后台任务或其他技术实现。



## 定义、首字母缩写词和缩略语



| 术语或缩写 | 定义 |

| --- | --- |

| HIS | Hospital Information System，医院信息系统。医院根据自身接诊或开单流程调用互认平台能力、向医生展示匹配并反馈处理及引用结果。 |

| LIS | Laboratory Information System，实验室信息系统。医院侧采集服务可以从 LIS 获取审核完成的检验报告，但互认平台不规定其内部采集方式。 |

| PACS | Picture Archiving and Communication System，医学影像存档与通信系统。互认平台不接收或保存 DICOM 影像文件，只处理检查报告随附的影像调阅地址及来源影像状态。 |

| 标准医疗项目 | 由互认平台统一维护、供报告采集、互认配置、匹配和统计使用的项目语义基准。标准项目编码在平台内全局唯一。 |

| 互认项目 | 互认平台在组织范围内为本地标准医疗项目建立的互认配置。配置引用标准项目编码，保存组织归属、可互认时间和自身启停状态；名称、类型、分类和分组来自本地标准目录。 |

| 可互认时间 | 从报告时间开始计算、报告可以作为互认匹配返回的时间长度。以天为单位，只允许正整数，最小值为一天；一天按连续二十四小时计算，结束边界包含在有效范围内。查询使用互认项目的当前配置，该配置不用于报告接收校验，也不是报告保存期限。 |

| 组织、医院、院区 | 平台业务归属层级为组织 → 医院 → 院区，分别使用组织编码、医院编码和院区编码定位；名称由可信组织服务提供。 |

| 院内项目 | 医院某一院区在本地业务系统中实际使用的检查或检验项目及其编码。互认平台不维护院内项目主数据或项目对照。报告明细可保留来源项目名称和可选来源项目编码作为原文追溯信息，不参与平台业务匹配。 |

| 标准项目类型、分类和分组 | 标准项目类型固定为检验、检查。分类和分组由互认平台统一维护，不按组织复制；一个分组只能归属一个分类，一个标准项目只能归属一个类型、分类和分组。 |

| 标准目录不可用 | 标准项目自身、所属分组或所属分类停用后的状态。停用上级不改写下级自身状态；上级恢复后，自身仍启用的下级对象和互认配置自动恢复实际有效。 |
| 报告业务标识 | 由组织、医院、院区、报告类型和报告单号共同组成，用于在互认平台唯一识别一份检验或检查报告。 |

| 报告识别信息 | 匹配响应中用于报告分组和项目关联的信息，由报告类型、来源报告单号、平台报告 ID 和报告版本 ID 组成。 |

| 完整报告提交 | 检验报告和检查报告分别提供的报告提交能力。医院只提交报告单号、当前完整结构化报告、源端报告修改时间及 PDF，不提交新增、更正或作废状态；平台按报告业务标识创建首个版本或追加新版本，每次成功保存均形成新版本。 |

| 报告作废 | 与完整报告提交分开的独立能力。医院只提交来源报告单号、作废时间和作废原因，不重复提交报告内容及 PDF。 |

| 源端报告修改时间 | 医院源系统中报告当前完整内容最后一次实际生成或修订的时间。该时间随每次完整上传保存，用于来源追溯，不用于判断是否重复上传、版本顺序或内容是否变化。 |

| 报告版本 | 一份报告的每次完整上传成功保存时形成的完整且不可变内容版本，由平台按成功保存顺序生成内部版本序号。旧版本保留用于管理端追溯，但停止参与后续匹配查询、引用详情和新的引用；最后成功保存的版本为当前有效版本。 |

| 当前有效报告 | 当前未被作废、且属于该报告最后成功保存版本的报告。是否能够成为互认匹配，还需满足互认项目状态、可互认时间及匹配查询的其他规则。 |

| 混合项目报告 | 同时包含提供或未提供互认项目编码明细的完整报告。无论是否存在当前有效互认项目编码，平台均接收并完整保存报告；只有关联当前组织内当前启用且标准目录层级有效互认项目的明细参与匹配，未提供或不可用编码的明细只用于版本保存、展示和来源追溯。 |

| 互认匹配 | 平台针对一个去重后的互认项目，按照匹配选择规则确定并返回的一份当前有效报告。联合报告可以同时为多个互认项目形成匹配，但报告内容不按项目拆分为多份报告。 |

| 互认匹配记录 | 平台针对一次成功处理并形成非空结果的匹配查询保存的完整匹配记录，具有平台生成的互认匹配记录 ID，并记录接收医院、院区、患者、本次来源就诊、互认匹配生成时间及全部实际返回项目。 |

| 互认匹配项 | 互认匹配记录内一个实际返回的项目，具有平台生成的互认匹配项 ID，关联本次拟开标准项目、互认项目、命中的报告版本及匹配内容。每次查询均生成新的互认匹配记录 ID 和互认匹配项 ID，不提供跨查询稳定匹配引用。 |

| 互认时间 | 医生实际作出某次采纳或不采纳处理结果的业务时间，由医院 HIS 提供并精确到秒，用于区分同一就诊中针对同一匹配发生的多次真实互认处理。 |

| 互认处理结果 | 医生明确作出的采纳或不采纳处理结果。匹配返回、结构化内容展示、PDF 或影像入口访问均不自动形成互认处理结果。 |

| 引用详情 | 医生采纳匹配后，医院 HIS 在有效期内获取的、可用于写入本次病历的项目内容及必要报告公共上下文。获取引用详情本身不表示已经成功写入病历。 |

| 引用详情有效时长 | 采纳处理结果首次成功保存后，医院 HIS 可以继续调用引用详情接口的全平台统一时长。该时长使用现有系统参数系统按正整数分钟维护，默认七百二十分钟。 |

| 引用结果 | 医院 HIS 将已采纳内容成功写入本次病历后向平台提交的实际引用事实。平台只接收已经引用的正向事实，不要求提交未引用状态。 |

| 提醒次数 | 平台成功处理匹配查询并生成非空互认匹配记录时，按集合内每个互认匹配项形成的统计次数。即使医院未收到响应，已经生成的提醒事实也不撤销；提醒不表示医院 HIS 已实际弹窗或医生已经查看、采纳或引用。 |

| 预计节省金额 | 医生采纳互认项目时，按照采纳处理结果成功保存时接收组织、接收医院、接收院区当前金额形成的业务统计金额。该金额不表示实际收费、医保结算、患者退费或医院财务收入。 |

| 医院业务科室和人员标识 | 医院侧在报告、互认处理结果或引用结果中直接提供的业务科室 ID、科室名称、人员 ID 和人员名称。ID 使用 String，唯一范围为院区级，不要求对应主体维护在平台权限体系中。 |

# 整体说明



## 产品总体效果



检验检查结果互认平台用于统一跨医疗机构的检查、检验项目语义，接收和管理医院审核完成的检查、检验报告，并在患者接诊或开单过程中向医院 HIS 提供可互认匹配。医生在医院 HIS 中查看匹配内容后作出采纳或不采纳处理结果；采纳后，医院 HIS 可以获取引用详情，将相应内容写入本次病历并反馈实际引用结果。



平台通过组织范围内统一的标准项目编码解决跨医院项目语义一致问题，通过患者精确关联、报告版本管理和匹配选择规则保证匹配业务身份明确。平台记录医院明确反馈的互认处理和引用事实，并面向医院及平台管理员提供权限范围内的统计、下钻和 Excel 导出能力。



平台不代替医生作出临床决定，不直接操作医院 HIS 中的医嘱或病历。匹配返回、结构化内容展示、PDF 查看或影像入口访问均不自动表示医生已经采纳或引用。报告中的来源异常、危急值、检查所见和诊断结论均按来源内容保存和展示，平台不重新计算、推断或改写临床结论。



## 产品功能



| 编号 | 功能 | 说明 |

| --- | --- | --- |

| F01 | 标准医疗项目目录管理 | 维护检验/检查类型下的标准项目分类、分组和标准医疗项目，以及当前有效标准目录。 |

| F02 | 标准项目互认配置 | 按组织选择当前有效标准项目，维护可互认时间和互认配置启停状态。 |

| F03 | 报告采集与生命周期 | 接收检验报告和检查报告的完整提交及独立作废，每次完整提交成功均形成新版本，保存完整结构化内容、PDF、版本关系和必要来源信息，并在管理端提供受权限控制的只读历史版本查看。 |

| F04 | 互认匹配查询 | 根据患者身份和一个或多个拟开标准项目编码返回符合条件的互认匹配，并对联合报告进行完整分组；没有匹配时返回空匹配结果。 |

| F05 | 互认处理结果 | 按互认匹配记录接收医生对全部互认匹配项一次完整、原子且不可更改的采纳或不采纳处理结果，并形成对应统计事实和预计节省金额。 |

| F06 | 获取引用详情 | 在互认处理结果为采纳且匹配报告版本仍有效时，返回本次病历引用所需的项目内容和报告公共上下文。 |

| F07 | 提交引用结果 | 接收医院 HIS 已成功写入本次病历的实际引用事实，记录实际引用时间、科室和医生。 |

| F08 | 互认统计与分析 | 提供提醒、采纳、不采纳、引用、同期互认率、预计节省金额、接收医院使用和来源医院被互认分析。 |

| F09 | 互认统计导出 | 按当前查询条件、数据权限和脱敏规则导出互认汇总及明细，文件格式为 Excel。 |

| F10 | 互认项目金额维护 | 平台管理员或医院管理员在权限范围内维护组织、医院、院区和标准项目对应的当前金额。 |



平台面向医院 HIS 的在线互认主流程由查询互认匹配、提交互认处理结果、获取引用详情和提交引用结果四类核心业务能力组成。报告采集、身份认证、互认项目配置、报告更正或作废等其他能力不计入这四类核心业务能力。



端到端业务过程如下：



1. 平台管理员维护平台统一的标准医疗项目类型、分类、分组和标准项目。

2. 平台管理员按组织为当前有效标准项目建立互认配置；医院管理员在组织、医院、院区范围内维护互认项目当前金额。

3. 医院侧采集服务在检查或检验报告审核完成或修订后重新审核时提交当前完整报告；报告失效时调用独立作废能力。

4. 医院 HIS 在患者接诊或开单过程中，以患者身份和拟开标准项目编码发起互认匹配查询。

5. 平台校验组织范围内互认项目编码，按当前有效报告、可互认时间和匹配选择规则返回符合条件的匹配结果。

6. 医院 HIS 向医生展示匹配结果及可用的 PDF、影像入口；医生根据患者当前情况作出采纳或不采纳处理结果。

7. 医院 HIS 使用互认匹配记录 ID，完整提交集合内全部互认匹配项的采纳或不采纳处理结果；平台原子保存实际决定、互认时间、科室、医生、不采纳原因或预计节省金额，首次保存后不得更改。

8. 对于已采纳匹配，医院 HIS 获取引用详情并将相应内容写入本次病历，写入成功后提交引用结果。

9. 平台依据匹配返回、已保存互认处理结果和实际引用事实形成权限范围内的统计、下钻和导出结果。



## 用户特征



| 用户或外部参与方 | 特征与职责 |

| --- | --- |

| 平台管理员 | 维护平台统一标准医疗项目目录和组织范围内的互认配置；维护所有组织、医院、院区的互认项目金额；按现有数据权限查看报告及只读历史版本；查看、下钻和导出授权范围内的互认统计。 |

| 医院管理员 | 维护本医院及有权院区的互认项目金额；查看本医院及有权院区上传报告的完整内容、只读历史版本和 PDF；查看接收侧互认使用统计、来源侧被互认统计及相应脱敏明细，并按权限导出。 |

| 医院侧采集服务 | 由医院或实施厂商负责，在来源报告审核完成或修订后重新审核时提交当前完整报告，在报告失效时调用独立作废能力，并处理明确失败和超时重传。该服务不属于互认平台的建设模块。 |

| 医院 HIS | 决定在线互认能力在接诊或开单流程中的调用时机，展示匹配，提交互认处理结果，获取引用详情，将内容写入病历并反馈引用结果。 |

| 医生 | 在医院 HIS 中查看匹配结构化内容、报告 PDF 或影像，根据患者当前情况作出采纳或不采纳处理结果；平台不代替医生判断。 |



医院侧采集服务、医院 HIS、LIS、PACS 和影像服务由医院或相应厂商建设和维护。互认平台只定义与其发生业务协作时的输入、输出、责任和状态边界，不规定医院内部页面、数据读取方式、采集表、轮询周期、本地队列、硬件或网络实现。



## 约束



1. 平台只接收上线后新产生并审核完成的检查、检验报告，不导入上线前历史报告。

2. 一份报告首次创建或追加后续完整版本时，均完整保存来源报告明细；只有当前组织内互认配置启用，且标准项目、所属分组和所属分类均启用的项目编码明细参与新的互认匹配。未提供编码，或明确提供但不存在、超出组织范围、停用或标准目录不可用的编码不阻止报告接收，但对应明细不参与互认。

3. 报告接收不按可互认时间筛选，但参与互认的项目必须同时满足互认配置、标准项目、所属分组和所属分类均启用；任一对象停用时只阻止新的匹配查询形成匹配项，不否定已经形成的匹配记录后续按 F05 保存真实处理事实的规则。

4. 跨院患者以证件类型和证件号码精确关联，并使用姓名、性别代码和出生日期进行一致性校验。平台不使用姓名相似度、电话或院内就诊卡进行替代匹配。

5. 报告上传、互认处理和引用结果涉及的医院业务科室和人员，由医院侧直接提供具体 ID 和名称；ID 使用 String，不要求对应主体存在于平台权限体系。

6. 必填的科室或人员字段必须同时提供 ID 和名称；可选字段的 ID 和名称必须同时有值或同时为空，不允许只提供其中一项。

7. 平台直接保存请求提供的具体 ID 和名称，不根据 ID 补查或覆盖名称。医院业务科室和人员 ID 在院区范围内唯一，同一 ID 在不同院区可以代表不同主体。

8. 每次完整报告提交或作废请求只处理一份报告。完整报告提交以一个请求同时提供完整结构化报告及 PDF，二者共同成功或共同失败；作废只提交来源报告单号、作废时间和作废原因。

9. 报告按可信调用身份中的组织、医院、院区、所调用报告类型能力和医院提供的报告单号唯一识别。医院不提交平台报告 ID 或组合报告业务标识，平台不使用患者、项目、报告内容或 PDF 判断报告身份。

10. 平台只按报告业务标识和生命周期状态处理完整提交，不比较完整内容或文件摘要，也不依据源端报告修改时间判断重传、版本顺序或内容是否变化。报告不存在时创建首个版本；报告存在且未作废时，每次成功完整提交均追加新版本，最后成功保存的版本为当前版本；报告已经作废时拒绝继续提交完整版本。

11. 后续完整版本形成后，原版本停止参与匹配查询、引用详情和新的引用；报告作废不形成内容版本且不物理删除，作废后不再返回为匹配或新的引用内容。

12. 每个互认项目只返回查询时点前、当前可互认时间内检查或检验时间最晚的一份有效报告；检查或检验时间相同时，优先选择报告时间较晚的一份；两者均相同时，在匹配数据及相关配置未变化的情况下稳定返回同一份报告。

13. 一份联合报告命中多个互认项目时，按一份完整报告分组返回；互认匹配、处理决定和引用事实仍按具体互认项目分别形成。

14. 每次非空匹配查询生成新的互认匹配记录 ID 和互认匹配项 ID；重试按新查询处理，不使用查询流水号、稳定匹配引用或幂等键恢复旧组。

15. 匹配查询、匹配返回、结构化内容展示、PDF 查看、影像入口访问和引用详情获取均不自动形成采纳或引用事实。

16. 互认处理结果必须来自医生明确反馈的采纳或不采纳，并完整覆盖互认匹配记录全部项目；首次保存后不得更正、撤销或删除。引用结果必须来自医院 HIS 已经成功写入本次病历的正向事实。平台不根据未反馈状态推断拒绝、忽略、采纳或引用。

17. 不采纳必须使用平台统一原因代码；选择其他原因时必须提供补充说明。各医院不得自行扩展或修改原因代码。

18. 预计节省金额在采纳处理结果成功保存时按接收组织、接收医院、接收院区的当前互认项目金额形成，不使用来源医院金额，不采集数量，不模拟按次、按部位、组合收费、医保结算或患者实际退费。

19. 提醒、采纳、不采纳、引用和预计节省金额分别使用已确认的业务时间归入统计期间，接口接收时间不得替代业务时间。

20. 医院管理员只能查看本院及有权院区的数据，平台管理员按授权查看组织范围内数据。统计页面和导出中的患者姓名、证件号码必须保持脱敏。

21. 本院报告匹配由全局开关控制，默认关闭；开启后使用全局本院报告排除时长，默认四十八小时。参数调整只影响后续查询，不倒改已有报告、互认处理、引用和统计事实。

22. 引用详情调用受全平台统一的引用详情有效时长控制，默认七百二十分钟；该限制只控制重新获取引用详情，不控制医院已经合法取得并保存的数据、PDF 下载或引用结果提交。

1. 互认平台本地标准目录能够稳定提供项目类型、分类、分组和标准项目，标准项目编码在平台内全局唯一。

2. 医院源系统和医院 HIS 能够为涉及的业务科室和人员提供院区范围内使用的 String 类型 ID 及对应名称，并保证必填字段完整、可选字段成对提供。

3. 平台权限体系继续提供菜单和接口授权，不承担医院业务科室和人员主数据维护、存在性校验或名称补全。

4. 权限系统负责菜单、接口和操作授权；能够请求某接口即表示已经获得对应授权，互认平台不重复判断操作权限。互认平台保留的组织、医院和院区校验仅用于可信业务归属及记录归属一致性，不构成操作权限校验。

5. 医院或实施厂商负责建设并运行医院侧采集服务。该服务能够从医院源系统识别首次审核完成、修订后重新审核或作废的报告，前两者调用相同的完整报告提交能力，作废调用独立作废能力。

6. 医院 LIS、PACS 或其他来源系统能够提供已确认字段中在源系统实际存在的内容；对于规定为“源系统存在时必须提供”的信息，医院不得在源系统存在时无故省略。

7. 医院 HIS 负责在合适的接诊或开单环节调用在线互认能力、向医生展示匹配、执行院内医嘱或病历操作，并在真实业务动作完成后提交处理或引用结果。

8. 接入医院只上传依其制度允许常规跨院共享的报告。需要专项授权才能共享的报告在相关授权机制另行明确前不上传。

9. 检查报告的影像调阅地址由医院或区域影像中心提供并负责其可用性、访问控制、内容和保存期限。平台只保存并原样返回地址，不测试、代理、缓存或保证可用性；报告形成后续版本或作废后，平台停止在后续响应中返回原地址，但无法撤回已经下发的外部地址。

10. 医院侧在完整报告提交超时或未取得明确结果时，可以原样重新提交完整报告及源端报告修改时间；每次成功提交均按新的完整上传形成新版本。作废因原报告不存在失败时，医院保证报告先成功提交后重新调用作废能力。

11. 医院 HIS 对已经接收并保存在院内的数据承担后续更新和失效处理责任。平台不通过主动推送补偿医院未反馈引用结果或未重新查询的情况。

12. 组织、医院和院区由可信组织服务提供编码及层级关系；检验协同和检查协同不向互认平台提供项目对照或同步数据。

13. 平台现有系统参数系统能够定义全平台统一参数、提供默认值和格式校验，并支持互认平台在每次获取引用详情时按参数编码读取当前值。

# 具体需求



## 功能



### F01 标准医疗项目目录管理



#### 参与者



| 参与者 | 职责 |

| --- | --- |

| 平台管理员 | 维护平台统一的标准项目类型、分类、分组和标准医疗项目。 |

| 互认平台 | 校验标准目录层级、唯一性和当前有效状态。 |



#### 需求背景



互认报告、互认配置和统计需要统一的项目语义。平台本地维护“项目类型 → 分类 → 分组 → 标准项目”的目录层级；项目类型固定为检验和检查，标准项目编码在平台内全局唯一。



#### 前置条件



1. 标准目录管理接口的操作授权由权限系统负责；本功能不重复判断操作权限。

2. 组织、医院和院区上下文可由可信组织服务确定；标准目录本身不按组织复制。



#### 后置条件



1. 分类、分组和标准项目保存成功后形成默认启用的标准目录对象。

2. 普通修改不改变启停状态；启停只能通过独立启用/停用操作完成。

3. 停用对象保留历史数据，但不属于当前有效标准目录；上级恢复后，自身仍启用的下级对象自动恢复当前有效，自身已停用的对象仍需独立启用。


#### 主事件流



1. 平台管理员进入标准目录管理页面。

2. 平台展示类型、分类、分组和标准项目层级。

3. 管理员新增或修改目录对象的可编辑资料，或执行独立启停操作。

4. 平台校验层级归属、名称和编码唯一性，以及分类项目类型的修改限制。

5. 校验通过后保存并返回最终状态。



#### 备选流



1. 分类名称在全平台标准目录内重复，或同一分类下分组名称重复时，平台拒绝保存；本版本不维护分类编码、分组编码或排序值。

2. 新增分组未归属有效分类、新增标准项目未归属有效分类和分组时，平台拒绝保存；此限制不用于拒绝停用对象或停用上级下的名称、备注维护。

3. 分类和分组的名称、备注均可修改，不受自身、上级启停状态及下级使用情况限制，名称唯一性规则不变。分类存在下级分组（含已停用）时不得修改项目类型，无下级分组时可修改。分组创建时确定所属分类，创建后不允许改挂，无论是否有下级项目；分类、分组均不得物理删除。

4. 标准项目创建后只允许修改备注；编码、名称、分类和分组不得通过普通修改改变。



#### 业务规则



1. 项目类型固定为检验和检查。

2. 分类名称在全平台标准目录内唯一，分组名称在同一分类下唯一，标准项目编码全局唯一。

3. 分类、分组和标准项目创建后默认启用；普通修改不改变启停状态。

4. 启用和停用必须通过独立命令完成；分类或分组停用不修改下级对象自身状态，上级恢复后自身仍启用的下级对象自动恢复当前有效。
5. 当前有效标准项目必须同时满足自身、所属分组和所属分类均启用。
6. 对已启用对象再次启用或对已停用对象再次停用时，平台按幂等成功处理：不改变已有状态，不重复发布启停事件。
7. 资料修改整份提交可编辑字段，备注未改时传原值、清空时传 `null`，不使用字段省略表达保留原值。即使内容相同也提交并执行校验、保存、更新操作人和操作时间及登记修改事件；启停仍单独维护，不适用此资料保存规则。

| 属性 | 说明 |

### F02 标准项目互认配置



#### 参与者



| 参与者 | 职责 |

| --- | --- |

| 平台管理员 | 在组织范围内选择本地当前有效标准项目，维护可互认时间和互认配置启停状态。 |

#### 需求背景



平台需要在本地标准目录基础上按组织选择允许参与互认的标准项目，并维护组织级互认时间和启停配置；标准项目类型、分类和分组直接复用本地标准目录，不再复制一套组织级分类分组。



#### 前置条件



1. 互认项目配置接口的操作授权由权限系统负责；本功能不重复判断操作权限。

2. 组织编码能够从可信组织上下文确定。

3. 新增或重新启用互认配置时，目标标准项目、所属分类和分组当前有效；仅修改既有配置可互认时间时不受本条件限制。



#### 后置条件



1. 互认配置保存成功后，形成一条默认启用的组织级互认配置。

2. 配置修改只调整可互认时间，不改变启停状态。

3. 启停状态由独立启用/停用操作维护。



#### 主事件流



1. 已获得菜单和接口授权的管理员进入当前组织的互认项目配置页面；平台管理员可选择允许的组织，医院管理员限定为可信上下文允许的所属组织。

2. 平台展示当前有效标准项目及已有互认配置。

3. 管理员选择标准项目并填写可互认时间，或修改已有配置时间、执行启停操作。

4. 平台校验组织归属、标准目录有效性、时间范围和重复配置。

5. 校验通过后保存配置并返回最终状态。



#### 备选流



1. 标准项目、分类或分组不可用时，平台拒绝新增或重新启用互认配置；目录恢复后，自身仍启用的互认配置自动恢复可用，自身已停用的配置仍需独立启用。配置或标准目录不可用时，仍允许修改既有配置的可互认时间，但不改变配置启停状态，也不因此形成新的匹配。
2. 可互认时间为空、零、负数、小数或永久有效时，平台拒绝保存。

3. 已存在相同组织和标准项目配置时，平台拒绝重复新增。



#### 业务规则



1. 互认配置引用本地标准项目编码，不重复保存标准项目名称、分类或分组实体属性。

2. 可互认时间以天为单位，只允许正整数，最小值为一天。

3. 互认配置创建后默认启用；普通修改不改变启停状态，启停通过独立命令完成。

4. 互认项目停用后不参与新的匹配；已有报告和历史处理事实保留。标准项目、分类或分组恢复启用后，配置自身仍启用的互认项目自动恢复用于新匹配；配置自身仍停用的互认项目必须单独启用。

5. 本功能不维护医院院内项目、不维护医院院区项目对照。

6. 对已启用互认配置再次启用或对已停用互认配置再次停用时，平台按幂等成功处理：不改变已有状态，不重复发布启停事件。



#### 关键属性



| 属性 | 说明 |

| --- | --- |

| 组织编码 | 互认配置归属的组织编码，来自可信组织上下文；标准目录本身不按组织复制。 |

| 项目类型 | 固定值检验或检查。 |

| 分类、分组 | 通过标准项目关联的本地目录对象派生展示，不随互认配置重复保存。 |

| 启停状态 | 启用或停用；停用后不参与新的匹配。停用配置仍按既有唯一键保留，不允许重复创建；恢复使用必须通过独立启用操作。 |

### F10 互认项目金额维护



#### 参与者



平台管理员、医院管理员、互认平台



#### 需求背景



平台需要按组织、医院、院区和标准项目维护接收侧当前金额，为采纳处理结果计算预计节省金额。金额不是标准项目本体属性，也不是医院项目对照数据。



#### 前置条件



1. 金额维护接口的操作授权由权限系统负责；本功能不重复判断操作权限。

2. 组织、医院和院区范围由可信上下文确定或按平台管理员授权选择。

3. 标准项目编码对应的平台本地标准项目已被当前组织选为互认项目。



#### 后置条件



1. 金额保存成功后成为该组织、医院、院区和标准项目的当前金额。

2. 未配置金额不阻碍互认处理；采纳时按零元形成预计节省金额。

3. 金额调整只影响之后成功保存的采纳处理结果，不重算历史金额。



#### 主事件流



1. 管理员选择权限范围内的组织、医院、院区和标准项目。

2. 平台展示当前金额或未配置状态。

3. 管理员输入非负且最多两位小数的人民币金额。

4. 平台校验数据范围和金额格式。

5. 校验通过后保存当前金额并更新最后操作信息。



#### 备选流



1. 医院管理员提交其他医院或无权院区时，平台拒绝保存。

2. 金额为负数或超过两位小数时，平台拒绝保存。

3. 标准项目不存在，或当前组织未建立该标准项目的互认配置时，平台拒绝保存。



#### 业务规则



1. 金额业务键为组织编码、医院编码、院区编码和标准项目编码。

2. 零元是有效配置；未配置金额按零元参与预计节省金额计算。

3. 不保存医院院内项目编码、名称或项目对照关系。

4. 不建立独立金额版本、金额变更历史或历史金额重算。

5. 只要组织级互认配置存在，标准目录或互认配置当前停用也允许查看和维护金额；停用不删除既有金额，金额只在后续新采纳形成时使用。



#### 关键属性



| 属性 | 说明 |

| --- | --- |

| 组织、医院、院区编码 | 金额数据范围和业务键组成。 |

| 标准项目编码 | 本地标准目录中的稳定项目编码。 |

| 当前金额 | 非负、最多两位小数的人民币金额。 |

| 最后操作信息 | 最后操作人和最后操作时间。 |



### F03 报告采集与生命周期



#### F03.1 公共报告要求与生命周期



##### 参与者



| 参与者 | 职责 |

| --- | --- |

| 医院源系统 | 在报告首次审核完成、修订后再次审核或作废时形成明确业务事件。 |

| 医院侧采集服务 | 首次审核和修订后重新审核均提交当前完整报告；报告失效时调用独立作废能力；处理失败和结果未知时按原请求重试。 |

| 互认平台 | 根据报告业务标识和生命周期状态创建首个版本或追加新版本；每次成功完整提交均保存一个新版本，最后成功保存的版本作为当前版本，并处理独立作废。 |

| 平台权限体系 | 提供菜单和接口授权，不负责医院业务科室和人员名称补全。 |

| 医院管理员 | 查看本医院及有权院区上传报告的完整内容、历史版本和对应 PDF。 |

| 平台管理员 | 按现有数据权限查看授权范围内报告的完整内容、历史版本和对应 PDF。 |



##### 需求背景



平台需要持续接收上线后新产生及修订后重新审核的检查、检验报告，保持来源报告的结构化内容和原始 PDF。医院不需要理解平台版本概念，也不提交新增、更正状态、平台报告 ID、组合报告业务标识、医院版本号或版本变更原因；平台通过相同的完整报告提交能力自行形成首个或后续完整版本。报告失效使用独立作废能力。平台还需为医院管理员和平台管理员提供受数据权限控制的只读历史版本查看，使报告修订、责任人员、来源备注和 PDF 能够追溯。



##### 前置条件



1. 完整报告已经完成医院内部审核；作废已经由医院源系统明确声明。

2. 报告可以不包含当前有效互认项目编码；未提供编码，或明确提供但不存在、超出组织范围、停用或标准目录不可用的编码不阻止完整报告提交，但对应明细不参与互认。

3. 报告携带有效的跨院患者标识、必填人口学信息、来源就诊标识及规定的报告公共信息。

4. 报告涉及的医院业务科室和人员已提供具体 ID 与名称；必填字段完整，可选字段成对提供。

5. 完整报告提交同时提供来源报告单号、完整结构化报告、源端报告修改时间及 PDF 文件流；上传请求可以携带 PDF 文件名，文件名缺失或无效时由平台使用“报告单号.pdf”作为安全下载名称。

6. 作废请求只提供来源报告单号、作废时间和作废原因；组织、医院、院区来自可信调用身份，报告类型由所调用的检验或检查作废能力确定。



##### 后置条件



1. 报告不存在时，完整提交成功后保存当前有效报告及首个完整版本，平台生成内部版本序号并记录实际接收时间。

2. 报告存在且未作废时，每次完整提交成功均保存完整且不可变的新版本及版本关系，原版本停止参与匹配查询、引用详情和新的引用；最后成功保存的版本作为当前版本。

3. 作废成功后保存作废时间和原因，不生成新的内容版本；报告停止参与匹配查询、引用详情和新的引用，但报告及历史版本不被物理删除。

4. 任一校验或保存步骤失败时，本次报告变更不产生部分业务数据。

5. 完整报告提交和报告作废成功时同步返回布尔值 true；完整报告重复提交只要校验和保存成功即返回 true，并按新的完整上传形成新版本。校验失败、报告已作废或原报告不存在时，平台直接使用现有框架抛出描述事实的业务异常，不以 false 表示业务失败；需求阶段不定义错误代码、异常响应 DTO 或传输格式。

6. 有权限的医院管理员和平台管理员可以在管理端报告详情中只读查看全部版本并下载各版本 PDF，医院 HIS 仍只能取得当前有效版本。



##### 主事件流



1. 医院源系统首次审核或修订后重新审核报告时，医院侧采集服务调用对应报告类型的完整报告提交能力；报告失效时调用独立作废能力。

2. 平台使用可信调用身份中的组织、医院和院区、所调用能力确定的报告类型以及医院提供的来源报告单号组合报告业务标识。

3. 平台校验调用组织、医院、院区、患者身份、来源就诊、业务科室和人员 ID/名称成对提供规则、报告公共字段和互认项目编码。

4. 完整报告提交时，平台将结构化报告和 PDF 文件流作为一个完整单元校验，保存上传请求携带或平台回退生成的 PDF 下载文件名；平台保留各明细提供或未提供的互认项目编码，只有当前组织内有效的编码形成后续互认匹配资格，编码当前不可用不拒绝来源当前完整内容。

5. 平台根据报告是否存在及生命周期状态创建首个版本或追加新版本；每次成功完整提交均形成新版本，不查询或比较历史版本的源端报告修改时间。作废则根据报告是否存在、生命周期状态、作废时间和原因处理。

6. 平台保存报告变更后同步返回最终成功结果；只有业务数据已经完整保存时才能返回成功。



##### 备选流



1. 报告不存在时形成首个版本；报告存在且未作废时，每次完整报告提交成功均形成新版本，不因源端报告修改时间相同、较早或较晚而拒绝或合并。

2. 报告已经作废时，新的完整报告提交失败，不允许通过再次提交或历史版本恢复。

3. 首次作废时，作废时间必须晚于或等于当前报告版本的平台接收时间，且不得晚于平台收到本次作废请求的时间，两个边界均包含；不以源端报告修改时间进行版本顺序判断。报告已作废且作废时间和原因均一致时幂等成功，任一不同则返回作废信息冲突。

4. 患者证件已存在但姓名、性别或出生日期不一致时返回患者身份信息冲突，不覆盖患者资料，也不创建第二个患者。

5. 报告没有任何当前有效互认项目编码时，平台仍接收并保存完整报告及 PDF，但该版本不形成匹配；明确提供但不存在、超出组织范围、停用或标准目录不可用的编码同样保留为来源报告内容且不参与互认。

6. 医院业务科室和人员 ID、名称字段不依赖平台权限体系存在性校验；字段缺失、仅提供 ID 或仅提供名称时，整次请求失败且不保存业务数据。

7. 结构化内容、PDF 或任一必填内容校验失败时，整份报告失败，不先保存其中一部分。

8. 调用超时或医院侧未取得明确结果时，医院侧可以原样重新提交完整报告；若重试成功则按一次新的完整上传形成新版本，不以幂等判重合并；作废因原报告不存在失败时，医院确认原报告提交成功后重试作废。



##### 业务规则



1. 检验报告和检查报告分别提供完整报告提交能力和独立作废能力，请求中不设置新增、更正或作废操作类型。

2. 每次请求只处理一份报告，不将多份报告组成共同成功或共同失败的业务批次；医院侧可以并发提交多份独立报告。

3. 报告业务标识由组织、医院、院区、报告类型和报告单号共同组成；组织、医院和院区来自可信调用身份。不同报告必须使用不同业务标识，平台不按患者、就诊、项目、报告内容或 PDF 推断报告身份。

4. 平台根据报告是否存在和生命周期状态自行判断创建首个版本或追加新版本；每次成功完整提交均形成新版本，不要求医院理解或提交平台版本状态。

5. 完整报告提交不支持局部字段修改，不要求更正原因或版本变更原因；检查和检验报告均使用来源报告已有的备注字段保存来源备注。

6. 作废不重复提交报告内容和 PDF，只改变报告生命周期状态，不形成内容版本；MVP 不建立只有作废信息、没有内容版本的占位报告。

7. 首次完整提交和每次有效后续完整提交分别形成完整且不可变的报告版本；平台保留原版本和新版本关系，旧版本责任人员及其他历史内容不得被新版本覆盖。

8. 每次完整报告提交必须提供源端报告修改时间；该时间随版本保存用于来源追溯，不要求严格递增，不用于重传、版本顺序或内容变化判断。具体传输格式应保留来源系统实际时间精度，报告时间和平台接收时间均不能替代源端报告修改时间。

9. 报告公共时间包括必填的申请时间、报告时间，以及源系统存在时应提供的审核时间；平台接收时间不作为来源报告业务时间。

10. 报告时间是计算可互认时间的起点。

11. 报告随附来源患者和就诊信息，平台不要求医院预先上传独立挂号或就诊记录。

12. 来源就诊由医院、院区、就诊类型和院内就诊流水号共同识别；就诊类型和稳定且不循环复用的院内就诊流水号必填。

13. 就诊类型使用门诊、急诊、住院、体检和其他五类固定值，不接受未知；“其他”只用于确实无法归入前四类的特殊就诊类型，不得作为来源字段缺失时的默认值。住院号、病区、病房和床位在住院来源系统存在时应提供，但不参与患者或就诊自动匹配。

14. 患者姓名、性别代码、出生日期、证件类型和证件号码必填。平台按证件类型和证件号码识别平台患者，并以姓名、性别代码和出生日期核对身份；相同证件下任一核对信息冲突时不得覆盖既有患者信息或创建第二个患者。同一报告首次提交时关联解析出的平台患者，后续完整版本必须仍关联该报告原有患者；解析到其他患者或发生身份冲突时拒绝追加版本，不允许报告跨患者迁移。

15. 患者联系电话和报告时年龄在源系统存在时应提供，只用于授权展示和人工核对，不参与患者匹配；联系电话默认脱敏展示。

16. 报告上传直接接收申请科室、申请医生、执行科室、报告科室、报告医生、审核医生及报告类型要求的检验人或检查医生的具体 ID 和名称；申请科室 ID、申请科室名称、申请医生 ID 和申请医生名称均为必填，任一缺失时整份报告提交失败；业务 ID 使用 String。

17. 必填科室或人员字段必须同时提供 ID 和名称；可选字段的 ID 和名称必须同时有值或同时为空。

18. 平台不根据业务科室或人员 ID 查询名称，不要求其存在于平台权限体系，也不因权限系统查不到对应主体而拒绝报告。

19. 科室或医生名称只随当前报告版本保存；后续报告版本可以提供新的具体 ID 和名称，已有版本不被动态改写。

20. 无论首次提交或后续完整版本，平台均保存完整报告内容；只有当前版本中提供且属于当前组织内当前启用、标准目录层级有效互认项目的明细能够形成匹配。未提供编码，或明确提供但不存在、超出组织范围、停用或标准目录不可用的编码不阻止报告接收，但对应明细不形成匹配。

21. 互认项目编码在报告接收时校验并随报告明细保存；后续互认项目配置变化不重写已有报告关系。来源项目名称和可选来源项目编码仅作为报告原文追溯信息。

22. 来源保密标识只按来源值保存，不驱动敏感等级、患者授权、上传审批或匹配过滤。需要专项授权才能共享的报告暂不上传。

23. 平台不采集来源医嘱优先级、院内报告过程状态、传输批次号、上传状态、校验标志或调用方事件标识。

24. 平台按照版本成功形成顺序生成内部版本序号，不要求医院提供版本号，也不解析或统一医院源系统自己的版本规则。

25. 平台不比较完整报告内容，不计算或要求医院提供 PDF 文件摘要；完整上传不做重传判定或幂等合并，版本形成只按报告业务标识、生命周期状态和本次成功保存顺序处理。

26. 平台以文件流接收 PDF，优先保存上传请求携带的 PDF 文件名并随版本用于下载；文件名缺失或无效时使用安全处理后的“报告单号.pdf”。文件名不从 PDF 内容或元数据推断，不参与报告身份、版本或幂等判断，平台内部使用独立文件标识保存 PDF。

27. 报告更正或作废立即限制旧版本继续参与匹配查询、互认处理结果保存、引用详情和新的引用；已经成功保存的互认处理结果及医院已经发生的引用事实不回滚，后者仍可按引用结果规则迟延提交。

28. 平台不因报告更正或作废建设下游主动推送、推送记录或恢复处理。

29. 管理端报告详情提供只读历史版本列表、完整版本详情和各版本 PDF 下载，不建设独立版本管理菜单，不展示不存在于来源报告中的更正原因或版本变更原因，也不提供自动差异比较、修改、删除、恢复、重新设为当前版本或重新启用。

30. 医院管理员默认可以查看本医院及有权院区上传报告的全部历史版本、完整内容和 PDF，不新增独立报告查看权限；平台管理员按现有数据权限查看授权范围，其他医院不得查看来源医院的历史版本。

31. 医院 HIS 在线业务接口只提供当前有效版本，不开放历史版本查询或下载。

#### F03.2 检验报告专项要求



##### 参与者



医院 LIS 或其他检验报告来源系统、医院侧采集服务、互认平台及报告涉及的业务科室和人员。



##### 需求背景



检验报告以一份报告单和一个标本为单位，可以包含普通检验结果、细菌鉴定结果和药敏结果。平台需要完整保留最终报告内容，同时只将提供有效互认项目编码的普通检验结果用于互认匹配。



##### 前置条件



1. 满足 F03.1 的公共前置条件。

2. 报告提供院内标本号、标本类型编码、标本类型名称和检测完成时间。

3. 报告至少包含一条普通检验结果；是否提供当前有效互认项目编码不影响报告接收。

4. 每条普通结果提供来源项目名称、完整来源结果文本、受控结果类型和唯一展示序号；来源项目编码可选，仅用于追溯。



##### 后置条件



平台保存一份与单一标本关联的完整检验报告、全部普通结果、可选细菌鉴定结果和药敏结果；只有提供且当前有效的互认项目编码的普通结果可以形成匹配，未提供或提供不可用编码的普通结果及补充结果只用于保持报告完整、展示和追溯。



##### 主事件流



1. 平台校验检验报告公共信息、标本信息和检验时间线。

2. 平台逐条识别普通检验结果中明确提供的互认项目编码；只有属于当前组织内当前启用且标准目录层级有效的编码形成匹配资格，不根据来源项目编码或名称推断。未提供或不可用编码仍随报告保存，不拒绝整份报告。

3. 平台保存普通结果来源原文、结果类型、展示顺序和源系统实际提供的辅助信息。

4. 报告包含细菌鉴定结果时，平台保存最终鉴定结论及相关来源信息。

5. 报告包含药敏结果时，平台校验其与细菌鉴定结果的明确关联并保存最终药敏结论及量值。

6. 全部结构化内容与 PDF 校验通过后，平台按 F03.1 保存报告变更。



##### 备选流



1. 报告同时包含已提供和未提供互认项目编码的普通结果时，平台完整接收报告，仅有效互认项目编码结果参与匹配。

2. 普通结果、细菌结果或药敏结果的来源明细标识缺失时，如源系统确实不存在则允许为空；提供时在相应报告版本范围内不得重复。

3. 培养未发现细菌时，仍应提交一条细菌鉴定结果表达未检出及来源结论，不要求伪造菌种编码或名称。

4. 单位、参考范围、LOINC、检测方法、仪器、收费代码等应填信息在源系统确实不存在或不适用时允许为空，不得由平台推断或填充占位值。

5. 结果展示序号缺失或在规定范围内重复时，平台拒绝报告。



##### 业务规则



1. 一份检验报告只对应一个标本；多个标本分别形成不同报告。

2. 标本采集时间、送检时间和检验科接收时间在源系统存在时应提供，检测完成时间必填；不采集上机、离心和培养过程节点。

3. 来源报告名称必填；报告类别编码、名称和报告备注在源系统存在时应提供，只用于展示、筛选和追溯。

4. 报告整体异常标识在源系统存在时应提供，不替代结果明细异常标志，也不参与互认资格判断。

5. 来源医嘱流水号在源系统存在时应提供，只用于追溯，不参与报告身份、患者关联和互认判断；不保存报告级单一医嘱项目代码。

6. 普通结果完整保存来源最终结果文本，并使用受控结果类型区分数值型、定性型和文本型；平台不重复采集独立定量、定性字段。

7. 平台不采集或推断统一检验结果代码，不解析、换算或重新判定来源结果。

8. LOINC 在源 LIS 已维护时应提供，但不替代互认项目编码，也不由平台根据来源名称推断互认项目。

9. 单位、参考范围和检测方法按来源文本保存；平台不统一单位、不拆分参考上下限、不换算或重算参考范围。

10. 普通结果可以分别提供来源仪器编号和名称；平台不维护仪器目录，仪器不参与匹配资格判断。

11. 每条普通结果的展示序号必填，在同一报告版本的普通结果内不得重复；平台不依赖接口数组或数据库顺序。

12. 来源检验收费项目编码和医保收费项目编码在源系统已维护时应提供，但不用于报告采集阶段的金额计算。

13. 异常标志按来源受控值保存，危急值标志按来源判断保存；平台不重新计算，也不因异常或危急值标志排除匹配。

14. 细菌鉴定和药敏结果是检验报告补充结果，不独立进行互认项目对码。

15. 检出具体菌种时来源菌种名称必填，来源菌种编码按源系统情况提供；未检出时保存明确检测结论和来源文字。

16. 菌落计数、培养基、培养时间、培养条件和发现方式按源系统实际内容提供并保存，平台不标准化或重建培养过程。

17. 细菌检测结论必填；详细描述、仪器、试验板信息按源系统情况提供，不据此重新判定临床结果。

18. 药敏结果必须明确关联细菌鉴定结果，提供受试药物名称和来源结论文字；来源代码按源系统情况提供。

19. 纸片含药量、MIC、抑菌环直径和参考值按包含单位及比较符号的来源文本保存，平台不拆分、换算或重新判读。

20. 药敏展示序号必填，在同一报告版本、同一细菌鉴定结果下不得重复；检测方法和试验板序号按来源情况提供。药敏结果不重复保存试验板名称，也不使用试验板序号代替与细菌鉴定结果的明确关联。

21. 报告级检验人 ID 和检验人名称必填；普通结果、细菌结果和药敏结果的检测人 ID 和检测人名称在源系统存在时应提供，缺失不阻止报告接收。可选人员的 ID 和名称必须同时有值或同时为空，所有人员 ID 使用 String。平台不采集明细审核人。

#### F03.3 检查报告专项要求



##### 参与者



医院 PACS 或其他检查报告来源系统、医院侧采集服务、互认平台、影像服务及报告涉及的业务科室和人员。



##### 需求背景



检查报告以一份来源报告为完整业务对象，可以包含一个或多个检查项目明细。项目、部位属于明细，检查所见、检查结论、PDF 和影像调阅入口属于整份报告，联合报告不因项目对码被拆成多份报告。



##### 前置条件



1. 满足 F03.1 的公共前置条件。

2. 报告提供一个或多个检查项目明细；是否提供当前有效互认项目编码不影响报告接收。

3. 每个项目明细提供来源项目名称，可以提供来源项目编码；存在明确检查部位时提供结构化部位集合。

4. 报告提供检查所见、检查结论、来源临床诊断名称、实际检查时间、检查医生 ID 和检查医生名称；检查医生 ID 使用 String。



##### 后置条件



平台保存完整检查报告、全部项目明细及其部位集合、报告级临床内容、PDF、来源影像状态和按规则提供的影像调阅地址；只有提供且当前有效的互认项目编码的项目形成匹配，未提供或提供不可用编码的项目只用于报告完整展示和追溯。



##### 主事件流



1. 平台校验检查报告公共信息、实际检查时间、检查医生和报告级临床内容。

2. 平台逐个识别检查项目明细中明确提供的互认项目编码；只有属于当前组织内当前启用且标准目录层级有效的编码形成匹配资格，不根据来源项目编码或名称推断，并保持项目与其部位集合的明确归属。未提供或不可用编码仍随报告保存，不拒绝整份报告。

3. 平台保存整份报告的检查所见、检查结论、来源诊断、病情描述、检查目的、检查方法及设备信息。

4. 平台按来源影像状态校验影像调阅地址的一致性。

5. 全部结构化内容、PDF 和按规则提供的影像信息校验通过后，平台按 F03.1 保存报告变更。



##### 备选流



1. 联合检查报告同时包含已提供和未提供互认项目编码的项目时完整接收，仅有效互认项目编码项目形成匹配。

2. 项目没有明确检查部位时部位集合允许为空；存在部位时部位名称必填，来源部位编码按源系统情况提供。

3. 特殊检查确实没有检查所见时，来源系统应明确提供“无”等来源表达，平台不自动补写。

4. 来源影像状态为有影像但没有跨院可用地址时仍可接收报告，并表达为存在影像但暂不可调阅。

5. 来源影像状态为无影像时调阅地址必须为空；状态为未知时地址可以有或无。



##### 业务规则



1. 一份检查报告可以包含一个或多个项目明细，各明细分别解析互认项目。

2. 检查项目明细不采集具有业务含义的展示序号，平台采用稳定、可重复的方式展示，来源版式和临床阅读顺序以 PDF 为准。

3. 检查部位归属于具体检查项目明细，不以分隔文本笼统归属于整份报告。

4. 每个部位名称必填，来源部位编码在源系统存在时应提供；平台不统一或推断部位编码。

5. 检查所见和检查结论属于报告级必填完整原文，不拆分或重复保存到项目明细，不由平台整理、推断或改写。

6. 平台不定义通用检查结果代码、定性结果或定量结果字段，不从所见或结论中抽取、换算结构化指标。

7. 来源检查类型编码和名称在源系统存在时应提供，只用于展示、筛选和追溯，不关联标准项目分类或决定互认资格。

8. 来源检查设备编号和名称、检查方法在源系统存在时应提供，均为报告级信息，不参与项目对码或匹配资格判断。

9. 来源临床诊断名称必填，诊断编码按源系统情况提供；平台不统一诊断编码，不从检查结论反推诊断。

10. 病情描述和检查目的在源系统存在时应提供，分别保存，不合并或自动生成，也不参与互认资格判断。

11. 实际检查时间必填，不采集预约时间，也不拆分检查开始和完成时间。

12. 检查医生 ID 和检查医生名称必填，ID 使用 String；检查医生可以与报告医生或审核医生为同一人员。

13. 一份检查报告最多保存一个 HTTPS 影像调阅地址。平台不接收、代理、缓存或长期保存 DICOM 文件。

14. 来源影像状态使用有影像、无影像或未知；平台不根据调阅地址是否为空反推来源影像状态。

15. 影像地址缺失不影响结构化报告和 PDF 的互认资格，报告作废后不再返回原地址。

16. 平台不采集 PACS 影像号、检查实例 UID、序列 UID 等影像技术标识，也不自行拼接影像调阅地址。

17. 来源检查报告整体异常标识在源系统存在时应提供，只用于报告列表提示、匹配快速提示和人工核对；平台不根据检查所见、检查结论或项目内容自行推断，也不因异常标识排除互认。

18. 来源检查报告备注在源系统存在时应提供，不存在时允许为空；备注随报告版本保存，仅用于报告展示、补充临床说明和问题追溯，不参与报告接收、项目互认资格、结果异常或版本顺序判断，也不替代作废原因。

| 属性组 | 关键属性 |

| --- | --- |

| 检查项目明细 | 来源项目名称、可选来源项目编码、互认项目编码及结构化检查部位集合。 |

| 检查部位 | 所属项目、来源部位编码、部位名称。 |

| 报告内容 | 检查所见、检查结论、来源整体异常标识、来源报告备注。 |

| 临床背景 | 来源临床诊断编码和名称、病情描述、检查目的。 |

| 检查信息 | 来源检查类型编码和名称、实际检查时间、检查方法、设备编号和名称、检查医生。 |

| 影像信息 | 来源影像状态、单个 HTTPS 影像调阅地址。 |



### F04 互认匹配查询



#### 参与者



| 参与者 | 职责 |

| --- | --- |

| 医院 HIS | 在患者接诊或开单过程中提交患者身份、本次来源就诊和一个或多个拟开标准项目编码，接收符合条件的匹配结果。 |

| 互认平台 | 整批校验患者和全部拟开项目，选择每个互认项目的最近有效报告，生成互认匹配记录及互认匹配项并形成提醒统计。 |

| 医生 | 在医院 HIS 中查看匹配结构化内容、PDF 或影像入口并作出临床决定。 |



#### 需求背景



医院 HIS 在拟开检查或检验项目时，需要查询同一患者在当前组织内是否存在仍可使用的其他医院结果。一次查询可能包含多个标准项目编码，平台需要先保证全部项目编码有效，再去除重复输入并只返回实际命中的匹配。非空结果必须作为一个互认匹配记录保存，以便后续整组处理和项目级追溯；全部项目编码正确但没有符合条件的报告属于正常空结果。



#### 前置条件



1. 调用方能够从可信身份上下文确定当前接收医院和接收院区。

2. 查询提供有效的患者证件类型和证件号码，以及本次来源就诊类型和院内就诊流水号。

3. 查询至少包含一个拟开标准项目编码，每个项目明确检查或检验类型。

4. 本次全部标准项目编码均属于当前组织内当前启用且标准目录层级有效的互认项目；任一编码不存在、未纳入组织互认范围、停用或标准目录不可用时整次查询失败。



#### 后置条件



1. 全部项目配置校验通过后只返回实际命中的匹配；没有任何符合条件的报告时返回空匹配结果且不创建互认匹配记录。

2. 非空查询结果生成一个新的互认匹配记录 ID，每个实际返回项目生成新的互认匹配项 ID；每个互认项目最多返回一份报告的当前有效内容。

3. 同一联合报告命中多个项目时只返回一份报告公共信息，各项目分别形成互认匹配项，但共同属于本次互认匹配记录。

4. 平台成功生成互认匹配记录后，按集合内每个互认匹配项形成一次提醒统计；无匹配或整次查询失败不形成提醒。医院未收到响应不撤销已经形成的提醒。

5. 查询本身不形成互认处理结果、引用结果或调阅状态。



#### 主事件流



1. 医院 HIS 提交患者身份、本次来源就诊和一个或多个拟开标准项目编码。

2. 平台校验调用医院院区、患者身份、来源就诊和项目输入。

3. 平台按当前组织、项目类型和标准项目编码整批校验当前有效互认项目；任一项目无法校验为当前可用互认项目时整次失败，并指出相关标准项目编码。

4. 同一次查询重复提供相同标准项目编码时只处理一次。

5. 平台针对每个去重互认项目筛选报告：来源组织与当前接收组织一致，报告版本当前有效、报告对应互认项目当前启用且标准目录层级有效、检查或检验时间不晚于查询时点，并处于当前可互认时间内。

6. 平台按本院报告匹配开关和本院报告排除时长处理来源医院与接收医院相同的报告。

7. 平台选择检查或检验时间最晚的一份报告；时间相同时选择报告时间较晚的一份；两者均相同时稳定选择同一份报告。

8. 平台按报告分组组织公共信息，生成本次互认匹配记录 ID，并为每个实际命中项目生成互认匹配项 ID；报告分组仅用于避免重复传输，不构成组下新的业务层级。

9. 平台成功生成并保存非空互认匹配记录后，同步返回互认匹配记录 ID、互认匹配生成时间、互认匹配项 ID、报告公共信息、项目级匹配内容及适用的 PDF 和影像入口，并形成提醒；没有任何报告命中时返回互认匹配记录 ID 和互认匹配生成时间均为空、报告及项目集合均为空的成功响应，且不创建组。



#### 备选流



1. 任一标准项目编码不存在、未纳入当前组织互认范围、停用或标准目录不可用时，平台使用现有框架抛出描述事实的业务异常，整次查询失败，不生成组、不返回同批其他匹配；需求阶段不定义错误代码或异常格式。

2. 患者不存在、没有满足时间和有效性规则的报告，或者报告均被本院匹配规则排除时，不返回相应匹配；没有任何匹配时返回成功的空匹配结果。

3. 查询输入、患者身份或调用归属校验失败时，整次查询失败，不形成提醒统计。

4. 一份报告已经更正时只使用新版本；报告已经作废时不参与匹配选择。

5. 一份联合报告同时命中多个互认项目时，报告公共内容只组织一次，项目匹配和处理边界仍相互独立。

6. 平台已经成功生成互认匹配记录后，即使医院 HIS 因网络超时未取得响应，也不撤销该互认匹配记录及提醒；医院重试作为新查询重新计算并生成新的互认匹配记录 ID、互认匹配项 ID，不恢复或复用前一集合。



#### 业务规则



1. 查询截止点使用平台收到本次查询的时间，医院 HIS 不需要额外提供挂号时间、入院时间或统一就诊时间。

2. 匹配时间判断使用检查报告的实际检查时间或检验报告的检测完成时间；该时间不得晚于查询时点。

3. MVP 只匹配来源组织与接收组织一致的报告。可互认时间从报告时间开始计算，并使用该组织互认项目查询时的当前正整数天配置；一天按连续二十四小时计算，经过时间小于或等于当前配置时满足时间条件，超过后不再满足。

4. 每个互认项目只返回最近一份有效报告，不返回其他较早独立报告或历史趋势。

5. 检查或检验时间相同时，报告时间是唯一业务选择条件。两者均相同时，不增加临床质量、机构级别或其他业务排序条件；在匹配数据及相关配置未变化时必须稳定返回同一份报告，具体稳定排序方式在设计阶段确定。

6. 联合报告按完整报告返回，但只有本次查询命中的互认项目形成互认匹配项，未命中项目不得形成集合内记录。

7. 同一次查询重复提供相同标准项目编码时，只形成一个匹配和一次提醒，不重复返回或统计。

8. 本院报告匹配开关为平台全局参数，默认关闭。关闭时来源医院与接收医院相同的报告不参与匹配，不区分院区。

9. 开关开启后，本院报告排除时长使用另一个全局非负整数小时参数，默认四十八小时；配置为零表示不增加额外等待时间，小数或负数无效。两个参数缺失时分别使用默认关闭和默认四十八小时；参数值非法或参数服务无法取得参数时，整次匹配查询失败，不使用其他兜底值。

10. 本院报告经过时间大于或等于排除时长，且小于或等于互认项目可互认时间时满足时间条件；两个边界均包含。

11. 排除时长可以等于或大于某些项目的可互认时间，不作为配置错误；大于时该项目不会返回本院报告。

12. 本院报告参数只影响后续匹配查询，不删除报告或撤销既有处理、引用和统计事实。

13. 检验匹配返回来源机构、报告名称、检查或检验时间、报告时间、报告识别信息、标本类型名称、本次命中互认项目对应的主要检验结果明细，以及平台 PDF 文件标识、下载入口和原始文件名；每条结果包含项目名称、来源结果原文、单位、参考范围、异常标志和危急值标志，不要求按来源报告中的业务序号返回。

14. 检验匹配不返回用于来源追溯的标本类型编码和院内标本号。

15. 检查匹配返回来源机构、报告名称、实际检查时间、报告时间、报告识别信息、命中项目的检查部位、整体异常标识、平台 PDF 文件标识、下载入口和原始文件名、来源影像状态及医院提供的影像入口。

16. 检查匹配不直接返回篇幅较大的检查所见和检查结论；医生通过 PDF 或影像查看后决定是否采纳。

17. 匹配中的异常和危急值仅表达来源医院判断，平台不重新计算，也不自动排除异常报告。

18. 提醒次数只表示平台成功提供匹配，不表示医院 HIS 已显示弹窗或医生已经查看、采纳、拒绝或引用。

19. 匹配响应不返回固定“互认超期时间”；平台按查询时点和互认项目当前可互认时间动态筛选。

20. 每次非空查询均生成新的互认匹配记录 ID 和互认匹配项 ID，不提供跨查询稳定匹配引用、查询幂等键或旧集合恢复能力；未反馈互认匹配记录不设有效期、过期状态或定时清理。

21. PDF 下载沿用医院 HIS 与平台既有接入机制，并返回对应报告版本保存的 PDF；不在匹配响应中返回 PDF 文件内容。

22. 匹配 PDF 入口不设独立有效期或一次性状态。每次下载校验调用医院、院区、匹配归属和报告版本有效性；报告形成后续版本或作废后停止提供旧版 PDF，医院已合法下载的数据不追回。

| 属性组 | 关键属性 |

| --- | --- |

| 调用归属 | 当前接收医院、接收院区，来自可信身份上下文。 |

| 患者与就诊 | 证件类型、证件号码、本次来源就诊类型、本次院内就诊流水号。 |

| 拟开项目 | 检查或检验类型、标准项目编码；校验并去重为互认项目。 |

| 互认匹配记录 | 平台生成的互认匹配记录 ID、互认匹配生成时间、接收医院院区、患者、本次来源就诊和全部实际返回项目。 |

| 匹配公共信息 | 来源医院及院区、来源报告名称、检查或检验时间、报告时间、报告识别信息、PDF 文件标识、下载入口和原始文件名。 |

| 互认匹配项 | 平台生成的互认匹配项 ID，绑定本次拟开标准项目、互认项目、匹配报告版本和项目内容。 |

匹配查询响应按报告公共信息和互认匹配项分别组织。同一联合报告命中多个互认项目时，报告公共信息只返回一次，互认匹配项通过报告 ID 和报告版本 ID 关联该公共信息；该响应分组仅用于避免重复传输，不增加互认匹配记录之下的持久化业务层级。



### F05 互认处理结果



#### 参与者



| 参与者 | 职责 |

| --- | --- |

| 医生 | 查看匹配后一次确认集合内每个互认匹配项的采纳或不采纳处理结果，并在首次提交前核对决定内容。 |

| 医院 HIS | 按互认匹配记录完整提交全部互认匹配项的互认结果、组级实际互认时间、互认科室和互认医生。 |

| 互认平台 | 整批校验并原子保存不可更改的项目级决定、不采纳原因和预计节省金额，维护对应统计事实。 |



#### 需求背景



平台只能记录医生明确作出的互认处理结果，不能从查询、调阅或医院后续行为推断采纳情况。一次互认匹配记录表达医生本轮需要共同确认的完整匹配记录，医院必须一次完整、原子提交全部项目的互认结果；首次成功保存后即成为不可更改的历史事实。



#### 前置条件



1. 医院 HIS 已取得匹配查询返回的互认匹配记录 ID 和全部互认匹配项 ID。

2. 医生已经明确作出采纳或不采纳处理结果。

3. 请求在组级请求互认匹配记录 ID、精确到秒的互认时间、互认科室 ID、互认科室名称、互认医生 ID 和互认医生名称；互认科室和互认医生的 ID 使用 String。项目数组完整提供该组全部互认匹配项 ID 及采纳或不采纳结果。

4. 不采纳时提供平台统一原因代码；原因为其他时提供补充说明。



#### 后置条件



1. 一次请求中的全部处理结果校验成功后共同保存；任一记录失败时整批不保存。

2. 互认匹配记录首次成功保存后，每个互认匹配项只保留该次不可更改的决定，不存在当前决定覆盖或决定版本。

3. 决定为采纳时形成采纳次数、来源医院被互认次数和预计节省金额；采纳处理结果通过其互认匹配项能够确定对应报告版本的使用关系，不单独保存报告使用关系。该组首次成功保存处理结果的时间作为引用详情有效期起点。不采纳时形成不采纳次数和原因。

4. 完整请求相同的幂等重试不重复计数；相同组提交任何不同业务内容时返回处理结果冲突，不覆盖原决定。



#### 主事件流



1. 医院 HIS 提交互认匹配记录 ID、集合级互认时间、互认科室和互认医生，以及完整覆盖该组全部互认匹配项的互认结果数组。

2. 平台先校验调用组织、医院、院区和互认匹配记录归属、项目数组是否完整且无重复或非法项目，再校验互认时间、互认结果内容及互认科室和互认医生的 ID/名称成对提供规则。平台不确认互认科室或互认医生是否存在于权限系统。

3. 平台确认每个互认匹配项属于该组并能够定位相应报告版本和互认项目；未命中既有完全相同的已保存处理结果时，绑定报告版本已经形成后续版本或作废的，整次请求失败且不保存任何处理结果。

4. 处理结果为不采纳时，平台校验统一原因代码及补充说明。

5. 处理结果为采纳时，平台读取接收组织、接收医院、接收院区和匹配互认项目对应的当前有效金额。

6. 平台按采纳处理结果成功保存时读取的当前金额形成预计节省金额。

7. 全部记录校验通过后，平台在一个整体操作中保存全部不可更改决定及对应统计事实。

8. 平台返回整次请求成功。



#### 备选流



1. 任一记录校验失败时整批不保存，使用现有框架抛出描述事实的业务异常，不返回逐条成功结果；涉及具体项目时指出相关互认匹配项 ID，需求阶段不定义错误代码、异常 DTO 或传输格式。

2. 全部处理结果保存成功时同步返回布尔值 true；相同业务键重复提交完全相同的处理内容时，平台优先识别既有已保存事实并同样返回 true，不新增记录或重复统计，且不因绑定报告版本后续失效改为失败。业务失败直接抛出业务异常，不以 false 表示失败。

3. 互认匹配记录已保存处理结果后再次提交不同互认时间、科室、医生、任一项目决定、不采纳原因或补充说明时，返回互认处理结果冲突，不更正、撤销、删除或覆盖首次决定。

4. 项目数组缺少集合内互认匹配项、重复请求互认匹配项、夹带其他互认匹配记录的互认匹配项或数量不一致时，整次失败且不保存任何项目。

5. 不采纳未提供原因、原因无效，或者原因为其他但缺少说明时，整批失败。

6. 互认科室或互认医生 ID、名称缺失，或只提供其中一项时，整批失败；平台不校验其是否存在、停用或属于当前调用医院、院区。

7. 接口超时、失败或未取得明确结果时，医院 HIS 使用相同互认时间和原记录重新提交。

8. 匹配返回后，只要匹配报告版本仍有效，平台允许采纳；金额发生变化时使用保存采纳处理结果时的当前金额，未配置金额按零元计算且不阻碍互认处理。



#### 业务规则



1. 处理结果值域只包括采纳和不采纳，不要求提交未处理、未查看、暂未决定或关闭提醒状态；长期未反馈的互认匹配记录不设有效期、过期状态或自动清理。

2. 匹配返回、结构化展示、PDF 或影像访问不自动形成处理结果。

3. 处理决定归属于互认匹配记录中的具体互认匹配项，不笼统归属于整份联合报告；集合内互认匹配项可以分别采纳或不采纳。

4. 一次请求必须完整覆盖互认匹配记录全部项目，并整体校验、整体保存，不允许部分提交或逐项部分成功。

5. 互认时间是医生实际作出决定的时间，保存到秒；接口接收时间不得替代互认时间。

6. 确有新的诊疗决定时，医院重新查询生成新的互认匹配记录并提交新的整组决定，不复用原组形成第二次处理。

7. 互认科室和互认医生表示实际作出决定的主体，接口调用账号不得替代；采纳和不采纳均必须提供互认科室 ID/名称和互认医生 ID/名称。

8. 互认科室和互认医生的 ID、名称按请求直接保存；平台不校验医生当前所属科室与互认科室一致。

9. 互认科室名称和互认医生名称不参与业务唯一键或幂等一致性判断；相同业务键的重试仍按既有互认处理结果事实规则处理。

10. 未命中完全相同的既有已保存处理结果时，平台保存新的互认处理结果前必须校验匹配项绑定报告版本仍为当前有效版本；报告已经形成后续版本或作废时，整次处理结果请求失败且不保存任何项目。

11. 统一不采纳原因字典由平台内置并使用本功能规定的固定代码，不提供医院新增、修改或停用；代码 `6` 表示其他情形确需复查，使用时补充说明必填。

12. 处理结果为采纳时不得填写不采纳原因；平台不审查不采纳的临床理由，也不据此干涉医院继续开单或采取其他诊疗措施。

13. 采纳时按决定成功保存时接收组织、医院、院区的当前金额形成预计节省金额，不使用来源医院金额，也不等待引用结果。

14. 未配置金额时按零元形成预计节省金额，不得因此阻碍采纳处理结果保存；负数或超过两位小数的无效金额应在金额配置保存时直接拒绝，不进入互认处理。互认项目停用或标准目录不可用时不得形成新的匹配；已经返回的匹配项只要绑定报告版本仍为当前有效版本，仍允许保存真实发生的采纳或不采纳处理结果。

15. 平台只保存预计节省金额，不在处理记录中重复保存一份当前金额。

16. 相同采纳的幂等重试不因当前金额已经变化而重新取价或计算金额。

17. 首次决定保存后不得在采纳和不采纳之间更改，已经形成的预计节省金额不通过决定更正取消或重算。

18. 报告后续更正或作废不撤销或重算已经形成的预计节省金额。

19. 预计节省金额归属于接收组织、医院、院区和互认科室，不在来源组织或来源医院侧重复形成贡献金额。

20. 互认时间必须晚于或等于互认匹配记录生成时间且不得晚于平台收到本次请求的时间，均精确到秒并允许相等；MVP 不设置未来时间容差。

21. 平台首次成功保存互认匹配记录处理结果时记录该组引用详情有效期起算时间；相同完整请求的幂等重试不更新该时间。

### F06 获取引用详情



#### 参与者



| 参与者 | 职责 |

| --- | --- |

| 医院 HIS | 在医生采纳匹配后请求写入本次病历所需的项目内容。 |

| 互认平台 | 校验调用归属、来源就诊、互认处理结果和匹配版本有效性，返回项目级引用内容。 |



#### 需求背景



匹配查询只用于医生判断，病历引用需要在采纳后通过独立能力取得受控内容。平台必须保证返回内容属于当前医院、本次就诊、已采纳项目和仍有效的报告版本。



#### 前置条件



1. 当前调用医院、院区能够从可信身份上下文确定。

2. 请求提供患者证件类型、证件号码、本次来源就诊类型和本次院内就诊流水号；医院和院区来自可信身份，不提交平台患者 ID、互认匹配记录 ID、互认匹配项 ID 或互认时间。

3. 本次就诊下至少存在一个已保存采纳处理结果的互认匹配项。

4. 平台在查询过程中逐项校验互认匹配项绑定的报告版本仍为当前有效版本。

5. 平台能够从现有系统参数系统读取合法的全平台统一引用详情有效时长。



#### 后置条件



1. 校验成功时返回该医院、院区、患者及本次就诊下仍可获取的全部已采纳互认匹配项内容及必要报告公共上下文，并携带互认匹配项 ID。

2. 获取引用详情不自动形成引用结果、引用次数或新的互认处理。

3. 校验失败时不返回受保护的报告引用内容。

4. 超出当前引用详情有效时长时不返回引用内容；有效期内允许在既有校验均通过时重复获取。



#### 主事件流



1. 医院 HIS 提交患者证件类型、证件号码、本次来源就诊类型和本次院内就诊流水号。

2. 平台使用当前医院、院区和请求信息严格匹配互认匹配记录，并校验患者身份、本次就诊和组归属一致。

3. 平台从现有系统参数系统读取当前全平台统一的引用详情有效时长，并校验参数存在且为合法的正整数分钟。

4. 平台以各互认匹配记录处理结果首次成功保存时间为起点分别计算经过时间，校验经过时间小于或等于当前有效时长。

5. 平台逐项校验决定为采纳、互认匹配项归属正确且绑定报告版本仍为当前有效版本；自然超过可互认时间不影响已经采纳项目获取详情。

6. 同一次就诊存在多个组且多个有效采纳绑定同一报告版本和互认项目时，只返回平台成功保存时间最近的一条采纳记录，较早事实和统计仍保留。

7. 平台返回全部仍有效项目的互认匹配项 ID、项目内容、必要报告公共上下文、PDF 文件信息和适用的来源影像信息，供医院 HIS 写入本次病历。



#### 备选流



1. 未匹配到该医院、院区、患者及本次就诊下的采纳记录时拒绝返回，并只描述“未查询到该就诊的互认采纳记录”等平台能够确认的事实，不泄露其他患者记录。

2. 报告已经形成后续版本、作废，或者互认匹配项绑定的版本不再是当前有效版本时不返回该项目；全部相关项目均失效时拒绝返回。

3. 联合报告只采纳其中部分项目时，仅返回已采纳互认匹配项对应内容，不返回其他不采纳、未命中或属于其他互认匹配项的内容。

4. 引用详情有效时长参数不存在、为零、负数、非整数或系统参数服务读取失败时，平台拒绝返回并给出明确配置错误，不使用代码兜底值。

5. 各组独立判断有效期；只要存在有效项目即正常返回这些项目，不因同次就诊其他项目超期或失效整次失败。全部项目均不可返回时拒绝并列明平台实际确认的原因，不返回成功空集合或“可引用/不可引用”双数组。



#### 业务规则



1. 获取引用详情与匹配查询、处理结果提交、引用结果提交相互独立。

2. 引用详情必须使用“当前医院 + 当前院区 + 患者证件类型 + 证件号码 + 就诊类型 + 就诊流水号”严格匹配互认匹配记录和不可更改的采纳处理结果。

3. 检验引用详情按当前互认项目返回相应检验结果，不细分为每条结果独立引用事实。

4. 检查所见和检查结论属于整份报告公共内容，可以随当前检查项目返回。

5. 必要报告公共上下文至少包括来源医疗机构、来源报告名称、检查或检验时间、报告时间、来源申请医生和来源审核医生。

6. 获取详情只表示平台提供了引用所需数据，不表示医院 HIS 已写入病历。

7. 引用详情再次返回平台 PDF 文件标识、下载入口和原始文件名；PDF 下载接口直接返回 `application/pdf` 文件流，不把文件转为 Base64。PDF 或影像访问不能替代获取引用详情，也不能形成引用结果。

8. 引用详情有效时长是全平台统一系统参数，所有医院、院区和互认项目使用同一值，不建立组织级覆盖、专用参数表或专用配置页面。

9. 参数值使用正整数分钟，默认七百二十分钟，即十二小时；不允许零、负数、非整数或永久有效。管理界面可以辅助显示小时，但参数值及校验统一使用分钟。

10. 每个互认匹配记录的有效期从平台首次成功保存该组完整处理结果的时间开始，不使用医院 HIS 提交的互认时间；该平台保存时间只用于引用授权，不改变采纳和统计的业务时间。

11. 相同完整请求的幂等重试不刷新有效期；同一次就诊存在多个互认匹配记录时，各组独立计算。

12. 每次请求读取当前参数值，不为采纳记录保存独立有效时长或截止时间；参数缩短或延长后立即按原起点影响既有采纳。

13. 有效期结束边界包含在允许范围内：经过时间小于或等于当前有效时长时允许，大于时拒绝。

14. 有效期内只要既有医院院区、患者、本次来源就诊、采纳处理结果和报告版本校验均通过，允许重复获取；已经提交引用结果也不提前关闭有效期。

15. 平台不建设一次性读取、读取后立即失效或消费状态；有效期只限制后续平台接口调用，不能控制医院已经合法取得并保存的数据。

16. 参数不存在、非法或参数服务失败时拒绝返回，不退化为永久有效，也不在互认平台代码中设置默认兜底。

17. PDF 下载入口本身不设置独立期限；医院在引用详情有效期内取得入口后，即使详情后来超期，只要调用医院院区、匹配归属正确且报告版本仍有效，仍允许下载。报告形成后续版本或作废后停止提供旧版 PDF。

18. PDF 下载沿用医院 HIS 与平台既有业务接入方式；具体方式不影响本功能的业务规则。

19. MVP 不为 PDF 下载建立独立业务记录、下载次数、下载状态或管理菜单，安全审计沿用现有框架接口访问日志，日志格式不在需求阶段固定。

20. 检查引用详情只原样返回医院提供的影像状态和外部调阅地址。平台不测试、代理、缓存或保证地址可用，不接收 DICOM；报告形成后续版本或作废后停止在后续响应中返回原地址，但无法撤回已经下发的外部地址。

### F07 提交引用结果



#### 参与者



| 参与者 | 职责 |

| --- | --- |

| 医院 HIS | 在已采纳内容成功写入本次病历后，提交一条或多条实际引用事实。 |

| 互认平台 | 对本次全部实际引用项目执行整批校验、原子保存，不返回逐条部分结果。 |



#### 需求背景



互认采纳和病历引用是连续但独立的业务事实。平台只有在医院 HIS 明确确认已成功写入病历后才能记录引用，不得从引用详情获取、文件访问或未反馈状态推断引用。



#### 前置条件



1. 医院 HIS 已将相应互认内容成功写入本次病历。

2. 请求只提交一个或多个实际引用项目；每项请求互认匹配项 ID、实际引用时间、引用科室 ID、引用科室名称、引用医生 ID 和引用医生名称，科室和医生 ID 使用 String，不重复提交互认匹配记录 ID、本次来源就诊或互认时间。

3. 每个互认匹配项所属互认匹配记录均存在完整互认处理结果，且该项目决定为采纳。

4. 每个引用项目的引用科室 ID/名称和引用医生 ID/名称均完整成对提供。



#### 后置条件



1. 一次请求中的全部引用项目校验成功后共同保存；任一项目失败时整次不保存，不返回逐条成功或失败结果。

2. 每个业务唯一键只形成一个引用事实，幂等重试不增加引用次数；报告使用关系继续由已保存的采纳处理结果及其互认匹配项反查，不单独形成记录。

3. 成功引用按实际引用时间计入引用统计，不再次增加采纳次数、来源医院被互认次数或预计节省金额。



#### 主事件流



1. 医院 HIS 提交一条或多条已经发生的引用结果。

2. 平台以每项互认匹配项 ID 反查所属互认匹配记录及其处理结果，校验当前调用医院和院区归属一致，并取得本次来源就诊和互认时间。

3. 平台校验每项互认匹配项决定为采纳，并校验每项引用科室和引用医生的 ID/名称成对提供规则；平台不确认其是否存在于权限系统。

4. 平台校验每项实际引用时间晚于或等于其所属互认匹配记录的互认时间且不晚于本次请求接收时间，再按互认匹配项 ID 检查是否已有引用结果及事实内容。

5. 全部项目校验通过后原子保存新引用事实；完全相同的既有事实按幂等处理。

6. 平台返回整次请求成功。



#### 备选流



1. 任一记录的引用科室或引用医生 ID、名称缺失或只提供其中一项，或者互认匹配项不存在、处理结果不存在或为不采纳时，整次请求失败，整批不保存。

2. 任一实际引用时间早于互认时间或晚于平台收到本次请求的时间时，整次失败；MVP 不设置未来时间容差。

3. 全部引用结果保存成功时同步返回布尔值 true；相同业务键且实际引用时间、科室和医生一致时同样返回 true，不新增记录或重复统计。业务失败直接抛出业务异常，不以 false 表示失败。

4. 相同业务键但任一事实字段不同，返回内容冲突，不覆盖已有引用结果。

5. 医院修正后重新提交完整原请求；接口超时、失败或未取得明确结果时也使用完整原请求重试，已存在的相同事实按幂等处理。

6. 报告在实际引用之后发生更正或作废、且医院稍后提交引用结果时，平台不因提交时报告已失效而拒绝该项已经发生的引用事实。



#### 业务规则



1. 平台只接收已经引用的正向事实，不要求医院提交未引用或引用失败状态。

2. 获取引用详情、查看结构化结果、访问 PDF 或影像均不自动形成引用结果。

3. 引用粒度为匹配报告版本中的具体互认项目，不继续细分到每条普通检验展示明细。

4. 同一互认匹配项最多形成一个引用事实，不要求医院生成额外幂等流水号；匹配项 ID 是全局唯一主键，一次请求可以包含来自不同互认匹配记录的项目。

5. 实际引用时间是医院成功写入病历的业务时间；接口接收时间不得替代。

6. 引用科室和引用医生是实际执行引用的主体，调用账号不得替代。

7. 平台直接保存引用科室 ID、引用科室名称、引用医生 ID 和引用医生名称，不校验医生当前所属科室与引用科室一致。

8. 平台不校验引用科室或引用医生是否存在、停用或属于平台权限系统；调用医院和院区仍从可信调用上下文确定。

9. 引用科室名称和引用医生名称必须与 ID 成对提交并保存，但不参与业务唯一键或幂等一致性判断；相同匹配项、实际引用时间、引用科室 ID 和引用医生 ID 的重试按幂等处理。

10. 报告更正或作废后，平台停止提供原版本引用详情和 PDF 下载入口；本规则所称阻止新的引用仅指不再由平台提供原版本后续引用所需内容。平台接收引用结果时不比较实际引用时间与更正或作废时间，不因提交时报告已失效拒绝医院明确反馈的既有引用事实。

11. 引用结果不设置独立提交期限，不受匹配可互认时间或引用详情有效期限制，也不要求平台证明医院曾调用引用详情接口。

12. 引用结果首次保存后不可更正、撤销、删除、冲销或后台补改；引用只增加引用次数，不再次增加互认采纳、来源医院被互认次数或预计节省金额。

13. 请求不要求完整覆盖该组全部已采纳项目，未提交项目只表示平台本次未收到引用事实，不推断为未引用；但本次提交数组作为整体原子处理。

14. 同一次诊疗决定将同一互认匹配项写入多份院内文书仍只形成一个引用事实；新的诊疗决定必须重新查询、形成新组并重新提交互认处理。

### F08 互认统计与分析



#### 参与者



| 参与者 | 职责 |

| --- | --- |

| 医院管理员 | 在本院及有权院区范围内查看接收侧互认使用汇总、来源侧被互认汇总及相应脱敏明细。 |

| 平台管理员 | 查看权限范围内的组织汇总、医院明细和业务下钻。 |

| 互认平台 | 按互认匹配记录、不可更改决定、引用事实、业务时间和权限范围计算统计。 |



#### 需求背景



平台需要同时反映匹配提供、医生决定、病历引用、预计节省金额和来源医院报告贡献，并保证每项指标能够回到相应业务明细核对。统计用于业务管理和监管，不用于自动评价医生绩效或替代真实财务结算。



#### 前置条件



1. 统计页面及接口操作授权由权限系统负责；本功能只基于既有业务归属范围返回统计数据，不重复判断操作权限。

2. 查询提供日期范围，并可按来源或接收的医院、院区、互认科室、互认医生、项目类型、分类、分组、互认项目及不采纳原因代码等条件筛选；来源与接收组织必须为同一组织。

3. 平台已保存匹配返回、首次成功保存且不可更改的互认处理结果、引用结果和采纳时按接收组织、医院、院区当前金额形成的预计节省金额事实。



#### 后置条件



1. 平台返回当前权限和查询条件范围内的汇总、分类统计及可下钻明细。

2. 统计按各指标已确认的业务时间归入期间，包含医院稍后提交的真实处理或引用事实。

3. 患者姓名和证件号码在统计页面及明细中保持脱敏。

4. 统计仅覆盖当前组织内的业务事实，不提供跨组织统计口径。



#### 主事件流



1. 用户进入接收医院互认使用分析或来源医院被互认分析页面。

2. 平台依据既有业务归属确定可访问的组织、医院和院区数据范围。

3. 用户选择日期范围及其他允许的查询条件。

4. 平台按指标对应业务时间汇总提醒、采纳、不采纳、引用、预计节省金额或来源医院被互认次数。

5. 平台计算同期互认率、不采纳原因次数及占比，并按标准项目分类组织统计。

6. 平台按当前查询条件返回当前组织内的汇总和明细。

7. 用户从汇总数字下钻查看对应脱敏业务明细。



#### 备选流



1. 提醒次数为零时，同期互认率不计算，不以零或百分之百代替。

2. 不采纳总次数为零时，各原因占比不计算。

3. 医院 HIS 稍后提交处理或引用结果时，重新查询原业务时间所属期间应包含新增事实。

4. 互认匹配记录未反馈时只保留提醒事实，不推断医生忽略、拒绝或采纳。

5. 查询时间与互认时间跨越统计边界导致短周期同期互认率超过百分之百时，按原始结果展示，不截断或强制封顶。

6. 查询条件超出当前业务归属范围时，平台拒绝查询或限制在该业务归属范围内。



#### 业务规则



1. 提醒次数在平台成功生成非空互认匹配记录时形成，按互认匹配生成时间归入统计期间；医院是否实际收到响应不改变已形成事实。

2. 同一次查询重复提供相同标准项目编码时只计一次提醒；联合报告命中多个不同互认项目时分别计数。

3. 无匹配或平台整次查询失败时不计提醒；平台已生成互认匹配记录但响应传输超时仍计提醒，医院重试生成的新组再次计数，不在统计阶段猜测并合并网络重试。

4. 采纳次数、不采纳次数、来源医院被互认次数和预计节省金额按互认时间归入统计期间。

5. 引用次数按实际引用时间归入统计期间。

6. 接口接收时间只用于传输、安全和审计，不改变统计归属日期。

7. 每个互认匹配项的采纳分别计算采纳次数、来源医院被互认次数和预计节省金额；相同完整请求的幂等重试不重复计数。

8. 引用结果只增加引用次数，不再次增加采纳、来源医院被互认次数或预计节省金额；没有引用结果不撤销已经成立的采纳。

9. 同期互认率为统计范围内采纳次数除以提醒次数并乘以百分之百。未收到处理结果的提醒保留在分母中，但不记为不采纳。

10. 平台不建立提醒与采纳的一一对应流水，不另设“采纳次数除以采纳与不采纳之和”的比例指标。

11. 不采纳原因统计按平台统一原因代码汇总次数及占比，占比分母为当前业务归属和查询条件下的不采纳总次数；原因汇总项可以按同一原因代码下钻和导出对应不采纳明细。

12. 其他原因统一归入其他分类，补充说明只在脱敏明细及导出中展示，不按任意文字生成新分类。

13. 接收医院使用分析包含提醒、采纳、不采纳、引用、同期互认率和预计节省金额。

14. 医院管理员在接收侧互认使用分析中只能查看本院及有权院区的数据；平台管理员按权限查看组织汇总及医院明细。

15. 来源医院被互认分析在接收侧明确采纳时形成，不等待引用结果；来源医院只统计次数和明细，不统计贡献金额。

16. 医院管理员在来源侧被互认分析中只能查看本院提供报告形成的数据；其他医院管理员不得查看与本院无关的来源医院数据。

17. 本院报告匹配开关开启后，本院报告形成的提醒、处理、引用和预计节省金额进入总体统计，本院报告被采纳也进入来源医院被互认总体次数。

18. MVP 不匹配、处理或统计不同组织之间的报告；来源组织与接收组织必须一致。

19. 同一组织内不同医院或同一医院不同院区之间的使用，可以按来源医院、来源院区、接收医院和接收院区筛选或分组，但不形成独立跨院区核心指标。

20. 互认使用和来源医院被互认统计统一按互认平台统一维护的项目类型、分类、分组及具体互认项目筛选和汇总，不使用各医院来源报告分类进行横向比较。

21. 接收医院汇总由查询明确选择医院、院区、互认科室或互认项目中的一个汇总维度；来源医院被互认汇总由查询明确选择来源医院、来源院区或互认项目中的一个汇总维度。互认科室按“院区 + 互认科室 ID”归类，互认医生只作为明细查询条件和展示内容，不形成互认率、金额或绩效排名。

22. 同一院区内相同互认科室 ID 不因不同业务记录中的互认科室名称不同而拆分统计对象；汇总展示名称使用当前查询范围内互认时间最晚一条处理结果记录保存的互认科室名称，下钻明细展示各业务记录自身保存的互认科室名称。

23. 提醒、采纳、不采纳、引用和来源医院被互认汇总均应支持下钻到对应业务明细。

24. 预计节省金额随采纳明细展示，不另建重复的金额事实或金额明细。

25. 统计管理页面中的患者姓名和证件号码必须脱敏，不提供解除脱敏或查看完整患者身份的能力。

26. 统计通过用户选择的日期范围展示汇总、分类和下钻明细，不生成按日、小时或分钟的趋势图。

27. 现有提醒、采纳、不采纳和引用明细提供只读“查看互认匹配记录”入口，不新增独立菜单；集合视图展示互认匹配记录 ID、互认匹配生成时间、接收医院院区、脱敏患者、本次就诊、未反馈或已处理状态、决定主体及全部互认匹配项。

28. 接收医院管理员通过统计和互认匹配记录视图不得查看其他来源医院的完整结构化报告、PDF 或影像地址；来源医院管理员仍通过本院报告历史查看本院完整报告。



#### 关键属性



| 指标或维度 | 说明 |

| --- | --- |

| 提醒次数 | 成功返回去重互认项目匹配的次数。 |

| 采纳次数 | 互认匹配项不可更改决定为采纳的次数。 |

| 来源医院被互认次数 | 来源报告被接收侧明确采纳的次数，不包含贡献金额。 |

### F09 互认统计导出



#### 参与者



| 参与者 | 职责 |

| --- | --- |

| 医院管理员 | 按权限导出本院及有权院区的接收侧互认使用汇总、来源侧被互认汇总及相应明细。 |

| 平台管理员 | 按权限导出组织或指定机构范围的数据。 |

| 互认平台 | 按当前查询条件、权限和脱敏规则生成 Excel 文件。 |



#### 需求背景



页面分页用于浏览，不能满足业务核对和线下汇总需求。平台需要在不扩大数据权限、不解除患者脱敏的前提下，导出当前查询条件下的全部匹配记录。



#### 前置条件



1. 导出接口操作授权由权限系统负责；本功能不重复判断操作权限。

2. 用户已经在统计页面形成有效查询条件。

3. 查询条件处于当前业务归属范围内。



#### 后置条件



1. 平台生成一个 `.xlsx` 文件，包含当前查询条件和业务归属范围内的全部匹配记录。

2. 导出中的患者姓名和证件号码与页面保持相同脱敏规则。

3. 导出不改变任何互认、引用或统计业务事实。



#### 主事件流



1. 用户在相应统计汇总或明细页面设置查询条件并发起导出。

2. 平台确认当前查询条件未超出既有业务归属范围。

3. 平台使用当前查询条件获取全部匹配记录，不使用页面当前页码和每页条数限制导出范围。

4. 平台按页面相同规则处理患者脱敏和指标口径。

5. 平台生成 Excel 文件供用户获取。



#### 备选流



1. 请求查询条件超出当前业务归属范围时，平台拒绝导出。

2. 当前查询没有匹配记录时，平台提示“当前条件下无可导出数据”，不生成 Excel 文件，也不扩大查询范围补充其他记录。

3. 导出过程中权限或查询条件校验失败时，不生成可获取文件。



#### 业务规则



1. 当前版本只提供 Excel `.xlsx` 格式，不同时提供 CSV、PDF 或其他格式。

2. 可导出互认使用汇总、提醒明细、采纳明细、不采纳明细、引用明细、来源医院被互认汇总和来源医院被互认明细。

3. 明细导出覆盖当前查询条件和权限范围内的全部匹配记录，不只导出页面当前页。

4. 导出必须继承当前查询条件和既有业务归属范围，不得扩大组织、医院或院区范围。

5. 患者姓名和证件号码始终脱敏，导出不提供完整身份或解除脱敏能力。

6. 预计节省金额随采纳明细导出，不另生成独立金额明细。

7. 其他不采纳原因的补充说明可以随有权脱敏明细导出，不据此生成新的原因分类。

8. MVP 不新增独立互认匹配记录导出；提醒、采纳、不采纳和引用明细导出增加互认匹配记录 ID 和互认匹配项 ID，用于跨明细核对。

9. 明细按互认匹配项一行展开，组级字段在同组各行重复；未反馈互认匹配项进入提醒明细并明确显示“未反馈”。

10. 互认匹配记录相关导出不包含完整报告结构化内容、PDF 文件标识或下载入口、影像调阅地址。



#### 关键属性



| 属性 | 说明 |

| --- | --- |

| 导出类型 | 互认使用汇总及四类明细、来源医院被互认汇总及明细；不单独导出互认匹配记录。 |

| 关联标识 | 提醒、采纳、不采纳和引用明细包含互认匹配记录 ID 与互认匹配项 ID。 |

| 文件格式 | Excel `.xlsx`。 |

| 查询条件 | 发起导出时页面当前有效查询条件。 |

| 数据范围 | 当前业务归属允许的组织、医院和院区范围。 |

| 记录范围 | 查询条件下全部匹配记录，不受页面分页限制。 |

| 脱敏规则 | 与对应统计页面一致，不允许解除。 |



## 设计约束



1. 本规约只定义业务需求和边界，不预设数据库表、接口路由、报文对象、代码模型、后台任务、部署方式或技术框架。

2. 平台使用互认匹配记录 ID 和互认匹配项 ID 定位互认处理和引用事实，不使用查询流水号、稳定匹配引用、拟开项目业务标识或调用方事件标识恢复或复用互认匹配记录。

3. 互认时间和实际引用时间必须保存到秒；报表可以按更粗粒度汇总，但不得降低原始业务时间精度。

4. 平台不得使用接口调用账号代替实际作出决定或执行引用的业务科室和人员。

5. 医院业务科室和人员的 ID、名称随对应业务记录保存；后续业务记录可以提供新的具体名称，不动态修改已有报告、互认处理或引用记录中的名称。

6. 平台不得根据名称或相似度自动推断标准项目、互认项目、LOINC、菌种、药敏、检查部位或诊断编码。

7. 平台不得根据患者姓名、电话或其他非跨院稳定标识进行模糊或概率患者匹配。

8. 平台不得解析、换算或重新判定来源检验结果、参考范围、异常、危急值、药敏结论、检查所见和检查结论。

9. 平台不得将查询、匹配返回、结构化展示、PDF、影像或引用详情访问自动解释为医生采纳或实际引用。

10. 完整报告提交必须保持结构化数据与 PDF 文件流共同成功或共同失败，不能先保存一部分后补齐另一部分。

11. 报告更正和作废不接入 PushCenter，不建设下游主动推送、推送记录、任务核对或恢复能力。

12. 平台不存储、代理或缓存 DICOM 文件，只保存来源影像状态和单个受控 HTTPS 影像调阅地址。

13. 影像调阅地址的定位参数由医院或区域影像中心封装，平台不得依据 PACS 或 DICOM 技术标识自行拼接。

14. 预计节省金额使用采纳处理结果成功保存时接收组织、接收医院、接收院区当前金额形成，不使用来源医院金额，也不模拟实际收费、医保结算、患者退费或医院收入。

15. 统计导出只使用 Excel `.xlsx` 格式，必须继承页面查询条件、权限和脱敏规则。

16. 当前版本不建设通用重量级审计、金额独立版本、趋势图、医生排名或绩效评价能力。

17. 引用详情有效时长复用现有系统参数系统，使用全平台统一的正整数分钟参数；不新建专用参数表、配置页面或组织级覆盖。

18. 报告版本形成不得依赖医院版本号、操作类型、完整内容比较、PDF 文件摘要或源端报告修改时间；平台使用报告业务标识、生命周期状态和成功保存顺序，每次成功完整上传均形成新版本。

19. 历史报告版本只在管理端按权限查看和下载，不得通过医院 HIS 在线业务接口开放，也不得提供修改、删除、恢复或重新启用能力。

### 用户界面



#### 通用界面要求



1. 平台页面的可见、查询、操作、下钻和导出能力必须受外部权限系统菜单授权以及可信组织、医院、院区上下文控制。

2. 页面应以业务名称、当前状态、关键时间和必要说明表达业务事实，不展示平台内部存储标识或技术排障信息。

3. 页面中的患者姓名、证件号码、联系电话等敏感信息按照对应业务用途和权限展示；统计及导出场景必须保持脱敏。

4. 页面具体布局、控件类型、菜单位置和视觉样式由界面设计确定，但不得减少本规约定义的业务能力、查询条件、状态提示或权限边界。



#### 互认项目管理



1. 页面进入时自动刷新当前有效标准项目目录，并提供手动刷新能力。

2. 页面展示互认项目的标准项目编码和按需获取的标准项目名称、类型、分类、分组、可互认时间、启停状态及必要的不可用说明，不展示创建人、创建时间、修改人或修改时间，也不展示或维护组织统一金额。

3. 页面支持从当前有效最细层标准项目中选择项目，填写可互认时间后新增并默认启用。

4. 页面支持修改可互认时间，并通过独立启用、停用操作维护启停状态；不提供物理删除或配置版本恢复。

5. 同组织目录或配置刷新失败时明确提示并保留原列表；切换组织后不展示旧组织数据，目标组织读取失败时禁止写操作。目录停用仍允许修改时间及停用配置，但拒绝重新启用。
6. 当前不可用说明只表达目录停用，不重复表达配置自身停用。多层同时停用时按分类、分组、标准项目顺序显示一个原因：“所属分类已停用”“所属分组已停用”或“标准项目已停用”；目录全部启用时无说明。



#### 互认项目金额维护

1. 平台管理员可以按授权组织、医院和院区查看、维护互认项目当前金额；医院管理员只能查看、维护本医院及有权院区。
2. 页面按组织、医院、院区和标准项目编码查询，展示标准项目名称、当前金额、未配置状态和最后修改信息。
3. 页面只允许选择当前组织已经建立互认配置的标准项目；目录或配置停用时仍可查看、维护金额，并显示当前不可用于新匹配。
4. 金额必填、不得小于零且最多两位小数；零元是有效配置，未配置与零元必须区分展示。
5. 页面不维护分类、分组、金额启停状态、院内项目或项目对照。

#### 互认项目分类分组管理



1. 平台管理员维护平台统一的分类和分组；项目类型固定为检验和检查。

2. 分类和分组页面展示名称、启停状态及使用情况；本版本不额外维护分类编码、分组编码或排序字段。

3. 页面支持新增、整份保存可编辑资料以及独立启用、停用。分类和分组名称、备注始终可编辑，唯一性规则不变；分类存在下级分组（含已停用）时项目类型只读。分组所属分类创建时确定，创建后只读，不提供改挂或拖拽移动；均不提供物理删除。资料未变化时保存仍提交，启停不在编辑表单中。

4. 新增分组必须归属有效分类；已有分组名称、备注维护不受所属分类停用限制。分类名称在全平台标准目录内唯一，分组名称在同一分类下唯一，修改时排除自身。

5. 停用分类或分组仍可查询历史数据，但下级对象不再属于当前有效标准目录，也不能用于新的互认配置。

6. 页面不展示、不维护医院院内项目编码、医院院内项目名称或任何项目对照信息。

#### 标准医疗项目管理

1. 平台管理员在标准目录中维护标准医疗项目，页面展示项目类型、所属分类、所属分组、标准项目编码、名称、备注和启停状态。MVP 阶段不展示也不返回标准项目使用情况；其统计口径与引用关系留待后续阶段明确，不影响分类和分组展示是否存在下级。

2. 页面支持在有效分类和分组下新增标准医疗项目、修改备注以及独立启用、停用；创建后的编码、名称、分类和分组不可通过普通修改改变，不提供物理删除。

3. 标准项目编码在全平台唯一；停用项目仍可查询历史数据，但不能用于新的互认配置或匹配业务。

#### 报告管理与历史版本

1. 报告列表支持按组织、医院、院区、报告时间日期范围、报告类型、报告单号、患者证件号码和患者姓名查询；患者姓名仅按明确输入条件查询，不用于患者身份匹配。

2. 平台在报告详情中提供只读历史版本区域，不建设独立版本管理菜单。

3. 历史版本按照平台成功形成顺序展示，明确标识当前有效版本、已被后续版本替代的历史版本和报告已作废状态。

4. 每个版本展示平台内部版本序号、源端报告修改时间、平台接收时间、报告责任人员、来源报告备注及 PDF 文件名；不展示或要求更正原因、版本变更原因。

5. 用户可以查看每个版本的完整结构化报告，并下载使用该版本所保存文件名的 PDF。

6. 医院管理员默认可以查看本医院及有权院区上传报告的全部历史版本、完整内容和 PDF，不新增独立报告查看权限；平台管理员按照现有数据权限查看授权范围内报告，其他医院不得查看来源医院报告的历史版本。

7. 页面不提供版本自动差异比较、修改、删除、恢复、重新设为当前版本或重新启用能力；查看历史版本不得改变报告业务有效性。

8. 医院 HIS 在线业务界面及接口只能使用当前有效版本，不提供历史版本查询或下载入口。



#### 接收医院互认使用统计



1. 页面支持按日期范围、医院、院区、互认科室和互认项目查询权限范围内的数据；互认医生可以作为明细查询条件。

2. 页面展示当前组织内的提醒、采纳、不采纳、引用、同期互认率和预计节省金额。

3. 提醒、采纳、不采纳和引用汇总数字支持下钻到对应脱敏明细，预计节省金额随采纳明细展示。

4. 页面提供不采纳原因次数及占比，并允许在明细中查看其他原因的脱敏补充说明。

5. 页面不提供趋势图、医生排名、绩效评价或患者身份解除脱敏能力。

6. 提醒、采纳、不采纳和引用明细提供只读“查看互认匹配记录”入口，展示组级信息和全部互认匹配项，不新增独立互认匹配记录菜单；未反馈只表示平台未收到结果。

7. 接收医院管理员不得通过统计或互认匹配记录页面打开其他来源医院的完整结构化报告、PDF 或影像地址。



#### 来源医院被互认统计



1. 医院管理员在来源医院被互认统计中只能查看本院报告形成的被互认汇总和脱敏明细；平台管理员按权限查看组织范围数据。

2. 页面展示当前组织内的被互认次数。

3. 明细可以展示互认项目、接收医院及院区、互认科室、互认医生和互认时间，患者姓名必须脱敏。

4. 页面不展示或汇总来源医院贡献金额。



#### 统计导出入口



1. 互认使用和来源医院被互认的汇总及明细页面按权限提供 Excel 导出入口。

2. 导出入口沿用页面当前查询条件和数据权限，导出全部匹配记录而非当前分页。

3. 页面应明确导出仍使用脱敏数据，不提供 CSV、PDF 或解除脱敏选项。

4. 当前查询没有匹配记录时，页面提示“当前条件下无可导出数据”，不生成空 Excel 文件。



#### 医院 HIS 界面边界



1. 匹配提醒、医生查看、采纳或不采纳操作、继续或撤销院内医嘱以及病历写入界面由医院 HIS 负责。

2. 互认平台不规定医院 HIS 的页面布局、弹窗形式、控件、菜单或调用时机。

3. 医院 HIS 的界面行为不得替代明确的处理结果和引用结果提交；关闭提示、查看文件或离开页面均不能由平台推断为采纳、不采纳或引用。
