# 简介

## 目的

本文档用于定义检验检查结果互认平台的软件需求规约，明确当前版本的业务范围、参与者、前置条件、后置条件、主事件流、备选流、业务规则、关键属性、设计约束和用户界面要求，作为后续设计、开发、测试、评审和验收的业务依据。

本文档适用于检验检查结果互认平台及其与标准项目管理系统、平台权限体系、医院侧采集服务和医院 HIS 之间的业务协作。医院 LIS、PACS 及医院侧采集服务的内部实现不属于互认平台的建设范围，本文仅在相关功能中描述其与互认平台之间必要的业务责任和交互边界。

本文档不替代接口设计文档、数据库设计、技术架构、安全设计、部署方案或医院院内系统改造方案。本文未定义具体路由、报文结构、数据传输协议、数据库表、代码模型、后台任务或其他技术实现。

## 定义、首字母缩写词和缩略语

| 术语或缩写 | 定义 |
| --- | --- |
| HIS | Hospital Information System，医院信息系统。医院根据自身接诊或开单流程调用互认平台能力、向医生展示候选并反馈处理及引用结果。 |
| LIS | Laboratory Information System，实验室信息系统。医院侧采集服务可以从 LIS 获取审核完成的检验报告，但互认平台不规定其内部采集方式。 |
| PACS | Picture Archiving and Communication System，医学影像存档与通信系统。互认平台不接收或保存 DICOM 影像文件，只处理检查报告随附的影像调阅地址及来源影像状态。 |
| 标准医疗项目 | 由标准项目管理系统统一维护的医疗项目，是各业务平台进行项目语义对齐的共同基准。 |
| 互认项目 | 互认平台从标准医疗项目中选定并保存、允许进入结果互认业务范围的最细层项目。互认项目保存标准项目编码和名称、可互认时间、启停状态和来源状态，不维护全县统一价格。 |
| 可互认时间 | 从报告时间开始计算、报告可以作为互认候选返回的时间长度。以天为单位，只允许正整数，最小值为一天；一天按连续二十四小时计算，结束边界包含在有效范围内。查询使用互认项目的当前配置，该配置不用于报告接收校验，也不是报告保存期限。 |
| 院内项目 | 医院某一院区在本地业务系统中实际使用的检查或检验项目及其编码。相同编码在不同医院或院区不必具有相同语义。 |
| 项目编码对照 | 医院在当前医院和院区范围内维护的院内项目与互认项目之间的一对一语义对应关系及当前价格。普通检验结果和检查项目明细通过当前有效对照关联互认项目。 |
| 来源不可用 | 互认项目所引用的标准医疗项目已不在标准项目管理系统当前有效目录中的状态。该状态保留既有业务数据，但阻止相关新增对照、新报告上传和已有报告查询。 |
| 报告业务标识 | 由医院、院区、报告类型和报告单号共同组成，用于在互认平台唯一识别一份检验或检查报告。 |
| 完整报告提交 | 检验报告和检查报告分别提供的报告提交能力。医院只提交报告单号、当前完整结构化报告、源端报告修改时间及 PDF，不提交新增、更正或作废状态；平台根据报告是否存在及修改时间自行创建首个版本或追加新版本。 |
| 报告作废 | 与完整报告提交分开的独立能力。医院只提交来源报告单号、作废时间和作废原因，不重复提交报告内容及 PDF。 |
| 源端报告修改时间 | 医院源系统中报告当前完整内容最后一次实际生成或修订的时间。同一报告每次实际修订后的时间必须严格递增，相同时间只表示同一次完整报告提交的重传。 |
| 报告版本 | 一份报告在首次完整提交或后续有效完整提交时形成的完整且不可变内容版本，由平台按成功形成顺序生成内部版本序号。旧版本保留用于管理端追溯，但停止参与后续候选查询、引用详情和新的引用。 |
| 当前有效报告 | 当前未被作废、且在存在更正时属于最新有效版本的报告。是否能够成为互认候选，还需满足互认项目状态、可互认时间及候选查询的其他规则。 |
| 混合项目报告 | 同时包含已对码和未对码项目明细的完整报告。至少有一个明细完成有效对码时可以接收整份报告，未对码明细只用于保持报告完整、展示和来源追溯。 |
| 互认候选 | 平台针对一个去重后的互认项目，按照候选选择规则确定并返回的一份当前有效报告。联合报告可以同时为多个互认项目形成候选，但报告内容不按项目拆分为多份报告。 |
| 候选提供组 | 平台针对一次成功处理并形成非空结果的候选查询保存的完整候选集合，具有平台生成的候选提供组 ID，并记录接收医院、院区、患者、本次来源就诊、候选提供时间及全部实际返回项目。 |
| 候选项目 | 候选提供组内一个实际返回的项目，具有平台生成的候选项目 ID，关联本次拟开院内项目、互认项目、命中的报告版本及候选内容。每次查询均生成新的组和项目 ID，不提供跨查询稳定候选引用。 |
| 互认时间 | 医生实际作出某次采纳或不采纳决定的业务时间，由医院 HIS 提供并精确到秒，用于区分同一就诊中针对同一候选发生的多次真实互认处理。 |
| 互认处理结果 | 医生明确作出的采纳或不采纳决定。候选返回、结构化内容展示、PDF 或影像入口访问均不自动形成互认处理结果。 |
| 引用详情 | 医生采纳候选后，医院 HIS 在有效期内获取的、可用于写入本次病历的项目内容及必要报告公共上下文。获取引用详情本身不表示已经成功写入病历。 |
| 引用详情有效时长 | 采纳决定首次成功保存后，医院 HIS 可以继续调用引用详情接口的全平台统一时长。该时长使用现有系统参数系统按正整数分钟维护，默认七百二十分钟。 |
| 引用结果 | 医院 HIS 将已采纳内容成功写入本次病历后向平台提交的实际引用事实。平台只接收已经引用的正向事实，不要求提交未引用状态。 |
| 提醒次数 | 平台成功处理候选查询并生成非空候选提供组时，按组内每个候选项目形成的统计次数。即使医院未收到响应，已经生成的提醒事实也不撤销；提醒不表示医院 HIS 已实际弹窗或医生已经查看、采纳或引用。 |
| 预计节省金额 | 医生采纳互认项目时，按照采纳决定成功保存时接收医院、接收院区当前启用项目编码对照的价格形成的业务统计金额。该金额不表示实际收费、医保结算、患者退费或医院财务收入。 |
| 平台科室 ID、平台医生 ID | 平台权限体系中用于标识科室和医生的业务接口标识。平台根据 ID 校验医院及院区归属、查询名称，并将 ID 和当次名称随业务记录保存。 |

# 整体说明

## 产品总体效果

检验检查结果互认平台用于统一跨医疗机构的检查、检验项目语义，接收和管理医院审核完成的检查、检验报告，并在患者接诊或开单过程中向医院 HIS 提供可互认候选。医生在医院 HIS 中查看候选内容后作出采纳或不采纳决定；采纳后，医院 HIS 可以获取引用详情，将相应内容写入本次病历并反馈实际引用结果。

平台通过互认项目和医院项目编码对照解决不同医院、院区使用不同院内项目编码的问题，通过患者精确关联、报告版本管理和候选选择规则保证候选业务身份明确。平台记录医院明确反馈的互认处理和引用事实，并面向医院及平台管理员提供权限范围内的统计、下钻和 Excel 导出能力。

平台不代替医生作出临床决定，不直接操作医院 HIS 中的医嘱或病历。候选返回、结构化内容展示、PDF 查看或影像入口访问均不自动表示医生已经采纳或引用。报告中的来源异常、危急值、检查所见和诊断结论均按来源内容保存和展示，平台不重新计算、推断或改写临床结论。

## 产品功能

| 编号 | 功能 | 说明 |
| --- | --- | --- |
| F01 | 互认项目管理 | 从当前有效的标准医疗项目中选取互认项目，维护可互认时间、启停状态和来源状态。 |
| F02 | 项目编码对照管理 | 医院在当前医院和院区范围内维护院内项目与互认项目之间的一对一关系及当前价格，并可同步检验协同、检查协同的已启用对照进行预填和比对。 |
| F03 | 报告采集与生命周期 | 接收检验报告和检查报告的完整提交及独立作废，平台自行创建首个版本或追加新版本，保存完整结构化内容、PDF、版本关系和必要来源信息，并在管理端提供受权限控制的只读历史版本查看。 |
| F04 | 互认候选查询 | 根据患者身份和一个或多个拟开院内项目返回符合条件的互认候选，并对联合报告进行完整分组；没有候选时返回空候选集合。 |
| F05 | 互认处理结果 | 按候选提供组接收医生对全部候选项目一次完整、原子且不可更改的采纳或不采纳决定，并形成对应统计事实和预计节省金额。 |
| F06 | 获取引用详情 | 在互认决定为采纳且候选报告版本仍有效时，返回本次病历引用所需的项目内容和报告公共上下文。 |
| F07 | 提交引用结果 | 接收医院 HIS 已成功写入本次病历的实际引用事实，记录实际引用时间、科室和医生。 |
| F08 | 互认统计与分析 | 提供提醒、采纳、不采纳、引用、同期互认率、预计节省金额、接收医院使用和来源医院被互认分析。 |
| F09 | 互认统计导出 | 按当前查询条件、数据权限和脱敏规则导出互认汇总及明细，文件格式为 Excel。 |

平台面向医院 HIS 的在线互认主流程由查询互认候选、提交互认处理结果、获取引用详情和提交引用结果四类核心业务能力组成。报告采集、身份认证、项目编码对照、报告更正或作废等其他能力不计入这四类核心业务能力。

端到端业务过程如下：

1. 平台管理员从标准医疗项目中选取并维护互认项目。
2. 医院在当前医院、院区范围内维护院内项目与互认项目的一对一编码对照及当前价格，也可以同步检验协同、检查协同的已启用对照后人工确认保存。
3. 医院侧采集服务在检查或检验报告审核完成或修订后重新审核时提交当前完整报告；报告失效时调用独立作废能力。
4. 医院 HIS 在患者接诊或开单过程中，以患者身份和拟开院内项目发起互认候选查询。
5. 平台解析项目编码对照，按当前有效报告、可互认时间和候选选择规则返回符合条件的候选结果。
6. 医院 HIS 向医生展示候选结果及可用的 PDF、影像入口；医生根据患者当前情况作出采纳或不采纳决定。
7. 医院 HIS 使用候选提供组 ID，完整提交组内全部候选项目的采纳或不采纳决定；平台原子保存实际决定、互认时间、科室、医生、不采纳原因或预计节省金额，首次保存后不得更改。
8. 对于已采纳候选，医院 HIS 获取引用详情并将相应内容写入本次病历，写入成功后提交引用结果。
9. 平台依据候选返回、当前有效互认决定和实际引用事实形成权限范围内的统计、下钻和导出结果。

## 用户特征

| 用户或外部参与方 | 特征与职责 |
| --- | --- |
| 平台管理员 | 维护互认项目及其业务配置；查看全县范围内的项目编码对照并在异常情况下按权限停用；按现有数据权限查看报告及只读历史版本；查看、下钻和导出全县范围的接收侧互认使用统计及来源侧被互认统计；不代替医院执行日常对码或价格维护。 |
| 医院管理员 | 在当前登录医院和有权院区范围内维护院内项目编码对照及当前价格，同步并核对检验协同、检查协同的已启用对照；查看本医院及有权院区上传报告的完整内容、只读历史版本和 PDF；查看接收侧互认使用统计、来源侧被互认统计及相应脱敏明细，并按权限导出。 |
| 医院侧采集服务 | 由医院或实施厂商负责，在来源报告审核完成或修订后重新审核时提交当前完整报告，在报告失效时调用独立作废能力，并处理明确失败和超时重传。该服务不属于互认平台的建设模块。 |
| 医院 HIS | 决定在线互认能力在接诊或开单流程中的调用时机，展示候选，提交互认处理结果，获取引用详情，将内容写入病历并反馈引用结果。 |
| 医生 | 在医院 HIS 中查看候选结构化内容、报告 PDF 或影像，根据患者当前情况作出采纳或不采纳决定；平台不代替医生判断。 |

医院侧采集服务、医院 HIS、LIS、PACS 和影像服务由医院或相应厂商建设和维护。互认平台只定义与其发生业务协作时的输入、输出、责任和状态边界，不规定医院内部页面、数据读取方式、采集表、轮询周期、本地队列、硬件或网络实现。

## 约束

1. 平台只接收上线后新产生并审核完成的检查、检验报告，不导入上线前历史报告。
2. 一份报告首次创建时至少包含一个能够通过当前有效项目编码对照关联互认项目的明细；报告已经存在时，后续完整版本即使不再包含有效对码也必须保存并替代旧版。已对码和未对码明细共同保留，只有有效对码明细形成候选。
3. 报告接收不按可互认时间进行筛选，但只将当前启用且来源有效的互认项目关系视为有效对码。互认项目停用或来源不可用时阻止只能关联该项目的报告首次创建，并停止相关候选；已经存在的报告仍允许提交后续完整版本。可互认时间在候选查询时按当前配置判断。
4. 跨院患者以证件类型和证件号码精确关联，并使用姓名、性别代码和出生日期进行一致性校验。平台不使用姓名相似度、电话或院内就诊卡进行替代匹配。
5. 报告上传、互认处理和引用结果涉及的科室、医生只接收平台科室 ID、平台医生 ID。任一 ID 不存在或不属于当前调用医院、院区时，按对应功能的整体校验规则拒绝保存。
6. 平台科室或医生 ID 存在且归属正确但已经停用时，允许医院补交真实的报告、互认处理或引用事实。平台不校验医生当前所属科室与同一业务记录中的科室一致。
7. 平台根据科室、医生 ID 查询并保存当次名称。科室或医生以后改名时，不动态修改已有业务记录保存的名称。
8. 每次完整报告提交或作废请求只处理一份报告。完整报告提交以一个请求同时提供完整结构化报告及 PDF，二者共同成功或共同失败；作废只提交来源报告单号、作废时间和作废原因。
9. 报告按可信调用身份中的医院、院区、所调用报告类型能力和医院提供的报告单号唯一识别。医院不提交平台报告 ID 或组合报告业务标识，平台不使用患者、项目、报告内容或 PDF 判断报告身份。
10. 平台根据全部历史版本中的源端报告修改时间判断完整提交重传及版本顺序，不比较完整内容或文件摘要。未命中历史版本时，报告不存在则创建首个版本，当前有效且修改时间晚于当前版本则追加新版本，时间早于或等于当前版本则拒绝；报告已经作废时拒绝继续提交完整版本。
11. 后续完整版本形成后，原版本停止参与候选查询、引用详情和新的引用；报告作废不形成内容版本且不物理删除，作废后不再返回为候选或新的引用内容。
12. 每个互认项目只返回查询时点前、当前可互认时间内检查或检验时间最晚的一份有效报告；检查或检验时间相同时，优先选择报告时间较晚的一份；两者均相同时，在候选数据及相关配置未变化的情况下稳定返回同一份报告。
13. 一份联合报告命中多个互认项目时，按一份完整报告分组返回；互认候选、处理决定和引用事实仍按具体互认项目分别形成。
14. 每次非空候选查询生成新的候选提供组 ID 和候选项目 ID；重试按新查询处理，不使用查询流水号、稳定候选引用或幂等键恢复旧组。
15. 候选查询、候选返回、结构化内容展示、PDF 查看、影像入口访问和引用详情获取均不自动形成采纳或引用事实。
16. 互认处理结果必须来自医生明确反馈的采纳或不采纳，并完整覆盖候选提供组全部项目；首次保存后不得更正、撤销或删除。引用结果必须来自医院 HIS 已经成功写入本次病历的正向事实。平台不根据未反馈状态推断拒绝、忽略、采纳或引用。
17. 不采纳必须使用平台统一原因代码；选择其他原因时必须提供补充说明。各医院不得自行扩展或修改原因代码。
18. 预计节省金额在采纳决定成功保存时按接收医院、接收院区当前启用项目编码对照的价格形成，不使用来源医院价格，不采集数量，不模拟按次、按部位、组合收费、医保结算或患者实际退费。
19. 提醒、采纳、不采纳、引用和预计节省金额分别使用已确认的业务时间归入统计期间，接口接收时间不得替代业务时间。
20. 医院管理员只能查看本院及有权院区的数据，平台管理员按授权查看全县数据。统计页面和导出中的患者姓名、证件号码必须保持脱敏。
21. 本院报告候选由全局开关控制，默认关闭；开启后使用全局本院报告排除时长，默认四十八小时。参数调整只影响后续查询，不倒改已有报告、互认处理、引用和统计事实。
22. 引用详情调用受全平台统一的引用详情有效时长控制，默认七百二十分钟；该限制只控制重新获取引用详情，不控制医院已经合法取得并保存的数据、PDF 下载或引用结果提交。

## 假设与依赖关系

1. 标准项目管理系统能够提供当前有效的标准医疗项目目录，并保证标准项目编码能够稳定标识相应项目。目录获取不完整或失败时，互认平台保留既有状态，不以不完整结果覆盖当前来源状态。
2. 医院在接入平台前已经将本医院、院区下需要参与业务的科室和医生维护到平台权限体系，并能够在院内系统中关联对应的平台 ID。
3. 平台权限体系能够根据平台科室 ID、平台医生 ID 返回其存在性、医院院区归属、停用状态和当前名称，并为平台页面提供必要的身份及数据权限控制。
4. 医院或实施厂商负责建设并运行医院侧采集服务。该服务能够从医院源系统识别首次审核完成、修订后重新审核或作废的报告，前两者调用相同的完整报告提交能力，作废调用独立作废能力。
5. 医院 LIS、PACS 或其他来源系统能够提供已确认字段中在源系统实际存在的内容；对于规定为“源系统存在时必须提供”的信息，医院不得在源系统存在时无故省略。
6. 医院 HIS 负责在合适的接诊或开单环节调用在线互认能力、向医生展示候选、执行院内医嘱或病历操作，并在真实业务动作完成后提交处理或引用结果。
7. 接入医院只上传依其制度允许常规跨院共享的报告。需要专项授权才能共享的报告在相关授权机制另行明确前不上传。
8. 检查报告的影像调阅地址由医院或区域影像中心提供并负责其可用性、访问控制、内容和保存期限。平台只保存并原样返回地址，不测试、代理、缓存或保证可用性；报告形成后续版本或作废后，平台停止在后续响应中返回原地址，但无法撤回已经下发的外部地址。
9. 医院侧在完整报告提交超时或未取得明确结果时，原样提交相同完整报告及源端报告修改时间；作废因原报告不存在失败时，医院保证报告先成功提交后重新调用作废能力。
10. 医院 HIS 对已经接收并保存在院内的数据承担后续更新和失效处理责任。平台不通过主动推送补偿医院未反馈引用结果或未重新查询的情况。
11. 检验协同和检查协同能够按当前医院、院区提供已经启用的项目对照，并使用稳定的标准项目编码和院内项目编码表达对照关系；互认平台不依据项目名称推断编码关系。
12. 平台现有系统参数系统能够定义全平台统一参数、提供默认值和格式校验，并支持互认平台在每次获取引用详情时按参数编码读取当前值。

## 当前版本范围与排除项

当前版本包含以下业务范围：

1. 互认项目及其可互认时间、启停状态和来源状态维护。
2. 医院、院区范围内的一对一项目编码对照、当前价格维护，以及检验协同、检查协同已启用对照的页面预填和比对。
3. 检验报告和检查报告的自动增量采集、完整报告提交、独立作废、完整版本保存，以及管理端只读历史版本查看和 PDF 下载。
4. 批量互认候选查询、项目去重、最近有效报告选择和候选结果返回。
5. 采纳、不采纳、不可更改的整组互认决定、不采纳原因和预计节省金额记录。
6. 引用详情有效期控制、详情获取和实际引用结果记录。
7. 接收医院使用统计、来源医院被互认分析、不采纳原因统计、明细下钻及 Excel 导出。
8. 与上述业务相关的医院院区归属校验、科室医生关联、页面数据权限和患者信息脱敏。

当前版本明确不包含以下能力：

1. 同一互认项目返回多个独立历史报告、历史趋势或多版本候选。
2. 独立的调阅状态、调阅反馈接口、调阅统计，或者以结构化内容、PDF、影像入口访问推断医生已查看、采纳或引用。
3. DICOM 影像文件上传、存储、代理或缓存，以及 PACS 影像号、检查实例 UID、序列 UID 等影像技术标识采集。
4. 平台上线前历史报告导入。
5. 查询业务流水号、调用方事件标识、拟开项目业务标识或通用传输批次设计。
6. 报告更正或作废后的下游主动推送、PushCenter 接入、推送记录、状态核对、自动恢复或人工恢复。
7. 医院 HIS 页面人工逐份上传报告、平台逐份审批正常报告或平台修改报告临床内容。
8. 医院内部 LIS、PACS、采集服务的数据读取、采集表、轮询、本地队列、硬件和网络实现。
9. 患者姓名模糊匹配、概率匹配，或者根据电话、院内就诊卡等信息替代跨院患者标识。
10. 标准编码、LOINC、菌种代码、药敏代码、检查部位代码、临床诊断、检查所见、检查结论或结果异常状态的自动推断、换算和重判。
11. 来源保密标识驱动的敏感报告分级、患者专项授权、上传医院逐份审批或特殊调阅流程。
12. 危急值通知、确认、回执、超时提醒、升级提醒或闭环处置；平台只保存和展示来源危急值标志。
13. 每次收费、按部位收费、组合收费、数量计费、医保结算、患者退费或医院财务收入模拟。
14. 项目编码对照价格的独立版本、变更历史或历史价格恢复，以及根据新价格重算既有预计节省金额。
15. 通用重量级审计、报告完整操作过程日志、医院实验室仪器原始日志或质控过程重建。
16. 报告采集前置机作为平台建设模块，以及医院侧采集任务、失败任务或传输状态管理页面。
17. 趋势图、医生互认率、预计节省金额排名、医生绩效排名或其他医生考核能力。
18. CSV、PDF 或其他统计导出格式，以及通过导出解除脱敏或扩大数据权限。
19. 本院报告按医院分别配置不同的候选规则，或者为本院报告开关和排除时长单独建设配置模块。
20. 互认决定或引用结果的更正、撤销、删除、冲销、后台补改或版本管理。

22. 项目对照同步记录、同步历史、同步结果回滚，以及同步后自动保存或自动启用对照。

# 具体需求

## 功能

### F01 互认项目管理

#### 参与者

| 参与者 | 职责 |
| --- | --- |
| 平台管理员 | 获取标准医疗项目目录，选择互认项目，维护可互认时间和启停状态。 |
| 标准项目管理系统 | 提供当前有效的最细层标准医疗项目及其类型、类别和分组信息。 |

#### 需求背景

不同医院需要使用统一的项目语义开展结果互认。平台从标准医疗项目中选择当前允许参与互认的最细层项目，并维护候选查询所需的可互认时间、启停状态和来源状态。各医院、院区的价格在项目编码对照中维护，不属于互认项目配置。

#### 前置条件

1. 操作人员具有互认项目管理权限。
2. 标准项目管理系统已配置为平台可调用的目录来源。
3. 新增互认项目所引用的标准医疗项目属于当前有效目录中的最细层项目。

#### 后置条件

1. 新增成功后形成一条默认启用的互认项目，保存标准项目编码和名称、可互认时间、启停状态及来源状态。
2. 配置修改后，新的可互认时间或启停状态按各自业务规则影响后续业务。
3. 项目停用或来源不可用时保留已有项目、编码对照、报告和历史业务事实。

#### 主事件流

1. 操作人员进入互认项目管理页面，平台自动获取一次当前有效标准项目目录；操作人员也可以手动刷新。
2. 平台在完整获取成功后，以标准项目编码核对已选互认项目的来源状态。
3. 操作人员从当前有效的最细层项目中选择一个、多个或全部项目。
4. 操作人员为每个拟新增项目填写可互认时间。
5. 平台校验项目来源、必填配置和重复选择情况。
6. 校验通过后保存互认项目并默认启用。
7. 操作人员可以后续调整可互认时间和启停状态。

#### 备选流

1. 标准目录获取失败或返回不完整时，平台提示刷新失败并保留原有目录核对结果和来源状态。
2. 已选标准项目不再属于当前有效目录时，平台将对应互认项目标记为来源不可用，不自动按名称或相似度替换。
3. 可互认时间为空，或者配置为零、负数、小数、永久有效等非法值时，平台拒绝保存本次新增或修改。
4. 已存在相同标准项目编码的互认项目时，平台拒绝重复新增。
5. 停用项目重新启用时，只有其标准项目来源当前有效才允许启用。

#### 业务规则

1. 互认项目必须引用当前有效标准目录中的最细层项目。
2. 互认项目保存标准项目编码和名称，不保存项目类型、类别和分组；类型、类别和分组按需从当前标准目录获取。
3. 可互认时间以天为单位，只允许配置正整数，最小值为一天；不接受零、负数、小数或永久有效配置。
4. 可互认时间中的一天按从报告时间起连续二十四小时计算，不按自然日零点截断；经过时间小于或等于当前配置时仍在候选窗口内，超过后停止参与候选查询。
5. 可互认时间只用于候选查询窗口，不用于报告接收校验或报告保存期限判断。
6. 可互认时间调整对已有报告的后续候选查询即时生效，不倒改已有互认处理或引用事实。
7. 互认项目不维护全县统一价格，各医院、院区的当前价格随项目编码对照维护。
8. 互认项目新增后默认启用，不提供物理删除。
9. 互认项目停用后，阻止只能关联该项目的报告首次创建，相关已有报告立即停止参与候选查询，但已有报告仍允许保存后续完整版本；重新启用后按当前可互认时间及其他候选规则重新判断。
10. 来源不可用时，阻止新增或重新启用相关编码对照、上传新报告和查询已有报告。
11. 替代标准项目必须作为新的互认项目重新选择，医院应重新调整项目编码对照。

#### 关键属性

| 属性 | 说明 |
| --- | --- |
| 标准项目编码 | 被选标准医疗项目的稳定编码，创建后不可替换为其他项目编码。 |
| 标准项目名称 | 选择互认项目时保存的标准医疗项目名称。 |
| 可互认时间 | 从报告时间开始计算的候选有效时长，以天为单位，必填正整数且最小为一天。 |
| 启停状态 | 启用或停用；新增后默认启用。 |
| 来源状态 | 来源有效或来源不可用，由完整目录刷新结果确定。 |
| 修改时间、修改人 | 使用平台框架已有信息记录维护操作，不形成独立配置版本。 |

### F02 项目编码对照管理

#### 参与者

| 参与者 | 职责 |
| --- | --- |
| 医院管理员 | 在当前医院和有权院区范围内新增、修改、启用或停用项目编码对照，维护当前价格，并核对同步结果。 |
| 平台管理员 | 跨机构查看编码对照，并在异常情况下按权限停用对照。 |
| 检验协同、检查协同 | 按当前医院、院区提供各自已经启用的项目对照。 |
| 互认平台 | 展示互认项目及当前对照，获取并比对协同对照，校验保存内容和一对一关系。 |

#### 需求背景

各医院和院区使用的院内项目编码、名称和价格不同。平台需要由医院自行维护院内项目与互认项目的一对一语义对应关系及当前价格，使报告上传和医院 HIS 候选查询能够解析到统一互认项目，并按接收医院、院区的当前价格形成预计节省金额。检验协同和检查协同已经维护过部分项目对照，互认平台应允许管理员同步其已启用对照进行页面预填和差异核对，避免重复录入，但同步不得代替管理员确认和保存。

#### 前置条件

1. 操作人员已登录平台并具有项目编码对照管理权限。
2. 医院管理员的当前医院和院区能够从可信登录上下文确定。
3. 新建或重新启用对照所选择的互认项目当前启用且来源有效。
4. 保存并启用对照时，院内项目编码、院内项目名称和当前价格已经明确。
5. 使用同步能力时，检验协同和检查协同至少有一个能够按当前医院、院区提供已启用对照或返回明确失败。

#### 后置条件

1. 新建成功后形成当前医院、院区下默认启用的项目编码对照及当前价格。
2. 同步但尚未保存的预填、比对和冲突状态只存在于当前页面，不形成项目编码对照或其他持久化记录。
3. 对照关系修改或启停只影响后续上传报告及后续院内项目解析，不重写已接收报告保存的互认项目关系。
4. 价格调整只影响之后成功保存的采纳决定，不重算历史预计节省金额。
5. 停用对照后保留既有对照和历史业务数据。
6. 使用“保存全部”时，校验通过的行保存成功，失败行保持未保存并显示原因；互不冲突的成功行不因其他行失败而回滚。

#### 主事件流

1. 医院管理员进入项目编码对照管理页面，平台按当前医院和院区限定数据范围。
2. 平台按互认项目展示分类、分组、互认项目名称和编码、本院项目名称和编码、当前价格、可互认时间及对照状态；可互认时间只读展示。
3. 医院管理员可以直接在表格行内填写本院项目名称、编码和当前价格，也可以点击一个“同步已有对照”操作。
4. 点击同步时，平台针对当前医院、院区同时获取检验协同和检查协同已经启用的对照，并按项目类型自动选择来源系统。
5. 平台使用标准项目编码定位互认项目，使用本院项目编码比较同步结果与当前已保存对照，并在表格行内预填或显示一致、差异、冲突和跳过结果。
6. 医院管理员核对同步结果，处理多个候选或编码冲突，填写或修改本院项目名称、编码、当前价格和备注。
7. 医院管理员对单行执行保存，或者点击页面顶部“保存全部”提交全部已编辑行。
8. 平台校验当前医院、院区、互认项目状态、本院项目编码、当前价格及启用对照的一对一关系。
9. 平台保存校验通过的行并默认启用，按行返回成功或明确失败结果；同步预填但未保存的其他行不参与业务。
10. 医院管理员可以后续修改本院项目名称、互认项目、当前价格和备注，或者启用、停用对照。

#### 备选流

1. 医院管理员不使用同步时，可以直接在对应互认项目行内填写本院项目名称、编码和当前价格并保存。
2. 当前医院、院区下的本院项目编码已经用于另一条启用对照，或者当前互认项目已经存在另一条启用对照时，平台拒绝保存或启用并指出相互冲突的行。
3. 所选互认项目停用或来源不可用时，平台拒绝新增、修改为该项目或重新启用相关对照。
4. 当前互认项目尚未对照且同步只返回一个院内项目时，平台预填本院项目名称和编码并标记“待补价格”，不自动保存。
5. 已有对照与同步本院项目编码一致时，平台保持现有数据不变，并显示“对照一致”。
6. 已有对照与同步本院项目编码不一致时，平台保留当前对照并显示当前编码、同步编码和“对照不一致”，等待管理员人工选择。
7. 本院项目编码相同但名称不同时，平台显示“名称不一致”的普通提示，不将其作为编码冲突，也不自动覆盖已保存名称。
8. 来源协同系统对同一标准项目返回多个已启用院内项目编码时，平台显示“来源存在多个对照”并列出全部候选，不自动预填其中任意一个；管理员选择一个后再填写价格并保存。
9. 同步取得的本院项目编码已经被互认平台用于另一个启用对照时，平台将相互涉及的行标记为冲突，管理员必须先解除或修改原对照。
10. 来源对照的标准项目尚未进入当前互认项目范围时，平台跳过该来源对照，不创建互认项目、对照或表格新行，并在同步汇总中提示跳过数量。
11. 互认平台已有启用对照但来源协同系统当前没有对应启用对照时，平台提示“来源系统当前未启用此对照”，不自动停用、删除或清空现有对照。
12. 一个协同系统调用失败时，平台保留另一个协同系统已经成功取得的结果，明确提示失败来源；失败不得解释为没有对照，也不得清空页面已有数据。
13. 页面存在尚未保存的人工编辑时，再次同步保留人工编辑；同步编码不同则显示差异，不直接覆盖。
14. “保存全部”中部分行校验失败时，其他互不冲突且校验通过的行继续保存；彼此违反一对一关系的全部冲突行都不保存，平台不得任意保留其中一条。
15. 平台管理员发现异常对照时，可以按权限停用，但不代替医院修改日常对码内容或价格。
16. 历史对码错误已经影响报告时，不通过修改对照重写报告，医院应对来源报告执行更正或作废。

#### 业务规则

1. 项目编码对照归属于确定的医院和院区，医院管理员不得跨越当前登录范围维护。
2. 启用对照在同一医院、院区内实行一对一：一个院内项目同时只能对照一个互认项目，一个互认项目同时也只能对照一个院内项目。
3. 不同医院、院区分别维护，不要求使用相同的院内项目编码、名称或价格。
4. 对照直接保存院内项目编码、名称和当前价格，不依赖平台内独立的院内项目目录。
5. 医院、院区和院内项目编码创建后不可修改；需要改变上述身份时应新建对照并停用原对照。
6. 院内项目名称、互认项目、当前价格和备注允许修改，修改只影响后续业务。
7. 当前价格单位为人民币元，必填、不得小于零且最多保留两位小数；零是明确维护的有效价格，负数或超过两位小数的价格无效，平台不得静默四舍五入。
8. 缺少价格或价格无效的对照不得保存为启用状态，也不参与报告上传、候选查询或预计节省金额计算。
9. 新建对照校验成功后默认启用，不经过平台逐条审批。
10. 项目编码对照只保留当前价格，不建立独立价格版本或价格变更历史；框架已有创建、修改信息记录最后一次维护。
11. 价格调整只影响之后成功保存的采纳决定，已经形成的历史预计节省金额不按最新价格重算。
12. 同步操作只获取检验协同和检查协同当前已启用的对照；检验项目从检验协同获取，检查项目从检查协同获取。
13. 页面只提供一个“同步已有对照”操作，同时处理检验和检查项目；每次同步只处理当前医院、院区，不跨组织混合数据。
14. 同步结果只用于当前页面预填和比对，不创建待确认记录，不自动新增、修改、保存或启用项目编码对照。
15. 标准项目编码用于定位互认项目，本院项目编码用于判断对照一致性；项目名称只用于展示和人工核对，不作为对照身份。
16. 对照一致使用绿色提示；编码不一致、来源存在多个对照和编码占用冲突使用红色警示；名称不一致和来源当前未启用使用普通提示。所有状态必须同时使用图标和文字，不得只依赖红色或绿色表达。
17. 单行保存和“保存全部”都必须由管理员明确触发，页面不得自动保存。
18. “保存全部”按行处理并返回结果；失败行不回滚其他互不冲突的成功行，相互冲突的行全部失败。
19. 同步操作本身不建立独立同步记录、同步历史或回滚功能，只展示本次成功、失败、一致、冲突和跳过数量汇总。
20. 对照不物理删除；停用阻止后续报告上传和新的候选查询，不改变已接收报告保存的互认项目关系。
21. 平台管理员可以跨机构查看和异常停用，但医院负责本院日常对码、价格及正确性。

#### 关键属性

| 属性 | 说明 |
| --- | --- |
| 医院、院区 | 对照的数据归属，来自创建时的可信组织范围，创建后不可修改。 |
| 院内项目编码 | 医院院区本地业务系统使用的项目编码，创建后不可修改。 |
| 院内项目名称 | 医院项目名称，允许修改且只影响后续上传。 |
| 互认项目 | 当前院内项目对应的互认项目，允许修改且只影响后续上传和解析。 |
| 当前价格 | 当前医院、院区对该院内项目维护的人民币元价格，最多两位小数；零为有效值。 |
| 可互认时间 | 来自互认项目的只读信息，不在编码对照页面修改。 |
| 启停状态 | 启用或停用；新增后默认启用。 |
| 备注 | 对照维护的补充说明，可选。 |
| 同步来源 | 检验项目来自检验协同，检查项目来自检查协同；仅用于本次页面核对。 |

| 比对状态 | 待补价格、对照一致、对照不一致、名称不一致、来源存在多个对照、来源当前未启用或编码占用冲突等页面状态。 |
| 创建及修改信息 | 使用平台框架已有创建人、创建时间、修改人和修改时间，不形成独立价格或同步历史。 |

### F03 报告采集与生命周期

#### F03.1 公共报告要求与生命周期

##### 参与者

| 参与者 | 职责 |
| --- | --- |
| 医院源系统 | 在报告首次审核完成、修订后再次审核或作废时形成明确业务事件。 |
| 医院侧采集服务 | 首次审核和修订后重新审核均提交当前完整报告；报告失效时调用独立作废能力；处理失败和结果未知时按原请求重试。 |
| 互认平台 | 根据报告业务标识和源端报告修改时间自行判断创建首个版本、历史重传、追加版本、顺序冲突或作废，保存报告及版本关系并同步返回最终处理结果。 |
| 平台权限体系 | 校验科室、医生的存在性和医院院区归属，并提供当次名称。 |
| 医院管理员 | 查看本医院及有权院区上传报告的完整内容、历史版本和对应 PDF。 |
| 平台管理员 | 按现有数据权限查看授权范围内报告的完整内容、历史版本和对应 PDF。 |

##### 需求背景

平台需要持续接收上线后新产生及修订后重新审核的检查、检验报告，保持来源报告的结构化内容和原始 PDF。医院不需要理解平台版本概念，也不提交新增、更正状态、平台报告 ID、组合报告业务标识、医院版本号或版本变更原因；平台通过相同的完整报告提交能力自行形成首个或后续完整版本。报告失效使用独立作废能力。平台还需为医院管理员和平台管理员提供受数据权限控制的只读历史版本查看，使报告修订、责任人员、来源备注和 PDF 能够追溯。

##### 前置条件

1. 完整报告已经完成医院内部审核；作废已经由医院源系统明确声明。
2. 报告首次完整提交时，至少包含一个能够通过当前有效项目编码对照关联到当前启用且来源有效互认项目的项目明细；报告已经存在时，后续完整版本即使不再包含当前有效互认项目也允许提交并替代旧版本。
3. 报告携带有效的跨院患者标识、必填人口学信息、来源就诊标识及规定的报告公共信息。
4. 报告涉及的平台科室 ID、平台医生 ID 已在当前调用医院和院区范围内存在。
5. 完整报告提交同时提供来源报告单号、完整结构化报告、源端报告修改时间及 PDF 文件流；上传请求可以携带 PDF 文件名，文件名缺失或无效时由平台使用“报告单号.pdf”作为安全下载名称。
6. 作废请求只提供来源报告单号、作废时间和作废原因；医院、院区来自可信调用身份，报告类型由所调用的检验或检查作废能力确定。

##### 后置条件

1. 报告不存在时，完整提交成功后保存当前有效报告及首个完整版本，平台生成内部版本序号并记录实际接收时间。
2. 报告当前有效且源端报告修改时间晚于当前版本时，保存完整且不可变的新版本及版本关系，原版本停止参与候选查询、引用详情和新的引用。
3. 作废成功后保存作废时间和原因，不生成新的内容版本；报告停止参与候选查询、引用详情和新的引用，但报告及历史版本不被物理删除。
4. 任一校验或保存步骤失败时，本次报告变更不产生部分业务数据。
5. 平台通过现有框架同步返回成功或直接抛出描述事实的业务异常；需求阶段不定义错误代码、异常响应 DTO 或传输格式。
6. 有权限的医院管理员和平台管理员可以在管理端报告详情中只读查看全部版本并下载各版本 PDF，医院 HIS 仍只能取得当前有效版本。

##### 主事件流

1. 医院源系统首次审核或修订后重新审核报告时，医院侧采集服务调用对应报告类型的完整报告提交能力；报告失效时调用独立作废能力。
2. 平台使用可信调用身份中的医院和院区、所调用能力确定的报告类型以及医院提供的来源报告单号组合报告业务标识。
3. 平台校验调用医院院区、患者身份、来源就诊、平台科室医生归属、报告公共字段和项目编码对照。
4. 完整报告提交时，平台将结构化报告和 PDF 文件流作为一个完整单元校验，保存上传请求携带或平台回退生成的 PDF 下载文件名；首次创建报告时核对至少一个项目明细已有效对码，已有报告的后续版本不重复使用该条件拒绝来源当前完整内容。
5. 平台先在全部历史版本中查询相同源端报告修改时间；已经存在时按历史提交重传处理，未命中时再根据报告是否存在、当前是否有效及修改时间顺序创建首个版本或追加新版本。作废则根据报告是否存在、生命周期状态、作废时间和原因处理。
6. 平台保存报告变更后同步返回最终成功结果；只有业务数据已经完整保存时才能返回成功。

##### 备选流

1. 全部历史版本中已经存在相同源端报告修改时间时，按同一次完整报告提交重传返回幂等成功，不生成新版本，也不因该版本已被替代或报告后来作废而改变结果。
2. 未命中历史版本且报告不存在时形成首个版本；报告当前有效且修改时间晚于当前版本时形成新版本；修改时间早于或等于当前版本时拒绝为过期或顺序冲突。
3. 报告已经作废时，新的完整报告提交失败，不允许通过再次提交或历史版本恢复。
4. 首次作废时，作废时间不得早于当前版本的源端报告修改时间，时间相等允许处理；报告已作废且作废时间和原因均一致时幂等成功，任一不同则返回作废信息冲突。
5. 患者证件已存在但姓名、性别或出生日期不一致时返回患者身份信息冲突，不覆盖患者资料，也不创建第二个患者。
6. 首次提交没有任何项目明细能够完成有效对码时拒绝接收整份报告；报告已经存在时，后续完整版本即使没有当前有效对码也必须保存并替代旧版本，但不形成候选。
7. 任一平台科室或医生 ID 不存在或跨越当前调用医院、院区时，整次请求失败且不保存业务数据。
8. 结构化内容、PDF 或任一必填内容校验失败时，整份报告失败，不先保存其中一部分。
9. 调用超时或医院侧未取得明确结果时，医院侧原样提交相同完整报告及源端报告修改时间，平台按历史版本和当前状态执行幂等、冲突或过期判断；作废因原报告不存在失败时，医院确认原报告提交成功后重试作废。

##### 业务规则

1. 检验报告和检查报告分别提供完整报告提交能力和独立作废能力，请求中不设置新增、更正或作废操作类型。
2. 每次请求只处理一份报告，不将多份报告组成共同成功或共同失败的业务批次；医院侧可以并发提交多份独立报告。
3. 报告业务标识由医院、院区、报告类型和报告单号共同组成；不同报告必须使用不同业务标识，平台不按患者、就诊、项目、报告内容或 PDF 推断报告身份。
4. 平台根据报告是否存在和源端报告修改时间自行判断创建首个版本、历史重传、追加新版本或顺序冲突，不要求医院理解或提交平台版本状态。
5. 完整报告提交不支持局部字段修改，不要求更正原因或版本变更原因；检查和检验报告均使用来源报告已有的备注字段保存来源备注。
6. 作废不重复提交报告内容和 PDF，只改变报告生命周期状态，不形成内容版本；MVP 不建立只有作废信息、没有内容版本的占位报告。
7. 首次完整提交和每次有效后续完整提交分别形成完整且不可变的报告版本；平台保留原版本和新版本关系，旧版本责任人员及其他历史内容不得被新版本覆盖。
8. 每次完整报告提交必须提供源端报告修改时间；同一报告的每次实际修订必须严格递增，相同时间只表示同一次完整报告提交重传。具体传输格式应保留足以满足严格递增要求的时间精度，报告时间和平台接收时间均不能替代源端报告修改时间。
9. 报告公共时间包括必填的申请时间、报告时间，以及源系统存在时应提供的审核时间；平台接收时间不作为来源报告业务时间。
10. 报告时间是计算可互认时间的起点。
11. 报告随附来源患者和就诊信息，平台不要求医院预先上传独立挂号或就诊记录。
12. 来源就诊由医院、院区、就诊类型和院内就诊流水号共同识别；就诊类型和稳定且不循环复用的院内就诊流水号必填。
13. 就诊类型使用门诊、急诊、住院、体检和其他五类固定值，不接受未知；“其他”只用于确实无法归入前四类的特殊就诊类型，不得作为来源字段缺失时的默认值。住院号、病区、病房和床位在住院来源系统存在时应提供，但不参与患者或就诊自动匹配。
14. 患者姓名、性别代码、出生日期、证件类型和证件号码必填。相同证件下姓名、性别或出生日期冲突时不得覆盖既有患者信息。
15. 患者联系电话和报告时年龄在源系统存在时应提供，只用于授权展示和人工核对，不参与患者匹配；联系电话默认脱敏展示。
16. 报告上传只接收平台科室和医生 ID，不接收院内科室编码、医生工号或调用方自行填写的名称。
17. 申请科室、申请医生、执行科室、报告科室、报告医生、审核医生及报告类型要求的检验人或检查医生，按各自规则保存平台 ID 和当次查询名称。
18. ID 存在且归属正确但主体停用时允许提交真实报告；平台不校验医生当前所属科室与报告科室一致。
19. 科室或医生以后改名时，已有报告版本继续展示保存时名称。
20. 一份报告首次提交时至少一个项目明细关联到当前启用且来源有效的互认项目才创建报告并保存全部内容；已有报告的后续完整版本无论是否仍包含有效互认项目都必须保存，只有当前版本中保存了有效互认项目关系的明细能够形成候选。
21. 项目对照关系在报告接收时解析并随报告明细保存；后续对照修改或停用不重写已有报告关系。
22. 来源保密标识只按来源值保存，不驱动敏感等级、患者授权、上传审批或候选过滤。需要专项授权才能共享的报告暂不上传。
23. 平台不采集来源医嘱优先级、院内报告过程状态、传输批次号、上传状态、校验标志或调用方事件标识。
24. 平台按照版本成功形成顺序生成内部版本序号，不要求医院提供版本号，也不解析或统一医院源系统自己的版本规则。
25. 平台不比较完整报告内容，不计算或要求医院提供 PDF 文件摘要；重传、冲突和版本顺序只按报告业务标识、全部历史版本、生命周期状态及源端报告修改时间判断。
26. 平台以文件流接收 PDF，优先保存上传请求携带的 PDF 文件名并随版本用于下载；文件名缺失或无效时使用安全处理后的“报告单号.pdf”。文件名不从 PDF 内容或元数据推断，不参与报告身份、版本或幂等判断，平台内部使用独立文件标识保存 PDF。
27. 报告更正或作废立即限制旧版本继续参与候选查询、引用详情和新的引用，但不否定医院稍后提交的既有互认处理或已发生引用事实。
28. 平台不因报告更正或作废建设下游主动推送、推送记录或恢复处理。
29. 管理端报告详情提供只读历史版本列表、完整版本详情和各版本 PDF 下载，不建设独立版本管理菜单，不展示不存在于来源报告中的更正原因或版本变更原因，也不提供自动差异比较、修改、删除、恢复、重新设为当前版本或重新启用。
30. 医院管理员默认可以查看本医院及有权院区上传报告的全部历史版本、完整内容和 PDF，不新增独立报告查看权限；平台管理员按现有数据权限查看授权范围，其他医院不得查看来源医院的历史版本。
31. 医院 HIS 在线业务接口只提供当前有效版本，不开放历史版本查询或下载。

#### F03.2 检验报告专项要求

##### 参与者

医院 LIS 或其他检验报告来源系统、医院侧采集服务、互认平台及报告涉及的平台科室和医生。

##### 需求背景

检验报告以一份报告单和一个标本为单位，可以包含普通检验结果、细菌鉴定结果和药敏结果。平台需要完整保留最终报告内容，同时只将完成有效项目对码的普通检验结果用于互认候选。

##### 前置条件

1. 满足 F03.1 的公共前置条件。
2. 报告提供院内标本号、标本类型编码、标本类型名称和检测完成时间。
3. 报告至少包含一条普通检验结果；首次创建报告时至少一条普通结果能够通过有效项目编码对照关联互认项目，已有报告的后续完整版本不受此条件限制。
4. 每条普通结果提供院内项目编码、名称、完整来源结果文本、受控结果类型和唯一展示序号。

##### 后置条件

平台保存一份与单一标本关联的完整检验报告、全部普通结果、可选细菌鉴定结果和药敏结果；已对码普通结果可以形成候选，未对码普通结果及补充结果只用于保持报告完整、展示和追溯。

##### 主事件流

1. 平台校验检验报告公共信息、标本信息和检验时间线。
2. 平台逐条校验普通检验结果，按来源医院、院区和院内项目编码解析当前有效对照。
3. 平台保存普通结果来源原文、结果类型、展示顺序和源系统实际提供的辅助信息。
4. 报告包含细菌鉴定结果时，平台保存最终鉴定结论及相关来源信息。
5. 报告包含药敏结果时，平台校验其与细菌鉴定结果的明确关联并保存最终药敏结论及量值。
6. 全部结构化内容与 PDF 校验通过后，平台按 F03.1 保存报告变更。

##### 备选流

1. 报告同时包含已对码和未对码普通结果时，平台完整接收报告，仅已对码结果参与候选。
2. 普通结果、细菌结果或药敏结果的来源明细标识缺失时，如源系统确实不存在则允许为空；提供时在相应报告版本范围内不得重复。
3. 培养未发现细菌时，仍应提交一条细菌鉴定结果表达未检出及来源结论，不要求伪造菌种编码或名称。
4. 单位、参考范围、LOINC、检测方法、仪器、收费代码等应填信息在源系统确实不存在或不适用时允许为空，不得由平台推断或填充占位值。
5. 结果展示序号缺失或在规定范围内重复时，平台拒绝报告。

##### 业务规则

1. 一份检验报告只对应一个标本；多个标本分别形成不同报告。
2. 标本采集时间、送检时间和检验科接收时间在源系统存在时应提供，检测完成时间必填；不采集上机、离心和培养过程节点。
3. 来源报告名称必填；报告类别编码、名称和报告备注在源系统存在时应提供，只用于展示、筛选和追溯。
4. 报告整体异常标识在源系统存在时应提供，不替代结果明细异常标志，也不参与互认资格判断。
5. 来源医嘱流水号在源系统存在时应提供，只用于追溯，不参与报告身份、患者关联和互认判断；不保存报告级单一医嘱项目代码。
6. 普通结果完整保存来源最终结果文本，并使用受控结果类型区分数值型、定性型和文本型；平台不重复采集独立定量、定性字段。
7. 平台不采集或推断统一检验结果代码，不解析、换算或重新判定来源结果。
8. LOINC 在源 LIS 已维护时应提供，但不替代项目编码对照，也不由平台根据名称推断。
9. 单位、参考范围和检测方法按来源文本保存；平台不统一单位、不拆分参考上下限、不换算或重算参考范围。
10. 普通结果可以分别提供来源仪器编号和名称；平台不维护仪器目录，仪器不参与候选资格判断。
11. 每条普通结果的展示序号必填，在同一报告版本的普通结果内不得重复；平台不依赖接口数组或数据库顺序。
12. 来源检验收费项目编码和医保收费项目编码在源系统已维护时应提供，但不用于报告采集阶段的金额计算。
13. 异常标志按来源受控值保存，危急值标志按来源判断保存；平台不重新计算，也不因异常或危急值标志排除候选。
14. 细菌鉴定和药敏结果是检验报告补充结果，不独立进行互认项目对码。
15. 检出具体菌种时来源菌种名称必填，来源菌种编码按源系统情况提供；未检出时保存明确检测结论和来源文字。
16. 菌落计数、培养基、培养时间、培养条件和发现方式按源系统实际内容提供并保存，平台不标准化或重建培养过程。
17. 细菌检测结论必填；详细描述、仪器、试验板信息按源系统情况提供，不据此重新判定临床结果。
18. 药敏结果必须明确关联细菌鉴定结果，提供受试药物名称和来源结论文字；来源代码按源系统情况提供。
19. 纸片含药量、MIC、抑菌环直径和参考值按包含单位及比较符号的来源文本保存，平台不拆分、换算或重新判读。
20. 药敏展示序号必填，在同一报告版本、同一细菌鉴定结果下不得重复；检测方法和试验板序号按来源情况提供。药敏结果不重复保存试验板名称，也不使用试验板序号代替与细菌鉴定结果的明确关联。
21. 报告级检验人必填；普通结果、细菌结果和药敏结果的检测人及明细审核人在源系统存在且能够关联平台医生时应提供，缺失不阻止报告接收。

##### 关键属性

| 属性组 | 关键属性 |
| --- | --- |
| 报告信息 | 来源报告名称、报告类别编码和名称、报告备注、整体异常标识、来源医嘱流水号。 |
| 标本信息 | 院内标本号、标本类型编码、标本类型名称。 |
| 检验时间线 | 标本采集时间、送检时间、检验科接收时间、检测完成时间。 |
| 普通结果 | 来源明细标识、院内项目编码和名称、来源结果文本、结果类型、LOINC、单位、参考范围、检测方法、仪器、展示序号、收费代码、异常标志、危急值标志、明细责任人员。 |
| 细菌鉴定 | 来源明细标识、检出状态、菌种编码和名称、菌落计数、培养信息、检测结论、详细描述、仪器、试验板、明细责任人员。 |
| 药敏结果 | 来源明细标识、关联细菌、受试药物、药敏代码、结论、抗药结果代码、纸片含药量、MIC、抑菌环直径、参考值、展示序号、检测方法、试验板序号、明细责任人员。 |

#### F03.3 检查报告专项要求

##### 参与者

医院 PACS 或其他检查报告来源系统、医院侧采集服务、互认平台、影像服务及报告涉及的平台科室和医生。

##### 需求背景

检查报告以一份来源报告为完整业务对象，可以包含一个或多个检查项目明细。项目、部位属于明细，检查所见、检查结论、PDF 和影像调阅入口属于整份报告，联合报告不因项目对码被拆成多份报告。

##### 前置条件

1. 满足 F03.1 的公共前置条件。
2. 报告提供一个或多个检查项目明细；首次创建报告时至少一个明细能够通过有效项目编码对照关联互认项目，已有报告的后续完整版本不受此条件限制。
3. 每个项目明细提供院内检查项目编码和名称；存在明确检查部位时提供结构化部位集合。
4. 报告提供检查所见、检查结论、来源临床诊断名称、实际检查时间和检查医生平台 ID。

##### 后置条件

平台保存完整检查报告、全部项目明细及其部位集合、报告级临床内容、PDF、来源影像状态和按规则提供的影像调阅地址；已对码项目形成候选，未对码项目只用于报告完整展示和追溯。

##### 主事件流

1. 平台校验检查报告公共信息、实际检查时间、检查医生和报告级临床内容。
2. 平台逐个检查项目明细解析当前有效编码对照，并保持项目与其部位集合的明确归属。
3. 平台保存整份报告的检查所见、检查结论、来源诊断、病情描述、检查目的、检查方法及设备信息。
4. 平台按来源影像状态校验影像调阅地址的一致性。
5. 全部结构化内容、PDF 和按规则提供的影像信息校验通过后，平台按 F03.1 保存报告变更。

##### 备选流

1. 联合检查报告同时包含已对码和未对码项目时完整接收，仅已对码项目形成候选。
2. 项目没有明确检查部位时部位集合允许为空；存在部位时部位名称必填，来源部位编码按源系统情况提供。
3. 特殊检查确实没有检查所见时，来源系统应明确提供“无”等来源表达，平台不自动补写。
4. 来源影像状态为有影像但没有跨院可用地址时仍可接收报告，并表达为存在影像但暂不可调阅。
5. 来源影像状态为无影像时调阅地址必须为空；状态为未知时地址可以有或无。

##### 业务规则

1. 一份检查报告可以包含一个或多个项目明细，各明细分别解析互认项目。
2. 检查项目明细不采集具有业务含义的展示序号，平台采用稳定、可重复的方式展示，来源版式和临床阅读顺序以 PDF 为准。
3. 检查部位归属于具体检查项目明细，不以分隔文本笼统归属于整份报告。
4. 每个部位名称必填，来源部位编码在源系统存在时应提供；平台不统一或推断部位编码。
5. 检查所见和检查结论属于报告级必填完整原文，不拆分或重复保存到项目明细，不由平台整理、推断或改写。
6. 平台不定义通用检查结果代码、定性结果或定量结果字段，不从所见或结论中抽取、换算结构化指标。
7. 来源检查类型编码和名称在源系统存在时应提供，只用于展示、筛选和追溯，不关联标准项目分类或决定互认资格。
8. 来源检查设备编号和名称、检查方法在源系统存在时应提供，均为报告级信息，不参与项目对码或候选资格判断。
9. 来源临床诊断名称必填，诊断编码按源系统情况提供；平台不统一诊断编码，不从检查结论反推诊断。
10. 病情描述和检查目的在源系统存在时应提供，分别保存，不合并或自动生成，也不参与互认资格判断。
11. 实际检查时间必填，不采集预约时间，也不拆分检查开始和完成时间。
12. 检查医生平台 ID 必填，可以与报告医生或审核医生为同一人员。
13. 一份检查报告最多保存一个 HTTPS 影像调阅地址。平台不接收、代理、缓存或长期保存 DICOM 文件。
14. 来源影像状态使用有影像、无影像或未知；平台不根据调阅地址是否为空反推来源影像状态。
15. 影像地址缺失不影响结构化报告和 PDF 的互认资格，报告作废后不再返回原地址。
16. 平台不采集 PACS 影像号、检查实例 UID、序列 UID 等影像技术标识，也不自行拼接影像调阅地址。
17. 来源检查报告整体异常标识在源系统存在时应提供，只用于报告列表提示、候选快速提示和人工核对；平台不根据检查所见、检查结论或项目内容自行推断，也不因异常标识排除互认。
18. 来源检查报告备注在源系统存在时应提供，不存在时允许为空；备注随报告版本保存，仅用于报告展示、补充临床说明和问题追溯，不参与报告接收、项目互认资格、结果异常或版本顺序判断，也不替代作废原因。

| 属性组 | 关键属性 |
| --- | --- |
| 检查项目明细 | 院内项目编码、院内项目名称、关联互认项目及结构化检查部位集合。 |
| 检查部位 | 所属项目、来源部位编码、部位名称。 |
| 报告内容 | 检查所见、检查结论、来源整体异常标识、来源报告备注。 |
| 临床背景 | 来源临床诊断编码和名称、病情描述、检查目的。 |
| 检查信息 | 来源检查类型编码和名称、实际检查时间、检查方法、设备编号和名称、检查医生。 |
| 影像信息 | 来源影像状态、单个 HTTPS 影像调阅地址。 |

### F04 互认候选查询

#### 参与者

| 参与者 | 职责 |
| --- | --- |
| 医院 HIS | 在患者接诊或开单过程中提交患者身份、本次来源就诊和一个或多个拟开院内项目，接收符合条件的候选结果。 |
| 互认平台 | 整批校验患者和全部拟开项目，选择每个互认项目的最近有效报告，生成候选提供组及候选项目并形成提醒统计。 |
| 医生 | 在医院 HIS 中查看候选结构化内容、PDF 或影像入口并作出临床决定。 |

#### 需求背景

医院 HIS 在拟开检查或检验项目时，需要查询同一患者是否存在仍可使用的跨机构结果。一次查询可能包含多个院内项目，平台需要先保证全部项目配置有效，再去除重复输入并只返回实际命中的候选。非空结果必须作为一个候选提供组保存，以便后续整组处理和项目级追溯；全部项目配置正确但没有符合条件的报告属于正常空结果。

#### 前置条件

1. 调用方能够从可信身份上下文确定当前接收医院和接收院区。
2. 查询提供有效的患者证件类型和证件号码，以及本次来源就诊类型和院内就诊流水号。
3. 查询至少包含一个拟开院内项目，每个项目明确检查或检验类型，并提供当前医院、院区使用的院内项目编码。
4. 本次全部拟开院内项目均存在当前有效对照，其对应互认项目当前可用；任一项目未对码、对照停用或互认项目不可用时整次查询失败。

#### 后置条件

1. 全部项目配置校验通过后只返回实际命中的候选；没有任何符合条件的报告时返回空候选集合且不创建候选提供组。
2. 非空查询结果生成一个新的候选提供组 ID，每个实际返回项目生成新的候选项目 ID；每个互认项目最多返回一份报告的当前有效内容。
3. 同一联合报告命中多个项目时只返回一份报告公共信息，各项目分别形成候选项目，但共同属于本次候选提供组。
4. 平台成功生成候选提供组后，按组内每个候选项目形成一次提醒统计；无候选或整次查询失败不形成提醒。医院未收到响应不撤销已经形成的提醒。
5. 查询本身不形成互认处理结果、引用结果或调阅状态。

#### 主事件流

1. 医院 HIS 提交患者身份、本次来源就诊和一个或多个拟开院内项目。
2. 平台校验调用医院院区、患者身份、来源就诊和项目输入。
3. 平台按当前医院、院区、项目类型和院内项目编码整批解析当前有效项目编码对照；任一项目无法解析为当前可用互认项目时整次失败，并指出相关院内项目编码。
4. 同一次查询重复提供相同院内项目时只处理一次；同一医院、院区内不同院内项目不得通过启用对照解析到同一个互认项目。
5. 平台针对每个去重互认项目筛选报告：报告版本当前有效、报告对应互认项目当前启用且来源有效、检查或检验时间不晚于查询时点，并处于当前可互认时间内。
6. 平台按本院报告候选开关和本院报告排除时长处理来源医院与接收医院相同的报告。
7. 平台选择检查或检验时间最晚的一份报告；时间相同时选择报告时间较晚的一份；两者均相同时稳定选择同一份报告。
8. 平台按报告分组组织公共信息，生成本次候选提供组 ID，并为每个实际命中项目生成候选项目 ID；报告分组仅用于避免重复传输，不构成组下新的业务层级。
9. 平台成功生成并保存非空候选提供组后返回候选并形成提醒；没有任何报告命中时返回空候选集合且不创建组。

#### 备选流

1. 任一拟开项目未对码、对照停用或对应互认项目不可用时，平台使用现有框架抛出描述事实的业务异常，整次查询失败，不生成组、不返回同批其他候选；需求阶段不定义错误代码或异常格式。
2. 患者不存在、没有满足时间和有效性规则的报告，或者报告均被本院候选规则排除时，不返回相应候选；没有任何候选时返回成功的空候选集合。
3. 查询输入、患者身份或调用归属校验失败时，整次查询失败，不形成提醒统计。
4. 一份报告已经更正时只使用新版本；报告已经作废时不参与候选选择。
5. 一份联合报告同时命中多个互认项目时，报告公共内容只组织一次，项目候选和处理边界仍相互独立。
6. 平台已经成功生成候选提供组后，即使医院 HIS 因网络超时未取得响应，也不撤销该组及提醒；医院重试作为新查询重新计算并生成新组、新项目 ID，不恢复或复用前一组。

#### 业务规则

1. 查询截止点使用平台收到本次查询的时间，医院 HIS 不需要额外提供挂号时间、入院时间或统一就诊时间。
2. 候选时间判断使用检查报告的实际检查时间或检验报告的检测完成时间；该时间不得晚于查询时点。
3. 可互认时间从报告时间开始计算，并使用互认项目查询时的当前正整数天配置；一天按连续二十四小时计算，经过时间小于或等于当前配置时满足时间条件，超过后不再满足。
4. 每个互认项目只返回最近一份有效报告，不返回其他较早独立报告或历史趋势。
5. 检查或检验时间相同时，报告时间是唯一业务选择条件。两者均相同时，不增加临床质量、机构级别或其他业务排序条件；在候选数据及相关配置未变化时必须稳定返回同一份报告，具体稳定排序方式在设计阶段确定。
6. 联合报告按完整报告返回，但只有本次查询命中的互认项目形成候选项目，未命中项目不得形成组内记录。
7. 同一次查询重复提供相同院内项目时，只形成一个候选和一次提醒，不重复返回或统计。
8. 本院报告候选开关为平台全局参数，默认关闭。关闭时来源医院与接收医院相同的报告不参与候选，不区分院区。
9. 开关开启后，本院报告排除时长使用另一个全局非负小时参数，默认四十八小时；配置为零表示不增加额外等待时间，负数无效。
10. 本院报告经过时间大于或等于排除时长，且小于或等于互认项目可互认时间时满足时间条件；两个边界均包含。
11. 排除时长可以等于或大于某些项目的可互认时间，不作为配置错误；大于时该项目不会返回本院报告。
12. 本院报告参数只影响后续候选查询，不删除报告或撤销既有处理、引用和统计事实。
13. 检验候选返回来源机构、报告名称、检查或检验时间、报告时间、报告识别信息、标本类型名称、本次命中互认项目对应的主要检验结果明细，以及平台 PDF 文件标识、下载入口和原始文件名；每条结果包含项目名称、来源结果原文、单位、参考范围、异常标志和危急值标志，不要求按来源报告中的业务序号返回。
14. 检验候选不返回用于来源追溯的标本类型编码和院内标本号。
15. 检查候选返回来源机构、报告名称、实际检查时间、报告时间、报告识别信息、命中项目的检查部位、整体异常标识、平台 PDF 文件标识、下载入口和原始文件名、来源影像状态及医院提供的影像入口。
16. 检查候选不直接返回篇幅较大的检查所见和检查结论；医生通过 PDF 或影像查看后决定是否采纳。
17. 候选中的异常和危急值仅表达来源医院判断，平台不重新计算，也不自动排除异常报告。
18. 提醒次数只表示平台成功提供候选，不表示医院 HIS 已显示弹窗或医生已经查看、采纳、拒绝或引用。
19. 候选响应不返回固定“互认超期时间”；平台按查询时点和互认项目当前可互认时间动态筛选。
20. 每次非空查询均生成新的候选提供组和候选项目 ID，不提供跨查询稳定候选引用、查询幂等键或旧组恢复能力；未反馈组不设有效期、过期状态或定时清理。
21. PDF 下载入口是与其他医院 HIS 接口相同的受认证平台接口地址，地址不携带 Bearer Token 或内部存储地址；医院使用标准 `Authorization` 请求头调用。平台返回 `application/pdf` 文件流并使用保存的文件名，不在候选 JSON 中返回 PDF Base64。
22. 候选 PDF 入口不设独立有效期或一次性状态。每次下载校验调用医院、院区、候选归属和报告版本有效性；报告形成后续版本或作废后停止提供旧版 PDF，医院已合法下载的数据不追回。

#### 关键属性

| 属性组 | 关键属性 |
| --- | --- |
| 调用归属 | 当前接收医院、接收院区，来自可信身份上下文。 |
| 患者与就诊 | 证件类型、证件号码、本次来源就诊类型、本次院内就诊流水号。 |
| 拟开项目 | 检查或检验类型、院内项目编码；解析并去重为互认项目。 |
| 候选提供组 | 平台生成的候选提供组 ID、候选提供时间、接收医院院区、患者、本次来源就诊和全部实际返回项目。 |
| 候选公共信息 | 来源医院及院区、来源报告名称、检查或检验时间、报告时间、报告识别信息、PDF 文件标识、下载入口和原始文件名。 |
| 候选项目 | 平台生成的候选项目 ID，绑定本次拟开院内项目、互认项目、候选报告版本和项目内容。 |
| 检验候选内容 | 标本类型名称及命中互认项目对应的主要普通检验结果明细。 |
| 检查候选内容 | 命中项目检查部位、整体异常标识、来源影像状态及影像入口。 |
| 候选集合 | 只包含符合条件的候选；没有符合条件的候选时为空集合。 |

### F05 互认处理结果

#### 参与者

| 参与者 | 职责 |
| --- | --- |
| 医生 | 查看候选后一次确认组内每个候选项目的采纳或不采纳决定，并在首次提交前核对决定内容。 |
| 医院 HIS | 按候选提供组完整提交全部候选项目决定、组级实际互认时间、决定科室和决定医生。 |
| 互认平台 | 整批校验并原子保存不可更改的项目级决定、不采纳原因和预计节省金额，维护对应统计事实。 |

#### 需求背景

平台只能记录医生明确作出的互认决定，不能从查询、调阅或医院后续行为推断采纳情况。一次候选提供组表达医生本轮需要共同确认的完整候选集合，医院必须一次完整、原子提交全部项目决定；首次成功保存后即成为不可更改的历史事实。

#### 前置条件

1. 医院 HIS 已取得候选查询返回的候选提供组 ID 和全部候选项目 ID。
2. 医生已经明确作出采纳或不采纳决定。
3. 请求在组级提供候选提供组 ID、精确到秒的互认时间、平台科室 ID 和平台医生 ID；项目数组完整提供该组全部候选项目 ID 及采纳或不采纳结果。
4. 不采纳时提供平台统一原因代码；原因为其他时提供补充说明。

#### 后置条件

1. 一次请求中的全部处理结果校验成功后共同保存；任一记录失败时整批不保存。
2. 候选提供组首次成功保存后，每个候选项目只保留该次不可更改的决定，不存在当前决定覆盖或决定版本。
3. 决定为采纳时形成采纳次数、来源医院被互认次数、报告使用关系、预计节省金额；该组首次成功保存处理结果的时间作为引用详情有效期起点。不采纳时形成不采纳次数和原因。
4. 完整请求相同的幂等重试不重复计数；相同组提交任何不同业务内容时返回处理结果冲突，不覆盖原决定。

#### 主事件流

1. 医院 HIS 提交候选提供组 ID、组级互认时间、决定科室和决定医生，以及完整覆盖该组全部候选项目的决定数组。
2. 平台先校验调用医院院区和候选提供组归属、项目数组是否完整且无重复或非法项目，再校验互认时间、决定内容及科室医生 ID 的存在性和归属。
3. 平台确认每个候选项目属于该组并能够定位相应报告版本和互认项目，但不因提交时报告后来更正或作废而拒绝医院明确反馈的既有处理事实。
4. 处理结果为不采纳时，平台校验统一原因代码及补充说明。
5. 处理结果为采纳时，平台校验接收医院、接收院区当前启用项目编码对照仍然指向候选对应的互认项目，并读取该对照的当前价格。
6. 平台按采纳决定成功保存时读取的接收医院、接收院区当前价格形成预计节省金额。
7. 全部记录校验通过后，平台在一个整体操作中保存全部不可更改决定及对应统计事实。
8. 平台返回整次请求成功。

#### 备选流

1. 任一记录校验失败时整批不保存，使用现有框架抛出描述事实的业务异常，不返回逐条成功结果；涉及具体项目时指出相关候选项目 ID，需求阶段不定义错误代码、异常 DTO 或传输格式。
2. 相同业务键重复提交完全相同的处理内容时返回幂等成功，不新增记录或重复统计。
3. 候选提供组已保存处理结果后再次提交不同互认时间、科室、医生、任一项目决定、不采纳原因或补充说明时，返回互认处理结果冲突，不更正、撤销、删除或覆盖首次决定。
4. 项目数组缺少组内项目、重复提供项目、夹带其他组项目或数量不一致时，整次失败且不保存任何项目。
5. 不采纳未提供原因、原因无效，或者原因为其他但缺少说明时，整批失败。
6. 任一科室或医生 ID 不存在或不属于当前调用医院、院区时，整批失败；ID 停用但存在且归属正确时允许提交。
7. 接口超时、失败或未取得明确结果时，医院 HIS 使用相同互认时间和原记录重新提交。
8. 候选返回后，接收医院、接收院区的对应启用对照已停用或已经改为另一个互认项目时，平台拒绝采纳该候选并要求医院 HIS 重新查询；只有价格发生变化时允许继续采纳并使用新价格。

#### 业务规则

1. 处理结果值域只包括采纳和不采纳，不要求提交未处理、未查看、暂未决定或关闭提醒状态；长期未反馈的候选提供组不设有效期、过期状态或自动清理。
2. 候选返回、结构化展示、PDF 或影像访问不自动形成处理结果。
3. 处理决定归属于候选提供组中的具体候选项目，不笼统归属于整份联合报告；组内项目可以分别采纳或不采纳。
4. 一次请求必须完整覆盖候选提供组全部项目，并整体校验、整体保存，不允许部分提交或逐项部分成功。
5. 互认时间是医生实际作出决定的时间，保存到秒；接口接收时间不得替代互认时间。
6. 确有新的诊疗决定时，医院重新查询生成新的候选提供组并提交新的整组决定，不复用原组形成第二次处理。
7. 平台科室和医生表示实际作出决定的主体，接口调用账号不得替代；采纳和不采纳均必须提供。
8. 平台分别校验科室和医生属于当前调用医院、院区，不校验医生当前所属科室与决定科室一致。
9. 科室和医生名称按提交时查询结果保存，名称不参与业务唯一键或幂等一致性判断。
10. 平台接收稍后提交的既有处理事实时，不比较互认时间与报告更正或作废时间。
11. 统一不采纳原因字典由平台内置并使用本功能规定的固定代码，不提供医院新增、修改或停用；代码 `6` 表示其他情形确需复查，使用时补充说明必填。
12. 处理结果为采纳时不得填写不采纳原因；平台不审查不采纳的临床理由，也不据此干涉医院继续开单或采取其他诊疗措施。
13. 采纳时按决定成功保存时接收医院、接收院区当前启用项目编码对照的价格形成预计节省金额，不使用来源医院对照价格，也不等待引用结果。
14. 对照关系已停用或已改为另一个互认项目时不得采纳旧候选；对照关系仍然有效且只有价格变化时，使用调整后的当前价格。
15. 平台只保存预计节省金额，不在处理记录中重复保存一份对照价格。
16. 相同采纳的幂等重试不因对照价格已经变化而重新取价或计算金额。
17. 首次决定保存后不得在采纳和不采纳之间更改，已经形成的预计节省金额不通过决定更正取消或重算。
18. 报告后续更正或作废不撤销或重算已经形成的预计节省金额。
19. 预计节省金额归属于接收医院、院区和决定科室，不在来源医院侧重复形成贡献金额。
20. 互认时间必须晚于或等于候选提供组生成时间且不得晚于平台收到本次请求的时间，均精确到秒并允许相等；MVP 不设置未来时间容差。
21. 平台首次成功保存候选提供组处理结果时记录该组引用详情有效期起算时间；相同完整请求的幂等重试不更新该时间。

### F06 获取引用详情

#### 参与者

| 参与者 | 职责 |
| --- | --- |
| 医院 HIS | 在医生采纳候选后请求写入本次病历所需的项目内容。 |
| 互认平台 | 校验调用归属、来源就诊、互认决定和候选版本有效性，返回项目级引用内容。 |

#### 需求背景

候选查询只用于医生判断，病历引用需要在采纳后通过独立能力取得受控内容。平台必须保证返回内容属于当前医院、本次就诊、已采纳项目和仍有效的报告版本。

#### 前置条件

1. 当前调用医院、院区能够从可信身份上下文确定。
2. 请求提供患者证件类型、证件号码、本次来源就诊类型和本次院内就诊流水号；医院和院区来自可信身份，不提交平台患者 ID、候选提供组 ID、候选项目 ID 或互认时间。
3. 本次就诊下至少存在一个已保存采纳决定的候选项目。
4. 平台在查询过程中逐项校验候选项目绑定的报告版本仍为当前有效版本。
5. 平台能够从现有系统参数系统读取合法的全平台统一引用详情有效时长。

#### 后置条件

1. 校验成功时返回该医院、院区、患者及本次就诊下仍可获取的全部已采纳候选项目内容及必要报告公共上下文，并携带候选提供组 ID 和候选项目 ID。
2. 获取引用详情不自动形成引用结果、引用次数或新的互认处理。
3. 校验失败时不返回受保护的报告引用内容。
4. 超出当前引用详情有效时长时不返回引用内容；有效期内允许在既有校验均通过时重复获取。

#### 主事件流

1. 医院 HIS 提交患者证件类型、证件号码、本次来源就诊类型和本次院内就诊流水号。
2. 平台使用当前医院、院区和请求信息严格匹配候选提供组，并校验患者身份、本次就诊和组归属一致。
3. 平台从现有系统参数系统读取当前全平台统一的引用详情有效时长，并校验参数存在且为合法的正整数分钟。
4. 平台以各候选提供组处理结果首次成功保存时间为起点分别计算经过时间，校验经过时间小于或等于当前有效时长。
5. 平台逐项校验决定为采纳、候选项目归属正确且绑定报告版本仍为当前有效版本；自然超过可互认时间不影响已经采纳项目获取详情。
6. 同一次就诊存在多个组且多个有效采纳绑定同一报告版本和互认项目时，只返回平台成功保存时间最近的一条采纳记录，较早事实和统计仍保留。
7. 平台返回全部仍有效项目的候选提供组 ID、候选项目 ID、项目内容、必要报告公共上下文、PDF 文件信息和适用的来源影像信息，供医院 HIS 写入本次病历。

#### 备选流

1. 未匹配到该医院、院区、患者及本次就诊下的采纳记录时拒绝返回，并只描述“未查询到该就诊的互认采纳记录”等平台能够确认的事实，不泄露其他患者记录。
2. 报告已经形成后续版本、作废，或者候选项目绑定的版本不再是当前有效版本时不返回该项目；全部相关项目均失效时拒绝返回。
3. 联合报告只采纳其中部分项目时，仅返回已采纳候选项目对应内容，不返回其他不采纳、未命中或属于其他候选项目的内容。
4. 引用详情有效时长参数不存在、为零、负数、非整数或系统参数服务读取失败时，平台拒绝返回并给出明确配置错误，不使用代码兜底值。
5. 各组独立判断有效期；只要存在有效项目即正常返回这些项目，不因同次就诊其他项目超期或失效整次失败。全部项目均不可返回时拒绝并列明平台实际确认的原因，不返回成功空集合或“可引用/不可引用”双数组。

#### 业务规则

1. 获取引用详情与候选查询、处理结果提交、引用结果提交相互独立。
2. 引用详情必须使用“当前医院 + 当前院区 + 患者证件类型 + 证件号码 + 就诊类型 + 就诊流水号”严格匹配候选提供组和不可更改的采纳决定。
3. 检验引用详情按当前互认项目返回相应检验结果，不细分为每条结果独立引用事实。
4. 检查所见和检查结论属于整份报告公共内容，可以随当前检查项目返回。
5. 必要报告公共上下文至少包括来源医疗机构、来源报告名称、检查或检验时间、报告时间、来源申请医生和来源审核医生。
6. 获取详情只表示平台提供了引用所需数据，不表示医院 HIS 已写入病历。
7. 引用详情再次返回平台 PDF 文件标识、下载入口和原始文件名；PDF 下载接口直接返回 `application/pdf` 文件流，不把文件转为 Base64。PDF 或影像访问不能替代获取引用详情，也不能形成引用结果。
8. 引用详情有效时长是全平台统一系统参数，所有医院、院区和互认项目使用同一值，不建立组织级覆盖、专用参数表或专用配置页面。
9. 参数值使用正整数分钟，默认七百二十分钟，即十二小时；不允许零、负数、非整数或永久有效。管理界面可以辅助显示小时，但参数值及校验统一使用分钟。
10. 每个候选提供组的有效期从平台首次成功保存该组完整处理结果的时间开始，不使用医院 HIS 提交的互认时间；该平台保存时间只用于引用授权，不改变采纳和统计的业务时间。
11. 相同完整请求的幂等重试不刷新有效期；同一次就诊存在多个候选提供组时，各组独立计算。
12. 每次请求读取当前参数值，不为采纳记录保存独立有效时长或截止时间；参数缩短或延长后立即按原起点影响既有采纳。
13. 有效期结束边界包含在允许范围内：经过时间小于或等于当前有效时长时允许，大于时拒绝。
14. 有效期内只要既有医院院区、患者、本次来源就诊、采纳决定和报告版本校验均通过，允许重复获取；已经提交引用结果也不提前关闭有效期。
15. 平台不建设一次性读取、读取后立即失效或消费状态；有效期只限制后续平台接口调用，不能控制医院已经合法取得并保存的数据。
16. 参数不存在、非法或参数服务失败时拒绝返回，不退化为永久有效，也不在互认平台代码中设置默认兜底。
17. PDF 下载入口本身不设置独立期限；医院在引用详情有效期内取得入口后，即使详情后来超期，只要调用医院院区、候选归属正确且报告版本仍有效，仍允许下载。报告形成后续版本或作废后停止提供旧版 PDF。
18. PDF 地址按照其他医院 HIS 业务接口相同的认证方式设计，地址不拼接 Bearer Token、用户名密码或内部存储地址；医院通过标准 `Authorization` 请求头调用。具体路由、字段名和地址生成方式由实现框架决定。
19. MVP 不为 PDF 下载建立独立业务记录、下载次数、下载状态或管理菜单，安全审计沿用现有框架接口访问日志，日志格式不在需求阶段固定。
20. 检查引用详情只原样返回医院提供的影像状态和外部调阅地址。平台不测试、代理、缓存或保证地址可用，不接收 DICOM；报告形成后续版本或作废后停止在后续响应中返回原地址，但无法撤回已经下发的外部地址。

#### 关键属性

| 属性组 | 关键属性 |
| --- | --- |
| 请求定位 | 当前医院院区、患者证件类型、证件号码、本次来源就诊类型和就诊流水号。 |
| 返回定位 | 候选提供组 ID 和候选项目 ID，供医院后续提交引用结果。 |
| 有效期依据 | 各候选提供组处理结果首次成功保存时间及请求时读取的全平台统一正整数分钟参数。 |
| 公共上下文 | 来源医疗机构、来源报告名称、检查或检验时间、报告时间、来源申请医生、来源审核医生。 |
| 检验引用内容 | 当前互认项目对应的检验结果及必要解释信息。 |
| 检查引用内容 | 当前互认项目、检查部位，以及整份报告的检查所见和检查结论。 |
| 文件内容 | PDF 文件标识、受认证下载入口、原始文件名，以及检查报告适用的来源影像状态和外部地址。 |

### F07 提交引用结果

#### 参与者

| 参与者 | 职责 |
| --- | --- |
| 医院 HIS | 在已采纳内容成功写入本次病历后，提交一条或多条实际引用事实。 |
| 互认平台 | 对候选提供组和本次全部实际引用项目执行整批校验、原子保存，不返回逐条部分结果。 |

#### 需求背景

互认采纳和病历引用是连续但独立的业务事实。平台只有在医院 HIS 明确确认已成功写入病历后才能记录引用，不得从引用详情获取、文件访问或未反馈状态推断引用。

#### 前置条件

1. 医院 HIS 已将相应互认内容成功写入本次病历。
2. 请求提供候选提供组 ID 和一个或多个实际引用项目；每项提供候选项目 ID、实际引用时间、引用科室 ID 和引用医生 ID，不重复提交本次来源就诊或互认时间。
3. 候选提供组存在完整互认处理结果，相关候选项目决定为采纳。
4. 全部引用科室和医生 ID 存在并属于当前调用医院、院区。

#### 后置条件

1. 一次请求中的全部引用项目校验成功后共同保存；任一项目失败时整次不保存，不返回逐条成功或失败结果。
2. 每个业务唯一键只形成一个引用事实，幂等重试不增加引用次数或重复形成报告使用关系。
3. 成功引用按实际引用时间计入引用统计，不再次增加采纳次数、来源医院被互认次数或预计节省金额。

#### 主事件流

1. 医院 HIS 提交一条或多条已经发生的引用结果。
2. 平台校验当前调用医院和院区与候选提供组归属一致，并从组及其处理结果取得本次来源就诊和互认时间。
3. 平台校验全部候选项目属于该组、决定为采纳，并校验每项引用科室和引用医生的存在性及归属。
4. 平台校验每项实际引用时间晚于或等于互认时间且不晚于本次请求接收时间，再按“候选提供组 ID + 候选项目 ID”检查是否已有引用结果及事实内容。
5. 全部项目校验通过后原子保存新引用事实；完全相同的既有事实按幂等处理。
6. 平台返回整次请求成功。

#### 备选流

1. 任一记录的科室或医生 ID 不存在或跨医院院区、候选项目不属于该组、决定不存在或为不采纳时，整次请求失败，整批不保存。
2. 任一实际引用时间早于互认时间或晚于平台收到本次请求的时间时，整次失败；MVP 不设置未来时间容差。
3. 相同业务键且实际引用时间、科室和医生一致时返回幂等成功。
4. 相同业务键但任一事实字段不同，返回内容冲突，不覆盖已有引用结果。
5. 医院修正后重新提交完整原请求；接口超时、失败或未取得明确结果时也使用完整原请求重试，已存在的相同事实按幂等处理。
6. 报告在实际引用之后发生更正或作废、且医院稍后提交引用结果时，平台不因提交时报告已失效而拒绝该项已经发生的引用事实。

#### 业务规则

1. 平台只接收已经引用的正向事实，不要求医院提交未引用或引用失败状态。
2. 获取引用详情、查看结构化结果、访问 PDF 或影像均不自动形成引用结果。
3. 引用粒度为候选报告版本中的具体互认项目，不继续细分到每条普通检验展示明细。
4. 同一候选提供组和候选项目最多形成一个引用事实，不要求医院生成额外幂等流水号。
5. 实际引用时间是医院成功写入病历的业务时间；接口接收时间不得替代。
6. 引用科室和引用医生是实际执行引用的主体，调用账号不得替代。
7. 平台分别校验引用科室和医生属于当前调用医院、院区，不校验医生当前所属科室与引用科室一致。
8. 科室或医生停用但仍存在且归属正确时，允许补交真实引用事实。
9. 报告更正或作废阻止继续获取原版本引用详情和发生新的引用，但平台接收引用结果时不比较实际引用时间与更正或作废时间，不拒绝医院明确反馈的既有引用事实。
10. 引用结果不设置独立提交期限，不受候选可互认时间或引用详情有效期限制，也不要求平台证明医院曾调用引用详情接口。
11. 引用结果首次保存后不可更正、撤销、删除、冲销或后台补改；引用只增加引用次数，不再次增加互认采纳、来源医院被互认次数或预计节省金额。
12. 请求不要求完整覆盖该组全部已采纳项目，未提交项目只表示平台本次未收到引用事实，不推断为未引用；但本次提交数组作为整体原子处理。
13. 同一次诊疗决定将同一候选项目写入多份院内文书仍只形成一个引用事实；新的诊疗决定必须重新查询、形成新组并重新提交互认处理。

#### 关键属性

| 属性 | 说明 |
| --- | --- |
| 候选提供组 | 候选提供组 ID，平台据此取得接收医院院区、本次来源就诊和互认时间。 |
| 候选项目 | 候选项目 ID，定位已采纳报告版本和具体互认项目。 |
| 实际引用时间 | 医院 HIS 成功写入本次病历的时间。 |
| 引用科室、引用医生 | 平台 ID 及提交时保存的名称。 |
| 整批处理结果 | 全部成功、全部幂等或整次失败，不提供逐条部分结果。 |

### F08 互认统计与分析

#### 参与者

| 参与者 | 职责 |
| --- | --- |
| 医院管理员 | 在本院及有权院区范围内查看接收侧互认使用汇总、来源侧被互认汇总及相应脱敏明细。 |
| 平台管理员 | 查看权限范围内的全县汇总、医院明细和业务下钻。 |
| 互认平台 | 按候选提供组、不可更改决定、引用事实、业务时间和权限范围计算统计。 |

#### 需求背景

平台需要同时反映候选提供、医生决定、病历引用、预计节省金额和来源医院报告贡献，并保证每项指标能够回到相应业务明细核对。统计用于业务管理和监管，不用于自动评价医生绩效或替代真实财务结算。

#### 前置条件

1. 当前用户已登录并具有对应统计页面及数据范围权限。
2. 查询提供日期范围，并可按允许的医院、院区、决定科室、决定医生或互认项目等条件筛选。
3. 平台已保存候选返回、当前有效互认决定、引用结果和采纳时按接收医院、院区对照价格形成的预计节省金额事实。

#### 后置条件

1. 平台返回当前权限和查询条件范围内的汇总、分类统计及可下钻明细。
2. 统计按各指标已确认的业务时间归入期间，包含医院稍后提交的真实处理或引用事实。
3. 患者姓名和证件号码在统计页面及明细中保持脱敏。
4. 总体统计和跨机构统计分别展示，跨机构作为总体子集，不重复累计。

#### 主事件流

1. 用户进入接收医院互认使用分析或来源医院被互认分析页面。
2. 平台依据登录身份确定可访问的医院、院区或县域数据范围。
3. 用户选择日期范围及其他允许的查询条件。
4. 平台按指标对应业务时间汇总提醒、采纳、不采纳、引用、预计节省金额或来源医院被互认次数。
5. 平台计算同期互认率、不采纳原因次数及占比，并按标准项目分类组织统计。
6. 平台同时提供总体口径和适用的跨机构子集口径。
7. 用户从汇总数字下钻查看对应脱敏业务明细。

#### 备选流

1. 提醒次数为零时，同期互认率不计算，不以零或百分之百代替。
2. 不采纳总次数为零时，各原因占比不计算。
3. 医院 HIS 稍后提交处理或引用结果时，重新查询原业务时间所属期间应包含新增事实。
4. 候选提供组未反馈时只保留提醒事实，不推断医生忽略、拒绝或采纳。
5. 查询时间与互认时间跨越统计边界导致短周期同期互认率超过百分之百时，按原始结果展示，不截断或强制封顶。
6. 医院管理员请求超出本院或有权院区的数据时，平台拒绝访问或将查询限制在授权范围内。

#### 业务规则

1. 提醒次数在平台成功生成非空候选提供组时形成，按候选提供时间归入统计期间；医院是否实际收到响应不改变已形成事实。
2. 同一次查询重复提供相同院内项目时只计一次提醒；联合报告命中多个不同互认项目时分别计数。
3. 无候选或平台整次查询失败时不计提醒；平台已生成候选组但响应传输超时仍计提醒，医院重试生成的新组再次计数，不在统计阶段猜测并合并网络重试。
4. 采纳次数、不采纳次数、来源医院被互认次数和预计节省金额按互认时间归入统计期间。
5. 引用次数按实际引用时间归入统计期间。
6. 接口接收时间只用于传输、安全和审计，不改变统计归属日期。
7. 每个候选项目的采纳分别计算采纳次数、来源医院被互认次数和预计节省金额；相同完整请求的幂等重试不重复计数。
8. 引用结果只增加引用次数，不再次增加采纳、来源医院被互认次数或预计节省金额；没有引用结果不撤销已经成立的采纳。
9. 同期互认率为统计范围内采纳次数除以提醒次数并乘以百分之百。未收到处理结果的提醒保留在分母中，但不记为不采纳。
10. 平台不建立提醒与采纳的一一对应流水，不另设“采纳次数除以采纳与不采纳之和”的比例指标。
11. 不采纳原因统计按平台统一原因代码汇总次数及占比，占比分母为当前权限和查询条件下的不采纳总次数。
12. 其他原因统一归入其他分类，补充说明只在脱敏明细及导出中展示，不按任意文字生成新分类。
13. 接收医院使用分析包含提醒、采纳、不采纳、引用、同期互认率和预计节省金额。
14. 医院管理员在接收侧互认使用分析中只能查看本院及有权院区的数据；平台管理员按权限查看全县汇总及医院明细。
15. 来源医院被互认分析在接收侧明确采纳时形成，不等待引用结果；来源医院只统计次数和明细，不统计贡献金额。
16. 医院管理员在来源侧被互认分析中只能查看本院提供报告形成的数据；其他医院管理员不得查看与本院无关的来源医院数据。
17. 本院报告候选开关开启后，本院报告形成的提醒、处理、引用和预计节省金额进入总体统计，本院报告被采纳也进入来源医院被互认总体次数。
18. 跨机构口径只包含来源医院与接收医院不同的记录，是总体统计的子集，不得与总体相加。
19. 同一医院不同院区之间的使用属于非跨机构，可以按来源院区和接收院区筛选或分组，但不形成独立跨院区核心指标。
20. 互认使用和来源医院被互认统计统一按标准项目目录中的检查或检验类型、类别、分组及具体互认项目筛选和汇总，不使用各医院来源报告分类进行横向比较。
21. 接收医院汇总支持医院、院区、决定科室和互认项目维度；决定医生只作为明细查询条件和展示内容，不形成互认率、金额或绩效排名。
22. 提醒、采纳、不采纳、引用和来源医院被互认汇总均应支持下钻到对应业务明细。
23. 预计节省金额随采纳明细展示，不另建重复的金额事实或金额明细。
24. 统计管理页面中的患者姓名和证件号码必须脱敏，不提供解除脱敏或查看完整患者身份的能力。
25. 统计通过用户选择的日期范围展示汇总、分类和下钻明细，不生成按日、小时或分钟的趋势图。
26. 现有提醒、采纳、不采纳和引用明细提供只读“查看候选组”入口，不新增独立菜单；组视图展示组 ID、候选时间、接收医院院区、脱敏患者、本次就诊、未反馈或已处理状态、决定主体及全部候选项目。
27. 接收医院管理员通过统计和候选组视图不得查看其他来源医院的完整结构化报告、PDF 或影像地址；来源医院管理员仍通过本院报告历史查看本院完整报告。

#### 关键属性

| 指标或维度 | 说明 |
| --- | --- |
| 提醒次数 | 成功返回去重互认项目候选的次数。 |
| 采纳次数 | 候选项目不可更改决定为采纳的次数。 |
| 不采纳次数 | 候选项目不可更改决定为不采纳的次数。 |
| 引用次数 | 医院 HIS 明确反馈成功写入病历的次数。 |
| 同期互认率 | 采纳次数除以提醒次数；提醒为零时不计算。 |
| 预计节省金额 | 当前有效采纳决定形成的金额合计，归属于接收医院、院区和决定科室。 |
| 来源医院被互认次数 | 来源报告被接收侧明确采纳的次数，不包含贡献金额。 |
| 不采纳原因 | 统一原因代码的次数、占比及脱敏明细。 |
| 业务时间 | 提醒按返回时间；处理及金额按互认时间；引用按实际引用时间。 |
| 统计范围 | 总体口径和来源医院不同于接收医院的跨机构子集口径。 |
| 分类维度 | 标准项目类型、类别、分组、互认项目，以及权限允许的医院、院区和决定科室。 |

### F09 互认统计导出

#### 参与者

| 参与者 | 职责 |
| --- | --- |
| 医院管理员 | 按权限导出本院及有权院区的接收侧互认使用汇总、来源侧被互认汇总及相应明细。 |
| 平台管理员 | 按权限导出全县或指定机构范围的数据。 |
| 互认平台 | 按当前查询条件、权限和脱敏规则生成 Excel 文件。 |

#### 需求背景

页面分页用于浏览，不能满足业务核对和线下汇总需求。平台需要在不扩大数据权限、不解除患者脱敏的前提下，导出当前查询条件下的全部匹配记录。

#### 前置条件

1. 用户具有对应统计页面和导出能力权限。
2. 用户已经在统计页面形成有效查询条件。
3. 查询条件处于当前用户可访问的数据范围内。

#### 后置条件

1. 平台生成一个 `.xlsx` 文件，包含当前查询条件和权限范围内的全部匹配记录。
2. 导出中的患者姓名和证件号码与页面保持相同脱敏规则。
3. 导出不改变任何互认、引用或统计业务事实。

#### 主事件流

1. 用户在相应统计汇总或明细页面设置查询条件并发起导出。
2. 平台重新校验用户权限和医院、院区数据范围。
3. 平台使用当前查询条件获取全部匹配记录，不使用页面当前页码和每页条数限制导出范围。
4. 平台按页面相同规则处理患者脱敏和指标口径。
5. 平台生成 Excel 文件供用户获取。

#### 备选流

1. 用户没有对应导出权限或请求超出数据范围时，平台拒绝导出。
2. 当前查询没有匹配记录时，平台提示“当前条件下无可导出数据”，不生成 Excel 文件，也不扩大查询范围补充其他记录。
3. 导出过程中权限或查询条件校验失败时，不生成可获取文件。

#### 业务规则

1. 当前版本只提供 Excel `.xlsx` 格式，不同时提供 CSV、PDF 或其他格式。
2. 可导出互认使用汇总、提醒明细、采纳明细、不采纳明细、引用明细、来源医院被互认汇总和来源医院被互认明细。
3. 明细导出覆盖当前查询条件和权限范围内的全部匹配记录，不只导出页面当前页。
4. 导出必须继承当前用户的数据权限和当前查询条件，不得扩大医院、院区或县域范围。
5. 患者姓名和证件号码始终脱敏，导出不提供完整身份或解除脱敏能力。
6. 预计节省金额随采纳明细导出，不另生成独立金额明细。
7. 其他不采纳原因的补充说明可以随有权脱敏明细导出，不据此生成新的原因分类。
8. MVP 不新增独立候选提供组导出；提醒、采纳、不采纳和引用明细导出增加候选提供组 ID 和候选项目 ID，用于跨明细核对。
9. 明细按候选项目一行展开，组级字段在同组各行重复；未反馈候选项目进入提醒明细并明确显示“未反馈”。
10. 候选组相关导出不包含完整报告结构化内容、PDF 文件标识或下载入口、影像调阅地址。

#### 关键属性

| 属性 | 说明 |
| --- | --- |
| 导出类型 | 互认使用汇总及四类明细、来源医院被互认汇总及明细；不单独导出候选提供组。 |
| 关联标识 | 提醒、采纳、不采纳和引用明细包含候选提供组 ID 与候选项目 ID。 |
| 文件格式 | Excel `.xlsx`。 |
| 查询条件 | 发起导出时页面当前有效查询条件。 |
| 数据范围 | 当前用户权限允许的医院、院区或县域范围。 |
| 记录范围 | 查询条件下全部匹配记录，不受页面分页限制。 |
| 脱敏规则 | 与对应统计页面一致，不允许解除。 |

## 设计约束

1. 本规约只定义业务需求和边界，不预设数据库表、接口路由、报文对象、代码模型、后台任务、部署方式或技术框架。
2. 平台使用候选提供组 ID 和候选项目 ID 定位互认处理和引用事实，不使用查询流水号、稳定候选引用、拟开项目业务标识或调用方事件标识恢复或复用候选组。
3. 互认时间和实际引用时间必须保存到秒；报表可以按更粗粒度汇总，但不得降低原始业务时间精度。
4. 平台不得使用接口调用账号代替实际作出决定或执行引用的平台科室、医生。
5. 平台科室和医生名称随业务记录保存；基础资料改名不得动态修改已有报告、互认处理或引用记录中的名称。
6. 平台不得根据名称或相似度自动推断标准项目、互认项目、LOINC、菌种、药敏、检查部位或诊断编码。
7. 平台不得根据患者姓名、电话或其他非跨院稳定标识进行模糊或概率患者匹配。
8. 平台不得解析、换算或重新判定来源检验结果、参考范围、异常、危急值、药敏结论、检查所见和检查结论。
9. 平台不得将查询、候选返回、结构化展示、PDF、影像或引用详情访问自动解释为医生采纳或实际引用。
10. 完整报告提交必须保持结构化数据与 PDF 文件流共同成功或共同失败，不能先保存一部分后补齐另一部分。
11. 报告更正和作废不接入 PushCenter，不建设下游主动推送、推送记录、任务核对或恢复能力。
12. 平台不存储、代理或缓存 DICOM 文件，只保存来源影像状态和单个受控 HTTPS 影像调阅地址。
13. 影像调阅地址的定位参数由医院或区域影像中心封装，平台不得依据 PACS 或 DICOM 技术标识自行拼接。
14. 预计节省金额使用采纳决定成功保存时接收医院、接收院区当前启用项目编码对照的价格形成，不使用来源医院价格，也不模拟实际收费、医保结算、患者退费或医院收入。
15. 统计导出只使用 Excel `.xlsx` 格式，必须继承页面查询条件、权限和脱敏规则。
16. 当前版本不建设通用重量级审计、对照价格独立版本、同步历史、趋势图、医生排名或绩效评价能力。
17. 引用详情有效时长复用现有系统参数系统，使用全平台统一的正整数分钟参数；不新建专用参数表、配置页面或组织级覆盖。
18. 报告版本顺序和重传判断不得依赖医院版本号、操作类型、完整内容比较或 PDF 文件摘要；平台使用报告业务标识、全部历史版本、生命周期状态和严格递增的源端报告修改时间。
19. 历史报告版本只在管理端按权限查看和下载，不得通过医院 HIS 在线业务接口开放，也不得提供修改、删除、恢复或重新启用能力。

## 接口

### 医院接入接口

本节集中说明医院侧系统接入互认平台所需的业务接口能力。平台管理端页面所需的内部支撑能力由 F01、F02、F08、F09 及“用户界面”章节规定，其前后端接口属于后续设计内容，不作为医院接入契约。平台调用标准项目管理系统、权限体系、现有系统参数系统、检验协同和检查协同等依赖关系已在“假设与依赖关系”中说明，本节不展开其技术规格。

| 接入能力 | 调用方 | 业务目的 | 主要业务输入与输出 | 对应功能 |
| --- | --- | --- | --- | --- |
| 检验完整报告提交 | 医院侧采集服务 | 将首次审核或修订后重新审核的当前完整检验报告提交至平台。 | 提交来源报告单号、完整结构化检验报告、源端报告修改时间和 PDF 文件流；平台自行创建首个版本、识别历史重传或追加新版本。 | F03.1、F03.2 |
| 检验报告作废 | 医院侧采集服务 | 声明既有检验报告不再有效。 | 提交来源报告单号、作废时间和原因，不重复提交报告内容及 PDF。 | F03.1 |
| 检查完整报告提交 | 医院侧采集服务 | 将首次审核或修订后重新审核的当前完整检查报告提交至平台。 | 提交来源报告单号、完整结构化检查报告、源端报告修改时间、PDF 文件流、来源影像状态和按规则提供的影像入口；平台自行创建首个版本、识别历史重传或追加新版本。 | F03.1、F03.3 |
| 检查报告作废 | 医院侧采集服务 | 声明既有检查报告不再有效。 | 提交来源报告单号、作废时间和原因，不重复提交报告内容及 PDF。 | F03.1 |
| 互认候选查询 | 医院 HIS | 在患者接诊或开单过程中查询可以提供给医生判断的互认候选。 | 提交患者身份、本次来源就诊和一个或多个拟开院内项目；平台返回符合条件的候选，没有候选时返回成功的空候选集合。 | F04 |
| 互认处理结果提交 | 医院 HIS | 按候选提供组提交医生针对全部候选项目作出的不可更改决定。 | 提交候选提供组 ID、组级互认时间和决定科室医生，以及完整候选项目决定数组；平台整批原子保存，任一失败整批不保存。 | F05 |
| 引用详情获取 | 医院 HIS | 在候选已被采纳后、引用详情有效期内获取写入本次病历所需的项目内容和报告公共上下文。 | 提交患者证件类型、证件号码、本次就诊类型和流水号；平台查询同次就诊仍有效的已采纳项目并返回候选提供组 ID、候选项目 ID、引用内容和文件入口。 | F06 |
| PDF 文件下载 | 医院 HIS | 下载候选或引用详情已经授权提供的报告 PDF。 | 使用响应中的平台下载地址并通过标准 `Authorization` 请求头携带现有令牌；平台校验医院院区、候选归属和报告版本后返回 `application/pdf` 文件流。 | F04、F06 |
| 引用结果提交 | 医院 HIS | 将互认内容已经成功写入本次病历的事实提交至平台。 | 提交候选提供组 ID 和实际引用项目数组，每项提供候选项目 ID、实际引用时间及引用科室医生；平台整批原子保存，不提供逐条部分结果。 | F07 |

医院接入接口共同遵循以下边界：

1. 调用方必须符合表中责任划分。医院侧采集服务负责报告提交，医院 HIS 负责在线候选查询、医生决定反馈和病历引用相关交互。
2. 当前调用医院和院区必须来自可信身份上下文；各接口不得使用调用账号替代实际报告、决定或引用所涉及的业务科室和医生。
3. 各接口的前置条件、后置条件、主事件流、备选流、业务规则、必填口径、幂等及冲突处理以对应功能章节为准，本节不重复改变其业务语义。
4. 本规约不定义接口路由、请求方法、报文对象、字段结构、异常响应 DTO、传输协议或技术错误码；业务失败使用现有框架业务异常，具体异常格式由实现框架决定。PDF 下载沿用其他医院 HIS 接口的认证方式，地址不携带 Bearer Token。
5. 平台内部接口不得作为医院接入契约直接承诺；医院接入接口的后续技术设计不得要求医院调用平台管理端专用接口完成上述业务流程。

### 用户界面

#### 通用界面要求

1. 平台页面的可见、查询、操作、下钻和导出能力必须受平台统一权限和可信医院院区上下文控制。
2. 页面应以业务名称、当前状态、关键时间和必要说明表达业务事实，不展示平台内部存储标识或技术排障信息。
3. 页面中的患者姓名、证件号码、联系电话等敏感信息按照对应业务用途和权限展示；统计及导出场景必须保持脱敏。
4. 页面具体布局、控件类型、菜单位置和视觉样式由界面设计确定，但不得减少本规约定义的业务能力、查询条件、状态提示或权限边界。

#### 互认项目管理

1. 页面进入时自动刷新当前有效标准项目目录，并提供手动刷新能力。
2. 页面展示互认项目的标准项目编码和名称、可互认时间、启停状态、来源状态及框架修改信息，不展示或维护全县统一价格。
3. 页面支持从当前有效最细层标准项目中选择项目，填写可互认时间后新增并默认启用。
4. 页面支持修改可互认时间和启停状态，不提供物理删除或配置版本恢复。
5. 目录刷新失败时明确提示并保留既有来源状态；来源不可用项目应有明确状态提示和受限操作。

#### 项目编码对照管理

1. 医院用户页面只展示和维护当前登录医院及有权院区的数据；平台管理员按权限跨机构查看和异常停用，不代替医院修改对照或价格。
2. 页面采用表格内直接填写和保存，不通过弹窗新增；按互认项目展示分类、分组、互认项目名称和编码、本院项目名称和编码、当前价格、可互认时间、启停状态、备注及比对状态。
3. 可互认时间来自互认项目并只读展示；本院项目名称、编码和当前价格在表格行内维护。
4. 页面提供一个“同步已有对照”操作，同时获取当前医院、院区的检验协同和检查协同已启用对照，并按项目类型自动匹配来源系统。
5. 未对照项目同步成功后预填本院项目名称和编码并提示“待补价格”，但不自动保存；管理员补充有效价格并明确保存后才建立和启用对照。
6. 页面以图标、文字和适当视觉提示共同表达“对照一致”“对照不一致”“名称不一致”“来源存在多个对照”“来源系统当前未启用此对照”和编码占用冲突，不得只依赖红绿颜色。
7. 编码不一致、来源存在多个对照或同步编码已被其他互认项目使用时，页面行内同时展示核对所需的当前值、同步值或全部候选，不自动覆盖或选择。
8. 页面支持单行保存和顶部“保存全部”；两者均须由管理员明确触发。“保存全部”按行显示成功或失败，失败行不回滚其他互不冲突的成功行。
9. 再次同步不得覆盖尚未保存的人工编辑；一个来源调用失败时不得清空页面已有数据，并应分别显示检验、检查来源的成功或失败结果。
10. 同步完成后展示本次成功、失败、一致、冲突和因不属于互认项目范围而跳过的数量，不提供同步历史或回滚页面。
11. 页面支持新增、修改、启用和停用对照；医院、院区、院内项目编码创建后不得提供修改入口。
12. 当前价格缺失、为负数、超过两位小数，一对一关系冲突，互认项目停用或来源不可用时，页面应明确提示不能保存或启用的业务原因；零价格应作为有效值处理。

#### 报告管理与历史版本

1. 平台在报告详情中提供只读历史版本区域，不建设独立版本管理菜单。
2. 历史版本按照平台成功形成顺序和源端报告修改时间展示，明确标识当前有效版本、已被更正的历史版本和报告已作废状态。
3. 每个版本展示平台内部版本序号、源端报告修改时间、平台接收时间、报告责任人员、来源报告备注及 PDF 文件名；不展示或要求更正原因、版本变更原因。
4. 用户可以查看每个版本的完整结构化报告，并下载使用该版本所保存文件名的 PDF。
5. 医院管理员默认可以查看本医院及有权院区上传报告的全部历史版本、完整内容和 PDF，不新增独立报告查看权限；平台管理员按照现有数据权限查看授权范围内报告，其他医院不得查看来源医院报告的历史版本。
6. 页面不提供版本自动差异比较、修改、删除、恢复、重新设为当前版本或重新启用能力；查看历史版本不得改变报告业务有效性。
7. 医院 HIS 在线业务界面及接口只能使用当前有效版本，不提供历史版本查询或下载入口。

#### 接收医院互认使用统计

1. 页面支持按日期范围、医院、院区、决定科室和互认项目查询权限范围内的数据；决定医生可以作为明细查询条件。
2. 页面展示提醒、采纳、不采纳、引用、同期互认率和预计节省金额，并区分总体口径与跨机构子集口径。
3. 提醒、采纳、不采纳和引用汇总数字支持下钻到对应脱敏明细，预计节省金额随采纳明细展示。
4. 页面提供不采纳原因次数及占比，并允许在明细中查看其他原因的脱敏补充说明。
5. 页面不提供趋势图、医生排名、绩效评价或患者身份解除脱敏能力。
6. 提醒、采纳、不采纳和引用明细提供只读“查看候选组”入口，展示组级信息和全部候选项目，不新增独立候选组菜单；未反馈只表示平台未收到结果。
7. 接收医院管理员不得通过统计或候选组页面打开其他来源医院的完整结构化报告、PDF 或影像地址。

#### 来源医院被互认统计

1. 医院管理员在来源医院被互认统计中只能查看本院报告形成的被互认汇总和脱敏明细；平台管理员按权限查看全县数据。
2. 页面展示被互认总体次数和跨机构被互认子集，不将两者相加。
3. 明细可以展示互认项目、接收医院及院区、决定科室、决定医生和互认时间，患者姓名必须脱敏。
4. 页面不展示或汇总来源医院贡献金额。

#### 统计导出入口

1. 互认使用和来源医院被互认的汇总及明细页面按权限提供 Excel 导出入口。
2. 导出入口沿用页面当前查询条件和数据权限，导出全部匹配记录而非当前分页。
3. 页面应明确导出仍使用脱敏数据，不提供 CSV、PDF 或解除脱敏选项。
4. 当前查询没有匹配记录时，页面提示“当前条件下无可导出数据”，不生成空 Excel 文件。

#### 医院 HIS 界面边界

1. 候选提醒、医生查看、采纳或不采纳操作、继续或撤销院内医嘱以及病历写入界面由医院 HIS 负责。
2. 互认平台不规定医院 HIS 的页面布局、弹窗形式、控件、菜单或调用时机。
3. 医院 HIS 的界面行为不得替代明确的处理结果和引用结果提交；关闭提示、查看文件或离开页面均不能由平台推断为采纳、不采纳或引用。
