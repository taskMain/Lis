# 智能体协作规范

## 1. 适用范围

本文规定项目中自定义智能体的任务路由、职责边界、文件所有权、交接方式和验收权限。单个智能体的专业行为仍以对应 `.toml` 配置为准。

- 仅在任务确实可以拆分或需要专业复核时使用多智能体协作。
- 不得为简单任务同时调用全部智能体。
- 跨阶段、跨专业、需要并行或跨会话交接的总体任务，可以由 `Project Shepherd` 负责项目级协调；简单任务不启用该角色。
- 总体协调任务和每个专业子任务都只指定一个主责智能体，其他智能体只能作为协作、审核或验收角色。
- 业务规则、范围或架构结论发生冲突时，由主责智能体汇总差异并交用户确认，不通过智能体投票决定。
- 产品决策未确认前，不得提前进入 SRS、数据库或代码实现。

## 2. 职责与任务路由

| 智能体 | 主要职责 | 典型任务 |
|---|---|---|
| `Project Shepherd` | 项目级协调、阶段状态、任务路由、依赖、风险和交接 | 跨阶段推进、多智能体编排、决策门、阻塞升级、跨会话恢复 |
| `Product Manager` | 需求澄清、MVP 边界和验收目标 | 业务决策、角色职责、范围取舍、验收口径 |
| `Sprint Prioritizer` | 阶段拆分、依赖和执行顺序 | 制定阶段计划、拆分任务、排列优先级 |
| `UX Architect` | 信息架构、业务流程和操作路径 | 菜单规划、页面职责、跨角色流程、交互边界 |
| `UI Designer` | 页面视觉、组件和状态设计 | 页面原型、表格、筛选器、详情、反馈状态 |
| `Software Architect` | 领域边界和总体技术架构 | 领域模型、模块划分、跨模块契约、架构决策 |
| `Backend Architect` | 后端领域、应用和集成实现 | Application、Domain、Repository、事务和外部服务 |
| `API Platform Engineer` | API 契约和集成治理 | OpenAPI、版本、错误码、SDK/Kiota、第三方接口 |
| `Frontend Developer` | 前端页面和 API Client 接入 | React 页面、状态管理、组件实现、前端性能 |
| `Database Optimizer` | 数据结构和查询性能 | 表结构、约束、索引、SQL、数据一致性 |
| `Identity & Access Engineer` | 身份、权限和数据范围 | 医院、院区、角色、登录上下文、授权校验 |
| `Minimal Change Engineer` | 控制修改范围和实现复杂度 | 评估最小改动、阻止无关重构和 MVP 膨胀 |
| `API Tester` | API 功能和异常验证 | 参数、权限、幂等、并发、第三方集成和错误响应 |
| `Test Automation Engineer` | 自动化和回归测试 | 单元测试、集成测试、Vitest、Playwright、稳定性治理 |
| `Evidence Collector` | 收集真实执行证据 | 页面、Network、Console、接口响应和最终数据状态 |
| `Reality Checker` | 最终验收和就绪判断 | 核验证据、识别缺口、判定 Passed、Blocked 或 NotRun |

## 3. 标准协作流程

1. 对于跨阶段或多智能体任务，`Project Shepherd` 明确总体目标、当前阶段、权威输入、排除项和下一决策门，并判断哪些步骤可以并行；简单任务直接交由单一专业智能体。
2. `Product Manager` 明确当前问题和待确认的业务决策。
3. `UX Architect` 与 `Software Architect` 分别评估流程影响和技术影响。
4. 用户确认决策后，`Sprint Prioritizer` 才能拆分实施任务和依赖顺序。
5. `Project Shepherd` 为各子任务指定唯一主责、文件所有权、前置依赖、交付物和适用验证，不代替专业智能体实施。
6. 实施任务分别交由后端、接口、前端、数据库或权限智能体。
7. `Minimal Change Engineer` 检查实现是否超出已确认范围或引入不必要抽象。
8. `API Tester` 和 `Test Automation Engineer` 执行适用验证，`Evidence Collector` 汇总真实证据。
9. `Reality Checker` 根据证据作最终判断；`Project Shepherd` 汇总阶段状态、遗留风险、下一主责和下一决策门。

## 4. 文件所有权与并行协作

- 主责智能体开始前必须声明负责的文件、目录或模块。
- `Project Shepherd` 默认只负责协调和交接，不拥有实施文件；只有任务明确要求维护协调类文档时，才声明对应文件所有权。
- 多个智能体不得同时修改同一文件；确需共同修改时，应改为串行交接。
- 智能体必须保留用户和其他任务已有修改，不得回退、覆盖、清理、暂存或提交非本任务内容。
- 发现其他智能体的修改时，应调整自己的实现与其兼容，不得直接恢复旧版本。
- 公共契约、领域模型、数据库结构和生成代码属于高冲突区域，必须指定唯一主责智能体。
- 架构或设计智能体默认提供决策和约束，不直接修改实施文件，除非任务明确授权。

## 5. 审核与验收权限

- `Evidence Collector` 只收集和整理证据，不宣布功能通过。
- `Reality Checker` 负责最终结论，但不得通过直接修改实现来制造通过结果。
- `Project Shepherd` 可以汇总阶段状态和阻塞，但不得代替 `Reality Checker` 宣布 `Passed`、`Closed`、`Ready` 或 `Complete`。
- `Minimal Change Engineer` 可以指出范围膨胀，但不能否定已经由用户明确批准的范围。
- 测试服务器、模拟数据、文档检查和构建成功不能自动替代真实接口或宿主页面证据。
- 未执行的验证必须记录为 `NotRun`；受环境或权限影响的验证记录为 `Blocked`。
- 只有适用验证均有真实证据时，才能使用 `Passed`、`Closed`、`Ready` 或 `Complete`。

## 6. 交接格式

智能体完成任务时应提供以下信息：

```markdown
## 任务交接

- 总协调智能体：
- 主责智能体：
- 当前阶段：
- 任务目标：
- 负责范围：
- 关键决策：
- 修改文件：
- 已执行验证：
- 未执行或受阻验证：
- 遗留风险：
- 建议下一主责智能体：
- 下一决策门：
```

交接内容必须区分事实、推断和建议，不得把计划、历史记录或替身测试描述为当前真实完成证据。
