# Testing Baseline

本文定义 MedicalRecognition 功能、缺陷、重构和治理任务共同遵循的验证纪律。语言和运行环境的差异分别见后端、前端及跨端测试规范。

## 1. 测试驱动规则

1. 新功能、缺陷修复和行为变化使用 RED-GREEN-REFACTOR：先写能够稳定复现目标缺失的测试，确认因该行为缺失而准确失败，再写最小实现并在保持通过后整理代码。
2. RED 不能来自编译错误、测试夹具错误、环境不可用或错误断言。
3. 等价重构先建立并通过能够冻结既有行为的特征测试、契约测试或现有回归集，再重构并保持通过；不得制造虚假 RED。
4. 注释、格式、文件结构、依赖方向和禁止 API 等静态 finding，优先使用 Analyzer、架构测试、源码契约或静态检查形成失败证据，不强制伪造行为 RED。
5. 修改后先运行目标验证，再运行直接影响范围；阶段或纵切收口时按风险执行规定的全量测试、构建、静态和契约检查。
6. 测试验证可观察结果、请求参数、持久化状态、事件或用户状态变化，不能只断言对象非空、组件存在、方法未抛异常或 mock 被调用。
7. 无法自动化时，记录原因、替代验证、未覆盖面和残余风险。
8. 测试用例的前提数据和业务状态必须能通过正常业务路径产生；正常业务不可达的状态（如唯一约束禁止的重复键、业务规则禁止的状态组合）不得作为普通测试用例的前提。验证约束本身、历史数据兼容、迁移或损坏数据防御时，可以构造不可达数据，但必须明确标注目的，且只用于验证约束或防御，不用于验证正常查询或业务行为。

## 2. 禁止事项

- 不为让测试通过而削弱生产校验、改变公共契约、增加测试专用生产入口或绕过真实业务链路。
- 不让测试依赖执行顺序、共享可变状态、不可控网络、固定等待或未经管理的当前时间。
- 不把 build、typecheck、接口直测、空列表、按钮可见或“点击未报错”写成功能通过。
- 不删除、跳过、放宽或改写既有有效测试来掩盖回归；需求确实变化时，先更新设计和测试意图。
- 不在没有新证据时沿用历史测试结果。

## 3. 状态与标签

测试结果只允许以下状态：

| 状态 | 含义 |
|---|---|
| `NotRun` | 尚未执行规定验证 |
| `Passed` | 本轮获得该验证面的完整通过证据 |
| `Failed` | 已执行且确认失败 |
| `Blocked` | 环境、权限、数据或外部依赖阻止执行 |
| `PendingRetest` | 已修改，但规定复测尚未完成 |
| `N/A` | 经范围确认后不适用于本轮 |

以下内容只能作为决策、证据或责任标签，不得进入测试结果统计，也不得替代 `Passed`：

| 标签 | 含义 |
|---|---|
| `DesignConfirmed` | 设计已经确认，不表示已经实现或运行验证通过 |
| `Rejected` | 方案已被否决，不得进入实现，也不计入测试结果 |
| `SourceConfirmed` | 已由源码、反编译或正式文档确认，不表示真实运行通过 |
| `AcceptedRisk` | 已知风险已经由项目负责人接受，不表示风险消失 |
| `Pending` | 决策尚未完成，受影响范围不得进入实现，也不计入测试结果 |
| `HostTransfer` | 经项目负责人确认转由宿主或框架团队处理，不表示已修复 |

运行验证实际通过时，测试结果写 `Passed` 并附运行环境和证据，不另设容易混淆的通过状态。

## 4. 完成证据

每个代码批次至少保留：起始工作区和任务边界、目标失败或等价重构基线、实现范围、目标验证、直接影响验证、构建或静态检查、未执行项和残余风险。阶段 `testReport.md` 的位置由 [Planning and Evidence](planning-and-evidence.md) 规定，更新时间和内容见 [Testing](testing.md)，不得只写在聊天、终端或 `impl.md` 中。

代码任务完成声明前还必须执行适用测试与检查，以及：

```powershell
git diff --check
gitnexus detect-changes --repo Dy.MedicalRecognition
```

GitNexus 不可解析的文档、SQL、生成物、配置和运行时行为仍需人工检查。
纯文档任务在完成检查阶段只执行文档静态检查和 `git diff --check`，不要求 GitNexus symbol `detect-changes`。提交闸门与完成检查分开判断：用户要求提交时，无论变更是否纯文档，提交前仍必须按 [GitNexus Workflow](gitnexus-workflow.md) 执行 `detect_changes`。

## 5. 风险驱动批次、审查与证据复用

代码批次按以下顺序执行；阶段计划可以收窄集合，但不得颠倒适用闸门：

1. 形成准确 RED，或为等价重构/静态 finding 建立对应基线。
2. 执行最小修改并取得目标 GREEN。
3. 使用明确 FQN 或等价精确范围验证直接调用方、持久化、SQL、契约和适用架构守卫，避免误命中其他既定失败的宽泛过滤器。
4. 自审范围、错误语义、0/1/N、输入与返回顺序、失败零写入和重复实现；独立审查实现正确性、任务边界和测试缺口。
5. finding 按其类型补行为 RED、特征/契约基线或静态失败证据，再做最小修正并复跑目标与精确影响验证。
6. 稳定后执行受影响项目全量、构建、静态、契约、`git diff --check` 和 GitNexus `detect-changes`；独立证据复核只核对最终数字、失败集合、契约、差异范围和文档状态。

批次按共同根因、契约、验证面、影响分析、停止条件和任务差异归属划分，不按单个文件或方法机械切分。同一项目、类型族或完整能力目录中的同质机械修改，在风险和责任边界一致时可以组成可审查的中等规模批次，共享一次任务快照、组合目标验证、构建、静态检查和整批审查。出现不同业务或错误语义、公共 HTTP/OpenAPI/Kiota、数据库/事务/SQL、可信组织范围、不同 HIGH/CRITICAL 流程、停止条件或负责人决策边界时必须拆分。

存在计划内治理失败时，维护精确 FQN、失败类别和关键错误摘要。全量测试后比较失败集合；新增失败、既定失败消失、错误内容意外变化或测试总数变化都必须单独归因，不能只依据通过数量判断成功。

最终验证后只修改文档时不重复代码测试。生产代码再次变化时，与变更影响重叠的证据失效并重跑目标、直接影响、受影响项目和适用运行验证；未受影响证据只有在记录 impact、版本、环境、时间和复用理由后才能继续使用。

完整矩阵不是每次生产代码变化后的默认动作。公共 HTTP/OpenAPI/Kiota、数据库/事务/SQL 结果、认证授权或可信组织范围、共享 Repository/缓存/错误处理等横切基础设施、HIGH/CRITICAL 影响、影响分析与实际失败不一致，或发布/阶段最终检查点明确要求单轮证据时，重新执行相应完整矩阵。

完整矩阵中的局部 LOW/MEDIUM finding 若未改变上述高风险边界，且 impact 与精确验证能够划清范围，可复用未受影响的同轮证据。收口报告分别列出复用项、失效项、修复后重测项、技术检查点和负责人授权；组合证据可以支持阶段结论，但不得描述成新执行的一次完整干净轮次。审查 finding、适用最终验证和证据复核未关闭前不得记录 `Passed`。
