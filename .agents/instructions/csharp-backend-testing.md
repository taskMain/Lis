# C# Backend Testing

本文约束 MedicalRecognition 后端自动化、仓储、SQL 和接口契约测试。共同纪律遵循 [Testing Baseline](testing-baseline.md)，跨端联调遵循 [Testing](testing.md)。

## 1. 必须覆盖

1. 应用和领域：正常流、关键失败流、状态边界、权限、组织范围、持久化结果和领域事件。
2. 仓储和 SQL：筛选、稳定排序、分页、唯一性、关联、软删除、组织范围、事务、并发、幂等及锁语义。
3. 契约：请求必填、长度、值域、枚举、DTO、HTTP、OpenAPI、文件和可空性。
4. 缺陷和行为变化：准确目标失败测试、直接调用方与受影响执行流程；等价重构：先通过的特征/契约测试和既有行为回归。

## 2. 应用与领域

- 测试可观察业务结果，不只验证方法调用或未抛异常。
- 领域事件验证类型、数量、关键载荷和逐业务对象语义，不为测试便利改变事件模型。
- 校验失败验证业务状态和持久化结果不变，并沿用项目既有异常链路。
- 时间逻辑使用可控时钟或确定输入，不依赖等待当前时间。
- 外部依赖使用稳定替身或受控环境，但不能用 mock 取代需要真实验证的数据库、序列化或框架行为。

## 3. 仓储与 SQL

- 普通查询验证条件组合、空值、边界值、重复数据、稳定唯一排序和数据范围。
- 分页验证第一页、中间页、末页、空页、边界数量、无重复和无遗漏；不得只验证返回数量。
- 事务、并发、幂等和锁必须使用能够体现真实数据库语义的后端集成测试；测试必须从后端 Host、公开 HTTP 或后端测试宿主进入实际 Application/Repository/DataMapper 链路，禁止代理使用 `dbctl`、数据库客户端或独立 SQL 绕过后端程序取证。
- SQL 优化同时保留结果正确性及后端可观察的耗时证据；执行计划或索引诊断只有在后端现有诊断能力能够提供时才记录，不为验收直接连接数据库。
- SQL/映射契约测试应阻止字段漏绑、错误别名、编码冒充名称和无意全量查询。
- 项目声明数据库 Provider 中立时，静态或架构测试必须阻止公共类型、DataRequest 和共享 SQL/XML 引入具体 Provider 类型、分页方言、空值排序、类型转换、JSON 运算符或版本特性。
- 新增或修改 SQL/XML Statement 时，静态检查或针对性审查必须覆盖 Statement 功能注释、字段中文注释，以及复杂查询的操作、原因和结果注释；注释结构通过不替代参数绑定、结果正确性、稳定排序和真实 Provider 运行验证。
- 数据库支持报告必须记录后端实际配置的 Provider；数据库版本只有在后端运行时或既有诊断信息能够提供时才记录，不得为取得版本单独连接数据库。当前 Provider 的 `Passed` 不得外推为其他 Provider 或跨数据库 `Passed`；每个声明支持的 Provider 都必须通过该 Provider 配置下的后端程序重跑相同的查询、分页、Count、稳定排序、并发和边界矩阵。
- Provider 生成 SQL 的断言应验证唯一窗口、参数语义、Count 一致和结果行为，不把某个数据库的 `LIMIT/OFFSET`、执行计划节点或 SQL 文本当作跨 Provider 固定契约。
- 直接 SQL、数据库客户端查询或脱离后端程序得到的行数、版本、执行计划和耗时不能作为应用验收证据；历史证据可以保留，但后续变更必须通过后端运行链重新取证。

集合、批量数据库查询和批量远程调用按适用业务语义覆盖：空集合或空白项、大小写或业务键重复、依赖返回 0/1/N 条、可信医院/院区/科室范围、请求与返回顺序不同、缺失/跨范围/非唯一结果、失败零写入，以及调用次数不随输入数量增长。

测试替身应集中记录调用次数、可信范围、输入集合及顺序、可配置返回集合、下游实际消费顺序和写入/更新次数；不得让每个测试以不同临时字段重复实现同一观测能力。

## 4. 契约与组织信息

- OpenAPI 使用结构化 diff 或等价检查，避免无关漂移。
- 枚举覆盖显式数值、名称、`Description`、元数据和代表性 `XxxText`。
- 组织测试区分可信登录主体、医院/院区编码和医院业务科室/人员字符串 ID；不得假设后者为 Guid 或属于权限系统。
- 平台主数据列表准备重复医院和院区，验证按去重范围调用及父级字典键；医院业务科室/人员测试验证 ID/名称成对保存、院区级范围、历史名称不回写及不向权限系统补查名称。
- 验证 DTO 同时保留稳定标识和真实名称；禁止关联平台组织表以及 `code as name`。
- 只有设计允许时验证名称解析失败降级；否则验证平台异常链路且业务状态不被误改。
- Scalar 和直接 HTTP 只证明接口或契约，不替代宿主页面验收。

## 5. 测试反射边界

- 独立测试项目、测试用例、测试框架和纯测试 helper 可以为明确的契约验证合理使用反射，前提是它们不进入生产发布包，也不被生产运行时代码引用。测试项目应保持不可打包或等价隔离，生产项目不得反向引用测试程序集。
- 测试反射必须服务于明确、稳定且可观察的契约，例如公开成员、Attribute、nullable metadata、序列化形态或框架行为；不得依赖未定义的成员顺序、私有实现偶然形态或宽泛程序集扫描制造脆弱断言。
- 不得仅为追求测试代码“零反射”，把简单可靠的反射契约测试强制改写为更复杂的 Roslyn 源码解析。只有源码声明形态、跨 partial/enclosing type、public/private 边界或编译期语法本身就是目标契约时，才优先使用 Roslyn/source contract。
- 测试 helper 位于共享基础设施、公共库或其他可能进入发布包的项目时不得直接视为测试豁免；无法确认发布边界时不得豁免，取得打包证据后再分类。
- 生产反射治理扫描默认排除已确认隔离的测试项目；测试中的反射可靠性由目标测试、mutation 或等价测试质量审查负责，不计入生产反射违规库存。

## 6. Roslyn/Source Contract 自审清单

使用 Roslyn 或其他源码契约替代运行时反射时，提交独立代码审查前逐项确认：

1. 声明数量覆盖 `0/1/N`，不能只验证当前恰好存在一个声明。
2. 明确 enclosing type、partial 文件集合和实际扫描范围；继承、跨文件 partial、嵌套类型或同名声明不能被无意漏过。
3. 区分 public/private 边界；不得把 private 成员误计入公共契约，也不得漏掉继承或其他声明位置的 public 成员。
4. nullable 契约不得只依赖强类型 delegate；nullable annotation 还必须由源码、编译诊断或等价的精确契约验证。
5. 方法参数逐项冻结数量、类型、modifier 和 default；不能只验证调用兼容性。
6. 按目标契约检查泛型参数、body、expression body 和 semicolon，避免兼容但不等价的声明形态绕过。
7. 名称匹配必须考虑 qualified name、alias-qualified name 和 `Attribute` 后缀，不能只比较简单文本。
8. 每项关键判定必须有对应 mutation 测试；至少证明删除、重复、类型或形态漂移能够按预期失败。
9. 新增测试 helper 必须有说明用途的中文 XML 注释。
10. 报告测试结果时区分测试方法数和测试运行器展开后的实际测试用例数，不得把 `[Theory]` 方法数写成执行用例数。

## 7. 后端执行差异

通用 TDD、审查、批次和证据复用顺序只遵循 [Testing Baseline](testing-baseline.md)。后端在相应检查点运行精确 FQN 测试、受影响测试项目、解决方案构建、适用 Analyzer/架构测试，以及按契约影响执行 OpenAPI 或经后端程序进入真实数据库的验证。涉及页面时继续执行 API Client、前端和宿主联调，不以单侧通过宣告功能完成。

无法执行项的报告方式遵循 [Testing](testing.md)。
