# C# Documentation And Reuse

本文约束手写 C# 生产代码中的业务注释、复用检索和新增抽象。生成代码和第三方源码除外。注释服务于契约和维护风险，不以成员数量或形式完整制造无意义文字。

## 1. 完成闸门

出现以下任一情况时不得声明任务完成：

- 必需 XML 注释缺失、与实现不一致或只复述名称。
- 业务代码注释使用架构术语代替具体业务动作、对象或规则。
- 计划新增共享抽象、依赖或基础设施前没有完成复用检索。
- 出现未在设计中声明的新共享抽象、项目或依赖包。
- 实际新增抽象或关键注释变化没有留下本文件要求的针对性证据。

## 2. XML 注释覆盖

所有手写生产代码中的类型、构造函数、方法、属性、字段、事件、枚举项、参数、返回值和可预期异常，都必须有中文 XML 文档。覆盖范围包括 public、protected、internal、private、partial、局部函数以及只读字段；不得因为名称、类型、访问级别、代码行数或调用次数看似容易推断而省略。

以下业务成员必须重点说明其业务语义：

- Request、Response/DTO、Command、DomainEvent、Entity、ValueObject、Manager、Repository 接口和外部端口。
- 保存用户、组织、医院、院区、科室、业务编码、状态、时间或快照的属性和字段。
- 承载状态流转、兼容、并发、事务、补偿、异常处理、复杂映射或特殊 SQL 的方法。
- 私有只读依赖字段，例如 Repository、解析器、组织范围服务和外部客户端；说明其负责读取或执行的业务对象，不只写类型名称。

接口实现没有额外业务行为时可以使用 `inheritdoc` 复用接口契约，但成员仍必须保留 XML 文档节点。简单赋值、普通初始化和一两步私有方法可以使用简短但具体的说明，不能以“名称和类型已经明确”为理由删除文档。

注释必须让不了解实现上下文的维护者独立理解成员用途；不能把“可由名称推断”当作省略理由。注释不得隐藏业务规则、可信数据来源、空值语义、异常、顺序或兼容边界。

同一手写 partial 类型的主声明说明整体业务职责；其他分片只在承载独立且不易从类型名判断的业务能力时补充有信息量的 `summary`，不得写“此分片负责”等空话。

## 3. 注释质量

- `summary` 说明业务职责、适用范围或不可见约束，不复述类型和方法名称。
- `param` 说明来源、单位、可信性、空值、顺序或业务语义；不要假定读者能从参数名推断。
- `returns` 说明业务结果、空值或顺序语义，不写“返回结果”。
- 可预期的业务和参数异常使用 `exception` 说明触发条件。
- 行内注释解释原因、特殊顺序、兼容边界、状态流转、时间/空值来源或特殊 SQL；简单赋值、普通初始化和显然投影仍不写行内注释，但方法 XML 文档不能省略。
- 复杂或较长方法必须按业务阶段补充方法内注释，说明校验、读取、批量处理、外部调用、写入、事件、空值和失败后果；只写一条笼统注释不算覆盖。
- 禁止将临时计划编号、整改批次和仅对当前任务有意义的说明写入生产代码。

Contracts、Application 和 Domain 优先使用通俗业务语言：AppService、Command 和 Manager 说明完成什么动作；Entity/ValueObject 说明对象和约束；DomainEvent 用过去式说明已发生事实；Repository 说明读写什么数据，不替领域判断状态。

业务注释禁止使用 `seam`、“事实重读”“事务内聚”“能力闭环”“适配边界”等需要猜测的表达，也不得用“通过依赖注入调用”“完成聚合编排”等实现说明代替业务职责。

Repository、Infrastructure、外部适配器、文件存储和并发控制可以在正确性需要时说明事务与补偿顺序、锁和唯一约束、协议兼容、资源清理及特殊 SQL。技术注释必须写清行为、原因和错误后果。

```csharp
/// <summary>
/// 审核待审核订单，并记录审核人、审核时间和最终审核结果。
/// </summary>
```

```csharp
// 数据库提交失败时删除本次新文件，避免保留没有业务记录引用的文件。
```

## 4. 复用检索闸门

新增通用映射、Helper、Extension、基类、异常、结果包装、HTTP 客户端、中间件或基础设施前，依次搜索：

1. 当前模块和同一聚合。
2. 当前解决方案的同类实现。
3. 项目已有共享包和框架公开 API。
4. 现有测试、生成器、映射器和扩展方法。

只有本轮准备新增上述能力时才提交复用检索表；没有新增计划时不创建空表。

| 准备新增的能力 | 搜索范围和关键词 | 找到的候选 | 是否复用 | 不复用原因 |
|---|---|---|---|---|
| 待填写 | 待填写 | 待填写 | 待填写 | 待填写 |

没有搜索结果也要记录范围和关键词，不能只写“未找到”。

## 5. 默认抽象预算

除功能本身必需且已进入设计的 Request、Command、Event、Entity、Manager 和 Repository 外，默认预算为：

| 项目 | 默认数量 |
|---|---:|
| 新共享 Helper/Util | 0 |
| 新 Extension | 0 |
| 新基类或通用接口 | 0 |
| 新 Middleware/Filter | 0 |
| 新通用 Result/Exception | 0 |
| 新项目或依赖包 | 0 |

超出预算必须说明现有候选不能复用的原因、至少两个真实调用点或明确框架边界、依赖方向和生命周期、删除该抽象会产生的实际重复或风险、测试方案及批准状态。“未来可能复用”“更优雅”“方便扩展”不是新增理由；只有一个调用点时默认使用局部实现或有业务名称的私有方法。

## 6. 针对性证据

完成前按实际变化提供证据，不逐成员抄录所有简单构造函数、DI 字段和自解释私有方法：

- 修改公共契约、领域类型、业务方法或复杂私有逻辑时，按文件或类型列出这些关键元素、业务语义和注释状态。
- 新增共享抽象或依赖时，逐项列出现有候选、新增理由、真实调用点和批准状态。
- 未新增共享抽象时写“无新增共享抽象”，不创建空的逐成员表。
- Analyzer 或审查发现的问题应保留规则编号、文件和结论，不能用“均已补充”代替。

| 文件/类型 | 关键契约或业务逻辑 | 注释语义检查 | 注释结论 |
|---|---|---|---|
| 待填写 | 待填写 | 待填写 | 待填写 |

| 新类型/依赖 | 现有候选 | 新增理由 | 调用点 | 批准状态 |
|---|---|---|---|---|
| 待填写 | 待填写 | 待填写 | 待填写 | 待填写 |

## 7. 自动化

- 使用 StyleCop 或等价 Roslyn Analyzer 检查选定的 XML 文档规则，排除生成代码并为历史违规维护固定 baseline。
- CI 运行 Analyzer、架构测试和差异检查；新增违规不得进入历史 baseline。
- 架构测试检查依赖方向、禁止 API、一个顶级类型一个文件等可机械判断规则。
- 新项目、依赖包和共享基础类型变化进入差异审查。

自动化尚未覆盖的关键业务注释和抽象变化使用第 6 节的针对性证据补足，不恢复无差别逐成员人工清单。
