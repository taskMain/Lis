# GitNexus Workflow

本文是 MedicalRecognition 使用 GitNexus 进行代码理解、影响分析、边界判断和提交前变更检查的单一事实来源。`HIGH`、`CRITICAL` 表示需要扩大审查和验证，不等同于必须停止实施。

> 本仓库通过根目录 `.gitnexusrc` 的 `skipAgentsMd: true` 阻止 `gitnexus analyze` 向 `AGENTS.md`/`CLAUDE.md` 注入上下文区块；GitNexus 的全部强制规则只以本文为权威来源，根文件不再保留生成区块。

## 1. 适用范围

本机可能同时注册多个 GitNexus 仓库。支持仓库参数的 CLI 查询显式使用 `--repo Dy.MedicalRecognition`；MCP 调用使用 `repo: "Dy.MedicalRecognition"`。`status` 在本项目根目录执行，`analyze` 在本项目根目录使用 `--name Dy.MedicalRecognition` 注册。实际语法以已安装 CLI 的 `--help` 为准，不向不支持的命令传 `--repo`。同一仓库的索引操作与图查询必须串行执行，避免 LadybugDB 文件锁或原生崩溃。

使用已安装的 `gitnexus` CLI 或已配置 MCP，不依赖技能脚本或尚不存在的 `.gitnexus/run.cjs`。初始仅有文档、尚无代码 symbol 时，不为迁移规则建立索引；首次建立代码后再按下文索引。未注册或工具不可用时不得回退查询其他项目。

1. 修改函数、类、方法或其他代码 symbol 前，必须执行 upstream impact，并记录直接调用方、受影响执行流程和风险等级。同一原子批次可集中分析和汇报，不要求为每个 LOW/MEDIUM symbol 打断实施单独发消息。
2. 文档、测试报告和纯说明性配置修改不要求执行 symbol impact；纯文档任务在完成检查阶段也不要求 `detect_changes`，只执行文档静态检查和 `git diff --check`。其中涉及代码行为约束时，仍应结合源码、契约和测试确认内容准确。
3. 探索陌生业务优先使用 query 定位执行流程，分析具体 symbol 时使用 context 补齐调用方、被调用方和所在流程。
4. 重命名 symbol 不使用文本批量替换，应使用能够理解调用图的 rename 能力；工具不可用时，必须通过源码搜索、编译和测试补足验证。
5. 提交是独立闸门：用户要求提交时，无论是否纯文档，提交前必须执行 `detect_changes()`，并结合 `git status`、`git diff` 和阶段允许范围判断实际影响。
6. 同一仓库的 `impact`、`context`、`detect-changes` 和索引操作串行执行，避免 LadybugDB 文件锁；需要分析多个 symbols 时逐项运行或由同一进程顺序编排，不并发打开图数据库。
7. 新增 symbol 没有既有 impact 目标时，记录该事实，分析已有调用入口和契约；尚无任何代码的初始化任务以设计、源码搜索、目标测试和构建建立基线，不伪造 impact 结果。代码形成后完成索引和适用变更检查。

## 2. HIGH/CRITICAL 边界审查机制

impact 或 `detect_changes()` 返回 `HIGH`、`CRITICAL` 时，先进行影响审查，不因等级本身自动停止。

满足以下条件时可以继续修改：

1. 受影响文件、symbols 和执行流程均属于当前阶段或当前已批准的多阶段范围。
2. 影响是实现目标所必需的预期传播，而不是偶然扩散。
3. 直接调用方、公共契约和受影响流程具有可执行的验证面。
4. 修改具有明确必要性，且能够通过目标测试、影响范围测试、构建、契约检查或页面验收验证。
5. 工作区包含多个阶段的累积修改时，能够将每项影响归属到已批准阶段；聚合风险等级不得单独作为阻断理由。

出现以下任一情况时，才停止并请求项目负责人决策：

1. 出现无法归属或计划外的跨阶段影响。
2. 需要改变公共 API、OpenAPI、领域事件、数据库公共结构、权限、数据范围或共享基础设施行为，且未在当前范围获批。
3. 继续操作可能造成破坏性数据修改、安全问题、用户已有修改丢失或不可逆外部影响。
4. 缺少足以覆盖关键调用方或执行流程的验证面，无法合理判断回归风险。
5. 完成索引恢复、符号消歧和补充验证后，仍无法确认影响边界。

风险报告应说明风险等级、直接调用方、受影响流程、当前阶段归属、验证方案和是否触发停止条件，不能只报告 `HIGH` 或 `CRITICAL` 标签。

## 3. 索引恢复与符号消歧

发现索引陈旧、目标未命中或结果不明确时，按以下顺序自动恢复：

1. 在项目根目录执行 `gitnexus status`，确认索引状态和新鲜度。
2. 已有代码且索引陈旧、缺失或无法覆盖近期代码时，在本项目根目录执行 `gitnexus analyze . --name Dy.MedicalRecognition --index-only`。保持 `.gitnexusrc` 的 `skipAgentsMd: true`；不使用 `--skills`、`--self-commit`，不自动生成技能或改写规则。
3. 重新执行 query、context 或 impact。
4. 同名 symbol 存在歧义时，使用 `file`、`kind` 或 `uid` 缩小目标；重建索引不能替代符号消歧。
5. DI、反射、配置驱动、动态路由或跨服务调用无法被静态图完整覆盖时，补充源码搜索、OpenAPI 或事件契约检查、编译和测试。
6. 自动恢复和补充验证后仍无法确认是否越过阶段边界时，才停止并请求项目负责人决策。

索引暂时不可用不自动阻断低风险文档工作或不涉及 symbol 的任务。涉及代码修改时，只有无法通过恢复、源码和验证面可靠确认影响边界，才构成阻断。

## 4. 阶段实施与批量修复

1. impact 在修复批次形成后、修改代码前执行，避免对尚未确定的候选问题反复分析。
2. 同一批准批次中，多个 symbols 属于同一共同根因、项目/能力目录、公共契约预期和验证面时，可以串行集中执行 upstream impact，并汇总直接调用方、执行流程、风险等级和统一停止条件；不要求按文件或方法建立独立批次。
3. 普通问题和可归属的高风险影响不打断完整审查或测试轮次；只有命中停止条件时才提前处理中断。
4. GitNexus 风险等级不能替代当前阶段规定的目标测试、回归矩阵、构建、契约检查或宿主页面验收。
5. 每轮根据实际影响、验证结果和未覆盖风险调整下一批；阶段报告的位置和更新规则遵循 [Planning and Evidence](planning-and-evidence.md) 与 [Testing](testing.md)。
6. 出现不同业务/错误/可信范围、不同公共契约或数据库边界、不同 HIGH/CRITICAL 执行流程、不同停止条件，或无法用同一任务局部 diff 归属时，必须拆分 impact 和执行批次。集中 impact 仍须逐个消歧目标 symbol，不得用一次类级结果掩盖同名方法或动态绑定边界。
7. 同一批准批次内的命名或等价重构可以集中记录 impact 并共享验证；Domain、Repository、HTTP 适配器和 Query 能力仅因命名相同不能合并，除非调用面、停止条件和局部 diff 都可共同归属。

同一批准批次的每个目标 symbol 仍须串行完成 upstream impact，但可作为一次集中分析和一次验证计划记录。`HIGH`/`CRITICAL` 必须明确 blast radius、验证面和停止条件，不因风险等级本身退化为逐文件 impact、测试或审查循环；只有执行流程、公共契约或停止条件不同才拆分。

## 5. 提交前检查

当前工作分支为 `main`，跟踪 `origin/main`；不能据此假定所有任务的比较基线。执行前核实用户指定基线、分支及远端配置，不沿用其他项目的 `master`，不把当前分支自动当作完整变更的比较起点。

1. 执行 `detect_changes()`；需要审查相对默认分支的整体变化时使用 compare 范围和正确的基准分支。
2. 将 GitNexus 可解析的 symbols 和执行流程与 `git status --short`、`git diff --stat`、当前阶段清单进行交叉核对。
3. 多阶段累积工作区返回 `HIGH` 或 `CRITICAL` 时，检查每项影响能否归属到已批准阶段，以及相应验证是否完成。
4. 发现意外跨阶段影响、公共契约变化或无法解释的文件时，不提交，先完成边界确认或请求项目负责人决策。
5. `detect_changes()` 只覆盖其能够解析的代码图，不得用它代替文档差异、SQL、生成物、运行时配置和宿主页面检查。
6. 审查目录移动、删除后重建或未跟踪目标文件时，同时检查 `git status --short`、已跟踪文件 `git diff`、未跟踪目标文件实际内容和 `detect_changes()`；不得因目标文件尚未跟踪而仅依赖 `git diff` 判断内容未变化。
